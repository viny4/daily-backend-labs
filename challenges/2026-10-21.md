## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee expenses. A core feature is the ability for company administrators to view and approve expense reports. The `expense_reports` table has grown to hundreds of millions of rows, with each report containing details like employee ID, submission date, total amount, status, and associated line items (stored in a separate `expense_report_items` table).

A critical page for administrators is the "Pending Approvals" dashboard, which shows a paginated list of all expense reports awaiting their approval. This query filters by `company_id`, `status='pending'`, and orders by `submission_date DESC`. It's executed frequently by thousands of administrators across different companies.

Recently, as the number of active companies and pending reports has scaled, administrators are reporting that the "Pending Approvals" dashboard takes an unacceptably long time to load, often 5-10 seconds, and sometimes even longer during peak hours. Database load is also spiking when these dashboards are heavily used, impacting other critical operations. The primary bottleneck has been identified as the database query to fetch these paginated results.

## Requirements

The primary goal is to significantly reduce the load time for the "Pending Approvals" dashboard for administrators, aiming for a response time under 500ms even during peak usage, without substantially increasing database load. You need to leverage Redis to cache these results effectively.

Consider the following constraints:

*   **Scale:** Millions of expense reports, thousands of active administrators, hundreds of `company_id`s.
*   **Freshness:** While near real-time is good, it's acceptable for the list of pending approvals to be up to 10-15 seconds stale. Approvals happen somewhat asynchronously, and a slight delay in seeing a report disappear from the pending list is tolerated.
*   **Concurrency:** Many administrators from the same company might be viewing the dashboard simultaneously.
*   **Multi-tenancy:** Caching must be isolated per `company_id`. An administrator from Company A should not see Company B's reports.
*   **Pagination:** The dashboard displays paginated results (e.g., 20 reports per page). The solution must efficiently handle requests for different pages.
*   **Dynamic Nature:** Reports are constantly being submitted, approved, or rejected, changing their `status`. This means the cached data needs to be invalidated or updated.

### 1. Python function to retrieve paginated pending expense reports

This function uses a "cache-aside" pattern. It first checks Redis. If the data is not found or is stale, it fetches from the database, stores it in Redis, and then returns it.

### 2. Cache Population and Pagination Strategy

**Strategy:** "Full List Caching" with individual report details embedded.

1.  **Cache Key:** For each `company_id`, a unique Redis key is used: `company:{company_id}:pending_reports:list` to store the ordered list of pending report objects, and `company:{company_id}:pending_reports:total` for the total count. This ensures multi-tenancy.
2.  **Cache Check:** When a request for `(company_id, page)` comes in, the system first checks if `company:{company_id}:pending_reports:list` exists in Redis.
3.  **Cache Hit:**
    *   If the key exists, retrieve the entire JSON-serialized list of reports and the total count.
    *   Deserialize the list.
    *   Calculate the `start_index` and `end_index` based on the requested `page` and `PAGE_SIZE`.
    *   Slice the deserialized list to get the reports for the specific page.
    *   Return the sliced list.
4.  **Cache Miss/Stale:**
    *   If the key does not exist (cache miss) or its TTL has expired (stale), the system queries the database.
    *   The database query fetches *all* pending expense reports for the given `company_id`, ordered by `submission_date DESC`. This query is optimized by the `idx_company_status_submission_date` index.
    *   The results (full report objects, not just IDs) are then JSON-serialized into a single string.
    *   This serialized string is stored in Redis under `company:{company_id}:pending_reports:list` with an appropriate `EXPIRE` (TTL) of 15 seconds. The total count is stored in `company:{company_id}:pending_reports:total` with the same TTL.
    *   The requested page is then extracted from this newly fetched and cached data and returned.

**Trade-offs:**
*   **Pros:** Simple to implement, efficient for subsequent page requests (no DB hit), good for concurrent access to different pages for the same company. Reduces database load significantly.
*   **Cons:** If the list of pending reports is very large (e.g., hundreds of thousands for a single company), storing the *full serialized objects* in a single Redis key can consume a lot of memory and bandwidth for serialization/deserialization. This is the primary scaling bottleneck for this specific implementation. A better approach for truly massive lists would be to store only report *IDs* in the list, and cache individual report details in a Redis Hash (`report:{id}`) or separate String keys, then use `MGET` or a pipeline to fetch details for the page's IDs. For the given scale (hundreds of millions of reports *total*, but pending reports for a *single company* might be in the thousands, not millions), storing full objects might be acceptable, but it's a known limitation.

### 3. Cache Invalidation/Update Strategy

The primary strategy for cache invalidation is **Time-To-Live (TTL)**.

**Strategy:**

1.  **TTL-based Expiration:** As implemented, each cached list of pending reports (`company:{company_id}:pending_reports:list` and `company:{company_id}:pending_reports:total`) is given a TTL of `REDIS_TTL_SECONDS` (e.g., 15 seconds). This satisfies the freshness requirement that data can be up to 10-15 seconds stale. When the TTL expires, the key is automatically removed by Redis, and the next request will result in a cache miss, triggering a fresh database fetch.

2.  **Proactive Invalidation (on status change):**
    When an expense report's status changes (e.g., from `pending` to `approved` or `rejected`), it should no longer appear in the "Pending Approvals" dashboard. To ensure this change is reflected quickly, we proactively invalidate the relevant cache entry.

    ```python
    # Pseudocode for an approval/rejection service
    def approve_expense_report(report_id: str, company_id: str, approver_id: str):
        # 1. Update database
        conn = get_db_connection()
        try:
            cur = conn.cursor()
            cur.execute(
                """
                UPDATE expense_reports
                SET status = 'approved', approved_by = %s, approval_date = NOW()
                WHERE id = %s AND company_id = %s;
                """,
                (approver_id, report_id, company_id)
            )
            conn.commit()
            print(f"Report {report_id} for company {company_id} approved in DB.")

            # 2. Invalidate Redis cache for this company
            cache_key_list = f"company:{company_id}:pending_reports:list"
            cache_key_total = f"company:{company_id}:pending_reports:total"
            
            # Use DEL to immediately remove the cache entry
            redis_client.delete(cache_key_list, cache_key_total)
            print(f"Invalidated cache for company {company_id}.")

        except Exception as e:
            conn.rollback()
            print(f"Error approving report {report_id}: {e}")
            raise
        finally:
            conn.close()

    # Similar function for reject_expense_report
    ```

**Combined Strategy:**
The system uses a hybrid approach:
*   **Primary:** TTL-based expiration handles eventual consistency and ensures freshness within the acceptable window without explicit invalidation for every minor change. This is the "fire and forget" mechanism.
*   **Secondary:** Proactive invalidation (using `DEL`) is triggered immediately upon a status change for an expense report. This ensures that approved/rejected reports disappear from the pending list much faster than waiting for the TTL to expire, improving user experience for critical actions.

### 4. Justification for Chosen Redis Data Structure(s)

*   **Redis String (JSON-encoded list):** For `company:{company_id}:pending_reports:list`.
    *   **Why:** A Redis String can store a JSON-encoded list of report objects (or IDs). This is simple to manage as a single atomic unit for a given company's pending reports. When a cache miss occurs, the entire list is fetched from the DB, serialized, and stored. When a cache hit occurs, the entire list is retrieved, deserialized, and then sliced for pagination. This works well for lists that are not excessively large (e.g., up to a few thousand reports).
    *   **Alternative (and better for very large lists):** For `company:{company_id}:pending_reports:list`, store a Redis **List** of *report IDs* (e.g., `LPUSH` or `RPUSH` IDs). Then, for individual report details, use Redis **Hashes** (e.g., `HSET report:{id} field1 value1 field2 value2`) or individual **Strings** (e.g., `SET report:{id} JSON_DATA`). When a page is requested, `LRANGE` the IDs, then `MGET` (for Strings) or `HMGET` (for Hashes) the details for those IDs. This is more memory-efficient as report details are stored once, and the list only contains lightweight IDs. It also allows updating individual report details without re-fetching the entire list. The current implementation chose the simpler JSON-encoded String for the exercise's scope, acknowledging the memory/bandwidth trade-off for very large lists.
*   **Redis String (Total Count):** For `company:{company_id}:pending_reports:total`.
    *   **Why:** A simple String is sufficient to store the integer count of pending reports. It's fetched and updated alongside the list of reports, ensuring consistency.

### Going Further: Potential Pitfalls and Race Conditions

**Scenario:** Multiple backend instances processing approvals concurrently.

Consider the following sequence of events:

1.  **Instance A** receives a request to approve `report_X` for `company_C`.
2.  **Instance A** updates `report_X` status to `approved` in the database.
3.  **Instance A** sends a `DEL` command to Redis for `company:C:pending_reports:list`.
4.  **Instance B** simultaneously receives a request for `company_C`'s pending reports (e.g., an admin refreshes the dashboard).
5.  **Instance B** checks Redis for `company:C:pending_reports:list`.
    *   **Race Condition 1: Stale Read after Invalidation:** If Instance B's request happens *after* Instance A's `DEL` but *before* Instance A's database commit (or if the database commit is slow), Instance B will see a cache miss, query the database, and potentially fetch a list that *still includes* `report_X` (if the DB transaction hasn't committed yet). Instance B then populates the cache with this stale data, effectively re-introducing `report_X` to the pending list in Redis.
    *   **Race Condition 2: Overwriting Fresh Data:** If Instance B's request happens *before* Instance A's `DEL`, Instance B might fetch fresh data from the DB (which correctly excludes `report_X` if the DB commit was fast enough). However, if Instance A's `DEL` then executes, it invalidates this fresh data. This isn't as critical as Race Condition 1, but it causes an unnecessary cache miss for the next request.

**Mitigation Strategies:**

1.  **"Cache-Aside with Write-Through" (or "Write-Invalidate") Pattern with Database Transaction Atomicity:**
    *   **Principle:** The cache invalidation should ideally be part of the same atomic transaction as the database write. If the database update fails, the cache should not be invalidated.
    *   **Implementation:**
        *   When approving/rejecting a report:
            1.  Start a database transaction.
            2.  Update the report status in the database.
            3.  **Commit the database transaction.**
            4.  **ONLY THEN** send the `DEL` command to Redis.
        *   This ensures that the `DEL` only happens if the database change is successful and visible.
        *   **Mitigates Race Condition 1:** By committing the DB transaction *before* invalidating, we ensure that any subsequent DB read (from a cache miss) will see the updated state. The window for reading stale data from the DB is minimized to the time between DB commit and `DEL` command execution, which is typically very small.

2.  **Delayed Invalidation (Less Ideal for Freshness):**
    *   **Principle:** Instead of `DEL`, set a very short TTL (e.g., 1-2 seconds) on the key.
    *   **Pros:** Simpler, avoids some race conditions where `DEL` might happen too early.
    *   **Cons:** Introduces a guaranteed delay for the change to be reflected, even if the database is updated immediately. This might not meet the "quickly reflected" expectation for critical actions.

3.  **Optimistic Locking / Versioning (More Complex):**
    *   **Principle:** Add a version number to the cached data. When fetching from the DB, also fetch a version number. When writing to Redis, include this version. When invalidating, if a new version is already in Redis, don't delete it.
    *   **Complexity:** This significantly complicates the cache management logic and requires careful handling of version numbers across the DB and Redis. Generally overkill for this specific problem where TTL and proactive `DEL` after DB commit are sufficient.

**Chosen Mitigation for this problem:**

The most effective and practical mitigation for the given requirements is to ensure the **database transaction commits successfully *before* the Redis `DEL` command is issued.**

```python
# Refined approve_expense_report function for better race condition handling
def approve_expense_report_mitigated(report_id: str, company_id: str, approver_id: str):
    conn = None
    try:
        conn = get_db_connection()
        cur = conn.cursor()

        # 1. Start DB transaction and update status
        cur.execute(
            """
            UPDATE expense_reports
            SET status = 'approved', approved_by = %s, approval_date = NOW()
            WHERE id = %s AND company_id = %s;
            """,
            (approver_id, report_id, company_id)
        )
        
        # 2. Commit DB transaction
        conn.commit()
        print(f"Report {report_id} for company {company_id} approved and DB committed.")

        # 3. ONLY THEN, invalidate Redis cache
        cache_key_list = f"company:{company_id}:pending_reports:list"
        cache_key_total = f"company:{company_id}:pending_reports:total"
        redis_client.delete(cache_key_list, cache_key_total)
        print(f"Invalidated cache for company {company_id} after DB commit.")

    except Exception as e:
        if conn:
            conn.rollback() # Rollback if anything goes wrong before commit
        print(f"Error approving report {report_id}: {e}")
        raise
    finally:
        if conn:
            conn.close()
```

This sequence minimizes the window where a cache miss could lead to fetching stale data from the database. The `DEL` command is very fast, so the time between DB commit and cache invalidation is usually negligible. The existing TTL on the cache also acts as a safety net, ensuring that even if a race condition leads to stale data being re-cached, it will only persist for a maximum of 15 seconds.
