## Worked answer

### 1. Caching Mechanism Outline

The core idea is to store the JSON-serialized list of reviews for a given product directly in Redis. When a request comes in, we first check Redis. If the data is present and valid, we return it immediately. Otherwise, we fetch from the database, store it in Redis, and then return it.

**Redis Key Structure:**

We'll use a simple key structure that uniquely identifies the product reviews.

*   **Key format:** `product_reviews:{product_id}`
*   **Example:** `product_reviews:12345`

**Redis Data Type:**

We will use the **String** data type to store the JSON-serialized list of review dictionaries.

*   **Data stored:** A JSON string representing a list of review objects. Each review object will include `id`, `user_id`, `username`, `rating`, `comment`, and `created_at`.

**Example Redis entry:**

```
SET product_reviews:12345 "[{\"id\": 1, \"user_id\": 101, \"username\": \"alice\", \"rating\": 5, \"comment\": \"Great product!\", \"created_at\": \"2023-01-01T10:00:00Z\"}, {\"id\": 2, \"user_id\": 102, \"username\": \"bob\", \"rating\": 4, \"comment\": \"Good value.\", \"created_at\": \"2023-01-02T11:00:00Z\"}]" EX 3600
```

**Cache Expiration:**

We will use a Time-To-Live (TTL) for cache entries.

*   **Initial TTL:** 1 hour (3600 seconds). This provides a balance between data freshness and cache hit rate. Since reviews are "relatively static," an hour is a reasonable starting point. This TTL will be used with the `EX` option on the `SET` command.

### 2. Cache Invalidation Strategy

Cache invalidation is crucial to ensure users always see the most up-to-date reviews. When a new review is submitted for a product, the corresponding cached entry for that product's reviews must be removed or updated.

**Trigger for Invalidation:**

The invalidation should be triggered immediately after a new review is successfully persisted to the database.

**Mechanism:**

1.  **Database Write:** When a new review is created (e.g., via a `POST /api/v1/products/{product_id}/reviews` endpoint), the application first writes the review to the `reviews` and potentially `users` tables.
2.  **Cache Deletion:** Immediately after the successful database write, the application sends a `DEL` command to Redis for the specific product's review cache key.

**Example Python/Django code for review submission:**

```python
import json
import redis
from django.db import transaction
from django.http import JsonResponse
from django.views.decorators.http import require_POST
from .models import Product, Review, User # Assuming these models exist

# Initialize Redis client (e.g., in settings.py or a utility module)
redis_client = redis.StrictRedis(host='localhost', port=6379, db=0)

@require_POST
def submit_review(request, product_id):
    try:
        product = Product.objects.get(id=product_id)
        data = json.loads(request.body)
        user_id = data.get('user_id') # In a real app, this would come from authenticated user
        rating = data.get('rating')
        comment = data.get('comment')

        # Basic validation
        if not all([user_id, rating, comment]):
            return JsonResponse({'error': 'Missing required fields'}, status=400)

        with transaction.atomic():
            # Create the new review in the database
            review = Review.objects.create(
                product=product,
                user_id=user_id,
                rating=rating,
                comment=comment
            )
            # Potentially update product's average rating, etc.

            # Invalidate the cache for this product's reviews
            cache_key = f'product_reviews:{product_id}'
            redis_client.delete(cache_key)
            print(f"Cache invalidated for key: {cache_key}")

        return JsonResponse({'message': 'Review submitted successfully', 'review_id': review.id}, status=201)

    except Product.DoesNotExist:
        return JsonResponse({'error': 'Product not found'}, status=404)
    except json.JSONDecodeError:
        return JsonResponse({'error': 'Invalid JSON'}, status=400)
    except Exception as e:
        # Log the error
        return JsonResponse({'error': 'An unexpected error occurred'}, status=500)

```

This "write-through with invalidation" strategy ensures that the next read request for that product's reviews will miss the cache, fetch the fresh data from the database (including the new review), and then populate the cache with the updated information.

### 3. Strategy to Prevent Cache Stampedes (Thundering Herd)

A "thundering herd" or cache stampede occurs when a popular cache entry expires, and many concurrent requests simultaneously try to fetch the data from the database, overwhelming it. We can mitigate this using a **lock-based approach** combined with a short **randomized expiration jitter**.

**Mechanism: Distributed Lock with `SET NX EX`**

1.  **Lock Key:** For each product, we'll introduce a separate Redis key to act as a distributed lock.
    *   **Lock Key format:** `product_reviews_lock:{product_id}`
    *   **Example:** `product_reviews_lock:12345`

2.  **`SET NX EX` for Locking:** When a cache miss occurs, the first request attempts to acquire a lock using `SET product_reviews_lock:{product_id} 1 EX 10 NX`.
    *   `NX`: Only set the key if it does not already exist (acquire the lock).
    *   `EX 10`: Set an expiration of 10 seconds for the lock. This is a safety mechanism to prevent deadlocks if the application crashes while holding the lock.

3.  **Lock Acquisition Logic:**
    *   **If lock acquired (SET NX returns true):** This request becomes the "cache rebuilder." It fetches data from the database, updates the main `product_reviews:{product_id}` cache key, and then releases the lock (or lets it expire).
    *   **If lock not acquired (SET NX returns false):** Another request is already rebuilding the cache. This request should wait briefly and then retry reading from the cache. A short, randomized backoff (e.g., 50-200ms) can prevent all waiting requests from retrying simultaneously.

**Randomized Expiration Jitter:**

To prevent many popular keys from expiring at the exact same moment (e.g., if they were all populated at the same time), we can add a small random jitter to the TTL when setting the cache.

*   Instead of `EX 3600`, use `EX (3600 + random_int(-300, 300))`. This spreads out the expiration times, reducing the likelihood of a massive stampede for multiple keys.

**Detailed Flow for `/api/v1/products/{product_id}/reviews`:**

1.  **Check Cache:**
    *   `GET product_reviews:{product_id}`
    *   **If hit:** Return cached data.
    *   **If miss:** Proceed to acquire lock.

2.  **Acquire Lock:**
    *   `SET product_reviews_lock:{product_id} 1 EX 10 NX`
    *   **If lock acquired (returns `True`):**
        *   Fetch reviews from the database (including `username` via join).
        *   Serialize reviews to JSON.
        *   Calculate a randomized TTL (e.g., 3600 + random_int(-300, 300)).
        *   `SET product_reviews:{product_id} <json_data> EX <randomized_ttl>`
        *   `DEL product_reviews_lock:{product_id}` (release lock explicitly, though it will expire anyway).
        *   Return data.
    *   **If lock not acquired (returns `False`):**
        *   Wait for a short, random duration (e.g., `time.sleep(random.uniform(0.05, 0.2))`).
        *   **Retry Check Cache:** Go back to step 1 (check cache again). This time, the cache rebuilder should have populated the cache, leading to a cache hit. If, for some reason, the cache is still empty after a few retries (e.g., rebuilder failed), the request might eventually proceed to acquire the lock itself if it expires.

This approach ensures only one request rebuilds the cache, while others wait briefly and then benefit from the newly populated cache.

### 4. Integration into Python/Django View

Here's how the caching logic would be integrated into the existing Django view.

```python
import json
import redis
import time
import random
from django.http import JsonResponse
from django.views.decorators.http import require_GET
from django.db.models import F # For efficient join in Django ORM
from .models import Product, Review, User # Assuming these models exist

# Initialize Redis client (e.g., in settings.py or a utility module)
# Ensure your Redis client is configured correctly for your environment
redis_client = redis.StrictRedis(host='localhost', port=6379, db=0, decode_responses=True)

# Cache settings
CACHE_TTL_SECONDS = 3600 # 1 hour
LOCK_TTL_SECONDS = 10    # 10 seconds for the distributed lock
RETRY_WAIT_MIN_MS = 50   # Minimum wait for cache stampede retry
RETRY_WAIT_MAX_MS = 200  # Maximum wait for cache stampede retry
MAX_RETRIES = 3          # Max attempts to read from cache during stampede

@require_GET
def get_product_reviews(request, product_id):
    cache_key = f'product_reviews:{product_id}'
    lock_key = f'product_reviews_lock:{product_id}'

    for attempt in range(MAX_RETRIES + 1): # +1 to allow initial check + MAX_RETRIES
        # 1. Try to fetch from cache
        cached_data = redis_client.get(cache_key)
        if cached_data:
            # Cache hit! Deserialize and return.
            return JsonResponse(json.loads(cached_data), safe=False)

        # Cache miss. Proceed to acquire lock to rebuild cache.
        # Only the first attempt should try to acquire the lock.
        if attempt == 0:
            # 2. Try to acquire a distributed lock
            # SET NX EX returns True if lock was acquired, False otherwise
            lock_acquired = redis_client.set(lock_key, 1, ex=LOCK_TTL_SECONDS, nx=True)

            if lock_acquired:
                # This request is the cache rebuilder
                try:
                    # 3. Fetch data from the database
                    # Optimized query: Select related user data in one go
                    reviews_queryset = Review.objects.filter(product_id=product_id).select_related('user').order_by('-created_at')

                    # Serialize reviews, including username from the joined User model
                    reviews_list = []
                    for review in reviews_queryset:
                        reviews_list.append({
                            'id': review.id,
                            'user_id': review.user.id, # Assuming 'user' is the related_name or default
                            'username': review.user.username,
                            'rating': review.rating,
                            'comment': review.comment,
                            'created_at': review.created_at.isoformat() # ISO 8601 format
                        })

                    json_data = json.dumps(reviews_list)

                    # 4. Store data in cache with randomized TTL
                    jitter = random.randint(-300, 300) # +/- 5 minutes
                    ttl_with_jitter = CACHE_TTL_SECONDS + jitter
                    redis_client.set(cache_key, json_data, ex=ttl_with_jitter)
                    print(f"Cache rebuilt for {cache_key} with TTL {ttl_with_jitter}s")

                    return JsonResponse(reviews_list, safe=False)

                except Product.DoesNotExist:
                    # If product doesn't exist, cache an empty list or a specific "not found" marker
                    # For simplicity, we'll just let it return 404 later if no reviews are found
                    # or cache an empty list if the product exists but has no reviews.
                    # If the product_id itself is invalid, the filter will return empty.
                    pass # Handled by returning empty list or 404 below

                finally:
                    # 5. Release the lock (optional, as it has a TTL, but good practice)
                    # Use a Lua script for atomic deletion if the lock value matches to prevent
                    # deleting a lock set by another process if this one took too long.
                    # For simplicity here, we just DEL, relying on TTL for safety.
                    redis_client.delete(lock_key)
            else:
                # Lock not acquired: another request is rebuilding the cache.
                # Wait a bit and retry reading from cache.
                wait_time_ms = random.uniform(RETRY_WAIT_MIN_MS, RETRY_WAIT_MAX_MS)
                time.sleep(wait_time_ms / 1000.0) # Convert ms to seconds
                print(f"Lock not acquired for {cache_key}, waiting {wait_time_ms:.2f}ms and retrying...")
        else:
            # Subsequent attempts after the first one should only retry reading from cache
            # if the lock was not acquired. If this is reached, it means the lock was not
            # acquired on the first attempt, and we are now retrying to read.
            wait_time_ms = random.uniform(RETRY_WAIT_MIN_MS, RETRY_WAIT_MAX_MS)
            time.sleep(wait_time_ms / 1000.0) # Convert ms to seconds
            print(f"Retrying cache read for {cache_key} after wait {wait_time_ms:.2f}ms (attempt {attempt}/{MAX_RETRIES})...")


    # If we reach here, it means cache miss, failed to acquire lock multiple times,
    # or the cache rebuilder failed to populate the cache within the retry window.
    # As a fallback, we could try fetching from DB one last time without a lock,
    # but that risks stampede. A better approach is to return a temporary error
    # or an empty list, allowing the next request to try again.
    # For this exercise, we'll do a final DB fetch if all else fails,
    # but in a production system, consider a circuit breaker or returning stale data.

    # Fallback: Final attempt to fetch from DB if all retries failed (risks stampede if many requests hit here)
    try:
        reviews_queryset = Review.objects.filter(product_id=product_id).select_related('user').order_by('-created_at')
        reviews_list = []
        for review in reviews_queryset:
            reviews_list.append({
                'id': review.id,
                'user_id': review.user.id,
                'username': review.user.username,
                'rating': review.rating,
                'comment': review.comment,
                'created_at': review.created_at.isoformat()
            })
        # Note: We don't cache here to avoid re-triggering stampede if the previous attempt failed
        # and we don't want to overwrite a potentially good cache entry from another rebuilder.
        return JsonResponse(reviews_list, safe=False)
    except Product.DoesNotExist:
        return JsonResponse({'error': 'Product not found'}, status=404)
    except Exception as e:
        # Log the error
        return JsonResponse({'error': 'Failed to retrieve reviews after multiple attempts'}, status=500)

```

**Explanation of Integration:**

*   **`redis_client`:** An initialized Redis client is used for all Redis operations. `decode_responses=True` is useful to automatically decode Redis responses from bytes to strings.
*   **`cache_key` and `lock_key`:** Defined based on `product_id`.
*   **Cache Hit:** If `redis_client.get(cache_key)` returns data, it's immediately deserialized and returned, achieving the target P95 latency.
*   **Cache Miss & Lock Acquisition:**
    *   `redis_client.set(lock_key, 1, ex=LOCK_TTL_SECONDS, nx=True)` is the core of the stampede prevention. It atomically attempts to set the lock key only if it doesn't exist, with a short expiration.
    *   If `lock_acquired` is `True`, the current request is responsible for fetching data from the DB.
    *   **Database Query:** `Review.objects.filter(...).select_related('user')` is used to fetch reviews and their associated usernames efficiently in a single query, minimizing DB round trips.
    *   **Serialization:** The fetched data is serialized into a list of dictionaries, then `json.dumps()` converts it to a JSON string.
    *   **Cache Population:** `redis_client.set(cache_key, json_data, ex=ttl_with_jitter)` stores the fresh data with a randomized TTL.
    *   **Lock Release:** `redis_client.delete(lock_key)` explicitly releases the lock.
*   **Lock Not Acquired (Waiting for Rebuilder):** If `lock_acquired` is `False`, it means another process is already rebuilding the cache. The current request waits for a random short period (`time.sleep`) and then retries fetching from the cache. This prevents a stampede. `MAX_RETRIES` prevents infinite waiting.
*   **Error Handling:** Basic error handling is included for `Product.DoesNotExist` and general exceptions.

**Trade-offs and What Breaks at 10x Scale:**

*   **Trade-off: Eventual Consistency:** The cache is eventually consistent. There's a brief window between a new review being submitted and the cache being invalidated/rebuilt where the old data might still be served. This is generally acceptable for reviews.
*   **Trade-off: Redis as a Single Point of Failure:** If the Redis instance goes down, all requests will hit the database, leading to a massive stampede and potential database overload. A robust Redis setup (e.g., Sentinel or Cluster) is essential.
*   **Trade-off: Increased Complexity:** Adding caching and distributed locks increases the complexity of the application code and introduces a new dependency (Redis).
*   **What breaks at 10x scale (10,000s RPS for popular products):**
    *   **Redis Network I/O:** While Redis is fast, at extreme scales, the network bandwidth between application servers and Redis could become a bottleneck if review payloads are very large.
    *   **Redis CPU:** If many products have very large numbers of reviews (e.g., 1000s of reviews per product), and these are frequently updated (leading to cache invalidations and rebuilds), Redis's single-threaded nature might become a bottleneck for JSON serialization/deserialization if it were doing that work (which it isn't here, the app server does). Here, the bottleneck would be the sheer volume of `GET` and `SET` commands.
    *   **Application Server CPU (Deserialization):** Even with caching, deserializing large JSON payloads on every request can still consume significant CPU, especially if the `reviews_list` for popular products becomes enormous (e.g., thousands of reviews). The problem statement mentions this as an existing issue. This solution moves the *serialization* to the cache-rebuilding path, but *deserialization* still happens on every cache hit.
    *   **Lock Contention:** While the stampede prevention helps, if the cache rebuild time is consistently longer than the `LOCK_TTL_SECONDS` or if there are many concurrent cache invalidations, there could still be contention on the locks, leading to more requests hitting the database or waiting.
    *   **Memory Usage in Redis:** Storing 50 million reviews for potentially millions of products, even if only popular ones are cached, can consume significant Redis memory. If average review size is 200 bytes and a product has 100 reviews, that's 20KB per product. 100,000 popular products would be 2GB. This needs monitoring.

### Going Further: Trade-offs for Redis Data Structure

When choosing the **String** data type for storing JSON-serialized review lists, I considered the following trade-offs:

**Advantages of String (JSON):**

1.  **Simplicity:** It's straightforward to implement. The application fetches data, serializes it once, stores it, and retrieves it as a whole.
2.  **Atomic Operations:** `SET` and `GET` operations on strings are atomic, ensuring data consistency for the entire review list.
3.  **Reduced Network Round Trips:** For the common use case of fetching *all* reviews for a product, retrieving a single string is highly efficient, minimizing network latency between the application and Redis.
4.  **Application-Level Control:** The application fully controls the serialization format, allowing for complex objects and easy integration with existing ORM output.

**Disadvantages of String (JSON):**

1.  **Partial Updates are Expensive:** If we needed to update just one review's comment or rating, we would have to fetch the entire JSON string, deserialize it, modify the specific review, re-serialize the entire list, and then store it back. This is inefficient and can lead to race conditions if not handled carefully (e.g., using optimistic locking or Lua scripts).
2.  **Increased Application Server CPU for Deserialization:** As noted in the problem, "serializing and deserializing large review payloads on the application servers contributes to high CPU usage." While caching moves *serialization* to the less frequent cache-rebuild path, *deserialization* still happens on every cache hit. If review lists are very large, this can still be a bottleneck.
3.  **No Redis-Native Querying/Filtering:** Redis cannot directly query or filter within the JSON string. If we needed to fetch reviews by a specific rating, or only reviews from a certain user for a product, we'd have to fetch the entire list and filter it in the application, negating some benefits.

**Under what conditions might a different data structure be more appropriate, and why?**

1.  **Hash (HSET/HGETALL):**
    *   **Structure:** `product_reviews:{product_id}` as a Hash, where each field is `review_id` and the value is the JSON-serialized single review object.
    *   **When appropriate:**
        *   **Frequent Partial Updates:** If individual reviews are frequently updated (e.g., an admin edits a comment), `HSET` allows updating a single review without touching others.
        *   **Fetching Individual Reviews:** If the API frequently needs to fetch a *single* review by its ID (`/api/v1/products/{product_id}/reviews/{review_id}`), `HGET` is efficient.
        *   **Moderately Sized Review Lists:** For products with a few hundred reviews, `HGETALL` (to fetch all reviews) is still efficient.
    *   **Why:** `HSET` provides O(1) access for individual fields. It allows for more granular caching and invalidation.
    *   **Trade-offs:** `HGETALL` still retrieves all fields, but Redis handles the parsing of individual review objects, potentially reducing application-side deserialization for the *entire list* if only a subset is needed. However, fetching *all* reviews still means multiple small objects over the network, which might be slightly less efficient than one large string for `GET ALL`.

2.  **Sorted Set (ZADD/ZRANGE):**
    *   **Structure:** `product_reviews:{product_id}` as a Sorted Set, where the `member` is the JSON-serialized review and the `score` is `created_at` (timestamp) or `rating`.
    *   **When appropriate:**
        *   **Ordering/Paging:** If the API frequently needs to fetch reviews ordered by `created_at` (newest first) or `rating` (highest first), or if it needs to support pagination (e.g., "give me reviews 10-20"), `ZRANGE` or `ZREVRANGE` is ideal.
        *   **Filtering by Score Range:** If filtering by rating range (e.g., "all 5-star reviews") is common, `ZRANGEBYSCORE` can be used.
    *   **Why:** Sorted Sets are designed for ordered data and range queries, which are very common for lists like reviews.
    *   **Trade-offs:** More complex to manage than a simple string. Updates to individual reviews still require removing and re-adding the member. Storing the full JSON in the member can be memory-intensive if reviews are large and many.

3.  **List (LPUSH/LRANGE):**
    *   **Structure:** `product_reviews:{product_id}` as a List, where each element is a JSON-serialized review.
    *   **When appropriate:**
        *   **Simple FIFO/LIFO:** If reviews were only ever added to one end and fetched from the other (e.g., a feed), or if simple pagination by index was sufficient.
    *   **Why:** Lists are good for simple queues or ordered collections where elements are added/removed from ends.
    *   **Trade-offs:** Not suitable for this scenario because arbitrary access, updates, or ordering by specific fields (like `created_at` or `rating`) are inefficient or impossible without fetching the entire list. `LRANGE 0 -1` would fetch all, similar to a string, but without the atomic `SET` for the whole list.

**Conclusion on Data Structure Choice:**

For the given scenario, where the primary requirement is to fetch *all* reviews for a product and the data is "relatively static" (meaning full list retrieval is the dominant operation, and partial updates are rare), the **String (JSON)** approach is the most straightforward and performs very well. It minimizes Redis operations and network overhead for the main use case.

If the requirements shifted to include frequent partial updates of reviews, or complex filtering/pagination directly on the cached data, then a **Hash** or **Sorted Set** would become more compelling, despite their increased complexity. Given the current constraints, the String approach offers the best balance of performance and simplicity.
