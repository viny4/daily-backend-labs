## Scenario

You are working on a rapidly growing e-commerce platform. A critical endpoint, `/api/v1/products/{product_id}/reviews`, fetches all reviews for a given product. This endpoint is frequently hit, especially for popular products. The `reviews` table, with over 50 million rows, stores `product_id`, `user_id`, `rating`, `comment`, and `created_at`. Each review also includes the `username` of the reviewer, which is fetched from the `users` table via a join.

While a single query for a product's reviews might be fast (e.g., 50-100ms with proper indexing), the sheer volume of requests for popular products (thousands per second during peak hours) is causing several issues:
1.  **Database connection pooling exhaustion:** The sustained load is constantly maxing out available database connections, leading to 503 errors for other critical parts of the application.
2.  **Increased database latency:** The database itself is showing signs of strain, with average query times for *all* queries slowly increasing.
3.  **Application server CPU spikes:** Serializing and deserializing large review payloads on the application servers contributes to high CPU usage, even for cached database results.

You need to implement a caching strategy using Redis to alleviate this pressure. The data for reviews for a given product is relatively static, changing only when a new review is submitted (which happens infrequently compared to reads).

## Requirements

Implement a robust caching strategy for the `/api/v1/products/{product_id}/reviews` endpoint using Redis. The solution must:
*   Significantly reduce database load for popular products.
*   Handle cache invalidation effectively when new reviews are added.
*   Account for the possibility of a "thundering herd" problem when the cache expires or is empty.
*   Assume the existing endpoint code is a Python/Django view and you have access to a Redis instance.
*   The overall P95 latency for this endpoint must be under 50ms, even during high load.

## Deliverables

1.  A clear outline of the caching mechanism, including the Redis key structure and data type choices.
2.  A description of how cache invalidation is triggered and handled when a new review is submitted for a product.
3.  A strategy to prevent cache stampedes or "thundering herd" issues upon cache expiration.
4.  An explanation of how the cached data would be integrated into the existing Python/Django view to serve responses.

## Going further

Describe the trade-offs you considered when choosing your Redis data structure for storing product reviews. Under what conditions might a different data structure be more appropriate, and why?
