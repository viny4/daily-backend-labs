## Scenario

Your team maintains a critical backend service for a popular online forum. A key feature is the ability for users to "follow" other users and to see a personalized "feed" of posts from the users they follow. This feed needs to be highly relevant and as close to real-time as possible. The `posts` table currently has hundreds of millions of rows, with thousands of new posts created every minute. The `follows` table (mapping a `follower_user_id` to a `followed_user_id`) also contains millions of relationships.

When a user requests their feed, the current implementation queries `posts` joined with `follows` to retrieve all posts from their followed users, sorted by creation date. This query has become extremely slow, often taking 5-10 seconds, especially for users who follow many others (e.g., hundreds or thousands). This latency is unacceptable and leads to a poor user experience.

## Requirements

The primary goal is to optimize the retrieval of a user's personalized feed.

Constraints:
*   The feed should show the most recent `N` posts (e.g., 50-100) from followed users.
*   Latency for feed retrieval must be consistently under 200ms, even for users following thousands of others.
*   New posts should appear in the feed as quickly as possible, ideally within a few seconds of being created.
*   The solution must scale to millions of users, hundreds of millions of posts, and millions of follow relationships.
*   Minimizing the impact on the write path (new post creation, new follow creation) is important.
*   The solution should be robust to temporary failures and data inconsistencies.

## Deliverables

1.  A high-level description of the improved data structure(s) or indexing strategy you would employ to store or facilitate access to user feeds.
2.  An explanation of how new posts would be incorporated into this system to maintain near real-time updates.
3.  A brief discussion of the trade-offs involved in your proposed solution, specifically regarding read latency vs. write overhead and storage costs.
4.  A plan for how users unfollowing someone would affect their feed and how this change would propagate.

## Going further

Consider a scenario where a user follows 100,000 other users. How would your proposed data structure or indexing strategy handle the storage and retrieval efficiency for such an edge case, and what are the theoretical upper bounds on the number of followed users before performance degrades significantly?

## Worked answer

### 1. Improved Data Structure(s) and Indexing Strategy

The core problem is that fetching a user's feed requires joining potentially millions of posts with millions of follow relationships, then sorting and limiting. This is an `O(F * P)` operation in the worst case (where `F` is the number of followed users and `P` is the number of posts from those users), which is inherently slow for large datasets.

To achieve sub-200ms latency, we need to pre-compute or pre-aggregate the feed data. The most effective strategy for this "fan-out on write" scenario is to use a dedicated **feed cache** or **feed store** for each user. This store will contain a denormalized list of post IDs (or full post data) relevant to that user, sorted by creation time.

We can implement this feed store using a key-value store like Redis, or a document database like MongoDB, or even a highly optimized relational table. Given the need for fast lookups and sorted lists, a Redis sorted set (`ZSET`) is an excellent choice. Each user's feed would be a `ZSET` where the member is the `post_id` and the score is the `timestamp` (or a derived sort key).

**Redis Schema:**

```
KEY: user_feed:{user_id}
TYPE: ZSET
MEMBERS: {post_id}
SCORES: {timestamp_in_ms_since_epoch} (e.g., 1678886400000 for March 15, 2023, 12:00:00 PM UTC)
```

**Feed Retrieval Logic:**

When a user requests their feed, the application would perform a single `ZREVRANGE` operation on their dedicated `ZSET` in Redis.

```redis
ZREVRANGE user_feed:{requesting_user_id} 0 {N-1} WITHSCORES
```

This command retrieves the top `N` most recent `post_id`s and their timestamps. The application can then fetch the full post details for these `post_id`s from the primary `posts` database (e.g., PostgreSQL) in a single batch query.

**Example SQL for batch fetching post details:**

```sql
SELECT
    post_id,
    author_user_id,
    content,
    created_at
FROM
    posts
WHERE
    post_id IN (post_id_1, post_id_2, ..., post_id_N)
ORDER BY
    created_at DESC; -- Ensure correct order if ZREVRANGE doesn't guarantee it for identical scores
```

This approach shifts the heavy lifting from read time to write time. Reading from a `ZSET` is `O(log(M) + N)` where `M` is the total number of posts in the user's feed and `N` is the number of posts requested. This is extremely fast.

### 2. Incorporating New Posts (Write Path)

New posts are incorporated into the system using a "fan-out on write" mechanism. When a new post is created, it needs to be added to the feed of all users who follow the post's author. This process should be asynchronous to avoid blocking the post creation itself.

**Workflow for New Post Creation:**

1.  **Post Creation:** A user creates a new post. The post is written to the primary `posts` database.
    ```sql
    INSERT INTO posts (post_id, author_user_id, content, created_at)
    VALUES ('post_xyz', 'user_A', 'My new post!', NOW());
    ```
2.  **Event Emission:** After successful post creation, an event is published to a message queue (e.g., Kafka, RabbitMQ, AWS SQS/SNS). The event payload should include `post_id`, `author_user_id`, and `created_at`.
    ```json
    {
        "event_type": "post_created",
        "post_id": "post_xyz",
        "author_user_id": "user_A",
        "created_at": 1678886400000
    }
    ```
3.  **Feed Update Service (Asynchronous Consumer):** A dedicated microservice (or a worker process) consumes these `post_created` events from the message queue.
    *   For each `post_created` event, it queries the `follows` table to find all `follower_user_id`s who follow `author_user_id`.
        ```sql
        SELECT follower_user_id
        FROM follows
        WHERE followed_user_id = 'user_A';
        ```
    *   For each `follower_user_id` found, it adds the `post_id` to their respective Redis `ZSET` feed.
        ```redis
        ZADD user_feed:{follower_user_id} {created_at_timestamp_ms} {post_id}
        ```
    *   To prevent feeds from growing indefinitely, we can also trim the `ZSET` to a maximum size (e.g., 1000 posts) immediately after adding a new post. This keeps memory usage bounded.
        ```redis
        ZREMRANGEBYRANK user_feed:{follower_user_id} 0 -1001
        ```
        (This removes the oldest posts, keeping the newest 1000).

This asynchronous processing ensures that new posts appear in feeds within seconds, depending on message queue latency and consumer processing speed.

### 3. Trade-offs

**Read Latency vs. Write Overhead:**

*   **Read Latency (Significantly Improved):** This solution drastically reduces read latency. Instead of complex database joins, feed retrieval becomes a single, fast Redis `ZREVRANGE` operation followed by a batch `SELECT` on the primary database. This easily meets the sub-200ms requirement.
*   **Write Overhead (Increased):** The primary trade-off is increased write overhead. When a post is created, we no longer just write to one table; we also have to:
    1.  Publish an event to a message queue.
    2.  Query the `follows` table to find all followers (can be a bottleneck for users with many followers).
    3.  Perform `N` Redis `ZADD` operations (where `N` is the number of followers).
    This means the write path for a single post is now `1 (DB write) + 1 (MQ publish) + M (DB reads for followers) + M (Redis writes)`. For a user with 1000 followers, this means 1000 Redis operations, which can add significant load to Redis and the feed update service.

**Storage Costs:**

*   **Increased Storage:** We are essentially duplicating data. Each `post_id` is stored once in the primary `posts` table and then potentially many times across various user feed `ZSET`s in Redis.
    *   If a post is seen by 10,000 followers, its `post_id` and `timestamp` are stored 10,000 times in Redis.
    *   Redis `ZSET`s are memory-intensive. Storing millions of `post_id`s (which are typically UUIDs or large integers) and their `timestamp` scores for millions of users can require a substantial amount of RAM for the Redis cluster.
    *   Example: If an average user's feed stores 500 post IDs, and there are 10 million users, that's 5 billion `(post_id, timestamp)` entries. If each entry is ~20 bytes (e.g., 16-byte UUID + 8-byte timestamp, optimized by Redis), that's 100GB of Redis memory *just for the feed data*. This requires careful sizing and potentially sharding of the Redis cluster.

**Data Consistency:**

*   **Eventual Consistency:** The feed update process is asynchronous, meaning there's a small window of eventual consistency. A newly created post might take a few milliseconds to a few seconds to appear in followers' feeds. This is generally acceptable for a social media feed.
*   **Robustness:** The message queue provides robustness. If the feed update service goes down, messages will queue up and be processed once it recovers. Retries can be implemented for Redis operations.

### 4. Unfollowing Users

When a user unfollows another user, their feed should immediately reflect this change by removing posts from the unfollowed user. This also needs to be handled on the write path, but for a "delete" operation.

**Workflow for Unfollowing:**

1.  **Unfollow Action:** A user (`follower_user_id`) unfollows another user (`followed_user_id`). The `follows` table is updated.
    ```sql
    DELETE FROM follows
    WHERE follower_user_id = 'user_B' AND followed_user_id = 'user_A';
    ```
2.  **Event Emission:** An `unfollow_event` is published to a message queue.
    ```json
    {
        "event_type": "user_unfollowed",
        "follower_user_id": "user_B",
        "followed_user_id": "user_A",
        "timestamp": 1678886500000
    }
    ```
3.  **Feed Update Service (Asynchronous Consumer):** The same (or a dedicated) service consumes `user_unfollowed` events.
    *   When `user_B` unfollows `user_A`, the service needs to remove all posts by `user_A` from `user_B`'s feed.
    *   This is tricky because `user_B`'s Redis `ZSET` only stores `post_id`s, not `author_user_id`s. To identify posts by `user_A`, the service would need to:
        1.  Fetch all `post_id`s currently in `user_B`'s feed.
        2.  Batch query the primary `posts` database to get the `author_user_id` for each of those `post_id`s.
        3.  Filter for posts where `author_user_id` matches `user_A`.
        4.  Remove these specific `post_id`s from `user_B`'s Redis `ZSET` using `ZREM`.

    This approach is inefficient if a user's feed is very large. A better approach is to augment the Redis feed entries to include the author ID, or to use a separate index.

**Revised Redis Schema for Unfollow Efficiency:**

To make unfollowing efficient, we can store more information in the Redis `ZSET` member. Instead of just `post_id`, we can store a composite key or a JSON string.

```
KEY: user_feed:{user_id}
TYPE: ZSET
MEMBERS: {post_id}:{author_user_id} (or JSON: {"post_id": "...", "author_id": "..."})
SCORES: {timestamp_in_ms_since_epoch}
```

With this, the unfollow process becomes:

1.  **Unfollow Event:** `user_B` unfollows `user_A`.
2.  **Feed Update Service:**
    *   It needs to iterate through `user_B`'s feed (`user_feed:{user_B}`) and find all members where the `author_user_id` part matches `user_A`.
    *   Redis `ZSCAN` can be used to iterate over the `ZSET` members. For each member, parse the `author_user_id` and if it matches `user_A`, add the full member string to a list for removal.
    *   Finally, use `ZREM` with all identified members.
        ```redis
        -- Example pseudo-code for ZSCAN and ZREM
        SCAN_CURSOR = 0
        POSTS_TO_REMOVE = []
        WHILE SCAN_CURSOR != 0 OR FIRST_ITERATION:
            (SCAN_CURSOR, MEMBERS_WITH_SCORES) = ZSCAN user_feed:{user_B} SCAN_CURSOR MATCH *:{user_A}
            FOR EACH (MEMBER, SCORE) IN MEMBERS_WITH_SCORES:
                POSTS_TO_REMOVE.ADD(MEMBER)
        IF POSTS_TO_REMOVE IS NOT EMPTY:
            ZREM user_feed:{user_B} POSTS_TO_REMOVE[0] POSTS_TO_REMOVE[1] ...
        ```
    *   This `ZSCAN` approach is still `O(M)` where `M` is the size of the user's feed, but it avoids a round trip to the primary database for each post. It can still be slow for very large feeds.

**Alternative for Unfollow (More Complex, but Faster):**

For extremely large feeds and frequent unfollows, a more sophisticated approach might involve:

*   **Per-Author Feeds:** Maintain a separate Redis `ZSET` for each author's posts: `author_posts:{author_id}`.
*   **User Feed as Union:** When a user requests their feed, dynamically merge the `author_posts` `ZSET`s of all followed users using `ZUNIONSTORE` (if the number of followed users is small enough for this to be fast) or a client-side merge. This is a "fan-out on read" approach, which we initially wanted to avoid.
*   **Hybrid Approach:** Keep the main `user_feed:{user_id}` for fast reads. For unfollows, instead of removing posts, we can mark them as "invalid" or "stale" by storing an `unfollowed_at` timestamp. When fetching the feed, filter out posts from unfollowed authors based on this timestamp. This adds complexity to the read path.

Given the requirement for sub-200ms latency, the "fan-out on write" with `ZSCAN` for unfollows is likely the most balanced approach. The `ZSCAN` operation, while `O(M)`, is performed asynchronously and doesn't block the user's feed retrieval. The impact is on the eventual consistency of the unfollow action.

### Going Further

#### Handling 100,000 Followed Users

If a user follows 100,000 other users, the "fan-out on write" strategy faces significant challenges:

1.  **New Post Write Amplification:** When an author posts, the feed update service needs to find all followers. If that author has 100,000 followers, the service will perform 100,000 `ZADD` operations. This creates immense load on Redis and the message queue consumer.
    *   **Problem:** A single popular post could trigger millions of Redis writes, potentially saturating network bandwidth, CPU on Redis servers, or the consumer service's capacity.
    *   **Mitigation:**
        *   **Batching Redis Writes:** Group `ZADD` operations into pipelines for each follower.
        *   **Sharding Redis:** Distribute `user_feed:{user_id}` keys across many Redis instances.
        *   **Rate Limiting/Prioritization:** Prioritize updates for less popular users or implement a tiered system where "super-follower" feeds are updated with slightly higher latency.
        *   **Dedicated Consumer Pool:** Have a large pool of consumers to handle the fan-out, potentially scaling out dynamically.

2.  **Unfollow Performance:** If a user follows 100,000 users, and then unfollows one, the `ZSCAN` approach to remove posts from that single unfollowed user from the follower's feed is still `O(M)` (where `M` is the size of the follower's feed). This is acceptable as it's asynchronous. However, if the *followed* user is unfollowed by many, the `DELETE FROM follows` and subsequent event processing could still be heavy.

3.  **Feed Size and Memory:** If a user follows 100,000 users, and each of those users posts frequently, the follower's feed (`user_feed:{user_id}`) could grow extremely large.
    *   **Problem:** If we keep, say, 1000 posts in the feed, and those 100,000 followed users generate posts, the 1000 posts will be constantly churned. The `ZREMRANGEBYRANK` operation helps keep the size bounded, but the rate of `ZADD`s and `ZREMRANGEBYRANK`s will be very high.
    *   **Mitigation:**
        *   **Aggressive Trimming:** Keep the `ZSET` size very small (e.g., 50-100 posts) for such "super-followers".
        *   **Hybrid Approach for Super-Followers:** For users following an extremely high number of others, a "fan-out on read" approach might be more suitable. Instead of pre-calculating their entire feed, we could:
            *   Store a small, highly relevant feed in Redis (e.g., posts from their top 100 most engaged-with followed users).
            *   For the rest, query a specialized, highly indexed database (e.g., Elasticsearch or a columnar store) that can quickly filter and sort posts from a large list of `author_user_id`s. This would involve a `WHERE author_user_id IN (...)` query on a large set, which is what we initially tried to avoid, but these databases are optimized for it. This introduces a second, slower path for edge cases.

#### Theoretical Upper Bounds

The performance degradation for the "fan-out on write" approach is primarily limited by:

1.  **Write Throughput of Redis:** The number of `ZADD` operations Redis can handle per second. A single Redis instance can typically handle tens of thousands to hundreds of thousands of operations per second. A cluster can scale this further.
2.  **Network Bandwidth:** The amount of data transferred between the feed update service and Redis.
3.  **CPU/Memory of Feed Update Service:** The service needs to fetch followers, construct Redis commands, and manage connections.
4.  **Database Read Throughput for `follows` table:** Querying `follows` for all followers of a popular author can be a bottleneck. An index on `followed_user_id` is crucial.

**Theoretical Upper Bound (based on fan-out):**

Let `R` be the Redis write operations per second (e.g., 100,000 ops/s for a single instance).
Let `AvgF` be the average number of followers per user.
Let `P` be the total number of new posts per second.

The total Redis writes per second are `P * AvgF`.
So, `P * AvgF <= R`.

If `R = 100,000 ops/s` and `AvgF = 100`, then `P * 100 <= 100,000`, meaning `P <= 1,000` new posts per second. This is a very high rate of posts.

However, the problem is not `AvgF`, but the *maximum* `F` for a single post. If a single post has `F_max` followers (e.g., 100,000), then that single post creation event will trigger `F_max` Redis writes. This can cause a temporary spike that overwhelms the system, even if the average load is fine.

**Degradation Point:**

Performance degrades significantly when:

*   **A single post's fan-out (`F_max`) approaches the Redis instance's capacity for `ZADD` operations within a short time window.** If `F_max` is 100,000, and Redis can do 100,000 ops/s, then that single post will consume 1 second of Redis write capacity. If multiple such posts happen concurrently, or if the consumer service can't keep up, the message queue will back up, and feeds will become stale.
*   **The total aggregate `P * AvgF` exceeds the total write capacity of the Redis cluster.**
*   **The `follows` table lookup for `follower_user_id`s becomes slow** due to lack of indexing or high contention.

For a user following 100,000 others, the read path (`ZREVRANGE`) remains extremely fast, as it only depends on the size of *their own feed* (`N`), not the number of people they follow. The bottleneck is purely on the write path and the fan-out process.

To truly scale beyond these limits for "super-followers" without impacting the write path for normal users, a hybrid approach (as mentioned above) or a more advanced feed generation system (e.g., using stream processing with Apache Flink or Spark Streaming to continuously update materialized views for super-followers) would be necessary.
