## Scenario

Your team maintains the backend for a B2B SaaS platform that helps e-commerce businesses analyze their product sales. A crucial part of the system is the `product_views` table, which logs every time a user views a product page. This table has grown significantly and now contains hundreds of millions of rows, recording views across thousands of distinct e-commerce stores (our clients).

A new analytics dashboard feature requires displaying the "Top 10 Most Viewed Products" for a given store within a specified date range. Currently, the query used to generate this report looks something like this:

```sql
SELECT product_id, COUNT(*) AS view_count
FROM product_views
WHERE store_id = :store_id AND viewed_at BETWEEN :start_date AND :end_date
GROUP BY product_id
ORDER BY view_count DESC
LIMIT 10;
```

This query, which was perfectly fine when the table was smaller, now takes 5-10 seconds to execute for many of your larger clients, well outside your 500ms latency budget for dashboard components. During peak hours, these slow queries also contribute to increased database connection pool pressure and higher CPU utilization on the database server.

The `product_views` table schema (simplified) is:
```sql
CREATE TABLE product_views (
    id BIGSERIAL PRIMARY KEY,
    store_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    user_id BIGINT,
    viewed_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Requirements

Optimize the provided SQL query to meet the 500ms latency budget, even for large `store_id` and wide date ranges (e.g., a full month for a store with millions of daily views). The solution must:

1.  Significantly reduce the execution time of the query.
2.  Maintain data accuracy for the "Top 10 Most Viewed Products" report.
3.  Be robust against concurrent queries from different stores and date ranges.
4.  Not introduce excessive write overhead that would impact the core `product_views` ingestion path (which handles thousands of inserts per second).

## Deliverables

1.  Provide the optimized SQL query (or queries) that achieves the performance target.
2.  Provide any necessary DDL statements (e.g., `CREATE INDEX`, `ALTER TABLE`) to support the optimized query.
3.  Explain *why* your proposed solution improves performance, referencing PostgreSQL's query execution characteristics.

## Worked answer

### Optimized SQL Query and DDL

The primary bottleneck for the original query is the full table scan or a large index scan required to filter by `store_id` and `viewed_at`, followed by grouping and ordering. To optimize this, we need an index that efficiently supports the `WHERE` clause and ideally helps with the `GROUP BY` and `ORDER BY` clauses.

#### DDL Statements

```sql
CREATE INDEX idx_product_views_store_viewed_product ON product_views (store_id, viewed_at DESC, product_id);
```

#### Optimized SQL Query

The SQL query itself remains unchanged, as the optimization comes from the underlying indexing strategy. PostgreSQL's query planner will automatically utilize the new index.

```sql
SELECT product_id, COUNT(*) AS view_count
FROM product_views
WHERE store_id = :store_id AND viewed_at BETWEEN :start_date AND :end_date
GROUP BY product_id
ORDER BY view_count DESC
LIMIT 10;
```

### Explanation of Performance Improvement

The `idx_product_views_store_viewed_product` index is a composite B-tree index designed to efficiently support the query's filtering, grouping, and ordering requirements.

1.  **Filtering (`WHERE store_id = :store_id AND viewed_at BETWEEN :start_date AND :end_date`):**
    *   The `store_id` column is the leading column in the index. This allows PostgreSQL to quickly narrow down the search space to only the rows belonging to the specified `store_id`. This is crucial because `store_id` has high selectivity (i.e., for a given query, only a small fraction of the total rows will match a specific `store_id`).
    *   Once `store_id` is matched, the `viewed_at` column in the index allows for efficient range scanning within the specified date range. The `DESC` order for `viewed_at` is a minor optimization for potential future queries that might want the latest views first, but for `BETWEEN` it doesn't significantly change performance compared to `ASC`.

2.  **Grouping (`GROUP BY product_id`):**
    *   After filtering by `store_id` and `viewed_at`, the index provides the `product_id` values in a sorted (or at least clustered) manner for a given `store_id` and `viewed_at` range. While the `product_id` is not strictly sorted across the entire index, within the filtered subset, the index scan can often provide rows in an order that aids the `GROUP BY` operation. PostgreSQL can perform a "Bitmap Heap Scan" or "Index Scan" followed by "GroupAggregate" which is more efficient than a full table scan followed by a hash aggregate.

3.  **Ordering (`ORDER BY view_count DESC`):**
    *   The `ORDER BY view_count DESC` clause requires counting views per product and then sorting. The index *does not directly* help with sorting by `view_count` because `view_count` is an aggregate result. However, by making the initial filtering and data retrieval much faster, it significantly reduces the amount of data that needs to be processed for the aggregation and final sort. The smaller the dataset passed to the `GROUP BY` and `ORDER BY` steps, the faster they will execute.

**Why this specific index?**

*   **`store_id` first:** This is paramount. Queries almost always specify `store_id`, and it's highly selective. Placing it first allows the index to act as a partition key, quickly isolating data for a single store.
*   **`viewed_at` second:** This allows efficient range scans for the date filter *within* a specific `store_id`.
*   **`product_id` last (included):** Including `product_id` as the third column makes this a "covering index" for the `SELECT product_id` part of the query, *if* the `COUNT(*)` could also be derived. While `COUNT(*)` cannot be directly derived from the index, having `product_id` in the index means that for the filtered rows, PostgreSQL can retrieve `product_id` directly from the index without needing to access the main table (the "heap") for that column. This can lead to "Index-Only Scans" if all other required columns (like `id`, `user_id`) are not needed, which is the case here. This further reduces disk I/O.

**Expected Performance Improvement:**

With this index, PostgreSQL can perform an "Index Scan" or "Bitmap Index Scan" on `idx_product_views_store_viewed_product`. Instead of scanning hundreds of millions of rows, it will efficiently navigate the index B-tree to find the relevant `store_id` entries, then scan a much smaller subset of index entries for the `viewed_at` range. This drastically reduces the number of rows read from disk and processed by the database engine, bringing execution time well within the 500ms budget.

### Trade-offs and Scalability

**Write Overhead:**
The primary trade-off is increased write overhead. Every `INSERT` into `product_views` will now also require an update to the `idx_product_views_store_viewed_product` index. Given "thousands of inserts per second," this is a significant consideration. However, B-tree indexes are highly optimized for writes. A single index with three columns is generally manageable. If we were adding many more indexes or very wide indexes, the write overhead would become more problematic. The chosen index is highly selective for reads, justifying this overhead.

**Disk Space:**
The index will consume additional disk space. For hundreds of millions of rows, an index on three `BIGINT` and one `TIMESTAMPTZ` column will be substantial, potentially tens or hundreds of gigabytes. This is generally an acceptable cost for critical read performance.

**Scalability at 10x:**
At ten times the current scale (billions of rows, tens of thousands of inserts/sec), the current solution might start to show limitations:

1.  **Index Size and Maintenance:** The index itself will become enormous. While B-trees scale well, operations like `VACUUM` (especially full vacuums) and index rebuilds could become very time-consuming.
2.  **Write Contention:** Tens of thousands of inserts per second could lead to increased write contention on the index, especially if many inserts target the same "hot" index pages. This could manifest as increased transaction latency for inserts.
3.  **Index-Only Scan Limitations:** If the table grows very large and updates/deletes are frequent, "Index-Only Scans" can become less effective due to "visibility map" issues (i.e., many rows in the index might point to dead tuples in the heap that haven't been vacuumed yet).

At this extreme scale, further optimizations might involve:

*   **Partitioning:** Table partitioning by `store_id` or `viewed_at` (e.g., by month) could significantly improve performance for both reads and writes. Queries would only scan relevant partitions. Indexing would then be per-partition, making indexes smaller and faster to maintain.
*   **Materialized Views:** For less real-time requirements, a materialized view could pre-aggregate the top products, refreshed periodically. This shifts the computational burden off the query path entirely.
*   **Separate Analytics Store:** For truly massive scale analytics, offloading data to a dedicated OLAP database (e.g., ClickHouse, Druid) or a data warehouse (e.g., Snowflake, BigQuery) might be necessary, leaving PostgreSQL to handle only the operational data.

### Going Further: Top 10 Most Viewed Products Across All Stores

If the `store_id` parameter is often omitted, and the dashboard needs to show the "Top 10 Most Viewed Products across *all* stores" within a date range, the current index `idx_product_views_store_viewed_product` would be less effective.

The query would look like this:

```sql
SELECT product_id, COUNT(*) AS view_count
FROM product_views
WHERE viewed_at BETWEEN :start_date AND :end_date
GROUP BY product_id
ORDER BY view_count DESC
LIMIT 10;
```

#### New Performance Challenges and Opportunities

1.  **Index Inefficiency:** The existing index `(store_id, viewed_at DESC, product_id)` would not be optimally used. Because `store_id` is the leading column and is not constrained in the `WHERE` clause, PostgreSQL would have to scan the entire index (or a very large portion of it) to find all `viewed_at` entries within the range, regardless of `store_id`. This would be almost as bad as a full table scan, as the index would not help in narrowing down the initial search space.

2.  **New Index Requirement:** To optimize this "all stores" query, a different index would be needed:

    ```sql
    CREATE INDEX idx_product_views_viewed_product ON product_views (viewed_at DESC, product_id);
    ```

    *   This index places `viewed_at` first, allowing for efficient range scanning across the entire dataset for the specified date range.
    *   `product_id` is included to potentially aid in `GROUP BY` and for Index-Only Scans.
    *   **Challenge:** This index would be very large and would still involve scanning a significant portion of the index if the date range is wide (e.g., a full month across all stores with millions of views daily). The `GROUP BY` and `ORDER BY` operations would still be performed on a potentially massive intermediate result set.

3.  **Aggregation Cost:** The primary challenge for the "all stores" query is the sheer volume of data that needs to be aggregated. Even with an efficient index on `viewed_at`, if a month has billions of views across all stores, grouping and counting `product_id` for all those views will be computationally intensive and likely exceed the 500ms latency budget.

#### Adaptation and Further Opportunities

For the "all stores" scenario, especially with wide date ranges, the approach needs to shift from real-time aggregation on the raw `product_views` table to pre-aggregation or a more specialized analytics solution.

**Proposed Adaptation (for "all stores"):**

The most robust solution for this specific "all stores" query, especially if it's frequently accessed and needs to be fast, is to use **Materialized Views**.

```sql
-- Create a materialized view to pre-aggregate daily top products across all stores
CREATE MATERIALIZED VIEW mv_daily_all_store_top_products AS
SELECT
    DATE_TRUNC('day', viewed_at) AS view_date,
    product_id,
    COUNT(*) AS view_count
FROM product_views
GROUP BY 1, 2
ORDER BY view_date DESC, view_count DESC;

-- Create an index on the materialized view for efficient querying
CREATE INDEX idx_mv_daily_all_store_top_products_date_product ON mv_daily_all_store_top_products (view_date DESC, product_id);
```

**Querying the Materialized View:**

```sql
-- To get top 10 for a specific date range across all stores:
SELECT product_id, SUM(view_count) AS total_view_count
FROM mv_daily_all_store_top_products
WHERE view_date BETWEEN :start_date AND :end_date
GROUP BY product_id
ORDER BY total_view_count DESC
LIMIT 10;
```

**Explanation:**

*   **Pre-aggregation:** The materialized view pre-calculates daily view counts for each product across all stores. This shifts the heavy `GROUP BY` computation from query time to refresh time.
*   **Faster Querying:** The query against the materialized view now only needs to sum up pre-aggregated daily counts, which is orders of magnitude faster than aggregating raw events. The `idx_mv_daily_all_store_top_products_date_product` index further speeds up filtering by `view_date`.
*   **Refresh Strategy:** The materialized view would need to be refreshed periodically (e.g., hourly, daily) using `REFRESH MATERIALIZED VIEW mv_daily_all_store_top_products;`. This refresh operation would be an expensive batch job, but it runs asynchronously to user queries.
*   **Trade-offs:**
    *   **Data Freshness:** The data in the materialized view is only as fresh as its last refresh. This might be acceptable for an analytics dashboard (e.g., "data up to 1 hour ago").
    *   **Storage:** The materialized view consumes additional storage.
    *   **Complexity:** Introduces a new component (materialized view) and a refresh schedule.

This approach effectively decouples the real-time ingestion path from the analytical query path, providing fast responses for complex aggregations at the cost of some data freshness and increased operational complexity.
