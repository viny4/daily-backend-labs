## Scenario

Your team maintains a critical internal service that powers your company's analytics dashboards. A frequently accessed dashboard displays the "Top N Most Active Customers" based on their recent API usage. The underlying `api_requests` PostgreSQL table, which logs every API call, has grown to over 500 million rows, with roughly 10 million new rows added daily.

The query to determine the top customers involves:
1. Counting API requests per customer within a sliding 24-hour window.
2. Ordering customers by their request count in descending order.
3. Limiting the result to the top N (typically N=50 or N=100).

This query, even with appropriate indexing on `customer_id` and `request_timestamp`, now takes 5-7 seconds to execute directly against the database, causing significant latency for the dashboard and occasionally contributing to database connection pool exhaustion during peak hours. The "active" window needs to be refreshed every 30-60 seconds to provide reasonably up-to-date data.

You need to integrate Redis to offload this heavy computation from the primary database and serve the "Top N Most Active Customers" list with a much lower latency.

## Requirements

1.  The solution must reduce the database load for the "Top N Most Active Customers" query to near zero for read operations.
2.  The API endpoint serving this data must respond within 50ms.
3.  The list of top customers must be updated every 30-60 seconds.
4.  The caching mechanism should gracefully handle Redis outages or unavailability without completely failing the dashboard, ideally falling back to a stale or directly-queried result.
5.  The system should be robust against concurrent updates to the cached data by multiple background workers, ensuring data consistency.

## Worked answer

### 1. Redis Data Structure(s)

For storing the "Top N Most Active Customers," a **Redis Sorted Set (ZSET)** is the most appropriate data structure.

*   **Why ZSET?**
    *   **Ordered by Score:** A ZSET stores members (in our case, `customer_id`s) associated with a numerical score (the API request count). This allows Redis to keep the set automatically sorted by score in ascending or descending order.
    *   **Efficient Range Queries:** We can retrieve the top N customers very efficiently using `ZREVRANGE` (to get the highest scores) or `ZRANGE` (for lowest scores) with `WITHSCORES` to get both the customer ID and their request count. This operation is `O(log(N) + M)` where N is the number of elements in the sorted set and M is the number of elements returned.
    *   **Atomic Updates:** While we won't be updating individual scores frequently in the read path, ZSET operations like `ZADD` are atomic, which is beneficial for background worker updates.

*   **Key Naming Convention:**
    We'll use a simple key like `top_active_customers`. If there were different "top N" lists (e.g., by region, by product), we might use `top_active_customers:{region}`.

### 2. Caching Strategy

The caching strategy will be a **write-through/refresh-ahead** approach, where a background job periodically computes the data and pushes it to Redis, and the API service reads directly from Redis.

*   **Population and Update:**
    1.  **Background Job:** A dedicated background worker (e.g., a cron job, a Kubernetes CronJob, or a message queue consumer) will be responsible for computing the "Top N Most Active Customers" list from the PostgreSQL database.
    2.  **Computation:** The job will execute the heavy SQL query against PostgreSQL.
    3.  **Atomic Swap in Redis:** Once the new list is computed, the background job will atomically replace the old list in Redis with the new one. This ensures that the API always reads a complete and consistent list.
    4.  **Frequency:** This job will run every 30-60 seconds as required.

*   **Invalidation:**
    *   Explicit invalidation is not strictly necessary in this model because the data is periodically *refreshed* in its entirety. The old data is simply overwritten.
    *   The Time-To-Live (TTL) for the Redis key can be set to be slightly longer than the refresh interval (e.g., 2x the refresh interval). This acts as a safety net: if the background job fails to run for an extended period, the key will eventually expire, signaling that the data is stale. However, the primary mechanism is the periodic refresh.

*   **API Service Logic:**
    1.  When the API endpoint for "Top N Most Active Customers" is hit, it attempts to read the `top_active_customers` ZSET directly from Redis.
    2.  If Redis returns data, it's immediately served (meeting the <50ms requirement).
    3.  If Redis is unavailable or the key doesn't exist (e.g., first load, or key expired due to prolonged background job failure), the fallback mechanism is triggered.

### 3. Background Job Logic

The background job will perform the following steps:

```sql
-- PostgreSQL query to get the top N active customers
-- N is typically 50 or 100
SELECT
    customer_id,
    COUNT(request_id) AS request_count
FROM
    api_requests
WHERE
    request_timestamp >= NOW() - INTERVAL '24 hours'
GROUP BY
    customer_id
ORDER BY
    request_count DESC
LIMIT 100; -- Example for N=100
```

**Background Job (e.g., Python/Node.js/Go pseudocode):**

```python
import redis
import psycopg2
import os
import time

REDIS_HOST = os.getenv('REDIS_HOST', 'localhost')
REDIS_PORT = int(os.getenv('REDIS_PORT', 6379))
REDIS_DB = int(os.getenv('REDIS_DB', 0))
REDIS_KEY = 'top_active_customers'
REDIS_TTL_SECONDS = 120 # 2x refresh interval (60s)

PG_HOST = os.getenv('PG_HOST', 'localhost')
PG_DB = os.getenv('PG_DB', 'analytics_db')
PG_USER = os.getenv('PG_USER', 'user')
PG_PASSWORD = os.getenv('PG_PASSWORD', 'password')

REFRESH_INTERVAL_SECONDS = 60

def get_top_customers_from_db(n=100):
    """
    Connects to PostgreSQL and fetches the top N active customers.
    """
    conn = None
    try:
        conn = psycopg2.connect(host=PG_HOST, database=PG_DB, user=PG_USER, password=PG_PASSWORD)
        cur = conn.cursor()
        query = f"""
            SELECT
                customer_id,
                COUNT(request_id) AS request_count
            FROM
                api_requests
            WHERE
                request_timestamp >= NOW() - INTERVAL '24 hours'
            GROUP BY
                customer_id
            ORDER BY
                request_count DESC
            LIMIT {n};
        """
        cur.execute(query)
        results = cur.fetchall()
        cur.close()
        return results
    except Exception as e:
        print(f"Error fetching from DB: {e}")
        return []
    finally:
        if conn:
            conn.close()

def refresh_cache():
    r = redis.StrictRedis(host=REDIS_HOST, port=REDIS_PORT, db=REDIS_DB, decode_responses=True)
    
    print(f"[{time.ctime()}] Starting cache refresh...")
    try:
        top_customers = get_top_customers_from_db(n=100)
        
        if not top_customers:
            print("No top customers found or DB error, skipping update.")
            return

        # Prepare data for ZADD: list of (score, member) tuples
        zset_data = [(count, customer_id) for customer_id, count in top_customers]

        # Use a temporary key and RENAME to ensure atomicity for readers
        temp_key = f"{REDIS_KEY}_temp_{int(time.time())}"
        
        # 1. Add all members to a temporary sorted set
        # ZADD can take multiple (score, member) pairs
        r.zadd(temp_key, dict(zset_data)) 
        
        # 2. Set TTL for the temporary key (optional, for cleanup if rename fails)
        r.expire(temp_key, REDIS_TTL_SECONDS * 2) 

        # 3. Atomically rename the temporary key to the main key
        # This replaces the old key with the new one.
        # If the old key doesn't exist, it's created.
        r.rename(temp_key, REDIS_KEY) 
        
        # 4. Set TTL for the main key
        r.expire(REDIS_KEY, REDIS_TTL_SECONDS)

        print(f"[{time.ctime()}] Cache refreshed successfully. Top {len(top_customers)} customers.")

    except redis.exceptions.ConnectionError as e:
        print(f"[{time.ctime()}] Redis connection error during refresh: {e}")
    except Exception as e:
        print(f"[{time.ctime()}] An unexpected error occurred during cache refresh: {e}")

if __name__ == "__main__":
    while True:
        refresh_cache()
        time.sleep(REFRESH_INTERVAL_SECONDS)
```

### 4. Fallback Mechanism for Redis Unavailability

The API endpoint's `get_top_customers` function already incorporates a fallback.

*   **Detection:**
    *   `redis.exceptions.ConnectionError`: Catches issues during Redis client initialization or during `zrevrange` operations.
    *   Empty `cached_data`: If the key exists but is empty, or if the key doesn't exist (e.g., first load, or key expired), it also triggers fallback.

*   **Fallback Strategy (`fallback_to_stale_or_db` function):**
    1.  **Serve Stale Data (Preferred):** The most graceful fallback is to serve the *last known good state*. This could be:
        *   A copy of the last successful Redis read stored in the API service's local memory (e.g., a global variable updated on every successful Redis read). This is fast but loses state on service restarts.
        *   A copy stored in a more persistent, but less performant, local cache (e.g., a file on disk, or a simple SQLite database).
    2.  **Limited Direct DB Query (Conditional):** If stale data isn't available or acceptable, a *highly optimized and limited* direct query to PostgreSQL could be attempted. This would likely be:
        *   A query for only the top 10-20 customers, not 100, to reduce load.
        *   Targeted at a read replica if available.
        *   With a very short timeout.
        *   **Trade-off:** This might still exceed the 50ms latency requirement and put some load back on the DB, but it's better than a complete failure.
    3.  **Return Empty/Error:** If no acceptable fallback data can be retrieved within a strict timeout, the API should return an empty list or a `503 Service Unavailable` error, indicating degraded service.

### Going Further: Race Conditions and Mitigation

If multiple background workers attempt to refresh the "Top N Most Active Customers" cache simultaneously, several race conditions and inconsistencies could arise:

1.  **Dirty Reads (if not atomic):** If a worker simply `DEL`etes the key and then starts `ZADD`ing new members, an API request could hit Redis in the middle of this process, receiving an incomplete or empty list.
2.  **Lost Updates:** If two workers compute the list and try to update the key directly (`ZADD`ing to the same key), the "last writer wins" and one worker's computation might be entirely overwritten by another, potentially older, computation.
3.  **Inconsistent State:** If workers are adding/removing individual members, they might interfere with each other, leading to a mixed-up list that never represents a single, consistent snapshot.

**Mitigation in the Chosen Strategy:**

Our strategy explicitly addresses these risks using Redis's atomic operations:

*   **Atomic Swap with `RENAME`:**
    The core of the mitigation is the use of a temporary key and the `RENAME` command.
    1.  Each background worker computes the full list independently.
    2.  Each worker then populates its results into a *unique temporary Redis key* (e.g., `top_active_customers_temp_{timestamp}`). This ensures that workers don't interfere with each other while building the new list.
    3.  Once a worker has fully populated its temporary key, it uses `RENAME {temp_key} {main_key}`. The `RENAME` command is atomic. It replaces the old `top_active_customers` key with the newly computed `temp_key` in a single, indivisible operation.
    4.  **How it mitigates:**
        *   **No Dirty Reads:** API readers will *always* see either the *old, complete* list or the *new, complete* list. They will never see a partially updated list because the switch is instantaneous from their perspective.
        *   **"Last Successful Computation Wins":** If multiple workers finish at roughly the same time, the one whose `RENAME` command executes last will set the final state. This is generally acceptable for a periodically refreshed cache; the dashboard will simply display the most recent successful computation. The slight overlap or re-computation is harmless.
        *   **No Inconsistent State:** Because the entire list is replaced, there's no risk of individual members being added or removed inconsistently.

*   **Redis Transactions (MULTI/EXEC) - Alternative/Complementary:**
    While `RENAME` handles the atomic swap for the entire key, if we needed to perform multiple operations on the *same* key atomically (e.g., delete all members and then add new ones, which is less efficient than `RENAME` for full replacement), we could use Redis transactions (`MULTI`/`EXEC`).
    ```python
    # Example of MULTI/EXEC for a full replacement (less efficient than RENAME for this case)
    # This would still have a window of empty data if used on the main key
    pipe = r.pipeline()
    pipe.delete(REDIS_KEY) # Delete old data
    pipe.zadd(REDIS_KEY, dict(zset_data)) # Add new data
    pipe.expire(REDIS_KEY, REDIS_TTL_SECONDS)
    pipe.execute() # All commands executed atomically
    ```
    However, for a full replacement, `RENAME` is superior because it ensures continuous availability of *some* data (either old or new) for readers. `MULTI`/`EXEC` with `DEL` would introduce a brief window where the key is empty.

*   **Distributed Locks (e.g., Redlock) - Less Ideal for this Scenario:**
    One might consider using a distributed lock (e.g., Redlock) to ensure only one worker refreshes the cache at a time.
    *   **Pros:** Guarantees only one worker is active, preventing redundant computation.
    *   **Cons:**
        *   **Complexity:** Adds significant complexity to the system.
        *   **Performance Bottleneck:** The lock itself can become a bottleneck if workers frequently contend.
        *   **Risk of Deadlock:** If a worker holding the lock crashes, the cache might not be updated until the lock expires, leading to prolonged staleness.
    *   **Why not ideal here:** Given that the computation is relatively independent and the `RENAME` strategy handles consistency for readers, the overhead and risks of a distributed lock outweigh the benefits for this specific problem. Redundant computation by multiple workers is a minor inefficiency compared to the benefits of simplicity and continuous availability.

By using the `RENAME` command, we achieve strong consistency for readers (always a complete list) and robustness against concurrent writers without introducing complex locking mechanisms.
