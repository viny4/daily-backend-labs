## Scenario

Your team maintains a critical internal service responsible for generating and delivering daily digest emails to millions of users. These emails summarize recent activity relevant to each user, such as new posts in followed topics, mentions, or direct messages. The system currently pulls all activity data for a user for the past 24 hours, aggregates it, renders an HTML template, and sends the email.

This service is built with Python/Django and uses PostgreSQL as its primary data store. The `user_activity_events` table, which stores all relevant events (e.g., `user_id`, `event_type`, `related_entity_id`, `timestamp`, `payload_json`), has grown significantly and now contains hundreds of millions of rows, with tens of millions added daily.

The current process involves a daily batch job that iterates through all active users. For each user, it fetches all their activity events from the `user_activity_events` table for the last 24 hours. As the number of users and activity events has scaled, this daily job has started to regularly exceed its allotted processing window (currently 4 hours), leading to delayed email deliveries and occasional timeouts during data retrieval from PostgreSQL. The database is also experiencing high CPU load during the email generation window.

## Requirements

The core problem is the inefficiency and scalability limitations of the current daily email digest generation process. The system needs to reliably generate and deliver these emails for all active users within a 4-hour window, even as user count and activity volume continue to grow. Latency for individual user data retrieval must be significantly reduced to avoid timeouts and high database load. The solution must handle potential failures gracefully, ensuring no user misses their daily digest due or receives duplicate digests.

### 2. Key components and technologies

The proposed architecture introduces several new components and modifies existing ones to address scalability, performance, and reliability.

1.  **Activity Event Producers**: These are the various services generating user activity (e.g., new posts, mentions, DMs). They will now publish events asynchronously to a message queue instead of directly writing to PostgreSQL.
    *   **Technology**: Existing services.
    *   **Contribution**: Decouples event generation from storage, reducing direct write load on PostgreSQL and enabling real-time processing.

2.  **Message Queue (Kafka/Kinesis)**: A highly scalable, durable, and fault-tolerant distributed streaming platform. All user activity events will be published here.
    *   **Technology**: Apache Kafka or AWS Kinesis.
    *   **Contribution**: Acts as a buffer for high-volume event streams, ensures durability of events, enables multiple consumers for different use cases (e.g., digest generation, analytics, real-time feeds), and decouples producers from consumers. This prevents direct database writes from becoming a bottleneck during peak activity.

3.  **Activity Stream Processor (Flink/Spark Streaming)**: A real-time stream processing engine that consumes events from the message queue. It will aggregate and transform raw activity events into a format optimized for digest generation.
    *   **Technology**: Apache Flink or Apache Spark Streaming.
    *   **Contribution**:
        *   **Pre-aggregation**: Instead of fetching all raw events daily, this processor aggregates events in real-time or near real-time. For example, it can count new posts, group mentions, or identify unique entities, storing only the *summary* data needed for the digest. This drastically reduces the data volume fetched during digest generation.
        *   **Materialized Views**: It effectively creates and maintains materialized views of user activity, optimized for read patterns.
        *   **Reduced Database Load**: Shifts the heavy aggregation workload from the daily batch job and PostgreSQL to a dedicated stream processing cluster.

4.  **User Digest Data Store (Cassandra/DynamoDB)**: A NoSQL wide-column or document database optimized for high-volume, low-latency reads and writes, particularly for key-value or column-family access patterns. This will store the pre-aggregated user activity data.
    *   **Technology**: Apache Cassandra or AWS DynamoDB.
    *   **Contribution**:
        *   **Scalability**: Horizontally scalable, allowing for massive data volumes and throughput without impacting performance.
        *   **Low Latency Reads**: Designed for fast retrieval of data given a primary key (e.g., `user_id`). This directly addresses the "latency for individual user data retrieval must be significantly reduced" requirement.
        *   **Schema Flexibility**: Can handle varying types of aggregated data per user.
        *   **Offloads PostgreSQL**: Removes the primary read burden for digest data from PostgreSQL.

5.  **User Activity Cache (Redis)**: An in-memory data structure store, used for very fast access to frequently requested or highly volatile user activity data.
    *   **Technology**: Redis.
    *   **Contribution**:
        *   **Further Reduces Latency**: Provides sub-millisecond latency for the most recent or critical activity data, acting as a hot cache in front of the User Digest Data Store.
        *   **Reduces Load on Data Store**: Prevents the User Digest Data Store from being hit for every single read, especially for users with very recent activity.

6.  **Daily Digest Orchestrator (Airflow/Temporal)**: A workflow orchestration engine responsible for scheduling, coordinating, and monitoring the daily digest generation process.
    *   **Technology**: Apache Airflow or Temporal.
    *   **Contribution**:
        *   **Reliable Scheduling**: Ensures the daily job starts precisely on time.
        *   **Workflow Management**: Manages the fan-out process, distributing the workload across many workers.
        *   **Error Handling & Retries**: Built-in mechanisms for retrying failed tasks and managing dependencies, crucial for "handling potential failures gracefully."
        *   **Visibility**: Provides a clear view of the progress and status of the entire digest generation process.

7.  **User Batch Processor (Kubernetes Pods/Lambda)**: A pool of stateless workers that fetch aggregated data for a batch of users, trigger email rendering, and send emails. These workers will be highly parallelized.
    *   **Technology**: Kubernetes Pods (for long-running, CPU-intensive tasks) or AWS Lambda (for event-driven, short-lived tasks).
    *   **Contribution**:
        *   **Massive Parallelization**: Can process hundreds of thousands or millions of users concurrently, drastically reducing the total processing time. This directly addresses the "reliably generate and deliver these emails for all active users within a 4-hour window" requirement.
        *   **Scalability**: Can scale horizontally by adding more pods/lambdas as needed.
        *   **Isolation**: Failures in one worker only affect a small batch of users.

8.  **Email Rendering Service**: A dedicated service responsible for taking aggregated user data and an HTML template, and producing the final HTML email content.
    *   **Technology**: Python/Django (existing, potentially refactored into a microservice).
    *   **Contribution**: Decouples rendering logic, allowing it to be scaled independently and potentially optimized (e.g., pre-compiling templates).

9.  **Email Sending Service (SES/SendGrid)**: A robust third-party email delivery service.
    *   **Technology**: AWS SES, SendGrid, Mailgun.
    *   **Contribution**: Handles the complexities of email delivery (SMTP, deliverability, bounce management, rate limiting), ensuring high deliverability and offloading this critical but complex task from our internal services.

10. **Existing PostgreSQL**: Will still be used as the primary data store for user profiles, subscriptions, and other core application data. It will no longer be the primary source for raw activity events or their aggregations for digest generation.
    *   **Contribution**: Reduced load, allowing it to focus on its core responsibilities without being overwhelmed by activity event queries. It might still store a "last sent digest timestamp" for each user.

### 3. Data access pattern changes

The core change is moving from on-demand, real-time aggregation from a transactional database to pre-aggregated, denormalized data stored in a highly scalable NoSQL store, accessed by a massively parallelized batch process.

**Current Pattern (Problematic):**

```sql
-- Executed for EACH user, daily
SELECT *
FROM user_activity_events
WHERE user_id = :user_id
  AND timestamp >= NOW() - INTERVAL '24 hours'
ORDER BY timestamp DESC;
```
This query, when run millions of times, causes:
*   **High I/O**: Reading potentially thousands of rows per user from a large table.
*   **High CPU**: PostgreSQL performing sorting and filtering on a massive scale.
*   **Locking/Contention**: Even with `READ COMMITTED`, high read volume can contend for resources.
*   **Index Inefficiency**: While `(user_id, timestamp)` is a good index, the sheer volume of data and queries still overwhelms the system.

**Proposed New Pattern:**

1.  **Event Ingestion**:
    *   Activity producers publish raw events to Kafka/Kinesis.
    *   Example Kafka message payload:
        ```json
        {
            "event_id": "uuid-123",
            "user_id": 12345,
            "event_type": "new_post",
            "related_entity_id": 67890,
            "timestamp": "2023-10-26T10:00:00Z",
            "payload": {"topic_id": 101, "post_title": "My new post"}
        }
        ```

2.  **Stream Processing & Pre-aggregation (Flink/Spark Streaming)**:
    *   The stream processor consumes events from Kafka/Kinesis.
    *   It maintains state per user (e.g., in-memory or using RocksDB for Flink) for the last 24 hours.
    *   It aggregates events into a digest-optimized structure. For example, instead of storing individual `new_post` events, it might store a count of new posts, a list of unique topics with new posts, or a summary of mentions.
    *   It writes these pre-aggregated summaries to the User Digest Data Store (Cassandra/DynamoDB) and potentially the User Activity Cache (Redis).

    *   **Example Cassandra Schema (`user_daily_digest_summary` table):**
        ```sql
        CREATE TABLE user_daily_digest_summary (
            user_id UUID,
            digest_date DATE, -- Partition key: user_id, Clustering key: digest_date
            new_posts_count INT,
            new_posts_topics LIST<TEXT>,
            mentions_count INT,
            mentions_list LIST<FROZEN<mention_summary>>, -- UDT for mention details
            direct_messages_count INT,
            direct_messages_senders LIST<TEXT>,
            last_updated TIMESTAMP,
            PRIMARY KEY ((user_id), digest_date)
        ) WITH CLUSTERING ORDER BY (digest_date DESC);

        CREATE TYPE mention_summary (
            mentioner_user_id UUID,
            entity_type TEXT,
            entity_id UUID,
            snippet TEXT
        );
        ```
        *   **Explanation**: `user_id` is the primary partition key, ensuring all data for a single user resides on one or a few nodes, enabling fast retrieval. `digest_date` is a clustering key, allowing us to query for specific days. We store aggregated counts and lists of relevant IDs/summaries, not individual raw events.

    *   **Example Redis Key/Value (for recent activity, short TTL):**
        ```
        KEY: user:{user_id}:activity:recent
        VALUE: JSON string of recent activity summary (e.g., {"new_posts": 5, "mentions": [{"from": "userX", "post": "..."}]})
        TTL: 1 hour (or less)
        ```

3.  **Daily Digest Generation (User Batch Processor)**:
    *   The orchestrator triggers the batch processor.
    *   Workers fetch a batch of `user_id`s (e.g., from a queue or a list of active users).
    *   For each `user_id` in its batch, a worker performs a direct lookup in the User Digest Data Store (Cassandra/DynamoDB) for the relevant `digest_date`.
    *   **Example Cassandra Query**:
        ```sql
        SELECT new_posts_count, new_posts_topics, mentions_count, mentions_list,
               direct_messages_count, direct_messages_senders
        FROM user_daily_digest_summary
        WHERE user_id = :user_id
          AND digest_date = :yesterday_date;
        ```
        This is a highly efficient primary key lookup, returning a single row (or very few rows if we store multiple days, but typically one for the daily digest).

    *   The worker then passes this pre-aggregated data to the Email Rendering Service.

**Benefits of the new pattern:**

*   **Massive Reduction in Database Load**: PostgreSQL is no longer queried for activity events. The User Digest Data Store handles high-volume reads efficiently due to its distributed nature and optimized access patterns.
*   **Low Latency per User**: Each user's digest data is retrieved with a single, fast primary key lookup in Cassandra/DynamoDB, typically in single-digit milliseconds.
*   **Pre-computation**: The heavy lifting of aggregation is shifted from the digest generation window to continuous stream processing, distributing the computational load over 24 hours.
*   **Scalability**: Both the stream processor and the NoSQL data store are horizontally scalable, accommodating growth in users and activity events.

### 4. Ensuring email delivery and preventing duplicates

Ensuring reliable delivery and preventing duplicates requires a combination of idempotent operations, robust workflow orchestration, and state tracking.

**Ensuring Delivery for All Users:**

1.  **Idempotent Operations**: All steps in the email generation and sending process should be designed to be idempotent. This means that performing an operation multiple times has the same effect as performing it once.
    *   **Email Rendering**: The rendering service should produce the same HTML for the same input data.
    *   **Email Sending**: The email sending service (e.g., SES) should ideally deduplicate based on a message ID or provide mechanisms to prevent sending the same email twice within a short window. If not, our system must ensure it only calls the sender once per unique digest.

2.  **Workflow Orchestration (Airflow/Temporal)**:
    *   **Task Retries**: The orchestrator is configured to automatically retry failed tasks (e.g., fetching user data, rendering, sending). This handles transient network issues, temporary database unavailability, or worker crashes.
    *   **Checkpointing/State Management**: The orchestrator maintains the state of the overall digest generation. It knows which users have been processed, which are pending, and which have failed.
    *   **Dead-Letter Queues (DLQs)**: For persistent failures (e.g., malformed user data, unrecoverable rendering errors), messages can be moved to a DLQ for manual inspection and reprocessing.
    *   **Batching and Checkpoints**: The Daily Digest Orchestrator will divide the total active users into smaller batches. After each batch is successfully processed and emails are sent, the orchestrator can record this progress. If the orchestrator itself fails, it can resume from the last successful checkpoint.

3.  **"Last Sent" Timestamp in PostgreSQL**:
    *   We maintain a `last_digest_sent_at` timestamp in the `users` table in PostgreSQL.
    *   The orchestrator or the User Batch Processor will only consider users whose `last_digest_sent_at` is older than the current digest period (e.g., 24 hours ago).
    *   **Atomicity**: After an email is successfully sent for a user, this timestamp is updated *atomically* in PostgreSQL. This update should be part of the final successful step for a user's digest.

    ```sql
    -- Example PostgreSQL schema for users table
    CREATE TABLE users (
        id UUID PRIMARY KEY,
        email TEXT NOT NULL,
        is_active BOOLEAN DEFAULT TRUE,
        last_digest_sent_at TIMESTAMP WITH TIME ZONE,
        -- ... other user details
    );
    ```

4.  **Monitoring and Alerting**:
    *   Comprehensive monitoring of the entire pipeline (Kafka lag, stream processor health, NoSQL database latency, worker success/failure rates, email sending service metrics).
    *   Alerts for prolonged processing times, high error rates, or significant backlogs in any queue. This allows operators to intervene if automated retries aren't sufficient.

**Preventing Duplicate Emails:**

1.  **Unique Digest ID**: Generate a unique ID for each digest attempt for a specific user and date. This ID can be passed through the entire pipeline.
    *   Example: `user_id-YYYY-MM-DD-digest-v1`

2.  **Email Sending Service Deduplication**:
    *   Many professional email sending services (like AWS SES) allow you to specify a `Message-ID` or `X-SES-Configuration-Set` header with a unique identifier. They can then use this to prevent sending the same email multiple times within a certain window.
    *   If the email sending service doesn't offer this, our Email Sending Service wrapper should implement it. Before calling the external service, it checks if an email with the same `Unique Digest ID` has already been successfully sent for that user and date.

3.  **State Tracking for Sent Digests**:
    *   The `last_digest_sent_at` timestamp in PostgreSQL is crucial here. A user is only eligible for a new digest if their `last_digest_sent_at` is before the current digest period.
    *   When a digest is successfully sent, the `last_digest_sent_at` is updated. If a worker crashes *after* sending the email but *before* updating this timestamp, a retry might pick up the user again. This is where idempotency and external email service deduplication become vital.
    *   **Transactional Update**: The update of `last_digest_sent_at` should be as close as possible to the actual email send operation. Ideally, the `User Batch Processor` would:
        1.  Fetch user data.
        2.  Generate digest content.
        3.  Call Email Sending Service (passing `Unique Digest ID`).
        4.  **ONLY IF** email sending is confirmed successful, update `last_digest_sent_at` for that user in PostgreSQL. This update should be a single, atomic operation.

    ```python
    # Pseudocode for User Batch Processor logic
    def process_user_digest(user_id, digest_date):
        # 1. Check if digest already sent for this period (optional, for extra safety)
        #    Could query PostgreSQL or a dedicated "sent_digests" table in Cassandra
        #    If already sent, return.

        # 2. Retrieve aggregated data
        digest_data = cassandra_client.get_user_digest_summary(user_id, digest_date)
        if not digest_data:
            # No activity for this user, skip sending digest
            return

        # 3. Render email
        email_html = email_rendering_service.render(user_id, digest_data)

        # 4. Generate unique ID for this specific digest attempt
        unique_digest_id = f"{user_id}-{digest_date.isoformat()}-digest"

        try:
            # 5. Send email (idempotent call to external service)
            email_sending_service.send_email(
                to_email=user.email,
                subject="Your Daily Digest",
                html_body=email_html,
                message_id=unique_digest_id # Used for deduplication by external service
            )

            # 6. Update last_digest_sent_at in PostgreSQL
            #    This is the critical step to mark completion.
            pg_client.update_user_last_digest_sent_at(user_id, datetime.now())

        except Exception as e:
            logger.error(f"Failed to send digest for user {user_id}: {e}")
            # The orchestrator will retry this user/task
            raise # Re-raise to signal failure to orchestrator
    ```

4.  **Graceful Handling of "No Activity"**: If a user has no activity events for the day, the system should ideally not send an empty email. The stream processor can filter these out, or the User Batch Processor can check if `digest_data` is empty before proceeding to render/send.

**Trade-offs:**

*   **Increased Complexity**: The proposed system is significantly more complex than the original, introducing several new distributed systems (Kafka, Flink, Cassandra). This means more components to monitor, manage, and troubleshoot.
*   **Eventual Consistency**: The pre-aggregated data in Cassandra/DynamoDB will be eventually consistent with the raw events. There might be a slight delay (seconds to minutes) between an event occurring and it appearing in the aggregated digest data. For a daily digest, this is acceptable.
*   **Data Duplication**: Data is duplicated across Kafka, the stream processor's state, Cassandra, and potentially Redis. This is a common trade-off in highly scalable systems for performance.
*   **Cost**: Operating a distributed stream processing pipeline and NoSQL database will be more expensive than just running PostgreSQL.

**What breaks first at 10x scale:**

At 10x scale (tens of millions of users, hundreds of millions of events daily, potentially billions of events), the bottlenecks would likely shift:

1.  **Kafka/Kinesis Throughput**: While highly scalable, the raw event ingestion rate could become a bottleneck if not properly provisioned and sharded. High message rates and large message sizes can strain brokers.
2.  **Stream Processor State Management**: Flink/Spark Streaming's ability to maintain state (e.g., for 24-hour windows for millions of users) can become a memory or disk I/O bottleneck if not carefully optimized (e.g., using RocksDB efficiently, proper checkpointing strategy).
3.  **User Digest Data Store Hot Spots**: While Cassandra/DynamoDB are scalable, if activity is heavily skewed towards a small percentage of "super users," those users' partitions could become hot spots, leading to localized performance degradation. Careful data modeling (e.g., further sharding `user_id` if necessary, or using techniques like "salted" partition keys) would be crucial.
4.  **Orchestrator Overhead**: Airflow/Temporal might struggle with scheduling and managing millions of individual tasks if not designed for massive fan-out. Temporal is generally better suited for very high-scale workflows than Airflow.
5.  **Email Sending Service Rate Limits**: Even third-party services like SES have rate limits. Sending tens of millions of emails in a short window might require pre-warming or negotiating higher limits.

### Going further: Customizable digest frequency and event types

Adapting the proposed system to customizable digest frequency (hourly, weekly) and event types requires extending the stream processing logic and the data model.

1.  **Flexible Stream Processing (Flink/Spark Streaming)**:
    *   **User Preferences Store**: Introduce a new data store (e.g., a dedicated table in PostgreSQL or a separate NoSQL store like DynamoDB) to store user preferences for digest frequency and event types. This store would be consulted by the stream processor.
    *   **Stateful Aggregation per Frequency**: The stream processor would need to maintain multiple aggregation windows per user based on their chosen frequency.
        *   For hourly digests: Aggregate events in 1-hour windows.
        *   For daily digests: Aggregate events in 24-hour windows.
        *   For weekly digests: Aggregate events in 7-day windows.
    *   **Dynamic Aggregation Logic**: The stream processor would need to dynamically apply filtering based on `event_type` preferences stored for each user.
        *   Example: If User A only wants `new_post` and `mention` events, the processor would ignore `direct_message` events for their digest.
    *   **Output to Multiple Data Stores/Tables**: The stream processor could write to different tables in the User Digest Data Store, or the same table with an additional `frequency` column.

2.  **Extended User Digest Data Store Schema**:
    *   The `user_daily_digest_summary` table would need to be generalized.

    ```sql
    CREATE TABLE user_digest_summary (
        user_id UUID,
        digest_period_start TIMESTAMP, -- e.g., start of hour, day, week
        frequency TEXT,              -- 'hourly', 'daily', 'weekly'
        event_type_preferences SET<TEXT>, -- e.g., {'new_post', 'mention'}
        -- Primary key to allow efficient lookup by user, period, and frequency
        PRIMARY KEY ((user_id, frequency), digest_period_start)
    ) WITH CLUSTERING ORDER BY (digest_period_start DESC);
    ```
    *   The actual aggregated data (e.g., `new_posts_count`, `mentions_list`) would become columns in this table, but only *relevant* columns would be populated based on `event_type_preferences`. Alternatively, a single `aggregated_payload JSONB` column could store the flexible summary.

3.  **Flexible Orchestration and Scheduling**:
    *   **Triggering**: The Daily Digest Orchestrator would need to become a "Digest Generation Orchestrator" that triggers based on different schedules.
        *   Hourly: A cron-like job triggers hourly batches.
        *   Daily: The existing daily trigger.
        *   Weekly: A weekly trigger.
    *   **User Grouping**: The orchestrator would query the `User Preferences Store` to identify which users are due for which frequency of digest. It would then create distinct batches for hourly, daily, and weekly users.
    *   **Batch Processor Adaptation**: The User Batch Processor would be modified to accept `frequency` as a parameter. When fetching data from `user_digest_summary`, it would use `user_id`, `frequency`, and the appropriate `digest_period_start` to retrieve the correct summary.

4.  **Refined Data Access Pattern**:
    *   When a User Batch Processor worker is triggered for, say, "hourly digests for 10 AM", it would:
        1.  Fetch a batch of users configured for hourly digests.
        2.  For each user, query `user_digest_summary` with `user_id`, `frequency='hourly'`, and `digest_period_start` for the 10 AM hour.
        3.  The `event_type_preferences` column could be used by the rendering service to further filter or customize the digest content, or the stream processor could have already applied this filter during aggregation.

**Adaptation Summary:**

*   **Stream Processor**: Becomes more complex, maintaining multiple aggregation windows and applying dynamic filtering based on user preferences. This is where the core logic for customization resides.
*   **Data Store**: The schema needs to accommodate `frequency` and `event_type_preferences`, potentially leading to more complex queries or a more generalized `JSONB` payload for aggregated data.
*   **Orchestrator**: Becomes multi-scheduled, triggering different workflows for different frequencies and grouping users accordingly.
*   **Batch Processor**: Becomes frequency-aware, fetching data based on the specific digest period and frequency.

This approach avoids reintroducing scalability bottlenecks because the heavy lifting of aggregation and filtering is still performed by the horizontally scalable stream processor, and data retrieval remains a fast primary key lookup in the NoSQL store. The complexity shifts to the stream processing logic and the orchestration layer, which are designed to handle such distributed workloads.
