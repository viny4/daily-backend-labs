## Scenario

Your team maintains a critical internal service responsible for generating high-resolution PDF invoices for enterprise customers. This service is invoked via an API endpoint, which queues a job to render a PDF using a third-party rendering library running in a Docker container, then stores the generated PDF in an S3 bucket. Finally, a link to the PDF is emailed to the customer.

Currently, the service runs on a single EC2 instance, processing jobs sequentially. As your customer base grows, the number of invoice generation requests has increased dramatically. During peak times (e.g., month-end), the queue backlog grows very large, leading to significant delays in invoice delivery, sometimes exceeding several hours. Customers are complaining about late invoices, impacting their internal processes.

The third-party PDF rendering library is CPU and memory intensive, taking 20-60 seconds to render a single invoice, depending on its complexity. The current EC2 instance frequently hits 100% CPU utilization and high memory pressure during these peak periods. Your goal is to improve the scalability and reliability of this invoice generation process to handle increased demand without manual intervention.

## Requirements

The new solution must:
*   **Scale automatically** to handle fluctuating demand, especially during month-end peaks, without manual intervention.
*   **Reduce invoice generation latency** such that most invoices are delivered within 10 minutes, even during peak load.
*   **Be resilient to individual worker failures**; if a rendering process crashes, the invoice generation should still complete.
*   **Keep operational overhead low** for your team.

## Deliverables

1.  Outline a high-level AWS architecture diagram (can be text-based using ASCII art or simply a list of services and their connections) that addresses the requirements.
2.  Describe the specific AWS services you would use for:
    *   **Queueing incoming invoice generation requests.**
    *   **Orchestrating the execution of the PDF rendering jobs.**
    *   **Running the containerized PDF rendering application.**
3.  Explain how this new architecture would handle a sudden spike of 1,000 invoice generation requests within a 5-minute window.

## Going further

Considering the CPU and memory intensive nature of the PDF rendering, explain how you would monitor the health and performance of your rendering workers and what specific metrics you would track to proactively identify and address bottlenecks or failures in the new architecture.

### 2. Specific AWS Services

#### Queueing incoming invoice generation requests

We would use **Amazon SQS (Simple Queue Service)** for queuing incoming invoice generation requests.

**Why SQS?**
*   **Decoupling:** SQS effectively decouples the API endpoint from the rendering workers. The API can quickly enqueue a request and respond, without waiting for the rendering process to complete.
*   **Scalability:** SQS is a fully managed service that scales automatically to handle any number of messages. It can absorb sudden spikes in requests without dropping messages.
*   **Durability:** Messages are redundantly stored across multiple availability zones until they are processed and deleted, ensuring no requests are lost even if workers fail.
*   **Reliability:** It supports standard queues for high throughput and at-least-once delivery, which is suitable for this scenario where occasional duplicate processing is acceptable (idempotent rendering is a good practice here).
*   **Integration:** SQS integrates seamlessly with other AWS services, particularly ECS, allowing for easy auto-scaling based on queue depth.

#### Orchestrating the execution of the PDF rendering jobs

We would use **Amazon ECS (Elastic Container Service) with Fargate launch type** for orchestrating the execution of the PDF rendering jobs.

**Why ECS Fargate?**
*   **Container Orchestration:** ECS is a highly scalable and fast container management service that makes it easy to run, stop, and manage Docker containers on a cluster.
*   **Fargate (Serverless Containers):** Fargate eliminates the need to provision, configure, and scale EC2 instances for the container hosts. AWS manages the underlying infrastructure, significantly reducing operational overhead. This directly addresses the requirement for low operational overhead.
*   **Integration with SQS:** ECS services can be configured to auto-scale based on SQS queue depth. This means as the number of messages in the queue increases, ECS Fargate will automatically launch more rendering tasks, and as the queue drains, it will scale down, saving costs.
*   **Task Definition:** We can define the CPU and memory requirements for each rendering task within the ECS Task Definition, ensuring the rendering library has sufficient resources.
*   **Resilience:** If a Fargate task (rendering process) crashes, ECS will automatically attempt to restart it or launch a new one, ensuring the job can be retried. Combined with SQS's visibility timeout and dead-letter queue (DLQ) capabilities, this ensures resilience to individual worker failures.

#### Running the containerized PDF rendering application

We would use **Docker containers** managed by **Amazon ECS Fargate** for running the containerized PDF rendering application.

**Why Docker containers on ECS Fargate?**
*   **Containerization:** Docker provides a consistent and isolated environment for the PDF rendering library and its dependencies. This eliminates "it works on my machine" issues and simplifies deployment.
*   **Portability:** The Docker image can be built once and run anywhere, including locally for development and testing, and on ECS for production.
*   **Resource Isolation:** Each rendering job runs in its own container, isolating it from other jobs and preventing resource contention or library conflicts.
*   **Scalability:** As mentioned, ECS Fargate can launch many instances of this container concurrently, allowing for parallel processing of invoices.
*   **Cost-Effectiveness:** Fargate's pay-per-second billing for CPU and memory resources consumed by the containers means we only pay for the resources used during the actual rendering process, which is ideal for bursty workloads.

### 3. Handling a sudden spike of 1,000 invoice generation requests

1.  **Ingestion:** The 1,000 invoice generation requests hit the API Gateway and are processed by the initial Lambda function. This Lambda function quickly validates the requests and enqueues 1,000 messages into the **SQS Queue**. The Lambda function is highly scalable and can handle this ingestion rate without issues.
2.  **Queue Absorption:** The SQS queue immediately absorbs all 1,000 messages. SQS is designed for high throughput and can handle millions of messages per second, so this spike will not overwhelm the queue itself. The messages will remain durable in the queue.
3.  **Auto-Scaling Trigger:** The **ECS Fargate Service** is configured with an auto-scaling policy based on the SQS queue depth. As the queue depth rapidly increases from 0 to 1,000 messages, the auto-scaling policy will detect this change.
4.  **Worker Provisioning:** The auto-scaling policy will trigger an increase in the desired count of ECS Fargate tasks. Fargate will quickly provision new container instances (tasks) to process the messages. The speed of provisioning depends on the configured scaling policies (e.g., step scaling, target tracking) and the specific resource requirements, but Fargate is generally fast at scaling out.
5.  **Parallel Processing:** Each newly launched Fargate task will poll the SQS queue, retrieve a message (representing an invoice generation request), and start rendering a PDF. Given the 20-60 second rendering time, if we assume an average of 40 seconds per invoice, and we want to process 1,000 invoices within 10 minutes (600 seconds), we would need approximately `1000 invoices * 40 seconds/invoice / 600 seconds = ~67 concurrent workers`. The auto-scaling will aim to reach this number of workers (or more, depending on configuration) to drain the queue efficiently.
6.  **Invoice Delivery:** As PDFs are rendered, they are uploaded to S3. The S3 bucket is configured to trigger a Lambda function on new object creation. This post-processing Lambda function retrieves the S3 link and sends the email notification via SES. This final step is also serverless and highly scalable.

This architecture ensures that the system can scale out rapidly to process the 1,000 requests in parallel, significantly reducing the overall processing time and meeting the 10-minute latency requirement. As the queue drains, Fargate tasks will automatically scale down, optimizing costs.

### Going further: Monitoring health and performance of rendering workers

To proactively identify and address bottlenecks or failures in the new architecture, we would leverage **Amazon CloudWatch** for monitoring and alarming.

#### Specific AWS Services for Monitoring:

*   **CloudWatch Metrics:** Collects metrics from all AWS services.
*   **CloudWatch Logs:** Centralized logging for ECS tasks and Lambda functions.
*   **CloudWatch Alarms:** Triggers notifications based on metric thresholds.
*   **CloudWatch Dashboards:** Visualizes key metrics for quick operational insights.
*   **AWS X-Ray:** For distributed tracing to understand end-to-end latency and identify bottlenecks across services (API Gateway, Lambda, SQS, ECS, S3).

#### Specific Metrics to Track:

1.  **SQS Queue Metrics (for overall system health and backlog):**
    *   **`ApproximateNumberOfMessagesVisible`**: The number of messages available for retrieval. A consistently high or growing value indicates a backlog and that workers are not keeping up.
    *   **`ApproximateNumberOfMessagesNotVisible`**: The number of messages currently being processed by workers. A high value here indicates active processing.
    *   **`ApproximateNumberOfMessagesDelayed`**: If using delayed queues, this shows messages waiting to become visible.
    *   **`NumberOfMessagesSent`**: Rate of incoming requests.
    *   **`NumberOfMessagesReceived`**: Rate of messages being picked up by workers.
    *   **`NumberOfMessagesDeleted`**: Rate of messages successfully processed and deleted.
    *   **Alarms:**
        *   `ApproximateNumberOfMessagesVisible` > X for Y minutes (e.g., > 100 for 5 minutes) -> indicates backlog.
        *   `NumberOfMessagesSent` significantly higher than `NumberOfMessagesDeleted` for extended periods -> indicates processing bottleneck.

2.  **ECS Fargate Task Metrics (for worker health and performance):**
    *   **`CPUUtilization` (per task/service)**: Percentage of allocated CPU being used. Consistently high (e.g., >90%) indicates CPU-bound tasks, potentially requiring more CPU allocation per task or more tasks.
    *   **`MemoryUtilization` (per task/service)**: Percentage of allocated memory being used. Consistently high (e.g., >90%) indicates memory-bound tasks, potentially requiring more memory allocation per task.
    *   **`RunningTaskCount`**: Number of active rendering tasks. Monitor this to ensure auto-scaling is functioning as expected.
    *   **`StoppedTaskCount`**: Number of tasks that stopped. Investigate reasons for stopping (e.g., `STOPPED_REASON`).
    *   **`HealthCheckStatus`**: If health checks are configured, this indicates task health.
    *   **Alarms:**
        *   `CPUUtilization` > 95% for 5 minutes -> indicates potential CPU bottleneck.
        *   `MemoryUtilization` > 90% for 5 minutes -> indicates potential memory bottleneck.
        *   `RunningTaskCount` not scaling up when `ApproximateNumberOfMessagesVisible` is high -> indicates auto-scaling misconfiguration or limits hit.
        *   `StoppedTaskCount` increasing rapidly -> indicates worker crashes.

3.  **Application-Specific Metrics (from within the Docker container):**
    *   **`InvoiceRenderTime`**: Custom metric (published to CloudWatch via Embedded Metric Format or CloudWatch Agent) tracking the duration of each PDF rendering job. This is crucial for understanding actual latency.
    *   **`InvoiceRenderSuccessCount` / `InvoiceRenderFailureCount`**: Custom metrics to track successful vs. failed rendering attempts.
    *   **`PDFSizeGenerated`**: Custom metric to understand the output size, which might correlate with rendering time or resource usage.
    *   **Logs (from container stdout/stderr)**: Structured logs (JSON) pushed to CloudWatch Logs, containing details about each rendering job (e.g., invoice ID, start time, end time, errors, resource usage within the container).
    *   **Alarms:**
        *   `InvoiceRenderTime` (p90 or p99) > 10 minutes -> indicates latency issues.
        *   `InvoiceRenderFailureCount` increasing rapidly -> indicates recurring rendering errors.

#### Proactive Identification and Addressing:

*   **Dashboards:** Create CloudWatch Dashboards combining SQS queue depth, ECS task CPU/Memory utilization, and custom `InvoiceRenderTime` metrics. This provides a single pane of glass for operational health.
*   **Alarms and Notifications:** Configure CloudWatch Alarms on critical metrics (e.g., high SQS backlog, high CPU/memory utilization, increased rendering failures, high `InvoiceRenderTime`). These alarms should notify the team via SNS (e.g., email, Slack integration) to prompt investigation.
*   **Log Analysis:** Use CloudWatch Logs Insights to query and analyze logs for specific error patterns, slow rendering jobs, or resource exhaustion messages from the rendering library.
*   **X-Ray Tracing:** Use X-Ray to trace individual requests from API Gateway through Lambda, SQS, ECS, and S3. This helps pinpoint exactly which stage of the process is introducing latency or failing.
*   **Scaling Adjustments:** If `CPUUtilization` or `MemoryUtilization` consistently hit thresholds, it might indicate that the allocated resources per Fargate task are insufficient, and we should increase the CPU/memory in the ECS Task Definition. If the SQS backlog grows despite high `CPUUtilization` across many tasks, it suggests the auto-scaling policy needs to be more aggressive or the maximum number of tasks needs to be increased.
*   **Dead-Letter Queue (DLQ):** Configure a DLQ for the SQS queue. Messages that fail to be processed after a certain number of retries (e.g., due to persistent rendering errors) will be moved to the DLQ. An alarm on the DLQ's `ApproximateNumberOfMessagesVisible` will alert the team to investigate and manually reprocess or fix the underlying issue.

By implementing this comprehensive monitoring strategy, the team can gain deep insights into the system's performance, quickly detect anomalies, and proactively address bottlenecks or failures before they significantly impact customers.
