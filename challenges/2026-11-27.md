## Scenario

Your team maintains a B2B SaaS platform that helps event organizers manage attendee registrations. A core feature allows organizers to upload a CSV file containing a list of attendees, which then triggers a batch process to import these attendees into the system and send them confirmation emails.

Currently, this process is handled by a single long-running EC2 instance. When an organizer uploads a file, a script on this instance processes it sequentially. While this worked initially, a popular annual conference is now using your platform, and they frequently upload large CSV files (up to 500,000 rows) with attendee lists. During peak times (e.g., a few weeks before the conference), multiple organizers upload files simultaneously. This often leads to:

1.  **Long processing queues:** Uploads can sit for minutes or even hours before processing begins, leading to a poor user experience.
2.  **Resource exhaustion:** The single EC2 instance occasionally runs out of memory or CPU, causing processing to fail or become extremely slow.
3.  **Lack of resilience:** If the instance fails during processing, incomplete imports and un-sent emails require manual intervention.

Your task is to refactor this attendee import workflow using AWS serverless technologies to improve scalability, reliability, and reduce operational overhead.

## Requirements

The new solution must:

*   Automatically scale to handle multiple large file uploads concurrently without manual intervention.
*   Be resilient to individual processing failures, allowing retries or dead-letter queuing.
*   Minimize the operational burden of managing servers.
*   Keep the end-to-end processing latency for a 10,000-row CSV under 60 seconds, even when 5 other similar files are being processed concurrently.
*   Assume the CSV parsing and email sending logic already exist as Python functions; focus on the infrastructure surrounding them.

## Deliverables

1.  A high-level architectural diagram (can be text-based) outlining the AWS services used and their interaction for the new attendee import workflow.
2.  A brief explanation of how concurrency is handled and how the solution scales under heavy load.
3.  A description of how the system handles errors during the processing of a single attendee row (e.g., invalid email format).

### 1. High-level architectural diagram

         |                           |

         | (via signed URL)          |
         V                           |
+------------------------------------+
|         AWS S3 Bucket              |

+------------------------------------+
         |

         | (configured on bucket)
         V
+------------------------------------+

         |    parses, processes rows
         |    (e.g., sends to another SQS for individual row processing)
         V
+------------------------------------+

         |    - Stores in DynamoDB/RDS
         |    - Sends confirmation email (via SES)
         V

**Explanation:**

1.  **S3 for Storage:** Organizers upload CSV files directly to an S3 bucket. This offloads file storage from the main application and provides a highly durable, scalable, and cost-effective storage solution. The web application generates a pre-signed S3 URL, allowing the client-side browser to upload directly to S3 without proxying through the backend, improving upload performance.
2.  **S3 Event Notifications:** When a new CSV file is successfully uploaded to S3, an S3 event notification is configured to send a message to an SQS queue. This decouples the upload event from the processing logic.
3.  **SQS for Decoupling and Buffering (File Level):** The `attendee-import-queue` acts as a buffer for incoming file processing requests. This ensures that even if multiple files are uploaded simultaneously, they are queued reliably and processed eventually. It also provides automatic retries for the Lambda function if it fails to process a message.
4.  **Lambda for File Processing (`AttendeeFileProcessor`):** This Lambda function is triggered by messages in the `attendee-import-queue`. Its primary responsibility is to:
    *   Download the CSV file from S3.
    *   Parse the CSV file.
    *   For each row (attendee), extract relevant data.
    *   Send each attendee's data as a separate message to another SQS queue (`attendee-row-processing-queue`). This "fan-out" pattern allows individual rows to be processed in parallel.
5.  **SQS for Decoupling and Buffering (Row Level):** The `attendee-row-processing-queue` buffers individual attendee records. This is crucial for handling the "fan-out" from the file processor and allows the row processing Lambda to scale independently.
6.  **Lambda for Row Processing (`AttendeeRowProcessor`):** This Lambda function is triggered by messages in the `attendee-row-processing-queue`. Each invocation processes a single attendee record. It performs the core business logic:
    *   Validates attendee data (e.g., email format).
    *   Stores the attendee record in a database (e.g., DynamoDB for NoSQL scalability or RDS for relational data).
    *   Sends a confirmation email using AWS SES (Simple Email Service).
7.  **DynamoDB/RDS and SES:** These are the final destinations for the processed data and the mechanism for sending emails, respectively. They are highly scalable and managed services.

### 2. How concurrency is handled and how the solution scales under heavy load

The solution leverages the inherent scalability of AWS serverless services, primarily SQS and Lambda, to handle concurrency and heavy load:

*   **SQS as a Buffer and Scalability Driver:**
    *   When multiple organizers upload files simultaneously, S3 sends multiple `ObjectCreated` events to the `attendee-import-queue`. SQS can handle a massive number of messages per second, acting as an elastic buffer.
    *   Similarly, when the `AttendeeFileProcessor` fans out individual rows, the `attendee-row-processing-queue` buffers these messages.
*   **Lambda's Concurrent Execution Model:**
    *   Both `AttendeeFileProcessor` and `AttendeeRowProcessor` Lambda functions are configured to be triggered by SQS. When there are messages in the queue, Lambda automatically scales up the number of concurrent invocations to process them.
    *   For `AttendeeFileProcessor`, if 5 files are uploaded concurrently, SQS will have 5 messages. Lambda will likely invoke 5 instances of this function in parallel, each processing a different file.
    *   For `AttendeeRowProcessor`, if a file with 10,000 rows is processed, the `AttendeeFileProcessor` will send 10,000 messages to the `attendee-row-processing-queue`. Lambda will then spin up many concurrent instances of `AttendeeRowProcessor` (up to the configured concurrency limit and regional quotas) to process these 10,000 messages in parallel.
    *   Lambda's default concurrency limit per region is 1,000, which can be increased upon request. This allows for thousands of attendee rows to be processed simultaneously across many Lambda instances.
*   **Decoupling with SQS:** By using SQS between the file upload, file parsing, and row processing steps, each stage can operate and scale independently. A backlog in one stage doesn't directly block preceding stages.
*   **Managed Services:** S3, SQS, Lambda, DynamoDB, and SES are all fully managed services. AWS automatically handles the underlying infrastructure, patching, and scaling, eliminating the operational burden of managing servers.

**Example for 10,000-row CSV under 60 seconds with 5 concurrent files:**

1.  **File Upload:** The 5 files are uploaded to S3.
2.  **File Processing:** S3 triggers 5 messages in `attendee-import-queue`. Lambda invokes 5 `AttendeeFileProcessor` instances concurrently. Each instance downloads its 10,000-row CSV, parses it, and sends 10,000 messages to `attendee-row-processing-queue`. Assuming parsing and SQS sending takes 10-15 seconds per file, this step completes quickly for all 5 files.
3.  **Row Processing:** The `attendee-row-processing-queue` now contains 50,000 messages (5 files \* 10,000 rows/file). Lambda's SQS integration will automatically scale up `AttendeeRowProcessor` instances. If each row takes, say, 100ms to process (database write + email send) and Lambda can run 1,000 concurrent instances, it can process 1,000 rows per 100ms, or 10,000 rows per second. Processing 50,000 rows would then take approximately 5 seconds.
    *   (100ms/row * 10,000 rows) / 1,000 concurrent Lambdas = 1 second for a single file's rows if all 1,000 Lambdas were dedicated to it.
    *   With 50,000 rows, and 1,000 concurrent Lambdas, the total time for all rows to be processed would be roughly (50,000 rows * 100ms/row) / 1,000 concurrent Lambdas = 5 seconds.
    *   This demonstrates that the row-level parallelism is highly effective, allowing the end-to-end latency for a 10,000-row file to remain well under 60 seconds, even with other files processed concurrently.

### 3. How the system handles errors during the processing of a single attendee row

The system is designed with multiple layers of error handling, particularly for individual attendee row processing:

1.  **Lambda Retry Mechanism (SQS Integration):**
    *   When an `AttendeeRowProcessor` Lambda invocation fails (e.g., due to an unhandled exception, network timeout, or transient database error), the message is not deleted from the `attendee-row-processing-queue`.
    *   SQS will automatically make the message visible again after a configurable `VisibilityTimeout`.
    *   Lambda will then attempt to re-process the message. This provides automatic retries for transient errors without any custom code.
    *   The number of retries can be controlled by configuring the `MaxReceiveCount` on the SQS queue's Redrive Policy.

2.  **Dead-Letter Queue (DLQ):**
    *   To prevent poison pill messages from endlessly retrying and consuming resources, the `attendee-row-processing-queue` is configured with a Redrive Policy that points to a Dead-Letter Queue (DLQ), e.g., `attendee-row-processing-dlq`.
    *   If a message fails to be processed successfully after the `MaxReceiveCount` (e.g., 3 retries), SQS automatically moves the message to the DLQ.
    *   Messages in the DLQ can then be inspected by developers or operations teams. This allows for manual intervention, debugging, or re-processing after a fix.
    *   **Example:** If an attendee row has an invalid email format that causes a consistent validation error, it will eventually land in the DLQ.

3.  **Idempotency:**
    *   It's crucial that the `AttendeeRowProcessor` function is **idempotent**. This means that processing the same message multiple times (due to retries) should produce the same result and not cause duplicates or incorrect state changes.
    *   **Implementation:** When storing attendee data, use a unique identifier (e.g., a combination of `upload_id` and `row_number` from the CSV, or a generated UUID) as the primary key in DynamoDB or a unique constraint in RDS. For email sending, ensure the email service (SES) handles duplicate requests gracefully or include a unique token in the email metadata to prevent sending the same email multiple times for the same logical event.

4.  **Structured Logging and Monitoring:**
    *   Both Lambda functions should emit structured logs (e.g., JSON) to AWS CloudWatch Logs. These logs should include relevant context like the file path, row number, and specific error messages.
    *   CloudWatch Alarms can be set up to monitor the `VisibleMessages` count in the DLQ, alerting operations teams when messages accumulate, indicating a systemic issue.
    *   CloudWatch Metrics can track Lambda errors and invocations, providing visibility into the health of the processing pipeline.

**Example of error handling for an invalid email format:**

1.  An `AttendeeRowProcessor` Lambda instance receives a message for a row with `email: "invalid-email"`.
2.  The Python validation logic inside the Lambda function detects the invalid format and raises an exception.
3.  The Lambda invocation fails. SQS makes the message visible again after the `VisibilityTimeout`.
4.  Lambda retries the message. It fails again.
5.  After the `MaxReceiveCount` (e.g., 3 attempts), SQS moves the message to `attendee-row-processing-dlq`.
6.  An alert fires because the `attendee-row-processing-dlq` has messages.
7.  An engineer inspects the DLQ message, sees the `email: "invalid-email"` in the payload, and understands the issue. They might then manually correct the data or decide to ignore that specific row.

### Going further

Explain the trade-offs between using AWS Lambda for this task versus using an ECS Fargate service, particularly concerning cold start times and maximum execution duration for extremely large files (e.g., 5 million rows).

#### AWS Lambda vs. ECS Fargate for Attendee Import

Both AWS Lambda and ECS Fargate are serverless compute options, but they have different sweet spots.

**AWS Lambda**

*   **Pros:**
    *   **True Serverless:** No servers to manage whatsoever. You only pay for compute time when your code is running.
    *   **Automatic Scaling:** Scales automatically and almost instantaneously from zero to thousands of concurrent executions.
    *   **Cost-Effective for Bursty Workloads:** Ideal for event-driven, intermittent, or highly variable workloads where you don't need compute resources constantly.
    *   **Integrated with AWS Events:** Deep integration with S3, SQS, DynamoDB Streams, etc., making event-driven architectures very natural.
    *   **Operational Overhead:** Extremely low operational overhead.
*   **Cons:**
    *   **Cold Starts:** When a Lambda function hasn't been invoked recently, AWS needs to initialize a new execution environment. This "cold start" can add latency (hundreds of milliseconds to a few seconds, depending on language/runtime and package size) to the first invocation. For our `AttendeeRowProcessor` processing 5 million rows, this is less of an issue because once warmed up, subsequent invocations will likely hit warm containers. However, for `AttendeeFileProcessor` which might only run occasionally, cold starts could add noticeable latency to the start of file processing.
    *   **Maximum Execution Duration:** Lambda functions have a maximum execution duration of **15 minutes**. This is a significant limitation for extremely large files.
        *   For a 5 million row CSV, if the `AttendeeFileProcessor` needs to download, parse, and fan out all 5 million rows to SQS, it might exceed 15 minutes. Even with efficient parsing, downloading a multi-GB file and processing it row by row could take longer.
        *   **Mitigation for Lambda:** For files exceeding the 15-minute limit, the `AttendeeFileProcessor` would need to be redesigned. For example, it could use S3 Select to filter/extract data directly from S3, or it could process the file in chunks, sending messages to SQS for each chunk, and then another Lambda processes those chunks. Alternatively, a step function could orchestrate multiple Lambda invocations to process parts of the file. This adds complexity.
    *   **Memory/CPU Limits:** While configurable, Lambda has practical limits on memory (up to 10GB) and corresponding vCPU. Very CPU-intensive parsing or complex transformations might push these limits.
    *   **Concurrency Limits:** While high (default 1000 per region), a sudden spike of millions of rows might temporarily hit this limit, leading to throttling (messages remaining in SQS until concurrency frees up).

**AWS ECS Fargate**

*   **Pros:**
    *   **No Cold Starts (or minimal):** Fargate containers are provisioned and kept running for the duration of your task. Once a task is running, there are no cold start penalties for subsequent requests/processing within that container.
    *   **Longer Execution Duration:** Fargate tasks can run for much longer durations, effectively limited by the task's lifecycle (e.g., hours or even days if configured). This makes it suitable for processing extremely large files (5 million rows or more) that might take longer than 15 minutes.
    *   **Higher Resource Limits:** Fargate tasks can be provisioned with more CPU (up to 16 vCPU) and memory (up to 120GB) than Lambda, making them suitable for very resource-intensive batch processing.
    *   **More Control:** You have more control over the container environment, including custom runtimes and more complex dependencies.
*   **Cons:**
    *   **Higher Operational Overhead (compared to Lambda):** While Fargate is "serverless" in that you don't manage EC2 instances, you still manage ECS clusters, task definitions, service definitions, scaling policies, and networking (VPC, security groups). It's more involved than just deploying a Lambda function.
    *   **Scaling Model:** Scaling is based on tasks and services. While auto-scaling policies can be configured (e.g., based on SQS queue depth), it's not as instantaneous or granular as Lambda's per-invocation scaling. There's a provisioning time for new Fargate tasks (typically 30 seconds to a few minutes).
    *   **Cost Model:** You pay for the entire duration a Fargate task is running, even if it's idle. For highly intermittent workloads, this can be more expensive than Lambda. For long-running batch jobs, it can be more cost-effective.
    *   **Integration with AWS Events:** While Fargate tasks can be triggered by SQS (via CloudWatch Events or custom polling), it requires more setup than Lambda's native SQS integration.

#### Trade-offs for 5 Million Rows

For a 5 million row CSV, the **15-minute Lambda execution limit** becomes the primary concern for the `AttendeeFileProcessor`.

*   **If using Lambda:**
    *   The `AttendeeFileProcessor` would likely need to be broken down. Instead of processing the entire file, it might just read the first X lines, or use S3 Select to extract specific columns, and then trigger a **Step Functions workflow**. This workflow could then orchestrate multiple Lambda invocations, each processing a chunk of the file or a range of rows. This adds significant architectural complexity to work around the duration limit.
    *   Alternatively, the initial Lambda could trigger an ECS Fargate task specifically for the heavy file parsing, which then fans out to the `attendee-row-processing-queue` for Lambda to handle individual rows. This hybrid approach leverages the strengths of both.

*   **If using ECS Fargate:**
    *   An ECS Fargate task could be launched (triggered by the S3 event via SQS, similar to Lambda) to handle the entire 5 million row CSV parsing and fan-out. It would have ample time (hours if needed) and resources (more CPU/memory) to download the file, parse it, and send 5 million messages to the `attendee-row-processing-queue`.
    *   The `AttendeeRowProcessor` Lambda functions would still be ideal for processing individual rows due to their granular scaling and cost-effectiveness for short-lived tasks.
    *   **Trade-off:** This approach would incur the higher operational overhead of managing ECS Fargate tasks and services for the file processing step, and potentially higher costs if the Fargate task sits idle waiting for files. The provisioning time for a new Fargate task would also add to the initial processing latency for a new file.

**Conclusion for 5 Million Rows:**

For the initial scenario (up to 500,000 rows, 60-second latency), **Lambda is generally preferred** due to its lower operational overhead and cost-effectiveness for bursty, event-driven workloads, provided the `AttendeeFileProcessor` can complete within 15 minutes.

For **extremely large files (e.g., 5 million rows)** where the file parsing and fan-out itself might exceed 15 minutes, **ECS Fargate becomes a more robust and simpler choice for the `AttendeeFileProcessor` component**. The `AttendeeRowProcessor` (for individual rows) would still likely remain a Lambda function due to its superior granular scaling and cost model for short, independent tasks. This would lead to a hybrid architecture.
