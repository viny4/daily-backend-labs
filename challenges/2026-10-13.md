## Scenario

Your team maintains a critical Node.js microservice that acts as an **integration layer** for a large enterprise SaaS platform. This service is responsible for securely ingesting customer data from various external sources (e.g., Salesforce, HubSpot, custom CSV uploads) and transforming it into a standardized internal format before persisting it.

A new critical requirement has emerged: **data transformations are becoming increasingly complex and customer-specific**. Some customers require intricate logic to clean, merge, or enrich their incoming data using custom rules before it hits your internal systems. These rules are defined by customer success engineers as "scripts" (plain JavaScript functions stored in your configuration system) that run within your service.

The current implementation executes these scripts directly using `eval()`, which has become a significant security and performance bottleneck. As the number of customers and the complexity of their scripts grow, you're observing:

1.  **Security vulnerabilities**: Malicious or poorly written scripts can access sensitive environment variables or perform unwanted system operations.
2.  **Performance degradation**: Long-running or CPU-intensive scripts block the event loop, causing request latency spikes for all concurrent data ingestions.
3.  **Lack of isolation**: A failing script for one customer can crash the entire service, impacting other customers.

You need to refactor this part of the service to safely and efficiently execute these customer-defined transformation scripts.

## Requirements

The refactored script execution mechanism must:

*   **Isolate script execution**: Each customer's script must run in an isolated environment, preventing access to the main Node.js process context (e.g., `process`, `require`, file system access).
*   **Enforce resource limits**: Scripts should be capped in terms of execution time and memory consumption to prevent denial-of-service attacks or runaway processes.
*   **Provide a controlled API**: Scripts should only be able to interact with the provided input data and return transformed output. No arbitrary side effects.
*   **Be resilient to script failures**: A script error for one customer should not affect other concurrent script executions or the stability of the main service.
*   **Be written in TypeScript**: Maintain strong typing for inputs and expected outputs of the transformation function.

## Deliverables

1.  A TypeScript module or class that provides a `runTransformationScript` function. This function should accept the script code (as a string), the input data (as a JSON-serializable object), and return the transformed data or throw an error.
2.  Demonstrate how to execute a simple, safe transformation script (e.g., adding a field to the input data) and a script that attempts to access `process.env`, showing that the latter is blocked.
3.  Demonstrate how to enforce a timeout on a deliberately long-running script, ensuring it's terminated within a specified duration.
4.  Define clear TypeScript interfaces for the input data, the expected output data, and any configuration passed to the script runner.

## Going further

How would you monitor and observe the resource usage (CPU, memory, execution time) of individual customer scripts in a production environment, and what strategies would you employ to dynamically adjust resource limits or quarantine problematic scripts without manual intervention?

## Worked answer

### Solution Overview

The core problem is safely executing untrusted JavaScript code with resource constraints. Node.js offers a powerful built-in module for this: `vm`. Specifically, the `vm.runInNewContext` and `vm.Script` APIs allow us to create isolated sandboxes. For more robust isolation and resource limiting, especially CPU and memory, we can leverage Node.js `Worker Threads`. Each script execution will happen in its own worker thread, which provides a separate V8 isolate and event loop, preventing blocking the main thread and offering better control over resource allocation and termination.

We will define a `ScriptRunner` class that encapsulates the logic for creating and managing worker threads for script execution.

### 1. TypeScript Module for `runTransformationScript`

First, let's define the TypeScript interfaces for our data and configuration.

```typescript
// src/types.ts

/**
 * Interface for the input data provided to the transformation script.
 * Must be JSON-serializable.
 */
export interface InputData {
  id: string;
  customerName: string;
  sourceSystem: string;
  payload: Record<string, any>; // Arbitrary customer data
  [key: string]: any; // Allow for additional top-level fields
}

/**
 * Interface for the output data expected from the transformation script.
 * Must be JSON-serializable.
 */
export interface TransformedData {
  id: string;
  transformedAt: string;
  processedPayload: Record<string, any>;
  // Any other fields added by the transformation
  [key: string]: any;
}

/**
 * Configuration for the script runner.
 */
export interface ScriptRunnerConfig {
  /**
   * Maximum execution time for a script in milliseconds.
   * If exceeded, the script will be terminated.
   */
  timeoutMs: number;
  /**
   * Maximum memory allowed for the worker thread in MB.
   * Note: This is a soft limit and relies on OS/Node.js heuristics.
   * More precise control might require external tools or cgroups.
   */
  memoryLimitMb?: number;
}

/**
 * The signature of the transformation function expected from the script.
 * It takes input data and returns transformed data.
 */
export type TransformationFunction = (data: InputData) => TransformedData;
```

Now, let's create the `ScriptRunner` class and the worker script.

```typescript
// src/scriptRunner.ts

import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';
import path from 'path';
import { InputData, TransformedData, ScriptRunnerConfig, TransformationFunction } from './types';

// This is the script that will run in the worker thread.
// It's defined as a separate file to be loaded by the Worker constructor.
// It expects `scriptCode` and `inputData` in `workerData`.
if (!isMainThread) {
  const { scriptCode, inputData } = workerData as { scriptCode: string; inputData: InputData };

  try {
    // Create a new Function from the script code.
    // This provides a clean scope, preventing direct access to the worker's global scope.
    // We explicitly pass `InputData` as the argument type.
    const transformFunction = new Function('data', scriptCode) as TransformationFunction;

    // Execute the transformation function
    const result = transformFunction(inputData);

    // Validate the result type (optional, but good practice)
    if (typeof result !== 'object' || result === null) {
      throw new Error('Transformation script did not return an object.');
    }

    // Send the result back to the main thread
    parentPort?.postMessage({ status: 'success', data: result });
  } catch (error: any) {
    // Send any errors back to the main thread
    parentPort?.postMessage({ status: 'error', message: error.message, stack: error.stack });
  } finally {
    // Ensure the worker exits cleanly
    process.exit(0);
  }
}

/**
 * Manages the execution of transformation scripts in isolated worker threads.
 */
export class ScriptRunner {
  private config: ScriptRunnerConfig;

  constructor(config: ScriptRunnerConfig) {
    this.config = config;
  }

  /**
   * Runs a transformation script in an isolated worker thread.
   *
   * @param scriptCode The JavaScript code of the transformation function (e.g., "return { ...data, newField: 'value' };").
   * @param inputData The input data for the transformation.
   * @returns A Promise that resolves with the transformed data or rejects with an error.
   */
  public async runTransformationScript(
    scriptCode: string,
    inputData: InputData,
  ): Promise<TransformedData> {
    return new Promise((resolve, reject) => {
      // Create a new Worker thread.
      // The `__filename` points to this file, and the `if (!isMainThread)` block
      // above will be executed in the worker.
      const worker = new Worker(__filename, {
        workerData: { scriptCode, inputData },
        // Set resource limits for the worker
        resourceLimits: {
          maxOldGenerationSizeMb: this.config.memoryLimitMb,
          maxYoungGenerationSizeMb: this.config.memoryLimitMb ? this.config.memoryLimitMb / 4 : undefined, // Heuristic
        },
        // Pass environment variables only if explicitly needed and filtered
        env: {}, // Explicitly pass an empty object to prevent inheriting parent env
      });

      let timeoutId: NodeJS.Timeout;

      // Set a timeout to terminate the worker if it runs too long
      timeoutId = setTimeout(() => {
        worker.terminate(); // Forcefully terminate the worker thread
        reject(new Error(`Script execution timed out after ${this.config.timeoutMs}ms.`));
      }, this.config.timeoutMs);

      // Listen for messages from the worker thread
      worker.on('message', (message: { status: string; data?: TransformedData; message?: string; stack?: string }) => {
        clearTimeout(timeoutId); // Clear the timeout if the script finishes
        if (message.status === 'success' && message.data) {
          resolve(message.data);
        } else {
          reject(new Error(`Script error: ${message.message || 'Unknown error'}\n${message.stack || ''}`));
        }
      });

      // Listen for errors from the worker thread itself (e.g., uncaught exceptions)
      worker.on('error', (err) => {
        clearTimeout(timeoutId);
        reject(new Error(`Worker thread error: ${err.message}`));
      });

      // Listen for the worker thread to exit
      worker.on('exit', (code) => {
        clearTimeout(timeoutId);
        if (code !== 0) {
          // If the worker exited with a non-zero code and no error was caught by 'error' listener,
          // it means it was likely terminated by us (timeout) or crashed unexpectedly.
          // If it was terminated by timeout, the reject has already happened.
          // If it crashed, 'error' would usually catch it. This is a fallback.
          reject(new Error(`Worker thread exited with code ${code}`));
        }
      });
    });
  }
}
```

**Explanation:**

1.  **`src/types.ts`**: Defines clear interfaces for `InputData`, `TransformedData`, `ScriptRunnerConfig`, and `TransformationFunction`. This ensures strong typing throughout our application and provides a contract for customer scripts.
2.  **`src/scriptRunner.ts`**:
    *   **Worker Thread Logic (`if (!isMainThread)` block)**: This part of the file runs when it's loaded as a worker thread.
        *   It receives `scriptCode` and `inputData` via `workerData`.
        *   `new Function('data', scriptCode)` is crucial for isolation. It creates a function from the provided string `scriptCode` in its own lexical environment. This function's scope does *not* include the worker's `global` object, `process`, `require`, etc., unless explicitly passed. We only pass `data`. This effectively sandboxes the script.
        *   The script's output is sent back to the main thread using `parentPort?.postMessage`.
        *   Errors are caught and also sent back, ensuring resilience.
        *   `process.exit(0)` ensures the worker thread terminates cleanly after execution.
    *   **`ScriptRunner` Class (Main Thread Logic)**:
        *   `constructor`: Takes `ScriptRunnerConfig` to configure timeouts and memory limits.
        *   `runTransformationScript`:
            *   Creates a `new Worker(__filename, {...})`. Passing `__filename` tells Node.js to load *this very file* as the worker script. The `if (!isMainThread)` block ensures only the worker-specific logic runs in the worker.
            *   `workerData`: This is how we pass the script code and input data to the worker. It's automatically cloned and sent.
            *   `resourceLimits`: This option allows setting soft memory limits for the V8 heap in the worker thread. `maxOldGenerationSizeMb` and `maxYoungGenerationSizeMb` control the size of different parts of the V8 heap. This is a best-effort limit and not a hard guarantee, as Node.js and the OS might still allocate memory outside these limits (e.g., for native code, I/O buffers).
            *   `env: {}`: **Crucially**, we pass an empty `env` object. By default, worker threads inherit environment variables from the parent thread. Setting `env: {}` explicitly prevents this, enhancing security.
            *   **Timeout Mechanism**: `setTimeout` is used to track script execution time. If the script doesn't send a message back before the timeout, `worker.terminate()` is called. `terminate()` is a forceful, synchronous kill of the worker thread, which is essential for preventing runaway scripts from consuming CPU indefinitely.
            *   **Event Listeners**: `worker.on('message')`, `worker.on('error')`, and `worker.on('exit')` handle communication and lifecycle events from the worker, resolving or rejecting the promise accordingly.

async function main() {

### Trade-offs and Scalability

**Trade-offs Accepted:**

1.  **Overhead of Worker Threads**: Creating a new worker thread for each script execution has a non-trivial overhead (memory and CPU) compared to simply using `vm.runInNewContext` in the main thread. This overhead is acceptable and necessary for the required isolation and termination capabilities. For very high throughput scenarios with extremely short-lived scripts, this overhead might become a bottleneck.
2.  **Memory Limits are Soft**: The `resourceLimits` for worker threads are advisory for the V8 heap. They do not prevent the worker from allocating memory outside the V8 heap (e.g., native buffers, C++ addons). Hard memory limits typically require OS-level mechanisms like cgroups (Linux) or containerization.
3.  **No Direct File System/Network Access**: The current setup completely blocks `require` and `process`, meaning scripts cannot perform file I/O, network requests, or other system operations. This is a security feature but also a limitation. If scripts *needed* controlled access to specific resources (e.g., a specific HTTP endpoint to enrich data), we would need to explicitly pass an API for that (e.g., a `fetch` function) into the `new Function`'s scope.
4.  **Serialization Overhead**: Data passed between the main thread and worker threads (via `workerData` and `postMessage`) is serialized and deserialized using the structured clone algorithm. For very large input/output data, this can introduce performance overhead. `SharedArrayBuffer` or `MessageChannel` could offer more advanced options for specific use cases but add complexity.

**What breaks first at ten times the scale:**

At ten times the scale (e.g., 10x more concurrent script executions or 10x more total scripts per second), the primary bottleneck will likely be:

1.  **CPU Contention**: If many scripts are CPU-intensive, even with timeouts, the total CPU usage of the Node.js process (across all worker threads) will spike. While workers prevent blocking the main event loop, the underlying CPU resources are still shared. This could lead to overall system slowdowns or even throttling by the underlying infrastructure.
2.  **Memory Consumption**: Each worker thread consumes a baseline amount of memory (for its V8 isolate, event loop, etc.) plus the memory used by the script itself. If hundreds or thousands of workers are active concurrently, the total memory footprint of the service could become very large, leading to OOM (Out Of Memory) errors or excessive swapping, degrading performance.
3.  **Worker Thread Creation/Teardown Overhead**: The constant creation and destruction of worker threads will incur a performance cost. While Node.js is optimized, there's a limit to how many threads can be efficiently managed.

### Going Further: Monitoring and Dynamic Resource Management

**Monitoring and Observation:**

1.  **Node.js `perf_hooks` and `worker_threads` `performance` API**:
    *   **Execution Time**: The `ScriptRunner` already measures execution time implicitly by using `setTimeout`. For more precise metrics, we could record `Date.now()` before and after `await worker.on('message')` and report the difference.
    *   **CPU Usage**: Node.js worker threads do not expose direct CPU usage metrics per worker. However, we can monitor the overall process CPU usage using tools like `pm2`, `Prometheus Node Exporter`, or `process.cpuUsage()` (though this is for the whole process). To get per-worker CPU, one would need to use OS-level tools (e.g., `top`, `htop` with thread view) or more advanced profiling.
    *   **Memory Usage**:
        *   `worker.resourceLimits`: While these are limits, they don't directly report current usage.
        *   `worker.performance.eventLoopUtilization()`: Can give insights into how busy the worker's event loop is.
        *   `v8.getHeapStatistics()` / `process.memoryUsage()`: Can be called *within the worker thread* and sent back to the main thread via `postMessage` before `process.exit(0)`. This would provide detailed heap and overall memory usage for that specific worker.
        *   **External Monitoring**: Tools like Prometheus, Grafana, Datadog, or New Relic can collect these metrics (via custom exporters or agents) and visualize them.

2.  **Logging**:
    *   Log script start, completion, errors, and resource usage (time, memory) with customer ID, script ID, and execution ID. This allows for post-mortem analysis and identifying problematic scripts.
    *   Structured logging (e.g., JSON logs) is crucial for easy parsing and analysis by log aggregation systems (ELK stack, Splunk, DataDog Logs).

**Strategies for Dynamic Adjustment and Quarantine:**

1.  **Adaptive Timeouts**:
    *   **Observation**: Monitor the average and P99 execution times for each unique script or customer.
    *   **Strategy**: If a script consistently runs quickly (e.g., <100ms), its timeout could be dynamically reduced to, say, 200ms. If a script is known to be complex but legitimate, its timeout could be increased (within reasonable bounds). This requires storing historical performance data.
    *   **Implementation**: A configuration service or database could store `scriptId -> { minTimeoutMs, maxTimeoutMs }` mappings, which the `ScriptRunner` fetches.

2.  **Dynamic Memory Limits**:
    *   **Observation**: Collect memory usage metrics (from `v8.getHeapStatistics()` within the worker) for each script execution.
    *   **Strategy**: Similar to timeouts, adjust `memoryLimitMb` based on historical usage. If a script typically uses 50MB, cap it at 75MB. If it consistently exceeds 200MB, flag it.
    *   **Implementation**: Requires a feedback loop from monitoring to configuration.

3.  **Circuit Breakers and Rate Limiting**:
    *   **Observation**: Track the failure rate (timeouts, errors) per script or per customer.
    *   **Strategy**:
        *   **Circuit Breaker**: If a specific script's failure rate exceeds a threshold (e.g., 5 failures in 1 minute), "open the circuit" for that script, temporarily preventing further executions for a cool-off period. This prevents a continuously failing script from consuming resources.
        *   **Rate Limiting**: Limit the number of concurrent executions for a single customer or a single script type. If a customer tries to run 100 transformations simultaneously, queue them or reject some.
    *   **Implementation**: Use libraries like `opossum` for circuit breakers or implement custom in-memory or distributed rate limiters (e.g., using Redis).

4.  **Quarantining Problematic Scripts**:
    *   **Observation**: Identify scripts that frequently hit resource limits (timeout, memory), have high error rates, or cause unexpected worker crashes.
    *   **Strategy**:
        *   **Automated Disabling**: Automatically disable a script in the configuration system if it consistently misbehaves. Alert customer success engineers to review and fix it.
        *   **Reduced Resource Allocation**: For "yellow-flagged" scripts, run them with stricter resource limits (e.g., lower timeout, lower memory) to minimize their impact if they misbehave.
        *   **Dedicated Resource Pools**: For extremely critical or problematic customers/scripts, consider running them on dedicated worker pools or even separate microservice instances to isolate their impact entirely.
    *   **Implementation**: Requires a centralized configuration store (e.g., Consul, etcd, a database) that the `ScriptRunner` can query for script status and limits. An automated system would update this store based on monitoring data.

5.  **Canary Deployments/A/B Testing for Scripts**:
    *   **Strategy**: When a customer provides a new or updated script, initially run it for a small percentage of their data or in a "dry run" mode, collecting metrics without affecting production data. Gradually increase traffic as confidence grows.
    *   **Implementation**: Requires a robust deployment and routing mechanism for scripts.

By combining robust monitoring with these dynamic strategies, the system can self-regulate, adapt to varying script behaviors, and maintain stability even with increasingly complex and customer-specific data transformations.
