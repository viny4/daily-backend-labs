## Scenario

Your team manages the backend service for a popular online collaboration platform. A core feature allows users to create and collaborate on `documents`. Over time, the `documents` table has grown substantially, now containing hundreds of millions of rows. Each document also has a history of revisions, stored in a separate `document_revisions` table, which is even larger.

Users frequently search for documents they own, or documents they've recently accessed. The application's dashboard displays a list of "My Documents" and "Recently Viewed Documents". The "My Documents" query fetches documents belonging to the authenticated user, ordered by their creation date. The "Recently Viewed Documents" query fetches documents based on a user's `last_accessed_at` timestamp, which is updated every time a user views a document. Both queries need to be performant, even as the tables scale.

The problem you're facing is that the "My Documents" query, which looks something like `SELECT id, title, created_at FROM documents WHERE owner_id = :user_id ORDER BY created_at DESC LIMIT 20;`, has started to degrade. For users with a very large number of documents (e.g., thousands or tens of thousands), this query can take several seconds, sometimes even timing out. The `owner_id` column is already indexed, but it's not enough.

Constraints:
*   The `documents` table currently has ~300 million rows.
*   The `document_revisions` table has ~2 billion rows (though it's not directly involved in *this specific* query, it highlights the scale of the overall system).
*   Latency for these dashboard queries must be under 100ms.
*   The solution should not require significant application-level changes, focusing on database-level optimization.
*   Any solution must be mindful of write performance on the `documents` table, as new documents are created frequently and `last_accessed_at` is updated often.

## Requirements

Optimize the "My Documents" query to consistently achieve sub-100ms latency, even for users with a high volume of documents.

## Worked answer

### 1. SQL `CREATE INDEX` statement

The problem describes a query that filters by `owner_id` and then orders by `created_at`. A composite index on `(owner_id, created_at DESC)` will be most effective. The `DESC` keyword in the index definition matches the `ORDER BY created_at DESC` clause in the query, allowing PostgreSQL to scan the index in the desired order without needing an extra sort step.

```sql
CREATE INDEX idx_documents_owner_created_at_desc ON documents (owner_id, created_at DESC);
```

### 2. `EXPLAIN ANALYZE` output for the original slow query

Let's assume a `documents` table with `id`, `owner_id`, `title`, `created_at`, and `last_accessed_at` columns. We'll also assume an existing index on `owner_id` (e.g., `CREATE INDEX idx_documents_owner_id ON documents (owner_id);`).

Here's a representative `EXPLAIN ANALYZE` output for the original query:

```sql
EXPLAIN ANALYZE SELECT id, title, created_at FROM documents WHERE owner_id = 123 ORDER BY created_at DESC LIMIT 20;
```


**Explanation of the slow query:**

*   **`Bitmap Index Scan on idx_documents_owner_id`**: This step efficiently finds all `owner_id = 123` rows using the existing index.
*   **`Bitmap Heap Scan on documents`**: PostgreSQL then fetches the actual rows from the table based on the bitmap. For a user with many documents (e.g., 50,000 rows), this can involve reading a large number of scattered data blocks, leading to many random I/O operations.
*   **`Sort`**: Crucially, after fetching *all* matching rows, PostgreSQL has to sort them by `created_at DESC`. Even with `LIMIT 20`, if the sort happens *after* fetching all rows, it's an expensive operation, especially if the intermediate result set is large (50,000 rows in this example). The `top-N heapsort` is efficient for small `N`, but it still needs to process all qualifying rows to find the top 20.
*   **High `Execution Time`**: The combined cost of fetching many rows and then sorting them leads to the observed multi-second latency.

### 3. `EXPLAIN ANALYZE` output for the optimized query

After adding the `idx_documents_owner_created_at_desc` index:

```sql
EXPLAIN ANALYZE SELECT id, title, created_at FROM documents WHERE owner_id = 123 ORDER BY created_at DESC LIMIT 20;
```

```
                                                              QUERY PLAN
---------------------------------------------------------------------------------------------------------------------------------------
 Limit  (cost=0.50..15.20 rows=20 width=28) (actual time=0.050..0.150 rows=20 loops=1)
   ->  Index Scan Backward on idx_documents_owner_created_at_desc  (cost=0.50..37500.00 rows=50000 width=28) (actual time=0.048..0.145 rows=20 loops=1)
         Index Cond: (owner_id = 123)
 Planning Time: 0.300 ms
 Execution Time: 0.180 ms
(5 rows)
```

**Explanation of the optimized query:**

*   **`Index Scan Backward on idx_documents_owner_created_at_desc`**: This is the key improvement. PostgreSQL can now use the new composite index directly.
    *   It first filters by `owner_id = 123`.
    *   Because `created_at DESC` is the second column in the index, and the query also orders by `created_at DESC`, PostgreSQL can perform a "backward" scan (or forward scan if the index was `ASC` and query `ASC`) on the index.
    *   This means it reads the index entries *already sorted* in the desired order.
*   **`Limit`**: The `LIMIT 20` clause can be applied immediately after finding the first 20 matching entries in the index. PostgreSQL doesn't need to scan all 50,000 documents for `owner_id = 123` or perform a separate sort. It stops as soon as 20 rows are found.
*   **Low `Execution Time`**: The query now only needs to read a small portion of the index and then fetch the corresponding 20 rows from the table, resulting in sub-millisecond latency.

### 4. Explanation of why the chosen index is effective

The composite index `(owner_id, created_at DESC)` is effective because it allows PostgreSQL to satisfy both the `WHERE` clause (`owner_id = :user_id`) and the `ORDER BY` clause (`created_at DESC`) directly from the index. By storing `created_at` in descending order within each `owner_id` group, the database can perform an "index-only scan" (or at least an index scan that avoids a full table sort) and stop reading as soon as the `LIMIT 20` is met. This avoids fetching and sorting a potentially massive number of rows from the main table, drastically reducing I/O and CPU overhead.

### Going further

#### Trade-offs involved in the proposed solution

1.  **Storage Overhead**:
    *   **Implication**: The new index `idx_documents_owner_created_at_desc` will consume additional disk space. For a table with 300 million rows, an index containing two `bigint` (for `owner_id` and `id` if implicitly included) and one `timestamp` column will be substantial, likely in the order of several gigabytes to tens of gigabytes.
    *   **Breakage at 10x scale**: At 3 billion rows, this index could easily be hundreds of gigabytes, potentially impacting backup/restore times and requiring more disk space.

2.  **Write Performance**:
    *   **Implication**: Every `INSERT` into the `documents` table and every `UPDATE` that modifies `owner_id` or `created_at` will require an update to this new index. This adds a small amount of overhead to write operations.
    *   **Breakage at 10x scale**: If write rates are extremely high (e.g., millions of writes per second), the cumulative overhead of maintaining multiple large indexes can become noticeable, potentially leading to increased write latency or contention. However, for typical web application loads, the impact is usually acceptable, especially given that `created_at` is only set once and `owner_id` rarely changes. Updates to `last_accessed_at` do *not* affect this index.

3.  **Implications for other queries**:
    *   **Positive**: This index could potentially benefit other queries that filter by `owner_id` and order by `created_at DESC`, or even just filter by `owner_id` and need `created_at` as part of the result set (as it's covered by the index).
    *   **Negative**: This specific index does not directly help queries that order by `created_at ASC`, or queries that order by `last_accessed_at`. For the "Recently Viewed Documents" query, a separate index on `(owner_id, last_accessed_at DESC)` would be needed. Adding too many indexes can exacerbate storage and write performance issues.

#### Why a plausible-looking approach is wrong

**Just adding an index on `created_at` (e.g., `CREATE INDEX idx_documents_created_at ON documents (created_at DESC);`) is insufficient.**

*   **Why it seems plausible**: It directly addresses the `ORDER BY` clause.
*   **Why it's wrong**: Without `owner_id` as the leading column, PostgreSQL would have to scan the entire `created_at` index (or a large portion of it) to find the top 20 most recently created documents *across all owners*, and then filter those down by `owner_id = :user_id`. This would be extremely inefficient. The `WHERE` clause on `owner_id` needs to be applied *first* to narrow down the search space. A composite index with `owner_id` as the leading column allows the database to efficiently locate the relevant subset of data before considering the ordering.
