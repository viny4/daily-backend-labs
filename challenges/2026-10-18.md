## Scenario

Your team maintains the backend for a popular online marketplace that facilitates transactions between sellers and buyers. A core component of this system is the `Order Fulfillment Service`, which handles the critical process of transitioning an order from "placed" to "shipped" to "delivered".

Due to rapid growth, the marketplace now processes millions of orders daily. The `Order Fulfillment Service` interacts with various external logistics partners (e.g., FedEx, UPS, local couriers) to retrieve tracking information and update order statuses. Each logistics partner has its own API, and the service polls these APIs periodically to check for status updates for active orders.

The problem is that the polling mechanism is becoming a significant bottleneck. There are now tens of millions of active orders at any given time, and polling all of them frequently is overwhelming the service, leading to increased latency, missed updates, and a high operational cost from API calls to external partners. Furthermore, some logistics partners have strict rate limits, and the current naive polling approach frequently hits these limits, causing further delays.

You've observed that the latency from an order status change at a logistics partner to it being reflected in your system can be up to several hours, which is unacceptable for customer experience.

## Requirements

Design and outline changes to the `Order Fulfillment Service` to efficiently and reliably track order status updates from external logistics partners at scale. Focus on reducing unnecessary API calls, respecting external rate limits, and improving the timeliness of status updates, while handling potential failures gracefully. The solution should operate with millions of active orders and hundreds of thousands of status updates per hour.

Constraints:
*   **Scale:** Tens of millions of active orders.
*   **Concurrency:** Hundreds of thousands of status updates per hour.
*   **External Dependencies:** Rely on external, potentially unreliable, rate-limited logistics partner APIs.
*   **Latency Budget:** Order status updates should be reflected in your system within minutes (ideally <5 minutes) of the external partner reporting them, not hours.
*   **Cost Efficiency:** Minimize unnecessary API calls to external partners.
*   **Fault Tolerance:** The system must continue to operate and eventually process updates even if individual external APIs are temporarily unavailable or return errors.

**Components:**

*   **Order Service:** The primary API for the marketplace, where orders are placed. It publishes initial tracking requests.
*   **Order Tracking Update Request Producer:** When an order is placed or a specific event (e.g., "shipped" status from a seller) occurs, this component publishes a message to the `Tracking Update Queue`.
*   **Tracking Update Queue (Kafka/SQS):** A durable, highly available message queue. It decouples the request producer from the processing logic, handles backpressure, and enables asynchronous processing.
    *   **Topic:** `order_tracking_updates`
*   **Tracking Update Consumer:** Consumes messages from the `Tracking Update Queue` and dispatches them to the `Tracking Update Processor`. Multiple consumers can run in parallel for scalability.
*   **Tracking Update Processor:** The brain of the operation.
    *   **Polling Scheduler:** Decides *when* to poll a specific logistics partner for a specific order. It stores and manages polling intervals and next-poll times.
    *   **Rate Limit Manager:** Tracks and enforces rate limits for each external logistics partner.
    *   **Status Updater:** Processes the received status updates, validates them, and updates the `Order Status Database`. It also publishes internal events (e.g., `OrderShippedEvent`) to other internal services.
*   **External Logistics API Clients:** Specific client implementations for each logistics partner (FedEx, UPS, etc.), encapsulating their API specifics and handling authentication.
*   **Order Status Database:** A persistent store for all order-related information, including the current status, tracking numbers, logistics partner, and metadata for polling (e.g., last polled time, next scheduled poll time, current polling interval).

### 2. Mechanism to Decide When to Poll

Instead of fixed-interval polling, we'll implement an **adaptive, event-driven, and prioritized polling strategy**.

**Core Idea:**
Polling frequency should depend on:
1.  **Order Status:** Orders in early stages (e.g., "placed", "processing") or very late stages ("delivered") need less frequent polling than orders in transit ("shipped", "in_delivery").
2.  **Time Elapsed Since Last Update:** If an order hasn't updated in a while, it might be stuck or simply not moving, warranting a different polling strategy.
3.  **Logistics Partner Reliability/Latency:** Some partners might be slower to update than others.
4.  **External Events:** If we receive a webhook (rare for all partners, but possible for some) or an internal event (e.g., seller marks as shipped), we can trigger an immediate poll.

**Mechanism Details:**

1.  **State-Dependent Polling Intervals:**
    *   We define different polling intervals based on the order's current status.
    *   **Example `polling_intervals` configuration:**
        ```json
        {
          "placed": "24h",
          "processing": "12h",
          "shipped": "15m",       // High priority for in-transit
          "in_delivery": "5m",    // Highest priority when close to delivery
          "delivery_attempted": "10m",
          "delivered": "48h",     // Low priority, just confirm
          "exception": "30m",     // Investigate exceptions more frequently
          "cancelled": "72h"
        }
        ```
    *   These intervals are stored in the `Order Status Database` for each order, specifically `next_poll_time`.

2.  **Adaptive Backoff/Exponential Backoff:**
    *   If an order's status hasn't changed after several polls, we can gradually increase the polling interval to save resources.
    *   Conversely, if an order is approaching its expected delivery date (if available), we can decrease the interval to ensure timely updates.
    *   **Algorithm:**
        *   Initial interval: `I_initial` (e.g., 5 minutes for "in_delivery").
        *   If status changes: Reset to `I_initial`.
        *   If status *doesn't* change for `N` consecutive polls: `I_new = min(I_max, I_current * backoff_factor)`.
            *   `I_max`: Maximum allowed interval (e.g., 6 hours for "shipped").
            *   `backoff_factor`: e.g., 1.5 or 2.0.
    *   This requires storing `last_status_change_time` and `consecutive_no_change_polls` in the database.

3.  **Polling Scheduler (Database-driven):**
    *   The `Polling Scheduler` component periodically queries the `Order Status Database` for orders whose `next_poll_time` is in the past.
    *   **SQL Query Example (simplified):**
        ```sql
        SELECT order_id, tracking_number, logistics_partner, current_status, last_polled_at, next_poll_at
        FROM orders
        WHERE next_poll_at <= NOW()
          AND current_status NOT IN ('delivered', 'cancelled', 'returned') -- No need to poll these frequently
        ORDER BY next_poll_at ASC, priority DESC -- Prioritize older polls and higher priority statuses
        LIMIT 1000; -- Batch processing
        ```
    *   For each fetched order, it publishes a `PollRequest` message to an internal queue (e.g., `poll_requests_queue`) which is then picked up by workers that call the external APIs.

4.  **Event-Driven Triggers:**
    *   **Internal Events:** When an order is initially placed, or a seller marks it as "shipped" in our system, an immediate `PollRequest` is generated.
    *   **Webhooks (if available):** If a logistics partner supports webhooks, we would integrate them. Upon receiving a webhook, we immediately update the order status and reset its `next_poll_time` to a very long interval, effectively stopping polling until a new event or a periodic re-validation is needed. This is the ideal, but often unavailable, solution.

**Database Schema Snippet for Polling:**

```sql
CREATE TABLE orders (
    order_id UUID PRIMARY KEY,
    tracking_number VARCHAR(255) NOT NULL,
    logistics_partner VARCHAR(50) NOT NULL, -- e.g., 'FEDEX', 'UPS'
    current_status VARCHAR(50) NOT NULL,    -- e.g., 'placed', 'shipped', 'in_delivery'
    last_polled_at TIMESTAMP WITH TIME ZONE,
    next_poll_at TIMESTAMP WITH TIME ZONE NOT NULL,
    last_status_change_at TIMESTAMP WITH TIME ZONE,
    consecutive_no_change_polls INT DEFAULT 0,
    expected_delivery_date DATE,             -- For predictive polling
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Index for efficient scheduling queries
CREATE INDEX idx_next_poll_at_status ON orders (next_poll_at, current_status);
```

### 3. Handling Rate Limiting with Individual External Logistics Partners

Rate limiting is critical to avoid being blocked. We'll implement a centralized `Rate Limit Manager` and use a token bucket algorithm per partner.

**Core Idea:**
Each external logistics partner has its own "bucket" of available API calls. When a `PollRequest` needs to be made, it first requests a token from the `Rate Limit Manager`. If no token is available, the request is delayed.

**Mechanism Details:**

1.  **Centralized Rate Limit Manager Service:**
    *   This service maintains the current rate limit status for *each* logistics partner (e.g., FedEx, UPS).
    *   It stores:
        *   `max_requests_per_period`: e.g., 1000 requests per minute.
        *   `period_in_seconds`: e.g., 60 seconds.
        *   `tokens_available`: Current tokens in the bucket.
        *   `last_refill_time`: When the bucket was last refilled.
    *   This state can be stored in a fast, distributed key-value store like Redis or a dedicated database table.

2.  **Token Bucket Algorithm:**
    *   Each partner has a virtual "bucket" that holds a certain number of tokens.
    *   Tokens are added to the bucket at a fixed rate (e.g., 1000 tokens per minute).
    *   To make an API call, a service must consume a token. If the bucket is empty, the call is delayed.
    *   **Implementation:**
        ```python
        # Pseudocode for RateLimitManager
        class RateLimitManager:
            def __init__(self, partner_configs):
                self.partner_limits = {} # {partner_name: {max_tokens, refill_rate, last_refill_time, current_tokens}}
                for partner, config in partner_configs.items():
                    self.partner_limits[partner] = {
                        "max_tokens": config["max_requests_per_period"],
                        "refill_rate": config["max_requests_per_period"] / config["period_in_seconds"],
                        "last_refill_time": time.time(),
                        "current_tokens": config["max_requests_per_period"]
                    }
                self.lock = threading.Lock() # Or distributed lock for multiple instances

            def acquire_token(self, partner_name):
                with self.lock: # Use distributed lock if multiple instances
                    limit_info = self.partner_limits.get(partner_name)
                    if not limit_info:
                        raise ValueError(f"Unknown partner: {partner_name}")

                    # Refill tokens
                    now = time.time()
                    time_elapsed = now - limit_info["last_refill_time"]
                    tokens_to_add = time_elapsed * limit_info["refill_rate"]
                    limit_info["current_tokens"] = min(limit_info["max_tokens"], limit_info["current_tokens"] + tokens_to_add)
                    limit_info["last_refill_time"] = now

                    if limit_info["current_tokens"] >= 1:
                        limit_info["current_tokens"] -= 1
                        return True # Token acquired
                    else:
                        return False # No token available

            def get_wait_time(self, partner_name):
                with self.lock:
                    limit_info = self.partner_limits.get(partner_name)
                    if not limit_info or limit_info["current_tokens"] >= 1:
                        return 0 # No wait needed

                    # Calculate time until next token is available
                    tokens_needed = 1 - limit_info["current_tokens"]
                    time_to_wait = tokens_needed / limit_info["refill_rate"]
                    return time_to_wait
        ```

3.  **Integration with Polling Workers:**
    *   When a `PollRequest` message is consumed by a worker (which then calls the external API client):
        ```python
        # Pseudocode for a Polling Worker
        def process_poll_request(request):
            partner = request.logistics_partner
            order_id = request.order_id

            while True:
                if rate_limit_manager.acquire_token(partner):
                    try:
                        status = external_api_client.get_status(partner, request.tracking_number)
                        # Process status, update DB, publish events
                        break # Success, exit loop
                    except ExternalAPIError as e:
                        if e.is_rate_limit_exceeded(): # Partner's explicit rate limit error
                            # Adjust rate_limit_manager's internal config for this partner
                            # (e.g., reduce max_tokens, increase period)
                            # This is a self-healing mechanism for misconfigured limits
                            log.warn(f"Partner {partner} explicitly rate limited. Adjusting strategy.")
                            time.sleep(rate_limit_manager.get_wait_time(partner) + random.uniform(1, 5)) # Add jitter
                            continue # Retry
                        else:
                            # Handle other API errors (retry, dead-letter)
                            break
                else:
                    wait_time = rate_limit_manager.get_wait_time(partner)
                    log.info(f"Rate limit hit for {partner}. Waiting for {wait_time:.2f} seconds.")
                    time.sleep(wait_time + random.uniform(0.1, 0.5)) # Add jitter to avoid thundering herd
        ```

4.  **Feedback Loop from External APIs:**
    *   Many external APIs return `X-RateLimit-Remaining`, `X-RateLimit-Reset`, or similar headers.
    *   The `External Logistics API Clients` should parse these headers and feed this real-time information back to the `Rate Limit Manager`. This allows the manager to dynamically adjust its internal token bucket parameters for greater accuracy than static configuration.

5.  **Dedicated Polling Queues (Optional but Recommended):**
    *   To further isolate and manage rate limits, we can have separate internal queues for `PollRequest` messages, one per logistics partner (e.g., `poll_requests_fedex`, `poll_requests_ups`).
    *   Each queue would have its own set of workers, configured with the specific rate limits for that partner. This prevents one partner's rate limit issues from affecting others.

### 4. Strategy for Ensuring Eventual Consistency of Order Statuses

Eventual consistency is inherent in distributed systems, especially when relying on external, asynchronous updates. Our strategy focuses on resilience, retries, and reconciliation.

**Core Idea:**
Never assume an update is final or that a poll will succeed. Use durable queues for all update requests, implement robust retry mechanisms, and schedule periodic full reconciliations to catch anything missed.

**Mechanism Details:**

1.  **Durable Message Queues for All Critical Steps:**
    *   `Tracking Update Queue (Kafka/SQS)`: For initial requests to process updates.
    *   `Poll Request Queue (Kafka/SQS)`: For requests to perform an actual API poll. If a worker fails, the message remains in the queue for another worker to pick up.
    *   `Status Update Processing Queue (Kafka/SQS)`: After an external API call, the raw status data is published here for idempotent processing and database updates.

2.  **Idempotent Status Updates:**
    *   The `Status Updater` must be idempotent. If it receives the same status update multiple times, it should produce the same result (e.g., only update if the new status is "newer" or represents a progression).
    *   **Example Logic:**
        ```sql
        -- When updating status, only proceed if the new status is a progression
        -- (assuming a defined status hierarchy, e.g., PLACED < SHIPPED < IN_DELIVERY < DELIVERED)
        UPDATE orders
        SET
            current_status = :new_status,
            last_polled_at = NOW(),
            last_status_change_at = CASE WHEN current_status != :new_status THEN NOW() ELSE last_status_change_at END,
            consecutive_no_change_polls = CASE WHEN current_status != :new_status THEN 0 ELSE consecutive_no_change_polls + 1 END,
            next_poll_at = calculate_next_poll_time(:new_status, :current_interval, :consecutive_no_change_polls),
            updated_at = NOW()
        WHERE order_id = :order_id
          AND (get_status_priority(:new_status) > get_status_priority(current_status) OR :force_update = TRUE);
        ```
        *   `get_status_priority()` would be a function or lookup table defining the progression.

3.  **Retry Mechanisms with Exponential Backoff and Jitter:**
    *   **External API Calls:** If an API call fails (network error, transient server error, timeout), the `Polling Worker` should retry with exponential backoff and jitter.
        *   `Retry 1: 1s, Retry 2: 3s, Retry 3: 10s, Retry 4: 30s, Retry 5: 60s`.
        *   After `N` retries, if still failing, the message should be moved to a Dead-Letter Queue (DLQ).
    *   **Queue Consumers:** If processing a message from any queue fails (e.g., database error during update), the message should be retried by the queue system (e.g., SQS visibility timeout, Kafka consumer group rebalance). After several retries, it should go to a DLQ.

4.  **Dead-Letter Queues (DLQs):**
    *   Each critical queue should have an associated DLQ.
    *   Messages that cannot be processed after multiple retries are moved to the DLQ.
    *   **Purpose:** Prevents poison pills from blocking the main queue.
    *   **Operational Aspect:** A dedicated team/process monitors DLQs, investigates failures, and manually re-processes or fixes data.

5.  **Periodic Reconciliation/Audit Job:**
    *   A separate batch job runs periodically (e.g., daily or weekly) to reconcile the state of *all* active orders with their respective logistics partners.
    *   **Process:**
        1.  Fetch a batch of orders from the `Order Status Database`.
        2.  For each order, perform a "deep" poll to the logistics partner, regardless of `next_poll_at`.
        3.  Compare the fetched status with the stored status.
        4.  If discrepancies are found, update the `Order Status Database` and potentially flag for manual review if the discrepancy is significant (e.g., order marked delivered externally but still "shipped" internally for a long time).
    *   This job is lower priority and can tolerate longer run times, acting as a safety net. It uses the same `Rate Limit Manager` but might have a dedicated, lower-priority token bucket or run during off-peak hours.

6.  **Monitoring and Alerting:**
    *   Monitor queue depths (if growing, indicates a bottleneck).
    *   Monitor DLQ messages (indicates persistent failures).
    *   Monitor latency of status updates (time from external update to internal reflection).
    *   Alert on significant discrepancies found by the reconciliation job.
    *   Alert on frequent rate limit hits for a partner (suggests misconfiguration or partner policy change).

By combining these strategies, we ensure that even with transient failures or delays, the system will eventually converge to the correct state, providing a robust and reliable order tracking experience.

### Going further

The trade-offs involved in prioritizing freshness of data versus cost/rate-limit adherence when designing a system that relies on polling external, rate-limited APIs are fundamental.

**Prioritizing Freshness of Data:**

*   **Pros:**
    *   **Improved Customer Experience:** Customers get real-time or near real-time updates, leading to higher satisfaction and fewer support inquiries.
    *   **Better Internal Decision Making:** Downstream systems (e.g., customer support, fraud detection, inventory management) operate with the most accurate information.
    *   **Competitive Advantage:** A highly responsive tracking system can differentiate a marketplace.
*   **Cons:**
    *   **Higher Cost:** More frequent API calls mean higher operational costs, especially if partners charge per call.
    *   **Increased Risk of Rate Limiting:** Aggressive polling is more likely to hit external rate limits, leading to temporary blocks and potentially *worse* freshness if calls are rejected.
    *   **Increased Infrastructure Load:** More frequent polling requires more processing power, network bandwidth, and database writes on our side.
    *   **Higher Error Rate:** More calls mean more opportunities for transient network issues or external API errors.

**Prioritizing Cost/Rate-Limit Adherence:**

*   **Pros:**
    *   **Lower Operational Cost:** Fewer API calls directly reduce expenses.
    *   **Reduced Risk of Being Blocked:** Respecting rate limits ensures continuous, albeit slower, access to partner APIs.
    *   **Lower Infrastructure Load:** Less frequent polling reduces the burden on our own systems.
    *   **Increased Stability:** Less aggressive interaction with external systems can lead to a more stable overall service.
*   **Cons:**
    *   **Stale Data:** Order statuses in our system will lag behind the actual status at the logistics partner.
    *   **Poor Customer Experience:** Customers might see outdated information, leading to frustration and increased support calls.
    *   **Delayed Internal Processes:** Business logic relying on status updates will be delayed.

**Under what circumstances would you lean towards one over the other, and how would your design reflect that choice?**

**Lean towards Freshness (and accept higher cost/rate-limit risk) when:**

*   **High-Value/Time-Sensitive Goods:** For perishable items, urgent medical supplies, or high-value electronics, real-time tracking is paramount.
*   **Critical Customer Experience:** If tracking is a primary differentiator or a major source of customer complaints when stale.
*   **Partners with High/Flexible Rate Limits:** If a partner offers generous rate limits or allows negotiation for higher limits.
*   **Proactive Problem Resolution:** To identify and address delivery exceptions (e.g., "delivery attempted," "package damaged") as quickly as possible.

**Design Reflection for Freshness:**

*   **Aggressive Polling Intervals:** Set `I_initial` (initial polling interval) for "in_delivery" and "shipped" statuses to be very low (e.g., 1-2 minutes).
*   **Slower Backoff:** Use a smaller `backoff_factor` or fewer `consecutive_no_change_polls` before increasing the interval, or even disable backoff for critical statuses.
*   **Prioritized Queues:** Implement priority queues where "in_delivery" orders get processed before "shipped" orders, and "shipped" before "placed".
*   **Higher Rate Limit Budgets:** Configure the `Rate Limit Manager` with the highest possible (negotiated) rate limits for each partner. Be prepared to pay for higher limits if available.
*   **Quick Retry Policies:** Shorter delays and more retries for API call failures.
*   **Proactive Monitoring:** Aggressive alerting on any delays in status updates or rate limit hits, indicating immediate intervention is needed.
*   **Leverage Webhooks Aggressively:** If *any* partner offers webhooks, prioritize integration to get instant updates and reduce polling for those partners.

**Lean towards Cost/Rate-Limit Adherence (and accept some data staleness) when:**

*   **Low-Value/Non-Time-Sensitive Goods:** For items where a few hours' delay in status update doesn't significantly impact the customer or business (e.g., bulk commodity items, non-urgent deliveries).
*   **Strict/Expensive Rate Limits:** When logistics partners have very restrictive rate limits, or API calls are prohibitively expensive.
*   **High Volume, Low Margin:** In scenarios where processing millions of orders daily means even a small per-call cost adds up significantly.
*   **Batch Processing Acceptable:** If internal systems can tolerate processing updates in batches rather than individually.

**Design Reflection for Cost/Rate-Limit Adherence:**

*   **Conservative Polling Intervals:** Set `I_initial` for "in_delivery" and "shipped" statuses to be higher (e.g., 15-30 minutes).
*   **Aggressive Backoff:** Use a larger `backoff_factor` (e.g., 2.0-3.0) and fewer `consecutive_no_change_polls` to quickly increase intervals for stagnant orders.
*   **Prioritize Updates for Critical Statuses Only:** While "in_delivery" might still be polled more frequently, "placed" or "processing" orders might only be polled once a day.
*   **Batch Polling:** If a partner API supports it, poll multiple tracking numbers in a single API call to reduce the number of requests.
*   **Strict Rate Limit Manager Configuration:** Configure the `Rate Limit Manager` precisely to partner-advertised limits, with a small buffer, and prioritize avoiding 429 errors.
*   **Longer Retry Delays:** For API call failures, use longer exponential backoff delays before retrying.
*   **Scheduled Reconciliation:** Rely more heavily on the periodic reconciliation job as the ultimate source of truth, accepting that some updates might only be caught then.
*   **Cost Monitoring:** Implement robust cost monitoring for external API calls to ensure adherence to budget.

In our scenario, with "millions of orders daily" and "tens of millions of active orders," and a "latency budget <5 minutes," we are leaning towards **freshness**, but with a strong emphasis on **smart cost/rate-limit management**. The proposed solution reflects this by:

*   Using adaptive polling based on status (prioritizing "in_delivery" and "shipped").
*   Implementing a robust `Rate Limit Manager` with feedback loops.
*   Leveraging queues for resilience and eventual consistency.
*   Including a reconciliation job as a safety net, but not as the primary update mechanism.

This hybrid approach attempts to get the best of both worlds: timely updates for critical phases while being mindful of resource consumption and external constraints.
