## Scenario

Your team maintains a critical backend service that handles user preferences for a large, multi-tenant SaaS platform. Each tenant can define a set of custom preferences for their users (e.g., notification settings, UI themes, data display options). These preferences are stored in a key-value fashion, but critically, a user's preferences are often *inherited* from their tenant's default settings, unless explicitly overridden by the user. 

The system currently stores all preferences in a single `user_preferences` table with columns like `user_id`, `tenant_id`, `key`, `value`, and `is_inherited` (a boolean indicating if this specific preference is an override or just reflects the tenant default). When a user requests their preferences, the system first fetches all preferences for their `user_id` and `tenant_id`. Then, it fetches all default preferences for their `tenant_id` where `user_id` is null (representing tenant defaults). Finally, it merges these two sets, with user-specific overrides taking precedence.

This approach was fine when there were a few thousand users and tenants. However, the platform has grown to millions of users across hundreds of thousands of tenants, each with potentially hundreds of distinct preference keys. The logic to fetch and merge preferences for a single user is now taking several hundred milliseconds, leading to noticeable UI lag and API latency, especially for users with many overridden preferences.

## Requirements

The goal is to optimize the retrieval of a user's *effective* preferences, considering both their explicit overrides and their tenant's inherited defaults, such that the operation completes reliably within 50ms (p99 latency). The solution must:

1.  Correctly apply the inheritance logic: user-specific preferences for a given key must always override tenant-wide defaults for that same key.
2.  Be efficient for tenants with many preference keys and users who have overridden only a few.
3.  Be robust to high concurrency, as many users might request their preferences simultaneously.
4.  Maintain data integrity and consistency, especially around which preferences are considered "active" for a user.

## Deliverables

1.  Describe the optimal data structure or algorithm to efficiently combine user-specific and tenant-default preferences.
2.  Provide pseudocode or a high-level description of the lookup process given a `user_id` and `tenant_id`.
3.  Explain any changes or additions to the database schema or indexing strategy that would be necessary.

## Going further

How would your approach change if, in addition to user and tenant preferences, there were also *global* platform defaults that applied to all tenants and users, which could be overridden by tenant defaults, which in turn could be overridden by user preferences?

## Worked answer

### 1. Optimal Data Structure or Algorithm

The core problem is efficiently merging two sets of key-value pairs (`user_preferences` and `tenant_defaults`), where one set takes precedence over the other. This is a classic "merge with override" scenario.

The most efficient data structure for this lookup and merge operation is a **hash map** (or dictionary/associative array). When retrieving preferences, we want to construct a final hash map representing the user's effective preferences.

The algorithm would involve two main steps:

1.  **Fetch Tenant Defaults:** Retrieve all default preferences for the given `tenant_id`. Store these in a hash map, where the key is the preference name (e.g., "notification_email") and the value is the preference value (e.g., "true"). This hash map represents the base set of preferences.
2.  **Fetch User Overrides:** Retrieve all user-specific preferences for the given `user_id` and `tenant_id`. Iterate through these user-specific preferences. For each user preference, add or update its corresponding entry in the hash map created in step 1. Because user preferences take precedence, simply inserting or overwriting the key-value pair in the hash map correctly applies the override logic.

This approach leverages the `O(1)` average-case time complexity of hash map lookups and insertions.

**Why this is optimal:**

*   **Efficiency:** By first populating the hash map with tenant defaults and then iterating through user overrides to update it, we perform a minimal number of operations. Each preference is processed at most twice (once for initial insertion from tenant defaults, and potentially once for update from user overrides).
*   **Correctness:** The "last write wins" nature of hash map updates naturally implements the override logic.
*   **Simplicity:** The logic is straightforward and easy to understand and maintain.
*   **Scalability:** Hash maps perform well even with a large number of keys, as long as the hash function distributes keys evenly.

**Why other approaches might be less optimal:**

*   **Direct SQL JOIN/UNION:** While possible, performing complex `JOIN` or `UNION` operations with `COALESCE` or `ROW_NUMBER()` directly in SQL to achieve the merge logic can be less performant, especially with many keys, as it might involve more data transfer and complex query planning. It also makes the application logic harder to reason about if the merge rules become more complex.
*   **Fetching all and then filtering:** The current approach of fetching all and then merging in application code is essentially what's described above, but the *efficiency bottleneck* is likely in the database queries themselves, not the in-memory merge. The proposed solution focuses on optimizing the database interaction and ensuring the in-memory merge is done optimally.

### 2. Pseudocode or High-Level Description of Lookup Process

Given `user_id` and `tenant_id`:

```pseudocode
function getUserEffectivePreferences(user_id, tenant_id):
    // Step 1: Initialize a hash map for effective preferences
    effective_preferences = new HashMap<String, String>() // Key: preference_key, Value: preference_value

    // Step 2: Fetch tenant-wide default preferences
    // SQL: SELECT key, value FROM user_preferences WHERE tenant_id = :tenant_id AND user_id IS NULL;
    tenant_defaults = database.query("SELECT key, value FROM user_preferences WHERE tenant_id = ? AND user_id IS NULL", tenant_id)

    // Populate effective_preferences with tenant defaults
    for each preference in tenant_defaults:
        effective_preferences.put(preference.key, preference.value)

    // Step 3: Fetch user-specific overrides
    // SQL: SELECT key, value FROM user_preferences WHERE user_id = :user_id AND tenant_id = :tenant_id;
    user_overrides = database.query("SELECT key, value FROM user_preferences WHERE user_id = ? AND tenant_id = ?", user_id, tenant_id)

    // Apply user overrides, which take precedence
    for each preference in user_overrides:
        effective_preferences.put(preference.key, preference.value) // Overwrites if key already exists

    return effective_preferences
```

This process involves two distinct database queries, followed by in-memory hash map operations. The critical performance gain comes from optimizing these two database queries.

### 3. Database Schema and Indexing Strategy

The existing `user_preferences` table schema is largely suitable, but its indexing is crucial.

**Existing Schema (conceptual):**

```sql
CREATE TABLE user_preferences (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT,       -- NULL for tenant defaults
    tenant_id BIGINT NOT NULL,
    key VARCHAR(255) NOT NULL,
    value TEXT NOT NULL,
    is_inherited BOOLEAN NOT NULL, -- This column becomes redundant with the new logic
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

**Proposed Schema Changes/Additions:**

The `is_inherited` column becomes redundant. If `user_id` is `NULL`, it's a tenant default. If `user_id` is present, it's a user override. This simplifies the data model slightly.

```sql
-- Updated table definition (removing is_inherited)
CREATE TABLE user_preferences (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT,       -- NULL for tenant defaults
    tenant_id BIGINT NOT NULL,
    preference_key VARCHAR(255) NOT NULL, -- Renamed 'key' to 'preference_key' to avoid SQL keyword conflicts
    preference_value TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    -- Constraint to ensure uniqueness for user-specific preferences
    -- A user can only have one value for a given key within a tenant
    UNIQUE (user_id, tenant_id, preference_key),

    -- Constraint to ensure uniqueness for tenant-wide defaults
    -- A tenant can only have one default value for a given key
    -- This requires a partial index or a separate constraint if user_id can be NULL
    -- For databases that support partial unique indexes (e.g., PostgreSQL):
    -- UNIQUE (tenant_id, preference_key) WHERE user_id IS NULL,
    -- For databases that don't (e.g., MySQL), a separate entry for tenant defaults is implied by the first UNIQUE constraint
    -- where user_id is NULL. The combination (NULL, tenant_id, preference_key) is unique.
);
```

**Indexing Strategy:**

The two critical queries are:

1.  `SELECT preference_key, preference_value FROM user_preferences WHERE tenant_id = :tenant_id AND user_id IS NULL;`
2.  `SELECT preference_key, preference_value FROM user_preferences WHERE user_id = :user_id AND tenant_id = :tenant_id;`

To optimize these, we need composite indexes:

*   **Index for Tenant Defaults:**
    `CREATE INDEX idx_tenant_defaults ON user_preferences (tenant_id, user_id, preference_key);`
    This index will efficiently cover queries for tenant defaults because `user_id IS NULL` is a highly selective condition when combined with `tenant_id`. The `preference_key` is included to make it a covering index for the `SELECT preference_key, preference_value` part, meaning the database can retrieve all necessary data directly from the index without needing to access the main table, further speeding up the query.

*   **Index for User Overrides:**
    `CREATE INDEX idx_user_overrides ON user_preferences (user_id, tenant_id, preference_key);`
    This index is crucial for quickly fetching all preferences for a specific user within a tenant. Again, `preference_key` is included for covering index benefits. The order `(user_id, tenant_id)` is important because `user_id` is typically more selective than `tenant_id` (a user belongs to only one tenant, but a tenant has many users).

**Why these indexes work:**

*   **Reduced I/O:** The indexes allow the database to quickly locate the relevant rows without scanning the entire table.
*   **Covering Indexes:** By including `preference_key` (and implicitly `preference_value` if the database stores it in the index or can use the index to find it efficiently), the queries can often be satisfied entirely by reading the index, avoiding costly table lookups. This is especially beneficial for `TEXT` columns like `preference_value` which can be large.
*   **Optimized Sorting/Filtering:** The composite indexes are ordered by the columns, making filtering by `tenant_id` and `user_id` extremely fast.

**Trade-offs:**

*   **Increased Write Overhead:** Adding indexes will slightly increase the time and resources required for `INSERT`, `UPDATE`, and `DELETE` operations on the `user_preferences` table, as the indexes must also be updated. Given that preference retrieval is the critical path, this is an acceptable trade-off.
*   **Increased Storage Space:** Indexes consume disk space. For millions of users and hundreds of preferences, these indexes could be substantial, but still far less than the performance gains.

**What breaks first at ten times the scale:**

At ten times the scale (hundreds of millions of users, millions of tenants, thousands of keys per tenant), the primary bottleneck will shift:

1.  **Index Size and Cache Misses:** The indexes themselves will become very large. If the working set of frequently accessed index pages exceeds available memory, disk I/O will increase, degrading performance.
2.  **Database Connection Pool Exhaustion:** With high concurrency, the database might struggle to handle the sheer number of concurrent queries, even if individual queries are fast.
3.  **Network Latency:** Even with optimized queries, the round-trip time to the database can become a significant factor if the application and database are geographically separated.
4.  **Hash Map Memory Usage:** If a single user or tenant has an extremely large number of preferences (e.g., tens of thousands), the in-memory hash map could consume significant memory, potentially leading to garbage collection pauses or out-of-memory errors in the application.

To mitigate these at extreme scale, further optimizations might include:

*   **Caching:** Implementing a distributed cache (e.g., Redis, Memcached) for frequently accessed user preferences. The cache would store the *merged* effective preferences, avoiding database hits entirely for subsequent requests. This introduces cache invalidation challenges.
*   **Database Sharding:** Sharding the `user_preferences` table by `tenant_id` or `user_id` to distribute the load across multiple database instances.
*   **Read Replicas:** Using read replicas to scale out read operations.

### Going Further: Global Platform Defaults

If global platform defaults are introduced, the inheritance hierarchy becomes:
**Global Defaults < Tenant Defaults < User Overrides**

The approach would extend naturally:

1.  **New Data Storage for Global Defaults:**
    A new table `global_preferences` would be ideal, as global defaults are independent of `tenant_id` and `user_id`.

    ```sql
    CREATE TABLE global_preferences (
        id BIGINT PRIMARY KEY AUTO_INCREMENT,
        preference_key VARCHAR(255) NOT NULL UNIQUE, -- Global keys must be unique
        preference_value TEXT NOT NULL,
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
        updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
    );
    -- Index for efficient lookup:
    CREATE UNIQUE INDEX idx_global_key ON global_preferences (preference_key);
    ```

2.  **Modified Lookup Algorithm:**
    The pseudocode would add an initial step to fetch global defaults.

    ```pseudocode
    function getUserEffectivePreferencesWithGlobal(user_id, tenant_id):
        effective_preferences = new HashMap<String, String>()

        // Step 1: Fetch Global Platform Defaults
        // SQL: SELECT preference_key, preference_value FROM global_preferences;
        global_defaults = database.query("SELECT preference_key, preference_value FROM global_preferences")
        for each preference in global_defaults:
            effective_preferences.put(preference.preference_key, preference.preference_value)

        // Step 2: Fetch Tenant-wide Default Preferences (overrides global)
        // SQL: SELECT preference_key, preference_value FROM user_preferences WHERE tenant_id = :tenant_id AND user_id IS NULL;
        tenant_defaults = database.query("SELECT preference_key, preference_value FROM user_preferences WHERE tenant_id = ? AND user_id IS NULL", tenant_id)
        for each preference in tenant_defaults:
            effective_preferences.put(preference.preference_key, preference.preference_value) // Overwrites global defaults

        // Step 3: Fetch User-specific Overrides (overrides tenant and global)
        // SQL: SELECT preference_key, preference_value FROM user_preferences WHERE user_id = :user_id AND tenant_id = :tenant_id;
        user_overrides = database.query("SELECT preference_key, preference_value FROM user_preferences WHERE user_id = ? AND tenant_id = ?", user_id, tenant_id)
        for each preference in user_overrides:
            effective_preferences.put(preference.preference_key, preference.preference_value) // Overwrites tenant/global defaults

        return effective_preferences
    ```

**Impact and Considerations:**

*   **Additional Database Query:** This adds a third database query to fetch global defaults. However, global defaults are likely a small, static set that changes infrequently. This query can be heavily cached at the application layer (e.g., in a static variable or a short-lived in-memory cache), making its performance impact negligible for most requests.
*   **Caching Strategy:** For global defaults, a very aggressive cache (e.g., application startup load or a long TTL cache) would be highly effective.
*   **Consistency:** The three-tiered merge logic remains simple and consistent. The "last write wins" principle of the hash map naturally handles the inheritance order.
*   **Performance:** The overall latency would still be dominated by the two queries to the `user_preferences` table, as the global defaults query would be fast (small result set, potentially cached). The 50ms target should still be achievable.
