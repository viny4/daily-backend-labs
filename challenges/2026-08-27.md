## Scenario

Your team maintains a critical internal service that manages customer agreements for a large B2B SaaS platform. A core feature of this service is generating a "Contract Health Report" which summarizes the status of all active agreements for a given customer. This report involves querying the `agreements` table, which has grown to 150 million rows, and joining it with a `customer_profiles` table (10 million rows) to filter by customer segment and other attributes.

The `agreements` table has columns like `agreement_id` (PK), `customer_id`, `status` (e.g., 'ACTIVE', 'EXPIRED', 'PENDING_RENEWAL'), `start_date`, `end_date`, `value`, and `last_updated_at`. The `customer_profiles` table includes `customer_id` (PK), `segment` (e.g., 'SMB', 'Enterprise'), `region`, and `onboarding_date`.

The "Contract Health Report" needs to display:
1. Total active agreements for the customer.
2. Total value of active agreements for the customer.
3. Count of agreements pending renewal within the next 30 days.
4. Average agreement value for active agreements, grouped by customer segment.

Currently, this report is generated on demand via an internal admin panel. A single report generation for an Enterprise customer (who might have tens of thousands of agreements) now takes consistently over 20 seconds, sometimes timing out. This latency is unacceptable, as internal users need these reports quickly for strategic decision-making.

## Requirements

The report generation must be significantly faster, ideally completing within 2-3 seconds for even the largest customers. The system should be able to handle concurrent requests for different customer reports without significant performance degradation. The solution must be cost-effective and maintain data freshness within 5 minutes. The current database is PostgreSQL.

## Deliverables

1. A high-level architectural diagram showing the components involved and their interactions.
2. A description of the proposed data flow from ingestion/updates to report generation.
3. Proposed changes to the database schema or indexing strategy to support the new performance requirements.
4. A brief explanation of how data freshness is maintained and how concurrent report requests are handled.

## Going further

How would your solution adapt if the business required the report to reflect real-time data (sub-second freshness) for a select group of "VIP" customers, while still keeping costs down for the vast majority of regular customers?

**Components:**

*   **PostgreSQL DB:** The primary transactional database for `agreements` and `customer_profiles`.
*   **CDC Stream (e.g., Debezium):** Captures row-level changes from PostgreSQL's Write-Ahead Log (WAL) and publishes them to Kafka.
*   **Kafka:** A distributed streaming platform used as a message broker for change data capture events.
*   **Report Aggregation Service:** A dedicated microservice that consumes CDC events from Kafka, processes them, and writes pre-aggregated data to the Materialized View DB. This service can be implemented using a framework like Spring Boot or Go with Kafka clients.
*   **Materialized View DB (e.g., PostgreSQL):** A separate PostgreSQL instance optimized for read performance, storing pre-aggregated and denormalized data specifically for reports. This could also be a data warehouse solution like ClickHouse or a NoSQL store like Cassandra if the reporting needs were more complex or required higher scale, but for this scenario, another PostgreSQL instance is cost-effective and familiar.
*   **Report API Service:** An internal API endpoint that the Admin Panel calls to fetch report data. It queries the Materialized View DB for aggregates and potentially the primary PostgreSQL DB for any detailed, non-aggregated data not present in the materialized views.
*   **Internal Admin Panel:** The UI that internal users interact with to request reports.

### 2. Proposed Data Flow

1.  **Transactional Data Updates:**
    *   When an `agreement` or `customer_profile` is created, updated, or deleted by the `Agreement Service` or `Customer Profile Service`, these changes are written to the primary PostgreSQL DB.
    *   The `last_updated_at` column in the `agreements` table is crucial for tracking changes.

2.  **Change Data Capture (CDC):**
    *   Debezium (or a similar CDC tool) monitors the PostgreSQL WAL for changes to the `agreements` and `customer_profiles` tables.
    *   Each change (INSERT, UPDATE, DELETE) is captured as an event and published to a dedicated Kafka topic (e.g., `dbserver.public.agreements`, `dbserver.public.customer_profiles`). The event payload includes the old and new row states.

3.  **Real-time Aggregation:**
    *   The `Report Aggregation Service` consumes messages from the Kafka topics.
    *   For each `agreement` change event:
        *   It fetches the associated `customer_profile` data (if not already cached or included in the event) to get `segment` and `region`.
        *   It re-calculates the relevant aggregates for the affected `customer_id` and `segment`. This could involve:
            *   Incrementing/decrementing counts based on `status` changes.
            *   Adding/subtracting `value` based on `status` or `value` changes.
            *   Updating `pending_renewal` counts based on `end_date` changes.
        *   These re-calculated aggregates are then written to the `Materialized View DB`. The updates should be idempotent to handle potential message re-processing.

4.  **Materialized View Storage:**
    *   The `Materialized View DB` stores the pre-aggregated data in tables specifically designed for reporting queries.

5.  **Report Generation:**
    *   An internal user requests a "Contract Health Report" for a specific `customer_id` via the `Internal Admin Panel`.
    *   The `Internal Admin Panel` calls the `Report API Service`.
    *   The `Report API Service` queries the `Materialized View DB` using the pre-calculated aggregates. For example, it might query a table `customer_agreement_summary` for total active agreements and value, and `customer_segment_summary` for average value by segment.
    *   If any specific detail not covered by aggregates is needed (e.g., a list of all pending renewal agreements with their IDs), it might perform a targeted query to the primary PostgreSQL DB, but this should be minimized.
    *   The `Report API Service` compiles the data and returns it to the `Internal Admin Panel`.

### 3. Proposed Changes to Database Schema or Indexing Strategy

**Primary PostgreSQL DB (`agreements` table):**

No major schema changes are required for the `agreements` table itself, as the aggregation happens downstream. However, robust indexing is crucial for the CDC process and any fallback queries.

```sql
-- Existing table schema (simplified for brevity)
CREATE TABLE agreements (
    agreement_id UUID PRIMARY KEY,
    customer_id UUID NOT NULL,
    status VARCHAR(50) NOT NULL,
    start_date DATE NOT NULL,
    end_date DATE NOT NULL,
    value NUMERIC(19, 4) NOT NULL,
    last_updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL
);

CREATE TABLE customer_profiles (
    customer_id UUID PRIMARY KEY,
    segment VARCHAR(50) NOT NULL,
    region VARCHAR(50) NOT NULL,
    onboarding_date DATE NOT NULL
);

-- Recommended Indexes for primary DB:
-- For efficient lookups by customer_id
CREATE INDEX idx_agreements_customer_id ON agreements (customer_id);

-- For filtering by status and customer_id
CREATE INDEX idx_agreements_customer_status ON agreements (customer_id, status);

-- For pending renewal calculation (end_date range queries)
CREATE INDEX idx_agreements_end_date ON agreements (end_date);

-- For CDC, ensuring last_updated_at is indexed can sometimes help,
-- though Debezium primarily uses the WAL.
CREATE INDEX idx_agreements_last_updated_at ON agreements (last_updated_at);
```

**Materialized View DB:**

This database will store pre-aggregated data. We'll create specific tables to hold the report's required aggregates.

```sql
-- Table to store customer-level aggregates
CREATE TABLE customer_agreement_summary (
    customer_id UUID PRIMARY KEY,
    total_active_agreements BIGINT NOT NULL DEFAULT 0,
    total_active_value NUMERIC(19, 4) NOT NULL DEFAULT 0.00,
    pending_renewal_30_days BIGINT NOT NULL DEFAULT 0,
    last_calculated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL
);

-- Table to store customer segment-level aggregates
CREATE TABLE customer_segment_summary (
    customer_id UUID NOT NULL,
    segment VARCHAR(50) NOT NULL,
    total_active_agreements_segment BIGINT NOT NULL DEFAULT 0,
    total_active_value_segment NUMERIC(19, 4) NOT NULL DEFAULT 0.00,
    average_active_value_segment NUMERIC(19, 4) NOT NULL DEFAULT 0.00,
    last_calculated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW() NOT NULL,
    PRIMARY KEY (customer_id, segment) -- Composite primary key
);

-- Indexes for Materialized View DB:
-- customer_agreement_summary already has PK on customer_id, which is indexed.
-- customer_segment_summary already has PK on (customer_id, segment), which is indexed.
```

**Explanation of Schema/Indexing:**

*   **Primary DB Indexes:** These indexes are standard best practices for the given query patterns and will help the CDC tool efficiently read data if it needs to perform snapshots or specific lookups.
*   **Materialized View DB Tables:**
    *   `customer_agreement_summary`: Directly stores the first three report requirements (total active, total value, pending renewal) for each customer. Queries against this table will be `SELECT ... FROM customer_agreement_summary WHERE customer_id = :id`, which are extremely fast (PK lookup).
    *   `customer_segment_summary`: Stores the data needed for the fourth requirement (average value by segment). It's denormalized to include `customer_id` and `segment` to allow direct lookup. The `average_active_value_segment` is pre-calculated to avoid on-the-fly division during report generation.
*   **No Materialized Views in Primary DB:** While PostgreSQL has native materialized views, we are creating separate tables in a dedicated "Materialized View DB". This offloads the aggregation workload from the primary transactional database, preventing contention and allowing independent scaling and optimization of the reporting layer. Native materialized views in the primary DB would still put refresh load on the critical transactional system.

### 4. Data Freshness and Concurrent Requests

**Data Freshness (within 5 minutes):**

*   **CDC (Debezium) + Kafka:** Debezium captures changes from the PostgreSQL WAL almost instantly. Kafka provides low-latency message delivery.
*   **Report Aggregation Service:** This service continuously consumes messages from Kafka. The processing logic within this service will be optimized for speed.
    *   **Batching:** The service can process messages in small batches to reduce database write overhead to the Materialized View DB.
    *   **Idempotent Updates:** When an agreement changes, the service will re-evaluate its impact on the aggregates and update the `customer_agreement_summary` and `customer_segment_summary` tables. For example, if an agreement's status changes from 'PENDING_RENEWAL' to 'ACTIVE', the service would decrement `pending_renewal_30_days` and increment `total_active_agreements` and `total_active_value`.
    *   **Optimistic Locking/Atomic Updates:** When updating aggregates in the Materialized View DB, the service should use atomic SQL updates (e.g., `UPDATE ... SET count = count + 1 WHERE customer_id = :id`) or optimistic locking to prevent race conditions if multiple instances of the aggregation service are running or if events for the same customer arrive very close together.
*   **Monitoring:** Set up monitoring and alerting on Kafka consumer lag for the `Report Aggregation Service` to ensure it's keeping up with the event stream. If lag increases, it indicates a processing bottleneck.

The combination of low-latency CDC, a fast message broker, and a dedicated, continuously running aggregation service ensures that changes are reflected in the Materialized View DB typically within seconds, easily meeting the 5-minute freshness requirement.

**Handling Concurrent Report Requests:**

*   **Dedicated Report API Service:** The `Report API Service` is a stateless microservice designed to handle many concurrent read requests. It can be scaled horizontally by adding more instances behind a load balancer.
*   **Materialized View DB Optimization:** The `Materialized View DB` is specifically designed for read performance.
    *   **Pre-aggregated Data:** All required aggregates are pre-calculated and stored in dedicated tables, meaning report queries are simple `SELECT` statements with primary key lookups, which are extremely fast and require minimal computational resources from the database.
    *   **Indexing:** The `customer_id` and `(customer_id, segment)` primary keys ensure very fast lookups.
    *   **Separation of Concerns:** By having a separate database for reporting, concurrent report queries do not contend for resources (CPU, I/O, locks) with the primary transactional workload on the main PostgreSQL DB.
*   **Caching (Optional but Recommended):** The `Report API Service` can implement a short-lived, in-memory cache (e.g., Redis) for frequently requested customer reports. Since freshness is 5 minutes, a 30-second or 1-minute cache TTL would significantly reduce database load for popular reports without violating freshness requirements.

This architecture ensures that each report request is served by querying highly optimized, pre-aggregated data, making it very fast and allowing the system to handle a high volume of concurrent requests without degrading performance.

### Going Further: Real-time Data for VIP Customers

If the business required sub-second freshness for a select group of "VIP" customers while keeping costs down for others, we would adapt the solution with a hybrid approach:

1.  **Identify VIP Customers:** Maintain a `vip_customer_ids` list or table, perhaps in a fast key-value store like Redis, that the `Report API Service` can quickly check.

2.  **Hybrid Report Generation Logic in Report API Service:**
    *   When a report request comes in for `customer_id`:
        *   **Check VIP Status:** The `Report API Service` first checks if `customer_id` is in the `vip_customer_ids` list.
        *   **For VIP Customers (Real-time):**
            *   Instead of querying the `Materialized View DB`, the `Report API Service` would query the **primary PostgreSQL DB directly** for the VIP customer's data.
            *   It would execute the original, more complex analytical queries on the `agreements` and `customer_profiles` tables.
            *   To make these queries fast enough for VIPs, we would need to ensure the primary DB has highly optimized indexes for these specific queries (e.g., `(customer_id, status)`, `(customer_id, end_date)`).
            *   Consider adding a dedicated read replica for the primary PostgreSQL DB that VIP reports can hit, further isolating the load from the main transactional writes. This replica would still be eventually consistent, but typically with very low lag (milliseconds).
        *   **For Regular Customers (5-minute freshness):**
            *   The `Report API Service` continues to query the `Materialized View DB` as described in the original solution.

3.  **Optimized Primary DB for VIP Queries:**
    *   Ensure the primary `agreements` table has the following indexes to support fast on-demand aggregation for VIPs:
        ```sql
        CREATE INDEX idx_agreements_vip_customer_status ON agreements (customer_id, status, value);
        CREATE INDEX idx_agreements_vip_customer_end_date ON agreements (customer_id, end_date);
        ```
        These composite indexes allow the database to quickly filter by `customer_id` and then efficiently perform aggregates on `status`, `value`, and `end_date` without full table scans for a single customer.

**Trade-offs and Why it Works:**

*   **Cost-effectiveness:** The expensive, real-time queries are only performed for a small subset of VIP customers, limiting the impact on the primary database. The vast majority still benefit from the pre-aggregated, cost-effective solution.
*   **Complexity:** The `Report API Service` becomes more complex due to the conditional logic and potentially needing to connect to two different databases (primary and materialized view DB).
*   **Primary DB Load:** While limited to VIPs, these direct queries still add load to the primary DB (or its read replica). This load must be carefully monitored. If the number of VIP customers or their agreement counts grows significantly, this approach might eventually become a bottleneck, requiring further scaling of the primary DB or a more sophisticated real-time analytics solution (e.g., a dedicated real-time OLAP database).
*   **Data Consistency:** For VIPs, the data is as fresh as the primary database's commit. For regular customers, it's eventually consistent within 5 minutes. This difference in consistency levels must be acceptable to the business.

This hybrid approach leverages the existing infrastructure and adds a targeted, higher-performance path for critical users, balancing cost and performance requirements.
