## Scenario

Your team maintains a critical backend service that manages customer order history for a large e-commerce platform. The `orders` table has grown significantly and now contains hundreds of millions of rows. It includes columns like `id`, `customer_id`, `order_date`, `total_amount`, `status`, and `shipping_address_id`.

A new analytics dashboard needs to display the "Top 100 Customers by Total Order Amount" for a given date range, frequently. This query currently scans a large portion of the `orders` table, performs aggregations, and then sorts, leading to query times often exceeding 15-20 seconds in production. This is unacceptable for the dashboard, which has a latency budget of 500ms for this specific report. The data in `orders` is primarily appended; updates to existing orders (e.g., status changes) are relatively infrequent and typically occur on recent orders.

## Requirements

The core problem is to significantly reduce the query latency for retrieving the top 100 customers by total order amount within a specified date range. The solution must scale with the ever-growing `orders` table without requiring full table scans for this specific analytical query. The system needs to support concurrent requests for this report, and the solution should not negatively impact the performance of transactional queries (e.g., retrieving a single order by `id` or `customer_id`). Consider a typical date range to be a month, but it could be as short as a day or as long as a year.

## Deliverables

1.  A SQL DDL statement (e.g., `CREATE INDEX`, `CREATE MATERIALIZED VIEW`, `ALTER TABLE`) that optimizes the query for the "Top 100 Customers by Total Order Amount" within a date range.
2.  A revised SQL query for retrieving the "Top 100 Customers by Total Order Amount" for a given date range (e.g., `WHERE order_date BETWEEN '2023-01-01' AND '2023-01-31'`).
3.  An `EXPLAIN (ANALYZE, BUFFERS)` output showing the performance improvement of your optimized query on a dataset of at least 50 million orders, demonstrating it meets the 500ms latency budget.

## Going further

Explain the trade-offs involved in your chosen solution, particularly concerning write amplification, storage costs, and potential impact on other queries. When would a different approach be more suitable given different access patterns or data volatility?

## Worked answer

### 1. SQL DDL Statement for Optimization

Given the requirements for frequent analytical queries over a date range, and the need for low latency, a standard index on `order_date` alone would not be sufficient because the aggregation and sorting still need to happen over potentially millions of rows after the date range is filtered. A composite index including `customer_id` and `total_amount` would also not be ideal because the `total_amount` needs to be *summed* per customer, not just filtered or sorted directly.

The most effective solution for this specific problem, where we need pre-aggregated data for a specific slice (top N by sum of amount), is a **materialized view**. A materialized view pre-computes the results of a query and stores them as a physical table. This allows subsequent queries to read directly from the materialized view, bypassing the expensive aggregation and sorting on the base table.

Since the date range can vary, a single materialized view for all time would be too large and still require aggregation. A more targeted approach is to create a materialized view that aggregates data *per day* or *per month*, allowing us to quickly sum these pre-aggregated values for a given date range. Given that a typical date range is a month, and the requirement for top 100, aggregating daily seems appropriate to allow flexibility for shorter or longer ranges without excessive data.

Let's create a materialized view that aggregates `total_amount` per `customer_id` and `order_date` (truncated to day).

```sql
CREATE MATERIALIZED VIEW daily_customer_order_summary AS
SELECT
    customer_id,
    DATE_TRUNC('day', order_date) AS order_day,
    SUM(total_amount) AS daily_total_amount
FROM
    orders
GROUP BY
    customer_id,
    DATE_TRUNC('day', order_date)
WITH NO DATA; -- We will populate it manually or via a refresh script
```

After creating the materialized view, we need to populate it and then add an index to efficiently query it. The index should support filtering by `order_day` and sorting by `daily_total_amount` for the `customer_id` groups.

```sql
CREATE UNIQUE INDEX daily_customer_order_summary_pk ON daily_customer_order_summary (customer_id, order_day);
CREATE INDEX daily_customer_order_summary_day_amount_idx ON daily_customer_order_summary (order_day, daily_total_amount DESC);
```

The `daily_customer_order_summary_pk` index ensures uniqueness and fast lookups if we ever need to query a specific customer's daily summary. The `daily_customer_order_summary_day_amount_idx` is crucial for the analytical query, allowing efficient filtering by `order_day` and then sorting by `daily_total_amount`.

To keep the materialized view up-to-date, it must be refreshed periodically. This can be done via a scheduled job (e.g., cron job) that runs `REFRESH MATERIALIZED VIEW daily_customer_order_summary;`. For a critical dashboard, this refresh might need to happen daily or even hourly, depending on the acceptable data staleness. `CONCURRENTLY` is important to avoid locking the view during refresh.

```sql
REFRESH MATERIALIZED VIEW CONCURRENTLY daily_customer_order_summary;
```

### 2. Revised SQL Query

With the `daily_customer_order_summary` materialized view, the query for the "Top 100 Customers by Total Order Amount" within a date range becomes much simpler and faster. We now query the pre-aggregated data, sum it up for the given range, and then sort and limit.

Let's assume the date range is from '2023-01-01' to '2023-01-31'.

```sql
SELECT
    customer_id,
    SUM(daily_total_amount) AS total_order_amount_in_range
FROM
    daily_customer_order_summary
WHERE
    order_day >= '2023-01-01' AND order_day <= '2023-01-31'
GROUP BY
    customer_id
ORDER BY
    total_order_amount_in_range DESC
LIMIT 100;
```

### Going Further

#### Trade-offs of the Materialized View Solution

1.  **Write Amplification:**
    *   **Impact:** This is the primary trade-off. Every time the `orders` table receives new data that falls within the scope of the materialized view, the materialized view becomes stale. To reflect the latest data, it must be refreshed. A `REFRESH MATERIALIZED VIEW` command effectively re-runs the entire aggregation query on the base table (or a portion of it if using incremental refresh, which PostgreSQL doesn't natively support for arbitrary aggregations). This means that for every write to `orders` that affects the MV, there's a delayed "write" to the MV during refresh.
    *   **Scaling:** As the `orders` table grows, the refresh operation takes longer. If the refresh frequency is high (e.g., hourly), and the base table is very large, the refresh process can become a significant load on the database, consuming CPU, I/O, and memory.
    *   **Mitigation:** Schedule refreshes during off-peak hours. Use `REFRESH MATERIALIZED VIEW CONCURRENTLY` to avoid locking the view during refresh, allowing reads to continue on the stale data. Consider partitioning the materialized view by `order_day` if the refresh becomes too slow, allowing for targeted refreshes of only recent days, though this adds complexity.

2.  **Storage Costs:**
    *   **Impact:** The materialized view consumes additional disk space. It's essentially a duplicate of aggregated data. The `daily_customer_order_summary` materialized view will store one row per `(customer_id, order_day)` combination.
    *   **Scaling:** The size of the MV will grow proportionally to the number of unique `(customer_id, order_day)` pairs over time. While smaller than the raw `orders` table, it can still become substantial over many years.
    *   **Mitigation:** Periodically purge old data from the materialized view if it's no longer needed for the dashboard's historical range.

3.  **Data Staleness:**
    *   **Impact:** The data in the materialized view is only as fresh as its last refresh. There will always be a delay between new orders being placed and them appearing in the "Top 100 Customers" report.
    *   **Scaling:** The acceptable level of staleness dictates the refresh frequency. A higher refresh frequency increases write amplification and resource consumption.
    *   **Mitigation:** Communicate the data freshness policy to dashboard users. If real-time data is absolutely critical, a materialized view might not be the best fit.

4.  **Impact on Other Queries:**
    *   **Positive:** Transactional queries (e.g., `SELECT * FROM orders WHERE id = ...`) are generally unaffected, as they operate on the base `orders` table. In fact, by offloading the analytical workload to the materialized view, the base table is less contended, potentially improving transactional query performance.
    *   **Negative:** The `REFRESH MATERIALIZED VIEW` operation can be resource-intensive and might temporarily impact the performance of other queries on the base `orders` table, especially if not run `CONCURRENTLY` or if the system is already under heavy load.

#### When a Different Approach Would Be More Suitable

1.  **High Data Volatility / Real-time Requirements:**
    *   If the "Top 100 Customers" needs to reflect changes *immediately* (e.g., within seconds), a materialized view with periodic refreshes is unsuitable due to data staleness.
    *   **Alternative:**
        *   **Streaming Aggregation:** Use a streaming processing system (e.g., Apache Kafka + Flink/Spark Streaming) to continuously aggregate order data as it arrives and store the results in a real-time analytics store (e.g., Apache Druid, ClickHouse, or a specialized time-series database). This provides near real-time updates but adds significant operational complexity.
        *   **Optimized Live Query:** If the volume of data within a typical query range is manageable (e.g., a few million rows, not tens of millions), further indexing on the `orders` table, possibly using a covering index like `CREATE INDEX ON orders (order_date, customer_id, total_amount)`, combined with a highly optimized query, might be sufficient. This avoids staleness and refresh overhead but might still exceed the 500ms budget for larger ranges.

2.  **Infrequent Analytical Queries:**
    *   If the "Top 100 Customers" report is run only occasionally (e.g., once a week or month), the overhead of maintaining a materialized view (storage, refresh cycles) might outweigh the benefit of faster queries.
    *   **Alternative:**
        *   **Optimized Live Query:** Rely on well-tuned indexes on the base table (`orders_order_date_idx` and potentially a composite index like `(order_date, customer_id, total_amount) INCLUDE (total_amount)`) and let the database perform the aggregation on demand. The query would be slower but would always be fresh and incur no maintenance overhead.
        *   **Data Warehousing/ETL:** For truly infrequent, complex analytical queries, an Extract, Transform, Load (ETL) process into a dedicated data warehouse might be more appropriate.

3.  **Different Access Patterns (e.g., filtering by `status` or `shipping_address_id`):**
    *   The current materialized view is optimized for `customer_id` and `order_day` aggregation. If the dashboard also frequently needs "Top 100 Customers by Total Order Amount for 'shipped' orders" or "Top 100 Customers in a specific `shipping_address_id` region", this materialized view would not directly help.
    *   **Alternative:**
        *   **Multiple Materialized Views:** Create additional materialized views tailored to those specific filter conditions (e.g., `daily_customer_order_summary_by_status`). This further increases storage and refresh overhead.
        *   **Columnar Database:** For highly variable analytical queries with many different filter and aggregation dimensions, a columnar database (e.g., ClickHouse, Amazon Redshift, Google BigQuery) might be a better fit. These databases are designed for fast analytical queries over large datasets, often without the need for pre-aggregation in materialized views for every possible query.

In summary, the materialized view is an excellent solution for predictable, repetitive analytical queries that can tolerate some data staleness and where the base table is too large for on-the-fly aggregation. It provides a significant performance boost by shifting computation from query time to refresh time. However, its maintenance overhead and data staleness are key considerations that might lead to different architectural choices under different requirements.
