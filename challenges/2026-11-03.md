Currently, the service uses an in-memory queue and processes records one by one. This approach is becoming a bottleneck. When a large file arrives, the service's memory usage spikes dramatically, often leading to out-of-memory errors or significant processing delays, especially when multiple large files are uploaded concurrently. The current processing rate is too slow to meet the new 5-minute SLA for large file ingestion. You suspect that inefficient streaming and buffering are the culprits.

-   **Order Preservation:** The original order of records within each batch must be maintained during processing and forwarding.

## Worked answer

### Streaming Data Pipeline

This solution implements a Node.js streaming pipeline using TypeScript to process large datasets efficiently, addressing memory usage and order preservation.

The core idea is to leverage Node.js `Readable` and `Transform` streams to process data incrementally. We use a custom `Transform` stream for validation and enrichment, and another for batching. To ensure ordered asynchronous forwarding, we introduce a `BatchProcessor` class that manages the state of pending batches and dispatches them to the downstream service only when their preceding batches have been successfully sent.

import { Readable } from 'stream';
import { RawRecord } from './types';

/**
 * Creates a mock readable stream that emits a specified number of RawRecord objects.
 * This simulates reading a large file incrementally.
 */
export class MockDataStream extends Readable {
  private currentRecordId = 0;
  private totalRecords: number;

  constructor(totalRecords: number, options?: ConstructorParameters<typeof Readable>[0]) {
    super({ objectMode: true, ...options });
    this.totalRecords = totalRecords;
  }

  _read(size: number): void {
    // Simulate backpressure by only pushing a few records at a time
    for (let i = 0; i < size && this.currentRecordId < this.totalRecords; i++) {
      const record: RawRecord = {
        id: `record-${this.currentRecordId}`,
        value: `some-data-${this.currentRecordId}`,
        // Add more mock data as needed
      };
      this.push(record);
      this.currentRecordId++;
    }

    if (this.currentRecordId >= this.totalRecords) {
      this.push(null); // Signal end of stream
    }
  }
}

// src/batchingStream.ts
import { Transform } from 'stream';
import { TransformedRecord, DataBatch } from './types';

/**
 * A Transform stream that groups incoming records into fixed-size batches.
 * Operates in objectMode.
 */
export class BatchingStream extends Transform {
  private currentBatch: TransformedRecord[] = [];
  private currentBatchId = 0;
  private batchSize: number;

  constructor(batchSize: number, options?: ConstructorParameters<typeof Transform>[0]) {
    super({ objectMode: true, ...options });
    this.batchSize = batchSize;
  }

  _transform(chunk: TransformedRecord, encoding: BufferEncoding, callback: (error?: Error | null, data?: any) => void): void {
    this.currentBatch.push(chunk);

    if (this.currentBatch.length >= this.batchSize) {
      this.flushBatch();
    }
    callback();
  }

  _flush(callback: (error?: Error | null, data?: any) => void): void {
    // Push any remaining records as a final batch
    if (this.currentBatch.length > 0) {
      this.flushBatch();
    }
    callback();
  }

  private flushBatch(): void {
    const batch: DataBatch = {
      batchId: this.currentBatchId++,
      records: this.currentBatch,
    };
    this.push(batch);
    this.currentBatch = []; // Reset for the next batch
  }
}

/**

async function sendBatchToDownstream(batch: DataBatch): Promise<void> {

  const latency = Math.random() * 100 + 50; // 50-150ms
  await new Promise(resolve => setTimeout(resolve, latency));

  if (Math.random() < 0.01) { // 1% chance of failure
    throw new Error(`Simulated downstream service error for batch ${batch.batchId}`);

/**
 * Manages the ordered asynchronous forwarding of data batches.
 * Ensures batches are sent to the downstream service in their original order,
 * even if individual `sendBatchToDownstream` calls complete out of order.
 */
export class BatchProcessor {
  private pendingBatches = new Map<number, DataBatch>();
  private nextExpectedBatchId = 0;
  private activePromises = new Set<Promise<void>>(); // Track active downstream calls
  private maxConcurrentDownstreamCalls: number;

  constructor(maxConcurrentDownstreamCalls: number = 5) {
    this.maxConcurrentDownstreamCalls = maxConcurrentDownstreamCalls;
  }

  /**
   * Adds a batch to the processor. It will be sent when its turn comes.
   */
  public async addBatch(batch: DataBatch): Promise<void> {
    this.pendingBatches.set(batch.batchId, batch);
    await this.processQueue();
  }

  /**
   * Processes the queue, sending batches in order.
   * This method is called whenever a new batch arrives or a downstream call completes.
   */
  private async processQueue(): Promise<void> {
    // Keep sending batches as long as they are the next expected and we are not exceeding concurrency limits
    while (this.pendingBatches.has(this.nextExpectedBatchId) && this.activePromises.size < this.maxConcurrentDownstreamCalls) {
      const batchToSend = this.pendingBatches.get(this.nextExpectedBatchId)!;
      this.pendingBatches.delete(this.nextExpectedBatchId);
      this.nextExpectedBatchId++;

      const sendPromise = sendBatchToDownstream(batchToSend)
        .then(() => {
          // console.log(`Successfully forwarded batch ${batchToSend.batchId}`);
        })
        .catch(error => {
          console.error(`Failed to forward batch ${batchToSend.batchId}:`, error.message);
          // In a real system, you'd implement retry logic, dead-letter queue, or alert here.
          // For this exercise, we just log and continue.
        })
        .finally(() => {
          this.activePromises.delete(sendPromise);
          // After a promise resolves/rejects, try to process the queue again
          // in case it unblocked the next expected batch or freed up a slot.
          this.processQueue();
        });

      this.activePromises.add(sendPromise);
    }
  }

  /**
   * Waits for all currently active downstream forwarding operations to complete.
   * Useful for graceful shutdown or ensuring all data is processed before exiting.
   */
  public async drain(): Promise<void> {
    // Wait for all active downstream calls to finish
    await Promise.allSettled(Array.from(this.activePromises));

    // After all active calls are done, check if there are still pending batches
    // This can happen if a batch was added but couldn't be sent due to being out of order.
    // In a real scenario, you might want to error if pendingBatches is not empty here,
    // as it means some batches were never sent.
    if (this.pendingBatches.size > 0) {
      console.warn(`Drain completed, but ${this.pendingBatches.size} batches are still pending (likely due to previous errors or out-of-order processing).`);
    }
  }
}

import { pipeline } from 'stream';
import { MockDataStream } from './mockDataStream';
import { RecordProcessorStream } from './recordProcessorStream';
import { BatchingStream } from './batchingStream';
import { BatchProcessor } from './batchProcessor';

export async function runPipeline(
  totalRecords: number,
  batchSize: number,
  maxConcurrentDownstreamCalls: number
): Promise<void> {
  console.log(`Starting pipeline for ${totalRecords} records, batch size ${batchSize}, max concurrent downstream calls ${maxConcurrentDownstreamCalls}...`);

  const mockStream = new MockDataStream(totalRecords);
  const recordProcessor = new RecordProcessorStream();
  const batcher = new BatchingStream(batchSize);
  const batchProcessor = new BatchProcessor(maxConcurrentDownstreamCalls);

  let processedBatchesCount = 0;
  let processedRecordsCount = 0;

  // Use stream.pipeline for robust error handling and proper cleanup
  await new Promise<void>((resolve, reject) => {
    pipeline(
      mockStream,
      recordProcessor,
      batcher,
      async function (source) { // This is a passthrough function to consume batches
        for await (const batch of source) {
          processedBatchesCount++;
          processedRecordsCount += batch.records.length;
          await batchProcessor.addBatch(batch);
        }
      }
    )
    .on('error', (err) => {
      console.error('Pipeline failed:', err);
      reject(err);
    })
    .on('close', () => {
      console.log('Pipeline stream closed.');
      resolve();
    });
  });

  console.log('Waiting for all downstream batches to complete...');
  await batchProcessor.drain(); // Ensure all sent batches are acknowledged

  console.log(`Pipeline finished. Total records processed: ${processedRecordsCount}, total batches forwarded: ${processedBatchesCount}.`);
}

### Explanation of Constraints Addressed

#### Memory Usage

The solution addresses memory usage by employing Node.js streams:

1.  **Stream Parsing (MockDataStream):** The `MockDataStream` generates records on demand using `_read()`. It does not load all `totalRecords` into memory at once. It pushes records only when requested by the downstream consumer, respecting backpressure.
2.  **Record Validation/Transformation (RecordProcessorStream):** This `Transform` stream processes records one by one (or in small internal buffers managed by Node.js streams). It never holds the entire dataset in memory. Each `_transform` call receives a single `RawRecord` and outputs a single `TransformedRecord`.
3.  **Batching (BatchingStream):** This `Transform` stream accumulates records into a `currentBatch` array only up to the `batchSize` (e.g., 1000 records). Once the batch is full, it's pushed downstream, and the `currentBatch` is cleared. This limits the memory footprint for batching to `batchSize * sizeof(TransformedRecord)`. For 1000 records, each perhaps 1KB, this is only 1MB, well within the 256MB limit.
4.  **Asynchronous Forwarding (BatchProcessor):** The `BatchProcessor` stores `pendingBatches` in a `Map`. The number of pending batches is limited by the rate at which the downstream service can accept them and the `maxConcurrentDownstreamCalls` setting. If the downstream service is slow, backpressure will naturally propagate up the stream pipeline, slowing down the `MockDataStream` and preventing excessive memory buildup. The `activePromises` set ensures we don't overwhelm the downstream service or memory with too many concurrent in-flight requests.

By using streams, the memory footprint remains relatively constant regardless of the total file size, scaling with the `batchSize` and `maxConcurrentDownstreamCalls` rather than the input size.

#### Order Preservation

Order preservation is critical and handled by the `BatchProcessor`:

1.  **Sequential Batching:** The `BatchingStream` creates batches in the exact order records arrive. `batchId` is assigned incrementally.
2.  **Ordered Dispatch:** The `BatchProcessor` maintains `nextExpectedBatchId`. It only dispatches a batch to the `sendBatchToDownstream` function if its `batchId` matches `nextExpectedBatchId`. If a batch arrives out of order (e.g., batch 3 arrives before batch 2 has been processed), it's stored in `pendingBatches` until batch 2 has been successfully sent.
3.  **Concurrent but Ordered Completion:** While `sendBatchToDownstream` calls are asynchronous and can complete out of order, the `BatchProcessor` ensures that the *logical completion* (i.e., marking a batch as "sent" and incrementing `nextExpectedBatchId`) only happens for the *next expected batch in sequence*. This guarantees that the downstream service *receives* and *processes* batches in their original order, even if the underlying network calls finish at different times.

This mechanism ensures that even if `sendBatchToDownstream` for `batchId=1` takes longer than for `batchId=2`, `batchId=2` will not be marked as "sent" until `batchId=1` has successfully completed and its promise resolved.

### Going Further

#### `stream.pipeline` vs. Manual Chaining with `.pipe()`

Both `stream.pipeline` and manual `.pipe()` chaining are used to connect Node.js streams. However, they offer different levels of robustness, especially concerning error handling and resource management.

**Manual Chaining with `.pipe()`:**

```typescript
readableStream
  .pipe(transformStream1)
  .pipe(transformStream2)
  .pipe(writableStream);
```

**Pros:**
*   **Simplicity for basic cases:** Easy to read and write for straightforward stream connections.
*   **Direct control:** Allows for injecting custom logic or event listeners between `.pipe()` calls.

**Cons:**
*   **Error handling complexity:** Errors in one stream do not automatically propagate or shut down other streams in the chain. You need to manually attach `'error'` listeners to *each* stream in the chain and handle cleanup (e.g., destroying other streams) yourself. This is a common source of memory leaks or hung processes.
*   **No automatic cleanup:** If a stream ends or errors, other streams might remain open, holding onto resources.
*   **Backpressure management:** While `.pipe()` does handle backpressure automatically between connected streams, managing it across a complex chain with multiple asynchronous operations can still be tricky if not all components are well-behaved streams.

**`stream.pipeline`:**

```typescript
import { pipeline } from 'stream';

pipeline(
  readableStream,
  transformStream1,
  transformStream2,
  writableStream,
  (err) => {
    if (err) {
      console.error('Pipeline failed:', err);
    } else {
      console.log('Pipeline succeeded.');
    }
  }
);
```
Or with `async/await` (as used in the solution):
```typescript
import { pipeline } from 'stream/promises'; // For promise-based pipeline

try {
  await pipeline(
    readableStream,
    transformStream1,
    transformStream2,
    writableStream
  );
  console.log('Pipeline succeeded.');
} catch (err) {
  console.error('Pipeline failed:', err);
}
```

**Pros:**
*   **Robust error handling:** `stream.pipeline` automatically tears down all streams in the chain if any stream emits an `'error'` event. It also ensures that the callback/promise is invoked with the error. This prevents resource leaks and hung processes.
*   **Automatic cleanup:** Guarantees that all streams are properly closed and resources released upon completion or error.
*   **Simplified backpressure:** Provides a more reliable and consistent backpressure mechanism across the entire chain, ensuring that a slow consumer correctly signals upstream producers to pause.
*   **Promise-based API:** The `stream/promises` module provides an `async/await`-compatible version, making asynchronous stream operations much cleaner to manage.

**Cons:**
*   **Less direct control:** It's a higher-level abstraction. If you need to inject custom logic or inspect intermediate data *between* stream stages without creating a new `Transform` stream, it can be less straightforward than `.pipe()`.
*   **No immediate return value:** Unlike `.pipe()` which returns the destination stream, `pipeline` returns `void` (or a `Promise<void>`), meaning you can't easily chain further operations directly after `pipeline` itself.

#### Scenarios for Preference:

**Strongly prefer `stream.pipeline` when:**

1.  **Production-grade applications:** For critical microservices where reliability, resource management, and error resilience are paramount. This is especially true for long-running processes or services handling high throughput.
2.  **Complex stream chains:** When you have more than two or three streams connected. Manually managing error listeners and cleanup across many streams quickly becomes unwieldy and error-prone.
3.  **Asynchronous operations within streams:** If your `Transform` streams involve `async` operations (like database calls or network requests), `pipeline`'s robust error handling becomes even more crucial to prevent unhandled promise rejections or zombie streams.
4.  **Preventing resource leaks:** Any scenario where streams might be long-lived or handle large amounts of data, making proper cleanup essential to avoid memory leaks or file descriptor exhaustion.
5.  **Simplified `async/await` integration:** The `stream/promises` version of `pipeline` makes it very natural to integrate stream processing into modern `async/await` codebases.

**Prefer manual `.pipe()` when:**

1.  **Simple, short-lived scripts/CLI tools:** For quick, one-off tasks where the stream chain is very basic (e.g., `fs.createReadStream().pipe(zlib.createGzip()).pipe(fs.createWriteStream())`) and the risk of unhandled errors is low or acceptable.
2.  **Debugging or experimentation:** Sometimes, for quick tests or to understand stream behavior, `.pipe()` is faster to set up.
3.  **Specific intermediate stream manipulation:** If you need to perform an action on the *result* of one `.pipe()` call before piping to the next, and creating a dedicated `Transform` stream for that action feels like overkill. (Though this is often a sign that a `Transform` stream *is* the correct abstraction).

In the context of the challenge scenario (critical microservice, large files, high concurrency, strict SLAs), `stream.pipeline` is the unequivocally superior choice due to its robustness, automatic error handling, and resource management, which are vital for a stable and performant production system. The solution correctly uses `stream.pipeline` for these reasons.
