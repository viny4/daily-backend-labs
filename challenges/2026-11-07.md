## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies track their internal assets (laptops, monitors, software licenses, etc.). Each asset has a unique identifier, a type (e.g., 'Laptop', 'Monitor', 'Software License'), and an assigned employee. Over time, the database of assets for some large enterprise clients has grown significantly, sometimes exceeding 5 million assets.

A critical feature is the "Asset Audit" report. This report is generated weekly for all clients and needs to quickly identify assets that have not been assigned to an employee for a prolonged period (e.g., more than 90 days), indicating they might be unutilized or misplaced. The current implementation fetches all assets for a client, filters them in application code, and then sorts them by the date they became unassigned. This process used to be fast but now, for larger clients, it can take several minutes to generate the report, often timing out the API gateway.

The `assets` table has columns like `id` (UUID), `client_id` (UUID), `asset_type` (VARCHAR), `assigned_employee_id` (UUID, nullable), `last_assigned_at` (TIMESTAMP), `unassigned_since` (TIMESTAMP, nullable). When an asset is assigned, `unassigned_since` is set to NULL. When it's unassigned, `unassigned_since` is set to the current timestamp.

## Requirements

The challenge is to optimize the retrieval of "unassigned assets" for a given `client_id` that have been unassigned for more than 90 days. The primary goal is to drastically reduce the query latency for the "Asset Audit" report generation, ensuring it completes within a 5-second window even for clients with millions of assets. The solution must be efficient in terms of database resource usage and must scale with the growing number of assets and clients. Concurrency is a concern, as multiple clients might trigger their reports simultaneously.

## Deliverables

1.  A SQL query that efficiently retrieves all assets for a given `client_id` that have been unassigned for more than 90 days, ordered by `unassigned_since` (oldest first).
2.  An explanation of the data structure(s) or indexing strategy you would propose to support this query.
3.  A brief analysis of the time complexity of your proposed solution for retrieving the relevant assets.

## Going further

Explain how your proposed indexing strategy would impact `INSERT` and `UPDATE` operations on the `assets` table, particularly for large clients, and what trade-offs you are making.

## Worked answer

### 1. SQL Query for Unassigned Assets

The following SQL query efficiently retrieves assets for a given `client_id` that have been unassigned for more than 90 days, ordered by `unassigned_since` (oldest first).

```sql
SELECT
    id,
    asset_type,
    assigned_employee_id,
    last_assigned_at,
    unassigned_since
FROM
    assets
WHERE
    client_id = 'a1b2c3d4-e5f6-7890-1234-567890abcdef' -- Replace with actual client_id
    AND unassigned_since IS NOT NULL
    AND unassigned_since < NOW() - INTERVAL '90 days'
ORDER BY
    unassigned_since ASC;
```

**Explanation:**

1.  **`SELECT ... FROM assets`**: We select the necessary columns from the `assets` table. It's good practice to select only the columns you need, rather than `SELECT *`, to reduce data transfer overhead.
2.  **`WHERE client_id = '...'`**: This is the primary filter, ensuring we only consider assets for the specified client. This is highly selective and crucial for performance.
3.  **`AND unassigned_since IS NOT NULL`**: This condition explicitly filters for assets that have been unassigned. Assets currently assigned will have `unassigned_since` as `NULL`.
4.  **`AND unassigned_since < NOW() - INTERVAL '90 days'`**: This is the core logic for identifying assets unassigned for more than 90 days.
    *   `NOW()` gets the current timestamp.
    *   `INTERVAL '90 days'` subtracts 90 days from the current timestamp.
    *   Comparing `unassigned_since` to be *less than* this calculated timestamp means the asset was unassigned *before* 90 days ago, thus satisfying the "more than 90 days" condition.
5.  **`ORDER BY unassigned_since ASC`**: This sorts the results by the `unassigned_since` timestamp in ascending order, presenting the oldest unassigned assets first, as required by the report.

### 2. Data Structure(s) and Indexing Strategy

To support the above query efficiently, we need a composite index. The most effective indexing strategy would be:

**Composite B-tree Index:**

```sql
CREATE INDEX idx_assets_client_unassigned_since ON assets (client_id, unassigned_since);
```

**Explanation of the Index:**

*   **B-tree Index:** This is the standard index type for most relational databases (like PostgreSQL, MySQL) and is excellent for equality lookups, range queries, and ordered retrieval.
*   **Composite Index `(client_id, unassigned_since)`:**
    *   **`client_id` (first column):** This is critical because the `WHERE` clause starts with `client_id = '...'`. The database can quickly navigate the B-tree to find the block of data corresponding to a specific `client_id`. This significantly narrows down the search space from millions of assets to potentially hundreds of thousands or fewer for a single client.
    *   **`unassigned_since` (second column):** Once the `client_id` is located, the index is then ordered by `unassigned_since` within that `client_id`'s partition of the index. This allows the database to:
        *   Efficiently apply the range condition `unassigned_since < NOW() - INTERVAL '90 days'` by traversing only a relevant segment of the index.
        *   Directly satisfy the `ORDER BY unassigned_since ASC` clause without needing a separate sort operation on the filtered results, as the data is already pre-sorted in the index. This is known as an "index-only scan" or "index scan with order by" depending on the database system and whether all selected columns are covered by the index or the table itself.

**Why this specific order?**

The order of columns in a composite index matters. Placing `client_id` first is crucial because it's used for an equality filter (`=`). This allows the index to be used to quickly locate the relevant client's data. If `unassigned_since` were first, the database would have to scan a much larger portion of the index (all assets unassigned for 90+ days, across *all* clients) before filtering by `client_id`.

### 3. Time Complexity Analysis

Let's analyze the time complexity with the proposed `idx_assets_client_unassigned_since` index.

*   **`N`**: Total number of assets in the `assets` table across all clients.
*   **`C`**: Number of distinct clients.
*   **`A_c`**: Average number of assets per client (`N/C`).
*   **`U_c`**: Number of unassigned assets for a specific client that meet the 90-day criterion.

1.  **Locating `client_id`:**
    *   Using the B-tree index, finding the starting point for a specific `client_id` takes approximately **O(log N)** time. This is because the index is structured as a tree, and traversing it to find a specific key is logarithmic with respect to the total number of entries in the index.

2.  **Scanning for `unassigned_since` within `client_id`:**
    *   Once the `client_id`'s segment in the index is found, the database needs to scan this segment to find assets where `unassigned_since < NOW() - INTERVAL '90 days'`.
    *   Since `unassigned_since` is the second column in the index, the data for a given `client_id` is already sorted by `unassigned_since`. The database can perform a range scan on this portion of the index.
    *   This scan will involve reading `U_c` entries from the index. The time complexity for this part is approximately **O(U_c)**. In the worst case, `U_c` could be a significant portion of `A_c` (e.g., if many assets are unassigned).

3.  **Ordering:**
    *   Because the index is ordered by `unassigned_since` within `client_id`, the `ORDER BY unassigned_since ASC` clause can be satisfied directly by the index scan. No additional sorting step is required.

4.  **Retrieving full rows (if not an index-only scan):**
    *   If the database cannot perform an index-only scan (i.e., if `asset_type`, `assigned_employee_id`, `last_assigned_at` are not part of the index or included columns), it will need to perform a "bookmark lookup" or "heap fetch" for each matching `id` to retrieve the other columns from the main table. This adds an I/O cost per row. In the worst case, this would be `U_c` random disk reads, which can be slow. However, modern databases often optimize this by reading blocks of data.

**Overall Time Complexity:**

The dominant factors are the initial index lookup and the subsequent scan.
*   **O(log N + U_c)**.

Given `N` up to 5 million, `log N` is small (e.g., `log2(5,000,000)` is around 22-23). The performance will primarily depend on `U_c`, the number of results returned for a specific client. If `U_c` is small (e.g., hundreds or thousands), the query will be very fast. If `U_c` is very large (e.g., hundreds of thousands), it will still be efficient because it avoids full table scans and unnecessary sorting, but the sheer volume of data returned will be the bottleneck.

This is a significant improvement over the original approach, which would involve:
*   `O(N)` to fetch all assets for a client (or `O(N)` for all clients if `client_id` wasn't indexed).
*   `O(N)` to filter in application code.
*   `O(N log N)` to sort in application code.

The proposed solution pushes the filtering and sorting to the database, leveraging optimized index structures, drastically reducing latency.

### Going Further: Impact on `INSERT` and `UPDATE` Operations

The proposed `CREATE INDEX idx_assets_client_unassigned_since ON assets (client_id, unassigned_since);` index will have the following impacts on `INSERT` and `UPDATE` operations:

**Impact on `INSERT` Operations:**

*   **Increased Write Latency:** Every time a new asset is inserted into the `assets` table, the database must also insert a corresponding entry into the `idx_assets_client_unassigned_since` index. This involves navigating the B-tree structure to find the correct insertion point and potentially reorganizing parts of the tree (e.g., page splits) to maintain its sorted order and balance.
*   **Increased Disk Space:** The index itself consumes disk space, proportional to the number of indexed columns and rows. For 5 million assets, this index will add a noticeable amount of storage overhead.
*   **Concurrency Contention:** During index updates, database systems typically acquire locks on index pages or nodes. In a high-concurrency environment with many `INSERT`s, this can lead to contention, where multiple transactions wait for locks to be released, potentially slowing down overall write throughput.

**Impact on `UPDATE` Operations:**

*   **Updates to `client_id` or `unassigned_since`:** If an `UPDATE` statement modifies either the `client_id` or the `unassigned_since` column for an existing asset, the database must effectively perform a "delete" from the old index location and an "insert" into the new index location. This is because the position of the entry in the B-tree depends on these values. This will incur similar overheads to an `INSERT` (latency, disk I/O, potential contention).
*   **Updates to other columns (e.g., `asset_type`, `last_assigned_at`):** If an `UPDATE` statement modifies columns *not* included in the index (like `asset_type` or `last_assigned_at`), the index itself does not need to be updated. However, the main table row will be updated, and depending on the database's MVCC (Multi-Version Concurrency Control) implementation, this might still involve writing a new version of the row, potentially leaving "dead tuples" that need vacuuming. The index remains unaffected.
*   **Updates to `assigned_employee_id` (which affects `unassigned_since`):** When an asset is assigned or unassigned, the `assigned_employee_id` and `unassigned_since` columns are typically updated.
    *   If `unassigned_since` changes from `NULL` to a timestamp (asset becomes unassigned), a new entry for `unassigned_since` will be added to the index.
    *   If `unassigned_since` changes from a timestamp to `NULL` (asset becomes assigned), the entry for `unassigned_since` will be removed from the index (or marked as invalid, depending on the database). Both scenarios incur index maintenance overhead.

**Trade-offs Made:**

1.  **Read Performance vs. Write Performance:** We are explicitly prioritizing read performance for the "Asset Audit" report. The trade-off is an increase in write latency and resource consumption (CPU, I/O) for `INSERT` and `UPDATE` operations that affect the indexed columns. For a system where reads are much more frequent or critical than writes, this is a common and acceptable trade-off.
2.  **Disk Space vs. Query Speed:** The index consumes additional disk space. This is a direct trade-off for faster query execution, as the index provides a pre-sorted, quickly searchable data structure.
3.  **Complexity vs. Simplicity:** Adding and maintaining indexes adds a layer of operational complexity (e.g., monitoring index size, fragmentation, ensuring indexes are used by queries). However, for critical performance requirements, this complexity is justified.
4.  **Specific Query Optimization vs. General Purpose:** This index is highly optimized for the specific "unassigned assets for a client" query. It might not be optimal for other types of queries (e.g., finding all assets of a certain `asset_type` across all clients).

**What breaks first at ten times the scale (50 million assets):**

At 50 million assets, the primary bottleneck will shift from query latency to **write throughput and overall database resource contention**, especially if `INSERT` and `UPDATE` rates are also scaled up proportionally.

1.  **Index Maintenance Overhead:** The cost of maintaining the `idx_assets_client_unassigned_since` index (and any other indexes) will become very significant. Each `INSERT` or relevant `UPDATE` will require more CPU cycles and I/O operations to update the larger B-tree structure. Page splits will be more frequent, leading to higher write amplification.
2.  **Disk I/O Contention:** With more data and more index updates, the database will perform a much higher volume of disk writes. If the underlying storage system cannot keep up, write operations will queue, leading to increased latency for all write transactions.
3.  **Memory Usage:** Larger indexes require more memory (RAM) for the database to cache frequently accessed index pages. If the index size exceeds available memory, the database will have to constantly read index pages from disk, severely degrading performance.
4.  **Vacuuming/Maintenance:** For databases like PostgreSQL, MVCC creates dead tuples. Larger tables and higher update rates mean more dead tuples, requiring more frequent and resource-intensive `VACUUM` operations to reclaim space and maintain performance.
5.  **Lock Contention:** With more concurrent operations on a larger dataset, the probability of lock contention on index pages or table rows increases, potentially leading to transaction slowdowns or deadlocks.

To mitigate these issues at 10x scale, one might need to consider:
*   **Sharding:** Distributing data across multiple database instances, typically by `client_id`, to reduce the size of individual tables and indexes.
*   **Faster Storage:** Upgrading to NVMe SSDs or other high-performance storage solutions.
*   **Database Tuning:** Extensive tuning of database parameters related to memory, caching, and concurrency.
*   **Delayed Index Updates (less common for critical indexes):** For less critical indexes, some systems allow for asynchronous index updates, but this introduces eventual consistency.
