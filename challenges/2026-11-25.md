## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee shifts and schedules. A core feature allows managers to generate **"Team Availability Reports"**. These reports show, for a selected date range (e.g., next 7 days), which employees are scheduled, on leave, or available for a specific department.

The data for these reports is derived from several tables: `employees` (employee details), `shifts` (scheduled shifts), and `leave_requests` (approved time off). Generating these reports involves complex joins and aggregations across millions of rows, especially for larger organizations with thousands of employees and extensive historical shift data.

Recently, the average generation time for these reports has climbed to 5-10 seconds, and during peak hours (e.g., Monday mornings when managers plan the week), database CPU utilization spikes, occasionally leading to timeouts. Managers often generate the same report multiple times within a short period, refreshing it to check for updates or sharing it with colleagues. The reports are specific to a `department_id` and a `date_range`, and potentially filterable by `employee_status` (e.g., only active employees). The system serves thousands of departments across hundreds of clients.

## Requirements

Implement a caching strategy using Redis to significantly reduce the latency of "Team Availability Reports" and alleviate the load on the PostgreSQL database. The solution should:

1.  **Prioritize read performance:** Most report requests are for data that changes infrequently within a workday.
2.  **Handle data staleness:** While low latency is critical, absolute real-time accuracy is not always required. A report that is a few minutes stale is acceptable, but a report from yesterday is not.
3.  **Support high concurrency:** Many managers might request the same report concurrently.
4.  **Manage cache size:** The number of unique reports can be large (many departments, many date ranges), so the cache should not grow indefinitely.

## Deliverables

1.  A Python/Django or TypeScript/Node.js function/method that, given `department_id`, `start_date`, `end_date`, and `employee_status_filter`, returns the "Team Availability Report" data, leveraging Redis for caching.
2.  Demonstrate how the cache is populated on a miss and how subsequent hits retrieve data from Redis.
3.  Define the cache key structure and the eviction policy (TTL/LRU) used.
4.  Briefly explain how the chosen cache invalidation strategy (or lack thereof) addresses data staleness requirements.

## Going further

Explain the trade-offs of using a "cache-aside" pattern versus a "read-through" or "write-through" cache for this specific scenario, particularly considering the report generation complexity and the acceptable staleness.

### 1. `generate_team_availability_report` function

import datetime

import redis

from django.db import models
from django.conf import settings

# Initialize Redis client
# In a real Django app, this would likely be configured via settings
# and potentially managed by a connection pool.
redis_client = redis.Redis(
    host=settings.REDIS_HOST,
    port=settings.REDIS_PORT,
    db=settings.REDIS_DB,
    decode_responses=True # Decodes responses from bytes to strings
)

# --- ORM Models (simplified for demonstration) ---
class Employee(models.Model):
    id = models.UUIDField(primary_key=True)
    department_id = models.UUIDField()
    first_name = models.CharField(max_length=100)
    last_name = models.CharField(max_length=100)
    status = models.CharField(max_length=50) # e.g., 'active', 'inactive', 'on_leave'

    class Meta:
        db_table = 'employees'

class Shift(models.Model):
    id = models.UUIDField(primary_key=True)
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE)
    shift_date = models.DateField()
    start_time = models.DateTimeField()
    end_time = models.DateTimeField()

    class Meta:
        db_table = 'shifts'

class LeaveRequest(models.Model):
    id = models.UUIDField(primary_key=True)
    employee = models.ForeignKey(Employee, on_delete=models.CASCADE)
    start_date = models.DateField()
    end_date = models.DateField()
    status = models.CharField(max_length=50) # e.g., 'approved', 'pending'

    class Meta:
        db_table = 'leave_requests'

# --- Report Generation Logic ---
def _fetch_report_from_db(
    department_id: str,
    start_date: datetime.date,
    end_date: datetime.date,
    employee_status_filter: Optional[str] = None
) -> List[Dict[str, Any]]:
    """
    Simulates fetching and aggregating complex report data from the database.
    This is the expensive operation we want to cache.
    """
    print(f"--- DB HIT: Generating report for department {department_id} from {start_date} to {end_date} ---")

    # Start with all employees in the department, potentially filtered by status
    employees_query = Employee.objects.filter(department_id=department_id)
    if employee_status_filter:
        employees_query = employees_query.filter(status=employee_status_filter)
    
    employees = list(employees_query.values('id', 'first_name', 'last_name', 'status'))
    employee_ids = [emp['id'] for emp in employees]

    # Fetch shifts for these employees within the date range
    shifts = Shift.objects.filter(
        employee_id__in=employee_ids,
        shift_date__range=(start_date, end_date)
    ).values('employee_id', 'shift_date', 'start_time', 'end_time')

    # Fetch approved leave requests for these employees within the date range
    # We need to consider overlaps, not just exact matches
    leave_requests = LeaveRequest.objects.filter(
        employee_id__in=employee_ids,
        status='approved',
        start_date__lte=end_date, # Leave starts on or before report end
        end_date__gte=start_date  # Leave ends on or after report start
    ).values('employee_id', 'start_date', 'end_date')

    # Aggregate data into the report format
    report_data: Dict[str, Dict[str, Any]] = {emp['id']: {
        'employee_id': emp['id'],
        'name': f"{emp['first_name']} {emp['last_name']}",
        'status': emp['status'],
        'availability': {} # Date -> 'scheduled', 'on_leave', 'available'
    } for emp in employees}

    # Initialize availability for all report days
    current_date = start_date
    while current_date <= end_date:
        for emp_id in report_data:
            report_data[emp_id]['availability'][current_date.isoformat()] = 'available'
        current_date += datetime.timedelta(days=1)

    # Apply shifts
    for shift in shifts:
        emp_id = shift['employee_id']
        shift_date_str = shift['shift_date'].isoformat()
        if emp_id in report_data and shift_date_str in report_data[emp_id]['availability']:
            report_data[emp_id]['availability'][shift_date_str] = 'scheduled'

    # Apply leave requests
    for leave in leave_requests:
        emp_id = leave['employee_id']
        leave_start = leave['start_date']
        leave_end = leave['end_date']
        
        current_leave_date = max(leave_start, start_date) # Start from report start or leave start
        while current_leave_date <= min(leave_end, end_date): # End at report end or leave end
            leave_date_str = current_leave_date.isoformat()
            if emp_id in report_data and leave_date_str in report_data[emp_id]['availability']:
                report_data[emp_id]['availability'][leave_date_str] = 'on_leave'
            current_leave_date += datetime.timedelta(days=1)

    # Convert availability dict to a sorted list of daily statuses for cleaner output
    for emp_id in report_data:
        report_data[emp_id]['availability'] = [
            {'date': date_str, 'status': status}
            for date_str, status in sorted(report_data[emp_id]['availability'].items())
        ]

    return list(report_data.values())


def generate_team_availability_report(
    department_id: str,
    start_date: datetime.date,
    end_date: datetime.date,
    employee_status_filter: Optional[str] = None
) -> List[Dict[str, Any]]:
    """
    Generates a Team Availability Report, leveraging Redis for caching.
    """
    cache_key = _build_cache_key(department_id, start_date, end_date, employee_status_filter)
    
    # Try to retrieve from cache
    cached_report_json = redis_client.get(cache_key)

    if cached_report_json:
        print(f"--- CACHE HIT for key: {cache_key} ---")
        # Deserialize the JSON string back into a Python list of dicts
        return json.loads(cached_report_json)
    
    print(f"--- CACHE MISS for key: {cache_key} ---")
    # Cache miss: generate report from database
    report_data = _fetch_report_from_db(department_id, start_date, end_date, employee_status_filter)
    
    # Serialize the report data to JSON and store in cache
    # We use a TTL of 5 minutes (300 seconds)
    # The report data can be quite large, so ensure Redis memory limits are configured.
    redis_client.setex(cache_key, settings.REPORT_CACHE_TTL_SECONDS, json.dumps(report_data, default=str))
    
    return report_data

# --- Helper for Cache Key ---
def _build_cache_key(
    department_id: str,
    start_date: datetime.date,
    end_date: datetime.date,
    employee_status_filter: Optional[str] = None
) -> str:
    """
    Constructs a unique cache key for a given report request.
    """
    key_parts = [
        "team_availability_report",
        str(department_id),
        start_date.isoformat(),
        end_date.isoformat()
    ]
    if employee_status_filter:
        key_parts.append(employee_status_filter)
    
    return ":".join(key_parts)

1.  **`redis_client` initialization:** Sets up a connection to Redis. `decode_responses=True` is crucial for `redis-py` to automatically decode byte responses to UTF-8 strings, making it easier to work with JSON.
2.  **`_fetch_report_from_db`:** This function encapsulates the expensive database operations. It performs joins and aggregations to compile the report. The complexity here justifies caching.
3.  **`generate_team_availability_report`:** This is the core function implementing the cache-aside pattern:
    *   It first constructs a unique `cache_key` based on all report parameters.
    *   It attempts to `GET` the report data from Redis using this key.
    *   **Cache Hit:** If data is found (`cached_report_json` is not `None`), it's deserialized from JSON and returned immediately.
    *   **Cache Miss:** If not found, it calls `_fetch_report_from_db` to generate the report.
    *   After generation, it serializes the `report_data` to a JSON string and stores it in Redis using `SETEX`. `SETEX` is used to set the key with an expiration time (TTL).
4.  **`_build_cache_key`:** This helper function ensures that every unique combination of `department_id`, `start_date`, `end_date`, and `employee_status_filter` maps to a distinct Redis key. Using `isoformat()` for dates ensures consistent string representation.

### 3. Define the cache key structure and the eviction policy (TTL/LRU) used.

**Cache Key Structure:**

The cache key is defined by the `_build_cache_key` function:

```python
def _build_cache_key(
    department_id: str,
    start_date: datetime.date,
    end_date: datetime.date,
    employee_status_filter: Optional[str] = None
) -> str:
    key_parts = [
        "team_availability_report",
        str(department_id),
        start_date.isoformat(),
        end_date.isoformat()
    ]
    if employee_status_filter:
        key_parts.append(employee_status_filter)
    
    return ":".join(key_parts)
```

Example Key: `team_availability_report:d1:2026-12-01:2026-12-07:active`

*   **Prefix (`team_availability_report`):** Clearly identifies the type of data being cached. This is good practice for managing different cache types and for easier inspection in Redis.
*   **`department_id`:** The primary identifier for the report's scope.
*   **`start_date.isoformat()` and `end_date.isoformat()`:** ISO 8601 format (`YYYY-MM-DD`) provides a consistent, unambiguous, and lexicographically sortable string representation for dates.
*   **`employee_status_filter` (optional):** Included if present, ensuring reports with different filters are cached separately.

This structure ensures that each unique combination of parameters results in a unique cache key, preventing incorrect data from being served.

**Eviction Policy:**

We are using a **Time-To-Live (TTL)** eviction policy, implemented via `redis_client.setex(cache_key, settings.REPORT_CACHE_TTL_SECONDS, json.dumps(report_data, default=str))`.

*   **`settings.REPORT_CACHE_TTL_SECONDS`:** This is configured to `300` seconds (5 minutes) in our example.
*   When `SETEX` is used, Redis automatically expires the key after the specified number of seconds. If a key is requested after its TTL has expired, it's treated as a cache miss.

Additionally, if the Redis server's memory usage reaches its configured `maxmemory` limit, Redis will employ a **Least Recently Used (LRU)** or other configured eviction policy (e.g., `allkeys-lru`, `volatile-lru`, `noeviction`) to free up space. For this scenario, `volatile-lru` (evict LRU keys with an expire set) or `allkeys-lru` (evict LRU keys regardless of expire) would be appropriate choices, with `volatile-lru` being more targeted if other data types are stored in the same Redis instance. Given that all our report keys have a TTL, `volatile-lru` would prioritize expiring keys that are less frequently accessed, even if their TTL hasn't fully elapsed.

### 4. Briefly explain how the chosen cache invalidation strategy (or lack thereof) addresses data staleness requirements.

The chosen strategy relies solely on **Time-To-Live (TTL)** for "invalidation." There is no explicit event-driven invalidation mechanism (e.g., deleting a cache key when a shift is updated or a leave request is approved).

**How it addresses staleness:**

*   **Acceptable Staleness:** The requirement states, "A report that is a few minutes stale is acceptable, but a report from yesterday is not." A 5-minute TTL (`REPORT_CACHE_TTL_SECONDS = 300`) directly meets this requirement. Reports will never be older than 5 minutes plus the time it takes to regenerate (which is acceptable given the 5-10 second generation time).
*   **Simplicity:** This approach is extremely simple to implement and manage. There's no complex logic for tracking dependencies or triggering invalidations across services.
*   **Reduced Database Load:** Even with a short TTL, the cache significantly reduces the load on the database, especially during peak hours, by serving frequently requested reports from Redis. Managers refreshing reports within a 5-minute window will get instant responses.

**Trade-offs and Limitations:**

*   **Eventual Consistency:** The reports are eventually consistent. If an employee's shift changes or a leave request is approved, the cached report will reflect this change only after its TTL expires and it's regenerated from the database. For "a few minutes stale is acceptable," this is fine.
*   **No Immediate Updates:** If a manager makes a critical change and immediately refreshes the report expecting to see it, they might be disappointed if the report is still cached. However, the scenario explicitly states that "absolute real-time accuracy is not always required."
*   **Potential for Brief Inaccuracy:** During the 5-minute window, the report might not reflect the absolute latest state of the underlying data. This is the inherent trade-off of caching for performance.

For this specific scenario, where "a few minutes stale is acceptable," a TTL-based strategy is a pragmatic and effective solution due to its simplicity and direct alignment with the staleness tolerance.

### Going further: Trade-offs of "cache-aside" versus "read-through" or "write-through" cache

Let's analyze the trade-offs for this specific "Team Availability Reports" scenario:

**1. Cache-Aside (Implemented Solution)**

*   **Description:** The application code is responsible for checking the cache before hitting the database. If data is in the cache (hit), it's returned. If not (miss), the application fetches data from the database, stores it in the cache, and then returns it.
*   **Pros for this scenario:**
    *   **Simplicity and Control:** Easy to implement with existing application logic and a Redis client library. We have full control over cache key generation, serialization, and TTLs.
    *   **Flexibility:** Allows for complex report generation logic (like our `_fetch_report_from_db` function) that might involve multiple database queries, aggregations, and business logic before the final report is formed. A generic caching layer might struggle with this.
    *   **Database Isolation:** The cache is entirely separate from the database. If Redis goes down, the application can still fall back to the database (though performance will suffer).
    *   **Cost-Effective:** Often uses a standalone Redis instance, which is generally more cost-effective than a database with built-in caching features for this scale.
*   **Cons for this scenario:**
    *   **Cache Stampede:** If a popular report expires and many concurrent requests hit the cache simultaneously, they will all miss, leading to multiple concurrent database queries for the same report. This can still spike database CPU. (Mitigation: Redis locks like `SETNX` can prevent this, but add complexity).
    *   **Dual Responsibility:** The application code is responsible for both data retrieval and cache management, potentially cluttering business logic.
    *   **Stale Data Window:** The report can be stale for the duration of the TTL.

**2. Read-Through Cache**

*   **Description:** The application interacts *only* with the cache. On a cache miss, the cache itself (or a caching layer/proxy) is responsible for fetching the data from the underlying data source (e.g., database), populating itself, and then returning the data to the application.
*   **Pros for this scenario:**
    *   **Simplified Application Logic:** The application doesn't need to know *how* data is fetched on a miss; it just asks the cache. This separates concerns.
    *   **Automatic Cache Population:** The caching layer handles the "miss" logic, reducing boilerplate in the application.
    *   **Reduced Cache Stampede (Potentially):** Many read-through caches (like some commercial offerings or custom proxies) can implement internal locking to prevent multiple concurrent fetches for the same key on a miss, thus mitigating cache stampede.
*   **Cons for this scenario:**
    *   **Complexity of Integration:** Implementing a read-through cache for a complex, aggregated report like this is challenging. The caching layer would need to understand how to execute the complex SQL joins and aggregations, or call a specific application endpoint to generate the report. This often requires a custom proxy or a highly configurable caching service.
    *   **Limited Flexibility for Complex Logic:** If the report generation involves more than just a direct database lookup (e.g., calling external APIs, applying complex business rules in application code), a generic read-through cache might not be able to execute this logic.
    *   **Vendor Lock-in/Overhead:** Often requires a specialized caching service or framework that supports read-through patterns, which might introduce vendor lock-in or additional operational overhead.

**3. Write-Through Cache**

*   **Description:** The application writes data to the cache, and the cache is responsible for writing that data to the underlying database. The write is only considered complete when both the cache and the database have been updated.
*   **Pros for this scenario:**
    *   **Data Consistency:** Ensures the cache is always consistent with the database on writes.
    *   **Simplified Writes:** Application only writes to the cache.
*   **Cons for this scenario:**
    *   **Not suitable for this scenario:** Write-through caches are primarily for *write-heavy* data that needs strong consistency between cache and database. Our "Team Availability Reports" are *read-only* reports derived from other data. We don't "write" reports; we "generate" them. Applying a write-through pattern here would be nonsensical, as the report data itself is not directly mutable by the application. Changes to employee shifts or leave requests happen in the `shifts` and `leave_requests` tables, not directly to the report data.

**Conclusion for this scenario:**

The **cache-aside** pattern is the most appropriate and pragmatic choice for "Team Availability Reports" due to:

1.  **Report Generation Complexity:** The reports involve complex joins and aggregations, which are best handled by the application's ORM and business logic (`_fetch_report_from_db`). A generic read-through cache would struggle to encapsulate this logic.
2.  **Acceptable Staleness:** The requirement for "a few minutes stale" perfectly aligns with a simple TTL-based cache-aside strategy, avoiding the need for complex, real-time invalidation.
3.  **High Concurrency (with caveats):** While cache-aside can suffer from cache stampede, for reports that are relatively stable for 5 minutes, the stampede window is limited. If stampede becomes a significant issue, we could augment the cache-aside with a distributed lock (e.g., using `SETNX` in Redis) to ensure only one worker regenerates the report on a miss, while others wait.
4.  **Operational Simplicity:** It's easier to implement and maintain with a standard Redis client library than trying to force a read-through pattern onto a highly aggregated, derived data set.

A read-through cache would be a strong contender if the cached items were simpler, directly mapping to single database records or simple queries that a caching layer could easily execute. A write-through cache is entirely unsuitable for this read-only, derived data scenario.
