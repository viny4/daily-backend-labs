## Scenario

Your team manages a multi-tenant SaaS platform where each customer has their own dedicated set of data within shared PostgreSQL tables, identified by a `tenant_id` column. A core part of the application involves a `documents` table that stores various types of documents uploaded by users. This table has grown significantly and now contains over 100 million rows, with an average of 10 million rows per tenant. The schema looks roughly like:

```sql
CREATE TABLE documents (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    document_type TEXT NOT NULL,
    uploaded_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    storage_path TEXT NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    is_deleted BOOLEAN DEFAULT FALSE,
    -- ... other document metadata
);
```

One critical and frequently accessed endpoint is responsible for retrieving all *active* documents (i.e., `is_deleted = FALSE`) for a specific tenant, ordered by their `uploaded_at` timestamp in descending order, with pagination. The query currently looks something like this:

```sql
SELECT id, document_type, uploaded_at, storage_path, file_size_bytes
FROM documents
WHERE tenant_id = '...' AND is_deleted = FALSE
ORDER BY uploaded_at DESC
OFFSET ... LIMIT ...;
```

This query was performing adequately when the table was smaller, but now, for larger tenants with millions of active documents, it frequently takes 5-10 seconds to execute, sometimes even timing out. This is causing significant user frustration and impacting the application's perceived performance. The latency budget for this endpoint is 500ms.

## Requirements

Optimize the performance of the described query to consistently meet the 500ms latency budget, even for tenants with millions of active documents. You have full control over database schema, indexes, and query modifications. The solution must not introduce significant new operational overhead (e.g., complex ETL processes, separate read-only replicas solely for this purpose) or dramatically increase storage costs. Concurrently, write operations (insertions, updates, and soft deletes) to the `documents` table must remain performant, ideally below 100ms.

## Worked answer

### 1. DDL Statement for Optimization

The primary bottleneck for the given query is the need to scan a large portion of the `documents` table to find active documents for a specific tenant and then sort them. A compound index that covers `tenant_id`, `is_deleted`, and `uploaded_at` in the correct order will allow PostgreSQL to efficiently locate and order the relevant rows without a full table scan or an in-memory sort.

```sql
CREATE INDEX idx_documents_tenant_active_uploaded_at_desc
ON documents (tenant_id, is_deleted, uploaded_at DESC)
WHERE is_deleted = FALSE;
```

**Explanation:**

*   `tenant_id`: This is the leading column in the index because it's the primary filter in the `WHERE` clause. This allows PostgreSQL to quickly narrow down the search to a specific tenant's data.
*   `is_deleted`: Including this column and adding a `WHERE is_deleted = FALSE` clause to the index creates a *partial index*. This means the index only stores entries for active documents, significantly reducing its size and making it more efficient for queries specifically looking for active documents. It also directly satisfies the `is_deleted = FALSE` condition without needing to check the table heap.
*   `uploaded_at DESC`: By including `uploaded_at` in descending order, the index can directly provide the rows in the desired sort order, eliminating the need for a separate sort operation (filesort) during query execution. This is crucial for performance with `ORDER BY ... DESC OFFSET ... LIMIT ...`.

### 3. Explanation of Performance Improvement

The chosen solution significantly improves performance by creating a **partial, composite index** `idx_documents_tenant_active_uploaded_at_desc`. This index allows PostgreSQL to perform an **Index Only Scan** (or at least an Index Scan) to efficiently locate rows matching `tenant_id` and `is_deleted = FALSE`, and crucially, retrieve them directly in `uploaded_at DESC` order. This eliminates the need for a full table scan and an expensive in-memory sort operation, which are the primary bottlenecks for the original query. The partial nature of the index also means it's smaller and faster to scan, as it only contains entries for active documents.

### 4. Impact on Write Operations

*   **`INSERT` operations:** New `INSERT`s will incur a slight overhead as the new row must also be added to the `idx_documents_tenant_active_uploaded_at_desc` index (if `is_deleted` is `FALSE`). This is generally a small, constant factor increase in write time.
*   **`UPDATE` operations (specifically `is_deleted` and `uploaded_at`):**
    *   Updating `is_deleted` from `FALSE` to `TRUE` (soft-delete): This will cause the corresponding entry to be removed from the partial index, as it no longer satisfies `WHERE is_deleted = FALSE`. This is a relatively cheap operation.
    *   Updating `is_deleted` from `TRUE` to `FALSE` (undelete): This will cause a new entry to be inserted into the partial index. This is similar to an `INSERT` operation's index overhead.
    *   Updating `uploaded_at`: If `is_deleted` is `FALSE`, updating `uploaded_at` will require updating the index entry to maintain the correct sort order. This is typically implemented as a delete-and-insert operation within the index structure.
*   **`DELETE` operations:** Hard `DELETE`s will require removing the corresponding entry from the `idx_documents_tenant_active_uploaded_at_desc` index (if it existed there), which is a relatively cheap operation.

In general, the impact on write operations will be a slight increase in latency due to index maintenance. For a single index, this overhead is usually well within the 100ms target for individual operations, especially given that B-tree index operations are highly optimized.

### Going Further

If the `is_deleted` column is updated very frequently (thousands of documents per second for a single tenant), the current solution could face challenges:

1.  **Index Bloat and Maintenance Overhead:** Frequent updates to `is_deleted` (especially toggling between `TRUE` and `FALSE`) will lead to a high rate of index entry insertions and deletions. This can cause index bloat (dead tuples in the index) and increase the workload for `VACUUM` and `AUTOVACUUM`, potentially impacting overall database performance. The index will need to be rebuilt or reindexed more frequently to reclaim space and maintain efficiency.
2.  **Cache Invalidation:** High update rates on `is_deleted` for a specific tenant mean that the relevant parts of the index are constantly changing. This can lead to increased cache misses for both read and write operations on that index, as the data blocks are frequently modified and evicted from memory.

**Alternative or Complementary Strategies:**

1.  **Separate "Active" Table / Materialized View (for extreme cases):** For tenants with extremely high soft-delete rates, consider maintaining a separate, smaller `active_documents` table or a `MATERIALIZED VIEW` that only contains `is_deleted = FALSE` documents.
    *   **Pros:** Reads from this table/view would be extremely fast as it's optimized for the active state.
    *   **Cons:** This introduces significant operational overhead. For a separate table, `INSERT`s would need to go into both tables, and `UPDATE`s/`DELETE`s would need to be synchronized. For a materialized view, refreshes (`REFRESH MATERIALIZED VIEW`) can be expensive and block reads, or require complex concurrent refresh strategies. This violates the "not introduce significant new operational overhead" requirement for most scenarios but might be considered for a single, hyperactive tenant.

2.  **Delayed Deletion / Asynchronous Processing:** Instead of immediately updating `is_deleted` in the main table, a soft-delete request could queue a background job. The `is_deleted` column could then be updated asynchronously, perhaps in batches.
    *   **Pros:** Reduces the immediate write load on the main `documents` table and its index.
    *   **Cons:** Introduces eventual consistency for the `is_deleted` status. Users might see a document as active for a short period after they "delete" it, which might not be acceptable for all applications.

3.  **Partitioning by `tenant_id`:** While not directly addressing the `is_deleted` update rate, partitioning the `documents` table by `tenant_id` (e.g., using `LIST` or `RANGE` partitioning) could help.
    *   **Pros:** Each tenant's data (and its associated index data) would reside in its own partition. This can reduce contention on index structures for very active tenants, as updates would be localized to a specific partition. It also makes maintenance operations (like `VACUUM` or `REINDEX`) more targeted.
    *   **Cons:** Adds complexity to schema management and query planning. While it helps with overall scalability, it doesn't fundamentally change the index update behavior for a single tenant's partition.

For most scenarios, the proposed partial index is robust. The "going further" scenario describes an extreme edge case. If `is_deleted` updates truly reach "thousands per second *for a single tenant*", the most practical first step would be to monitor index bloat and `autovacuum` activity closely. If index bloat becomes problematic, a strategy of scheduled `REINDEX` operations during off-peak hours might be necessary. If the latency of `is_deleted` updates themselves becomes an issue, then asynchronous processing or a separate active table might be considered, but with a clear understanding of the trade-offs in consistency and operational complexity.
