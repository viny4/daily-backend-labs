## Scenario

Your team maintains a critical backend service that processes real-time sensor data from industrial IoT devices. Each device sends a stream of measurements (e.g., temperature, pressure, vibration) at a high frequency. To detect anomalies and trigger alerts, the service needs to maintain a "sliding window" of the most recent `N` measurements for each device and quickly calculate aggregate statistics (like average, min, max) over this window.

The current implementation stores all incoming data in a time-series database, then queries it for each aggregation, which is becoming prohibitively slow as the number of devices and data velocity increases. You need a more efficient in-memory approach that can keep up with the data ingest rate and provide low-latency query responses.

## Requirements

The system must handle hundreds of thousands of active devices, each potentially sending measurements every few seconds. The sliding window size `N` can vary per device, but is typically between 100 and 1000 measurements. The primary constraint is real-time processing: a new measurement must be processed and the window updated within 10-50 milliseconds, and aggregate statistics for a device's window must be available within 100 milliseconds. Concurrency is a concern as multiple devices might send data simultaneously, and multiple clients might request statistics. The solution should be resilient to individual device data streams temporarily stopping or starting.

## Worked answer

### 1. Data Structure for a Single Device's Sliding Window

To efficiently manage a sliding window and calculate aggregate statistics (average, min, max) in real-time, we need a data structure that supports fast appends, fast evictions from the front, and quick access to statistical aggregates. A simple `list` or `array` would allow O(1) appends but O(N) evictions (if shifting elements) or O(N) for min/max if re-scanning.

The most suitable data structure for this scenario is a **Deque (Double-Ended Queue)**, specifically implemented using a **circular buffer** or a **doubly linked list**, combined with auxiliary data structures to track min/max.

For the core window data, a **Deque** is ideal because it provides O(1) time complexity for adding elements to one end and removing elements from the other end. This directly supports the "sliding" nature of the window: new measurements are added to the back, and old measurements are removed from the front.

To maintain min and max efficiently, we can augment the Deque with two additional **Monotonic Deques** (also known as "min-deque" and "max-deque"). A monotonic deque stores elements in strictly increasing (for min) or decreasing (for max) order. When a new element is added, elements larger (for min-deque) or smaller (for max-deque) than it are removed from the back. When an element is removed from the front of the main window, if it's the current min/max, it's also removed from the front of the corresponding monotonic deque.

**Why this combination is suitable:**

*   **O(1) Add/Evict:** The main Deque ensures that adding a new measurement and evicting the oldest one are constant-time operations.
*   **O(1) Min/Max Query:** The monotonic deques allow us to retrieve the current minimum and maximum values in O(1) time, as they are always at the front of their respective deques.
*   **O(1) Average Query:** The sum of values can be maintained incrementally. When a new value is added, it's added to the sum. When an old value is evicted, it's subtracted from the sum. The count of elements is also maintained. Average is then `sum / count`.

**High-level structure for a single device:**

```
DeviceWindow {
    measurements: Deque<Measurement>  // Stores (timestamp, value) tuples
    min_deque: Deque<Value>           // Monotonically increasing values
    max_deque: Deque<Value>           // Monotonically decreasing values
    current_sum: float                // Sum of all values in 'measurements'
    current_count: int                // Number of values in 'measurements'
    window_size: int                  // Maximum capacity N
}

Measurement {
    timestamp: long
    value: float
}
```

### 2. `add_measurement(device_id, timestamp, value)` Operation

This operation adds a new measurement to the window, updates the sum and count, and evicts the oldest measurement if the window size `N` is exceeded. It also updates the monotonic deques for min/max tracking.

```pseudocode
// Global store for all device windows
DEVICE_WINDOWS: Map<device_id, DeviceWindow>

function add_measurement(device_id: string, timestamp: long, value: float):
    // 1. Retrieve or initialize device window
    if device_id not in DEVICE_WINDOWS:
        // Assume default window_size N is configured per device or globally
        // For simplicity, let's say N=500 for new devices
        DEVICE_WINDOWS[device_id] = new DeviceWindow(window_size=500)

    window = DEVICE_WINDOWS[device_id]

    // 2. Add new measurement to the main window and update sum/count
    new_measurement = {timestamp: timestamp, value: value}
    window.measurements.add_back(new_measurement)
    window.current_sum += value
    window.current_count += 1

    // 3. Update min_deque
    while not window.min_deque.is_empty() and window.min_deque.peek_back() > value:
        window.min_deque.remove_back()
    window.min_deque.add_back(value)

    // 4. Update max_deque
    while not window.max_deque.is_empty() and window.max_deque.peek_back() < value:
        window.max_deque.remove_back()
    window.max_deque.add_back(value)

    // 5. Evict oldest measurement if window size is exceeded
    if window.current_count > window.window_size:
        oldest_measurement = window.measurements.remove_front()
        window.current_sum -= oldest_measurement.value
        window.current_count -= 1

        // 6. Update min_deque and max_deque for eviction
        // Only remove if the oldest_measurement.value was the actual min/max
        // and is still at the front of the monotonic deque.
        if oldest_measurement.value == window.min_deque.peek_front():
            window.min_deque.remove_front()
        if oldest_measurement.value == window.max_deque.peek_front():
            window.max_deque.remove_front()

    // Optional: Clean up device window if no data for a long time
    // (e.g., if oldest_measurement.timestamp is too old, or device inactive)
    // This is a separate concern for long-term memory management.
```

### 3. `get_window_statistics(device_id)` Operation

This operation retrieves the current average, min, and max values from the sliding window for a given device.

```pseudocode
function get_window_statistics(device_id: string): (average: float, min: float, max: float):
    if device_id not in DEVICE_WINDOWS:
        // Handle case where device has no data or is unknown
        return (NaN, NaN, NaN) // Or throw an error, return default values

    window = DEVICE_WINDOWS[device_id]

    if window.current_count == 0:
        // Handle empty window
        return (NaN, NaN, NaN)

    // Average is directly available from pre-calculated sum and count
    average = window.current_sum / window.current_count

    // Min and Max are directly available from the front of monotonic deques
    min_val = window.min_deque.peek_front()
    max_val = window.max_deque.peek_front()

    return (average, min_val, max_val)
```

### 4. Concurrency Handling for the Same Device

Concurrency is a critical concern when multiple threads/processes might try to add measurements or query statistics for the *same* device simultaneously. Without proper synchronization, race conditions could lead to corrupted data (e.g., incorrect sum, count, or inconsistent states of deques) or incorrect statistics being returned.

The most straightforward approach to handle concurrency for a single device's window is to use a **mutex (mutual exclusion lock)** associated with each `DeviceWindow` object.

**Approach:**

1.  **Per-Device Lock:** Each `DeviceWindow` instance should have its own lock (e.g., a `threading.Lock` in Python, `std::mutex` in C++, `sync.Mutex` in Go).
2.  **Acquire Lock:** Before any operation (`add_measurement` or `get_window_statistics`) modifies or reads the `DeviceWindow`'s internal state, the lock for that specific `device_id`'s window must be acquired.
3.  **Release Lock:** After the operation completes, the lock must be released.

**Pseudocode for `add_measurement` with locking:**

```pseudocode
// DeviceWindow structure with a lock
DeviceWindow {
    measurements: Deque<Measurement>
    min_deque: Deque<Value>
    max_deque: Deque<Value>
    current_sum: float
    current_count: int
    window_size: int
    lock: Mutex // Add a mutex to each window
}

function add_measurement(device_id: string, timestamp: long, value: float):
    // ... (initialization of window if not exists, outside the lock if possible,
    //      or use a global lock for map access, then per-device lock)

    // Simplified: Assume window exists or is created safely
    window = DEVICE_WINDOWS[device_id]

    window.lock.acquire() // Acquire lock for this specific device's window
    try:
        // All the logic from the previous add_measurement pseudocode goes here
        // ... (add to measurements, update sum/count, update min/max deques, evict oldest)
    finally:
        window.lock.release() // Ensure lock is always released
```

**Pseudocode for `get_window_statistics` with locking:**

```pseudocode
function get_window_statistics(device_id: string): (average: float, min: float, max: float):
    if device_id not in DEVICE_WINDOWS:
        return (NaN, NaN, NaN)

    window = DEVICE_WINDOWS[device_id]

    window.lock.acquire() // Acquire lock for this specific device's window
    try:
        if window.current_count == 0:
            return (NaN, NaN, NaN)

        average = window.current_sum / window.current_count
        min_val = window.min_deque.peek_front()
        max_val = window.max_deque.peek_front()
        return (average, min_val, max_val)
    finally:
        window.lock.release() // Ensure lock is always released
```

**Trade-offs:**

*   **Pros:** Simple to implement, guarantees data consistency and correctness.
*   **Cons:** Introduces contention if many threads frequently access the *same* device's window. This could become a bottleneck if a single device receives extremely high data velocity or is queried very frequently by multiple clients. However, given "hundreds of thousands of active devices," the probability of multiple threads contending for the *exact same* device's lock simultaneously is lower than if there were only a few devices. Most contention would be distributed across different device locks.
*   **Alternative (more complex):** Using a **Read-Write Lock (RWLock)** could allow multiple readers (`get_window_statistics`) to access the window concurrently, while still ensuring exclusive access for writers (`add_measurement`). This would improve read throughput but adds complexity. Given the 100ms latency requirement for stats, a simple mutex might be sufficient if write operations are fast enough.

**Scalability at 10x:**

At ten times the scale (millions of devices, higher data velocity), the primary bottleneck would likely shift from individual device contention to:

1.  **Memory:** Storing hundreds of thousands or millions of `DeviceWindow` objects, each with its deques, sum, count, and lock, will consume significant RAM. Each `Measurement` object also has overhead.
2.  **Global `DEVICE_WINDOWS` Map Contention:** The `Map<device_id, DeviceWindow>` itself might become a contention point if many threads are trying to add *new* devices or look up existing ones concurrently. This could be mitigated by using a concurrent map (e.g., `ConcurrentHashMap` in Java, sharded map, or protecting access with a global RWLock).
3.  **CPU for Lock Management:** While individual operations are O(1), the overhead of acquiring and releasing millions of locks per second across all devices could add up.

The chosen data structure itself (Deque + Monotonic Deques) remains efficient, but the surrounding infrastructure for managing millions of these structures and their concurrent access would need careful optimization (e.g., sharding devices across multiple service instances, using lock-free data structures where possible, or optimizing memory layout).

### Going Further

**Time Complexity (Big O Notation):**

*   **`add_measurement` operation:**
    *   **Main Deque (measurements):** `add_back()` and `remove_front()` are O(1).
    *   **Monotonic Deques (min_deque, max_deque):** In the worst case, when adding a new value, we might remove all existing elements from the back of a monotonic deque. This seems like O(N), but crucially, each element is added to the monotonic deque *at most once* and removed *at most once*. Therefore, over a sequence of `k` operations, the total time spent on monotonic deque operations is O(k). This is known as **amortized O(1)**. Similarly, removing elements from the front due to window eviction is O(1).
    *   **Sum and Count updates:** O(1).
    *   **Overall:** The `add_measurement` operation has an **amortized time complexity of O(1)**.

*   **`get_window_statistics` operation:**
    *   **Average:** `current_sum` and `current_count` are directly available, so calculation is O(1).
    *   **Min/Max:** `peek_front()` on the monotonic deques is O(1).
    *   **Overall:** The `get_window_statistics` operation has a **time complexity of O(1)**.

**How this prevents degradation to O(N) or worse:**

The chosen data structure and algorithm prevent degradation to O(N) or worse because:

1.  **Deque for Window Management:** A `Deque` (implemented as a circular buffer or doubly linked list) allows for O(1) additions to the back and O(1) removals from the front. This is crucial for the "sliding" aspect, as we don't need to shift elements or reallocate large arrays when the window moves. A simple `list` or `array` would typically incur O(N) for evictions (if elements are shifted) or O(N) for re-scanning for min/max.
2.  **Incremental Sum/Count:** Instead of re-calculating the sum and count over the entire window every time (which would be O(N)), we maintain `current_sum` and `current_count` incrementally. Each `add_measurement` operation performs O(1) arithmetic updates.
3.  **Monotonic Deques for Min/Max:** This is the key innovation for O(1) min/max queries. Without them, calculating min/max would require iterating through all `N` elements in the window, resulting in an O(N) operation. The monotonic deques ensure that the current min and max are always at their front, accessible in O(1). While the `add_measurement` operation might involve multiple removals from the back of the monotonic deques, the amortized analysis shows that this cost is spread out, making the average cost per operation O(1).

**Why O(1) is critical for real-time scenario:**

*   **Predictable Performance:** O(1) operations mean that the time taken to process a measurement or retrieve statistics does not depend on the window size `N`. This is vital for real-time systems where latency guarantees are paramount. If operations were O(N), a larger window size (e.g., 1000 measurements) would directly lead to longer processing times, potentially violating the 10-50ms processing and 100ms query latency requirements.
*   **High Throughput:** With O(1) operations, the system can process a very high volume of measurements per second. If it were O(N), increasing `N` would reduce the number of measurements that could be processed within a given time frame, making it impossible to keep up with high-frequency data streams.
*   **Scalability:** The O(1) nature of operations allows the system to scale efficiently with the number of devices and data velocity. While the *total* number of operations increases with more devices, the performance per device remains constant regardless of its window size, making resource planning more predictable.
*   **Resource Efficiency:** Avoiding full window scans (O(N)) for every operation saves CPU cycles, which can then be used to process more devices or handle other system tasks.
