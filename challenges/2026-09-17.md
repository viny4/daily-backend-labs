## Scenario

Your team maintains a critical backend service that manages customer support tickets for a large enterprise SaaS platform. Historically, all attachments (files like screenshots, log snippets, or documents) associated with these tickets were stored directly in the primary PostgreSQL database as `BYTEA` columns. This seemed fine when the company was smaller, but now, with millions of tickets and an average of 3-5 attachments per ticket, the `ticket_attachments` table has grown to hundreds of gigabytes, and the largest individual attachments are several megabytes.

Specifically, the `GET /api/v1/tickets/{ticket_id}` endpoint, which fetches a ticket's details along with all its attachments, is becoming a bottleneck. This endpoint is frequently accessed by support agents, and its latency has crept up to 3-5 seconds, even for tickets with only a few attachments. Loading all attachment data into memory on the application server and then serving it is resource-intensive and slow. Your monitoring shows high I/O wait on the database and increased memory usage in your application servers during these requests.

## Requirements

The primary goal is to significantly improve the performance and scalability of attachment handling for support tickets. You need to reduce the latency of fetching ticket details and their attachments, specifically targeting the `GET /api/v1/tickets/{ticket_id}` endpoint. The solution must handle potential growth to hundreds of millions of attachments and accommodate individual attachments up to 50MB in size. It should also be cost-effective and resilient to failures. Support agents should still be able to view and download attachments seamlessly.

Constraints:
*   **Scale:** Millions of tickets, potentially hundreds of millions of attachments.
*   **Latency:** `GET /api/v1/tickets/{ticket_id}` endpoint should return within 500ms for typical cases, excluding the actual file download time from the client's perspective.
*   **Attachment Size:** Up to 50MB per attachment.
*   **Cost-effectiveness:** Avoid overly complex or expensive solutions where simpler alternatives exist.
*   **Durability:** Attachment data must be durable and highly available.
*   **Security:** Attachments can contain sensitive customer data, so access must be properly controlled and authenticated.

### 1. High-level Architecture Diagram

```mermaid
graph TD
    subgraph Client
        A[Support Agent Browser]

    subgraph Existing Backend Service
        B[Django Application Server]
        C[PostgreSQL Database]
    end

    subgraph New Attachment Storage
        D[Cloud Object Storage (e.g., S3, GCS)]
        E[CDN (Optional, e.g., CloudFront, Cloudflare)]
    end

    A -- 1. GET /api/v1/tickets/{ticket_id} --> B
    B -- 2. Query ticket_attachments table --> C
    C -- 3. Returns attachment metadata (IDs, filenames, object storage URLs/keys) --> B
    B -- 4. Returns ticket details + attachment metadata --> A

    A -- 5. User clicks "Download Attachment" --> B
    B -- 6. Request pre-signed URL for attachment_id --> D
    D -- 7. Returns pre-signed URL --> B
    B -- 8. Redirect (302) to pre-signed URL --> A
    A -- 9. Direct download from --> E
    E -- 10. Cache/Serve attachment --> D
```

**Explanation:**

1.  **Client Request:** A support agent's browser makes a `GET /api/v1/tickets/{ticket_id}` request to the Django application server.
2.  **Database Query (Metadata Only):** The Django application queries the PostgreSQL database for the ticket's details and **only the metadata** (e.g., ID, filename, size, object storage key/URL) of its associated attachments. The actual attachment `BYTEA` data is no longer stored in PostgreSQL.
3.  **Metadata Return:** PostgreSQL returns the ticket details and attachment metadata to the Django application.
4.  **API Response:** The Django application constructs the API response, including the ticket details and a list of attachment metadata (but no actual file content), and sends it back to the client. This significantly reduces the data transferred from the DB to the app server and from the app server to the client for the initial ticket fetch.
5.  **Attachment Download Request:** When the agent wants to download a specific attachment, their browser makes a separate request to the Django application (e.g., `GET /api/v1/attachments/{attachment_id}/download`).
6.  **Pre-signed URL Generation:** The Django application, after verifying the agent's authorization, requests a pre-signed URL from the Cloud Object Storage service for the specified attachment. This URL grants temporary, time-limited access to download the file directly from object storage.
7.  **Pre-signed URL Return:** The Cloud Object Storage service generates and returns the pre-signed URL.
8.  **Client Redirect:** The Django application responds to the client with a HTTP 302 Redirect to the pre-signed URL.
9.  **Direct Download:** The client's browser then makes a direct request to the pre-signed URL, downloading the attachment directly from the Cloud Object Storage (potentially via a CDN).
10. **CDN Caching/Serving:** If a CDN is used, it caches the attachment and serves it to the client, further reducing latency and load on the object storage for frequently accessed attachments.

### 2. Backend Service and Database Schema Changes

#### PostgreSQL Database Schema Changes

The core change is to remove the `BYTEA` column and replace it with a reference to the object storage.

**Old `ticket_attachments` table (simplified):**

```sql
CREATE TABLE ticket_attachments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ticket_id UUID NOT NULL REFERENCES tickets(id),
    filename VARCHAR(255) NOT NULL,
    content_type VARCHAR(100) NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    data BYTEA NOT NULL, -- This column is the problem
    uploaded_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

**New `ticket_attachments` table:**

```sql
CREATE TABLE ticket_attachments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ticket_id UUID NOT NULL REFERENCES tickets(id),
    filename VARCHAR(255) NOT NULL,
    content_type VARCHAR(100) NOT NULL,
    file_size_bytes BIGINT NOT NULL,
    -- New column: Stores the key/path to the object in cloud storage
    object_storage_key VARCHAR(512) NOT NULL UNIQUE,
    uploaded_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    -- Optional: Add a hash for integrity checking
    checksum_sha256 VARCHAR(64)
);
```

**Migration Strategy:**

1.  Add the `object_storage_key` and `checksum_sha256` columns to the `ticket_attachments` table, allowing NULLs initially.
2.  Implement a background migration process (e.g., a batch job or a series of scripts) to:
    *   Read `BYTEA` data from existing attachments.
    *   Upload each attachment to the new Cloud Object Storage, generating a unique `object_storage_key` (e.g., `tickets/{ticket_id}/{attachment_id}/{filename}`).
    *   Update the `ticket_attachments` table with the `object_storage_key` and `checksum_sha256` for each migrated attachment.
    *   Once all attachments are migrated and verified, remove the `BYTEA` column. This requires careful planning for downtime or a phased rollout. A common approach is to keep the `BYTEA` column for a while, mark it as deprecated, and only delete it after ensuring the new system is stable and all data is migrated.
3.  Ensure new attachments are stored directly in object storage from the start.

3.  **New Attachment Upload Endpoint (`POST /api/v1/tickets/{ticket_id}/attachments`):**
    *   When a new attachment is uploaded, the backend service will:
        *   Receive the file content.
        *   Generate a unique `object_storage_key` (e.g., `f"tickets/{ticket_id}/{attachment_uuid}/{filename}"`).
        *   Upload the file content directly to the Cloud Object Storage using its SDK (e.g., `boto3` for S3, `google-cloud-storage` for GCS).
        *   Store the `object_storage_key` and other metadata (filename, size, content type, checksum) in the `ticket_attachments` table in PostgreSQL.
        *   Return success to the client.

    **Example (simplified view logic):**
    ```python
    from django.conf import settings
    import boto3 # or google.cloud.storage

    # Initialize S3 client (or GCS client)
    s3_client = boto3.client(
        's3',
        aws_access_key_id=settings.AWS_ACCESS_KEY_ID,
        aws_secret_access_key=settings.AWS_SECRET_ACCESS_KEY,
        region_name=settings.AWS_S3_REGION_NAME
    )
    S3_BUCKET_NAME = settings.AWS_S3_BUCKET_NAME

    @api_view(['POST'])
    def upload_attachment(request, ticket_id):
        # ... authentication and authorization checks ...
        ticket = get_object_or_404(Ticket, id=ticket_id)
        uploaded_file = request.FILES['file']

        # Generate unique key for S3
        attachment_uuid = uuid.uuid4()
        object_storage_key = f"tickets/{ticket_id}/{attachment_uuid}/{uploaded_file.name}"

        try:
            # Upload to S3
            s3_client.upload_fileobj(uploaded_file, S3_BUCKET_NAME, object_storage_key)

            # Save metadata to DB
            attachment = Attachment.objects.create(
                ticket=ticket,
                filename=uploaded_file.name,
                content_type=uploaded_file.content_type,
                file_size_bytes=uploaded_file.size,
                object_storage_key=object_storage_key
            )
            return Response(AttachmentMetadataSerializer(attachment).data, status=status.HTTP_201_CREATED)
        except Exception as e:
            logger.error(f"Error uploading attachment: {e}")
            return Response({"error": "Failed to upload attachment"}, status=status.HTTP_500_INTERNAL_SERVER_ERROR)
    ```

4.  **New Attachment Download Endpoint (`GET /api/v1/attachments/{attachment_id}/download`):**
    *   This endpoint will handle requests to download a specific attachment.
    *   It will retrieve the `object_storage_key` from the database based on `attachment_id`.
    *   It will then generate a pre-signed URL from the Cloud Object Storage service for that key.
    *   Finally, it will return an HTTP 302 Redirect response to the client, pointing to the pre-signed URL.

    **Example (simplified view logic):**
    ```python
    import datetime

    @api_view(['GET'])
    def download_attachment(request, attachment_id):
        # ... authentication and authorization checks ...
        attachment = get_object_or_404(Attachment, id=attachment_id)

        # Ensure the user has access to this ticket/attachment
        # e.g., if request.user is not in ticket.assigned_agents: raise PermissionDenied

        try:
            # Generate a pre-signed URL for download
            # Expiration time should be short, e.g., 5-15 minutes
            presigned_url = s3_client.generate_presigned_url(
                'get_object',
                Params={
                    'Bucket': S3_BUCKET_NAME,
                    'Key': attachment.object_storage_key,
                    'ResponseContentDisposition': f'attachment; filename="{attachment.filename}"'
                },
                ExpiresIn=300 # URL valid for 5 minutes
            )
            return Response(status=status.HTTP_302_FOUND, headers={'Location': presigned_url})
        except Exception as e:
            logger.error(f"Error generating pre-signed URL for attachment {attachment_id}: {e}")
            return Response({"error": "Failed to generate download link"}, status=status.HTTP_500_INTERNAL_SERVER_ERROR)
    ```

### 3. Security and Access Control

Security and access control are paramount, especially with sensitive customer data. The new architecture leverages the backend service as the gatekeeper for all attachment access.

1.  **Authentication and Authorization on Backend:**
    *   **Initial Ticket Fetch (`GET /api/v1/tickets/{ticket_id}`):** When a support agent requests ticket details, the Django backend performs its standard authentication (e.g., session-based, JWT) and authorization checks (e.g., "Is this agent assigned to this ticket?", "Does this agent have the 'view_tickets' permission?"). Only if authorized, the backend retrieves the attachment metadata from PostgreSQL.
    *   **Attachment Download Request (`GET /api/v1/attachments/{attachment_id}/download`):** This is the critical point for access control. Before generating a pre-signed URL, the backend **must** perform robust authorization checks:
        *   **Authentication:** Verify the user is logged in.
        *   **Attachment Ownership/Access:** Check if the authenticated user has permission to access the specific `attachment_id`. This typically involves looking up the `attachment_id` in the database, finding its associated `ticket_id`, and then verifying the user's permissions against that ticket (e.g., is the user an agent assigned to the ticket, or a manager with broad access?).
        *   **Tenant Isolation:** If it's a multi-tenant system, ensure the attachment belongs to the tenant the user is authorized to access.

2.  **Pre-signed URLs for Direct Download:**
    *   **Temporary Access:** Pre-signed URLs provide temporary, time-limited access to the object storage. The `ExpiresIn` parameter (e.g., 5 minutes) ensures that even if a URL is intercepted, it quickly becomes invalid.
    *   **No Permanent Credentials:** The client never receives any cloud storage credentials. The backend service, using its own IAM roles/credentials, generates the URL.
    *   **Object-Level Permissions:** The pre-signed URL is specific to a single object (`object_storage_key`), preventing unauthorized access to other files in the bucket.
    *   **Content-Disposition Header:** The `ResponseContentDisposition` parameter in `generate_presigned_url` ensures that the browser downloads the file with the correct filename, rather than trying to display it inline (which could be a security risk for certain file types if not handled carefully client-side).

3.  **Cloud Object Storage Security:**
    *   **Private Bucket:** The Cloud Object Storage bucket (e.g., S3 bucket) should be configured as private, meaning no public read or write access.
    *   **IAM Policies:** The backend service's IAM role/credentials should have the minimum necessary permissions: `s3:GetObject` (for generating pre-signed URLs) and `s3:PutObject` (for uploading new attachments) on the specific bucket and object paths (e.g., `arn:aws:s3:::your-bucket-name/tickets/*`).
    *   **Encryption:** All attachments should be encrypted at rest in the object storage (e.g., S3 Managed Keys - SSE-S3, or Customer Master Keys - SSE-KMS for higher security). Data in transit between the client, backend, and object storage should use TLS/SSL.
    *   **Versioning:** Enable versioning on the object storage bucket to protect against accidental deletions or overwrites.

4.  **CDN Security (if used):**
    *   If a CDN like CloudFront is used, it should be configured to use signed URLs or signed cookies to restrict access to the content. This means the CDN itself would also require a signature, generated by the backend, to serve the file. This adds another layer of control, ensuring the CDN only serves content to authorized requests. For simplicity in this answer, we assumed direct pre-signed URLs from S3, but a signed CDN URL would be an enhancement for very high-security needs or if the CDN is directly exposed for downloads without a redirect.

In summary, the backend remains the single point of truth for authorization. It acts as an intermediary, validating every download request before issuing a temporary, secure key (the pre-signed URL) that allows direct access to the file without exposing the backend to the burden of proxying large file transfers.

### Going Further: Trade-offs of Pre-signed URLs vs. Proxying Downloads

Let's compare the two primary approaches for serving attachments from cloud object storage:

#### 1. Pre-signed URLs (Proposed Solution)

**How it works:** The backend authenticates and authorizes the user, then generates a time-limited URL from the object storage service (e.g., S3, GCS) that allows direct download by the client. The client then downloads the file directly from the object storage.

**Advantages:**
*   **Scalability:** The backend service is offloaded from serving large files. The object storage service (and CDN, if used) handles the heavy lifting of data transfer, which is highly scalable and optimized for this task. This prevents the backend from becoming a bottleneck due to network I/O or memory usage for large files.
*   **Performance:** Direct download from object storage or CDN reduces latency for the client, as the data doesn't have to traverse the backend application server.
*   **Cost-effectiveness:** Generally cheaper for large-scale data transfer as object storage egress costs are often lower than running additional application servers to handle proxying.
*   **Simplicity (for backend):** The backend logic is simpler, primarily focused on authorization and URL generation, not file streaming.

**Disadvantages:**
*   **Loss of Real-time Control:** Once a pre-signed URL is issued, the backend loses direct control over that specific download. If a user's permissions are revoked immediately after a URL is issued, the download might still complete if the URL hasn't expired.
*   **Complexity for Analytics/Logging:** Tracking download metrics (e.g., who downloaded what, when, how many times) requires additional setup. You'd typically rely on object storage access logs (e.g., S3 access logs) and process them separately, or implement client-side tracking, which can be less reliable.
*   **Security Nuances:** While secure, it requires careful handling of expiration times and ensuring the pre-signed URL itself doesn't expose sensitive information (e.g., internal bucket names). If the URL is shared, anyone with the URL can download the file until it expires.
*   **CORS Configuration:** If the client-side application is making direct requests to the pre-signed URL from a different origin, Cross-Origin Resource Sharing (CORS) headers might need to be configured on the object storage bucket.

#### 2. Proxying Downloads Through Backend Service

**How it works:** The backend authenticates and authorizes the user, then fetches the file from object storage itself, streams it through its own application server, and sends it to the client.

**Advantages:**
*   **Full Control:** The backend has complete, real-time control over the download process. If a user's permissions are revoked mid-download, the backend can immediately terminate the stream.
*   **Centralized Logging/Analytics:** All download requests pass through the backend, making it easy to log and track every download event directly within the application's existing logging infrastructure.
*   **Custom Processing:** Allows for on-the-fly processing of files (e.g., watermarking, virus scanning, format conversion) before serving them to the client.
*   **Simplified CORS:** No need to configure CORS on the object storage bucket, as all requests go through the application's origin.

**Disadvantages:**
*   **Scalability Bottleneck:** The backend application servers become a bottleneck. Streaming large files consumes significant network I/O, CPU, and memory resources on the application servers, limiting their ability to handle other requests and increasing operational costs.
*   **Performance Degradation:** Increased latency for clients as the data has an extra hop through the application server.
*   **Higher Operational Cost:** Requires more application server instances to handle the same load, leading to higher infrastructure costs.
*   **Increased Complexity (for backend):** The backend needs to handle efficient file streaming, error handling during streaming, and potentially partial downloads (HTTP Range requests).

#### When to Choose Which Approach:

*   **Choose Pre-signed URLs (Recommended for this scenario):**
    *   **High Scale & Performance Critical:** When dealing with millions of attachments and the primary goal is to offload file serving from the backend to improve performance and scalability, as in the given scenario.
    *   **Large Files:** When attachments can be large (up to 50MB), proxying becomes very inefficient and resource-intensive for the backend.
    *   **Cost-Effectiveness:** When minimizing infrastructure costs for file serving is important.
    *   **Acceptable Control Trade-off:** When the slight delay in revoking access (due to URL expiration) is acceptable for the security model.

*   **Choose Proxying Downloads Through Backend:**
    *   **Strict Real-time Access Control:** If immediate revocation of download access is a critical security requirement (e.g., highly sensitive government documents, financial data where every second matters).
    *   **Mandatory On-the-Fly Processing:** If every download requires custom backend processing (e.g., applying dynamic watermarks, real-time virus scanning, encryption/decryption specific to the user).
    *   **Detailed Real-time Analytics:** If very granular, real-time download tracking is essential and cannot be reliably achieved through object storage logs or client-side events.
    *   **Small Scale & Small Files:** For systems with low attachment download volume and very small file sizes where the overhead on the backend is negligible.

**Conclusion for the Scenario:**

For the given scenario with millions of tickets, hundreds of millions of attachments, individual attachments up to 50MB, and a requirement for `GET /api/v1/tickets/{ticket_id}` to return within 500ms, **pre-signed URLs are the clear superior choice.** Proxying downloads would quickly overwhelm the Django application servers, leading to the same or worse performance bottlenecks than the original PostgreSQL `BYTEA` approach, but with higher infrastructure costs. The trade-off of slightly less real-time control is acceptable given the significant gains in scalability, performance, and cost-effectiveness. Security can be adequately managed with short expiration times and robust backend authorization before URL generation.
