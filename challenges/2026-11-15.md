## Scenario

Your team maintains the backend for a B2B SaaS platform that processes millions of customer support tickets daily. A critical feature is the "Ticket Assignment" service, which routes newly created tickets to the appropriate support agent or team. Historically, this was a simple round-robin or least-loaded assignment handled by a single Python/Django application instance.

However, the platform has grown significantly. You now have hundreds of thousands of active agents across thousands of organizations. The assignment logic has become more complex, factoring in agent skills, availability (online/offline, capacity), time zones, and even "priority" tickets that need immediate attention. The current single-instance assignment service is struggling under load, leading to:

1.  **High Latency:** New tickets take several seconds to be assigned, impacting customer experience and SLA adherence.
2.  **Assignment Bottlenecks:** During peak hours, the single service instance becomes a bottleneck, causing a backlog of unassigned tickets.
3.  **Inconsistent Assignments:** Race conditions occasionally lead to multiple agents being assigned the same ticket, or tickets being assigned to agents who are no longer available.

You've decided to re-architect the Ticket Assignment service as a distributed system to handle the increased scale and complexity.

## Requirements

Design and outline a distributed approach for the Ticket Assignment service. The system should reliably assign new tickets to available agents, considering their dynamic state (online/offline, current workload, skills).

Constraints:
*   **High Throughput:** The system must handle bursts of thousands of new tickets per second.
*   **Low Latency:** Assignments should typically complete within 100-200ms.
*   **Consistency:** A ticket must be assigned to *exactly one* available agent, and that agent's workload/availability must be updated atomically with the assignment.
*   **Fault Tolerance:** The system should continue to operate and assign tickets even if individual assignment nodes or state stores fail temporarily.
*   **Scalability:** The solution must be able to scale horizontally to accommodate future growth in tickets and agents.
*   **Dynamic Agent State:** Agent availability and workload change frequently and must be reflected accurately in assignment decisions.

### 1. High-level Architecture Diagram

```
+-------------------+      +---------------------+      +---------------------+
| Ticket Ingestion  |      |  Ticket Assignment  |      |  Agent State Mgmt   |
| (API Gateway, etc.)|      |  Service (Workers)  |      |  Service (Workers)  |
+---------+---------+      +----------+----------+      +----------+----------+
          |                            |                            |
          |  New Ticket                |  Assignment Request        |  Agent Status Update
          v                            v                            v
+---------+---------+      +----------+----------+      +----------+----------+
|  Kafka Topic:     |<----->|  Kafka Topic:     |<----->|  Kafka Topic:     |
|  `new_tickets`    |      |  `assignment_reqs`|      |  `agent_updates`  |
+---------+---------+      +----------+----------+      +----------+----------+
          |                            |                            |
          |  Ticket Data               |  Assigned Ticket           |  Agent State
          v                            v                            v
+---------+---------+      +----------+----------+      +----------+----------+
|  Primary Database |      |  Redis Cluster    |      |  Redis Cluster    |
|  (PostgreSQL)     |      |  (Agent Workloads, |      |  (Agent Availability)|
|                   |      |   Locks)          |      |                   |
+-------------------+      +-------------------+      +-------------------+
          ^                            |
          |  Assignment Result         |
          +----------------------------+
```

**Components:**

*   **Ticket Ingestion:** The entry point for new tickets (e.g., a REST API endpoint, a message from another service). It validates and publishes new tickets to Kafka.
*   **Kafka Topic (`new_tickets`):** A durable, highly scalable message queue for newly created tickets awaiting assignment.
*   **Ticket Assignment Service (Workers):** A horizontally scalable group of stateless workers that consume from `new_tickets`, apply assignment logic, and attempt to assign tickets.
*   **Kafka Topic (`assignment_reqs`):** (Optional, but useful for complex retry/re-evaluation) For assignment workers to publish requests to other workers or for re-evaluation if initial attempts fail.
*   **Agent State Management Service (Workers):** Processes real-time updates about agent availability (online/offline, capacity changes) and publishes them to Kafka.
*   **Kafka Topic (`agent_updates`):** A stream of events reflecting changes in agent status.
*   **Redis Cluster:**
    *   **Agent Availability/Skills Store:** Stores the current, dynamic state of agents (online/offline, skills, current capacity/workload). This is a fast, in-memory store for quick lookups during assignment. Each agent's state is stored under a unique key.
    *   **Distributed Locks:** Used for ensuring atomic updates and preventing race conditions during assignment.
*   **Primary Database (PostgreSQL):** The source of truth for all persistent ticket data, agent profiles (static skills, teams), and the final committed assignment results.

### 2. Data Flow for a New Ticket

Let's trace a new ticket from creation to assignment:

1.  **Ticket Creation & Ingestion:**
    *   A user creates a new support ticket via the platform's frontend.
    *   The request hits the **Ticket Ingestion** service (e.g., a Django API endpoint).
    *   The ingestion service performs initial validation, persists the basic ticket details to the **Primary Database** (e.g., `tickets` table with `status = 'NEW'`, `assigned_agent_id = NULL`), and generates a unique `ticket_id`.
    *   It then publishes a message to the `new_tickets` Kafka topic. The message payload includes `ticket_id`, `organization_id`, `ticket_priority`, `required_skills`, etc.

    ```json
    // Kafka message on `new_tickets` topic
    {
      "event_type": "ticket_created",
      "ticket_id": "TKT-12345",
      "organization_id": "ORG-ABC",
      "priority": "HIGH",
      "required_skills": ["billing", "technical_support"],
      "created_at": "2026-11-15T10:00:00Z"
    }
    ```

2.  **Ticket Assignment Worker Consumption:**
    *   One of the **Ticket Assignment Service Workers** (a consumer group for `new_tickets`) receives the `ticket_created` message.
    *   The worker immediately marks the ticket as "in-progress" in a local cache or a temporary distributed store (e.g., Redis `SET ticket_assignment_in_progress:TKT-12345 1 EX 300`) to prevent other workers from attempting to assign the same ticket concurrently if Kafka's "at-least-once" delivery causes duplicates.

3.  **Agent Search & Selection:**
    *   The worker queries the **Redis Cluster** (Agent Availability/Skills Store) to find suitable agents. The query considers:
        *   `organization_id` (from ticket)
        *   `required_skills` (from ticket)
        *   `online_status` (from Redis: `agent:{id}:status = 'online'`)
        *   `current_workload` (from Redis: `agent:{id}:workload_count`)
        *   `max_capacity` (from Redis: `agent:{id}:max_capacity`)
        *   `time_zone` (from Redis or Primary DB)
    *   The worker applies the complex assignment logic (e.g., weighted least-loaded, skill matching, priority boosts) to select the *best* candidate agent (e.g., `agent_id = AGT-007`).

4.  **Atomic Assignment & Workload Update (Concurrency Control):**
    *   To ensure consistency, the worker attempts to acquire a distributed lock for the *selected agent* and the *ticket*. This is crucial.
    *   Using Redis, this could be a Lua script or a multi-key transaction (`MULTI`/`EXEC` or `WATCH`/`MULTI`/`EXEC`) that performs the following **atomically**:
        *   Checks if `ticket_id` is still unassigned (e.g., `ticket_assignment_status:TKT-12345` is not `assigned`).
        *   Checks if `agent_id` is still available (`agent:{id}:status = 'online'` and `agent:{id}:workload_count < agent:{id}:max_capacity`).
        *   If both are true:
            *   Increments `agent:{id}:workload_count`.
            *   Sets `ticket_assignment_status:TKT-12345` to `assigned` with `agent_id`.
            *   Sets `ticket_assigned_to:TKT-12345` to `AGT-007`.
        *   Releases the locks.
    *   If the atomic operation fails (e.g., another worker assigned the ticket, or the agent became unavailable), the worker retries the process (steps 3-4) or publishes to `assignment_reqs` for re-evaluation.

5.  **Commit to Primary Database:**
    *   Once the atomic assignment in Redis is successful, the worker updates the **Primary Database**.
    *   It sends an `UPDATE` query: `UPDATE tickets SET status = 'ASSIGNED', assigned_agent_id = 'AGT-007', assigned_at = NOW() WHERE ticket_id = 'TKT-12345' AND status = 'NEW';`
    *   The `WHERE status = 'NEW'` clause is a critical optimistic concurrency check. If another worker somehow managed to assign it concurrently (which shouldn't happen with the Redis locks, but as a defense-in-depth), this update would affect 0 rows, and the worker would know its assignment was superseded.

6.  **Post-Assignment Actions:**
    *   The worker publishes an `assignment_completed` event to a Kafka topic (e.g., `ticket_events`) for other services (e.g., notifications, analytics).
    *   The worker cleans up any temporary state (e.g., `ticket_assignment_in_progress:TKT-12345`).

### 3. Concurrency Control Strategy

The core of concurrency control lies in ensuring that:
1.  A ticket is assigned to *exactly one* agent.
2.  An agent's workload/availability is updated *atomically* with the assignment.

Our strategy combines several layers:

*   **Kafka Consumer Group Semantics:** By using a Kafka consumer group for `new_tickets`, each message is delivered to *exactly one* consumer within the group. This largely prevents multiple workers from simultaneously picking up the *same* ticket message initially. However, Kafka's "at-least-once" delivery can lead to duplicate messages in failure scenarios, so further mechanisms are needed.

*   **Idempotency Key / In-Progress Flag:** When a worker picks up a `ticket_created` message, it first checks a short-lived, distributed "in-progress" flag in Redis (e.g., `SETNX ticket_assignment_in_progress:TKT-12345 1 EX 300`). If `SETNX` returns 0, another worker is already processing this ticket, and the current worker can back off or retry later. This handles duplicate Kafka messages.

*   **Distributed Locks (Redis SETNX or Redlock):** This is the most critical component for atomic assignment.
    *   When an assignment worker has identified a candidate agent (`AGT-007`) for a ticket (`TKT-12345`), it attempts to acquire a lock for *both* the ticket and the agent.
    *   A simple approach uses `SETNX` for each resource:
        ```
        LOCK_TICKET_KEY = "lock:ticket:TKT-12345"
        LOCK_AGENT_KEY = "lock:agent:AGT-007"

        # Try to acquire ticket lock
        result_ticket_lock = REDIS.set(LOCK_TICKET_KEY, WORKER_ID, nx=True, ex=10)
        if not result_ticket_lock:
            # Ticket already locked by another worker, retry or abort
            return

        # Try to acquire agent lock
        result_agent_lock = REDIS.set(LOCK_AGENT_KEY, WORKER_ID, nx=True, ex=10)
        if not result_agent_lock:
            # Agent already locked, release ticket lock and retry
            REDIS.delete(LOCK_TICKET_KEY)
            return
        ```
    *   **Better: Atomic Multi-Key Update with Lua Script:** To avoid deadlocks and ensure atomicity across multiple keys (ticket status and agent workload), a Redis Lua script is superior. This script runs on the Redis server, ensuring the operations are atomic from the client's perspective.

    ```lua
    -- Lua script for atomic assignment
    -- KEYS[1]: ticket_assignment_status:TKT-12345
    -- KEYS[2]: agent:AGT-007:workload_count
    -- KEYS[3]: agent:AGT-007:status
    -- KEYS[4]: agent:AGT-007:max_capacity
    -- ARGV[1]: assigned_agent_id (e.g., AGT-007)
    -- ARGV[2]: current_timestamp

    local ticket_status = redis.call('GET', KEYS[1])
    local agent_workload = tonumber(redis.call('GET', KEYS[2]))
    local agent_status = redis.call('GET', KEYS[3])
    local agent_max_capacity = tonumber(redis.call('GET', KEYS[4]))

    -- Check if ticket is unassigned and agent is online and has capacity
    if ticket_status == nil and agent_status == 'online' and agent_workload < agent_max_capacity then
        redis.call('SET', KEYS[1], ARGV[1]) -- Mark ticket as assigned to this agent
        redis.call('INCR', KEYS[2])         -- Increment agent's workload
        redis.call('SET', 'ticket_assigned_to:' .. string.sub(KEYS[1], 25), ARGV[1]) -- Store agent_id for ticket
        return 1 -- Success
    else
        return 0 -- Failed (ticket already assigned, or agent unavailable/full)
    end
    ```
    This script would be executed with `EVAL` on the Redis cluster. If it returns 1, the assignment is successful in Redis. If 0, the worker knows it failed and can retry or pick another agent.

*   **Optimistic Concurrency in Primary Database:** As a final safeguard, the `UPDATE` query to PostgreSQL includes a `WHERE status = 'NEW'` clause. If the ticket's status is no longer `NEW` (meaning another worker successfully assigned it and committed to the DB), the update will affect 0 rows, signaling a conflict.

**Trade-offs:**
*   **Complexity:** Using distributed locks and Lua scripts adds complexity compared to a single-threaded approach.
*   **Performance vs. Consistency:** The Redis Lua script provides strong consistency for the assignment decision itself. However, it requires a round trip to Redis and serializes access to agent/ticket state, which can be a bottleneck if *many* workers contend for the *same few* agents. Our system assumes a large pool of agents, mitigating this.
*   **Redis as a critical path:** Redis becomes a single point of failure for assignment logic if not properly clustered and replicated.

### 4. Failure Handling (Agent State)

Consider the scenario: An assignment worker (Worker A) successfully executes the Redis Lua script, assigning `TKT-12345` to `AGT-007` and incrementing `AGT-007`'s workload. However, Worker A crashes *before* it can update the Primary Database or publish the `assignment_completed` event.

This leads to an inconsistent state:
*   **Redis:** `TKT-12345` is marked as assigned to `AGT-007`, and `AGT-007`'s workload is incremented.
*   **Primary Database:** `TKT-12345` is still `status = 'NEW'`, `assigned_agent_id = NULL`.
*   **Agent:** `AGT-007`'s actual workload is less than what Redis indicates.

Here's how the system would handle this:

1.  **Idempotent Database Update & Retries:**
    *   The Kafka consumer for `new_tickets` (Worker A) is configured for retries. If Worker A crashes, Kafka will eventually re-deliver the `ticket_created` message to another worker (Worker B) in the same consumer group, or to Worker A if it restarts.
    *   When Worker B (or a restarted Worker A) picks up `TKT-12345` again, it will attempt the assignment process.
    *   During the "Atomic Assignment & Workload Update" step (the Lua script), the script will find that `ticket_assignment_status:TKT-12345` already exists and is set to `AGT-007`. The Lua script will return `0` (failure), indicating the ticket is already assigned.
    *   Worker B then proceeds to the "Commit to Primary Database" step. It will attempt the `UPDATE tickets SET status = 'ASSIGNED', assigned_agent_id = 'AGT-007', assigned_at = NOW() WHERE ticket_id = 'TKT-12345' AND status = 'NEW';`.
    *   This `UPDATE` query will succeed because the `WHERE status = 'NEW'` clause is still true. The database will now reflect the assignment.
    *   Worker B then publishes the `assignment_completed` event.

2.  **Reconciliation/Idempotency for Agent Workload:**
    *   The critical part is that the Redis workload increment (`INCR`) happened. If the database update failed, the agent's workload in Redis is inflated.
    *   **Solution 1: Periodic Reconciliation:** A background job periodically scans tickets in the Primary Database that are `status = 'ASSIGNED'` and compares the `assigned_agent_id` with the current workload counts in Redis. If discrepancies are found (e.g., an agent's Redis workload is higher than the count of tickets assigned to them in the DB that are still `status = 'ASSIGNED'`), the Redis workload can be corrected downwards. This is eventually consistent.
    *   **Solution 2: Agent Workload as a Derived State:** Instead of `INCR`/`DECR` on a counter, the agent's workload in Redis could be derived from a `SET` of currently assigned `ticket_id`s.
        *   When assigning: `SADD agent:{id}:assigned_tickets TKT-12345`.
        *   Workload is `SCARD agent:{id}:assigned_tickets`.
        *   When a ticket is resolved/unassigned: `SREM agent:{id}:assigned_tickets TKT-12345`.
        *   The Lua script would then check `SCARD` and `SADD`. This makes reconciliation simpler: if a ticket is assigned in Redis but not in the DB, it can be removed from the set. This is more robust against partial failures.

    Let's refine the Lua script for Solution 2:

    ```lua
    -- Lua script for atomic assignment with Set-based workload
    -- KEYS[1]: ticket_assignment_status:TKT-12345
    -- KEYS[2]: agent:AGT-007:assigned_tickets (SET)
    -- KEYS[3]: agent:AGT-007:status
    -- KEYS[4]: agent:AGT-007:max_capacity
    -- ARGV[1]: assigned_agent_id (e.g., AGT-007)
    -- ARGV[2]: current_timestamp

    local ticket_status = redis.call('GET', KEYS[1])
    local agent_current_workload = redis.call('SCARD', KEYS[2]) -- Get count from set
    local agent_status = redis.call('GET', KEYS[3])
    local agent_max_capacity = tonumber(redis.call('GET', KEYS[4]))

    -- Check if ticket is unassigned and agent is online and has capacity
    if ticket_status == nil and agent_status == 'online' and agent_current_workload < agent_max_capacity then
        redis.call('SET', KEYS[1], ARGV[1])         -- Mark ticket as assigned to this agent
        redis.call('SADD', KEYS[2], ARGV[1])        -- Add ticket to agent's assigned set
        redis.call('SET', 'ticket_assigned_to:' .. string.sub(KEYS[1], 25), ARGV[1]) -- Store agent_id for ticket
        return 1 -- Success
    else
        return 0 -- Failed
    end
    ```

    With this, if Worker A crashes after the Redis script but before DB update, the `SADD` operation is done. When Worker B picks up the ticket, it finds `ticket_assignment_status` already set. It then proceeds to update the DB. If the DB update fails, the ticket is still in `agent:{id}:assigned_tickets`. The periodic reconciliation job would then find `TKT-12345` in `agent:{id}:assigned_tickets` but not in the DB as `ASSIGNED`, and it can `SREM` it from Redis.

**Key Takeaways:**
*   **Idempotency:** All operations that modify state must be idempotent or protected by idempotent checks.
*   **Optimistic Concurrency:** Use `WHERE` clauses in database updates to ensure you're modifying the state you expect.
*   **Reconciliation:** For distributed systems, eventual consistency and periodic reconciliation jobs are often necessary to clean up inconsistencies arising from partial failures.
*   **Derived State:** Storing workload as a derived set of assigned tickets in Redis makes reconciliation simpler and more robust than a simple counter.

### Going further

**Scenario:** An agent unexpectedly goes offline *after* being assigned a ticket but *before* they have a chance to accept it. How would your system detect this and re-assign the ticket without human intervention, ensuring the original agent doesn't also see it later if they come back online?

This requires a mechanism to track the "acceptance" state of an assignment and react to agent status changes.

1.  **Assignment State Tracking:**
    *   Introduce a new state for tickets: `ASSIGNED_PENDING_ACCEPTANCE`.
    *   When an assignment worker successfully assigns a ticket to an agent, it updates the Primary Database to `status = 'ASSIGNED_PENDING_ACCEPTANCE'` and sets `assigned_agent_id`.
    *   It also publishes an `assignment_pending_acceptance` event to a Kafka topic (e.g., `ticket_events`).

2.  **Agent Acceptance Mechanism:**
    *   The agent's client application (e.g., web UI, desktop app) receives notifications for `assignment_pending_acceptance` events.
    *   When the agent *explicitly accepts* the ticket, their client sends an `accept_ticket` API call to the backend.
    *   The backend validates the acceptance and updates the Primary Database: `UPDATE tickets SET status = 'ASSIGNED', accepted_at = NOW() WHERE ticket_id = 'TKT-12345' AND assigned_agent_id = 'AGT-007' AND status = 'ASSIGNED_PENDING_ACCEPTANCE';`.
    *   It also publishes an `assignment_accepted` event.

3.  **Agent Offline Detection & Re-assignment:**
    *   **Agent State Management Service:** This service continuously monitors agent presence (e.g., heartbeats from agent clients, WebSocket connections). When an agent goes offline, it publishes an `agent_offline` event to the `agent_updates` Kafka topic.
    *   **Re-assignment Worker:** A dedicated consumer group for `agent_updates` (or a separate worker that subscribes to both `agent_updates` and `ticket_events`) monitors these events.
    *   When an `agent_offline` event for `AGT-007` is received:
        *   The re-assignment worker queries the Primary Database for all tickets currently in `status = 'ASSIGNED_PENDING_ACCEPTANCE'` and `assigned_agent_id = 'AGT-007'`.
        *   For each such ticket (`TKT-12345`):
            *   It attempts to acquire a distributed lock for `TKT-12345` (to prevent multiple re-assignment workers from acting on it).
            *   It updates the Primary Database: `UPDATE tickets SET status = 'REASSIGN_REQUIRED', assigned_agent_id = NULL, assigned_at = NULL WHERE ticket_id = 'TKT-12345' AND status = 'ASSIGNED_PENDING_ACCEPTANCE';`
            *   It publishes a `ticket_reassign_required` event to the `new_tickets` Kafka topic (or a dedicated `reassign_tickets` topic). This effectively puts the ticket back into the assignment queue.
            *   It also needs to decrement the agent's workload in Redis (if using the counter method) or remove the ticket from the agent's assigned set (if using the set method). This should be part of the atomic update when changing the ticket status.

4.  **Preventing Original Agent from Seeing Re-assigned Ticket:**
    *   **Client-side Filtering:** The agent's client application should only display tickets that are `ASSIGNED` (accepted) or `ASSIGNED_PENDING_ACCEPTANCE` *and* whose `assigned_agent_id` matches the current agent. If a ticket's status changes to `REASSIGN_REQUIRED` or is assigned to a *different* agent, the client should automatically remove it from the original agent's view.
    *   **Backend Authorization:** Any API call from an agent to view or interact with a ticket must include an authorization check that verifies `assigned_agent_id` matches the requesting agent and the `status` is appropriate (e.g., not `REASSIGN_REQUIRED`).
    *   **Event-driven UI Updates:** The `ticket_reassign_required` event (or `assignment_completed` for the new agent) can be pushed to agent clients via WebSockets to immediately update their UI, removing the re-assigned ticket from the original agent's queue.

**Refined Redis State for Agent Workload (Set-based):**

When an agent goes offline, the re-assignment worker would perform an atomic operation in Redis:

```lua
-- Lua script to remove ticket from agent's assigned set during re-assignment
-- KEYS[1]: agent:AGT-007:assigned_tickets (SET)
-- ARGV[1]: TKT-12345

redis.call('SREM', KEYS[1], ARGV[1])
return 1
```

This ensures that the agent's workload count in Redis is immediately corrected, and the agent's capacity is freed up for new assignments once they come back online. The original agent's client, upon receiving the `ticket_reassign_required` event, would remove the ticket from their UI. If the agent comes back online, their client will re-sync and only show tickets that are currently assigned to them and not in a re-assignment state.
