## Scenario

Your team manages the backend service for a popular online forum. A key feature is the "trending posts" section on the homepage, which displays posts that have received significant engagement (likes, comments) recently. The `posts` table has grown to over 50 million rows, and the `post_interactions` table (recording likes, comments, etc.) has hundreds of millions of rows.

The current "trending posts" query calculates a score for each post based on the sum of interactions within the last 24 hours, ordered by this score, and limited to the top 20. This query runs every 5 minutes and is intended to complete within 500ms to keep the homepage snappy. Recently, this query has started taking 3-5 seconds to execute, sometimes spiking higher, leading to a noticeable delay in loading the trending section. This directly impacts user experience and engagement.

Constraints:
- The `posts` table has `id` (PK), `title`, `content`, `created_at`, `user_id`.
- The `post_interactions` table has `id` (PK), `post_id` (FK to `posts`), `user_id`, `interaction_type` (e.g., 'like', 'comment'), `created_at`.
- The interaction data is highly write-heavy, with thousands of new interactions per second during peak times.
- The system must remain highly available during any schema changes or optimizations.
- The trending algorithm is subject to change, so any solution should ideally not be overly rigid.

## Requirements

Optimize the PostgreSQL database to ensure the "trending posts" query consistently runs within the 500ms latency budget, given the scale and write-heavy nature of the `post_interactions` table. You should focus on improving the performance of the aggregation and ordering steps involved in calculating trending scores.

## Worked answer

### 1. SQL Script for Indexes and Materialized View

Given the write-heavy nature of `post_interactions` and the need for fast, repetitive reads for trending posts, a materialized view is the most suitable approach. It pre-calculates the trending scores, allowing the read query to be extremely fast. To support efficient refreshes of the materialized view, we'll need an index on `post_interactions`.

```sql
-- Index on post_interactions for efficient filtering by created_at and aggregation
CREATE INDEX IF NOT EXISTS ix_post_interactions_created_at_post_id
ON post_interactions (created_at DESC, post_id);

-- Materialized view to pre-calculate trending scores
-- This view will store the sum of interactions for each post within the last 24 hours.
CREATE MATERIALIZED VIEW IF NOT EXISTS mv_trending_posts AS
SELECT
    p.id AS post_id,
    p.title,
    p.created_at AS post_created_at,
    COUNT(pi.id) AS interaction_count,
    NOW() AS calculated_at -- Timestamp when this score was calculated
FROM
    posts p
JOIN
    post_interactions pi ON p.id = pi.post_id
WHERE
    pi.created_at >= NOW() - INTERVAL '24 hours'
GROUP BY
    p.id, p.title, p.created_at
ORDER BY
    interaction_count DESC
WITH NO DATA; -- Create empty, we'll refresh it immediately

-- Create an index on the materialized view for fast ordering and lookup
CREATE UNIQUE INDEX IF NOT EXISTS ix_mv_trending_posts_post_id ON mv_trending_posts (post_id);
CREATE INDEX IF NOT EXISTS ix_mv_trending_posts_interaction_count ON mv_trending_posts (interaction_count DESC);

-- Initial refresh of the materialized view
REFRESH MATERIALIZED VIEW mv_trending_posts;
```

**Explanation:**

1.  **`ix_post_interactions_created_at_post_id`**: This index is crucial for the materialized view's refresh process.
    *   `created_at DESC`: Allows for efficient filtering of recent interactions (`pi.created_at >= NOW() - INTERVAL '24 hours'`). The `DESC` order can sometimes help with range scans where the most recent data is accessed first, though for this specific `WHERE` clause, a simple `(created_at, post_id)` would also work well.
    *   `post_id`: Included as a second column to support the `GROUP BY` clause efficiently, as the data for each `post_id` will be clustered together after filtering by `created_at`. This is a "covering index" for the `WHERE` and `GROUP BY` parts of the materialized view definition.

2.  **`mv_trending_posts`**: This materialized view pre-computes the `interaction_count` for each post within the last 24 hours.
    *   It joins `posts` and `post_interactions` and filters `post_interactions` by `created_at`.
    *   `COUNT(pi.id)` gives us the trending score.
    *   `NOW() AS calculated_at` is included to show when the data was last refreshed, which can be useful for debugging or monitoring staleness.
    *   `WITH NO DATA` is used to create the view definition quickly, then `REFRESH` is called separately. This is good practice for large views.

3.  **Indexes on `mv_trending_posts`**:
    *   `ix_mv_trending_posts_post_id`: A unique index on `post_id` allows for fast lookups if we ever need to fetch a specific post's trending score.
    *   `ix_mv_trending_posts_interaction_count`: This index is critical for the final "top 20" query, enabling very fast `ORDER BY interaction_count DESC LIMIT 20` operations directly on the pre-sorted data.

### 2. Optimized SQL Query

The optimized query simply selects from the materialized view, which already contains the pre-calculated and ordered trending scores.

```sql
SELECT
    post_id,
    title,
    interaction_count
FROM
    mv_trending_posts
ORDER BY
    interaction_count DESC
LIMIT 20;
```

**Explanation:**

This query is extremely fast because it avoids any joins, aggregations, or complex filtering at read time. All the heavy lifting is done during the materialized view refresh. It simply reads the top 20 rows from a pre-indexed table.

### Going Further

#### Trade-offs Involved

**1. Write Performance (for `post_interactions`):**
*   **Impact:** Minimal direct impact on `INSERT`s into `post_interactions`. The `ix_post_interactions_created_at_post_id` index will add a slight overhead to each `INSERT` (writing to the index in addition to the table), but this is generally acceptable for a single index on a write-heavy table.
*   **Refresh Impact:** The main write-related trade-off is the cost of *refreshing* the materialized view. `REFRESH MATERIALIZED VIEW` is a blocking operation by default (it locks the view, preventing reads, until it completes). For a view based on 500 million rows, this refresh can take seconds to minutes, depending on the data churn and server resources.
    *   **Mitigation:** PostgreSQL 9.4+ introduced `REFRESH MATERIALIZED VIEW CONCURRENTLY`. This allows the refresh to happen without blocking reads, but it requires a `UNIQUE` index on the materialized view (which we've added: `ix_mv_trending_posts_post_id`). `CONCURRENTLY` refreshes are slower than non-concurrent ones because they involve two passes over the data and more complex locking, but they ensure high availability.
    *   **Further Mitigation:** For extremely high refresh frequency or very large datasets where even `CONCURRENTLY` is too slow, one might consider a "double-buffering" strategy (creating a new view, populating it, then swapping names) or incremental refresh techniques (e.g., using triggers or external tools to update the view only for new data). However, for a 5-minute refresh of a 24-hour window, `REFRESH MATERIALIZED VIEW CONCURRENTLY` is usually sufficient.

**2. Storage Overhead:**
*   **Impact:** The materialized view `mv_trending_posts` itself consumes storage space. It stores the `post_id`, `title`, `post_created_at`, and `interaction_count` for all posts that had interactions in the last 24 hours. The indexes on the materialized view (`ix_mv_trending_posts_post_id`, `ix_mv_trending_posts_interaction_count`) also consume space.
*   **Estimation:** If, say, 10 million posts have interactions in a 24-hour window, the materialized view would have 10 million rows. Each row is relatively small (a few integers/bigints and a varchar). The indexes would add further overhead. This is a reasonable amount of storage (likely tens of GBs) compared to the original tables, but it's an additional cost.
*   **Trade-off:** We are trading disk space for read performance. Given the critical nature of the trending posts feature, this is a worthwhile trade-off.

**3. Refresh Strategy for Derived Data:**
*   **Strategy:** The materialized view needs to be refreshed periodically. The scenario states the query runs every 5 minutes, implying the trending data can be up to 5 minutes stale. Therefore, a `REFRESH MATERIALIZED VIEW CONCURRENTLY` run every 5 minutes (or slightly more frequently, e.g., every 3 minutes, to ensure it completes before the next cycle) via a cron job or an external scheduler is appropriate.
*   **Staleness:** The data in the materialized view is only as fresh as its last refresh. If the refresh takes 3 minutes, and it runs every 5 minutes, the data could be up to 8 minutes old (5 minutes until refresh starts + 3 minutes for refresh to complete). This staleness is an inherent trade-off of materialized views. For "trending" data, a few minutes of staleness is usually acceptable.
*   **Resource Consumption during Refresh:** The refresh operation will consume CPU, memory, and I/O resources on the database server. This is the "cost" of pre-calculating the data. It's important to monitor the refresh duration and resource usage to ensure it doesn't negatively impact other database operations, especially during peak write times.

#### Adaptability to Changing Trending Definitions

**1. Rolling 7-day Window Instead of 24 Hours:**
*   **Adaptation:** This change is straightforward. We would simply modify the `WHERE` clause in the materialized view definition:
    ```sql
    -- Original:
    -- WHERE pi.created_at >= NOW() - INTERVAL '24 hours'
    -- New:
    WHERE pi.created_at >= NOW() - INTERVAL '7 days'
    ```
*   **Impact:**
    *   **Refresh Time:** The refresh would likely take longer because it needs to process a larger volume of `post_interactions` data (7 days' worth instead of 24 hours'). The `ix_post_interactions_created_at_post_id` index would still be highly effective, but the scan range is wider.
    *   **Storage:** The `mv_trending_posts` materialized view would likely contain more rows (more posts would have interactions over a 7-day period), leading to increased storage consumption for the view and its indexes.
    *   **Read Performance:** The read performance of the `SELECT ... LIMIT 20` query would remain unaffected, as it still just reads from the pre-computed materialized view.

**2. Different Interaction Types Weighted Differently:**
*   **Adaptation:** This would require modifying the `COUNT(pi.id)` aggregation in the materialized view to a `SUM` of weighted scores.
    ```sql
    -- Example: Likes = 1 point, Comments = 2 points, Shares = 3 points
    CREATE MATERIALIZED VIEW IF NOT EXISTS mv_trending_posts AS
    SELECT
        p.id AS post_id,
        p.title,
        p.created_at AS post_created_at,
        SUM(CASE pi.interaction_type
                WHEN 'like' THEN 1
                WHEN 'comment' THEN 2
                WHEN 'share' THEN 3
                ELSE 0 -- Handle unknown types gracefully
            END) AS weighted_interaction_score, -- Renamed for clarity
        NOW() AS calculated_at
    FROM
        posts p
    JOIN
        post_interactions pi ON p.id = pi.post_id
    WHERE
        pi.created_at >= NOW() - INTERVAL '24 hours' -- Or 7 days
    GROUP BY
        p.id, p.title, p.created_at
    ORDER BY
        weighted_interaction_score DESC
    WITH NO DATA;

    -- The index on the score column would need to be updated:
    -- DROP INDEX IF EXISTS ix_mv_trending_posts_interaction_count;
    -- CREATE INDEX IF NOT EXISTS ix_mv_trending_posts_weighted_interaction_score ON mv_trending_posts (weighted_interaction_score DESC);
    ```
*   **Impact:**
    *   **Refresh Time:** The refresh time might slightly increase due to the `CASE` statement within the `SUM` aggregation, but this is usually a minor overhead compared to the I/O of reading the base data.
    *   **Storage:** No significant change in storage, as we're still storing one score per post.
    *   **Read Performance:** The read performance of the `SELECT ... LIMIT 20` query would remain unaffected, as it still reads from the pre-computed materialized view, just ordering by a different (but still indexed) score column.
    *   **Index Change:** The index on the score column of the materialized view would need to be recreated to reflect the new column name and ensure it's still ordered correctly.

The materialized view approach is quite flexible for changes to the trending algorithm's definition, as long as the changes can be expressed within the view's SQL definition. The primary impact will be on the refresh duration and storage, not on the read latency of the trending section itself.

#### Why other plausible approaches are wrong or less optimal:

*   **Adding more indexes to `post_interactions` for the original query:**
    *   An index like `(created_at DESC, post_id)` or `(post_id, created_at DESC)` would certainly help the original query by speeding up the `WHERE` clause and potentially the `GROUP BY`.
    *   However, for 500 million `post_interactions` rows, even with an index, scanning and aggregating 24 hours of data (which could be tens of millions of rows during peak times) and then sorting the results for potentially millions of distinct posts would still be a very expensive operation. The `GROUP BY` and final `ORDER BY` would likely still push it over the 500ms budget, especially as the number of active posts grows.
    *   The overhead of maintaining such an index on a highly write-heavy table is also a concern, as every insert would need to update the index.
    *   The fundamental problem is that the original query performs a full aggregation on a large, volatile dataset on every request, which is inherently slow for high-volume reads.

*   **Using a regular view:**
    *   A regular view simply stores the query definition; it does not store the results. Every time the view is queried, the underlying complex query (joins, filters, aggregations) would be executed from scratch. This would offer no performance improvement over the original query.

*   **Caching the query results in application layer (e.g., Redis):**
    *   While caching is a good complementary strategy, it doesn't solve the root database performance issue. The first request after cache expiry (or a cache miss) would still hit the slow database query.
    *   It also adds complexity to the application layer (cache invalidation, consistency models).
    *   A materialized view effectively acts as a server-side cache that is managed by the database itself, providing better consistency guarantees and offloading the computation.

*   **Partitioning `post_interactions` by `created_at`:**
    *   Partitioning by `created_at` could significantly speed up the `WHERE pi.created_at >= NOW() - INTERVAL '24 hours'` clause by allowing the query to only scan relevant partitions. This is a good general optimization for time-series data.
    *   However, even with partitioning, the aggregation (`GROUP BY post_id`) across potentially millions of rows within the relevant partitions would still be a bottleneck for a synchronous read query.
    *   Partitioning is a good strategy to combine with a materialized view, as it would make the `REFRESH` operation faster by reducing the amount of data scanned for the base query of the materialized view. It's an orthogonal improvement that could further enhance the solution, but the materialized view is the primary driver for fast *read* performance.
