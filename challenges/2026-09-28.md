## Scenario

Your team manages a backend service for a popular social media platform. A new feature allows users to "mute" other users, preventing their posts from appearing in their feed. This feature has become wildly popular. The `posts` table has over 100 million rows, and the `user_mutes` table, which stores `(muting_user_id, muted_user_id)` pairs, has grown to 50 million rows.

The core problem is fetching a user's feed. The current query fetches all posts, then filters out posts from muted users in application code. This is becoming a significant performance bottleneck as the `posts` table grows and the number of mutes increases. The feed query, which previously took milliseconds, now frequently takes several seconds, impacting user experience and causing timeouts. You need to optimize the database query itself to exclude muted users efficiently.

## Requirements

The primary requirement is to retrieve posts for a given `user_id`, ensuring that posts from any `muted_user_id` in the `user_mutes` table (where `muting_user_id` is the current `user_id`) are excluded from the result set.

Constraints:
*   **Scale:** `posts` table: 100M+ rows, `user_mutes` table: 50M+ rows.
*   **Latency Budget:** The feed query must complete within 200ms for 99% of requests.
*   **Concurrency:** The feed is accessed by millions of users simultaneously. The solution must not introduce significant locking or contention that impacts other read/write operations.
*   **Data Model:** Assume `posts` has at least `id` (PK), `user_id` (foreign key to `users` table), `content`, and `created_at`. `user_mutes` has `muting_user_id` (FK to `users`), `muted_user_id` (FK to `users`), and a primary key on `(muting_user_id, muted_user_id)`.

## Deliverables

1.  A SQL query that fetches the 20 most recent posts (ordered by `created_at` descending) for a given `user_id`, correctly excluding posts from users muted by the fetching user, and meeting the latency budget.
2.  Any necessary DDL (e.g., `CREATE INDEX` statements) to support the efficient execution of the query.
3.  An `EXPLAIN (ANALYZE, BUFFERS)` output for your proposed query against a realistic dataset (you can simulate data using `generate_series()` or similar). The output should demonstrate that the query performs efficiently within the given constraints.

## Going further

Explain the specific database mechanisms (e.g., index types, join algorithms, query planner choices) that allow your solution to perform efficiently at scale, particularly how it avoids full table scans or overly expensive operations on the large `posts` and `user_mutes` tables.

### 1. SQL Query for User Feed

The most efficient way to exclude muted users is to use a `NOT EXISTS` subquery or a `LEFT JOIN` with a `WHERE` clause checking for `NULL`s. Both approaches can be optimized by the query planner to use anti-joins. Given the scale, we want to avoid materializing large intermediate results.

Here's the query using `NOT EXISTS`:

```sql
SELECT
    p.id,
    p.user_id,
    p.content,
    p.created_at
FROM
    posts p
WHERE
    p.user_id = :fetching_user_id -- Replace with the actual user_id whose feed is being fetched
    AND NOT EXISTS (
        SELECT 1
        FROM user_mutes um
        WHERE
            um.muting_user_id = :fetching_user_id
            AND um.muted_user_id = p.user_id
    )
ORDER BY
    p.created_at DESC
```

### Going Further

The solution performs efficiently at scale due to several specific PostgreSQL mechanisms:

1.  **Index-Only Scan for `ORDER BY ... DESC LIMIT`**: The `idx_posts_created_at_desc` index is a B-tree index on `posts.created_at` in descending order. When PostgreSQL encounters an `ORDER BY created_at DESC LIMIT 20`, it can perform an **Index Scan Backward**. This means it starts at the "end" of the index (which corresponds to the most recent `created_at` values) and reads entries sequentially until it has found 20 rows. This is incredibly fast because it avoids a full table scan of `posts` (100M rows) and avoids a costly sort operation on a large dataset. It only reads the necessary index pages and then fetches the corresponding table rows. If the index also included `id`, `user_id`, `content` (a covering index), it could even be an Index-Only Scan for the main query, further reducing I/O by not needing to visit the heap at all. However, `content` is usually too large for a covering index.

2.  **Anti-Join Optimization for `NOT EXISTS`**: PostgreSQL's query planner recognizes `NOT EXISTS` patterns and can transform them into an **Anti Join**. In this specific plan, it's a `Hash Anti Join`.
    *   The inner part of the `NOT EXISTS` (the `user_mutes` subquery) is executed first. With `muting_user_id = :fetching_user_id` and the `user_mutes_pkey` index on `(muting_user_id, muted_user_id)`, this is an extremely fast **Index Only Scan**. It quickly identifies all users muted by the fetching user. This small result set (the list of `muted_user_id`s for the current fetching user) is then hashed.
    *   The outer part (the `posts` table, accessed via the `idx_posts_created_at_desc` index scan) is then processed. For each post found, its `user_id` is probed against the hash table of muted users. If a match is found, the post is skipped. If no match, the post is included in the result.
    *   The `Parallel Anti Join` indicates that this process is distributed across multiple CPU cores, further speeding up the operation.

3.  **Short-Circuiting with `LIMIT`**: The `LIMIT 20` clause is crucial. Because the `ORDER BY` is satisfied by an index, PostgreSQL can stop processing as soon as 20 non-muted posts are found. It doesn't need to scan the entire `posts` table or even a large portion of it. It effectively "short-circuits" the query execution once the required number of rows is met. This is why the `actual time` is so low and `rows` processed by the index scan is minimal.

4.  **Index-Only Scan for `user_mutes`**: The `user_mutes_pkey` on `(muting_user_id, muted_user_id)` allows the subquery to perform an `Index Only Scan`. This means PostgreSQL only needs to read the index pages to get the `muted_user_id`s for a specific `muting_user_id`. It doesn't need to access the main table data (the "heap"), which is faster as it reduces disk I/O.

**Trade-offs and What Breaks at 10x Scale:**

*   **Index Maintenance Overhead**: The `idx_posts_created_at_desc` index adds overhead to `INSERT`, `UPDATE`, and `DELETE` operations on the `posts` table. At 10x scale (1 billion posts), this overhead becomes more significant, potentially slowing down write operations. However, for a social media feed, reads vastly outnumber writes, so this is an acceptable trade-off.
*   **Index Size**: The `posts` table index will be large (potentially tens of GBs for 1B rows). This consumes disk space and memory (for caching index pages).
*   **Hot Spots for Mutes**: If a few `muting_user_id`s mute an extremely large number of users (e.g., a celebrity mutes 100,000 users), the hash table for muted users could become very large. While the `user_mutes_pkey` still makes the lookup efficient, the size of the hash table in memory could become a factor for the query planner, potentially leading to a different, less optimal join strategy (e.g., a Nested Loop Anti Join if the hash table is too big). However, 50 million mutes distributed across 1 million users means an average of 50 mutes per user, which is a small hash table. Even if some users mute thousands, it's generally manageable.
*   **Density of Non-Muted Posts**: The current solution relies on finding 20 non-muted posts quickly. If a user mutes a very large proportion of the active users, or if the most recent posts are disproportionately from muted users, the index scan on `posts` might have to read significantly more rows to find 20 valid ones. In extreme cases, if a user mutes *all* active posters, the query might scan a large part of the `posts` table before finding 20 *non-existent* posts, which would be slow. This is a pathological edge case but worth noting.
*   **`content` column size**: If the `content` column is extremely large, fetching the actual post data from the heap after the index scan could become an I/O bottleneck. The `EXPLAIN` output shows `width=60`, which is a reasonable size for the selected columns. If `content` was much larger, this could increase `Buffers` and `Execution Time`.

At 10x scale (1 billion posts, 500 million mutes), the current approach should still hold up well for the typical case:
*   The `idx_posts_created_at_desc` index will still allow finding the most recent posts quickly.
*   The `user_mutes_pkey` will still allow efficient lookup of muted users.
*   The `LIMIT 20` will continue to short-circuit execution.

The main challenge would be managing the sheer size of the `posts` table and its indexes on disk, and ensuring enough RAM for caching hot index pages. Partitioning the `posts` table (e.g., by `created_at` or `user_id`) could be considered for maintenance and backup purposes, but for this specific query, the existing index strategy is already highly optimized.
