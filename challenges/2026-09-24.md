*Thursday. Question and worked answer, both generated.*

---

Your team maintains a critical backend service for a fast-growing online collaboration platform. Users frequently upload various types of files (documents, images, videos) to shared workspaces. These files need to be accessible and downloadable by other users in the workspace. The platform currently handles about 5 million file uploads daily, with an average file size of 2MB, but can range from a few kilobytes to several gigabytes. Storage costs are becoming a concern, and download latency for large files is occasionally reported as high.

## Requirements

Design a system to efficiently store, retrieve, and serve user-uploaded files, considering the following constraints:

-   **High throughput:** Support 5 million uploads and a much higher number of downloads daily.
-   **Low latency:** Target average download latency under 200ms for files under 10MB, and acceptable streaming performance for larger files.
-   **Cost-effectiveness:** Minimize storage and transfer costs.
-   **Durability and availability:** Files must be highly durable and available, as data loss or unavailability directly impacts user productivity.
-   **Security:** Ensure that only authorized users can access files. Assume a separate authentication/authorization service exists.
-   **Scalability:** The system should scale to handle 10x growth in file uploads and downloads over the next two years.

## Deliverables

1.  A high-level architectural diagram (text-based or conceptual) showing the main components involved in the file upload and download process.
2.  A brief description of the technologies you would choose for each major component and *why* (e.g., storage, CDN, processing queue).
3.  Outline the request flow for both a file upload and a file download, specifying key interactions between components.
4.  Identify two potential bottlenecks in your design and propose a solution for each.

## Going further

How would you handle the requirement for private files within a multi-tenant system where files from different tenants might be stored in the same underlying storage bucket/system, ensuring data isolation and preventing unauthorized cross-tenant access, while still leveraging CDN benefits?

### 2. Technology choices and rationale

*   **API Gateway:** AWS API Gateway or Google Cloud Endpoints.
    *   **Why:** Provides a single entry point for all API requests, handling authentication, authorization (via integration with the existing auth service), rate limiting, and load balancing. This offloads common concerns from the backend services and improves security and scalability.
*   **Upload Service & Download Service:** Microservices built with a stateless framework (e.g., Spring Boot, Node.js with Express, Go with Gin) running on a container orchestration platform (e.g., Kubernetes, AWS ECS/EKS).
    *   **Why:** These services are responsible for generating pre-signed URLs, interacting with the database for metadata, and coordinating with the object storage. Being stateless allows for easy horizontal scaling. Using pre-signed URLs offloads the actual file transfer directly to the object storage, reducing the load on these services and improving performance.
*   **Database Service (File Metadata):** PostgreSQL (managed service like AWS RDS or Google Cloud SQL).
    *   **Why:** A relational database is ideal for storing structured metadata about files (e.g., file ID, user ID, workspace ID, filename, size, MIME type, storage path, upload timestamp, access permissions). PostgreSQL offers strong consistency, transactional integrity, and can scale vertically and horizontally (with sharding if needed at extreme scale). It's a mature, reliable choice.
    *   **Schema Example:**
        ```sql
        CREATE TABLE files (
            file_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
            workspace_id UUID NOT NULL,
            uploader_user_id UUID NOT NULL,
            filename VARCHAR(255) NOT NULL,
            mime_type VARCHAR(100) NOT NULL,
            file_size_bytes BIGINT NOT NULL,
            storage_path TEXT NOT NULL, -- e.g., "bucket-name/folder/file_id.ext"
            upload_timestamp TIMESTAMPTZ DEFAULT NOW(),
            status VARCHAR(50) DEFAULT 'uploaded', -- e.g., 'uploaded', 'processing', 'failed'
            checksum VARCHAR(64), -- e.g., SHA256 for integrity verification
            is_public BOOLEAN DEFAULT FALSE,
            created_at TIMESTAMPTZ DEFAULT NOW(),
            updated_at TIMESTAMPTZ DEFAULT NOW()
        );

        CREATE INDEX idx_files_workspace_id ON files (workspace_id);
        CREATE INDEX idx_files_uploader_user_id ON files (uploader_user_id);
        ```
*   **Object Storage:** AWS S3 or Google Cloud Storage.
    *   **Why:** These are highly durable (11 nines of durability), highly available, cost-effective, and massively scalable object storage solutions. They are designed for storing large amounts of unstructured data. They natively support pre-signed URLs for secure, temporary access, and integrate well with CDNs. Their tiered storage options (e.g., S3 Standard, S3 Infrequent Access, S3 Glacier) allow for cost optimization based on access patterns.
*   **CDN (Content Delivery Network):** AWS CloudFront or Google Cloud CDN.
    *   **Why:** A CDN caches frequently accessed files at edge locations globally, drastically reducing download latency for users worldwide. It also offloads traffic from the origin (object storage), reducing transfer costs and improving scalability. It's crucial for achieving low latency and acceptable streaming performance for larger files.
*   **Message Queue (Optional but Recommended for Post-Upload Processing):** AWS SQS/SNS or Google Cloud Pub/Sub.
    *   **Why:** While not explicitly shown in the core diagram, a message queue is essential for asynchronous processing of uploaded files (e.g., virus scanning, thumbnail generation, video transcoding, metadata extraction). The Upload Service can publish a message to the queue after a successful upload, and dedicated worker services can consume these messages. This decouples the upload process from time-consuming post-processing tasks, improving upload response times.

### 3. Request flow

#### File Upload Flow

1.  **Client Request:** A user initiates a file upload from their client application.
2.  **API Gateway:** The client sends an authenticated request to the API Gateway (e.g., `POST /upload`). The API Gateway authenticates the user and authorizes the request (e.g., checking if the user has permission to upload to the specified workspace).
3.  **Upload Service:** The API Gateway forwards the request to the Upload Service.
4.  **Database Interaction (Metadata):** The Upload Service generates a unique `file_id` and creates a preliminary entry in the `files` database table, including metadata like `workspace_id`, `uploader_user_id`, `filename`, `mime_type`, and a placeholder `file_size_bytes` (or 0 initially). It also determines the `storage_path` in the object storage (e.g., `my-bucket/workspace_id/file_id.ext`).
5.  **Pre-signed URL Generation:** The Upload Service requests a pre-signed PUT URL from the Object Storage service for the determined `storage_path`. This URL grants temporary write access to a specific object location.
6.  **Response to Client:** The Upload Service returns the pre-signed PUT URL and the `file_id` to the client.
7.  **Direct File Upload:** The client directly uploads the file to the Object Storage using the pre-signed URL. This bypasses the backend services, reducing their load.
8.  **Client Notification (Optional):** The client notifies the Upload Service (e.g., `PUT /upload/{file_id}/complete`) upon successful completion of the direct upload.
9.  **Database Update:** The Upload Service updates the `files` table with the actual `file_size_bytes` and potentially a `checksum` after verifying the upload completion.
10. **Asynchronous Processing (Optional):** The Upload Service publishes a message to a Message Queue (e.g., `file_uploaded` event) for any post-upload processing (e.g., virus scanning, thumbnail generation).

#### File Download Flow

1.  **Client Request:** A user requests to download a file (e.g., `GET /download/{file_id}`).
2.  **API Gateway:** The client sends an authenticated request to the API Gateway. The API Gateway authenticates the user and authorizes the request (e.g., checking if the user has permission to access `file_id` within `workspace_id`).
3.  **Download Service:** The API Gateway forwards the request to the Download Service.
4.  **Database Query (Metadata):** The Download Service queries the `files` database table using the `file_id` to retrieve its metadata, including `storage_path` and `is_public` status.
5.  **Pre-signed URL Generation (if private) / CDN URL (if public):**
    *   **Private File:** If the file is private or requires specific authorization, the Download Service requests a pre-signed GET URL from the Object Storage for the `storage_path`. This URL grants temporary read access.
    *   **Public File:** If the file is marked as public and suitable for direct CDN access, the Download Service constructs a CDN URL for the `storage_path`.
6.  **Response to Client:** The Download Service returns the pre-signed GET URL or the CDN URL to the client.
7.  **Direct File Download:** The client directly downloads the file from either the Object Storage (via the pre-signed URL) or the CDN (via the CDN URL). The CDN will serve cached versions if available, otherwise, it will fetch from the Object Storage.

### 4. Potential bottlenecks and solutions

1.  **Bottleneck 1: Database contention for file metadata.**
    *   **Problem:** With 5 million uploads and potentially tens of millions of downloads daily, the `files` metadata database could become a bottleneck, especially during peak times. Writes (new file entries, updates) and reads (for download requests) could overwhelm a single database instance, leading to increased latency and timeouts.
    *   **Solution:**
        *   **Read Replicas:** For the vast majority of download requests, read consistency is acceptable with a slight delay. Deploy multiple read replicas for the PostgreSQL database. The Download Service can be configured to direct read queries to these replicas, significantly offloading the primary database instance.
        *   **Connection Pooling:** Implement efficient connection pooling in the application services (Upload/Download Services) to manage database connections effectively and reduce overhead.
        *   **Caching:** Implement a caching layer (e.g., Redis or Memcached) for frequently accessed file metadata, especially for popular files. Before querying the database, the Download Service would check the cache. This reduces database load for hot files.
        *   **Sharding (Long-term):** If read replicas and caching are insufficient at 10x scale, consider sharding the `files` table based on `workspace_id` or `uploader_user_id`. This distributes the database load across multiple database instances. This is a complex solution and should only be considered when other scaling methods are exhausted.

2.  **Bottleneck 2: CDN cache misses and origin fetches for large or infrequently accessed files.**
    *   **Problem:** While a CDN is great for popular files, very large files (multiple GBs) or infrequently accessed files might not be cached at the nearest edge location. This leads to direct fetches from the origin (Object Storage), increasing download latency and potentially incurring higher egress costs from the origin. For streaming, consistent latency is crucial.
    *   **Solution:**
        *   **CDN Configuration Optimization:**
            *   **Longer Cache TTLs:** Configure longer Time-To-Live (TTL) values for files in the CDN, especially for immutable files, to maximize cache hit rates.
            *   **Byte-Range Requests:** Ensure the CDN and Object Storage are configured to fully support HTTP byte-range requests. This allows clients to resume interrupted downloads and stream parts of a file without downloading the entire object, which is critical for large files and video streaming.
            *   **Pre-warming (Selective):** For known popular or upcoming large files (e.g., a new software release), consider proactively "pre-warming" the CDN cache by making requests to populate edge caches before peak demand. This is typically done for a small, critical subset of files.
        *   **Multi-Region Object Storage / CDN Origin:** For a global user base, consider having Object Storage buckets in multiple geographic regions, with the CDN configured to pull from the closest origin. This reduces the "first-mile" latency for cache misses.
        *   **Adaptive Streaming (for Video):** For video files, implement adaptive bitrate streaming (e.g., HLS or DASH). This involves encoding videos into multiple resolutions/bitrates and serving them in small chunks. The client can then dynamically switch between bitrates based on network conditions, providing a smoother streaming experience even with varying latency. This requires a dedicated video processing pipeline (e.g., using a message queue and worker services for transcoding).

### Going further: Private files in a multi-tenant system with CDN

Handling private files in a multi-tenant system while leveraging CDN benefits requires a careful balance between security and performance. The core challenge is that CDNs typically cache based on URLs, and a simple public URL for a private file would expose it.

Here's how to address it:

1.  **Dynamic URL Generation (Pre-signed URLs):**
    *   **Mechanism:** Instead of serving a direct CDN URL for private files, the Download Service generates a **pre-signed URL** from the Object Storage. This URL includes a temporary signature and an expiration timestamp.
    *   **CDN Integration:** The pre-signed URL is then used as the **origin URL** for the CDN. The CDN itself can be configured to cache responses based on the *path* of the URL, but critically, it must be configured to **forward query parameters** to the origin. This allows the pre-signed signature to be passed through to the Object Storage for validation.
    *   **Client Flow:**
        1.  Client requests `GET /download/{file_id}`.
        2.  API Gateway -> Download Service (authenticates/authorizes user for `file_id`).
        3.  Download Service generates a pre-signed URL for the file in Object Storage (e.g., `https://mybucket.s3.amazonaws.com/tenantA/file123.pdf?AWSAccessKeyId=...&Expires=...&Signature=...`).
        4.  Download Service returns a **CDN-specific URL** that points to the CDN distribution, with the pre-signed URL as a query parameter or path segment (e.g., `https://cdn.example.com/private/tenantA/file123.pdf?s3_url=https://mybucket.s3.amazonaws.com/tenantA/file123.pdf?AWSAccessKeyId=...`).
        5.  The CDN receives this request. It's configured to:
            *   **Cache based on the canonical path:** `cdn.example.com/private/tenantA/file123.pdf`.
            *   **Forward all query parameters** to the origin.
            *   **Use the pre-signed S3 URL as its origin fetch URL.**
    *   **Security:** The pre-signed URL ensures that only requests with a valid signature and within the expiration window can access the file from the origin. The CDN acts as a proxy, but the underlying access control is still managed by the Object Storage's pre-signed URL mechanism.
    *   **Data Isolation (Tenant Separation):** Files for different tenants are stored in separate logical paths within the Object Storage bucket (e.g., `s3://my-bucket/tenantA/file1.pdf`, `s3://my-bucket/tenantB/file2.pdf`). The `storage_path` in the `files` metadata table includes the tenant identifier. The Download Service ensures that a user from `tenantA` can only generate a pre-signed URL for files under `s3://my-bucket/tenantA/`.

2.  **CDN Signed URLs/Cookies (More Advanced):**
    *   **Mechanism:** Some CDNs (like AWS CloudFront) offer their own "Signed URLs" or "Signed Cookies" features. Instead of relying solely on S3 pre-signed URLs, the Download Service can generate a CDN-signed URL.
    *   **How it works:**
        1.  The Download Service, after authorizing the user, generates a CDN-signed URL for the specific file (e.g., `https://cdn.example.com/tenantA/file123.pdf?Expires=...&Signature=...&Key-Pair-Id=...`).
        2.  The CDN is configured with a trusted key pair. When a request comes in with a signed URL, the CDN itself validates the signature and expiration.
        3.  If valid, the CDN serves the file from its cache or fetches it from the origin (Object Storage).
    *   **Benefits:** This approach allows the CDN to enforce access control directly at the edge, potentially reducing the number of requests that hit the origin (Object Storage) for authorization checks. It also offers more granular control over access policies (e.g., IP address restrictions, specific HTTP methods).
    *   **Data Isolation:** Similar to pre-signed S3 URLs, the CDN-signed URL would be generated for a specific tenant's file path, ensuring isolation. The Download Service's authorization logic is paramount here.

**Trade-offs:**

*   **Increased Complexity:** Both approaches add complexity compared to serving static public files. Generating and managing signed URLs (either S3 or CDN) requires backend logic.
*   **Cache Hit Rate:** For private files, the cache hit rate might be lower than for truly public files, especially if each user gets a unique signed URL with a short expiration. However, if the CDN is configured to cache based on the *base path* and ignore the signature parameters for caching purposes, then multiple users requesting the *same file* (even with different signed URLs) could benefit from a single cached object. This requires careful CDN configuration.
*   **Expiration Management:** Signed URLs have expiration times. If a user tries to download a file after the URL expires, they will receive an access denied error and need to request a new URL from the backend. This is a security feature but can impact user experience if expiration times are too short.
*   **Cost:** While CDNs reduce egress costs from the origin, signed URLs might slightly increase processing costs on the CDN or backend services due to signature generation and validation.

**Why a plausible-looking approach is wrong:**

*   **Storing tenant IDs directly in object metadata and relying solely on CDN for access control:**
    *   **Problem:** You cannot rely on CDN rules alone to enforce tenant-level access control for private files. CDNs are primarily caching and delivery mechanisms. While they can have some access control features (like signed URLs), they are not a substitute for a robust authorization service. Simply putting a `tenant_id` in the S3 object key (e.g., `s3://bucket/tenantA/file.pdf`) does not inherently prevent `tenantB` from guessing or trying to access `tenantA`'s files if the CDN is configured to serve everything publicly.
    *   **Why it's wrong:** Without a backend service generating temporary, authorized access tokens (like pre-signed URLs or CDN-signed URLs), any direct URL to a file in the CDN would be publicly accessible, completely bypassing your authorization logic and leading to massive data breaches. The CDN's job is to deliver content *fast*, not to be the primary arbiter of who can see what. That responsibility lies with your backend services and the underlying storage's access control mechanisms.
