## Scenario

Your team maintains a critical Node.js microservice responsible for processing incoming requests to apply discount codes to user orders. This service interacts with a third-party discount provider API to validate codes and apply discounts. The service currently experiences intermittent high latency and timeouts, especially during peak sales events.

Upon investigation, you've identified that the third-party API has a rate limit of 10 requests per second per client IP and imposes significant latency (500-1500ms) for each request. Your service, however, can receive bursts of hundreds of requests per second for discount applications from your frontend, far exceeding the third-party API's capacity. Direct calls to the third-party API are causing your service to queue up requests in memory, eventually leading to memory exhaustion or excessive response times for users. The existing implementation uses a simple `fetch` call directly within the request handler.

You need to refactor the discount application logic to gracefully handle these rate limits and latencies, ensuring that user requests are processed reliably without overwhelming the third-party API or crashing your service.

## Requirements

The service must continue to process discount application requests. However, instead of making direct, synchronous calls to the rate-limited third-party API, it should buffer and process these requests in a controlled manner. Assume the third-party API returns a simple `success: boolean` and `discountAmount: number | null` for a given `discountCode: string` and `orderId: string`.

Constraints:

*   **Third-party API Rate Limit:** Max 10 requests per second.
*   **Third-party API Latency:** High and variable (500-1500ms).
*   **High Influx of Requests:** Your service can receive bursts far exceeding the third-party API's rate limit.
*   **Reliability:** Requests should not be lost.
*   **Response Time:** Users expect a response, even if it's "pending" or "failed to apply."
*   **Memory Usage:** The solution should not lead to excessive memory consumption under high load.

## Deliverables

1.  A TypeScript module that encapsulates the logic for interacting with the third-party discount API, ensuring the 10 RPS rate limit is strictly adhered to.
2.  A mechanism to queue incoming discount application requests from your service's request handlers and process them using the rate-limited module.
3.  A way for the original request handler to receive the result of the discount application (success/failure and discount amount) once it's processed by the rate-limited queue, potentially asynchronously.
4.  Basic error handling for third-party API failures (e.g., network issues, non-2xx responses) within the rate-limited processing.

## Worked answer

### 1. TypeScript module for rate-limited API interaction

To adhere to the 10 requests per second (RPS) rate limit, we'll implement a token bucket algorithm. This allows for bursts up to a certain size while maintaining the average rate. For simplicity and strict adherence to 10 RPS, we'll use a simpler approach: ensuring a minimum delay between requests.

We'll use a `Promise` queue to serialize requests and introduce a delay. This ensures that even if multiple requests arrive simultaneously, they are processed one by one, with a minimum interval between them.

```typescript
// src/thirdPartyDiscountApi.ts

/**
 * Represents the response from the third-party discount API.
 */
interface ThirdPartyApiResponse {
  success: boolean;
  discountAmount: number | null;
}

/**
 * Simulates the third-party discount API interaction.
 * In a real scenario, this would involve `fetch` or an HTTP client.
 * It also simulates the high latency.
 */
async function callThirdPartyApi(
  discountCode: string,
  orderId: string
): Promise<ThirdPartyApiResponse> {
  const latency = Math.random() * 1000 + 500; // 500-1500ms latency
  console.log(
    `[ThirdPartyAPI] Calling for code: ${discountCode}, order: ${orderId} (simulated latency: ${latency.toFixed(
      0
    )}ms)`
  );
  await new Promise((resolve) => setTimeout(resolve, latency));

  // Simulate success/failure
  const success = Math.random() > 0.2; // 80% success rate
  const discountAmount = success ? parseFloat((Math.random() * 100).toFixed(2)) : null;

  if (!success) {
    console.warn(
      `[ThirdPartyAPI] Failed for code: ${discountCode}, order: ${orderId}`
    );
    // Simulate a network error or non-2xx response for error handling demonstration
    if (Math.random() < 0.1) { // 10% chance of "network error"
      throw new Error("Simulated network error or non-2xx response");
    }
  } else {
    console.log(
      `[ThirdPartyAPI] Success for code: ${discountCode}, order: ${orderId}, amount: ${discountAmount}`
    );
  }

  return { success, discountAmount };
}

// --- Rate Limiter Implementation ---

const REQUEST_INTERVAL_MS = 1000 / 10; // 100ms interval for 10 RPS
let lastRequestTime = 0; // Timestamp of the last successful API call
let processingPromise: Promise<any> = Promise.resolve(); // Chain promises to serialize requests

/**
 * Encapsulates the logic for interacting with the third-party discount API,
 * ensuring the 10 RPS rate limit is strictly adhered to.
 *
 * @param discountCode The discount code to validate.
 * @param orderId The order ID to apply the discount to.
 * @returns A Promise that resolves with the API response, or rejects on critical errors.
 */
export async function applyDiscountRateLimited(
  discountCode: string,
  orderId: string
): Promise<ThirdPartyApiResponse> {
  // Chain the new request to the existing processing promise.
  // This ensures requests are processed sequentially.
  processingPromise = processingPromise
    .then(async () => {
      const now = Date.now();
      const timeSinceLastRequest = now - lastRequestTime;
      const delayNeeded = REQUEST_INTERVAL_MS - timeSinceLastRequest;

      if (delayNeeded > 0) {
        console.log(`[RateLimiter] Delaying for ${delayNeeded.toFixed(0)}ms...`);
        await new Promise((resolve) => setTimeout(resolve, delayNeeded));
      }

      lastRequestTime = Date.now(); // Update last request time after potential delay

      try {
        const result = await callThirdPartyApi(discountCode, orderId);
        return result;
      } catch (error) {
        console.error(
          `[RateLimiter] Error calling third-party API for ${discountCode}, ${orderId}:`,
          error instanceof Error ? error.message : String(error)
        );
        // Re-throw to propagate the error to the caller
        throw error;
      }
    })
    .catch((error) => {
      // If a previous promise in the chain rejected, this catch block
      // will prevent subsequent .then() from executing unless explicitly handled.
      // We re-throw to ensure the error propagates to the current caller.
      throw error;
    });

  return processingPromise;
}
```

**Explanation:**

*   **`REQUEST_INTERVAL_MS`**: Calculated as `1000ms / 10 RPS = 100ms`. This is the minimum time that must pass between the *start* of two consecutive API calls.
*   **`lastRequestTime`**: Tracks when the last API call was initiated.
*   **`processingPromise`**: This is the core of the serialization. It's a `Promise` that always resolves (or rejects) with the result of the *last* API call. Each new call to `applyDiscountRateLimited` chains its execution to this promise using `.then()`. This ensures that:
    1.  Only one `callThirdPartyApi` is active at any given time.
    2.  The `delayNeeded` calculation and `setTimeout` are executed *before* each API call, ensuring the rate limit.
*   **`delayNeeded`**: Calculates how much time is left until `REQUEST_INTERVAL_MS` has passed since the `lastRequestTime`. If positive, a `setTimeout` introduces the necessary delay.
*   **Error Handling**: The `try...catch` block inside the `processingPromise` chain catches errors from `callThirdPartyApi` (e.g., simulated network issues). It logs the error and re-throws it, ensuring that the original caller of `applyDiscountRateLimited` can handle it. The outer `.catch` on `processingPromise` ensures that if a previous request in the chain failed, subsequent requests still attempt to run, but if the *current* request fails, its error is propagated.

**Trade-offs:**

*   **Strict Rate Limiting**: This approach is very strict. It will never exceed 10 RPS on average.
*   **No Bursting**: Unlike a true token bucket, this doesn't allow for bursts. If 10 requests arrive simultaneously after a long idle period, they will still be processed with 100ms intervals, taking 1 second to process the first 10.
*   **In-memory Queue**: The `processingPromise` implicitly creates an in-memory queue of pending operations. If the service receives a massive burst of requests (e.g., thousands), this promise chain can grow very long, potentially leading to increased memory usage and very long wait times for requests at the back of the queue.

### 2. Mechanism to queue incoming requests and process them

We need a way for the request handler to submit a request and get a `Promise` back that resolves when the discount is applied. We'll use a separate queue management module that interacts with our rate-limited API client. This queue will store `Promise` resolvers and rejecters, allowing us to resolve/reject the original request's promise once the API call completes.

```typescript
// src/discountRequestQueue.ts

import { applyDiscountRateLimited } from './thirdPartyDiscountApi';

/**
 * Represents a pending discount request in the queue.
 */
interface QueuedRequest {
  discountCode: string;
  orderId: string;
  resolve: (result: DiscountApplicationResult) => void;
  reject: (error: Error) => void;
}

/**
 * Represents the result of a discount application,
 * which will be returned to the original request handler.
 */
export interface DiscountApplicationResult {
  status: 'success' | 'failed' | 'error';
  discountAmount: number | null;
  message?: string;
}

const requestQueue: QueuedRequest[] = [];
let isProcessingQueue = false;

/**
 * Adds a discount application request to the queue.
 * @param discountCode The discount code.
 * @param orderId The order ID.
 * @returns A Promise that resolves with the `DiscountApplicationResult` when processed.
 */
export function queueDiscountApplication(
  discountCode: string,
  orderId: string
): Promise<DiscountApplicationResult> {
  return new Promise((resolve, reject) => {
    requestQueue.push({ discountCode, orderId, resolve, reject });
    console.log(
      `[Queue] Added request for ${discountCode}, ${orderId}. Queue size: ${requestQueue.length}`
    );
    processQueue(); // Attempt to process the queue
  });
}

/**
 * Processes items from the queue one by one, using the rate-limited API.
 * This function is designed to be called multiple times but only execute
 * the processing loop once concurrently.
 */
async function processQueue() {
  if (isProcessingQueue) {
    return; // Already processing
  }

  isProcessingQueue = true;
  console.log('[Queue] Starting queue processing...');

  while (requestQueue.length > 0) {
    const request = requestQueue.shift(); // Get the next request from the front of the queue

    if (!request) {
      // Should not happen if requestQueue.length > 0, but for type safety
      break;
    }

    const { discountCode, orderId, resolve, reject } = request;
    console.log(
      `[Queue] Processing request for ${discountCode}, ${orderId}. Remaining: ${requestQueue.length}`
    );

    try {
      const apiResponse = await applyDiscountRateLimited(discountCode, orderId);

      if (apiResponse.success) {
        resolve({
          status: 'success',
          discountAmount: apiResponse.discountAmount,
          message: 'Discount applied successfully',
        });
      } else {
        resolve({
          status: 'failed',
          discountAmount: null,
          message: 'Discount code invalid or not applicable',
        });
      }
    } catch (error) {
      // Handle critical errors during API call (e.g., network issues, service unavailable)
      console.error(
        `[Queue] Critical error processing ${discountCode}, ${orderId}:`,
        error instanceof Error ? error.message : String(error)
      );
      reject({
        status: 'error',
        discountAmount: null,
        message: `Failed to apply discount due to service error: ${
          error instanceof Error ? error.message : 'Unknown error'
        }`,
      });
    }
  }

  isProcessingQueue = false;
  console.log('[Queue] Queue processing finished.');
}
```

**Explanation:**

*   **`QueuedRequest`**: An interface to store the `discountCode`, `orderId`, and the `resolve`/`reject` functions of the `Promise` returned to the original request handler.
*   **`requestQueue`**: A simple array acting as a FIFO (First-In, First-Out) queue.
*   **`isProcessingQueue`**: A flag to ensure that only one `processQueue` loop is active at any given time. This prevents race conditions if `queueDiscountApplication` is called rapidly.
*   **`queueDiscountApplication`**: This is the entry point for request handlers. It creates a `Promise`, stores its `resolve`/`reject` functions along with the request data in `requestQueue`, and then calls `processQueue`.
*   **`processQueue`**:
    *   It runs in a `while` loop as long as there are items in `requestQueue`.
    *   It uses `requestQueue.shift()` to get the next request.
    *   It `await`s `applyDiscountRateLimited`, which handles the rate limiting.
    *   Based on the `apiResponse` or any errors, it calls the stored `resolve` or `reject` function, fulfilling the `Promise` returned to the original request handler.
    *   The `try...catch` block here specifically handles critical errors from the `applyDiscountRateLimited` call (e.g., network errors, non-2xx responses), distinguishing them from a "failed" discount application (where the API returned `success: false`).

**Trade-offs:**

*   **In-memory Queue**: The `requestQueue` is still an in-memory queue. Under extreme load, it can grow very large, consuming significant memory. If the Node.js process crashes, all pending requests in this queue are lost.
*   **Single-threaded Processing**: The `processQueue` loop and the `applyDiscountRateLimited` promise chain effectively serialize all discount requests through a single point. While necessary for strict rate limiting, it means the overall throughput is capped by the rate limiter, and the latency for requests at the back of a long queue will be very high.

### 3. Way for the original request handler to receive the result

The `queueDiscountApplication` function already returns a `Promise<DiscountApplicationResult>`. A typical Express.js (or similar framework) request handler can `await` this promise.

```typescript
// src/server.ts (Example Express.js server)

import express from 'express';
import { queueDiscountApplication, DiscountApplicationResult } from './discountRequestQueue';

const app = express();
const PORT = 3000;

app.use(express.json()); // For parsing application/json

// Simulate a high influx of requests
let requestCounter = 0;
setInterval(() => {
  // Simulate a burst of 50 requests every 5 seconds
  for (let i = 0; i < 50; i++) {
    const discountCode = `CODE${Math.floor(Math.random() * 100)}`;
    const orderId = `ORDER${++requestCounter}`;
    console.log(`[Server] Incoming request for ${discountCode}, ${orderId}`);

    // This is where a real HTTP request handler would call queueDiscountApplication
    queueDiscountApplication(discountCode, orderId)
      .then((result: DiscountApplicationResult) => {
        console.log(
          `[Server] Result for ${discountCode}, ${orderId}: Status=${result.status}, Amount=${result.discountAmount}`
        );
        // In a real handler, you would send this result back to the user.
        // For simulation, we just log it.
      })
      .catch((error: DiscountApplicationResult) => {
        console.error(
          `[Server] Error for ${discountCode}, ${orderId}: Status=${error.status}, Message=${error.message}`
        );
        // In a real handler, you would send an error response back to the user.
      });
  }
}, 5000);


// Example HTTP endpoint (not strictly required by the challenge but good for context)
app.post('/apply-discount', async (req, res) => {
  const { discountCode, orderId } = req.body;

  if (!discountCode || !orderId) {
    return res.status(400).json({ message: 'discountCode and orderId are required' });
  }

  try {
    const result = await queueDiscountApplication(discountCode, orderId);
    // Depending on requirements, you might return 'pending' immediately
    // or wait for the result as shown here.
    res.status(200).json(result);
  } catch (error) {
    console.error(`[Server] Handler caught error for ${discountCode}, ${orderId}:`, error);
    // The error caught here is the DiscountApplicationResult with status 'error'
    res.status(500).json(error);
  }
});

app.listen(PORT, () => {
  console.log(`Server listening on port ${PORT}`);
  console.log(`Simulating incoming requests every 5 seconds.`);
  console.log(`Access http://localhost:${PORT}/apply-discount with POST to test.`);

```

**Explanation:**

*   The `server.ts` file demonstrates how a request handler would integrate.
*   The `app.post('/apply-discount', ...)` handler directly `await`s the `queueDiscountApplication` promise. This means the HTTP response for that specific request will be held open until the discount application is processed by the rate-limited queue.
*   The `setInterval` block simulates a high influx of requests, calling `queueDiscountApplication` directly and logging the results when they eventually come back. This shows how the asynchronous nature works.
*   The `DiscountApplicationResult` interface provides a standardized structure for the outcome, including `status`, `discountAmount`, and an optional `message`. This allows the frontend to display meaningful feedback.

**Trade-offs:**

*   **Long-polling/Delayed Responses**: If the queue is long, users might experience very long response times (potentially tens of seconds or even minutes) as their request waits for its turn. This might exceed typical HTTP server timeout limits (e.g., 30-60 seconds for many load balancers/proxies).
*   **Resource Consumption**: Holding HTTP connections open for extended periods consumes server resources.
*   **User Experience**: Users might perceive the service as slow or unresponsive if they have to wait too long.

**Alternative (for "Going Further"):**

For better user experience and to avoid holding HTTP connections, a common pattern is to return an immediate "pending" response with a correlation ID, and then use WebSockets or server-sent events (SSE) to push the final result to the client once it's available. This would require more complex client-side logic and a mechanism to store pending request results (e.g., in Redis) keyed by the correlation ID.

### 4. Basic error handling for third-party API failures

Error handling is implemented at two levels:

1.  **Inside `thirdPartyDiscountApi.ts` (`applyDiscountRateLimited`):**
    *   The `callThirdPartyApi` function simulates network errors by sometimes throwing an `Error`.
    *   The `try...catch` block within `applyDiscountRateLimited` catches these critical errors. It logs them and then re-throws them. This ensures that any issues preventing the API call from even returning a `success: false` (e.g., network down, DNS failure, API gateway error) are propagated.

2.  **Inside `discountRequestQueue.ts` (`processQueue`):**
    *   The `try...catch` block around `await applyDiscountRateLimited(...)` in `processQueue` catches the re-thrown critical errors.
    *   Instead of resolving with a `status: 'failed'`, it calls the `reject` function of the original `Promise` (returned to the request handler). This signals a more severe, unexpected issue.
    *   It constructs a `DiscountApplicationResult` with `status: 'error'` and a descriptive message for the `reject` function, ensuring a consistent error structure.
    *   If `applyDiscountRateLimited` returns a response where `success: false` (meaning the API was reached, but the discount was invalid), this is handled as a `status: 'failed'` and resolves the promise, which is a "business logic" failure rather than a "system" error.

This two-tiered approach differentiates between:
*   **System Errors**: Problems preventing the API call from completing successfully (e.g., network issues, API unavailable). These `reject` the promise.
*   **Business Logic Failures**: The API call completed, but the discount was not applicable (e.g., invalid code). These `resolve` the promise with a `status: 'failed'`.

### Going further

#### Trade-offs: Client-side Rate Limiter vs. Third-party API's 429 Responses

**Client-side Rate Limiter (Implemented Approach):**

*   **Pros:**
    *   **Proactive Control:** You have full control over the rate at which you send requests. You can guarantee you won't exceed the limit, preventing your service from being blacklisted or receiving 429s.
    *   **Predictable Performance:** By controlling the outbound rate, you can better predict the throughput and latency for your internal queue.
    *   **Reduced Overhead:** You avoid the overhead of making a request, receiving a 429, and then retrying. This can be more efficient, especially with high latency APIs.
    *   **Simplified Logic (for strict limits):** For simple, fixed rate limits, a client-side limiter can be straightforward to implement.

*   **Cons:**
    *   **Static Configuration:** The rate limit (e.g., 10 RPS) is hardcoded or configured statically. If the third-party API changes its limits, your service needs to be updated and redeployed.
    *   **Underutilization:** If the third-party API *could* handle more requests temporarily (e.g., it has burst capacity you don't know about), your client-side limiter might underutilize its capacity.
    *   **Complexity for Dynamic Limits:** If the third-party API's rate limits are dynamic (e.g., based on account tier, time of day), a client-side limiter becomes much more complex to implement accurately.
    *   **Resource Consumption:** The in-memory queue can consume significant memory under sustained high load and is not resilient to service restarts.

**Relying on Third-party API's Rate-Limiting Responses (e.g., HTTP 429 Too Many Requests):**

*   **Pros:**
    *   **Dynamic Adaptation:** You automatically adapt to the third-party API's actual, current rate limits. If they increase capacity, you benefit immediately. If they reduce it, you gracefully handle it.
    *   **Optimal Utilization:** You can potentially utilize the API's full capacity, including any burst capacity, by sending requests until you hit the limit.
    *   **Source of Truth:** The API itself is the ultimate source of truth for its rate limits.

*   **Cons:**
    *   **Reactive Approach:** You only know you've hit the limit *after* making a request and receiving a 429. This means some requests will always fail initially.
    *   **Increased Latency/Overhead:** Each 429 response adds latency (the round trip to the API) and consumes resources (on both client and server) that could have been used for a successful request.
    *   **Backoff Strategy Complexity:** Implementing an effective retry-with-backoff strategy (e.g., exponential backoff with jitter) is crucial but can be complex to get right, especially across multiple concurrent workers.
    *   **Potential for Blacklisting:** Repeatedly hitting the 429 limit without proper backoff can sometimes lead to temporary IP blacklisting by aggressive rate limiters.
    *   **Queue Management Still Needed:** Even with 429s, you still need a queue and a retry mechanism to ensure requests are eventually processed, which adds complexity.

#### When to choose one approach or combine them:

*   **Choose Client-Side Rate Limiter when:**
    *   The third-party API has a **well-defined, static, and strict rate limit** that is unlikely to change.
    *   You prioritize **predictability and preventing any 429 errors** over maximizing API utilization.
    *   The cost of a failed request (even a 429) is high (e.g., billing implications, critical user experience impact).
    *   Your service is the **only consumer** of the third-party API from your client IP, simplifying coordination.
    *   You are willing to accept potential underutilization for stability.

*   **Choose Relying on 429 Responses when:**
    *   The third-party API's rate limits are **dynamic, complex, or not fully documented**.
    *   You want to **maximize API utilization** and are comfortable with some initial request failures.
    *   The third-party API provides useful `Retry-After` headers with its 429 responses, guiding your backoff strategy.
    *   You have a robust and well-tested **retry-with-backoff mechanism** in place.
    *   You are integrating with multiple third-party APIs, each with different rate-limiting behaviors.

*   **Combine Both Approaches (Recommended for Robustness):**
    This is often the most robust solution for critical services.
    1.  **Implement a Client-Side Rate Limiter:** Set it to a conservative rate (e.g., 80-90% of the documented limit) to proactively prevent most 429s. This acts as your primary defense.
    2.  **Implement a Retry-with-Backoff for 429s:** If, despite your client-side limiter, you *still* receive a 429 (e.g., due to a temporary API capacity drop, or another service sharing your IP hitting the limit), your system should gracefully back off and retry. This acts as a fallback and allows for dynamic adaptation.
    3.  **Circuit Breaker Pattern:** Additionally, implement a circuit breaker around the third-party API calls. If the API consistently returns errors (including 429s) or times out, the circuit breaker can temporarily "open," failing fast for new requests instead of hammering the API, giving it time to recover.

For the given scenario, where the rate limit is strict and the API latency is high, a **client-side rate limiter with an internal queue (as implemented)** is a good starting point. It provides immediate control and prevents overwhelming the API. However, for true production resilience, combining it with a robust retry mechanism for unexpected 429s and a circuit breaker would be ideal.

#### What breaks first at ten times the scale?

At ten times the scale (hundreds to thousands of requests per second from the frontend), the current implementation's primary points of failure would be:

1.  **Memory Exhaustion:** The `requestQueue` (an in-memory array) and the `processingPromise` chain would grow extremely large. Each `QueuedRequest` object and each pending `Promise` consumes memory. Thousands of pending requests, each holding references, would quickly exhaust the Node.js process's memory, leading to crashes.
2.  **Excessive Latency for Users:** Requests at the back of a very long queue would experience extremely high end-to-end latency. If the queue has 1000 requests and each takes 100ms to process due to rate limiting, the last request will wait 100 seconds *before* its API call even starts, plus the 500-1500ms API latency. This will lead to HTTP timeouts at the load balancer or client side.
3.  **Service Restarts Lead to Data Loss:** If the Node.js process crashes (due to memory exhaustion or other issues) or is intentionally restarted, all pending requests in the `requestQueue` are lost. This violates the "Reliability: Requests should not be lost" requirement at scale.

To handle ten times the scale, the in-memory queue would need to be replaced with a **persistent, distributed queue** like Redis, RabbitMQ, or Kafka. This would decouple the request ingestion from the processing, provide resilience against service restarts, and allow for horizontal scaling of the discount processing workers.
