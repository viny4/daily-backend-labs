## Scenario

Your team maintains a critical internal service that manages customer support tickets. The `tickets` table in PostgreSQL has grown to tens of millions of rows.

A new compliance requirement dictates that for any ticket that has been `CLOSED` for more than 90 days, we must generate an anonymized summary for long-term archival. This process needs to run daily, identifying all eligible tickets and enqueueing them for processing. Due to the high volume of tickets, a naive query and iteration approach is causing significant performance degradation on the production database, impacting the responsiveness of the support portal. The current solution attempts to fetch all eligible tickets at once, which often results in database timeouts and excessive memory usage in the application.

## Worked answer

### 1. Efficiently Retrieving Eligible Ticket IDs in Batches

The core idea is to retrieve ticket IDs in small, manageable batches using a cursor-like approach, rather than fetching all at once. This avoids loading the entire result set into memory and reduces the duration of database locks or high-resource queries. We'll use a `WHERE` clause with an `ORDER BY` and `LIMIT` to paginate through the results.

First, let's assume a simplified `tickets` table schema:

```sql
CREATE TABLE tickets (
    id BIGSERIAL PRIMARY KEY,
    status VARCHAR(50) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    closed_at TIMESTAMP WITH TIME ZONE,
    -- other relevant columns
    -- ...
);

-- Index for efficient lookup of closed tickets by closed_at
CREATE INDEX idx_tickets_status_closed_at ON tickets (status, closed_at) WHERE status = 'CLOSED';
-- Consider a covering index if other columns are frequently accessed with status/closed_at
-- CREATE INDEX idx_tickets_status_closed_at_id ON tickets (status, closed_at, id) WHERE status = 'CLOSED';
```

### 2. Explanation of Data Structure/Algorithmic Approach

The chosen approach is **cursor-based pagination** (sometimes called keyset pagination or seek method pagination).

**Why it's suitable:**

*   **Memory Efficiency:** Instead of fetching potentially millions of `id`s into application memory, we fetch only `batch_size` (e.g., 1,000 to 10,000) IDs at a time. This keeps the application's memory footprint well within the 512MB budget.
*   **Database Load:** Each query is lightweight, fetching only a small subset of data. The `WHERE status = 'CLOSED' AND closed_at < %s AND id > %s ORDER BY id ASC LIMIT %s` query can efficiently use the `idx_tickets_status_closed_at` index (or a covering index `idx_tickets_status_closed_at_id`) to quickly locate the starting point and retrieve the next `LIMIT` rows. This avoids full table scans and long-running transactions that could hold locks or consume excessive database resources.
*   **Scalability:** This method scales well with increasing data volume because the cost of each individual query remains relatively constant, regardless of the total number of eligible tickets. The total execution time will increase linearly with the number of tickets, but the impact on the database per query remains low.
*   **Robustness:** By processing in batches and recording progress, the job can be stopped and restarted without losing all progress.

**Alternative (and why it's less suitable):**

*   **OFFSET/LIMIT pagination:** While common, `OFFSET` pagination (`SELECT id FROM tickets WHERE ... ORDER BY id LIMIT 1000 OFFSET 1000000;`) becomes very inefficient at large offsets. The database still has to scan or traverse 1,000,000 rows to find the starting point for the 1,001st batch, making later queries progressively slower and more resource-intensive. Our cursor-based approach (`id > %s`) directly "seeks" to the next starting point using the index.

### 3. Handling Job Failure and Restart

The process handles resuming through the `last_processed_id` mechanism:

1.  **State Persistence:** Before starting to process a new batch of tickets, the job first attempts to retrieve `last_processed_id` from a persistent store (e.g., Redis, a dedicated `job_state` table in PostgreSQL, or even a file for simpler cases). This `last_processed_id` represents the highest `id` that was successfully enqueued in the *previous* run or previous batch of the *current* run.
2.  **Query Modification:** The `fetch_ticket_ids_batch` function incorporates this `last_processed_id` into its `WHERE` clause: `AND id > %s`. This ensures that the next query only fetches tickets with IDs strictly greater than the last successfully processed one, preventing re-processing of already enqueued tickets.
3.  **Progress Checkpointing:** After successfully enqueuing a batch of `ticket_ids` (i.e., the `db_client.enqueue_for_archival` call completes without error), the job updates the `last_processed_id` in the persistent store to the maximum `id` from the just-processed batch. This acts as a checkpoint.
4.  **Idempotency:** The downstream archival process (which consumes from the message queue) should ideally be idempotent. If, due to an edge case (e.g., the `record_last_processed_id` call fails but `enqueue_for_archival` succeeded), a ticket ID is enqueued twice, the archival process should handle it gracefully (e.g., by checking if an archive already exists for that ticket). However, the `id > %s` mechanism significantly reduces the chance of duplicate enqueues from the batching job itself.

If the job crashes (e.g., due to an out-of-memory error, network issue, or application bug) after enqueuing a batch but *before* updating `last_processed_id`, the next run will retrieve the `last_processed_id` from before the crash. This means it might re-enqueue a few tickets from the partially processed batch. This is where the idempotency of the downstream archival service becomes crucial. However, if the crash happens *after* `last_processed_id` is updated, the job will correctly pick up from the next unprocessed ID.

### Going Further

The chosen data structure/algorithm, **cursor-based pagination (or keyset pagination)**, specifically mitigates memory pressure and database load in several ways:

1.  **Memory Pressure Mitigation:**
    *   **Fixed Memory Footprint:** The application only ever holds `batch_size` ticket IDs in memory at any given time. If `batch_size` is 1000 and each ID is an 8-byte `BIGINT`, a batch consumes only 8KB of memory. Even with Python object overhead, this is negligible compared to the 512MB budget. This contrasts sharply with fetching all eligible IDs at once, which could easily exceed 512MB for tens of millions of tickets (e.g., 50 million IDs * 8 bytes/ID = 400MB raw data, plus Python object overhead, which could easily push it over 512MB).
    *   **No Large Result Set Buffering:** Database drivers often buffer entire result sets in memory before returning them to the application. With `LIMIT`, the driver only needs to buffer `batch_size` rows, keeping memory usage low on both the database client and server sides.

2.  **Database Load Mitigation:**
    *   **Index Utilization:** The `WHERE status = 'CLOSED' AND closed_at < %s AND id > %s ORDER BY id ASC LIMIT %s` query is highly optimized by a composite index on `(status, closed_at, id)` (or `(status, closed_at)` with `id` as the primary key implicitly ordered). The `id > %s` clause allows the database to directly "seek" to the next starting point in the index, avoiding the need to scan or sort previous rows.
    *   **Short-Lived Transactions/Queries:** Each batch query is quick to execute. This means:
        *   **Reduced Lock Contention:** The database holds locks (e.g., shared locks for reads) for a very short duration, minimizing interference with other concurrent operations on the `tickets` table (e.g., agents updating tickets).
        *   **Lower Resource Consumption:** Each query consumes CPU, I/O, and memory for a brief period. The overall load is spread out over the job's execution time, rather than a single spike that could overwhelm the database.
        *   **Connection Pool Efficiency:** Database connections are held for shorter periods, making the connection pool more efficient and less likely to exhaust available connections.
    *   **Predictable Performance:** The execution time of each batch query remains relatively constant regardless of how many batches have already been processed. This makes the job's overall performance more predictable and easier to monitor.

**Key Properties for Performance at Scale:**

*   **`ORDER BY id ASC`:** Ensures a consistent, deterministic order for pagination. The `id` column (typically a `BIGSERIAL` primary key) is monotonically increasing, making it an excellent "cursor" for sequential processing.
*   **`id > %s` (Keyset/Seek Pagination):** This is the critical component. It leverages the index to jump directly to the next logical starting point, avoiding the performance degradation associated with `OFFSET`.
*   **`LIMIT %s`:** Restricts the number of rows returned by each query, directly controlling memory usage and query execution time.
*   **Appropriate Indexing:** An index on `(status, closed_at, id)` (or `(status, closed_at)` if `id` is the primary key and implicitly ordered) is crucial. It allows the database to efficiently filter by `status` and `closed_at`, and then quickly find the next `id` in sequence without a full table scan.

**Trade-offs and What Breaks at 10x Scale:**

*   **Total Execution Time:** While individual queries are fast, the total job execution time scales linearly with the number of eligible tickets. If the number of `CLOSED` tickets eligible for archival grows to 500 million (10x current scale), and each batch takes 100ms, processing 500,000 batches would take 50,000 seconds (approx. 14 hours), exceeding the 30-minute execution limit.
    *   **Mitigation:** To handle this, we would need to:
        *   **Increase `batch_size`:** Up to a point, increasing `batch_size` reduces the number of round trips to the database, improving throughput. However, too large a batch can reintroduce memory pressure or longer query times.
        *   **Parallel Processing:** Divide the work. For example, process tickets closed in different date ranges concurrently (e.g., one worker handles `closed_at` from Jan-Mar, another from Apr-Jun). This would require a more sophisticated job orchestrator and careful management of `last_processed_id` per worker.
        *   **Database Sharding:** If the `tickets` table itself is sharded, each shard could run its own archival job.
*   **`last_processed_id` Storage Contention:** If the `record_last_processed_id` mechanism uses a single row in a database table for checkpointing, frequent updates (after every batch) could lead to write contention or slow down if the checkpointing store becomes a bottleneck.
    *   **Mitigation:** Use a highly performant key-value store like Redis, or batch checkpointing (e.g., update `last_processed_id` every 10 batches instead of every batch, accepting slightly more re-processing on crash).
*   **Index Maintenance Overhead:** A composite index on `(status, closed_at, id)` adds overhead to `INSERT`, `UPDATE`, and `DELETE` operations on the `tickets` table. At 10x scale, with potentially higher write rates, this overhead could become noticeable.
    *   **Mitigation:** Regularly monitor index usage and performance. Ensure the index is truly beneficial for the read queries. Consider partial indexes if `status = 'CLOSED'` is a small fraction of all tickets.
*   **Network Latency:** If the application server and database are geographically distant, network latency for each batch query can add up.
    *   **Mitigation:** Co-locate the application and database. Increase `batch_size` to amortize latency over more rows.

This approach is robust and efficient for the current scale, but like all solutions, it has limits that would require further architectural evolution at significantly higher volumes.
