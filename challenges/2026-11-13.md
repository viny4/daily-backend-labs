## Worked answer

### 1. AWS Services and Core Architectural Pattern

The core architectural pattern to achieve direct, secure, and performant file uploads is using **S3 Pre-Signed URLs**. This approach offloads the file transfer directly to S3, bypassing our application servers.

The AWS services involved are:

*   **Amazon S3 (Simple Storage Service):** For highly durable, scalable, and secure object storage. This is where the files will ultimately reside.
*   **AWS IAM (Identity and Access Management):** To define granular permissions for our backend application to generate pre-signed URLs and for S3 to enforce access.
*   **Your Django/Node.js Backend Application:** To authenticate users, authorize upload requests, generate pre-signed URLs, and record file metadata.
*   **Your Frontend Client (e.g., React, Vue.js, mobile app):** To request a pre-signed URL from the backend and then use it to upload the file directly to S3.
*   **Amazon S3 Event Notifications (optional but recommended):** To asynchronously notify the backend when an object is successfully created in S3, providing a robust way to confirm uploads and trigger post-processing. This can be configured to send events to an **Amazon SQS (Simple Queue Service) queue** or an **AWS Lambda function**.

**Architectural Flow:**

1.  The frontend client authenticates with the backend application.
2.  The frontend requests an upload URL from the backend, providing desired file metadata (e.g., `client-id`, `file-name`, `content-type`).
3.  The backend validates the user's authentication and authorization to upload for the given `client-id`.
4.  If authorized, the backend generates an S3 Pre-Signed URL for a `PUT` operation to a specific S3 key (e.g., `s3://your-bucket/client-id/file-id.ext`). This URL is time-limited and contains embedded credentials allowing direct upload to S3.
5.  The backend returns the Pre-Signed URL and the final S3 object key to the frontend.
6.  The frontend uses the Pre-Signed URL to perform an HTTP `PUT` request, directly uploading the file content to S3.
7.  S3 processes the upload.
8.  (Optional, but recommended) S3 sends an event notification (e.g., `s3:ObjectCreated:Put`) to an SQS queue or Lambda function upon successful upload.
9.  The backend consumes this event (from SQS or Lambda) or the frontend reports success, and the backend records the S3 object key, file size, and other metadata in its PostgreSQL database.

### 2. High-Level Steps for Frontend Client Upload

Here's how a frontend client (e.g., a web application using JavaScript's `fetch` API) would handle an upload:

1.  **User Action:** The user selects a file (e.g., via an `<input type="file">` element).
2.  **Initiate Upload Request to Backend:** The frontend makes an authenticated API call to your backend application to request a pre-signed URL.

    ```javascript
    // Example using fetch API
    async function initiateFileUpload(file) {
        const response = await fetch('/api/v1/files/upload-initiate', {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'Authorization': `Bearer ${yourAuthToken}` // Your authentication token
            },
            body: JSON.stringify({
                fileName: file.name,
                fileType: file.type,
                fileSize: file.size,
                clientId: 'some-client-id-from-context' // Or derived from user session
            })
        });

        if (!response.ok) {
            throw new Error('Failed to get pre-signed URL');
        }

        const data = await response.json();
        return { uploadUrl: data.uploadUrl, s3Key: data.s3Key };
    }
    ```

3.  **Direct Upload to S3:** Upon receiving the `uploadUrl` and `s3Key` from the backend, the frontend performs an HTTP `PUT` request directly to the `uploadUrl` with the file content.

    ```javascript
    async function uploadFileToS3(file, uploadUrl) {
        const response = await fetch(uploadUrl, {
            method: 'PUT',
            headers: {
                // S3 pre-signed URLs often require specific headers to match the signature.
                // The backend should specify these when generating the URL.
                // Common ones include Content-Type, x-amz-acl.
                'Content-Type': file.type,
                // 'x-amz-acl': 'private', // Example: if you want to set ACL during upload
            },
            body: file // The File object itself can be used as the body
        });

        if (!response.ok) {
            throw new Error('Failed to upload file to S3');
        }

        console.log('File uploaded successfully to S3!');
        return response;
    }
    ```

4.  **Notify Backend of Completion (Optional, but good for immediate feedback):** After the S3 upload is complete, the frontend can optionally make another API call to the backend to confirm the upload and trigger immediate processing if necessary. This is a fallback/complement to S3 event notifications.

    ```javascript
    async function confirmUploadCompletion(s3Key, fileSize) {
        const response = await fetch('/api/v1/files/upload-complete', {
            method: 'POST',
            headers: {
                'Content-Type': 'application/json',
                'Authorization': `Bearer ${yourAuthToken}`
            },
            body: JSON.stringify({
                s3Key: s3Key,
                fileSize: fileSize,
                status: 'completed'
            })
        });

        if (!response.ok) {
            throw new Error('Failed to confirm upload completion');
        }
        console.log('Backend notified of upload completion.');
    }
    ```

5.  **Putting it all together:**

    ```javascript
    async function handleUserFileUpload(selectedFile) {
        try {
            const { uploadUrl, s3Key } = await initiateFileUpload(selectedFile);
            await uploadFileToS3(selectedFile, uploadUrl);
            await confirmUploadCompletion(s3Key, selectedFile.size); // Or rely on S3 events
            alert('File upload process completed!');
        } catch (error) {
            console.error('Upload failed:', error);
            alert('File upload failed. Please try again.');
        }
    }
    ```

### 3. Django/Node.js Backend Authorization and Metadata Recording

#### Backend Authorization and Pre-Signed URL Generation

The backend's role is crucial for security: it authenticates the user, authorizes their request to upload a file for a specific client, and generates a secure, time-limited pre-signed URL.

```python
import boto3
from botocore.exceptions import ClientError
from django.conf import settings
from rest_framework.views import APIView
from rest_framework.response import Response
from rest_framework import status
from rest_framework.permissions import IsAuthenticated

class InitiateFileUploadView(APIView):
    permission_classes = [IsAuthenticated]

    def post(self, request):
        user = request.user
        # Assuming user profile has a client association
        try:
            user_client = user.userprofile.client
        except AttributeError:
            return Response({"error": "User not associated with a client."}, status=status.HTTP_403_FORBIDDEN)

        file_name = request.data.get('fileName')
        file_type = request.data.get('fileType')
        file_size = request.data.get('fileSize') # For validation, not strictly needed for pre-signed URL
        client_id_from_request = request.data.get('clientId') # For explicit client selection if user has many

        if not all([file_name, file_type]):
            return Response({"error": "fileName and fileType are required."}, status=status.HTTP_400_BAD_REQUEST)

        # --- Authorization Logic ---
        # Ensure the user is authorized to upload for the specified client_id
        # In this simple example, we assume a user belongs to one client.
        # If a user can upload for multiple clients, more complex logic is needed.
        if client_id_from_request and str(user_client.id) != client_id_from_request:
             return Response({"error": "Unauthorized client ID for upload."}, status=status.HTTP_403_FORBIDDEN)

        # Generate a unique file ID for S3 key
        file_uuid = uuid.uuid4()
        s3_key = f"{user_client.id}/{file_uuid}.{file_name.split('.')[-1]}" # e.g., 'client-id/uuid.ext'

        s3_client = boto3.client(
            's3',
            region_name=settings.AWS_S3_REGION_NAME,
            aws_access_key_id=settings.AWS_ACCESS_KEY_ID,
            aws_secret_access_key=settings.AWS_SECRET_ACCESS_KEY
        )

        try:
            # Generate pre-signed URL for PUT operation
            # The ContentType header is crucial for S3 to correctly store the file type
            # and for the browser to send the correct header during upload.
            # Max file size constraint can be added here using Conditions if using POST pre-signed URLs.
            # For PUT, S3 doesn't enforce size limits in the pre-signed URL itself.
            # We enforce it in the backend before generating.
            if file_size and file_size > 500 * 1024 * 1024: # 500 MB
                 return Response({"error": "File size exceeds 500MB limit."}, status=status.HTTP_400_BAD_REQUEST)

            presigned_url = s3_client.generate_presigned_url(
                ClientMethod='put_object',
                Params={
                    'Bucket': settings.AWS_S3_BUCKET_NAME,
                    'Key': s3_key,
                    'ContentType': file_type,
                    # 'ACL': 'private' # Optional: Set object ACL if needed
                },
                ExpiresIn=3600 # URL valid for 1 hour
            )

            # Create a pending entry in the database
            UploadedFile.objects.create(
                client=user_client,
                s3_key=s3_key,
                file_name=file_name,
                file_type=file_type,
                uploaded_by=user,
                status='pending_upload'
            )

            return Response({
                "uploadUrl": presigned_url,
                "s3Key": s3_key,
                "fileId": file_uuid
            }, status=status.HTTP_200_OK)

        except ClientError as e:
            # Log the error for debugging
            print(f"Error generating pre-signed URL: {e}")
            return Response({"error": "Could not generate upload URL."}, status=status.HTTP_500_INTERNAL_SERVER_ERROR)

    path('api/v1/files/upload-initiate', InitiateFileUploadView.as_view(), name='initiate-file-upload'),
    # ... other paths
]
```

#### Recording File Metadata in PostgreSQL

After the file is successfully uploaded to S3, the backend needs to update its database record. This can be done in two primary ways:

1.  **Frontend Notification (less reliable):** The frontend sends a `confirmUploadCompletion` request to the backend after the S3 upload. The backend then updates the `UploadedFile` record. This is simpler but relies on the client's network connection and successful final request.
2.  **S3 Event Notifications (more robust):** S3 can be configured to send an event (e.g., `s3:ObjectCreated:Put`) to an SQS queue or trigger a Lambda function when an object is created. Your backend (or another service) then consumes this event to update the database. This is preferred for reliability and decoupling.

**Django Example (S3 Event Notification via SQS):**

```python
# Assuming you have a consumer service/management command that polls an SQS queue
# or a Lambda function that triggers an API endpoint on your Django app.

# tasks.py (e.g., using Celery or a custom management command)
from django.conf import settings
from .models import UploadedFile
import boto3
import json

sqs_client = boto3.client(
    'sqs',
    region_name=settings.AWS_S3_REGION_NAME,
    aws_access_key_id=settings.AWS_ACCESS_KEY_ID,
    aws_secret_access_key=settings.AWS_SECRET_ACCESS_KEY
)

def process_s3_upload_event(message_body):
    try:
        s3_event = json.loads(message_body)
        for record in s3_event.get('Records', []):
            if record['eventName'].startswith('ObjectCreated:'):
                bucket_name = record['s3']['bucket']['name']
                s3_key = record['s3']['object']['key']
                file_size = record['s3']['object']['size']

                if bucket_name == settings.AWS_S3_BUCKET_NAME:
                    try:
                        uploaded_file = UploadedFile.objects.get(s3_key=s3_key, status='pending_upload')
                        uploaded_file.file_size = file_size
                        uploaded_file.status = 'completed'
                        uploaded_file.save()
                        print(f"Successfully updated file {s3_key} in DB.")
                    except UploadedFile.DoesNotExist:
                        print(f"Warning: UploadedFile record for {s3_key} not found or already processed.")
                    except Exception as e:
                        print(f"Error updating file {s3_key}: {e}")
    except json.JSONDecodeError:
        print(f"Invalid JSON message: {message_body}")
    except Exception as e:
        print(f"Error processing S3 event: {e}")


def poll_sqs_for_s3_events():
    queue_url = settings.AWS_S3_EVENT_SQS_QUEUE_URL # Configure this in settings
    while True:
        response = sqs_client.receive_message(
            QueueUrl=queue_url,
            MaxNumberOfMessages=10,
            WaitTimeSeconds=20 # Long polling
        )
        messages = response.get('Messages', [])
        for message in messages:
            process_s3_upload_event(message['Body'])
            sqs_client.delete_message(
                QueueUrl=queue_url,
                ReceiptHandle=message['ReceiptHandle']
            )
        # Add a small delay if no messages were received to avoid busy-waiting
        if not messages:
            import time
            time.sleep(5)

# You would typically run `poll_sqs_for_s3_events()` in a separate worker process
# or as a Celery beat task, or a dedicated Lambda function.
```

### 4. AWS IAM Policy Statements and S3 Bucket Policy

#### IAM Policy for Backend Application

The IAM role associated with your Django/Node.js backend application servers needs permissions to generate pre-signed URLs for `put_object` operations.

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:PutObject",
                "s3:PutObjectAcl"  // If you set ACLs during pre-signed URL generation
            ],
            "Resource": "arn:aws:s3:::your-s3-bucket-name/*"
        },
        {
            "Effect": "Allow",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::your-s3-bucket-name/*"
        }
    ]
}
```
**Explanation:**
*   `s3:PutObject`: Allows the backend to create pre-signed URLs for uploading objects.
*   `s3:PutObjectAcl`: If your `generate_presigned_url` call includes `ACL` parameters (e.g., `'ACL': 'private'`), this permission is required.
*   `s3:GetObject`: While not strictly required for *generating* upload URLs, it's common for backend applications to also need to retrieve objects (e.g., for serving or processing). It's included here as a common practice.
*   `"Resource": "arn:aws:s3:::your-s3-bucket-name/*"`: Grants these permissions for all objects within your specific S3 bucket. You could make this more granular if needed, e.g., `arn:aws:s3:::your-s3-bucket-name/${aws:PrincipalTag/client-id}/*` if your backend instance has a client-id tag, but typically the backend generates URLs for *any* client it's authorized to manage.

#### S3 Bucket Policy Adjustments

The existing S3 bucket policy generally does not need significant changes for pre-signed URLs. Pre-signed URLs derive their permissions from the IAM user/role that *generates* them, not directly from the bucket policy.

However, it's crucial to ensure that your bucket policy does *not* explicitly deny `s3:PutObject` actions for the specific S3 keys or conditions that the pre-signed URLs will target. If your bucket policy has a broad `Deny` statement, you might need to add an exception.

**Example of a minimal S3 bucket policy (assuming default private access):**

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Deny",
            "Principal": "*",
            "Action": "s3:PutObject",
            "Resource": "arn:aws:s3:::your-s3-bucket-name/*",
            "Condition": {
                "Null": {
                    "aws:Referer": "true"
                },
                "Bool": {
                    "aws:SecureTransport": "false"
                }
            }
        },
        {
            "Effect": "Allow",
            "Principal": {
                "AWS": "arn:aws:iam::ACCOUNT_ID:role/your-backend-instance-role"
            },
            "Action": [
                "s3:GetObject",
                "s3:ListBucket"
            ],
            "Resource": [
                "arn:aws:s3:::your-s3-bucket-name",
                "arn:aws:s3:::your-s3-bucket-name/*"
            ]
        }
    ]
}
```
**Explanation:**
*   The first `Deny` statement is a common security practice to prevent anonymous HTTP uploads and enforce HTTPS. This doesn't interfere with pre-signed URLs because they carry their own authentication.
*   The second `Allow` statement grants your backend's IAM role (which generates the pre-signed URLs) necessary permissions to interact with the bucket. This is usually managed via IAM policies attached to the role, not primarily the bucket policy, but it's good to ensure the bucket policy doesn't override it.

**Key Point:** The pre-signed URL itself contains a signature that authenticates the request. The S3 bucket policy's main role here is to ensure that no other policies explicitly *deny* the actions that the pre-signed URL is trying to perform. For direct uploads, the most important aspect is the IAM policy of the entity generating the URL.

#### S3 Event Notification Configuration (Optional but Recommended)

To enable the robust backend notification, you'd configure S3 event notifications.

**Via AWS Console or Terraform:**

```terraform
resource "aws_sqs_queue" "s3_upload_events" {
  name                       = "your-app-s3-upload-events-queue"
  delay_seconds              = 0
  max_message_size           = 262144
  message_retention_seconds  = 345600 # 4 days
  receive_wait_time_seconds  = 20
  visibility_timeout_seconds = 300 # 5 minutes
}

resource "aws_s3_bucket_notification" "bucket_notification" {
  bucket = "your-s3-bucket-name"

  queue {
    id        = "s3_object_created_notification"
    queue_arn = aws_sqs_queue.s3_upload_events.arn
    events    = ["s3:ObjectCreated:*"]
    # You can add prefix/suffix filters if needed, e.g.,
    # filter_prefix = "uploads/"
    # filter_suffix = ".pdf"
  }
}

# Grant S3 permission to send messages to the SQS queue
resource "aws_sqs_queue_policy" "sqs_policy" {
  queue_url = aws_sqs_queue.s3_upload_events.id
  policy = jsonencode({
    Version = "2012-10-17",
    Statement = [
      {
        Effect    = "Allow",
        Principal = { Service = "s3.amazonaws.com" },
        Action    = "sqs:SendMessage",
        Resource  = aws_sqs_queue.s3_upload_events.arn,
        Condition = {
          ArnEquals = { "aws:SourceArn" = "arn:aws:s3:::your-s3-bucket-name" }
        }
      }
    ]
  })
}
```

### Going Further: Trade-offs

This approach of offloading direct file uploads to S3 using pre-signed URLs offers significant advantages but also introduces some trade-offs compared to proxying all uploads through your backend application servers.

#### Advantages of Direct Uploads (Pre-Signed URLs)

1.  **Performance & Latency:**
    *   **Reduced Latency:** Files are uploaded directly to S3's highly optimized global network, often leveraging AWS's edge locations (like CloudFront if configured) for faster transfers, especially for users geographically distant from your application servers.
    *   **Increased Throughput:** Your API servers are no longer a bottleneck for large file transfers. They only handle small metadata requests (initiate upload, confirm completion), freeing up CPU, memory, and network bandwidth for core business logic.
    *   **Eliminates Timeouts:** Large file uploads no longer tie up API server connections for extended periods, reducing the likelihood of server-side timeouts and improving overall API responsiveness.

2.  **Scalability:**
    *   **S3 Scales Infinitely:** S3 is designed for virtually unlimited scale. As your upload volume grows, S3 automatically handles the increased load without requiring you to scale your application servers proportionally for file transfer capacity.
    *   **Decoupled Scaling:** You can scale your application servers based on business logic demands, independent of file upload volume.

3.  **Security:**
    *   **Reduced Attack Surface:** File content never touches your application servers, reducing the risk of malicious file uploads (e.g., viruses, oversized files, unauthorized content) directly impacting your server's filesystem or memory.
    *   **Granular S3 Permissions:** Pre-signed URLs enforce specific S3 permissions (e.g., `s3:PutObject` only), for a specific key, and for a limited time, minimizing the window of vulnerability.
    *   **No Server-Side Storage:** Eliminates the need for temporary storage on your application servers, reducing the risk of data leakage or resource exhaustion.

4.  **Cost-Effectiveness:**
    *   **Reduced EC2 Costs:** Less CPU, memory, and network utilization on your EC2 instances means you can run smaller instances or fewer instances, leading to lower compute costs.
    *   **Optimized Network Costs:** Data transfer costs within AWS (e.g., EC2 to S3) are often lower than egress costs to the internet. Direct S3 uploads minimize data transfer *through* your EC2 instances.

#### Trade-offs of Direct Uploads

1.  **Operational Complexity:**
    *   **Frontend Logic:** The frontend client needs more sophisticated logic to handle the two-step process (request URL, then upload). This adds complexity compared to a single `POST` request to the backend.
    *   **Error Handling:** Error handling becomes more distributed. The frontend needs to handle S3-specific errors during the direct upload, and the backend needs to handle potential S3 event processing failures.
    *   **S3 Event Notifications:** Setting up and reliably consuming S3 event notifications (e.g., via SQS or Lambda) adds infrastructure and monitoring overhead.
    *   **CORS Configuration:** S3 buckets require correct Cross-Origin Resource Sharing (CORS) configuration to allow direct uploads from your frontend's domain.

2.  **Security (Specific Considerations):**
    *   **Pre-Signed URL Leaks:** If a pre-signed URL is compromised before its expiration, an unauthorized party could upload a file. The short expiration time mitigates this risk.
    *   **Client-Side Validation:** While the backend authorizes the *intent* to upload, client-side validation (e.g., file type, size) is crucial for user experience but can be bypassed. Server-side validation (e.g., checking `Content-Type` in the S3 event, or even using S3 Object Lambda for advanced validation) is still necessary for robust security. S3's pre-signed POST URLs offer more robust server-side validation capabilities (e.g., content-length range, content-type) directly in the signature, but PUT pre-signed URLs are simpler for single file uploads.

3.  **Resilience:**
    *   **Distributed Failure Points:** While the overall system is more resilient due to S3's high availability, you now have more components that can fail (backend for URL generation, S3 for upload, S3 event delivery, SQS/Lambda for processing). This requires comprehensive monitoring across these services.
    *   **Eventual Consistency:** If relying solely on S3 event notifications, the database update is eventually consistent. There might be a short delay between a successful S3 upload and the file metadata appearing in your PostgreSQL database. The frontend might need to poll for status or display a "processing" state.

#### What Breaks First at Ten Times the Scale?

In the scenario, the initial problems were **latency spikes, API server load, and security concerns**.

With the direct upload approach:

*   **API server load:** This is largely mitigated. The API servers handle only metadata, which scales much better.
*   **Latency spikes:** Upload latency is now primarily dependent on the user's network connection to S3 and S3's own performance, which is generally excellent. The initiation latency (requesting the pre-signed URL) is still on your API server but is a small, fast request.
*   **Security concerns:** Greatly improved by offloading the direct file handling.

At **ten times the scale**, the most likely points of strain or increased complexity would be:

1.  **Backend `initiateFileUpload` endpoint:** While it's a small request, if you have 10x the *number* of concurrent uploads (not just larger files), this endpoint will see a significant increase in traffic. Ensure your backend API is horizontally scalable and your database can handle the increased `INSERT` rate for `UploadedFile` records.
2.  **S3 Event Notification Processing:** If you're using SQS, the queue will grow, and your consumer service (e.g., Django management command, Lambda) needs to scale to process messages efficiently. If it falls behind, database updates will be delayed.
3.  **PostgreSQL Database:** The `UploadedFile` table will grow 10x faster. Ensure proper indexing (especially on `s3_key`, `client_id`, `status`) and that your database can handle the increased write load and query volume for metadata.
4.  **IAM Rate Limits:** While unlikely for typical SaaS, if you generate an extremely high volume of pre-signed URLs per second, you could theoretically hit AWS IAM API rate limits. This is generally very high and adjustable, but worth noting.

The core S3 upload mechanism itself is designed to handle massive scale, so it's unlikely to be the bottleneck. The surrounding services that orchestrate and track these uploads will be the areas to monitor and scale.
