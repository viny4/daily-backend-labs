## Scenario

Your team maintains a backend service for a popular online learning platform. One core feature is tracking student progress through courses. Each course is broken down into modules, and each module into individual lessons. As students complete lessons, their progress is recorded.

A new feature requires displaying a student's overall progress across *all* courses they are currently enrolled in, specifically the total number of unique lessons they have completed. The current implementation fetches all completed lessons for each course, then iterates through them to build a unique set. This works fine for individual courses, but for students enrolled in many courses (e.g., 50-100), with each course having hundreds of lessons, this approach has become a bottleneck. The latency for loading the student dashboard is now unacceptable, often exceeding 5 seconds.

You have access to data representing a student's completed lessons, which can be thought of as a list of `(course_id, lesson_id)` tuples. Assume `lesson_id` is unique *within* a course, but not globally (e.g., `lesson_id=1` in `course_id=101` is different from `lesson_id=1` in `course_id=102`).

## Requirements

The current approach is leading to high CPU usage on the backend and unacceptable latency for the student dashboard. You need to design and implement a more efficient way to calculate the total count of *unique lessons* a student has completed across all their enrolled courses.

Constraints:
*   **Scale:** A student can be enrolled in up to 100 courses. Each course can have up to 500 lessons.
*   **Latency Budget:** The calculation for a single student must complete within 200 milliseconds.
*   **Memory:** The solution should be reasonably memory-efficient, as many students might be querying this simultaneously.
*   **Data Format:** You can assume the input is a list of `(course_id, lesson_id)` pairs, representing all completed lessons for a given student.
*   **No Database Changes:** For this exercise, assume you cannot alter the database schema or add new indexes. The optimization must happen within the application layer given the existing data.

## Worked answer

### 1. Python Function `count_unique_completed_lessons`

```python
def count_unique_completed_lessons(completed_lessons: list[tuple[int, int]]) -> int:
    """
    Calculates the total count of unique completed lessons across all courses for a student.

    A lesson is considered unique if its (course_id, lesson_id) pair is unique.

    Args:
        completed_lessons: A list of (course_id, lesson_id) tuples representing
                           all lessons completed by a student.

    Returns:
        The total count of unique completed lessons.
    """
    # Using a set of tuples directly is efficient for uniqueness checks.
    # Python's built-in set uses a hash table for O(1) average-case insertion and lookup.
    unique_lessons = set(completed_lessons)
    return len(unique_lessons)

# Example Usage (demonstrated in section 3)
```

### 2. Explanation of Data Structure and Algorithm

The chosen approach uses a Python `set` to store the `(course_id, lesson_id)` tuples. A `set` is a highly optimized data structure for storing unique elements, implemented internally as a hash table. When an element (in this case, a tuple) is added to a set, its hash value is computed, and this hash is used to quickly determine if the element already exists in the set. If it does, the new element is ignored; otherwise, it's added. This process ensures that only unique elements are stored.

This is significantly more efficient than a naive approach that might involve sorting the list and then iterating to count unique elements, or using a list and checking `if element not in list` before appending. Sorting a list of `N` elements typically takes `O(N log N)` time. Checking `if element not in list` for a list of `K` elements takes `O(K)` time in the worst case, leading to `O(N^2)` for `N` insertions. In contrast, adding `N` elements to a hash set takes `O(N)` time on average, because each insertion and uniqueness check is `O(1)` on average. Given the constraints (up to 100 courses * 500 lessons = 50,000 completed lessons), `O(N)` average-case performance for set construction is crucial for meeting the 200ms latency budget. The memory usage is also efficient, storing each unique `(course_id, lesson_id)` tuple once.

### Going Further

If `lesson_id` were globally unique across all courses (meaning `lesson_id=1` always refers to the same lesson, regardless of `course_id`), the performance characteristics and optimal approach would change.

**Current Approach (using `set` of `(course_id, lesson_id)` tuples):**
*   **Time Complexity:** `O(N)` on average, where `N` is the total number of completed lesson records. Each tuple insertion into the set is `O(1)` on average.
*   **Space Complexity:** `O(U)`, where `U` is the number of unique `(course_id, lesson_id)` tuples. In the worst case, `U=N`.

**If `lesson_id` were globally unique:**
The `course_id` would become irrelevant for determining uniqueness. We would only need to consider the `lesson_id`.

*   **Optimal Approach:** The most optimal approach would still be to use a `set`, but this time, a `set` of `lesson_id` integers directly.
    ```python
    def count_unique_globally_unique_lessons(completed_lessons: list[tuple[int, int]]) -> int:
        unique_lesson_ids = set()
        for course_id, lesson_id in completed_lessons:
            unique_lesson_ids.add(lesson_id) # Only add lesson_id
        return len(unique_lesson_ids)
    ```
    Alternatively, using a generator expression for conciseness:
    ```python
    def count_unique_globally_unique_lessons_concise(completed_lessons: list[tuple[int, int]]) -> int:
        return len(set(lesson_id for course_id, lesson_id in completed_lessons))
    ```

*   **Time Complexity:** Still `O(N)` on average, where `N` is the total number of completed lesson records. Each integer insertion into the set is `O(1)` on average. The initial iteration to extract `lesson_id`s is `O(N)`.
*   **Space Complexity:** `O(U_L)`, where `U_L` is the number of unique `lesson_id`s. This would likely be less than `U` (the number of unique `(course_id, lesson_id)` tuples) because multiple courses could share the same globally unique `lesson_id`. Storing integers in the set would also generally consume less memory per element than storing tuples.

**Would the current approach still be optimal?**
No, the current approach (using `set` of `(course_id, lesson_id)` tuples) would **not** be optimal if `lesson_id` were globally unique.

*   **Redundancy:** It would store `(course_id, lesson_id)` pairs, even though `course_id` is no longer needed for uniqueness. For example, if `lesson_id=100` is globally unique, then `(101, 100)` and `(102, 100)` would be counted as two distinct unique lessons by the current function, even though they refer to the same global lesson. This would lead to an incorrect (higher) count.
*   **Memory Inefficiency:** Storing tuples `(course_id, lesson_id)` consumes more memory than storing just `lesson_id` integers. While Python tuples are relatively lightweight, for very large `N`, this difference could become noticeable.
*   **Correctness:** The primary reason it wouldn't be optimal is that it would yield an **incorrect count** based on the new definition of uniqueness. The problem statement explicitly defines uniqueness as `(course_id, lesson_id)` pairs, so the current solution is correct for the given problem. If the definition changed to `lesson_id` being globally unique, the solution would need to adapt to only consider `lesson_id` for uniqueness.
