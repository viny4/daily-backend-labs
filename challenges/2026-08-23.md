## Scenario

Your team maintains a backend service that manages customer subscriptions for a multi-tenant SaaS platform. When a customer's subscription is due for renewal, a background worker process attempts to charge their payment method. If the charge fails (e.g., insufficient funds, expired card), the system needs to retry the charge a few times over a period, with increasing delays between retries.

Currently, failed charges are simply logged, and a separate, single cron job picks up all `FAILED` charges once an hour and retries them. This system worked fine when you had hundreds of customers, but with 500,000 active subscriptions, and a 5% daily failure rate (meaning 25,000 failed charges daily needing retries), the single cron job is overwhelmed. It regularly misses retry windows, leading to frustrated customers and delayed revenue. The business demands that retries happen reliably within 5 minutes of their scheduled time.

You've identified that the bottleneck is the centralized polling. You need a more robust, distributed approach to schedule and execute these payment retries. The system must be resilient to individual worker failures and avoid duplicate charge attempts for the same failed payment.

## Requirements

The current system relies on a single process. You need to design and outline a solution that distributes the scheduling and execution of payment retries across multiple workers. Consider the following constraints:

*   **Scale:** Handle at least 25,000 failed payments daily, each potentially requiring 3-5 retries.
*   **Concurrency:** Multiple worker instances should be able to process retries concurrently without stepping on each other's toes.
*   **Reliability:** A worker failing mid-processing should not prevent a retry from happening, nor should it lead to a retry being processed twice.
*   **Latency Budget:** Retries must be attempted within 5 minutes of their scheduled time.
*   **Idempotency:** The payment gateway allows identical charge requests within a short window, but we want to avoid sending duplicate requests from our side.

## Worked answer

### 1. Core Components of the Distributed Retry System

To address the limitations of the single cron job and meet the new requirements, we'll introduce several new components and modify existing ones:

1.  **Database (PostgreSQL):**
    *   **`payments` table:** Stores the state of each payment attempt, including its status, scheduled retry time, and retry count.
    *   **`payment_retries` table:** A new table to explicitly track individual retry attempts, their scheduled times, and their current state (e.g., `PENDING`, `PROCESSING`, `SUCCESS`, `FAILED`). This decouples the retry scheduling from the main `payments` table.
2.  **Message Queue (Kafka or RabbitMQ):** A distributed, fault-tolerant message queue will be used to trigger retry processing. This allows for asynchronous, decoupled communication between the scheduler and workers.
3.  **Scheduler Service:** A dedicated service responsible for identifying `PENDING` retries from the database whose `scheduled_at` time has passed and enqueuing them onto the message queue. This service can run as multiple instances for high availability, using a leader election mechanism (e.g., Zookeeper, etcd, or a database-backed lock) to ensure only one instance is actively scheduling at a time.
4.  **Worker Pool (Payment Retry Workers):** Multiple stateless worker instances that consume messages from the message queue, process the payment retry, and update the database.

#### Database Schema Changes

We'll introduce a new table `payment_retries` and modify the `payments` table to link to it.

```sql
-- Existing payments table (simplified)
CREATE TABLE payments (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id UUID NOT NULL,
    subscription_id UUID NOT NULL,
    amount NUMERIC(10, 2) NOT NULL,
    currency TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'PENDING', -- e.g., 'PENDING', 'CHARGED', 'FAILED'
    last_attempt_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- New payment_retries table
CREATE TYPE retry_status AS ENUM ('PENDING', 'PROCESSING', 'SUCCESS', 'FAILED', 'CANCELLED');

CREATE TABLE payment_retries (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    payment_id UUID NOT NULL REFERENCES payments(id),
    retry_number INT NOT NULL, -- 1st retry, 2nd retry, etc.
    scheduled_at TIMESTAMP WITH TIME ZONE NOT NULL,
    status retry_status NOT NULL DEFAULT 'PENDING',
    processed_by TEXT, -- Identifier of the worker that processed it
    processed_at TIMESTAMP WITH TIME ZONE,
    external_charge_id TEXT, -- ID from payment gateway if successful
    failure_reason TEXT,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    -- Ensures only one PENDING/PROCESSING retry for a given payment_id and retry_number
    UNIQUE (payment_id, retry_number)
);

CREATE INDEX idx_payment_retries_scheduled_at_status ON payment_retries (scheduled_at, status);
CREATE INDEX idx_payment_retries_payment_id ON payment_retries (payment_id);

-- Add a column to payments to track the current retry attempt
ALTER TABLE payments
ADD COLUMN current_retry_id UUID REFERENCES payment_retries(id);
```

### 2. Flow of a Failed Payment

Here's the detailed flow:

1.  **Initial Payment Failure:**
    *   A user's subscription renewal payment is attempted by the main payment service.
    *   If the charge fails, the `payments` table `status` is updated to `FAILED`.
    *   Crucially, a new entry is inserted into the `payment_retries` table:
        *   `payment_id` points to the failed payment.
        *   `retry_number` is `1`.
        *   `scheduled_at` is set to `NOW() + <initial_delay>` (e.g., 5 minutes).
        *   `status` is `PENDING`.
    *   The `payments.current_retry_id` is updated to point to this new `payment_retries` entry.

    *Example SQL for initial failure:*
    ```sql
    -- Assume payment_id = 'a1b2c3d4-e5f6-7890-1234-567890abcdef' failed
    INSERT INTO payment_retries (payment_id, retry_number, scheduled_at, status)
    VALUES ('a1b2c3d4-e5f6-7890-1234-567890abcdef', 1, NOW() + INTERVAL '5 minutes', 'PENDING')
    RETURNING id; -- Let's say it returns 'r1id'

    UPDATE payments
    SET status = 'FAILED',
        last_attempt_at = NOW(),
        current_retry_id = 'r1id'
    WHERE id = 'a1b2c3d4-e5f6-7890-1234-567890abcdef';
    ```

2.  **Scheduling Retries (Scheduler Service):**
    *   The Scheduler Service continuously queries the `payment_retries` table for `PENDING` retries whose `scheduled_at` is in the past.
    *   It uses a query like:
        ```sql
        SELECT id, payment_id, retry_number
        FROM payment_retries
        WHERE status = 'PENDING' AND scheduled_at <= NOW()
        ORDER BY scheduled_at ASC
        LIMIT 1000
        FOR UPDATE SKIP LOCKED; -- Important for concurrency
        ```
    *   For each identified retry, it attempts to atomically update its status to `PROCESSING` and enqueue a message to the message queue.
    *   The message payload includes `payment_retry_id`, `payment_id`, and `retry_number`.

    *Example Scheduler Logic (pseudocode):*
    ```
    while true:
        tx = db.beginTransaction()
        try:
            retries = db.query("SELECT id, payment_id, retry_number FROM payment_retries WHERE status = 'PENDING' AND scheduled_at <= NOW() LIMIT 1000 FOR UPDATE SKIP LOCKED")
            for retry in retries:
                // Atomically update status to PROCESSING
                updated_rows = db.execute("UPDATE payment_retries SET status = 'PROCESSING', processed_at = NOW() WHERE id = ? AND status = 'PENDING'", retry.id)
                if updated_rows == 1:
                    message_queue.publish("payment_retry_topic", {
                        "payment_retry_id": retry.id,
                        "payment_id": retry.payment_id,
                        "retry_number": retry.retry_number
                    })
                else:
                    // Another scheduler instance or worker picked it up already, skip
                    log.warn("Retry %s already processed or status changed", retry.id)
            tx.commit()
        except Exception as e:
            tx.rollback()
            log.error("Scheduler error: %s", e)
        sleep(1 second)
    ```

3.  **Executing Retries (Payment Retry Workers):**
    *   Multiple Payment Retry Workers continuously consume messages from the `payment_retry_topic` in the message queue.
    *   When a worker receives a message:
        *   It fetches the full `payment_retry` record and associated `payment` record from the database using the `payment_retry_id`.
        *   It verifies the `payment_retry.status` is `PROCESSING`. If not, it logs a warning and might NACK the message (depending on queue semantics) or just discard it to avoid reprocessing.
        *   It calls the external Payment Gateway to attempt the charge.
        *   **Outcome 1: Successful Charge:**
            *   The worker updates the `payments` table: `status = 'CHARGED'`, `last_attempt_at = NOW()`.
            *   The worker updates the `payment_retries` table for the current retry: `status = 'SUCCESS'`, `external_charge_id = <gateway_id>`.
            *   The worker acknowledges the message in the message queue.
        *   **Outcome 2: Failed Charge (but eligible for more retries):**
            *   The worker updates the `payment_retries` table for the current retry: `status = 'FAILED'`, `failure_reason = <reason>`.
            *   It then inserts a *new* `payment_retries` record for the *next* retry attempt:
                *   `payment_id` points to the original payment.
                *   `retry_number` is `current_retry_number + 1`.
                *   `scheduled_at` is `NOW() + <increasing_delay>`.
                *   `status` is `PENDING`.
            *   The `payments.current_retry_id` is updated to point to this new `PENDING` retry.
            *   The worker acknowledges the message in the message queue.
        *   **Outcome 3: Failed Charge (and no more retries allowed):**
            *   The worker updates the `payments` table: `status = 'FINAL_FAILED'`, `last_attempt_at = NOW()`.
            *   The worker updates the `payment_retries` table for the current retry: `status = 'FAILED'`, `failure_reason = <reason>`.
            *   The worker acknowledges the message in the message queue.

    *Example Worker Logic (pseudocode):*
    ```
    on message received from "payment_retry_topic":
        payment_retry_id = message.payment_retry_id
        payment_id = message.payment_id

        tx = db.beginTransaction()
        try:
            retry_record = db.get("SELECT * FROM payment_retries WHERE id = ? FOR UPDATE", payment_retry_id)
            if retry_record.status != 'PROCESSING':
                log.warn("Received message for retry %s but status is %s, skipping.", payment_retry_id, retry_record.status)
                tx.rollback()
                message_queue.ack(message) // Acknowledge to prevent reprocessing
                return

            payment_record = db.get("SELECT * FROM payments WHERE id = ?", payment_id)

            charge_result = payment_gateway.charge(payment_record.customer_id, payment_record.amount)

            if charge_result.success:
                db.execute("UPDATE payments SET status = 'CHARGED', last_attempt_at = NOW() WHERE id = ?", payment_id)
                db.execute("UPDATE payment_retries SET status = 'SUCCESS', external_charge_id = ?, processed_at = NOW() WHERE id = ?", charge_result.id, payment_retry_id)
            else:
                db.execute("UPDATE payment_retries SET status = 'FAILED', failure_reason = ?, processed_at = NOW() WHERE id = ?", charge_result.reason, payment_retry_id)

                if retry_record.retry_number < MAX_RETRIES:
                    next_retry_number = retry_record.retry_number + 1
                    next_scheduled_at = NOW() + calculate_exponential_backoff(next_retry_number)
                    new_retry_id = db.insert("INSERT INTO payment_retries (payment_id, retry_number, scheduled_at, status) VALUES (?, ?, ?, 'PENDING') RETURNING id", payment_id, next_retry_number, next_scheduled_at)
                    db.execute("UPDATE payments SET current_retry_id = ? WHERE id = ?", new_retry_id, payment_id)
                else:
                    db.execute("UPDATE payments SET status = 'FINAL_FAILED', last_attempt_at = NOW() WHERE id = ?", payment_id)

            tx.commit()
            message_queue.ack(message)
        except Exception as e:
            tx.rollback()
            log.error("Worker error processing retry %s: %s", payment_retry_id, e)
            message_queue.nack(message) // NACK to allow reprocessing by another worker
    ```

### 3. Preventing Multiple Workers from Processing the Same Retry

Several mechanisms are employed to prevent duplicate processing:

1.  **Database-backed State Machine with Atomic Updates:**
    *   **`payment_retries.status` column:** This is the primary mechanism. A retry must be in `PENDING` status to be picked up by the scheduler, and then transition to `PROCESSING`.
    *   **`FOR UPDATE SKIP LOCKED` in Scheduler:** When the scheduler queries for `PENDING` retries, `FOR UPDATE SKIP LOCKED` ensures that rows selected by one scheduler instance are immediately locked and skipped by other concurrent scheduler instances. This prevents multiple schedulers from trying to enqueue the same retry.
    *   **Atomic `UPDATE` in Scheduler:** The scheduler updates the `payment_retries.status` from `PENDING` to `PROCESSING` with a `WHERE id = ? AND status = 'PENDING'` clause. Only one scheduler instance will succeed in this update for a given `id`. If the update affects 0 rows, it means another scheduler or worker already changed its status.
    *   **Worker Verification:** When a worker receives a message, it first fetches the `payment_retry` record and verifies its status is `PROCESSING`. If it's already `SUCCESS` or `FAILED` (perhaps due to a race condition where another worker finished quickly), the worker can safely ignore or acknowledge the message.

2.  **Message Queue Guarantees (At-Least-Once Delivery with Idempotency):**
    *   Message queues like Kafka or RabbitMQ typically offer "at-least-once" delivery. This means a message *might* be delivered more than once (e.g., if a worker crashes after processing but before acknowledging).
    *   Our database-backed state machine (specifically the `status` column and atomic updates) handles this. Even if a worker receives the same message twice, the first attempt will change the `payment_retries.status` to `PROCESSING` (or `SUCCESS`/`FAILED`). The subsequent attempt will find the status is no longer `PENDING` or `PROCESSING` and will not re-execute the charge.
    *   The `payment_retries.id` is a unique identifier for each specific retry attempt. The Payment Gateway itself should ideally support idempotency keys (e.g., a unique request ID) to prevent duplicate charges if the *same* charge request is sent multiple times within a short window. Our workers would pass `payment_retry.id` or a derived UUID as this idempotency key to the payment gateway.

3.  **Unique Constraint on `(payment_id, retry_number)`:**
    *   The `UNIQUE (payment_id, retry_number)` constraint on `payment_retries` ensures that for a given original payment, there can only be one entry for `retry_number 1`, one for `retry_number 2`, etc. This prevents accidental creation of multiple "next retry" records if a worker somehow tries to insert it twice.

### 4. Justification of Technology Choices

*   **PostgreSQL:** A robust, ACID-compliant relational database. Its strong transactional guarantees are crucial for maintaining consistency in the state machine (e.g., updating `payment_retries.status` and inserting a new retry record within a single transaction). Features like `FOR UPDATE SKIP LOCKED` are essential for concurrent scheduling.
*   **Kafka (or RabbitMQ):**
    *   **Scalability:** Both are highly scalable and can handle the required throughput of 25,000+ messages daily, even with retries.
    *   **Durability:** Messages are persisted, ensuring that even if all workers or the scheduler crash, no retry events are lost.
    *   **Decoupling:** Separates the scheduling logic from the execution logic, allowing independent scaling of schedulers and workers.
    *   **Load Balancing:** Automatically distributes messages to available worker instances, ensuring concurrent processing.
    *   **At-Least-Once Delivery:** Provides the guarantee that messages will eventually be processed, which is critical for financial operations. We handle potential duplicates through idempotency.
    *   *Choice between Kafka/RabbitMQ:* For high throughput and long-term retention of messages (for auditing/replay), Kafka is often preferred. For simpler setup and more traditional queue semantics (e.g., explicit message acknowledgment/NACK), RabbitMQ can be a good fit. Given the scale, Kafka is a strong candidate.
*   **Scheduler Service (Custom Application):** While managed services exist (e.g., AWS Step Functions, Azure Logic Apps), a custom service offers maximum flexibility for complex retry logic (e.g., exponential backoff with custom rules) and direct database interaction for atomic state updates. Leader election (e.g., using a distributed lock manager like Zookeeper/etcd, or even a simple database lock) ensures high availability without duplicate scheduling.

### Going Further: Worker Crashes After Successful Charge but Before DB Update

This is a classic "distributed transaction" problem and a critical scenario to address.

**Potential Issues:**

1.  **Duplicate Charge:** If the worker crashes *after* sending the charge request to the payment gateway (which succeeds) but *before* updating the `payment_retries.status` to `SUCCESS` and `payments.status` to `CHARGED`, the message queue might not receive an acknowledgment. The message would then be redelivered to another worker (or the same worker after restart). This new worker would see the `payment_retry.status` still as `PROCESSING` (or potentially `PENDING` if the initial `PROCESSING` update was also lost), leading it to attempt the charge again. This results in two charges for the same payment.
2.  **Stale State:** The payment remains in a `FAILED` or `PROCESSING` state in our system, even though it was successfully charged externally. This leads to customer confusion, delayed revenue recognition, and potential manual reconciliation.
3.  **Lost Retry Information:** The `external_charge_id` from the successful gateway call might be lost if not persisted.

**Mitigation in this Design:**

Our design mitigates this through a combination of idempotency and eventual consistency checks:

1.  **Payment Gateway Idempotency:** This is the *most crucial* defense. When the worker sends a charge request to the payment gateway, it *must* include an idempotency key. The `payment_retry.id` is a perfect candidate for this.
    *   If the first worker sends `charge(payment_retry_id='X', ...)` and succeeds, the payment gateway records this.
    *   If the worker crashes and the message is redelivered, the second worker sends `charge(payment_retry_id='X', ...)`. The payment gateway, upon receiving the same idempotency key, will recognize it as a duplicate request for an already successful charge and will typically return the *original successful response* without processing the charge again. This prevents duplicate charges at the source.

2.  **Transactional Database Updates:** The worker's logic for updating the `payment_retries` and `payments` tables is wrapped in a single database transaction. This ensures atomicity: either all database updates commit, or none do. If the worker crashes *during* the transaction (e.g., after the `UPDATE payments` but before `UPDATE payment_retries`), the entire transaction will be rolled back, leaving the `payment_retries.status` as `PROCESSING` (or `PENDING` if the initial `PROCESSING` update was also part of the same transaction or was lost).

3.  **Message Queue NACK/Timeout:** If the worker crashes before acknowledging the message, the message queue's timeout mechanism will eventually redeliver the message. The new worker will then pick it up.

4.  **Worker Logic for Redelivery:**
    *   When a worker receives a message for `payment_retry_id='X'`, it first fetches the `payment_retry` record.
    *   If `payment_retry.status` is `PROCESSING`, it proceeds.
    *   It then calls the payment gateway with `payment_retry_id='X'` as the idempotency key.
    *   **Scenario 1: Gateway returns success (even if it was a duplicate request):** The worker then updates the DB to `SUCCESS` and `CHARGED`. This correctly reflects the state.
    *   **Scenario 2: Gateway returns failure:** The worker processes it as a failure, potentially scheduling a new retry.

5.  **Reconciliation/Monitoring (Long-Term Safety Net):**
    *   Even with the above, it's good practice to have an eventual consistency check. A separate daily/hourly reconciliation job could:
        *   Identify `payment_retries` records stuck in `PROCESSING` for an unusually long time (e.g., > 1 hour).
        *   For such records, it could query the payment gateway using the `payment_retry.id` (as the idempotency key) to check the actual status of the charge.
        *   If the gateway indicates success, the reconciliation job can update our database to `SUCCESS` and `CHARGED`.
        *   If the gateway indicates failure or no record, the reconciliation job could re-enqueue the message or mark the retry as `FAILED` and schedule a new one.
    *   Alerting for `payment_retries` stuck in `PROCESSING` state is also crucial for operational visibility.

By combining strong idempotency at the payment gateway, transactional database updates, and robust worker logic for redelivered messages, we can ensure that even in the face of worker crashes, payments are not double-charged and the system eventually converges to the correct state.
