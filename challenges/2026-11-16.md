## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee shifts and schedules. A core feature is the ability for managers to view an "Audit Log" of all changes made to shifts. This `shift_audits` table has grown significantly and now contains hundreds of millions of rows across thousands of tenants.

When a manager loads the audit log for their company, the application performs a query like this: `SELECT * FROM shift_audits WHERE company_id = ? AND created_at BETWEEN ? AND ? ORDER BY created_at DESC LIMIT 100 OFFSET ?;`. This query has become extremely slow, often taking 5-10 seconds, especially for companies with a high volume of shift changes. The pagination makes it particularly painful, as each subsequent page load also incurs significant latency.

The `shift_audits` table has the following simplified structure (don't worry about exact types, just assume appropriate ones):
- `id` (PK)
- `company_id` (FK to companies table)
- `shift_id` (FK to shifts table, can be NULL if the audit is about a new shift)
- `audited_by_user_id` (FK to users table)
- `action_type` (e.g., 'CREATE_SHIFT', 'UPDATE_START_TIME', 'DELETE_SHIFT')
- `old_value` (JSONB)
- `new_value` (JSONB)
- `created_at` (timestamp with timezone)
- `metadata` (JSONB, for additional context)

## Requirements

The primary goal is to significantly reduce the latency of the audit log query for managers.
- Query response times for the audit log must be consistently under 500ms, even for companies with millions of audit entries.
- The solution must support efficient pagination (`OFFSET` and `LIMIT`).
- The solution must not introduce significant write latency overhead (e.g., more than 50ms) to the `shift_audits` table, as shift changes are a frequent operation.
- The solution should be implemented purely using PostgreSQL features (e.g., indexes, partitioning, materialized views, etc.). No application-level changes or new services are allowed for this challenge.

3.  An `EXPLAIN (ANALYZE, BUFFERS)` output for the *optimized* query (which might be the same SQL as before, or slightly modified to leverage your DDL changes) against the same representative dataset, showing a significant performance improvement within the required latency budget.

## Worked answer

### 1. DDL Statement for Optimization

The primary bottleneck for the given query is the combination of filtering by `company_id` and `created_at`, followed by sorting and pagination. A multi-column B-tree index is the most suitable PostgreSQL feature to address this.

```sql
CREATE INDEX idx_shift_audits_company_created ON shift_audits (company_id, created_at DESC);
```

**Explanation:**

*   **`company_id`**: This is the leading column in the index because it's used for equality filtering, which significantly reduces the number of rows the database needs to consider.
*   **`created_at DESC`**: After filtering by `company_id`, the query needs to sort the results by `created_at` in descending order. Including `created_at` as the second column in the index, with the `DESC` order specified, allows PostgreSQL to read the data directly in the desired sort order. This avoids an explicit sort operation, which can be very expensive, especially with `OFFSET`.
*   **B-tree Index**: B-tree indexes are efficient for equality lookups, range scans, and ordered retrieval, making them perfect for this scenario.

### 3. `EXPLAIN (ANALYZE, BUFFERS)` Output for the Optimized Query

First, apply the index:

```sql
CREATE INDEX idx_shift_audits_company_created ON shift_audits (company_id, created_at DESC);
ANALYZE shift_audits; -- Update statistics after index creation
```

Now, run the same query again. PostgreSQL's planner should automatically pick up the new index.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM shift_audits
WHERE company_id = 100
  AND created_at BETWEEN '2026-10-01 00:00:00+00' AND '2026-11-01 00:00:00+00' -- Same date range
ORDER BY created_at DESC
LIMIT 100 OFFSET 0;
```

**Expected `EXPLAIN` Output (simulated, actual values will vary):**

```

  Buffers: shared hit=20 read=150 written=0

        Index Cond: (company_id = 100 AND created_at <= '2026-11-01 00:00:00+00'::timestamp with time zone AND created_at >= '2026-10-01 00:00:00+00'::timestamp with time zone)

Planning Time: 0.200 ms
Execution Time: 15.789 ms
```

**Analysis of Optimized Query:**

*   **`Index Scan Backward`**: This is the key improvement. PostgreSQL now uses the `idx_shift_audits_company_created` index.
    *   It performs an equality lookup on `company_id = 100` to quickly find the relevant section of the index.
    *   Then, it scans the `created_at` part of the index in `BACKWARD` order (because `created_at DESC` was specified in the index and the query's `ORDER BY`) to retrieve records within the date range.
    *   Since the index already provides the data in the desired sort order, no separate `Sort` operation is needed.
*   **`Index Cond`**: The filters `company_id = 100` and `created_at BETWEEN ? AND ?` are applied directly by the index scan, meaning only relevant index entries and their corresponding table rows are accessed.
*   **`Buffers`**: The number of `read` buffers is drastically reduced (e.g., from hundreds of thousands to a few hundred). This signifies that very little data needed to be fetched from disk, as the index provides a highly efficient path.
*   **`Execution Time`**: The `15.789 ms` (under 20 milliseconds) is well within the 500ms requirement, demonstrating a significant performance improvement.

### Going Further

#### Why the chosen solution improves performance for both initial and subsequent pagination requests

The `CREATE INDEX idx_shift_audits_company_created ON shift_audits (company_id, created_at DESC);` index dramatically improves performance for several reasons:

1.  **Efficient Filtering (`company_id`):** The `company_id` being the leading column allows PostgreSQL to quickly narrow down the search space to only the rows belonging to the specific company. This is an O(log N) operation on the index, where N is the total number of companies, rather than an O(N) scan of the entire table.

2.  **Pre-sorted Data (`created_at DESC`):** By including `created_at DESC` as the second column in the index, the data for each `company_id` is already stored in the index in the desired descending order of `created_at`.
    *   **Initial Query (`OFFSET 0`):** When `OFFSET 0` is used, the database can directly read the first `LIMIT` rows from the index in the correct order, avoiding a costly in-memory or on-disk sort operation.
    *   **Subsequent Pagination (`OFFSET N`):** This is where the index truly shines for pagination. With a plain table scan and sort, each `OFFSET N` query would typically require sorting the *entire* result set up to `N + LIMIT` rows and then discarding the first `N` rows. This means the cost of sorting grows linearly with `N`. With the index, PostgreSQL can efficiently skip `N` entries in the index and then read the next `LIMIT` entries. The cost of skipping `N` entries in a B-tree is logarithmic or proportional to the number of entries skipped, but crucially, it doesn't involve re-sorting a large dataset. It's more like navigating a pre-sorted list.

3.  **Index-Only Scans (Partial):** While the query `SELECT *` prevents a full index-only scan (as it needs all columns from the table), the index still allows for an efficient "index scan," where the index is used to locate the exact table rows (tuples) needed. The `Index Scan Backward` operation directly navigates the index to find the `company_id` and `created_at` range, then fetches the complete row data for only those 100 records. This is far more efficient than scanning the entire table.

#### How PostgreSQL's query planner utilizes your changes

The query planner, upon seeing the `WHERE company_id = ? AND created_at BETWEEN ? AND ? ORDER BY created_at DESC LIMIT ? OFFSET ?` pattern, will evaluate the cost of using the new index versus a sequential scan or other available indexes.

1.  **Index Selection:** It will recognize that `idx_shift_audits_company_created` covers both the equality filter (`company_id`), the range filter (`created_at BETWEEN`), and the ordering (`created_at DESC`). This makes it a highly attractive candidate.
2.  **Scan Method:** It will choose an `Index Scan Backward` because the `ORDER BY created_at DESC` matches the index's `created_at DESC` definition. If the query had `ORDER BY created_at ASC`, it would likely choose an `Index Scan` (forward).
3.  **No Explicit Sort:** Because the index provides the data in the required order, the planner can completely eliminate the `Sort` node from the execution plan, which was a major cost factor in the original query.
4.  **Early Filtering:** The `Index Cond` shows that the `company_id` and `created_at` filters are applied directly within the index scan, meaning only the relevant index entries are processed, and only the corresponding table rows are fetched.

#### Potential trade-offs for write operations

While the index significantly improves read performance, it introduces trade-offs for write operations (`INSERT`, `UPDATE`, `DELETE`):

1.  **Write Latency Overhead:**
    *   **`INSERT`:** Every new row inserted into `shift_audits` must also have an entry added to `idx_shift_audits_company_created`. This involves navigating the B-tree structure, potentially splitting index pages, and writing the new index entry to disk. This adds a small but measurable overhead to each insert.
    *   **`UPDATE`:** If `company_id` or `created_at` are updated (which is unlikely for an audit log, but possible for other tables), the old index entry must be marked as invalid, and a new one inserted. Even if other columns are updated, PostgreSQL's MVCC (Multi-Version Concurrency Control) often means a new row version is created, potentially leading to index updates.
    *   **`DELETE`:** Deleting a row requires marking its corresponding index entry as deleted.
    *   **Impact:** For a high-volume table like `shift_audits` (frequent shift changes), this cumulative overhead can add up. The requirement states "not introduce significant write latency overhead (e.g., more than 50ms)". A single index addition typically adds a few milliseconds to an insert, so it should stay within this budget, but it's a factor to monitor.

2.  **Disk Space Usage:** Indexes consume disk space. For a table with 100 million rows, an index on two columns (an `INT` and a `TIMESTAMP WITH TIME ZONE`) will be substantial, potentially tens of GBs. This increases storage costs and backup sizes.

3.  **Maintenance Overhead:**
    *   **`VACUUM`:** Dead tuples (from `UPDATE`s and `DELETE`s) and dead index entries need to be cleaned up by `VACUUM` (or autovacuum). More indexes mean more work for `VACUUM`.
    *   **Index Bloat:** Over time, frequent `UPDATE`s and `DELETE`s can lead to index bloat, where the index consumes more space than necessary and becomes less efficient. This might necessitate periodic `REINDEX` operations during maintenance windows.

#### What breaks first at ten times the scale

At ten times the scale (1 billion rows total, 10 million rows per company for a high-volume company), the primary bottleneck will likely shift from the `Sort` operation to **I/O contention and index size/maintenance**.

1.  **Index Size and Cache Misses:** The `idx_shift_audits_company_created` index will grow to hundreds of GBs. It will become increasingly difficult for the most frequently accessed parts of the index (e.g., for active companies) to remain in RAM (shared buffers). This will lead to more disk I/O for index lookups, even for the optimized query. While still much faster than a full table scan, the latency might creep up from tens of milliseconds to hundreds of milliseconds due to cache misses.

2.  **Write Latency:** The overhead of maintaining the index for 10x the write volume will become more pronounced. Each `INSERT` will take slightly longer, and the cumulative effect could push the write latency beyond the 50ms budget, especially during peak times.

3.  **`VACUUM` and Autovacuum Performance:** With 10x the rows and updates/deletes, `autovacuum` will have significantly more work to do on both the table and the index. If `autovacuum` cannot keep up, table and index bloat will increase, leading to slower read queries and consuming more disk space. This could manifest as increased query latency or even transaction ID wraparound issues if left unchecked.

4.  **`OFFSET` Pagination:** While the index helps, `OFFSET` pagination still has limitations at extreme scales. If a user tries to access page 10,000 (e.g., `OFFSET 1000000 LIMIT 100`), the database still has to traverse 1 million index entries before returning the desired 100. This can become slow. A more robust solution for deep pagination at this scale often involves "keyset pagination" (also known as "seek method pagination"), where you paginate based on the last `created_at` and `id` of the previous page, like `WHERE company_id = ? AND created_at < ? OR (created_at = ? AND id < ?) ORDER BY created_at DESC LIMIT 100;`. This avoids the linear scan of `OFFSET`. However, the challenge explicitly asked for `OFFSET` support, and the index is the best PostgreSQL-only solution for it.

To handle 10x scale effectively, one might consider:
*   **Partitioning:** Partitioning the `shift_audits` table by `company_id` (or `created_at` if queries are mostly time-based across all companies) could further reduce the index size per partition and improve I/O locality.
*   **Keyset Pagination:** As mentioned, switching from `OFFSET` to keyset pagination for deep dives.
*   **Read Replicas:** Offloading audit log reads to read replicas to reduce the load on the primary database.
