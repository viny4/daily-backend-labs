## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee expenses. A core feature is the ability for company administrators to view and approve expense reports. Each expense report can contain many individual expenses.

The `expense_reports` table has grown significantly over time, now containing tens of millions of records. An `expense_report` has a `status` field (e.g., `pending`, `approved`, `rejected`) and a `submission_date`. Company administrators frequently access a dashboard that displays a count of expense reports in each status, broken down by week or month, for their company. This dashboard query is becoming a performance bottleneck, taking 5-10 seconds to load for larger companies, which is unacceptable for a frequently used administrative interface.

The current query often looks like this (simplified):

```sql
SELECT
    status,
    DATE_TRUNC('week', submission_date) AS week_start,
    COUNT(*) AS report_count
FROM
    expense_reports
WHERE
    company_id = :company_id
GROUP BY
    status, week_start
ORDER BY
    week_start DESC, status;
```

This query is run for each `company_id` when an admin logs in. There are thousands of companies, and the data changes throughout the day as employees submit reports and admins approve them. The historical weekly/monthly counts for a given company change infrequently once reports are processed, but the current week's data is very active.

## Requirements

Implement a caching strategy using Redis to significantly reduce the load on the PostgreSQL database and decrease the dashboard's load time to under 500ms for these aggregate counts. The solution must account for:

1.  **Data Freshness:** While exact real-time accuracy isn't strictly necessary for historical weekly/monthly aggregates, the *current* week's data should be reasonably fresh (within 5 minutes). Older, completed periods can be staler (up to 30 minutes).
2.  **Concurrency:** Multiple administrators from the same company might access the dashboard simultaneously.
3.  **Multi-tenancy:** The caching mechanism must correctly isolate data per `company_id`.
4.  **Cache Invalidation/Eviction:** Design a strategy for when cache entries should expire or be refreshed. Assume the total number of distinct `(company_id, status, week_start)` combinations over the last year is in the hundreds of thousands, and fetching all at once is too much.

You do not need to set up a full Django/Node application. Focus on the Python/TypeScript logic that interacts with Redis and potentially a mocked database layer.

### `get_expense_report_dashboard_data` function

We'll implement a Python function `get_expense_report_dashboard_data` that orchestrates fetching data from Redis or a mocked database.

```python
import redis
import json
import datetime
from typing import List, Dict, Any, Optional
from collections import defaultdict

# --- Mock Database Layer ---
# In a real application, this would be an ORM or direct DB client.
# We'll simulate fetching data from a database.

MOCK_DB_DATA = defaultdict(list)

def _generate_mock_db_data(company_id: str):
    """Generates some mock data for a given company_id."""
    today = datetime.date.today()
    for i in range(50): # Simulate data for the last 50 weeks
        week_start = today - datetime.timedelta(weeks=i)
        week_start = week_start - datetime.timedelta(days=week_start.weekday()) # Normalize to Monday
        
        # Simulate different statuses and counts
        MOCK_DB_DATA[company_id].append({
            "status": "pending",
            "week_start": week_start.isoformat(),
            "report_count": 10 + i % 5
        })
        MOCK_DB_DATA[company_id].append({
            "status": "approved",
            "week_start": week_start.isoformat(),
            "report_count": 50 - i % 10
        })
        if i % 3 == 0: # Some weeks have rejected reports
            MOCK_DB_DATA[company_id].append({
                "status": "rejected",
                "week_start": week_start.isoformat(),
                "report_count": 2 + i % 2
            })

# Pre-populate mock data for a few companies
_generate_mock_db_data("company_alpha")
_generate_mock_db_data("company_beta")


def fetch_data_from_database(company_id: str) -> List[Dict[str, Any]]:
    """
    Simulates fetching aggregated expense report data from PostgreSQL.
    This would execute the SQL query provided in the scenario.
    """
    print(f"--- DB CALL: Fetching data for company_id: {company_id} ---")
    # Simulate a delay for database query
    import time
    time.sleep(1.5) 
    
    # Filter data for the requested company_id
    return MOCK_DB_DATA.get(company_id, [])

# --- Redis Client Setup ---
# In a real application, this would be configured via environment variables or a config file.
# For demonstration, we'll use a local Redis instance.
redis_client = redis.Redis(host='localhost', port=6379, db=0, decode_responses=True)

# --- Caching Strategy Implementation ---

def get_expense_report_dashboard_data(company_id: str) -> List[Dict[str, Any]]:
    """
    Retrieves aggregated expense report data for a company, utilizing Redis cache.
    """
    current_week_start = (datetime.date.today() - datetime.timedelta(days=datetime.date.today().weekday())).isoformat()
    
    # Attempt to fetch all relevant keys from Redis in one go
    # We'll fetch both historical and current week data.
    # For simplicity, we'll iterate through potential keys. In a real system,
    # if we knew the exact historical weeks, we could MGET specific keys.
    # However, since the dashboard might request "last N weeks", we'll fetch
    # the entire company's cached data if present.

    cache_key_prefix = f"expense_reports:company:{company_id}:aggregates:"
    
    # Try to get the entire company's aggregated data from a single cache key
    # This assumes we cache all relevant weekly aggregates for a company together.
    # Alternative: Cache each week's aggregate separately. See discussion below.
    
    # For this solution, we'll cache all historical data for a company under one key,
    # and the current week's data under a separate, more volatile key.
    
    historical_cache_key = f"{cache_key_prefix}historical"
    current_week_cache_key = f"{cache_key_prefix}current_week"

    cached_historical_data = redis_client.get(historical_cache_key)
    cached_current_week_data = redis_client.get(current_week_cache_key)

    data_from_cache = []
    if cached_historical_data:
        data_from_cache.extend(json.loads(cached_historical_data))
        print(f"--- CACHE HIT: Historical data for {company_id} ---")
    
    if cached_current_week_data:
        data_from_cache.extend(json.loads(cached_current_week_data))
        print(f"--- CACHE HIT: Current week data for {company_id} ---")

    # If we have all data (both historical and current week) from cache, return it.
    # This check is simplified: it assumes if both keys exist, we have "enough".
    # A more robust check might verify if the cached data covers the requested time range.
    if cached_historical_data and cached_current_week_data:
        return data_from_cache
    
    # If not fully cached, fetch from DB
    print(f"--- CACHE MISS: Fetching all data from DB for {company_id} ---")
    db_data = fetch_data_from_database(company_id)
    
    # Separate DB data into current week and historical
    historical_data = []
    current_week_data = []
    for item in db_data:
        if item["week_start"] == current_week_start:
            current_week_data.append(item)
        else:
            historical_data.append(item)
            
    # Cache historical data (longer TTL)
    if historical_data:
        redis_client.setex(
            historical_cache_key,
            datetime.timedelta(minutes=30), # Staler: 30 minutes TTL
            json.dumps(historical_data)
        )
        print(f"--- CACHE SET: Historical data for {company_id} with TTL 30m ---")
    
    # Cache current week data (fresher TTL)
    if current_week_data:
        redis_client.setex(
            current_week_cache_key,
            datetime.timedelta(minutes=5), # Fresher: 5 minutes TTL
            json.dumps(current_week_data)
        )
        print(f"--- CACHE SET: Current week data for {company_id} with TTL 5m ---")

    return db_data

# --- Demonstration ---
if __name__ == "__main__":

    # In this specific implementation, if *any* part of the cache is missing,

    # This is a design choice. An alternative would be to fetch only the missing part.
    # Given the scenario, fetching all data when a part is missing is simpler and safer
```

### Cache Key Generation Strategy

Our strategy uses two distinct cache keys per `company_id` to differentiate between active and historical data, allowing for different TTLs.

1.  **Historical Data Key:**
    *   **Format:** `expense_reports:company:{company_id}:aggregates:historical`
    *   **Example:** `expense_reports:company:company_alpha:aggregates:historical`
    *   **Purpose:** Stores all weekly/monthly aggregates for `company_id` *excluding* the current week. This data changes infrequently.
    *   **Value:** A JSON string representing a list of dictionaries, where each dictionary contains `status`, `week_start`, and `report_count`.

2.  **Current Week Data Key:**
    *   **Format:** `expense_reports:company:{company_id}:aggregates:current_week`
    *   **Example:** `expense_reports:company:company_alpha:aggregates:current_week`
    *   **Purpose:** Stores the weekly aggregates for the *current* week for `company_id`. This data is highly active.
    *   **Value:** A JSON string representing a list of dictionaries, similar to the historical data, but only for the current week.

**Why two keys instead of one per `(company_id, status, week_start)` combination?**

*   **Reduced Network Overhead:** Fetching all relevant data for a company in one or two `GET` operations (or `MGET` if we knew all keys upfront) is more efficient than potentially hundreds of individual `GET` requests for each `(status, week_start)` combination. The dashboard displays *all* counts for a company, so fetching them together makes sense.
*   **Simplified Logic:** It simplifies the application logic for cache population and retrieval. We fetch all data from the DB once, split it, and cache it.
*   **Atomic Updates:** When the data for a company is refreshed from the database, we can update its entire historical or current week cache entry atomically using `SETEX`. This avoids a scenario where a client might see a mix of old and new data for different weeks if individual week keys were updated asynchronously.

**Trade-offs of this key strategy:**

*   **Larger Cache Values:** Storing all historical data for a company in a single key means the value can be large. Redis is optimized for smaller key-value pairs, but for hundreds of thousands of entries (as stated in the scenario), this is acceptable. If a single company had millions of historical weekly aggregates, we might reconsider.
*   **Less Granular Invalidation:** If only one historical week's data changes (e.g., an old report was retroactively approved), we invalidate and re-fetch *all* historical data for that company. Given the requirement that historical data changes infrequently, this is an acceptable trade-off for simplicity and reduced database load.

### Cache Invalidation/Eviction Policy

Our strategy employs a **Time-To-Live (TTL)**-based eviction policy, differentiated by data freshness requirements:

1.  **Historical Data:**
    *   **TTL:** 30 minutes.
    *   **Rationale:** The scenario states that "historical weekly/monthly counts for a given company change infrequently once reports are processed." A 30-minute staleness is acceptable for these older, completed periods. This significantly reduces database load for data that rarely changes.
    *   **Mechanism:** When `get_expense_report_dashboard_data` is called and the `historical_cache_key` is missing or expired, the system fetches *all* data from the database, separates historical data, and stores it in Redis with a 30-minute `EXPIRE` or `SETEX` command.

2.  **Current Week Data:**
    *   **TTL:** 5 minutes.
    *   **Rationale:** The "current week's data is very active" and needs to be "reasonably fresh (within 5 minutes)." A shorter TTL ensures that administrators see recent changes quickly without hammering the database on every request.
    *   **Mechanism:** Similar to historical data, when `current_week_cache_key` is missing or expired, the system fetches *all* data from the database, separates current week data, and stores it in Redis with a 5-minute `EXPIRE` or `SETEX` command.

**Combined Invalidation Logic:**

*   When `get_expense_report_dashboard_data` is called:
    *   It first checks for both `historical_cache_key` and `current_week_cache_key`.
    *   If *both* are present in the cache, it returns the combined cached data immediately (cache hit).
    *   If *either* key is missing or expired, it triggers a full database fetch for *all* data for that `company_id`. This ensures that even if only the current week's data has expired, we still get a consistent, up-to-date view of all data.
    *   After fetching from the database, the data is split, and both historical and current week portions are re-cached with their respective TTLs.

**Why not use explicit invalidation (e.g., `DEL` on data change)?**

*   **Complexity:** Explicit invalidation requires integrating cache invalidation logic into every write operation (e.g., when an expense report status changes, or a new report is submitted). This adds significant complexity, especially in a distributed system, and can lead to race conditions or missed invalidations.
*   **Granularity:** For aggregate counts, a single report change might affect multiple `(status, week_start)` buckets. Determining exactly which cache keys to invalidate for a specific change can be complex.
*   **Acceptable Staleness:** The requirements explicitly state that "exact real-time accuracy isn't strictly necessary" and provide acceptable staleness windows. This makes TTL-based caching a perfect fit, as it's simpler and more robust.

**Eviction (Redis's perspective):**

Redis will automatically evict keys when their TTL expires. If Redis runs out of memory, it will use its configured eviction policy (e.g., LRU, LFU) to remove keys without a TTL or keys with a TTL that haven't expired yet, to make space for new data. Given "hundreds of thousands" of combinations, the total cache size should be manageable, and TTL-based eviction will be the primary mechanism.

### Going Further

#### Trade-offs of the chosen caching strategy regarding consistency versus availability

Our chosen strategy prioritizes **availability** and **performance** over strong **consistency**.

*   **Consistency:** We operate under an **eventual consistency** model. Data in the cache is not guaranteed to be perfectly up-to-the-second accurate. There's a window of staleness (5 minutes for current week, 30 minutes for historical) during which the cache might serve outdated information. This is an explicit trade-off accepted by the requirement that "exact real-time accuracy isn't strictly necessary."
*   **Availability:** By serving data from Redis, we significantly reduce the load on the PostgreSQL database. If the database experiences a temporary slowdown or outage, the application can continue serving cached (though potentially stale) data, improving the perceived availability of the dashboard. This is a common pattern for read-heavy workloads where some staleness is acceptable.
*   **Performance:** The primary goal of reducing dashboard load time to under 500ms is achieved by serving most requests directly from Redis, which is orders of magnitude faster than a complex SQL query on a large table.

**What breaks first at ten times the scale?**

At ten times the scale, with potentially tens of thousands of companies and hundreds of millions of expense reports, the following aspects would likely break or become problematic first:

1.  **Database Load During Cache Misses/Refreshes:** While Redis offloads most reads, when a cache entry expires or is missing, the database still needs to serve the full query. If many cache entries expire simultaneously (e.g., at the 5-minute or 30-minute mark for many companies) or if there's a sudden surge of requests for uncached companies, the database could still be overwhelmed. The current 1.5-second simulated DB query time would become a major bottleneck.
2.  **Redis Memory Usage:** Storing all historical data for a company in a single key, while efficient for network calls, could lead to large Redis values. With tens of thousands of companies, the total memory footprint of these large JSON blobs could become substantial, potentially exceeding the available RAM on the Redis instance, leading to aggressive eviction or requiring larger Redis instances.
3.  **Serialization/Deserialization Overhead:** `json.dumps` and `json.loads` can become CPU-intensive for very large data structures. While Python's `json` module is optimized, processing hundreds of kilobytes or megabytes of JSON for each request could add noticeable latency at scale.
4.  **Network Latency for Large Cache Values:** Transferring very large JSON strings between the application server and Redis can consume network bandwidth and add latency, even if Redis itself is fast.

#### Modifying the approach for "all data fresh within 30 seconds"

If the business requirement changed to "all data, including historical data, needed to be 'fresh' within 30 seconds of a status change or new submission," our current TTL-based approach would be insufficient. We would need to implement a **write-through or write-behind caching strategy with explicit invalidation**.

Here's how the approach would need to be modified:

1.  **Reduced TTLs (as a fallback):**
    *   While explicit invalidation is primary, very short TTLs (e.g., 30 seconds) could be maintained as a safety net to eventually correct any missed invalidations.

2.  **Explicit Cache Invalidation on Writes:**
    *   **Identify affected keys:** Whenever an expense report's `status` changes or a new report is submitted, we must identify all `company_id`s and `week_start` periods affected by this change.
    *   **Invalidation Logic:**
        *   When a report's status changes or a new report is submitted for `company_id` and `submission_date`:
            1.  Calculate the `week_start` for that `submission_date`.
            2.  Invalidate the `current_week_cache_key` for `company_id` if `week_start` is the current week.
            3.  Invalidate the `historical_cache_key` for `company_id` if `week_start` is a historical week.
            4.  This would involve issuing `DEL expense_reports:company:{company_id}:aggregates:current_week` or `DEL expense_reports:company:{company_id}:aggregates:historical` commands to Redis.
    *   **Integration Points:** This invalidation logic would need to be integrated into:
        *   The service layer responsible for updating expense report statuses.
        *   The service layer responsible for creating new expense reports.
        *   Potentially, a background job that processes bulk updates.

3.  **Asynchronous Cache Refresh (Write-Behind/Event-Driven):**
    *   Instead of waiting for a read to trigger a DB fetch (read-through), we could proactively refresh the cache.
    *   **Message Queue:** Upon a data change (status update, new report), publish an event to a message queue (e.g., Kafka, RabbitMQ).
    *   **Cache Worker:** A dedicated worker service would consume these events. For each event, it would:
        1.  Identify the `company_id` and `week_start` affected.
        2.  Re-run the aggregate SQL query for that specific `company_id` (or potentially just the affected `week_start` if the caching strategy was more granular).
        3.  Update the corresponding cache keys in Redis with the fresh data.
    *   **Benefits:** This decouples the write operation from the cache update, keeping write latency low. It also ensures the cache is proactively updated, improving read performance for subsequent requests.
    *   **Challenges:** Adds significant operational complexity (managing message queues, workers, ensuring exactly-once processing).

4.  **More Granular Caching (Optional but beneficial):**
    *   Instead of caching all historical data for a company in one key, we might cache each `(company_id, week_start)` combination separately.
    *   **Key Format:** `expense_reports:company:{company_id}:week:{week_start_isoformat}`
    *   **Value:** JSON array of `{status, report_count}` for that specific week.
    *   **Benefits:** Allows for more precise invalidation and refresh. If only one week's data changes, only that specific week's key needs to be invalidated/refreshed.
    *   **Challenges:** Increases the number of Redis keys, potentially leading to more network round trips if fetching a range of weeks (though `MGET` can mitigate this). Requires more complex logic to combine data from multiple keys for a dashboard view.

**Trade-offs of the modified approach (30-second freshness):**

*   **Increased Complexity:** Moving from simple TTL-based caching to explicit invalidation and asynchronous refresh significantly increases system complexity, requiring message queues, worker services, and robust error handling.
*   **Higher Operational Overhead:** More components to monitor and maintain.
*   **Potential for Cache Invalidation Bugs:** Incorrect invalidation logic can lead to serving stale data indefinitely or excessive database hits.
*   **Database Load for Refreshes:** While reads are offloaded, the database still needs to handle the load from proactive cache refreshes. If many events occur simultaneously, this could still strain the DB.
*   **Stronger Consistency:** Achieves closer to real-time consistency (within 30 seconds) at the cost of the above complexities.

For "millions of reports," the asynchronous cache refresh with a message queue would be almost mandatory to prevent write operations from becoming bottlenecks due to synchronous cache updates or invalidations. The database would still need to be highly optimized for the aggregate queries that feed the cache.
