## Scenario

Your team maintains a core service for a popular B2B SaaS platform that manages complex project portfolios for thousands of enterprise clients. A central feature is the "Project Activity Feed," which displays a chronological list of significant events related to a project (e.g., "User X created task Y," "User Z commented on task A," "Project status changed to 'Completed'").

Currently, all activity events across all projects and clients are stored in a single `project_activities` PostgreSQL table. This table has grown significantly and now contains over **500 million rows**, with a high write throughput of **5,000-10,000 events per second** during peak hours. Each event includes `project_id`, `user_id`, `event_type`, `payload` (JSONB), and `created_at`.

The Project Activity Feed is a frequently accessed feature. Users often load the latest activities for a specific project, but also filter by date range, user, or event type. The query to retrieve the last 50 activities for a large project now regularly takes **3-5 seconds**, causing a noticeable delay and poor user experience. Furthermore, some analytical queries that aggregate activity data across multiple projects for a single client are timing out.

## Requirements

Design a system improvement to optimize the performance of the Project Activity Feed and related analytical queries. The solution must support:

*   **Low Latency Reads:** Retrieving the latest 50 activities for a given `project_id` must consistently complete within **100ms**.
*   **High Write Throughput:** The system must continue to handle the current write load of 5,000-10,000 events per second without significant degradation.
*   **Data Retention:** All historical activity data must remain queryable for at least 1 year for audit and compliance purposes, even if slowly.
*   **Multi-tenancy:** The platform serves thousands of independent enterprise clients, each with potentially many projects. Solutions should consider how to isolate or scale for individual client needs.
*   **Durability and Consistency:** No activity events should be lost, and the order of events for a given project must be maintained.
*   **Cost-effectiveness:** While performance is paramount, the solution should avoid excessively expensive infrastructure if more pragmatic options exist.

## Deliverables

1.  A high-level architectural diagram (text-based or conceptual components) showing the proposed changes to the system.
2.  A description of the key technologies and services you would use, justifying your choices based on the requirements.
3.  An explanation of how the system would handle reads for the Project Activity Feed, specifically addressing the 100ms latency requirement.
4.  An explanation of how the system would handle writes, ensuring high throughput and data durability.

### 2. Key technologies and services

1.  **PostgreSQL (Main Database):**
    *   **Role:** The ultimate source of truth for all activity events, providing durability, strong consistency, and long-term data retention for audit and analytical queries. It will store the full 1-year history.
    *   **Justification:** Already in use, familiar to the team. Its robust transactional capabilities are essential for ensuring no data loss. While it struggles with the current read load, it's suitable for historical/analytical queries that don't have strict latency requirements, especially after offloading the hot path. We will implement partitioning to manage table size effectively.
2.  **Kafka (Event Bus):**
    *   **Role:** A high-throughput, fault-tolerant distributed streaming platform. It acts as an intermediary for all activity writes, decoupling the API service from the persistence layer and enabling asynchronous processing.
    *   **Justification:** Handles the 5,000-10,000 events/sec write load with ease. Provides durability (replicated logs) and guarantees message order within a partition, which is crucial for maintaining event sequence per project. Its publish-subscribe model allows multiple consumers (e.g., historical storage, real-time feed processing) to process events independently.
3.  **Activity Ingester Service:**
    *   **Role:** A dedicated microservice responsible for consuming events from Kafka and writing them to the PostgreSQL main database.
    *   **Justification:** Decouples the write path from the API. It can batch writes to PostgreSQL, significantly improving write efficiency and reducing load on the database compared to individual inserts. It can handle retries and error logging for persistence failures.
4.  **Kafka Streams / Apache Flink (Stream Processing):**
    *   **Role:** A real-time stream processing framework to consume events from Kafka, perform light transformations/denormalization if needed, and populate the low-latency read store.
    *   **Justification:** Processes events in near real-time, enabling the activity feed to be updated quickly. Can handle high event rates and complex processing logic (though for this use case, it's relatively simple: filter, transform, push). Kafka Streams is a good choice for teams already using Kafka due to its tight integration. Flink offers more advanced stateful processing capabilities if future requirements demand it.
5.  **Redis (Sorted Sets):**
    *   **Role:** A high-performance in-memory data store used to serve the Project Activity Feed for low-latency reads.
    *   **Justification:** Sorted Sets are ideal for this use case. Each `project_id` can map to a Redis Sorted Set key. Events are stored with their `created_at` timestamp as the score, allowing efficient retrieval of the latest N events (e.g., `ZREVRANGE`). Redis is extremely fast (sub-millisecond latency for reads) and can handle high read QPS. It's a cache, but a highly durable one if configured with AOF persistence. It will store a limited window of recent activity (e.g., the last few thousand events per project, or events from the last 7-30 days).

### 3. How the system handles reads for the Project Activity Feed

The Project Activity Feed (latest 50 activities for a `project_id`) will be served primarily from **Redis Sorted Sets**.

1.  **Write Path to Redis:**
    *   When an activity event is produced, it's published to Kafka.
    *   The Kafka Streams/Flink application consumes this event.
    *   For each event, it constructs a unique member string (e.g., a JSON representation of the event or a unique ID + event data) and uses the `created_at` timestamp as the score.
    *   It then executes a `ZADD` command to add this event to the sorted set corresponding to its `project_id`.
    *   To manage memory and ensure only recent data is kept, the stream processor can also periodically (or after each `ZADD`) trim the sorted set using `ZREMRANGEBYRANK 0 -N` to keep only the latest `N` events, or `ZREMRANGEBYSCORE -inf (current_timestamp - X_days)` to keep events within a time window. This ensures Redis doesn't grow indefinitely.

    Example Redis command sequence for an event:
    ```
    # Event: { project_id: "proj123", user_id: "userX", event_type: "created_task", created_at: 1678886400, payload: {...} }
    # Store the full event JSON as the member for simplicity, or just its ID and fetch details from PostgreSQL if needed.
    ZADD project_activity:proj123 1678886400 '{"id":"event_uuid_1", "user_id":"userX", "type":"created_task", ...}'
    # After adding, trim to keep only the latest 1000 events for this project
    ZREMRANGEBYRANK project_activity:proj123 0 -1001
    ```

2.  **Read Path from Redis:**
    *   When a user requests the Project Activity Feed for `project_id=X`, the API service queries Redis.
    *   It uses the `ZREVRANGE` command to retrieve the latest 50 events for that `project_id`. This command is extremely fast, typically completing in sub-milliseconds.
    *   The API service then deserializes the event data (if stored as JSON strings) and returns it to the client.

    Example Redis command for reading:
    ```
    ZREVRANGE project_activity:proj123 0 49
    ```
    This retrieves the 50 most recent events (highest scores/timestamps) for `project_id=proj123`.

3.  **Handling Filters (Date Range, User, Event Type):**
    *   **Latest N events:** Directly from Redis using `ZREVRANGE`.
    *   **Filtering by Date Range:** For *recent* date ranges (within the Redis retention window), this can be done by fetching a larger set from Redis and filtering in the application layer, or by using `ZREVRANGEBYSCORE` if the range is purely time-based. However, Redis Sorted Sets are not optimized for arbitrary multi-attribute filtering.
    *   **Filtering by User/Event Type:** This is not efficient directly in Redis. For these types of queries, especially those spanning longer historical periods or requiring complex aggregations, the API service would fall back to querying the **PostgreSQL main database**.
    *   **PostgreSQL for Analytical/Historical Queries:** The PostgreSQL database, containing all historical data, will be optimized for these queries through:
        *   **Partitioning:** The `project_activities` table will be partitioned by `client_id` (if possible, or `project_id` if clients are too disparate) and then by `created_at` (e.g., monthly or quarterly partitions). This significantly improves query performance by allowing PostgreSQL to scan only relevant partitions.
        *   **Indexing:** Appropriate indexes on `(project_id, created_at DESC)`, `(project_id, user_id, created_at DESC)`, `(project_id, event_type, created_at DESC)`, and `(client_id, created_at DESC)` will be crucial.
        *   **Read Replicas:** For heavily used analytical queries, read replicas can offload the primary database.

This dual-storage approach (Redis for hot reads, PostgreSQL for cold/analytical reads) ensures the 100ms latency requirement for the primary activity feed while maintaining full historical data and supporting complex queries.

### 4. How the system handles writes

The system employs an asynchronous, event-driven write model to achieve high throughput and durability.

1.  **API Service (Initial Write):**
    *   When the API service receives an activity event (e.g., via an HTTP POST request), it performs basic validation.
    *   It then immediately publishes the event to a Kafka topic (e.g., `project_activity`). The API service does *not* wait for the event to be persisted in PostgreSQL or Redis.
    *   It returns a success response to the client as soon as the event is successfully acknowledged by Kafka. Kafka's high durability (due to replication) ensures that once Kafka acknowledges the message, it's highly unlikely to be lost.

    Example API service logic (pseudo-code):
    ```python
    def handle_activity_event(request_body):
        event = parse_event(request_body)
        # Add metadata like unique event ID, timestamp
        event['id'] = generate_uuid()
        event['created_at'] = int(time.time()) # Unix timestamp

        try:
            producer.send('project_activity', key=event['project_id'].encode('utf-8'), value=json.dumps(event).encode('utf-8'))
            producer.flush() # Ensure message is sent to Kafka broker
            return {"status": "success", "message": "Event accepted"}, 202
        except Exception as e:
            logger.error(f"Failed to send event to Kafka: {e}")
            return {"status": "error", "message": "Internal server error"}, 500
    ```

2.  **Kafka (Event Bus):**
    *   Kafka acts as a highly scalable, durable buffer. Events are partitioned by `project_id` (or `client_id` if a client generates a huge volume) to ensure ordered processing for events within the same project/client.
    *   Kafka's replication (e.g., 3 replicas) ensures durability even if a broker fails.

3.  **Activity Ingester Service (Asynchronous Persistence to PostgreSQL):**
    *   This service continuously consumes events from the `project_activity` Kafka topic.
    *   It batches events (e.g., 1,000 events or every 1 second, whichever comes first) to optimize writes to PostgreSQL. Batching significantly reduces the overhead of individual transactions and network round trips.
    *   It inserts these batches into the `project_activities` PostgreSQL table.
    *   Error handling and retry mechanisms are implemented to ensure eventual consistency and prevent data loss if PostgreSQL is temporarily unavailable. Dead-letter queues (DLQs) can be used for events that consistently fail to process.

4.  **Kafka Streams / Flink (Asynchronous Persistence to Redis):**
    *   As described in the read section, this stream processor also consumes from the `project_activity` Kafka topic.
    *   It processes events in real-time, updating the Redis Sorted Sets for the Project Activity Feed. This ensures that the feed is near real-time.

**Durability and Consistency:**
*   **Durability:** Events are durable once acknowledged by Kafka (due to replication). The Activity Ingester ensures eventual durability in PostgreSQL. Redis can also be configured for persistence (AOF/RDB) for an additional layer of durability, though its primary role is a fast cache.
*   **Consistency:** For a given `project_id`, event order is maintained because Kafka partitions ensure messages with the same key go to the same partition, and consumers process messages within a partition in order. Both the Ingester and the Stream Processor will see events for a specific project in the correct sequence. The "eventual consistency" model is acceptable here, as users expect the activity feed to be *eventually* updated, not strictly synchronously.

**Trade-offs:**
*   **Eventual Consistency:** The primary trade-off is that the activity feed (Redis) and the historical database (PostgreSQL) are eventually consistent. There might be a slight delay (milliseconds to a few seconds) between an event being published and it appearing in the feed or being persisted in PostgreSQL. This is generally acceptable for activity feeds.
*   **Increased Complexity:** The system introduces new components (Kafka, Stream Processor, Ingester Service, Redis), increasing operational complexity compared to a monolithic PostgreSQL setup.
*   **Data Duplication:** Data is duplicated across Kafka logs, Redis, and PostgreSQL. This is a common pattern in high-performance systems to optimize for different access patterns.

### Going further

Gracefully handling a specific enterprise client generating an order of magnitude more activity events than all other clients combined (a "noisy neighbor" problem) requires mechanisms for isolation and dynamic scaling.

Here's how the proposed solution would handle it:

1.  **Kafka Partitioning and Consumer Groups:**
    *   **Current State:** Events are likely partitioned by `project_id`. If one client has many projects, or one project is extremely active, it could still concentrate load.
    *   **Improvement:** If `client_id` is a more appropriate granularity for isolation, we would partition the Kafka topic by `client_id`. This ensures that all events for a single client are processed by a specific subset of Kafka brokers and consumer instances.
    *   **Dynamic Scaling of Consumers:** The `Activity Ingester` and `Kafka Streams/Flink` applications are consumer groups. Kafka automatically distributes partitions among consumers in a group. If a client becomes extremely active, its partitions will be assigned to specific consumer instances. We can then **horizontally scale out the consumer group** (add more instances of the Ingester and Stream Processor). Kafka will rebalance partitions, allowing more consumer instances to process the high-volume client's data in parallel, without impacting other clients' partitions.

2.  **Dedicated Kafka Topics (Optional, for Extreme Cases):**
    *   For an *extremely* noisy client, we could consider creating a **dedicated Kafka topic** (e.g., `project_activity_client_XYZ`) just for that client's events.
    *   **Benefit:** This provides complete isolation. The high-volume client's traffic would not contend for resources (broker I/O, network bandwidth, consumer group processing capacity) with other clients on the main `project_activity` topic.
    *   **Drawback:** Increases operational overhead (managing more topics, potentially more consumer groups). The API service would need logic to route events to the correct topic. This is usually reserved for clients that are *orders of magnitude* larger than the next largest, not just "a bit bigger."

3.  **Resource Isolation in Downstream Systems:**
    *   **PostgreSQL:**
        *   **Partitioning:** By partitioning the `project_activities` table by `client_id` (and then `created_at`), queries for other clients will not have to scan the massive partitions belonging to the noisy client. This is a critical isolation mechanism for analytical queries.
        *   **Read Replicas:** If the noisy client generates a lot of *read* traffic for its historical data, dedicated read replicas could be provisioned for its partitions, or a pool of read replicas could be scaled up.
        *   **Resource Pools (e.g., PgBouncer):** Using connection poolers like PgBouncer, we can configure different connection pools with varying resource limits (e.g., max connections, query timeouts) for different client types or even specific clients, providing some level of QoS.
    *   **Redis:**
        *   **Sharding/Clustering:** Redis Cluster automatically shards data across multiple nodes. If a single client's `project_id` keys become too numerous or too large, they will naturally be distributed across the cluster.
        *   **Dedicated Redis Instances/Clusters:** For an extremely noisy client, we could provision a **dedicated Redis instance or cluster** specifically for their activity feeds. This provides absolute isolation from other clients, preventing their high write/read load from impacting the performance of other clients' feeds. This is a more expensive option but guarantees performance.

4.  **Rate Limiting and Backpressure:**
    *   **API Layer:** Implement client-specific rate limiting at the API gateway or service level. This prevents a single client from overwhelming the entire system by simply sending too many requests. While it might impact the noisy client's ability to submit events, it protects the overall system.
    *   **Kafka Backpressure:** Kafka itself provides natural backpressure. If downstream consumers (Ingester, Stream Processor) cannot keep up, Kafka will buffer messages. If the buffer fills up (or retention limits are hit), producers might eventually block or fail. This signals that more consumer resources are needed.

**Summary of Approach for Noisy Neighbor:**

The primary strategy would be to leverage **Kafka's partitioning and consumer group scaling** to handle the increased write throughput. For read performance, **PostgreSQL partitioning by `client_id`** and **Redis Cluster's sharding** would naturally distribute the load. In extreme cases, **dedicated Kafka topics or Redis instances** for the problematic client would provide complete resource isolation, albeit at a higher operational and financial cost. The key is to identify the bottleneck (write, read, specific component) and apply targeted scaling and isolation.
