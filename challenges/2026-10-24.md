## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee expenses. A critical component is the expense approval workflow. When an employee submits an expense report, it enters an approval queue. Each report needs to be approved by a manager, then potentially by a department head, and finally by finance. This workflow can involve up to three sequential approval steps.

The `expense_reports` table now contains tens of millions of records, and the `approval_steps` table (linking reports to their current approval status and approver) has grown proportionally. When a manager logs in, they need to see a list of *all* expense reports awaiting their approval, across all departments they manage. This list needs to be quickly filterable and sortable (e.g., by submission date, amount, or employee name).

Currently, fetching this list for a manager with hundreds or thousands of pending approvals is taking unacceptably long (over 5 seconds), causing UI lag and frustration. The query often involves joining `expense_reports` with `approval_steps`, `employees`, and potentially `departments` tables.

*   **Complex filtering/sorting:** The resulting list needs to support efficient filtering (e.g., by specific employee, date range, minimum/maximum amount) and sorting by multiple criteria.
*   **Latency budget:** The entire operation (fetching and preparing the initial list of pending reports for a manager) must complete within 500ms.
*   **Concurrency:** Multiple managers will be querying their pending approvals concurrently.

## Worked answer

### 1. Data Structures for Efficient Querying

The core problem is that a simple join-based query on `expense_reports` and `approval_steps` becomes inefficient due to the sheer volume of data and the need for complex filtering and sorting. The database engine has to scan large portions of these tables, perform joins, and then filter, which is slow.

To optimize this, we need a data structure that pre-computes or pre-indexes the relationship between managers and their pending reports, allowing for direct, fast access. We're essentially building a specialized index or a materialized view of the pending reports for each manager.

I would consider two primary approaches:

1.  **Specialized Index Table (Chosen Approach):** A dedicated table designed specifically for manager-pending-report lookups.
2.  **In-memory Cache/Search Index (e.g., Elasticsearch):** While powerful, this adds significant operational complexity and potential consistency challenges for a core business workflow. It's a good "going further" option but not my primary choice for a first-pass optimization within a relational database context, especially given the strict consistency requirements of financial data.

**Chosen Approach: Specialized Index Table**

A new table, let's call it `manager_pending_reports`, would serve as a highly optimized index. This table would store denormalized, pre-filtered information about each expense report awaiting a specific manager's approval.

**Schema for `manager_pending_reports`:**

```sql
CREATE TABLE manager_pending_reports (
    manager_id UUID NOT NULL,
    expense_report_id UUID NOT NULL,
    tenant_id UUID NOT NULL, -- For multi-tenancy partitioning
    submission_date TIMESTAMP WITH TIME ZONE NOT NULL,
    amount NUMERIC(19, 4) NOT NULL,
    currency TEXT NOT NULL,
    employee_id UUID NOT NULL,
    employee_name TEXT NOT NULL, -- Denormalized for quick display
    report_title TEXT NOT NULL,  -- Denormalized for quick display
    current_approval_step_order INT NOT NULL, -- e.g., 1 for manager, 2 for department head
    PRIMARY KEY (manager_id, expense_report_id), -- Composite primary key for uniqueness and efficient lookup
    -- Covering index for common queries:
    INDEX idx_manager_pending_reports_manager_id_submission_date (manager_id, tenant_id, submission_date DESC, expense_report_id),
    INDEX idx_manager_pending_reports_manager_id_amount (manager_id, tenant_id, amount DESC, expense_report_id),
    INDEX idx_manager_pending_reports_manager_id_employee_name (manager_id, tenant_id, employee_name ASC, expense_report_id),
    -- Foreign keys for data integrity (optional, but good practice):
    FOREIGN KEY (manager_id) REFERENCES employees(id),
    FOREIGN KEY (expense_report_id) REFERENCES expense_reports(id),
    FOREIGN KEY (employee_id) REFERENCES employees(id),
    FOREIGN KEY (tenant_id) REFERENCES tenants(id)
);
```

**Why this is superior to a simple join-based query:**

1.  **Pre-filtered Data:** This table *only* contains reports awaiting approval by a specific manager. The expensive filtering logic (joining `approval_steps` to find the *current* step, checking the `approver_id`, and ensuring it's `pending`) is performed *once* when the report enters this state, not on every read.
2.  **Denormalization for Reads:** Key display fields like `employee_name` and `report_title` are denormalized into this table. This eliminates the need for joins to `employees` or `expense_reports` tables during the common read path, significantly reducing query time.
3.  **Optimized Indexing:** The composite primary key `(manager_id, expense_report_id)` ensures extremely fast lookups for a specific report for a manager. More importantly, the additional covering indexes (`idx_manager_pending_reports_manager_id_submission_date`, etc.) are designed to support the required filtering and sorting directly. When a manager logs in, the query can use an index scan directly on `manager_id`, then efficiently sort and filter within that manager's pending reports without touching the large base tables.
4.  **Reduced I/O:** Queries against `manager_pending_reports` will typically read fewer pages from disk compared to queries involving multiple large tables, as the data is compact and tailored for this specific use case.
5.  **Scalability for Multi-tenancy:** Including `tenant_id` in the indexes allows for efficient partitioning and ensures that queries for one tenant/manager don't interfere with others, even if the overall table is large.

### 2. Key Operations and Time Complexity

This section outlines how the `manager_pending_reports` table handles the core operations.

*   **`N`**: Number of expense reports in the system.
*   **`M`**: Number of approval steps.
*   **`K`**: Number of pending reports for a specific manager.
*   **`P`**: Number of managers.

#### a. Adding a New Pending Report for a Manager

This occurs when an employee submits a report, and it enters the first approval step, or when a report moves from one approval step to the next, making it pending for a new manager.

**Algorithm:**

1.  When an `expense_report` is submitted or an `approval_step` is completed, determine the `next_approver_id` and the `expense_report_id`.
2.  Fetch necessary denormalized data (`submission_date`, `amount`, `employee_id`, `employee_name`, `report_title`, `current_approval_step_order`) from `expense_reports` and `employees` tables.
3.  Insert a new record into `manager_pending_reports`.

**Pseudo-code (simplified):**

```sql
-- Assuming a trigger or service logic detects a new pending state
INSERT INTO manager_pending_reports (
    manager_id, expense_report_id, tenant_id, submission_date, amount, currency,
    employee_id, employee_name, report_title, current_approval_step_order
)
SELECT
    as.approver_id AS manager_id,
    er.id AS expense_report_id,
    er.tenant_id,
    er.submission_date,
    er.amount,
    er.currency,
    e.id AS employee_id,
    e.name AS employee_name,
    er.title AS report_title,
    as.step_order AS current_approval_step_order
FROM
    expense_reports er
JOIN
    approval_steps as ON er.id = as.expense_report_id
JOIN
    employees e ON er.employee_id = e.id
WHERE
    er.id = :new_expense_report_id_or_updated_report_id
    AND as.status = 'PENDING'
    AND as.approver_id IS NOT NULL
    AND as.is_current_step = TRUE; -- Assuming a flag for the active approval step
```

**Time Complexity:**
*   **Database write:** O(log K) for index updates on `manager_pending_reports`.
*   **Source data read (for denormalization):** O(1) if indexed by `expense_report_id`.
*   **Overall:** Dominated by the database write, typically very fast.

#### b. Marking a Report as Approved (or Rejected)

This means the report is no longer pending for the current manager.

**Algorithm:**

1.  Update the `approval_steps` table to reflect the new status (e.g., 'APPROVED', 'REJECTED').
2.  If the report is fully approved/rejected or moves to a new approver, delete the corresponding entry from `manager_pending_reports`.
3.  If it moves to a *new* manager, perform an "Add" operation for the new manager.

**Pseudo-code (simplified):**

```sql
-- When an approval step is completed for a report
DELETE FROM manager_pending_reports
WHERE manager_id = :current_manager_id
  AND expense_report_id = :approved_expense_report_id;

-- (If the report moves to a new approver, an INSERT operation for the new approver would follow)
```

**Time Complexity:**
*   **Database write:** O(log K) for index updates on `manager_pending_reports`.
*   **Overall:** Very fast, as it's a direct delete by primary key.

#### c. Querying for a Manager's Pending Reports

This is the critical read operation.

**Algorithm:**

1.  Query `manager_pending_reports` using `manager_id` and `tenant_id`.
2.  Apply additional filters (e.g., `submission_date` range, `amount` range, `employee_name` LIKE).
3.  Apply sorting (e.g., `submission_date DESC`, `amount DESC`).
4.  Apply pagination (LIMIT/OFFSET).

**Pseudo-code (high-level):**

```sql
SELECT
    expense_report_id,
    submission_date,
    amount,
    currency,
    employee_id,
    employee_name,
    report_title,
    current_approval_step_order
FROM
    manager_pending_reports
WHERE
    manager_id = :manager_id
    AND tenant_id = :tenant_id
    -- Optional filters:
    AND submission_date BETWEEN :start_date AND :end_date
    AND amount >= :min_amount AND amount <= :max_amount
    AND employee_name ILIKE :employee_name_filter
ORDER BY
    CASE WHEN :sort_by = 'submission_date' THEN submission_date END DESC,
    CASE WHEN :sort_by = 'amount' THEN amount END DESC,
    CASE WHEN :sort_by = 'employee_name' THEN employee_name END ASC
LIMIT :page_size OFFSET :offset;
```

**Time Complexity:**
*   **Index scan:** O(log P + K_filtered) where `K_filtered` is the number of reports matching the `manager_id` and other filters. The `manager_id` part of the index allows for a very fast seek.
*   **Sorting:** If the `ORDER BY` clause matches one of the covering indexes (e.g., `submission_date DESC`), it's effectively O(1) for the already sorted data. If it requires a different sort, it's O(K_filtered log K_filtered) in the worst case, but often much faster if the data fits in memory.
*   **Overall:** Extremely efficient. For a manager with `K` pending reports, the query performance is largely independent of `N` (total reports) and `M` (total approval steps). It scales with `K`, which is typically much smaller than `N`. The covering indexes ensure that the database can satisfy the query directly from the index, minimizing table reads.

### Going Further

#### Trade-offs of Maintaining `manager_pending_reports`

1.  **Write Amplification:**
    *   **Description:** Every time an expense report changes its approval status or moves to a new approver, it results in at least one `DELETE` and potentially one `INSERT` operation on `manager_pending_reports`, in addition to the updates on the primary `expense_reports` and `approval_steps` tables. This increases the total number of write operations.
    *   **Impact:** Higher CPU and I/O load on the database during write-heavy periods (e.g., peak submission times, mass approvals). This can lead to increased transaction latency for approval actions.
    *   **Mitigation:** Batching updates where possible (e.g., for mass approvals), using efficient database indexing, and ensuring the database server is adequately provisioned for write throughput.

2.  **Memory Footprint / Storage Cost:**
    *   **Description:** `manager_pending_reports` is a denormalized table, duplicating some data (like `employee_name`, `report_title`, `amount`, `submission_date`) that already exists in `expense_reports` and `employees`. This increases the overall storage footprint of the database.
    *   **Impact:** Higher disk usage, potentially more memory needed for caching indexes and data blocks.
    *   **Mitigation:** Carefully select which fields to denormalize – only those frequently needed for display and filtering. Avoid denormalizing large text fields or binary data. The chosen fields are relatively small.

3.  **Consistency Management Overhead:**
    *   **Description:** The `manager_pending_reports` table is a derived data structure. It must be kept in sync with the primary source of truth (`expense_reports`, `approval_steps`). Any discrepancy leads to stale or incorrect data being shown to managers.
    *   **Impact:** Requires robust mechanisms (e.g., database triggers, event-driven updates, transactional consistency) to ensure atomicity and consistency. This adds complexity to the application logic and potential points of failure.
    *   **Mitigation:** See the "Consistency Issues" section below.

4.  **Schema Evolution Complexity:**
    *   **Description:** If new fields are added to `expense_reports` that are deemed critical for manager display, `manager_pending_reports` might need to be altered and backfilled.
    *   **Impact:** Schema changes become more involved, potentially requiring downtime or complex migration strategies.
    *   **Mitigation:** Design the denormalized table with foresight, including fields that are likely to be needed. Use a robust schema migration tool.

#### What breaks first at ten times the scale?

At ten times the scale (hundreds of millions of expense reports, millions of pending reports, thousands of concurrent managers), the primary bottleneck will likely shift from simple read performance to:

1.  **Write Contention on `manager_pending_reports`:** With a massive increase in report submissions and approvals, the write load on `manager_pending_reports` (inserts/deletes) could become a bottleneck. High concurrency on this table could lead to lock contention, slowing down the approval workflow itself.
2.  **Index Size and Maintenance:** The indexes on `manager_pending_reports` will grow very large. While they provide fast reads, their maintenance (updates, inserts, deletes) becomes more expensive. Rebuilding indexes could take significant time.
3.  **Long-Tail Manager Performance:** While the average manager's performance remains good, managers with an *exceptionally* high number of pending reports (e.g., thousands or tens of thousands) might still experience slower queries, as `K_filtered` becomes large. The `LIMIT/OFFSET` pagination can also become inefficient for deep pages on very large result sets.
4.  **Database Server Resource Saturation:** Overall CPU, memory, and I/O on the database server will be significantly higher due to the increased data volume and write amplification.

#### Handling Potential Consistency Issues

The `manager_pending_reports` table is a cache or materialized view. The primary source of truth remains `expense_reports` and `approval_steps`. Maintaining consistency is paramount for financial data.

Here's how to handle potential consistency issues:

1.  **Transactional Consistency (Preferred for Strong Consistency):**
    *   **Mechanism:** Wrap the updates to `expense_reports`, `approval_steps`, and `manager_pending_reports` within a single database transaction.
    *   **How it works:** If any part of the transaction fails (e.g., the `INSERT` into `manager_pending_reports`), the entire transaction is rolled back, ensuring that the primary data and the derived data remain in sync.
    *   **Example (pseudo-code):**
        ```sql
        BEGIN;
        -- Update primary approval_steps table
        UPDATE approval_steps SET status = 'APPROVED', approved_at = NOW() WHERE id = :step_id;
        -- Delete from manager_pending_reports
        DELETE FROM manager_pending_reports WHERE expense_report_id = :report_id AND manager_id = :current_manager_id;
        -- (Optional: If moving to next step, insert for new manager)
        -- INSERT INTO manager_pending_reports (...) VALUES (...);
        COMMIT;
        ```
    *   **Trade-off:** Increases the duration of database locks, potentially impacting concurrency on the base tables during peak write times. However, for critical financial data, this trade-off is often acceptable.

2.  **Event-Driven Architecture with Idempotency (for eventual consistency or complex workflows):**
    *   **Mechanism:** When an `approval_step` status changes, an event is published to a message queue (e.g., Kafka, RabbitMQ). A dedicated consumer service subscribes to these events and updates `manager_pending_reports`.
    *   **How it works:**
        *   The primary update (to `approval_steps`) is committed first.
        *   An event (`ExpenseReportApprovedEvent`, `ExpenseReportMovedToNextApproverEvent`) is published.
        *   The consumer service processes this event, performing the `DELETE`/`INSERT` on `manager_pending_reports`.
        *   The consumer must be **idempotent** to handle duplicate events gracefully (e.g., check if the record already exists before inserting, or if it's already deleted before deleting).
    *   **Trade-off:** Introduces eventual consistency. There might be a short delay (milliseconds to seconds) between the primary update and the `manager_pending_reports` table being updated. During this window, a manager might see a report they just approved still in their pending list. This might be acceptable depending on the business tolerance for stale reads. Adds operational complexity (message queue, consumer service).
    *   **Reconciliation:** A periodic batch job can run to compare `manager_pending_reports` against the `expense_reports` and `approval_steps` tables, identifying and correcting any discrepancies. This acts as a safety net.

3.  **Database Triggers (Less Recommended for Complex Logic):**
    *   **Mechanism:** Define `AFTER INSERT`, `AFTER UPDATE`, `AFTER DELETE` triggers on `approval_steps` (or `expense_reports`) that automatically perform the corresponding `INSERT`/`DELETE` operations on `manager_pending_reports`.
    *   **How it works:** Ensures strong consistency within the database transaction.
    *   **Trade-off:** Triggers can be difficult to debug, maintain, and can hide complex logic within the database, making application-level reasoning harder. They can also add overhead to every write operation on the base tables. For simple, direct updates, they might be considered, but for complex logic involving multiple tables or conditional inserts, application-level logic is generally preferred.

For this scenario, **transactional consistency** is the most robust and simplest approach to guarantee strong consistency, especially given the financial nature of the data. If the write load becomes extreme, moving to an **event-driven architecture with eventual consistency and a reconciliation mechanism** would be the next step, accepting the trade-off of slight latency for higher write throughput and scalability.
