## Scenario

Your team maintains a critical backend service for a growing online marketplace. This service is responsible for managing product inventory. When a customer views a product page, the system needs to display the *current available stock* for that product. The `products` table in PostgreSQL has grown to over 50 million rows, and the `stock_level` column is updated frequently (hundreds of times per second across various products) as orders are placed, cancelled, and new inventory arrives.

Currently, every product page view hits the database directly to fetch the `stock_level` for the specific product. This is causing significant load on the PostgreSQL database, leading to increased query latencies and occasional timeouts during peak traffic hours (e.g., flash sales, holiday seasons). The database CPU utilization frequently spikes above 80% during these periods, and adding more read replicas has only partially mitigated the issue due to cache invalidation and replication lag.

The business demands that displayed stock levels are *eventually consistent* within a few seconds, but high accuracy is paramount for preventing overselling.

## Worked answer

### 1. Redis Data Structure Choice

Given the need to store stock levels for millions of distinct products and retrieve them by `product_id`, a simple **Redis Hash** is the most suitable data structure.

*   **Key:** `product_stock:{product_id}`
*   **Field:** `stock_level`
*   **Value:** The integer stock level

**Justification:**

1.  **Direct Access:** Each product's stock level can be accessed directly using its `product_id` as part of the key. This maps perfectly to the requirement of fetching a specific product's stock.
2.  **Memory Efficiency:** For a large number of products, using individual keys for each product (`product_stock:123`, `product_stock:456`) would consume more memory due to key overhead. A Redis Hash allows storing multiple field-value pairs under a single key. However, in this specific scenario, we are storing *one* stock level per product. A simple string key-value pair (`product:{product_id}:stock` -> `stock_level`) would also work. The choice of a Hash with a single field (`stock_level`) is slightly more verbose but offers flexibility if we later decide to cache other product attributes (e.g., `last_updated_at`, `is_available`) alongside the stock level under the same product key, without changing the key structure. For simplicity and directness, a simple string key-value pair is also perfectly acceptable and perhaps even slightly more idiomatic for a single value. Let's proceed with the simple string key-value approach for clarity.

    **Revised Data Structure:**
    *   **Key:** `product:{product_id}:stock`
    *   **Value:** The integer stock level

    **Justification for Revised Choice:**
    *   **Simplicity:** It's the most straightforward key-value mapping.
    *   **Performance:** `GET` and `SET` operations on string keys are O(1), which is ideal for high-throughput access.
    *   **Scalability:** Redis can efficiently handle millions of such keys.
    *   **Atomicity:** `INCRBY` (for updates) and `GET` operations are atomic.

3.  **Atomic Operations:** Redis provides atomic operations like `INCRBY` which are crucial for safely updating stock levels in a concurrent environment, even if we primarily use the database as the source of truth for updates.
4.  **TTL (Time-To-Live):** We can set a TTL on each key to ensure that stale data eventually expires and is re-fetched from the database, contributing to eventual consistency. A TTL of 5-10 seconds would align with the business requirement of stock levels being eventually consistent within a few seconds.

The read path will implement a **Cache-Aside** strategy combined with a **Write-Through** or **Write-Behind** approach on the write path (described later).

import logging
from django.conf import settings # Assuming Django settings for DB connection

redis_client = redis.StrictRedis(
    host=settings.REDIS_HOST,
    port=settings.REDIS_PORT,
    db=settings.REDIS_DB,
    decode_responses=True # Decodes responses to Python strings

    return psycopg2.connect(
        host=settings.DB_HOST,
        database=settings.DB_NAME,
        user=settings.DB_USER,
        password=settings.DB_PASSWORD
    )

# --- Read Path Logic ---
def get_product_stock_level(product_id: int) -> int:
    redis_key = f"product:{product_id}:stock"
    cache_ttl_seconds = 10 # Cache entries expire after 10 seconds

    try:
        # 1. Try to fetch from Redis
        stock_level_str = redis_client.get(redis_key)
        if stock_level_str is not None:
            logging.debug(f"Cache hit for product {product_id}")
            return int(stock_level_str)

        logging.debug(f"Cache miss for product {product_id}")

        # 2. If not in Redis, fetch from PostgreSQL
        conn = None
        try:
            conn = get_db_connection()
            cursor = conn.cursor()
            cursor.execute(
                "SELECT stock_level FROM products WHERE id = %s FOR UPDATE NOWAIT", # Use FOR UPDATE NOWAIT to prevent deadlocks if another transaction is updating this row
                (product_id,)
            )
            result = cursor.fetchone()
            if result:
                db_stock_level = result[0]
                logging.info(f"Fetched stock {db_stock_level} for product {product_id} from DB.")

                # 3. Store in Redis with a TTL
                # Use SETEX for atomic set and expire
                redis_client.setex(redis_key, cache_ttl_seconds, db_stock_level)
                return db_stock_level
            else:
                logging.warning(f"Product {product_id} not found in database.")
                # Optionally cache a "not found" state with a shorter TTL
                redis_client.setex(redis_key, 60, -1) # Cache -1 for "not found"
                return 0 # Or raise an error, depending on business logic
        except psycopg2.OperationalError as e:
            logging.error(f"Database connection error: {e}")
            # Fallback: If DB is down, we might serve stale data if available
            # For this scenario, we prioritize accuracy, so we'd rather fail.
            raise # Re-raise to indicate a critical failure
        except psycopg2.errors.LockNotAvailable:
            logging.warning(f"Failed to acquire lock for product {product_id} in DB. Retrying or handling.")
            # This can happen if another transaction is already holding a lock.
            # For reads, we might retry without FOR UPDATE or just return 0/error.
            # Given the scenario, a read should ideally not block.
            # A simple SELECT without FOR UPDATE is usually sufficient for reads.
            # The FOR UPDATE was added for robustness against concurrent updates,
            # but for a pure read, it's generally not needed and can cause contention.
            # Let's remove FOR UPDATE for the read path to avoid blocking reads.
            # Re-evaluating: The FOR UPDATE NOWAIT was a misstep for a pure read.
            # A simple SELECT is sufficient. The stock_level column is frequently updated,
            # but we accept eventual consistency for reads.
            conn = get_db_connection()
            cursor = conn.cursor()
            cursor.execute(
                "SELECT stock_level FROM products WHERE id = %s",
                (product_id,)
            )
            result = cursor.fetchone()
            if result:
                db_stock_level = result[0]
                redis_client.setex(redis_key, cache_ttl_seconds, db_stock_level)
                return db_stock_level
            else:
                return 0 # Or raise
        finally:
            if conn:
                conn.close()

    except redis.exceptions.ConnectionError as e:
        logging.error(f"Redis connection error: {e}. Falling back to database.")
        # If Redis is down, fall back to database directly.
        # This ensures durability and accuracy, but increases DB load.

        try:
            conn = get_db_connection()
            cursor = conn.cursor()
            cursor.execute(
                "SELECT stock_level FROM products WHERE id = %s",

            )
            result = cursor.fetchone()
            if result:
                return result[0]
            else:
                return 0
        finally:

    except Exception as e:
        logging.critical(f"An unexpected error occurred: {e}")

**Explanation:**

*   **Cache-Aside:** The application code is responsible for checking the cache first. If the data is not found (cache miss), it fetches from the database, and then populates the cache.
*   **TTL:** Each cache entry has a Time-To-Live (TTL) of 10 seconds. This ensures that even if a cache invalidation fails, the data will eventually expire and be re-fetched from the database, guaranteeing eventual consistency within a reasonable timeframe.
*   **Redis Failure Handling:** If Redis is unavailable, the system gracefully falls back to querying the PostgreSQL database directly. This ensures that the service remains operational and accurate, albeit with increased database load.
*   **Database Failure Handling:** If the database is unavailable, the `get_product_stock_level` function will raise an exception, indicating a critical service degradation.
*   **Minimizing Database Reads:** For frequently accessed products, subsequent requests will hit Redis, significantly reducing the load on PostgreSQL. Only cache misses or expired entries will trigger a database read.

### 3. Pseudocode for Updating Product Stock Level (Write Path)

The write path will implement a **Write-Through** strategy, ensuring that both Redis and PostgreSQL are updated. This is critical for maintaining accuracy and preventing overselling.

```python
import redis
import psycopg2
import logging
from django.conf import settings
from django.db import transaction # For Django ORM transaction management

# Initialize Redis client (same as above)
redis_client = redis.StrictRedis(
    host=settings.REDIS_HOST,
    port=settings.REDIS_PORT,
    db=settings.REDIS_DB,
    decode_responses=True
)

# PostgreSQL connection (simplified for pseudocode)
def get_db_connection():
    return psycopg2.connect(
        host=settings.DB_HOST,
        database=settings.DB_NAME,
        user=settings.DB_USER,
        password=settings.DB_PASSWORD
    )

# --- Write Path Logic ---
def update_product_stock_level(product_id: int, quantity_change: int) -> int:
    """
    Updates the stock level for a product.
    quantity_change can be positive (new stock) or negative (order/cancellation).
    Returns the new stock level.
    """
    redis_key = f"product:{product_id}:stock"
    new_stock_level = None

    # We need to ensure atomicity and consistency between DB and Redis.
    # The database is the source of truth.
    conn = None
    try:
        conn = get_db_connection()
        # Use a transaction to ensure atomicity for the DB update
        with conn: # This automatically handles commit/rollback for psycopg2
            cursor = conn.cursor()

            # 1. Fetch current stock level from DB and update it
            # Use SELECT FOR UPDATE to prevent race conditions at the DB level
            # and ensure we're updating the most current value.
            cursor.execute(
                "SELECT stock_level FROM products WHERE id = %s FOR UPDATE",
                (product_id,)
            )
            result = cursor.fetchone()

            if not result:
                logging.error(f"Product {product_id} not found in database for update.")
                raise ValueError(f"Product {product_id} not found.")

            current_db_stock = result[0]
            new_stock_level = current_db_stock + quantity_change

            # Business logic: Prevent overselling (stock cannot go below zero)
            if new_stock_level < 0:
                logging.warning(
                    f"Attempted to set stock below zero for product {product_id}. "
                    f"Current: {current_db_stock}, Change: {quantity_change}"
                )
                raise ValueError("Cannot reduce stock below zero.")

            cursor.execute(
                "UPDATE products SET stock_level = %s WHERE id = %s",
                (new_stock_level, product_id)
            )
            logging.info(f"DB updated: Product {product_id} stock changed from {current_db_stock} to {new_stock_level}.")

            # 2. Invalidate or update Redis cache *after* successful DB commit
            # Using DEL is safer than SET for invalidation, as SET might write an old value
            # if the DB transaction fails and rolls back.
            # Alternatively, SET the new value if we are certain of the DB commit.
            try:
                # Invalidate the cache entry to force a fresh read on next access
                redis_client.delete(redis_key)
                logging.debug(f"Invalidated Redis cache for product {product_id}.")
                # Optionally, update Redis with the new value immediately (Write-Through)
                # This makes the cache immediately consistent with the DB.
                # redis_client.set(redis_key, new_stock_level)
                # logging.debug(f"Updated Redis cache for product {product_id} to {new_stock_level}.")
            except redis.exceptions.ConnectionError as e:
                logging.error(f"Redis connection error during cache invalidation for product {product_id}: {e}. "
                              "Cache might be stale until TTL expires.")
                # The system must still function even if Redis is down.
                # The TTL on read path will eventually correct this.

            return new_stock_level

    except psycopg2.OperationalError as e:
        logging.error(f"Database connection error during stock update: {e}")
        raise # Critical error, re-raise
    except ValueError as e:
        logging.error(f"Business logic error during stock update: {e}")
        raise # Re-raise for caller to handle
    except Exception as e:
        logging.critical(f"An unexpected error occurred during stock update: {e}")
        raise # Re-raise for higher-level error handling
    finally:
        if conn:
            conn.close()

# Example usage (e.g., after an order is placed)
# try:
#     new_stock = update_product_stock_level(product_id=123, quantity_change=-1)
#     print(f"New stock for product 123: {new_stock}")
# except ValueError as e:
#     print(f"Error: {e}")
# except Exception as e:
#     print(f"Critical error: {e}")
```

**Explanation:**

*   **Database as Source of Truth:** All stock updates are first and foremost applied to the PostgreSQL database. This ensures durability and accuracy.
*   **`SELECT FOR UPDATE`:** This SQL clause is crucial. It locks the specific product row in the database, preventing other concurrent transactions from modifying it until the current transaction commits or rolls back. This eliminates race conditions at the database level when reading the current stock before updating it.
*   **Database Transaction:** The entire database operation (select and update) is wrapped in a transaction. If any part fails, the transaction is rolled back, ensuring data integrity.
*   **Cache Invalidation (Write-Through):** After a successful database update, the corresponding Redis cache entry is explicitly deleted. This forces the next read request for that product to fetch the freshest data from the database, then repopulate the cache. This is a common and robust strategy for cache invalidation.
    *   **Alternative: Update Cache Directly:** Instead of `DEL`, we could `SET` the new `new_stock_level` directly into Redis. This makes the cache immediately consistent. However, if the `SET` operation fails (e.g., Redis is down), the cache becomes stale. `DEL` is generally safer as it guarantees the cache will be refreshed from the DB on the next read, relying on the read path's fallback logic. Given the requirement for high accuracy and preventing overselling, `DEL` is preferred here. If Redis is down, the `DEL` will fail, but the DB update will succeed, and the read path will fall back to the DB.
*   **Redis Failure Handling:** If Redis is unavailable during the update, the `DEL` operation will fail, but the database update will still succeed. The system remains operational, and the read path's TTL mechanism will eventually correct the stale cache entry. This prioritizes database integrity and service availability over immediate cache freshness.
*   **Business Logic:** The `if new_stock_level < 0:` check prevents overselling by rejecting updates that would result in negative stock.

### 4. Handling Race Conditions and Ensuring Eventual Consistency

**Race Conditions:**

1.  **Concurrent Reads (Cache Misses):**
    *   **Problem:** Multiple concurrent requests for the same product might experience a cache miss simultaneously. Each request would then hit the database, fetch the stock, and attempt to write it to Redis. This is known as a "thundering herd" or "cache stampede."
    *   **Mitigation:**
        *   **`SETNX` (Set If Not Exists) with `EX` (Expire):** When a cache miss occurs, the first request can attempt to acquire a "lock" in Redis using `SETNX` (e.g., `redis_client.set(f"product:{product_id}:lock", "1", ex=5, nx=True)`). If successful, it fetches from the DB and populates the cache. Other requests seeing the lock can either wait (e.g., with a short sleep and retry) or proceed to the database directly. This is complex to implement correctly.
        *   **Simpler Approach (Chosen):** Rely on the database's ability to handle concurrent reads. PostgreSQL is highly optimized for this. While multiple requests might hit the DB for the same product during a cache stampede, they will all get the correct current stock. The subsequent `redis_client.setex()` calls will simply overwrite each other, with the last one winning. This is acceptable because the values are identical, and the TTL ensures eventual consistency. The primary goal is to reduce *sustained* DB load, which the cache achieves after the initial stampede.
        *   **TTL:** The cache TTL helps here too. Even if a stampede occurs, the cache will be populated, and subsequent reads will hit Redis.

2.  **Concurrent Writes to Database:**
    *   **Problem:** Multiple orders for the same product arriving simultaneously could lead to incorrect stock levels if not handled atomically.
    *   **Mitigation (Implemented):**
        *   **`SELECT FOR UPDATE`:** This is the primary mechanism. When `update_product_stock_level` is called, it acquires a row-level lock on the product in PostgreSQL. Any other transaction attempting to `SELECT FOR UPDATE` or `UPDATE` the same row will wait until the first transaction commits or rolls back. This guarantees that only one update operation modifies the stock level at a time for a given product, preventing lost updates.
        *   **Database Transactions:** The entire update operation (read current stock, calculate new stock, write new stock) is wrapped in a single database transaction. This ensures atomicity: either all changes are committed, or none are.

3.  **Race between DB Update and Cache Invalidation:**
    *   **Problem:** A request reads stale data from Redis *just before* the write path updates the DB and invalidates the cache.
        1.  Read path: `GET product:{id}:stock` returns `100`.
        2.  Write path: `UPDATE products SET stock_level = 99 WHERE id = {id}`.
        3.  Write path: `DEL product:{id}:stock`.
        4.  Read path: `SETEX product:{id}:stock 100` (populating cache with stale data).
    *   **Mitigation:** This specific race condition (known as the "read-after-write" or "cache-aside invalidation race") is a classic problem.
        *   **Solution (Implemented):** The chosen strategy of **deleting the cache entry *after* the database write commits** is generally robust. If a read occurs *before* the `DEL` but *after* the DB commit, it might serve stale data for a very brief moment. However, the subsequent `DEL` will ensure the cache is cleared. The critical part is that the `SETEX` on the read path happens *before* the `DEL` on the write path.
        *   **The "Read-After-Write" Race (Revisited):**
            1.  Client A reads `stock=100` from Redis.
            2.  Client B updates DB to `stock=99`, then `DEL`s `product:{id}:stock` from Redis.
            3.  Client A (having missed the `DEL` due to timing) performs a `SETEX product:{id}:stock 100` (re-populating with stale data).
            *   This is a real problem.
        *   **Improved Mitigation (Write-Through with `SET`):** To fully mitigate this, the write path should update Redis with the *new* value *after* the database commit, rather than just deleting.
            ```python
            # Inside update_product_stock_level, after DB commit:
            try:
                redis_client.setex(redis_key, cache_ttl_seconds, new_stock_level) # SET with TTL
                logging.debug(f"Updated Redis cache for product {product_id} to {new_stock_level}.")
            except redis.exceptions.ConnectionError as e:
                logging.error(f"Redis connection error during cache update for product {product_id}: {e}. "
                              "Cache might be stale until TTL expires.")
            ```
            This makes the cache immediately consistent. If the `SETEX` fails, the cache will remain stale until its existing TTL expires, or until the next successful update/read-and-populate. This is a trade-off: immediate consistency if Redis is up, but potential staleness if Redis is down during the write.
        *   **Chosen Strategy (DEL then Read-Populate):** The original `DEL` strategy is often preferred for simplicity and robustness against Redis failures. The risk of the read-after-write race is mitigated by the short TTL (10 seconds). Even if a stale entry is re-populated, it will expire quickly. Given the requirement for "eventually consistent within a few seconds," this is an acceptable trade-off. The business demands "high accuracy is paramount for preventing overselling," which is handled by the `SELECT FOR UPDATE` and transaction on the write path, not by the read cache. The read cache is for display purposes, where a few seconds of staleness is acceptable.

**Ensuring Eventual Consistency:**

1.  **TTL (Time-To-Live):** Every entry in Redis has a TTL (e.g., 10 seconds). This is the primary mechanism for eventual consistency. Even if a cache invalidation fails (e.g., Redis is down during an update), the stale entry will eventually expire, forcing a fresh read from the database.
2.  **Database as Source of Truth:** All updates go through the database first. This guarantees that the authoritative data is always correct and durable. Redis is merely a performance layer.
3.  **Cache Invalidation on Write:** Explicitly deleting the cache entry after a successful database write ensures that subsequent reads will fetch the latest data. This accelerates consistency compared to relying solely on TTL.
4.  **Redis Failure Fallback:** If Redis is unavailable, the read path falls back to the database. This ensures that the system always serves accurate data, even if it means increased database load temporarily. This prioritizes accuracy and availability over cache performance during Redis outages.

**Trade-offs Accepted:**

*   **Brief Staleness:** There's a small window (up to the TTL, or until the next successful cache invalidation) where the displayed stock level might not be perfectly up-to-the-second accurate. This is acceptable per the "eventually consistent within a few seconds" requirement.
*   **Increased Latency on Cache Misses:** Cache misses will incur the latency of a database query. However, for hot products, the hit rate should be very high, making this infrequent.
*   **Redis Operational Overhead:** Introducing Redis adds another component to manage, monitor, and scale.
*   **Complexity:** The logic for handling cache misses, invalidation, and fallbacks adds complexity to the application code.
*   **Potential for Cache Stampede:** While mitigated, a sudden surge of requests for a previously uncached product could still temporarily overload the database.

**What Breaks First at Ten Times the Scale:**

At ten times the scale (thousands of concurrent updates, tens of thousands of concurrent reads per second):

1.  **PostgreSQL Write Contention:** Even with `SELECT FOR UPDATE`, if a single product receives an extremely high number of concurrent updates (e.g., a viral product during a flash sale), the row-level locks in PostgreSQL could become a bottleneck. Transactions would queue up, leading to increased latency for updates and potentially timeouts.
    *   **Mitigation:** For extremely high-contention products, consider sharding the `products` table or using a more specialized inventory system that can handle atomic decrements at a higher rate (e.g., using Redis `DECRBY` as the primary inventory source, then asynchronously writing to DB, but this introduces significant complexity around consistency and durability). For this challenge, the current approach is robust for typical high-volume scenarios.
2.  **Redis Network I/O / CPU:** While Redis is very fast, tens of thousands of `GET` and `SETEX` operations per second will consume network bandwidth and Redis server CPU. A single Redis instance might become saturated.
    *   **Mitigation:** Redis clustering (sharding data across multiple Redis nodes) would be necessary.
3.  **Application Server CPU/Memory:** The application servers themselves would need to scale horizontally to handle the increased request volume, both for processing requests and managing Redis/DB connections.
4.  **Database Connection Pool Exhaustion:** If the number of concurrent cache misses or Redis failures becomes too high, the application might exhaust its database connection pool, leading to service degradation.

**Scenario where a stale cache entry for a product's stock level could lead to a severe business problem despite eventual consistency:**

Consider a scenario where a product has a very low stock level, say **1 unit**, and is extremely popular (e.g., a limited edition item).

1.  **Initial State:**
    *   PostgreSQL: `product_X` stock = 1
    *   Redis: `product:X:stock` = 1 (TTL set to 10 seconds)

2.  **Order 1:**
    *   Customer A views `product_X`. Cache hit, displays 1 unit.
    *   Customer A places an order.
    *   `update_product_stock_level(product_X, -1)` is called.
    *   Database: `SELECT FOR UPDATE` gets 1. New stock becomes 0. `UPDATE` sets stock to 0.
    *   Redis: `DEL product:X:stock` is called. (Assume this succeeds).
    *   Customer A's order is confirmed.

3.  **Race Condition / Stale Cache Issue:**
    *   **Problem:** Immediately after `DEL product:X:stock` (step 2), but *before* the cache entry has been re-populated by a subsequent read, Customer B views `product_X`.
    *   **Cache Miss:** `get_product_stock_level(product_X)` results in a cache miss.
    *   **Database Read:** `get_product_stock_level` queries the database, which now correctly returns `0`.
    *   **Cache Populate:** `get_product_stock_level` then `SETEX product:X:stock 0` in Redis.

    This sequence works as intended. The problem arises if the `DEL` operation in step 2 fails (e.g., Redis connection error), or if there's a very specific timing window where a read happens *after* the DB update but *before* the `DEL` (less likely with `DEL` after commit, but still possible in distributed systems).

    **Let's re-evaluate the "read-after-write" race condition, which is the more severe problem here.**

    1.  **Initial State:**
        *   PostgreSQL: `product_X` stock = 1
        *   Redis: `product:X:stock` = 1 (TTL 10s)

    2.  **Order 1 (Customer A):**
        *   Customer A views `product_X`. Cache hit, displays 1 unit.
        *   Customer A places an order.
        *   `update_product_stock_level(product_X, -1)` starts.
        *   DB transaction begins: `SELECT FOR UPDATE` gets 1. `UPDATE` sets stock to 0. DB commits.
        *   **CRITICAL POINT:** Before the `DEL product:X:stock` command from Order 1's write path reaches Redis, another read occurs.

    3.  **Concurrent Read (Customer B):**
        *   Customer B views `product_X`.
        *   `get_product_stock_level(product_X)` is called.
        *   It hits Redis and finds `product:X:stock` = 1 (the stale value, as `DEL` hasn't happened yet).
        *   Customer B is shown that 1 unit is available.

    4.  **Order 1 (continued):**
        *   The `DEL product:X:stock` command from Order 1's write path finally executes, removing the stale entry.

    5.  **Order 2 (Customer B):**
        *   Customer B, seeing 1 unit available, attempts to place an order.
        *   `update_product_stock_level(product_X, -1)` is called for Customer B.
        *   DB transaction begins: `SELECT FOR UPDATE` gets 0 (the correct current stock).
        *   Business logic: `new_stock_level = 0 - 1 = -1`.
        *   **Problem:** The `if new_stock_level < 0:` check triggers. Customer B's order is rejected because stock is already 0.

    **Severe Business Problem:** Customer B was shown that the product was in stock (1 unit), but their order was then rejected. This leads to a **poor customer experience**, frustration, and potential loss of sale. For a limited edition, high-demand item, this can be particularly damaging to brand reputation. While overselling is prevented (which is good), the misleading information is the problem.

**How the Proposed Solution Might Exacerbate or Mitigate This Specific Issue:**

*   **Exacerbation:** The chosen `DEL` strategy, while robust for general eventual consistency, is susceptible to this specific "read-after-write" race condition where a read happens *after* the DB commit but *before* the `DEL` command is processed by Redis. If the `DEL` is delayed (e.g., network latency, Redis busy), the window for this race increases. The TTL helps, but 10 seconds is still a long time to display incorrect stock for a fast-moving item.

*   **Mitigation (within the proposed solution's framework):**
    1.  **Shorter TTL:** Reducing the `cache_ttl_seconds` to a very low value (e.g., 1-2 seconds) would shrink the window during which stale data could be served. However, this increases cache misses and thus database load.
    2.  **Immediate Cache Update (Write-Through `SET`):** As discussed, changing the write path to `redis_client.setex(redis_key, cache_ttl_seconds, new_stock_level)` instead of `DEL` would mitigate this specific race. If the `SETEX` succeeds, the cache is immediately updated with the correct value. If it fails (Redis down), the cache might remain stale until its existing TTL expires, but at least it won't be *re-populated* with stale data by a concurrent read. This is a stronger form of consistency for the cache.
    3.  **Client-Side Retries/Refresh:** On the frontend, if an order fails due to insufficient stock, the UI could immediately refresh the stock level from the backend (forcing a fresh read) and display an updated message.
    4.  **"Soft Lock" in Redis for Low Stock:** For critical, low-stock items, a more aggressive strategy could be employed. When stock hits 1 or 0, a Redis key could be set (e.g., `product:X:low_stock_alert`) that triggers a more frequent refresh or bypasses the cache entirely for that specific product until stock is replenished. This adds complexity for specific product handling.

In summary, while the `DEL` strategy is generally good, for highly critical, low-stock scenarios where misleading information is a severe problem, switching to an immediate `SETEX` (Write-Through) on the write path is a stronger mitigation for the "read-after-write" race, accepting the trade-off that Redis failure during the `SETEX` would leave the cache stale until TTL, rather than forcing an immediate DB read.
