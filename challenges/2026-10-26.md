Your team manages the backend service for a popular online travel booking platform. A core feature allows users to search for flights. The `flights` table contains tens of millions of active flight segments, with new flights added and old ones expiring daily. Each flight has a `departure_airport_code`, `arrival_airport_code`, `departure_time`, `arrival_time`, and `price`.

The main search endpoint needs to find direct flights between two airports for a given date. This query is executed hundreds of times per second.

Recently, users have reported that flight searches for popular routes, especially those looking several months into the future, have become noticeably slower, sometimes taking 2-3 seconds. Your monitoring confirms that the database query for these searches is the bottleneck. The current query looks something like this:

```sql
SELECT *
FROM flights
WHERE departure_airport_code = 'JFK'
  AND arrival_airport_code = 'LAX'
  AND departure_time::date = '2027-01-15'
ORDER BY price ASC;
```

## Requirements

The primary constraint is to reduce the average latency of this flight search query to under 100ms, even for popular routes and dates several months out. The `flights` table is growing by hundreds of thousands of rows daily, and updates to existing flight prices and times are frequent, occurring multiple times per hour for a significant portion of active flights. The solution must not significantly degrade write performance (insertions and updates) or consume excessive disk space. You only need to focus on optimizing the direct flight search query described.

## Deliverables

1. The exact SQL statement(s) to create any necessary indexes or database objects.
2. A brief explanation (2-3 sentences) of *why* your proposed solution addresses the latency issue, specifically mentioning the problematic parts of the original query.
3. A brief explanation (1-2 sentences) of how your solution considers the impact of frequent writes to the `flights` table.

## Going further

Describe a scenario where your chosen indexing strategy might perform poorly or become a maintenance burden, and suggest an alternative approach for that specific scenario.

## Worked answer

### Deliverables

#### 1. SQL statement(s) to create necessary indexes

```sql
CREATE INDEX idx_flights_search_date_price ON flights (departure_airport_code, arrival_airport_code, departure_time, price);
```

#### 2. Explanation of why the solution addresses latency

The original query's bottleneck is the `departure_time::date = '2027-01-15'` condition, which prevents effective index usage on `departure_time` due to the function call (`::date`) on the column. The proposed index `(departure_airport_code, arrival_airport_code, departure_time, price)` allows PostgreSQL to perform an index-only scan or at least an index scan for the `WHERE` clauses, efficiently filtering by airport codes and `departure_time` directly. The `ORDER BY price ASC` clause is also satisfied by the index, eliminating the need for an expensive sort operation.

#### 3. Impact on frequent writes

This B-tree index will incur a small overhead on writes (inserts, updates, deletes) because the index structure must also be updated. However, since the index only includes columns frequently used in the search query and is relatively narrow, the impact on write performance should be minimal and acceptable for hundreds of thousands of daily row additions and multiple updates per hour. PostgreSQL's MVCC (Multi-Version Concurrency Control) design ensures that readers are not blocked by writers, and vice-versa, further mitigating performance degradation during concurrent operations.

### Going further

A scenario where this indexing strategy might perform poorly or become a maintenance burden is if the `departure_time` column has extremely low cardinality after truncating to a date (e.g., all flights for a given route on a specific date depart at exactly the same time, or within a very narrow window). If there are millions of flights for 'JFK' to 'LAX' on '2027-01-15', and the `departure_time` values are not sufficiently diverse to help narrow down the results further within the index, the index might still have to scan a large number of index entries for that date. This could lead to a less efficient index scan, especially if the `price` column then has many identical values, making the final `ORDER BY` less effective.

In such a scenario, where a single date for a popular route yields an extremely large result set, the index could become very wide for specific key combinations, potentially leading to increased disk I/O and slower lookups for those specific popular dates.

An alternative approach for this specific scenario could be to use a **partitioned table** based on `departure_time` (e.g., by month or quarter). This would allow queries to only scan the relevant partition(s) for a given date range, significantly reducing the amount of data the database needs to consider. Within each partition, a more focused index like `(departure_airport_code, arrival_airport_code, price)` could be applied. This strategy would improve performance for queries spanning large datasets by limiting the search space, but it introduces complexity in table management (e.g., creating new partitions, detaching old ones) and might require changes to how new flight data is ingested.
