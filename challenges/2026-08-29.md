## Scenario

Your team maintains a critical backend service for a popular online forum. Users frequently create posts, and each post can receive many comments. To foster community engagement, the platform displays a "Trending Posts" section on the homepage, which shows posts that have received a significant amount of *recent* interaction. This section is updated every 30 seconds.

Currently, "trending" is defined by the number of comments a post has received within the last 24 hours. The forum has grown significantly, with hundreds of thousands of posts created daily and millions of comments. The existing solution queries the `comments` table, filtering by `created_at` timestamp and `post_id`, then grouping and counting. This approach has become a major bottleneck, often taking several seconds to compute, and sometimes timing out under peak load, leading to an inconsistent or empty "Trending Posts" section.

The `posts` table has columns `id`, `title`, `user_id`, `created_at`.
The `comments` table has columns `id`, `post_id`, `user_id`, `content`, `created_at`.

## Requirements

The "Trending Posts" section needs to display the top 100 posts by comment count in the last 24 hours. This calculation must be fast, ideally completing within 100ms, and robust enough to handle high read traffic to this endpoint. The solution should consider that new comments are constantly being added and old comments are continuously falling outside the 24-hour window. The system is multi-tenant in the sense that many users are simultaneously viewing the trending posts.

2.  An explanation of how this data structure would be updated when a new comment is added.

4.  A brief description of how the system would query this data structure to get the top 100 posts.

## Worked answer

### 1. High-level description of data structure(s)

To efficiently track and retrieve the top 100 trending posts by comment count within the last 24 hours, we need a data structure that can:
1.  **Store counts for posts:** Each post needs its current comment count within the 24-hour window.
2.  **Order posts by count:** We need to quickly identify the top 100 posts.
3.  **Handle time-based expiry:** Comments continuously fall out of the 24-hour window, decrementing post counts.
4.  **Handle new additions:** New comments increment post counts.

A single data structure is unlikely to handle all these requirements optimally. We can combine several structures:

*   **Redis Sorted Set (`ZSET`) for Top Posts:** A Redis `ZSET` is ideal for storing posts and their comment counts, ordered by count. It allows efficient retrieval of the top N elements. The `score` of an element would be the post's comment count, and the `member` would be the `post_id`.
*   **Redis Hashes (`HASH`) for Comment Expiry Tracking:** To handle comment expiry, we need to know *when* each comment was added so we can decrement the count when it expires. Storing individual comment timestamps in the `ZSET` is not feasible. Instead, we can use a Redis `HASH` for each `post_id` to store a count of comments added in each minute (or a small time bucket) within the 24-hour window. This allows us to decrement counts based on aggregated time buckets rather than individual comments.
*   **Redis List (`LIST`) or Stream (`STREAM`) as a Message Queue:** To decouple the comment creation event from the trending posts update logic, we'll use a message queue. When a new comment is added, an event is published to this queue. This ensures that the critical path of adding a comment to the database remains fast, and trending post updates are handled asynchronously.

**Overall Architecture:**

1.  **Database (PostgreSQL):** Stores the canonical `posts` and `comments` data.
2.  **Application Service:** When a new comment is created, it's written to the database and then an event is published to a message queue.
3.  **Trending Posts Worker (Consumer):** A dedicated service consumes events from the message queue, updates the Redis data structures, and periodically handles expiry.
4.  **Trending Posts API (Reader):** Queries the Redis `ZSET` to retrieve the top 100 posts.

### 2. How the data structure would be updated when a new comment is added

When a new comment is added to the `comments` table, the application service performs the following steps:

1.  **Insert into Database:**
    ```sql
    INSERT INTO comments (post_id, user_id, content, created_at)
    VALUES (:post_id, :user_id, :content, NOW());
    ```

2.  **Publish to Message Queue:**
    After a successful database insert, the application publishes a message to a queue (e.g., Kafka, RabbitMQ, or a simple Redis `LIST`/`STREAM`). The message payload would include at least `post_id` and `created_at`.

    Example using Redis `LPUSH` (as a simple queue for demonstration):
    ```python
    # Python pseudo-code in the application service
    import redis
    import json
    from datetime import datetime

    r = redis.Redis(host='localhost', port=6379, db=0)

    def create_comment(post_id, user_id, content):
        # ... database insert logic ...
        comment_created_at = datetime.now().isoformat() # Get the exact timestamp from DB or application
        message = {
            "post_id": post_id,
            "created_at": comment_created_at
        }
        r.lpush("new_comments_queue", json.dumps(message))
        print(f"Comment for post {post_id} created and queued.")
    ```

3.  **Trending Posts Worker (Consumer) Processing:**
    A dedicated worker service continuously consumes messages from the `new_comments_queue`. For each message:

    *   **Increment Post Count in `ZSET`:** The worker increments the score of the `post_id` in the `trending_posts` sorted set. If the `post_id` doesn't exist, it's added with a score of 1.
        ```redis
        ZINCRBY trending_posts 1 <post_id>
        ```

    *   **Track Comment Timestamp for Expiry:** To handle expiry, we need to know that a comment was added for this post at this specific time. We'll use a Redis `HASH` per `post_id` to store counts for minute-level buckets. The key for this hash would be `post_comments_by_minute:<post_id>`. The fields in the hash would be minute timestamps (e.g., `YYYYMMDDHHMM`), and their values would be the count of comments added in that minute.

        ```python
        # Python pseudo-code in the trending posts worker
        import redis
        import json
        from datetime import datetime

        r = redis.Redis(host='localhost', port=6379, db=0)

        def process_new_comment_event(message_payload):
            post_id = message_payload["post_id"]
            created_at_str = message_payload["created_at"]
            created_at = datetime.fromisoformat(created_at_str)

            # 1. Update the ZSET
            r.zincrby("trending_posts", 1, post_id)

            # 2. Update the HASH for expiry tracking
            minute_bucket = created_at.strftime("%Y%m%d%H%M")
            r.hincrby(f"post_comments_by_minute:{post_id}", minute_bucket, 1)

            # Set an expiry on the hash key itself to clean up old post data if it becomes inactive
            # This is a safety net; minute buckets within the hash will be handled by the expiry process.
            # Set to slightly more than 24 hours to ensure all minute buckets are processed.
            r.expire(f"post_comments_by_minute:{post_id}", 25 * 3600)
        ```

### 3. How the data structure would handle comments expiring (falling outside the 24-hour window)

Handling expiry is crucial and requires a separate mechanism. The `trending_posts` `ZSET` itself doesn't automatically decrement scores. We need a periodic process.

**Expiry Worker:** A dedicated worker service runs periodically (e.g., every minute or every 5 minutes). Its job is to identify and process expired comments.

1.  **Determine Expiry Window:** For each run, calculate the timestamp for 24 hours ago. For example, if it's 2026-08-29 10:00:00, comments created before 2026-08-28 10:00:00 need to be expired. The minute bucket to expire would be `202608281000`.

2.  **Iterate Through Active Posts:** The worker needs to know which posts have active comments. It can get this by iterating through the `trending_posts` `ZSET` (or a separate set of all active `post_id`s). However, iterating through potentially hundreds of thousands of posts every minute is inefficient.

    A more efficient approach is to use a **Global Time-Bucket Hash** or a **Global Sorted Set of Active Posts with Oldest Comment Timestamp**.
    Let's refine the expiry tracking:

    **Refined Expiry Tracking:** Instead of `post_comments_by_minute:<post_id>`, we can use a **Global Sorted Set for Expiry (`expiry_track_posts`)**.
    When a comment is added:
    *   `ZINCRBY trending_posts 1 <post_id>`
    *   `HINCRBY post_comments_by_minute:<post_id> <minute_bucket> 1`
    *   Additionally, we need to know *which minute buckets* exist for *which posts*.
        We can use a `ZSET` where the score is the `minute_bucket` timestamp (as an integer) and the member is `post_id:minute_bucket`.

        ```redis
        # When a new comment for post_id at created_at is processed
        # minute_bucket_int = int(created_at.strftime("%Y%m%d%H%M"))
        # ZADD expiry_minute_buckets <minute_bucket_int> <post_id>:<minute_bucket_int>
        ```
        This approach would still require iterating through all `post_id:minute_bucket` pairs for the expired minute.

    **Simpler Expiry (Polling `post_comments_by_minute` hashes):**
    The expiry worker can:
    *   Get all `post_comments_by_minute:*` keys using `KEYS post_comments_by_minute:*` (in a small, controlled environment) or `SCAN` (in production).
    *   For each `post_comments_by_minute:<post_id>` hash:
        *   Identify the minute bucket that is now 24 hours old.
        *   Retrieve the count for that bucket using `HGET`.
        *   If a count exists, decrement the `trending_posts` `ZSET` score by that amount using `ZINCRBY <post_id> -<count>`.
        *   Remove the expired bucket from the `post_comments_by_minute:<post_id>` hash using `HDEL`.
        *   If a post's score in `trending_posts` drops to 0 or below, it can be removed from the `ZSET` using `ZREM`.

    **Example Expiry Worker Logic (Python pseudo-code):**

    ```python
    import redis
    from datetime import datetime, timedelta

    r = redis.Redis(host='localhost', port=6666, db=0)

    def run_expiry_worker():
        print("Running expiry worker...")
        # Calculate the minute bucket that expired 24 hours ago
        # Example: if now is 10:05, comments from 10:05 (yesterday) to 10:04 (yesterday) are still valid.
        # Comments from 10:04 (yesterday) and earlier are expired.
        # So, we need to expire the minute bucket that represents `now - 24 hours - 1 minute`.
        # Or, more simply, expire anything that is `now - 24 hours`.
        
        # Let's say we expire comments that are *strictly older* than 24 hours.
        # If current time is 2026-08-29 10:05:30, then comments from 2026-08-28 10:05:30 are expiring.
        # The minute bucket for 2026-08-28 10:05 needs to be processed.
        
        expiry_time = datetime.now() - timedelta(hours=24)
        expired_minute_bucket = expiry_time.strftime("%Y%m%d%H%M")

        # Use SCAN to iterate over all post_comments_by_minute hashes
        cursor = '0'
        while cursor != 0:
            cursor, keys = r.scan(cursor=cursor, match='post_comments_by_minute:*', count=100)
            for key in keys:
                post_id = key.decode('utf-8').split(':')[1]
                
                # Get the count for the expired minute bucket
                expired_count_str = r.hget(key, expired_minute_bucket)
                if expired_count_str:
                    expired_count = int(expired_count_str)
                    
                    # Decrement the score in the trending_posts ZSET
                    r.zincrby("trending_posts", -expired_count, post_id)
                    
                    # Remove the expired bucket from the post's hash
                    r.hdel(key, expired_minute_bucket)
                    
                    print(f"Expired {expired_count} comments for post {post_id} from minute {expired_minute_bucket}")

                    # Optional: Clean up ZSET if score drops to 0 or below
                    current_score = r.zscore("trending_posts", post_id)
                    if current_score is not None and current_score <= 0:
                        r.zrem("trending_posts", post_id)
                        r.delete(key) # Delete the hash if the post has no active comments left
                        print(f"Post {post_id} removed from trending_posts and its comment hash deleted.")

        print("Expiry worker finished.")

    # This worker would run on a schedule, e.g., every minute.
    # schedule.every(1).minute.do(run_expiry_worker)
    # while True:
    #     schedule.run_pending()
    #     time.sleep(1)
    ```

    **Trade-off:** Using `SCAN` to find all `post_comments_by_minute:*` keys can be slow if there are millions of active posts. A more robust solution for very high scale would involve maintaining a separate `ZSET` of `post_id`s, ordered by their *oldest comment timestamp*. The expiry worker would then only process posts whose oldest comment timestamp is now outside the 24-hour window. However, this adds complexity to updating that `ZSET` when new comments arrive or old ones expire. The `SCAN` approach is simpler to implement and often sufficient for hundreds of thousands of active posts if `count` is tuned and the worker runs frequently.

### 4. Brief description of how the system would query this data structure to get the top 100 posts

Querying the top 100 posts is the simplest part, leveraging the Redis `ZSET`.

The Trending Posts API service would directly query Redis:

```redis
ZREVRANGE trending_posts 0 99 WITHSCORES
```

This command returns the top 100 members (post IDs) from the `trending_posts` sorted set, ordered from highest score to lowest, along with their scores (comment counts).

**Example API endpoint (Python pseudo-code):**

```python
import redis
import json

r = redis.Redis(host='localhost', port=6379, db=0)

def get_trending_posts():
    # Get top 100 post_ids and their scores (comment counts)
    # ZREVRANGE returns members and scores as tuples (member, score)
    top_posts_with_scores = r.zrevrange("trending_posts", 0, 99, withscores=True)

    trending_posts_list = []
    for post_id_bytes, score_float in top_posts_with_scores:
        post_id = int(post_id_bytes.decode('utf-8'))
        comment_count = int(score_float)
        
        # In a real application, you would then fetch post details (title, etc.)
        # from your primary database (e.g., PostgreSQL) using these post_ids.
        # This can be done with a single batch query:
        # SELECT id, title, user_id FROM posts WHERE id IN (...)
        
        trending_posts_list.append({
            "post_id": post_id,
            "comment_count": comment_count,
            # "title": "Fetched from DB",
            # "user_id": "Fetched from DB"
        })
    
    return json.dumps(trending_posts_list)
```

### Going further

#### Time Complexity

*   **Adding a new comment:**
    *   **Database write:** `O(log N)` or `O(1)` on average for indexed inserts, depending on the database and indexing strategy.
    *   **Message queue publish:** `O(1)` amortized.
    *   **Redis `ZINCRBY`:** `O(log M)` where M is the number of elements in the `ZSET`.
    *   **Redis `HINCRBY`:** `O(1)` amortized.
    *   **Overall:** Dominated by `O(log M)` for the `ZSET` update.

*   **Removing an expired comment (via expiry worker):**
    This is amortized over the period the worker runs.
    *   **Redis `SCAN`:** `O(N_active_posts)` over a full iteration, where `N_active_posts` is the number of posts with comments in the last 24 hours. Each `SCAN` call is `O(1)` for the number of keys returned.
    *   **Redis `HGET`:** `O(1)`.
    *   **Redis `ZINCRBY` (decrement):** `O(log M)` where M is the number of elements in the `ZSET`.
    *   **Redis `HDEL`:** `O(1)`.
    *   **Redis `ZREM` (if score <= 0):** `O(log M)`.
    *   **Overall:** The `SCAN` operation dominates, making the expiry process `O(N_active_posts * log M)` in the worst case if every active post has an expired comment, or `O(N_active_posts)` if we only consider the `SCAN` and `HGET/HDEL` operations (ignoring `ZINCRBY` for each post). This is why the `SCAN` approach needs to be carefully managed for very large `N_active_posts`.

*   **Querying for the top 100 posts:**
    *   **Redis `ZREVRANGE`:** `O(log M + K)` where M is the number of elements in the `ZSET` and K is the number of elements requested (100 in this case).
    *   **Database query for post details:** `O(K)` for a batch `WHERE IN` query if an index exists on `post_id`.
    *   **Overall:** `O(log M + K)`. This is extremely efficient.

#### Space Complexity Implications

*   **`trending_posts` `ZSET`:** `O(N_active_posts)` where `N_active_posts` is the number of unique posts that have received at least one comment in the last 24 hours. Each entry stores a `post_id` and its score.
*   **`post_comments_by_minute:<post_id>` Hashes:** For each active post, we store up to `24 * 60 = 1440` minute buckets. Each bucket stores a minute timestamp (e.g., `YYYYMMDDHHMM` string) and a count.
    *   Space for these hashes: `O(N_active_posts * 1440 * (size_of_minute_string + size_of_count_integer))`.
    *   If `N_active_posts` is hundreds of thousands, this can be substantial: `200,000 posts * 1440 buckets/post * (12 bytes for minute + ~4 bytes for count) = 200,000 * 1440 * 16 bytes = 4.6 GB`. This is a significant amount of RAM, but manageable for a dedicated Redis instance. Redis's efficient hash encoding for small hashes can reduce this, but for 1440 fields, it will likely use regular hash table encoding.

**As the number of active posts grows:**

*   **`trending_posts` `ZSET`:** Scales linearly with `N_active_posts`. Redis `ZSET`s are highly optimized, but at millions of entries, operations like `ZINCRBY` will still be `O(log M)`.
*   **`post_comments_by_minute:<post_id>` Hashes:** The total memory usage for these hashes will grow linearly with `N_active_posts`. This is the primary concern for space complexity. If `N_active_posts` reaches millions, the memory requirement could exceed typical server capacities (e.g., `1,000,000 * 1440 * 16 bytes = 23 GB`).

**Trade-offs and What Breaks First:**

1.  **Memory Usage for Expiry Tracking:** The `post_comments_by_minute:<post_id>` hashes are the biggest memory consumers. If `N_active_posts` grows into the millions, the 23GB estimate shows this could become a bottleneck.
    *   **Mitigation:**
        *   **Larger Time Buckets:** Instead of minute-level buckets, use 5-minute or 10-minute buckets. This reduces the number of fields in each hash (e.g., `24 * 60 / 5 = 288` buckets for 5-minute buckets), significantly reducing memory. The trade-off is slightly less precise expiry (a comment might be counted for up to 4 minutes longer than 24 hours).
        *   **Probabilistic Counting (HyperLogLog):** Not suitable here as we need exact counts.
        *   **External Storage for Expiry:** If Redis memory becomes a critical issue, the detailed minute-by-minute counts could be stored in a time-series database (e.g., InfluxDB, Cassandra) or even a dedicated table in PostgreSQL, and the expiry worker would query that. This adds complexity and latency to the expiry process but offloads Redis memory.
        *   **Redis Cluster:** Distribute the `post_comments_by_minute` hashes across a Redis cluster.

2.  **Expiry Worker `SCAN` Performance:** If `N_active_posts` is extremely high (tens of millions), iterating through all `post_comments_by_minute:*` keys using `SCAN` can take a long time, potentially causing the expiry process to fall behind.
    *   **Mitigation:**
        *   **More Efficient Expiry Tracking:** Instead of `SCAN` all keys, maintain a `ZSET` of `post_id`s ordered by their *oldest comment timestamp*. The expiry worker would only need to `ZRANGEBYSCORE` this `ZSET` to find posts with expired comments. This adds complexity to updating this `ZSET` when new comments arrive (e.g., if a post gets a new comment, its oldest comment timestamp might not change, but if its *only* old comment expires, its oldest timestamp would become the next oldest).
        *   **Batch Processing:** The `SCAN` approach is fine if the worker can process a batch of keys quickly enough. Running multiple expiry workers in parallel (each with a different `SCAN` cursor or range) could also help.

3.  **Redis Single Threaded Nature:** While Redis is fast, all commands run on a single thread. Heavy `SCAN` operations or very large `ZINCRBY` operations (if `M` is huge) could block other Redis operations for brief periods. However, for typical loads and well-designed data structures, this is rarely an issue for the operations described.

The proposed solution provides excellent read performance (`O(log M + K)`) and good write performance (`O(log M)`). The primary scaling challenge will be the memory consumption and the efficiency of the expiry worker as the number of *active* posts (those with comments in the last 24 hours) grows into the millions.
