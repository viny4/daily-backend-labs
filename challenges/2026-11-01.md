## Scenario

Your team maintains a backend service for a popular online learning platform. A new initiative involves building a "Course Recommendations" system. When a user lands on their dashboard, the system needs to quickly suggest relevant courses.

Initially, a simple approach was taken: fetch the user's enrolled courses, then query for other courses that share common tags or categories. This worked fine when the platform had thousands of courses and hundreds of thousands of users.

Now, the platform has grown significantly. There are over 5 million active users, and the course catalog boasts 500,000 unique courses. Each course can have dozens of tags, and each user can be enrolled in hundreds of courses. The recommendation query, which involves fetching user enrollments and then cross-referencing course tags, has become too slow. It now takes 5-10 seconds to generate recommendations for a single user, leading to a poor user experience and increased load on the primary PostgreSQL database.

The product team insists on near real-time recommendations (under 500ms latency) for the dashboard, and the recommendations should reflect recently added courses and user activity within the last 24 hours. The primary database cannot handle this read load, and complex JOINs or subqueries on the `enrollments` and `courses_tags` tables are now prohibitively expensive.

## Requirements

Design and outline a system to provide personalized course recommendations with a target latency of under 500ms. The system must:

1.  **Decouple recommendation generation** from the primary OLTP database to reduce load.
2.  **Scale to millions of users** querying concurrently.
3.  **Handle eventual consistency** for recommendations (it's acceptable if a course added a few minutes ago isn't immediately recommended, as long as it appears within an hour).
4.  **Prioritize read performance** for the recommendation endpoint.
5.  **Minimize operational complexity** where possible, leveraging existing Python/Node.js/PostgreSQL/TypeScript knowledge.

4.  Explain how a user request for recommendations would flow through your new system.

## Worked answer

### 1. High-level Architecture

The core idea is to pre-compute recommendations offline or near-offline and serve them from a highly optimized, denormalized data store. This decouples the heavy computation from the user-facing request path and offloads the primary OLTP database.

Here's a high-level overview of the proposed architecture:

```mermaid
graph TD
    subgraph User-Facing
        UserBrowser[User Browser/App] --> RecommendationService[Recommendation Service (API)]
        RecommendationService --> RecommendationDataStore[Recommendation Data Store (e.g., Redis/Cassandra)]
    end

    subgraph Backend Services
        RecommendationService -->|Optional: Fallback/Cold Start| PrimaryDB[Primary OLTP DB (PostgreSQL)]
        PrimaryDB -- Replication/CDC --> ChangeDataCapture[Change Data Capture (e.g., Debezium)]
        EnrollmentService[Enrollment Service] -- Event: UserEnrolled --> MessageQueue[Message Queue (e.g., Kafka)]
        CourseService[Course Service] -- Event: CourseUpdated/Added --> MessageQueue
    end

    subgraph Recommendation Generation
        MessageQueue --> RecommendationProcessor[Recommendation Processor (Batch/Stream)]
        RecommendationProcessor --> PrimaryDB[Primary OLTP DB (PostgreSQL)]

    end

**Core Components and Responsibilities:**

1.  **Primary OLTP Database (PostgreSQL):** The source of truth for user enrollments, course details, tags, etc. It will primarily be written to by other services and read by the Recommendation Processor.
2.  **Change Data Capture (CDC) / Eventing:**
    *   **Debezium (or similar):** Monitors the PostgreSQL transaction log for changes to `enrollments`, `courses`, and `course_tags` tables. Publishes these changes as events to a message queue.
    *   **Application Events:** Services like `EnrollmentService` and `CourseService` explicitly publish events (e.g., `UserEnrolled`, `CourseUpdated`, `CourseAdded`) to a message queue when relevant data changes. This is often more robust than pure CDC for specific business events.
3.  **Message Queue (Kafka):** A durable, high-throughput message broker. It buffers events from CDC and application services, ensuring that the Recommendation Processor can consume them reliably, even during spikes or downtime.
4.  **Recommendation Processor (Python/Node.js):**
    *   **Batch Processing:** Periodically (e.g., hourly or daily) re-computes recommendations for a large set of users or all users. This can be a Spark job, a Flink job, or a custom Python script running on a cron. It reads data from the Primary DB (or a read replica) and writes pre-computed recommendations to the Recommendation Data Store.
    *   **Stream Processing:** Consumes events from the Message Queue (e.g., `UserEnrolled`, `CourseAdded`). For `UserEnrolled` events, it might trigger a re-computation for that specific user. For `CourseAdded` events, it might update recommendations for users whose profiles now match the new course. This component is crucial for achieving near real-time updates.
    *   **Recommendation Logic:** Implements the actual recommendation algorithm (e.g., collaborative filtering, content-based filtering based on tags, popularity, recency).
5.  **Recommendation Data Store (Redis/Cassandra):**
    *   A highly optimized, low-latency key-value store or wide-column store. It stores the pre-computed recommendations in a denormalized format, optimized for fast reads by `user_id`.
    *   **Redis:** Excellent for low-latency reads, especially if recommendations are relatively small and fit in memory. Can be scaled horizontally with sharding.
    *   **Cassandra:** Better for very large datasets that don't fit in memory, offering high availability and linear scalability.
6.  **Recommendation Service (API - Python/Node.js/TypeScript):**
    *   A lightweight, stateless microservice.
    *   Exposes an endpoint (e.g., `/users/{user_id}/recommendations`).
    *   Fetches pre-computed recommendations directly from the Recommendation Data Store.
    *   Applies any final filtering or personalization (e.g., removing already enrolled courses, sorting).
    *   Handles caching at the service layer (e.g., in-memory or a local Redis cache) to further reduce latency and load on the Recommendation Data Store.
    *   Includes a fallback mechanism to query the Primary DB directly for recommendations if the Recommendation Data Store is unavailable or doesn't have data for a user (e.g., cold start for a new user). This fallback would be slower but ensures availability.

### 2. Data Model for Recommendation Data Store

Given the requirement for low-latency reads for a specific user's recommendations, a key-value store or a wide-column store is ideal. We'll choose **Redis** for its simplicity, excellent read performance, and existing Python/Node.js ecosystem familiarity. For larger scale or if recommendations don't fit in memory, Cassandra would be a strong alternative.

The data will be denormalized to optimize for the primary query pattern: "get recommendations for `user_id`".

**Data Store Type Justification:**
*   **Redis (Key-Value Store):**
    *   **Pros:** Extremely fast reads (sub-millisecond typically), simple API, supports various data structures (lists, sets, sorted sets), familiar to many developers. Excellent for caching and serving pre-computed data.
    *   **Cons:** Primarily in-memory (can be persistent, but memory is the bottleneck), scaling requires sharding, can be less durable than a distributed database without careful configuration.
    *   **Fit:** Perfect for the "under 500ms latency" requirement, especially if the list of recommendations per user is not excessively large (e.g., a few dozen course IDs).

**Redis Data Structure:**

We will store recommendations as a **Redis List** or **Sorted Set** for each user. A Sorted Set is preferable if we want to store a score alongside each course (e.g., a relevance score) and retrieve them in a specific order.

**Key Structure:**

`recommendations:{user_id}`

**Value Structure (Sorted Set):**

Each member of the sorted set will be a `course_id`, and its score will be a relevance score.

```
Key: "recommendations:12345" (for user_id 12345)

Sorted Set Members:
    "course_id_A" (score: 0.95)
    "course_id_B" (score: 0.88)
    "course_id_C" (score: 0.82)
    ...
    "course_id_Z" (score: 0.51)
```

**Example Redis Commands:**

*   **To store/update recommendations for a user:**
    ```redis
    ZADD recommendations:12345 0.95 course_id_A 0.88 course_id_B 0.82 course_id_C
    ```
    (Note: `ZADD` is additive; to replace, you might `DEL` first or just `ZADD` with new scores, which updates existing members.)

*   **To retrieve recommendations for a user (top N):**
    ```redis
    ZREVRANGE recommendations:12345 0 9 WITHSCORES
    ```
    This retrieves the top 10 course IDs and their scores for user `12345`.

**Alternative Value Structure (JSON string in a String key):**

If we need to store more metadata per recommendation (e.g., course title, image URL, reason for recommendation), we could store a JSON string. However, this requires deserialization on read and makes sorting/filtering within Redis harder.

```
Key: "recommendations:12345"

Value:
```json
[
  {
    "course_id": "course_id_A",
    "score": 0.95,
    "title": "Advanced Python",
    "image_url": "...",
    "tags": ["python", "advanced", "programming"]
  },
  {
    "course_id": "course_id_B",
    "score": 0.88,
    "title": "Distributed Systems Fundamentals",
    "image_url": "...",
    "tags": ["distributed", "systems", "backend"]
  }
]
```

**Justification for Sorted Set over JSON String:**

*   **Performance:** Sorted Sets allow direct retrieval of top N items without deserializing a large JSON blob.
*   **Flexibility:** Scores can be easily updated, and courses can be added/removed from the set without re-writing the entire list.
*   **Simplicity:** The Recommendation Service only needs `course_id`s. It can then fetch full course details from a separate Course Service or cache if needed. This keeps the recommendation payload small and fast.

### 3. Recommendation Generation and Update Process

The process combines batch processing for comprehensive updates and stream processing for near real-time freshness.

**Data Sources:**

*   **Primary OLTP DB (PostgreSQL):**
    *   `users` table: `user_id`, `created_at`, etc.
    *   `enrollments` table: `enrollment_id`, `user_id`, `course_id`, `enrolled_at`.
    *   `courses` table: `course_id`, `title`, `description`, `created_at`, `updated_at`.
    *   `course_tags` table: `course_id`, `tag_id`.
    *   `tags` table: `tag_id`, `tag_name`.

**Recommendation Logic (Simplified Content-Based Example):**

For each user, identify courses they are enrolled in. Find tags associated with these courses. Recommend other courses that share many of these tags, prioritizing recently added courses or popular courses. Exclude courses the user is already enrolled in.

**Process Flow:**

1.  **Initial Batch Computation (Cold Start / Full Refresh):**
    *   **Trigger:** Scheduled daily/hourly cron job (e.g., Airflow, Kubernetes CronJob) or manual trigger.
    *   **Component:** Recommendation Processor (e.g., a Python script using `psycopg2` or an ORM).
    *   **Steps:**
        a.  **Fetch all users:** Read `user_id` from the `users` table.
        b.  **For each user:**
            i.  **Fetch enrolled courses and their tags:**
                ```sql
                SELECT c.course_id, ct.tag_id
                FROM enrollments e
                JOIN course_tags ct ON e.course_id = ct.course_id
                WHERE e.user_id = :user_id;
                ```
            ii. **Aggregate user's tag profile:** Count occurrences of each tag to build a "tag vector" for the user.
            iii. **Identify candidate courses:** Query for courses that are *not* enrolled by the user but share common tags. Prioritize by `courses.created_at` (for new courses) or a popularity metric.
                ```sql
                SELECT c.course_id, COUNT(ct.tag_id) AS common_tags_count, c.created_at
                FROM courses c
                JOIN course_tags ct ON c.course_id = ct.course_id
                WHERE c.course_id NOT IN (SELECT course_id FROM enrollments WHERE user_id = :user_id)
                AND ct.tag_id IN (:user_preferred_tag_ids) -- Tags derived from user's enrolled courses
                GROUP BY c.course_id, c.created_at
                ORDER BY common_tags_count DESC, c.created_at DESC
                LIMIT 50; -- Limit candidates to process
                ```
            iv. **Score and rank:** Assign a relevance score to each candidate course based on tag overlap, recency, popularity, etc.
            v.  **Store in Redis:** Use `ZADD` to store the top N (e.g., 20-50) `course_id`s and their scores in the `recommendations:{user_id}` Sorted Set.
                ```python
                # Example Python code snippet for Redis update
                import redis
                r = redis.Redis(host='localhost', port=6379, db=0)
                user_id = 12345
                recommendations = {
                    "course_id_A": 0.95,
                    "course_id_B": 0.88,
                    "course_id_C": 0.82
                }
                # To replace existing recommendations:
                r.delete(f"recommendations:{user_id}")
                r.zadd(f"recommendations:{user_id}", recommendations)
                ```
        c.  **Error Handling:** Implement retries and dead-letter queues for failed computations.

2.  **Stream Processing (Near Real-time Updates):**
    *   **Trigger:** Events from Message Queue (Kafka).
    *   **Component:** Recommendation Processor (e.g., a Python service using `confluent-kafka-python` or a Node.js service).
    *   **Event Types and Actions:**
        *   **`UserEnrolled` event (from Enrollment Service or CDC on `enrollments` table):**
            *   **Payload:** `{ "user_id": "...", "course_id": "...", "enrolled_at": "..." }`
            *   **Action:** When a user enrolls in a new course, their recommendation profile changes. The processor should:
                1.  Fetch the user's current enrolled courses and their tags (potentially from a cache or Primary DB).
                2.  Re-compute recommendations for *this specific user* using the updated profile.
                3.  Update the `recommendations:{user_id}` Sorted Set in Redis.
                4.  Crucially, remove the newly enrolled `course_id` from the user's recommendations if it was present.
        *   **`CourseAdded` / `CourseUpdated` event (from Course Service or CDC on `courses`/`course_tags` tables):**
            *   **Payload:** `{ "course_id": "...", "tags": ["...", "..."], "created_at": "..." }`
            *   **Action:** When a new course is added or an existing course's tags change, it might become relevant for many users. This is the most challenging event to handle efficiently at scale.
                1.  **Option A (Simpler, less real-time):** Mark a global "dirty" flag or trigger a mini-batch job to re-evaluate recommendations for users whose profiles might match the new/updated course. This could involve querying users who share tags with the new course. This is acceptable given "within an hour" eventual consistency.
                2.  **Option B (More complex, more real-time):** If the recommendation logic is simple (e.g., "new courses with tags X, Y, Z"), the processor could identify users interested in those tags and add the new course to their recommendation lists (if not already enrolled). This requires maintaining an inverted index (tag -> user_ids) which adds complexity.
                3.  **Chosen Approach (for this design):** For `CourseAdded`/`CourseUpdated`, we lean on the hourly/daily batch job to pick up new courses for most users. For *critical* freshness, the stream processor could identify a small subset of "highly active" users whose profiles are a strong match and update them immediately. For the "within an hour" requirement, the batch job is sufficient for most `CourseAdded` events. The stream processor *will* ensure that a newly enrolled course is immediately removed from a user's recommendations.

### 4. User Request Flow

When a user lands on their dashboard and the frontend requests recommendations:

1.  **User Browser/App:** Makes an HTTP GET request to the Recommendation Service.
    *   `GET /api/v1/users/{user_id}/recommendations`
    *   Includes `Authorization` header with user's JWT or session token.

2.  **Recommendation Service (API):**
    *   **Authentication & Authorization:** Validates the user's token and ensures `user_id` in the path matches the authenticated user.
    *   **Cache Check (Optional, In-memory/Local Redis):** Checks its local cache for recommendations for `user_id`. If found and fresh, returns immediately.
    *   **Redis Query:** Constructs the Redis key `recommendations:{user_id}` and queries the Recommendation Data Store (Redis).
        ```python
        # Example Python code in Recommendation Service
        import redis
        r = redis.Redis(host='redis-recommendations.example.com', port=6379, db=0)

        def get_recommendations(user_id: str, limit: int = 10):
            key = f"recommendations:{user_id}"
            # ZREVRANGE returns members in descending order of score
            raw_recs = r.zrevrange(key, 0, limit - 1, withscores=True)
            
            if not raw_recs:
                # Fallback to cold start or slow path
                return _generate_fallback_recommendations(user_id)

            course_ids = [rec[0].decode('utf-8') for rec in raw_recs]
            
            # Optional: Fetch full course details from Course Service (or cache)
            # course_details = course_service.get_course_details(course_ids)
            # Combine course_ids with details and scores
            
            return [{"course_id": cid, "score": score} for cid, score in raw_recs]
        ```
    *   **Response Processing:**
        *   If recommendations are found in Redis:
            *   The service receives a list of `(course_id, score)` tuples.
            *   It might then fetch additional course metadata (title, image, etc.) from a separate Course Service (or a local cache of course data) to enrich the response. This can be done in parallel for multiple courses.
            *   Filters out any courses the user has recently enrolled in (if not already handled by the processor).
            *   Returns a JSON array of recommended courses.
        *   If no recommendations are found for `user_id` in Redis (e.g., new user, cold start, data corruption):
            *   **Fallback Mechanism:** The service can trigger a synchronous, on-demand recommendation generation for this user. This would involve querying the Primary OLTP DB directly, running the recommendation logic, and then storing the result in Redis for future requests. This path will be slower (potentially 1-2 seconds) but ensures a response. This should be rare.
            *   Alternatively, it could return a default set of popular courses or an empty list.
    *   **Response:** Sends a JSON response back to the user's browser/app.

### Going Further

**Trade-offs made between data freshness, consistency, and read latency:**

1.  **Read Latency vs. Data Freshness (Trade-off Accepted):**
    *   **Prioritized:** Read Latency (under 500ms). This was achieved by pre-computing recommendations and serving them from a fast, denormalized data store (Redis).
    *   **Compromised:** Data Freshness. Recommendations are not strictly real-time. There's an acceptable delay for new courses or user activity to be reflected.
        *   New `enrollments` are reflected quickly (within seconds to minutes) because stream processing immediately updates a user's recommendations.
        *   New `courses` or `course_tag` updates might take longer (up to an hour, as per requirement) to propagate to all relevant users, relying on batch jobs or less aggressive stream processing for `CourseAdded` events.
    *   **Why this trade-off?** Achieving sub-500ms latency for 5 million users with complex recommendation logic against a transactional database is impossible. Pre-computation is the only viable path. The product team explicitly stated "eventual consistency for recommendations (it's acceptable if a course added a few minutes ago isn't immediately recommended, as long as it appears within an hour)", which directly informed this decision.

2.  **Consistency vs. Availability (Trade-off Accepted):**
    *   **Prioritized:** Availability. The Recommendation Service is designed to be highly available.
    *   **Compromised:** Strong Consistency. The Recommendation Data Store (Redis) is eventually consistent with the Primary OLTP DB. If the Recommendation Processor fails, or there's a delay in event processing, the recommendations might be temporarily stale.
    *   **Why this trade-off?** Recommendations are a "nice-to-have" feature, not mission-critical like user authentication or course enrollment. Serving slightly stale recommendations is preferable to serving no recommendations or causing the entire dashboard to fail. The fallback mechanism to the Primary DB further enhances availability, albeit with higher latency.

3.  **Operational Complexity vs. Performance/Scale (Trade-off Accepted):**
    *   **Prioritized:** Performance and Scalability. The chosen architecture introduces several new components (Kafka, Redis, Recommendation Processor) to achieve the performance and scale requirements.
    *   **Compromised:** Operational Complexity. This system is significantly more complex than the initial single-database approach. It requires managing Kafka clusters, Redis instances (potentially sharded), and the Recommendation Processor (which could be a distributed stream processing application).
    *   **Why this trade-off?** The initial simple system no longer meets requirements. Growth necessitates a more sophisticated, distributed approach. We tried to minimize complexity by leveraging existing knowledge (Python/Node.js/PostgreSQL) and common patterns (message queues, key-value stores). Using managed services for Kafka and Redis would significantly reduce operational burden.

**Monitoring in Production:**

Monitoring would focus on the health of each component and the end-to-end performance of the recommendation feature.

**Key Metrics and Indicators:**

1.  **Recommendation Service (API):**
    *   **Latency:** P90, P99 latency for `GET /users/{user_id}/recommendations`. Target: < 500ms.
    *   **Error Rate:** HTTP 5xx errors. Should be near 0.
    *   **Throughput:** Requests per second.
    *   **Cache Hit Ratio:** For any in-service caching.
    *   **Fallback Count:** Number of requests hitting the slower fallback path (e.g., querying Primary DB directly). This should be very low.
    *   **Metrics Tool:** Prometheus/Grafana, Datadog.

2.  **Recommendation Data Store (Redis):**
    *   **Latency:** `ZREVRANGE` command latency. Should be < 10ms.
    *   **Memory Usage:** Monitor against allocated memory to prevent evictions or OOM errors.
    *   **CPU Usage:** For Redis processes.
    *   **Network I/O:** Traffic in/out.
    *   **Replication Lag:** If using Redis replicas.
    *   **Metrics Tool:** Redis `INFO` command, cloud provider metrics (e.g., AWS CloudWatch for ElastiCache).

3.  **Recommendation Processor (Batch/Stream):**
    *   **Batch Job Completion Time:** How long does the daily/hourly batch job take? Should be predictable and within its window.
    *   **Batch Job Success Rate:** Percentage of successful runs.
    *   **Stream Processor Lag:** How far behind is the stream processor from the head of the Kafka topic? Measured in messages or time. This is crucial for freshness. Target: seconds to low minutes.
    *   **Processed Events Rate:** Events processed per second.
    *   **Error Rate:** Errors during recommendation computation or Redis writes.
    *   **Resource Utilization:** CPU, memory, network of the processing instances.
    *   **Metrics Tool:** Kafka Consumer Lag Exporter, custom application metrics (e.g., using `statsd` or Prometheus client libraries), cloud provider metrics.

4.  **Message Queue (Kafka):**
    *   **Producer Throughput:** Messages published per second.
    *   **Consumer Throughput:** Messages consumed per second.
    *   **Broker Health:** Disk usage, CPU, network.
    *   **Unconsumed Messages:** Number of messages in topics that haven't been consumed (indicates a backlog or stalled consumer).
    *   **Metrics Tool:** Kafka JMX metrics, Confluent Control Center, cloud provider metrics.

5.  **Primary OLTP DB (PostgreSQL):**
    *   **CPU/Memory/Disk I/O:** Ensure the Recommendation Processor's reads don't overload it.
    *   **Connection Count:** Monitor for spikes from the processor.
    *   **Replication Lag:** If CDC uses a replica.
    *   **Metrics Tool:** `pg_stat_statements`, cloud provider metrics.

**Most Indicative Metrics for System Health:**

*   **Recommendation Service P99 Latency:** Directly reflects user experience. If this spikes, users are seeing slow recommendations.
*   **Recommendation Processor Stream Lag:** The most direct measure of data freshness. If lag grows, recommendations are getting stale.
*   **Recommendation Processor Error Rate:** Indicates issues in the core logic or data pipeline.
*   **Recommendation Data Store Read Latency (P99):** Critical for the performance of the serving layer.
*   **Recommendation Service Fallback Count:** A high number indicates issues with the pre-computation pipeline or Redis, forcing the system onto the slower path.

**What breaks first at ten times the scale (50 million users, 5 million courses):**

1.  **Recommendation Processor (Batch):**
    *   **Issue:** The daily/hourly batch job would take prohibitively long to re-compute recommendations for 50 million users. A full scan and re-computation for all users would become too resource-intensive and might not complete within the desired window.
    *   **Solution:** Move to a more sophisticated incremental batch processing or a purely stream-based approach where only affected users/courses trigger re-computation. Leverage distributed processing frameworks like Apache Spark or Flink more heavily.

2.  **Recommendation Data Store (Redis):**
    *   **Issue:** 50 million users, each with 20-50 course IDs, would require a massive amount of memory. Even with sharding, managing such a large in-memory dataset becomes complex and expensive.
    *   **Solution:** Transition to a distributed wide-column store like **Cassandra** or a NoSQL document database like **MongoDB**. These are designed for petabyte-scale data and high write/read throughput across many nodes, without the memory constraints of Redis. The data model would adapt to Cassandra's partitioning keys.

3.  **Message Queue (Kafka):**
    *   **Issue:** 10x scale means 10x more events (enrollments, course updates). While Kafka is highly scalable, managing a cluster under extreme load requires careful tuning, more brokers, and potentially more partitions.
    *   **Solution:** Ensure Kafka cluster is properly provisioned and monitored. Auto-scaling Kafka brokers or using a managed service becomes even more critical.

4.  **Primary OLTP DB (PostgreSQL):**
    *   **Issue:** Even with CDC, the Recommendation Processor might still need to query the primary DB for full data during re-computations or cold starts. 10x scale would put immense pressure on read replicas if not carefully managed.
    *   **Solution:** Ensure the Recommendation Processor primarily reads from dedicated read replicas or a data warehouse (e.g., a data lake fed by CDC) rather than the primary OLTP database. Reduce the frequency and scope of full table scans.

The current design is a solid foundation for the initial 5 million users, but significant architectural shifts (e.g., Redis to Cassandra, batch to pure stream processing with Spark/Flink) would be necessary to handle 10x growth gracefully.
