## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their marketing campaigns. A critical component is the `Campaign Performance Dashboard`, which aggregates metrics (clicks, impressions, conversions, spend) across hundreds of thousands of campaigns daily. Each campaign typically generates thousands to millions of raw event records (e.g., `click_events`, `impression_events`) per day.

The raw event data is stored in a data warehouse (e.g., Snowflake, BigQuery) and is updated asynchronously. For the dashboard, we compute daily aggregate metrics for each campaign, storing them in a `campaign_daily_metrics` table in PostgreSQL. This table currently has over 500 million rows and grows by millions daily.

The `Campaign Performance Dashboard` allows users to view campaign performance over various date ranges (e.g., "last 7 days", "last 30 days", "custom range"). It also supports filtering by campaign status, client, and a few other dimensions. Currently, queries for a single client viewing their campaigns over the last 30 days take 10-15 seconds to load, often timing out under peak load. This is a P0 issue affecting core business operations.

## Requirements

The primary goal is to reduce the latency of dashboard queries to under 2 seconds for a typical "last 30 days" view for a client with 10,000 campaigns. The solution must scale to support hundreds of concurrent users. Data accuracy is paramount, and aggregates must reflect the data warehouse's state, usually with a delay of up to 1-2 hours. The current system uses Django ORM for most queries, but direct SQL is an option.

## Deliverables

1.  A high-level architectural diagram illustrating the proposed changes to the data flow and query path.
2.  A description of the key technologies and services you would introduce or modify.
3.  An explanation of how the proposed solution addresses the latency and concurrency requirements.
4.  A brief discussion of potential trade-offs (e.g., cost, operational complexity, data freshness).

## Going further

How would you ensure that the aggregated data displayed on the dashboard remains consistent, especially if the underlying raw event data in the data warehouse is occasionally backfilled or corrected for past dates?

### 2. Key technologies and services introduced or modified

The core problem is that PostgreSQL is not optimized for analytical queries over hundreds of millions of rows, especially with `GROUP BY` and `ORDER BY` operations across large date ranges. We need to offload these analytical workloads to specialized data stores.

1.  **ClickHouse (New):** A column-oriented database designed for analytical queries and real-time reporting. It excels at aggregating large volumes of data quickly.
    *   **Purpose:** Store the `campaign_daily_metrics` data, optimized for time-series aggregations and filtering. It will be the primary source for historical metric queries.
    *   **Schema (ClickHouse):**
        ```sql
        CREATE TABLE campaign_daily_metrics_ch (
            client_id UInt32,
            campaign_id UInt64,
            metric_date Date,
            status LowCardinality(String), -- e.g., 'active', 'paused', 'completed'
            clicks UInt64,
            impressions UInt64,
            conversions UInt64,
            spend Decimal64(4) -- Stored as Int64, scaled by 10^4
        ) ENGINE = MergeTree()
        ORDER BY (client_id, campaign_id, metric_date)
        PARTITION BY toYYYYMM(metric_date);
        ```
        *   `MergeTree` engine is standard for analytical workloads.
        *   `ORDER BY (client_id, campaign_id, metric_date)` ensures data is physically sorted this way, optimizing queries that filter by client and campaign over date ranges.
        *   `PARTITION BY toYYYYMM(metric_date)` allows ClickHouse to prune data files not relevant to the query's date range, significantly speeding up queries.
        *   `LowCardinality(String)` is efficient for columns with a limited number of distinct values like `status`.
        *   `Decimal64(4)` for `spend` ensures precision while being efficient.

2.  **Redis (New):** An in-memory data store, ideal for caching frequently accessed data.
    *   **Purpose:** Cache the most recent (e.g., "today", "yesterday") campaign metrics and potentially pre-aggregated "last 7 days" or "last 30 days" summaries for very active campaigns/clients. This reduces load on ClickHouse for the most common, recent data access patterns.
    *   **Data Structure (Redis):** Hash maps for daily metrics, sorted sets for leaderboards, or simple key-value for pre-aggregated summaries.
        *   **Key for daily metrics:** `campaign:{campaign_id}:metrics:{date}`
        *   **Value:** JSON string of metrics: `{"clicks": 1234, "impressions": 5678, ...}`
        *   **Key for pre-aggregated summaries:** `client:{client_id}:campaign:{campaign_id}:summary:last30d`
        *   **Value:** JSON string of aggregated metrics.

3.  **Elasticsearch (New):** A distributed search and analytics engine.
    *   **Purpose:** Store campaign metadata (name, status, client_id, start/end dates) and enable fast filtering and searching for campaigns. When a user applies filters (e.g., "active campaigns for Client X"), Elasticsearch can quickly return the `campaign_id`s that match, which are then used to query ClickHouse for metrics.
    *   **Schema (Elasticsearch):**
        ```json
        PUT /campaigns
        {
          "mappings": {
            "properties": {
              "campaign_id": { "type": "long" },
              "client_id": { "type": "long" },
              "campaign_name": { "type": "text" },
              "status": { "type": "keyword" },
              "start_date": { "type": "date", "format": "yyyy-MM-dd" },
              "end_date": { "type": "date", "format": "yyyy-MM-MM" },
              "tags": { "type": "keyword" }
            }
          }
        }
        ```
        *   `campaign_id`, `client_id` for exact matching.
        *   `campaign_name` for full-text search.
        *   `status`, `tags` as `keyword` for efficient filtering.

4.  **Data Ingestion/Synchronization (Modified):**
    *   The existing daily aggregation job (e.g., dbt, Spark) will now not only write to PostgreSQL but also push data to ClickHouse, Elasticsearch, and potentially trigger Redis cache updates.
    *   **Change Data Capture (CDC) or Batch Sync:** For `campaign_daily_metrics`, a batch job (e.g., using `clickhouse-client` or a custom Python script) will load daily aggregates from PostgreSQL into ClickHouse. For Elasticsearch, a similar process will sync campaign metadata. Redis can be updated directly by the aggregation job or a separate service.

5.  **Backend API (Django - Modified):**
    *   The Django ORM will be bypassed for analytical queries. Instead, the backend will construct direct SQL queries for ClickHouse and API calls for Elasticsearch and Redis.
    *   **Query Orchestration Logic:**
        1.  Receive dashboard request (client_id, date_range, filters).
        2.  Query Elasticsearch to get `campaign_id`s matching filters (e.g., `client_id`, `status`).
        3.  For recent data (e.g., last 2 days), attempt to fetch from Redis cache.
        4.  For historical data or cache misses, construct and execute a ClickHouse query using the `campaign_id`s from Elasticsearch and the requested date range.
        5.  Combine results from Redis and ClickHouse, perform any final calculations/formatting, and return to the client.

### 3. How the proposed solution addresses latency and concurrency

1.  **Latency Reduction:**
    *   **Specialized Data Stores:** ClickHouse is purpose-built for fast analytical queries over large datasets. Its columnar storage, efficient compression, and vectorized query execution allow it to aggregate millions of rows in milliseconds, a task PostgreSQL struggles with.
    *   **Query Pruning:** ClickHouse's `PARTITION BY` and `ORDER BY` clauses ensure that only relevant data blocks are read from disk, drastically reducing I/O for date-range and `client_id`/`campaign_id` filtered queries.
    *   **Indexing and Filtering:** Elasticsearch provides extremely fast filtering and searching on campaign metadata, quickly narrowing down the `campaign_id`s before querying metrics. This avoids full table scans or complex joins in the metrics store.
    *   **Caching with Redis:** For the most recent and frequently accessed data (e.g., "today", "yesterday", or pre-calculated "last 7 days" summaries), Redis provides sub-millisecond access. This offloads a significant portion of the read traffic from ClickHouse, especially for popular dashboards.
    *   **Parallel Query Execution:** The backend can issue parallel requests to Elasticsearch (for campaign IDs) and potentially ClickHouse (for different date segments if needed), then combine results.

2.  **Concurrency Handling:**
    *   **Distributed Systems:** ClickHouse and Elasticsearch are distributed systems designed to scale horizontally. Adding more nodes allows them to handle increased query load and data volume.
    *   **Read Replicas:** Both ClickHouse and Elasticsearch support read replicas, allowing query load to be distributed across multiple instances, preventing a single point of contention.
    *   **Caching Layer:** Redis acts as a highly concurrent, low-latency buffer. Many concurrent users requesting the same popular recent data will hit Redis, not the analytical databases, significantly reducing the load on ClickHouse and Elasticsearch. Redis can handle hundreds of thousands of operations per second.
    *   **Separation of Concerns:** By separating campaign metadata (Elasticsearch) from metrics (ClickHouse) and recent data (Redis), we ensure that different types of queries don't contend for the same resources. A metadata search won't slow down a metrics aggregation.
    *   **Optimized Query Path:** The proposed query path is designed to be efficient:
        1.  **Elasticsearch (Filter):** Fast lookup of `campaign_id`s (e.g., 50-200ms for complex filters).
        2.  **Redis (Cache Hit):** Sub-millisecond response for recent data.
        3.  **ClickHouse (Aggregations):** Fast aggregation over millions of rows (e.g., 500ms - 1.5s for a 30-day range for 10,000 campaigns).
        The combined latency should consistently be under 2 seconds.

### 4. Potential trade-offs

1.  **Cost:**
    *   **Increased Infrastructure:** Introducing ClickHouse, Elasticsearch, and Redis means more servers, storage, and networking. These are specialized systems that require dedicated resources.
    *   **Operational Overhead:** Managed services (e.g., AWS ElastiCache for Redis, AWS OpenSearch for Elasticsearch, Aiven/Altinity for ClickHouse) can mitigate operational complexity but come at a higher cost than self-hosting.
    *   **Data Duplication:** Data is duplicated across PostgreSQL (source of truth for daily aggregates), ClickHouse (analytical store), Elasticsearch (metadata), and Redis (cache). This increases storage costs.

2.  **Operational Complexity:**
    *   **More Systems to Manage:** We are moving from one primary database (PostgreSQL) to four distinct data stores (PostgreSQL, ClickHouse, Elasticsearch, Redis). Each has its own operational requirements for monitoring, backups, patching, scaling, and disaster recovery.
    *   **Data Synchronization:** Maintaining consistency and ensuring data freshness across these systems requires robust ETL/ELT pipelines and monitoring. Failures in synchronization can lead to stale or inconsistent data on the dashboard.
    *   **Debugging:** Tracing issues across multiple distributed systems can be more challenging than debugging a single monolithic database.

3.  **Data Freshness:**
    *   **Acceptable Delay:** The requirement states a delay of up to 1-2 hours is acceptable. This aligns well with batch loading into ClickHouse and Elasticsearch. Redis can be updated more frequently if needed.
    *   **Eventual Consistency:** The system will be eventually consistent. There will be a delay between when data appears in the data warehouse, is processed into `campaign_daily_metrics`, and then propagated to ClickHouse, Elasticsearch, and Redis. Users might observe a slight lag compared to the absolute latest raw data.

4.  **Development Complexity:**
    *   **New Skill Sets:** The team will need to learn how to interact with and optimize queries for ClickHouse, Elasticsearch, and Redis. This includes understanding their query languages, data modeling best practices, and operational nuances.
    *   **Backend Logic:** The Django backend will become more complex, orchestrating queries across multiple data stores rather than relying solely on the ORM.

**What breaks first at ten times the scale?**

At ten times the scale (e.g., 5 billion `campaign_daily_metrics` rows, 1 million campaigns, hundreds of thousands of concurrent users), the primary bottleneck will likely shift:

1.  **ClickHouse Cluster Size:** While ClickHouse scales well, aggregating data for 100,000 campaigns over 30 days (3 million rows per query) for thousands of concurrent users will require a significantly larger ClickHouse cluster (more nodes, more RAM, faster disks). The cost and operational complexity of managing such a cluster will be substantial.
2.  **Data Ingestion Pipeline:** The daily aggregation job and the subsequent synchronization to ClickHouse, Elasticsearch, and Redis will become a major bottleneck. Processing and moving billions of daily events and millions of aggregated metric rows within the acceptable freshness window will require a highly optimized and scalable ETL/ELT pipeline (e.g., Kafka for real-time updates, Spark for large batch processing).
3.  **Redis Cache Management:** With millions of campaigns, managing the Redis cache effectively (what to cache, how long to cache, cache invalidation strategies) becomes more complex. Eviction policies and memory pressure will need careful tuning.
4.  **Elasticsearch Indexing:** Indexing metadata for millions of campaigns and handling high query loads will require a larger Elasticsearch cluster. Re-indexing or schema changes can become time-consuming.

### Going further: Ensuring data consistency with backfills/corrections

Ensuring consistency when underlying raw event data is backfilled or corrected for past dates is a critical challenge. The proposed solution can handle this with a combination of strategies:

1.  **Idempotent Daily Aggregation Jobs:**
    *   The daily aggregation job that populates `campaign_daily_metrics` in PostgreSQL (and subsequently ClickHouse) must be **idempotent**. This means running the job for a specific `metric_date` multiple times should produce the same result.
    *   When a backfill or correction occurs in the raw data warehouse for a past date `D`, the aggregation job for date `D` (and potentially subsequent dates if metrics are cumulative) should be re-run.
    *   **Mechanism:** The aggregation job should perform a `DELETE` then `INSERT` or an `UPSERT` (e.g., `INSERT ... ON CONFLICT UPDATE` in PostgreSQL, or `REPLACE INTO` in ClickHouse) for the affected `(campaign_id, metric_date)` tuples.

2.  **ClickHouse Data Handling:**
    *   **Replacing Data:** ClickHouse's `MergeTree` engine supports replacing data for specific partitions or keys. If the aggregation job for `metric_date` `D` is re-run and new data is generated, we can:
        *   **Option A (Recommended): `ReplacingMergeTree` Engine:** Use the `ReplacingMergeTree` engine in ClickHouse. When new data with the same `(client_id, campaign_id, metric_date)` primary key is inserted, the engine will automatically replace older versions during merges. This simplifies the ingestion logic.
            ```sql
            CREATE TABLE campaign_daily_metrics_ch (
                client_id UInt32,
                campaign_id UInt64,
                metric_date Date,
                status LowCardinality(String),
                clicks UInt64,
                impressions UInt64,
                conversions UInt64,
                spend Decimal64(4)
            ) ENGINE = ReplacingMergeTree() -- Key change here
            ORDER BY (client_id, campaign_id, metric_date)
            PARTITION BY toYYYYMM(metric_date);
            ```
        *   **Option B: `ALTER TABLE ... DELETE` then `INSERT`:** Manually delete the affected rows for the specific `metric_date` and `campaign_id`s, then insert the corrected data. This is more explicit but requires careful coordination.
            ```sql
            ALTER TABLE campaign_daily_metrics_ch DELETE WHERE metric_date = '2023-10-26' AND campaign_id IN (123, 456);
            -- Then insert the corrected data
            INSERT INTO campaign_daily_metrics_ch (...) VALUES (...);
            ```
    *   **Orchestration:** The data pipeline (e.g., Airflow, Prefect) that runs the daily aggregation job should be configured to detect backfills or receive triggers. If a backfill for `2023-10-26` occurs, the pipeline should re-run the aggregation job for `2023-10-26` and push the updated data to ClickHouse.

3.  **Redis Cache Invalidation/Refresh:**
    *   When historical data is corrected, any cached data in Redis for the affected `(campaign_id, metric_date)` keys must be invalidated or refreshed.
    *   **Mechanism:**
        *   **Targeted Invalidation:** The data ingestion pipeline, after pushing corrected data to ClickHouse, should send explicit invalidation messages to Redis for the affected keys (e.g., `DEL campaign:{campaign_id}:metrics:{date}`).
        *   **Time-to-Live (TTL):** Ensure all Redis keys have a reasonable TTL. This provides an eventual consistency fallback – even if invalidation fails, the stale data will eventually expire.
        *   **Re-population:** For pre-aggregated summaries (e.g., "last 30 days"), if any of the underlying daily data changes, the entire summary needs to be re-calculated and re-cached. The pipeline should trigger this re-calculation for affected campaigns.

4.  **Elasticsearch Updates:**
    *   Campaign metadata (e.g., `status`) is less likely to be backfilled in the same way as metrics, but if it is, Elasticsearch documents need to be updated.
    *   **Mechanism:** The data synchronization job for Elasticsearch should perform `UPSERT` operations. If a document with a given `campaign_id` already exists, it should be updated with the new metadata. Elasticsearch's indexing process handles this efficiently.

5.  **Monitoring and Alerting:**
    *   Implement robust monitoring for the data pipelines to detect failures in data synchronization or backfill processing.
    *   Set up alerts for data freshness metrics (e.g., "last updated timestamp" for each campaign/date in ClickHouse vs. data warehouse).

By combining idempotent aggregation, ClickHouse's data replacement capabilities, targeted cache invalidation, and robust pipeline orchestration, we can ensure that the dashboard eventually reflects the corrected historical data with minimal manual intervention. The 1-2 hour acceptable delay provides a sufficient window for these updates to propagate.
