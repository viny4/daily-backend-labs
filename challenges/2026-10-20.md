## Scenario

Your team maintains a critical Node.js microservice responsible for generating various types of user-facing reports (e.g., "Monthly Usage Summary," "Detailed Activity Log") for a large B2B SaaS platform. These reports often involve aggregating data from several internal and external APIs. Due to the diverse nature of customer requirements and the potentially large data volumes, the report generation process can be quite time-consuming, ranging from a few seconds for simple reports to several minutes for complex, high-volume ones.

Currently, report generation is a synchronous HTTP request, which frequently leads to timeouts for larger reports and a poor user experience. Your product team wants to allow users to trigger report generation and then be notified when the report is ready for download. This notification could be via email or an in-app message.

The service must handle concurrent report generation requests from thousands of users across multiple tenants. Each tenant's data must be strictly isolated. The existing `generateReport` function is a pure business logic function that takes report parameters and returns the report data (e.g., a CSV string or a PDF buffer). It is CPU-bound and can take a long time to execute.

## Requirements

Implement an asynchronous report generation mechanism for the Node.js microservice. The solution needs to be robust, scalable, and provide clear feedback to the user. You should consider how to offload the CPU-intensive work without blocking the main event loop and how to manage the lifecycle of these long-running tasks.

Constraints:
*   **Latency:** The initial API request to *trigger* report generation must respond within 500ms.
*   **Concurrency:** The system must be able to handle hundreds of concurrent report generation requests without significant performance degradation.
*   **Failure Modes:** Report generation can fail (e.g., external API timeout, data validation error). The system must gracefully handle these failures and notify the user.
*   **Resource Management:** The CPU-bound nature of `generateReport` should not block other incoming API requests.
*   **No new databases/queues:** You are *not* allowed to introduce new database tables or external queueing systems (e.g., RabbitMQ, SQS, Redis streams) for this particular challenge. You must use existing Node.js and TypeScript capabilities to manage the asynchronous processing within the scope of a single microservice instance.
*   **Existing `generateReport` function:** You cannot modify the internal implementation of the `generateReport` function itself. It remains a synchronous, potentially long-running function.

## Deliverables

1.  A new API endpoint (`POST /reports/generate`) that accepts report parameters and immediately returns a unique `reportId` and a status indicating that report generation has started.
2.  A mechanism to execute the CPU-bound `generateReport` function in the background without blocking the main Node.js event loop.
3.  A new API endpoint (`GET /reports/:reportId/status`) that allows polling for the status of a report (`PENDING`, `GENERATING`, `COMPLETED`, `FAILED`).
4.  Placeholder logic for notifying the user (e.g., a `console.log` indicating "Report X for user Y is ready/failed") when a report completes or fails.

## Going further

Explain the trade-offs of using Node.js worker threads versus child processes for offloading CPU-bound tasks in this scenario. When would you choose one over the other, and what are the main considerations for managing state and communication between the main thread and these background processes?

/**
 * Simulates an existing, synchronous, CPU-bound report generation function.
 * DO NOT MODIFY THIS FUNCTION.
 * It takes a long time to execute.
 */
export function generateReport(params: ReportParameters): string {
  console.log(`[Worker] Starting generation for report: ${params.reportType} for tenant ${params.tenantId}`);
  const startTime = Date.now();

  // Simulate CPU-bound work:
  // A simple busy-wait loop to consume CPU cycles
  let result = 0;
  for (let i = 0; i < 5_000_000_000; i++) { // Adjust this number to control duration

  // Simulate potential failure
  if (Math.random() < 0.1) { // 10% chance of failure
    throw new Error('Simulated external API timeout or data validation error during report generation.');
  }

  const duration = (Date.now() - startTime) / 1000;
  const reportContent = `Report generated for ${params.reportType} (Tenant: ${params.tenantId}, User: ${params.userId}) in ${duration.toFixed(2)}s. Result checksum: ${result.toFixed(0)}`;
  console.log(`[Worker] Finished generation for report: ${params.reportType}. Content length: ${reportContent.length}`);
  return reportContent;
}

### 2. Mechanism to Execute CPU-Bound Work in the Background

Given the constraint "No new databases/queues" and the need to offload CPU-bound work without blocking the main event loop, Node.js Worker Threads are the ideal solution within a single microservice instance. Worker threads allow you to run JavaScript code in parallel in separate threads, each with its own V8 instance, without sharing memory directly (communication happens via message passing). This is perfect for CPU-bound tasks as it prevents them from blocking the main event loop, which is crucial for handling incoming HTTP requests.

We'll create a worker file that will execute our `generateReport` function.

`src/worker.ts`:
```typescript
import { parentPort, workerData } from 'worker_threads';
import { generateReport } from './reportGenerator';
import { ReportParameters } from './types';

// This script runs in a worker thread.
// workerData will contain the parameters passed from the main thread.
const params: ReportParameters = workerData;

try {
  // Execute the CPU-bound synchronous function
  const reportData = generateReport(params);
  // Send the result back to the main thread
  parentPort?.postMessage({ status: 'COMPLETED', reportData });
} catch (error: any) {
  // Send error details back to the main thread
  parentPort?.postMessage({ status: 'FAILED', error: error.message });
}
```
*Explanation*: This `worker.ts` file is designed to be run as a worker thread. It receives `ReportParameters` via `workerData`, executes the synchronous `generateReport` function, and then posts the result (either `COMPLETED` with `reportData` or `FAILED` with an `error` message) back to the main thread using `parentPort.postMessage()`.

### 3. Report Management and API Endpoints

Now, let's integrate this with an Express server to expose the required API endpoints and manage report states. We'll use an in-memory store for report metadata, as new databases are not allowed.

`src/index.ts`:
```typescript
import express from 'express';
import { v4 as uuidv4 } from 'uuid';
import { Worker } from 'worker_threads';
import path from 'path';

import { ReportParameters, ReportMetadata, ReportStatus } from './types';

const app = express();
const PORT = process.env.PORT || 3000;

app.use(express.json());

// In-memory store for report metadata.
// This will be lost if the service restarts.
const reports: Map<string, ReportMetadata> = new Map();

/**
 * Placeholder for user notification logic.
 */
function notifyUser(reportId: string, userId: string, status: ReportStatus, details?: string) {
  if (status === 'COMPLETED') {
    console.log(`[Notification] Report ${reportId} for user ${userId} is READY! Details: ${details}`);
    // In a real system, this would send an email, push notification, or in-app message.
  } else if (status === 'FAILED') {
    console.log(`[Notification] Report ${reportId} for user ${userId} FAILED. Reason: ${details}`);
    // Notify user about the failure.
  }
}

/**
 * POST /reports/generate
 * Triggers asynchronous report generation.
 */
app.post('/reports/generate', async (req, res) => {
  const params: ReportParameters = req.body;

  // Basic validation
  if (!params.tenantId || !params.userId || !params.reportType) {
    return res.status(400).json({ error: 'Missing required report parameters: tenantId, userId, reportType' });
  }

  const reportId = uuidv4();
  const newReport: ReportMetadata = {
    reportId,
    tenantId: params.tenantId,
    userId: params.userId,
    reportType: params.reportType,
    status: 'PENDING',
    createdAt: new Date(),
  };

  reports.set(reportId, newReport);
  console.log(`Report ${reportId} for tenant ${params.tenantId} (user: ${params.userId}) created with status PENDING.`);

  // Offload report generation to a worker thread
  const worker = new Worker(path.resolve(__dirname, 'worker.js'), {
    workerData: params, // Pass parameters to the worker
  });

  // Update report status to GENERATING immediately after worker creation
  newReport.status = 'GENERATING';
  newReport.startedAt = new Date();
  reports.set(reportId, newReport); // Update in map

  worker.on('message', (message: { status: ReportStatus; reportData?: string; error?: string }) => {
    const currentReport = reports.get(reportId);
    if (!currentReport) return; // Should not happen

    currentReport.status = message.status;
    currentReport.completedAt = new Date();

    if (message.status === 'COMPLETED') {
      currentReport.reportData = message.reportData;
      console.log(`Report ${reportId} COMPLETED.`);
      notifyUser(currentReport.reportId, currentReport.userId, 'COMPLETED', 'Your report is ready for download.');
    } else if (message.status === 'FAILED') {
      currentReport.failedReason = message.error;
      console.error(`Report ${reportId} FAILED: ${message.error}`);
      notifyUser(currentReport.reportId, currentReport.userId, 'FAILED', message.error);
    }
    reports.set(reportId, currentReport); // Update final status in map
    worker.terminate(); // Terminate worker after completion/failure
  });

  worker.on('error', (err) => {
    const currentReport = reports.get(reportId);
    if (!currentReport) return;

    currentReport.status = 'FAILED';
    currentReport.completedAt = new Date();
    currentReport.failedReason = `Worker thread error: ${err.message}`;
    reports.set(reportId, currentReport);
    console.error(`Worker for report ${reportId} encountered an error:`, err);
    notifyUser(currentReport.reportId, currentReport.userId, 'FAILED', `Internal server error during report generation: ${err.message}`);
    worker.terminate();
  });

  worker.on('exit', (code) => {
    if (code !== 0) {
      console.error(`Worker for report ${reportId} exited with code ${code}`);
      const currentReport = reports.get(reportId);
      if (currentReport && currentReport.status !== 'COMPLETED' && currentReport.status !== 'FAILED') {
        // If the worker exited unexpectedly before sending a message
        currentReport.status = 'FAILED';
        currentReport.completedAt = new Date();
        currentReport.failedReason = `Worker exited unexpectedly with code ${code}`;
        reports.set(reportId, currentReport);
        notifyUser(currentReport.reportId, currentReport.userId, 'FAILED', `Report generation process terminated unexpectedly.`);
      }
    }
  });

  // Respond immediately, meeting the latency constraint
  res.status(202).json({
    reportId: newReport.reportId,
    status: newReport.status,
    message: 'Report generation started. You can poll the status endpoint.',
  });
});

/**
 * GET /reports/:reportId/status
 * Retrieves the current status of a report.
 */
app.get('/reports/:reportId/status', (req, res) => {
  const { reportId } = req.params;
  const report = reports.get(reportId);

  if (!report) {
    return res.status(404).json({ error: 'Report not found.' });
  }

  // For 'COMPLETED' reports, we might want to return a download URL,
  // but for this exercise, we'll just return the status and data.
  const response: Partial<ReportMetadata> = {
    reportId: report.reportId,
    status: report.status,
    createdAt: report.createdAt,
    startedAt: report.startedAt,
    completedAt: report.completedAt,
    failedReason: report.failedReason,
  };

  if (report.status === 'COMPLETED') {
    // In a real scenario, this would be a URL to download the report from storage (S3, etc.)
    // For this exercise, we return the data directly (which is not scalable for large reports).
    response.reportData = report.reportData;
  }

  res.status(200).json(response);
});

app.listen(PORT, () => {
  console.log(`Server running on http://localhost:${PORT}`);
});
```
*Explanation*:
1.  **`POST /reports/generate`**:
    *   Accepts `ReportParameters` in the request body.
    *   Generates a unique `reportId` using `uuidv4`.
    *   Initializes `ReportMetadata` with `PENDING` status and stores it in the `reports` `Map`.
    *   Crucially, it creates a new `Worker` thread, passing the `reportParameters` as `workerData`. The `worker.js` file (compiled from `worker.ts`) is executed in this new thread.
    *   Immediately updates the report status to `GENERATING` in the main thread's `reports` map.
    *   Sets up event listeners (`'message'`, `'error'`, `'exit'`) for the worker thread.
        *   When the worker posts a `message` (either `COMPLETED` or `FAILED`), the main thread updates the `ReportMetadata` in its `reports` map accordingly.
        *   The `notifyUser` function is called to simulate user notification.
        *   The worker thread is terminated (`worker.terminate()`) to free up resources.
    *   Responds immediately with a `202 Accepted` status, `reportId`, and initial status, fulfilling the 500ms latency constraint.
2.  **`GET /reports/:reportId/status`**:
    *   Retrieves the `reportId` from the URL parameters.
    *   Looks up the `ReportMetadata` in the `reports` `Map`.
    *   Returns the current status and other metadata. For `COMPLETED` reports, it also includes the `reportData` (in a real system, this would be a link to a stored file).
3.  **In-Memory Store (`reports` Map)**: This fulfills the "No new databases" constraint. It stores `ReportMetadata` in the main thread's memory.
4.  **`notifyUser`**: A placeholder function that logs to the console. In a real application, this would integrate with an email service, push notification system, or an in-app messaging queue.

### Trade-offs and Scalability

**Trade-offs Accepted:**

1.  **In-Memory State for Report Metadata**:
    *   **Pro**: Meets the "No new databases/queues" constraint, simple to implement.
    *   **Con**: **Not durable**. All report metadata (and generated report data) is lost if the microservice instance restarts or crashes. This is the biggest limitation for a critical production system.
    *   **Con**: **Not scalable horizontally**. If you run multiple instances of this microservice, each instance will have its own `reports` map, meaning a request to instance A might not find a report triggered on instance B. This breaks tenant isolation if a user requests a report status from a different instance than the one that initiated it.
    *   **Breaks first at ten times the scale**: The in-memory store will be the first point of failure. With thousands of concurrent reports, the memory usage could become problematic, and more importantly, the lack of durability and horizontal scalability makes it unsuitable for production beyond a single, non-critical instance.

2.  **Worker Thread Management**:
    *   **Pro**: Effectively offloads CPU-bound work, preventing the main event loop from blocking.
    *   **Con**: Each worker thread consumes memory (its own V8 instance) and CPU resources. Creating hundreds or thousands of workers concurrently could lead to high memory consumption and context switching overhead, potentially saturating the machine's CPU and memory.
    *   **Con**: No built-in queueing or throttling for worker threads. If 1000 users simultaneously trigger reports, 1000 worker threads will be spawned, potentially overwhelming the system. A more robust solution would involve a worker pool or an external queue.

3.  **Direct Report Data Return**:
    *   **Pro**: Simple for this exercise.
    *   **Con**: `reportData` is stored directly in memory within `ReportMetadata`. This is not scalable for large reports (e.g., multi-GB CSVs or PDFs). In a real system, `reportData` would be a reference (e.g., S3 URL) to a file stored in an external, durable object storage.

**What breaks first at ten times the scale (thousands of concurrent users/reports):**

1.  **Memory Exhaustion**: The in-memory `reports` Map will grow indefinitely, consuming more and more RAM. If reports contain large `reportData` strings, this will accelerate memory exhaustion.
2.  **CPU Saturation/Worker Thread Overhead**: Spawning hundreds or thousands of worker threads simultaneously will likely saturate the CPU cores, leading to high context switching, reduced throughput, and potentially crashing the process due to resource limits.
3.  **Lack of Durability and Horizontal Scalability**: Any restart of the service or scaling to multiple instances will lead to lost report statuses and data, making the system unreliable. Users would lose track of their reports.

### Going Further: Worker Threads vs. Child Processes

Both Node.js Worker Threads and Child Processes can be used to offload CPU-bound tasks. They differ primarily in their isolation, communication mechanisms, and resource usage.

#### Node.js Worker Threads

*   **Mechanism**: Worker threads run in separate threads within the *same Node.js process*. Each worker has its own V8 isolate, event loop, and memory space, but they share the same underlying operating system process.
*   **Isolation**: Less isolated than child processes. While they have separate memory, they share the same process resources (e.g., file descriptors, network connections, process memory limits). An unhandled error in a worker *can* potentially affect the main thread or other workers, though typically it just terminates the worker.
*   **Communication**: Uses message passing (`postMessage`, `on('message')`) via a shared memory buffer (structured cloning algorithm). This is efficient for passing small to medium-sized data.
*   **Resource Usage**: Lighter-weight than child processes. Spawning a worker thread is faster and consumes less memory than a full child process because it doesn't need to re-initialize the entire Node.js runtime.
*   **Use Cases**: Ideal for CPU-bound tasks that need to run in parallel without blocking the main event loop, especially when the tasks are relatively short-lived or don't require full process isolation. Examples: image processing, data compression, heavy computations, parsing large files.

#### Node.js Child Processes

*   **Mechanism**: Child processes run as entirely separate operating system processes, distinct from the main Node.js process. They are spawned using modules like `child_process` (`fork`, `spawn`, `exec`).
*   **Isolation**: Highly isolated. Each child process has its own independent memory space, V8 instance, event loop, and OS resources. A crash or memory leak in a child process will not directly affect the parent process or other child processes.
*   **Communication**: Uses IPC (Inter-Process Communication) channels, typically standard I/O streams (stdin, stdout, stderr) or a special IPC channel for `forked` processes. Communication is generally slower and more resource-intensive than worker thread message passing, especially for large data.
*   **Resource Usage**: Heavier-weight. Spawning a child process involves creating a new OS process, which is slower and consumes more memory (a full Node.js runtime instance for each).
*   **Use Cases**: Suitable for tasks that require strong isolation, might be long-running and prone to crashes, or involve external executables. Examples: running shell commands, executing scripts in different languages, long-running data processing jobs that might consume a lot of memory and could crash independently.

#### When to choose one over the other in this scenario:

*   **Worker Threads (Chosen for this solution)**:
    *   **Why**: The challenge explicitly states "within the scope of a single microservice instance" and "existing Node.js and TypeScript capabilities." Worker threads fit this perfectly. They are designed for CPU-bound tasks in Node.js, allowing the main event loop to remain responsive. They are lighter-weight than child processes, which is beneficial for potentially hundreds of concurrent tasks. The `generateReport` function is pure business logic, so it doesn't need to run external commands or have extreme isolation from the main process.
    *   **Main Considerations**:
        *   **Memory**: While lighter, many concurrent workers can still consume significant memory. Monitoring and potentially pooling workers would be necessary in a production system.
        *   **Error Handling**: Errors in workers are caught by the main thread, allowing for graceful failure handling and status updates.
        *   **Communication**: Message passing is efficient for sending report parameters and receiving results.

*   **Child Processes**:
    *   **When to choose**: If the `generateReport` function were, for example, a Python script, a C++ executable, or a complex data pipeline that might crash the entire Node.js process if run in-thread, then child processes would be a better choice due to their stronger isolation. If the report generation itself was a very long-running, memory-intensive process that could benefit from being completely separate (e.g., to be managed by an external process manager), child processes would also be considered.
    *   **Main Considerations**:
        *   **Overhead**: Higher overhead for spawning and communication.
        *   **Communication**: More complex to manage IPC, especially for structured data.
        *   **Resource Management**: Each child process is a full Node.js instance, leading to higher memory footprint per task.

#### Managing State and Communication

**State Management:**

*   **Main Thread**: The main thread (our Express server) is responsible for managing the overall state of the report generation requests. It holds the `ReportMetadata` (in our case, in the `reports` Map). This state is updated based on messages received from the workers.
*   **Worker/Child Process**: The worker/child process only needs the state relevant to its specific task (the `ReportParameters`). It performs its computation and then communicates the outcome back to the main thread. It generally should not maintain long-term state itself.

**Communication:**

*   **Worker Threads**:
    *   **Main to Worker**: `new Worker(..., { workerData: params })` passes initial data.
    *   **Worker to Main**: `parentPort.postMessage({ status: 'COMPLETED', reportData })` sends results or status updates.
    *   **Main to Worker (after start)**: `worker.postMessage(...)` can send additional messages if needed, but for a one-off task, `workerData` is usually sufficient.
    *   **Error Handling**: `worker.on('error', ...)` and `worker.on('exit', ...)` on the main thread are crucial for handling unexpected worker termination or errors.
*   **Child Processes (e.g., using `fork`)**:
    *   **Main to Child**: `child.send(message)` or passing arguments when spawning.
    *   **Child to Main**: `process.send(message)` from within the child process.
    *   **Standard I/O**: `child.stdout.on('data', ...)` and `child.stderr.on('data', ...)` for logging or streaming data.
    *   **Error Handling**: `child.on('error', ...)` and `child.on('exit', ...)` on the main thread are essential.

In both cases, the communication protocol should be clearly defined (e.g., an object with `status` and `payload` fields) to ensure reliable data exchange and error reporting. For this challenge, worker threads were the more appropriate and efficient choice given the constraints and nature of the task.
