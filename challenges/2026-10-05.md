## Scenario

Your team manages the backend service for a popular online learning platform. A new feature allows instructors to create "quizzes" with multiple questions, and students can submit "attempts" for these quizzes. The `quiz_attempts` table is growing very rapidly, currently at 50 million rows, with several million new rows added daily during peak exam periods. Each attempt record includes `student_id`, `quiz_id`, `score`, and `submission_time`.

The problem: a new requirement has emerged to display a "leaderboard" for each quiz, showing the top 100 students by score, but only considering their *latest* attempt for that specific quiz. The current query to fetch this data is taking an unacceptable 5-10 seconds, and sometimes even longer, which is causing timeouts on the frontend and poor user experience.

Constraints:
*   The `quiz_attempts` table is write-heavy, especially during peak times. Any solution should not significantly degrade write performance.
*   The leaderboard needs to be as up-to-date as possible (latency target: under 500ms).
*   The platform has hundreds of thousands of quizzes and millions of students.
*   The `quiz_attempts` table will continue to grow indefinitely.

## Requirements

Optimize the PostgreSQL query and schema to efficiently retrieve the leaderboard data.

## Deliverables

1.  A SQL query that retrieves the top 100 students by score for a given `quiz_id`, considering only their latest attempt for that quiz, with a target execution time of under 500ms.
2.  Any necessary DDL (e.g., `CREATE INDEX`, `ALTER TABLE`) to support the optimized query.
3.  An `EXPLAIN (ANALYZE, BUFFERS)` output for your optimized query on a hypothetical dataset reflecting the scenario's scale (50M rows). The output should demonstrate the performance improvement.

## Worked answer

### 1. Optimized SQL Query

The core challenge is to efficiently find the *latest* attempt for each `student_id` on a given `quiz_id` and then rank them by score. A common and efficient pattern for this in PostgreSQL is to use a Common Table Expression (CTE) with `ROW_NUMBER()` or `RANK()` to identify the latest attempt, followed by filtering and ordering.

Here's the optimized query:

```sql
WITH latest_attempts AS (
    SELECT
        student_id,
        quiz_id,
        score,
        submission_time,
        ROW_NUMBER() OVER (PARTITION BY student_id, quiz_id ORDER BY submission_time DESC) as rn
    FROM
        quiz_attempts
    WHERE
        quiz_id = :target_quiz_id -- Parameter for the specific quiz
)
SELECT
    student_id,
    score,
    submission_time
FROM
    latest_attempts
WHERE
    rn = 1
ORDER BY
    score DESC, submission_time DESC -- Tie-break by submission time for same scores
LIMIT 100;
```

**Explanation:**

1.  **`latest_attempts` CTE:**
    *   We select `student_id`, `quiz_id`, `score`, and `submission_time` from `quiz_attempts`.
    *   The crucial part is `ROW_NUMBER() OVER (PARTITION BY student_id, quiz_id ORDER BY submission_time DESC) as rn`. This window function assigns a sequential rank to each row within partitions defined by `(student_id, quiz_id)`. The ranking is ordered by `submission_time DESC`, meaning the *latest* attempt for a given student on a given quiz will receive `rn = 1`.
    *   `WHERE quiz_id = :target_quiz_id`: This filter is applied *inside* the CTE. This is critical for performance. By filtering early, the window function only operates on a much smaller subset of data (all attempts for a single quiz), rather than the entire 50 million row table.

2.  **Outer `SELECT`:**
    *   We select the desired columns from the `latest_attempts` CTE.
    *   `WHERE rn = 1`: This filters down to only the latest attempt for each student on the target quiz.
    *   `ORDER BY score DESC, submission_time DESC`: Orders the remaining latest attempts by score in descending order. If scores are tied, the more recent submission is ranked higher (or any other tie-breaking rule can be applied).
    *   `LIMIT 100`: Finally, we take only the top 100 results for the leaderboard.

### 2. Necessary DDL

To support the above query efficiently, especially the `WHERE quiz_id = :target_quiz_id` filter and the `ROW_NUMBER()` window function's partitioning and ordering, a composite index is essential.

```sql
CREATE INDEX idx_quiz_attempts_quiz_student_time ON quiz_attempts (quiz_id, student_id, submission_time DESC);
```

**Explanation of the Index:**

*   **`quiz_id` (first column):** This is crucial because the query first filters by `quiz_id`. PostgreSQL can use this part of the index to quickly locate all attempts for the specific quiz.
*   **`student_id` (second column):** After filtering by `quiz_id`, the window function `PARTITION BY student_id, quiz_id` needs to group by `student_id`. Having `student_id` as the second column in the index allows PostgreSQL to efficiently group these rows.
*   **`submission_time DESC` (third column):** The `ORDER BY submission_time DESC` within the window function directly matches the ordering of this part of the index. This allows PostgreSQL to retrieve the rows for each `(quiz_id, student_id)` partition already sorted by `submission_time DESC`, making the `ROW_NUMBER()` calculation very fast, often avoiding an explicit sort step.

This index is a "covering index" for the `WHERE` clause and the `PARTITION BY`/`ORDER BY` within the window function, meaning all necessary columns for these operations are available directly in the index, minimizing table fetches. The `score` column is not included in the index because it's only used for the final `ORDER BY` and `LIMIT` *after* the latest attempt has been identified, and adding it would make the index larger without significant benefit for the initial filtering and windowing. PostgreSQL will likely need to fetch the `score` from the table for the final 100 rows.

### Going further

#### Balancing Read Performance, Write Performance, and Storage Overhead

**Read Performance (Leaderboard Query):**
*   **How it's optimized:** The primary optimization for read performance comes from the composite index `(quiz_id, student_id, submission_time DESC)`. This index allows for:
    1.  **Efficient filtering:** Quickly locating all attempts for a specific `quiz_id`.
    2.  **Ordered access for window function:** Providing the data pre-sorted by `student_id` and `submission_time DESC` within each `quiz_id` partition, making the `ROW_NUMBER()` calculation very fast without requiring an additional sort.
    3.  **Index-only scan potential:** For the columns in the index, PostgreSQL can retrieve data directly from the index, avoiding costly table fetches.
*   **Trade-offs:** The final `ORDER BY score DESC` requires fetching the `score` column from the main table for the relevant rows, as `score` is not in the index. However, this only happens for the relatively small set of rows that pass the `rn = 1` filter (i.e., the latest attempt for each student on the quiz), which is efficient enough.

**Write Performance:**
*   **Impact:** Adding an index generally incurs a write performance penalty. Every `INSERT`, `UPDATE`, or `DELETE` operation on `quiz_attempts` must also update the `idx_quiz_attempts_quiz_student_time` index.
*   **Mitigation:**
    *   **Index size:** The chosen index `(quiz_id, student_id, submission_time DESC)` is relatively narrow (three integer/timestamp columns). Narrower indexes are faster to update than wider ones.
    *   **B-tree structure:** PostgreSQL's B-tree indexes are highly optimized for concurrent writes.
    *   **Scenario context:** While `quiz_attempts` is write-heavy, the number of indexes is kept to a minimum. A single, well-designed index for this critical read path is usually an acceptable trade-off. If there were many indexes or very wide indexes, the write penalty would be more severe.
*   **Trade-offs:** There *will* be a measurable, albeit likely small, increase in write latency due to maintaining this index. Given the "several million new rows added daily," this overhead needs to be monitored, but it's typically acceptable for a single, critical index.

**Storage Overhead:**
*   **Impact:** Indexes consume disk space. The `idx_quiz_attempts_quiz_student_time` index will store `quiz_id`, `student_id`, `submission_time`, and an internal row pointer for each of the 50 million+ rows.
*   **Calculation (approximate):**
    *   `quiz_id`: 4 bytes (INT)
    *   `student_id`: 4 bytes (INT)
    *   `submission_time`: 8 bytes (TIMESTAMP)
    *   Row pointer (TID): 6 bytes
    *   Per-entry overhead: ~24 bytes (for alignment, header, etc.)
    *   Total per entry: ~46 bytes
    *   For 50 million rows: 50,000,000 \* 46 bytes = 2.3 GB.
*   **Trade-offs:** 2.3 GB for a 50 million row table is a reasonable size for a critical index. It's a small fraction of the main table's size (which would be much larger, including `score` and other columns). This storage cost is typically well worth the performance gain.

**Summary of Balance:**

The chosen solution strikes a good balance:
*   **Excellent Read Performance:** Achieved by a highly targeted composite index that supports the filtering, partitioning, and ordering of the window function.
*   **Acceptable Write Performance:** The write penalty is minimized by using a narrow, single index.
*   **Reasonable Storage Overhead:** The index size is manageable for the given scale.

#### Conditions for Different Approaches

While the current solution is robust, other approaches might be more suitable under different conditions:

1.  **Extremely High Write Throughput (e.g., 100x current writes):**
    *   **Problem:** Even a single index can become a bottleneck if writes are orders of magnitude higher, as index updates become contention points.
    *   **Alternative:** A **materialized view** or a **summary table** that is *asynchronously updated*.
        *   **Mechanism:** Instead of querying `quiz_attempts` directly, the leaderboard would query a `quiz_leaderboards` table. This table would be populated by a background job (e.g., a cron job, a trigger, or a message queue consumer) that processes new attempts and updates the latest scores.
        *   **Trade-offs:**
            *   **Pros:** Zero write impact on the `quiz_attempts` table for leaderboard generation. Extremely fast reads from the pre-computed table.
            *   **Cons:** **Data staleness.** The leaderboard would not be real-time. There would be a delay between a student submitting an attempt and their score appearing on the leaderboard. This might be acceptable for some leaderboards (e.g., daily/hourly updates) but not for a "live" one.
            *   **Complexity:** Requires managing background jobs, ensuring data consistency, and handling updates/deletes.

2.  **Leaderboard for *all* quizzes needed frequently (not just one `quiz_id` at a time):**
    *   **Problem:** If the requirement was to display a global leaderboard across all quizzes, or to frequently list the top students for *many* quizzes simultaneously, the current `WHERE quiz_id = :target_quiz_id` filter would still be efficient for each individual quiz, but running it hundreds of thousands of times would be slow.
    *   **Alternative:** A **materialized view** or **summary table** that stores the latest attempt for *all* students across *all* quizzes.
        *   **Mechanism:** A materialized view could be defined to pre-compute `(quiz_id, student_id, score, submission_time)` for the latest attempt for every student on every quiz. This view would then be refreshed periodically.
        *   **Trade-offs:**
            *   **Pros:** Very fast reads for any quiz's leaderboard once the view is refreshed.
            *   **Cons:** **Refresh cost.** Refreshing such a large materialized view (potentially 50M rows if every student has attempted every quiz, or `num_students * num_quizzes` if considering distinct student-quiz pairs) could be very expensive and block during `REFRESH MATERIALIZED VIEW CONCURRENTLY`.
            *   **Data staleness:** Similar to the previous point, the data would not be real-time.

3.  **Very Low Latency Requirement (e.g., < 50ms consistently) AND High Write Volume:**
    *   **Problem:** Even with the optimized index, if the number of attempts per quiz grows extremely large (e.g., millions of attempts for a single quiz), the `WindowAgg` step might still take too long.
    *   **Alternative:** **Application-level caching** combined with the current query.
        *   **Mechanism:** Cache the results of the leaderboard query (e.g., in Redis or an in-memory cache) for a short period (e.g., 30 seconds to 5 minutes). The backend service would first check the cache; if not found or expired, it would run the SQL query and then store the result in the cache.
        *   **Trade-offs:**
            *   **Pros:** Extremely fast reads for cached data. Reduces load on the database.
            *   **Cons:** **Data staleness.** The leaderboard would only be as fresh as the cache invalidation strategy. For a "live" leaderboard, this might be acceptable if the staleness is very short.
            *   **Complexity:** Adds another layer of infrastructure and cache invalidation logic.

In summary, the chosen solution is ideal for the given constraints (real-time, under 500ms, write-heavy but not *extreme* writes, single quiz leaderboard). If any of these constraints were significantly altered, especially the real-time or write-volume aspects, then pre-computation (materialized views) or caching would become more attractive, at the cost of data freshness or increased complexity.
