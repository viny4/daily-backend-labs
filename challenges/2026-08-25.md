## Worked answer

### 1. Rate Limiter Implementation

We will implement a token bucket algorithm for our rate limiter. This algorithm is well-suited for handling bursts while maintaining a sustained average rate. A token bucket has a capacity (the maximum burst size) and a refill rate (the sustained rate). Tokens are added to the bucket at the refill rate, up to its capacity. To perform an operation, a token must be removed from the bucket. If no tokens are available, the operation must wait.

Our `TokenBucketRateLimiter` class will manage the tokens. When a request to send a transaction comes in, it will attempt to acquire a token. If successful, the operation proceeds immediately. If not, it will wait until a token becomes available. We'll use a `Promise`-based approach to allow asynchronous waiting.

```typescript
// types.ts
export type Transaction = {
  id: string;
  amount: number;
  currency: string;
  // ... other transaction details
};

export type PaymentGatewayResponse = {
  success: boolean;
  transactionId: string;
  message?: string;
  statusCode?: number;
};

export type SendToGatewayFn = (transaction: Transaction) => Promise<PaymentGatewayResponse>;

// TokenBucketRateLimiter.ts
import { SendToGatewayFn, Transaction, PaymentGatewayResponse } from './types';

/**
 * Implements a token bucket rate limiting algorithm.
 * Allows a certain number of operations (tokens) per unit of time,
 * with a maximum burst capacity.
 */
export class TokenBucketRateLimiter {
  private bucketCapacity: number; // Maximum number of tokens the bucket can hold (burst capacity)
  private refillRatePerSecond: number; // How many tokens are added per second
  private tokens: number; // Current number of tokens in the bucket
  private lastRefillTime: number; // Timestamp of the last refill (ms)
  private pendingRequests: Array<{ resolve: () => void; reject: (err: Error) => void }>; // Queue for waiting requests

  /**
   * @param capacity The maximum number of tokens the bucket can hold (burst capacity).
   * @param ratePerSecond The rate at which tokens are added to the bucket per second.
   */
  constructor(capacity: number, ratePerSecond: number) {
    if (capacity <= 0 || ratePerSecond <= 0) {
      throw new Error('Capacity and rate per second must be positive numbers.');
    }
    this.bucketCapacity = capacity;
    this.refillRatePerSecond = ratePerSecond;
    this.tokens = capacity; // Start with a full bucket
    this.lastRefillTime = Date.now();
    this.pendingRequests = [];

    // Periodically refill tokens to handle cases where no requests are actively being processed
    // but time is passing. This ensures the bucket fills up even when idle.
    setInterval(() => this.refillTokens(), 100); // Refill every 100ms
  }

  /**
   * Refills the token bucket based on elapsed time since the last refill.
   * This method is called internally and also periodically by a timer.
   */
  private refillTokens(): void {
    const now = Date.now();
    const timeElapsedMs = now - this.lastRefillTime;
    this.lastRefillTime = now;

    const tokensToAdd = (timeElapsedMs / 1000) * this.refillRatePerSecond;
    this.tokens = Math.min(this.bucketCapacity, this.tokens + tokensToAdd);

    // If there are pending requests and we now have tokens, process them.
    this.processPendingRequests();
  }

  /**
   * Attempts to acquire a token. If no token is available, the request
   * is queued and will wait until a token becomes available.
   * @returns A Promise that resolves when a token is acquired.
   */
  private acquireToken(): Promise<void> {
    this.refillTokens(); // Always try to refill before checking tokens

    if (this.tokens >= 1) {
      this.tokens--;
      return Promise.resolve();
    } else {
      // No tokens available, queue the request
      return new Promise<void>((resolve, reject) => {
        this.pendingRequests.push({ resolve, reject });
      });
    }
  }

  /**
   * Processes pending requests in the queue if tokens are available.
   */
  private processPendingRequests(): void {
    while (this.tokens >= 1 && this.pendingRequests.length > 0) {
      this.tokens--;
      const { resolve } = this.pendingRequests.shift()!;
      resolve();
    }
  }

  /**
   * Wraps an asynchronous function with rate limiting.
   * The wrapped function will only execute when a token is available.
   *
   * @param fn The function to be rate-limited.
   * @returns A new function that is rate-limited.
   */
  public wrap<T extends any[], R>(fn: (...args: T) => Promise<R>): (...args: T) => Promise<R> {
    return async (...args: T): Promise<R> => {
      await this.acquireToken(); // Wait for a token
      return fn(...args); // Execute the original function
    };
  }
}
```

The `TokenBucketRateLimiter` class:
*   **`bucketCapacity`**: Set to `100` to allow for a burst of 100 requests.
*   **`refillRatePerSecond`**: Set to `100` to maintain the 100 requests/second average.
*   **`tokens`**: Tracks the current number of available tokens.
*   **`lastRefillTime`**: Used to calculate how many tokens should be added based on elapsed time.
*   **`pendingRequests`**: An array of `Promise` resolvers/rejecters. When a request needs to wait, its `resolve` function is stored here. When tokens become available, these `resolve` functions are called in order, effectively releasing the waiting requests.
*   **`refillTokens()`**: Calculates and adds tokens to the bucket based on the time elapsed since the last refill. It also triggers `processPendingRequests` to release any waiting requests if tokens are now available.
*   **`acquireToken()`**: The core logic. It first calls `refillTokens()` to ensure the token count is up-to-date. If tokens are available, it decrements the count and resolves immediately. Otherwise, it creates a new `Promise` and adds its `resolve` and `reject` functions to `pendingRequests`.
*   **`processPendingRequests()`**: Iterates through `pendingRequests` and resolves them as long as tokens are available. This ensures fairness (FIFO) for waiting requests.
*   **`wrap<T, R>(fn: (...args: T) => Promise<R>): (...args: T) => Promise<R>`**: This higher-order function takes an asynchronous function (`fn`) and returns a new function. The new function first calls `acquireToken()` (which might wait) and then executes the original `fn`.

### Trade-offs and Scalability

**Trade-offs Accepted:**

1.  **In-memory Queue and Rate Limiter State**: The current solution uses an in-memory `Array` for the transaction queue and an in-memory `TokenBucketRateLimiter` instance. This is simple and performs well within a single Node.js process.
2.  **Fairness (FIFO)**: The `pendingRequests` array in the `TokenBucketRateLimiter` and the `transactionQueue` both operate on a First-In, First-Out (FIFO) principle. This ensures that older transactions are processed before newer ones, which is generally desirable for fairness.
3.  **Latency under High Load**: When the incoming request rate significantly exceeds the outgoing rate limit, transactions will accumulate in the `transactionQueue`. This will inevitably increase the end-to-end latency for individual transactions. The system prioritizes avoiding `429` errors over immediate processing of every transaction.
4.  **Resource Usage**: The in-memory queue will consume memory proportional to the backlog. Under extreme, sustained overload, this could lead to memory exhaustion.
5.  **Single Point of Failure**: Being a single Node.js process, if the process crashes, all in-memory queue data and rate limiter state are lost. This is acceptable given the constraint "The solution must run within a single Node.js process."

**What Breaks First at Ten Times the Scale (1000 req/s limit, 10000 req/s incoming):**

At ten times the scale, with an incoming load of 10,000 requests/second and a gateway limit of 1,000 requests/second:

1.  **Memory Exhaustion**: The most immediate and critical failure point would be the in-memory `transactionQueue`. With a sustained difference of 9,000 transactions/second, the queue would grow by 9,000 transactions every second. Even if each `Transaction` object is small (e.g., 1KB), this would be 9MB/second, leading to GBs of memory consumption very quickly. The Node.js process would likely crash due to out-of-memory errors.
2.  **CPU Contention / Event Loop Blocking**: While Node.js is non-blocking, managing a very large in-memory queue (frequent `push`/`shift` operations on a large array) and the overhead of many pending promises in the rate limiter could start to put pressure on the event loop, leading to increased processing latency for even non-rate-limited operations.
3.  **Increased Latency**: Transactions would experience extremely high latencies, potentially minutes or hours, as they wait in a massive queue. This would render the service unusable from a user perspective long before a crash.
4.  **Loss of Data on Crash**: If the process crashes (e.g., due to memory exhaustion), all transactions in the in-memory queue that haven't been sent to the gateway would be lost. For mission-critical financial transactions, this is unacceptable.

To address these issues at higher scales, one would need:
*   **Persistent Queue**: Replace the in-memory `Array` with a robust, persistent message queue (e.g., Kafka, RabbitMQ, AWS SQS). This provides durability, allows for horizontal scaling of consumers, and offloads memory pressure.
*   **Distributed Rate Limiting**: If multiple Node.js instances were processing transactions, a distributed rate limiter (e.g., using Redis or a dedicated rate-limiting service) would be necessary to coordinate across instances and enforce a global limit.
*   **Backpressure Mechanisms**: Implement explicit backpressure to upstream services, signaling when the service is overloaded and cannot accept more requests, rather than just buffering indefinitely.

### Going Further: Token Bucket vs. Leaky Bucket

Both token bucket and leaky bucket algorithms are commonly used for rate limiting, but they have different characteristics regarding how they handle bursts and smooth traffic.

**Token Bucket Algorithm (Implemented Solution):**

*   **How it works**: A bucket holds "tokens." Tokens are added to the bucket at a fixed rate (the refill rate), up to a maximum capacity (the burst capacity). Each operation consumes one token. If no tokens are available, the operation must wait until a token is added.
*   **Throughput**: Allows for a sustained average rate equal to the refill rate.
*   **Burst Handling**: Excellent. It allows bursts of traffic up to the `bucketCapacity` to pass through immediately. If the bucket is full, a burst of `N` requests will be processed as fast as the system can handle them, up to `N` tokens. This means a service can respond quickly to sudden spikes in demand without being immediately throttled, as long as the burst doesn't exceed the bucket's capacity.
*   **Traffic Smoothing**: Does *not* smooth traffic. While it limits the average rate, it allows bursts. The output rate can be highly variable, matching the input rate for short periods (up to the burst capacity).
*   **Use Case Fit for Scenario**:
    *   **Pros**: This is a good fit for our scenario. The payment gateway has a strict limit of 100 req/s, but it doesn't explicitly state that it cannot handle *any* burst. Allowing a burst of 100 requests (our capacity) means that if we receive 100 requests simultaneously after a period of idleness, they can all be sent out immediately. This minimizes latency for those initial requests and provides better responsiveness under intermittent load. It proactively avoids `429` errors by ensuring we only send when we have a "token" to do so.
    *   **Cons**: If the incoming load consistently exceeds the refill rate, the queue will grow indefinitely, leading to increased latency for transactions. However, this is a property of any rate limiter when input > output, and the token bucket effectively buffers this excess.

**Leaky Bucket Algorithm:**

*   **How it works**: Imagine a bucket with a hole in the bottom. Incoming requests are "water" poured into the bucket. The water "leaks out" at a constant rate (the output rate). If the bucket overflows, incoming requests are discarded (or rejected).
*   **Throughput**: Allows for a sustained average rate equal to the leak rate.
*   **Burst Handling**: Poor. It strictly smooths traffic. Any burst beyond the bucket's capacity will be immediately dropped/rejected. Even if the bucket has space, the output rate remains constant, meaning a burst will fill the bucket and then be processed at the steady leak rate, leading to higher latency for burst requests.
*   **Traffic Smoothing**: Excellent. It produces a very smooth, constant output rate, regardless of how bursty the input traffic is (as long as it doesn't overflow).
*   **Use Case Fit for Scenario**:
    *   **Pros**: If the payment gateway was extremely sensitive to *any* deviation from a perfectly smooth 100 req/s, a leaky bucket would be ideal. It guarantees a constant output rate.
    *   **Cons**: For our scenario, a leaky bucket would be less desirable. If we received 100 requests in a single millisecond, a leaky bucket would only send them out one by one over the next second. This would introduce unnecessary latency for those requests, even though the gateway might be able to handle a burst of 100 requests within a second. The requirement to minimize latency for individual transactions while respecting the limit suggests that allowing controlled bursts (which a token bucket does) is better. A leaky bucket would also likely discard requests if the bucket capacity is exceeded, which is not what we want for mission-critical transactions (we prefer to queue them).

**Conclusion for this Scenario:**

The **Token Bucket** algorithm is superior for this specific scenario. It allows for handling short bursts of incoming requests (up to the bucket capacity) without immediately throttling them, which helps minimize latency for those requests. It still strictly enforces the average rate limit of 100 requests per second. The problem statement emphasizes "resilient to short bursts" and "minimize latency for individual transactions," both of which are strengths of the token bucket model. A leaky bucket would be too rigid, forcing all traffic into a perfectly smooth stream, which would increase latency for bursty inputs even if the average rate is respected.
