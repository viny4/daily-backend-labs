## Scenario

Your team maintains the backend for a large B2B SaaS platform that processes and stores various types of financial data for thousands of enterprise clients. A critical component is the **`audit_log` service**, which records every significant action performed by users within the system. This includes actions like "Invoice created," "Payment processed," "User role updated," etc.

The `audit_log` service currently writes directly to a PostgreSQL table named `audit_events`. Each event contains a timestamp, user ID, tenant ID, action type, and a JSONB payload with details specific to the action.

The problem: Our largest enterprise clients, which account for 80% of our daily events, are now running into issues. They regularly query their audit logs for compliance and reporting. Specifically, a common query is "show me all 'Payment processed' events for tenant X in the last 30 days." These queries are now taking 10-15 seconds for these large clients, which is unacceptable. The `audit_events` table has grown to over 500 million rows, with approximately 100 million new rows added monthly across all tenants. The database I/O is consistently high, impacting other critical services.

## Requirements

Design a system to improve the query performance and write scalability of the `audit_log` service, specifically for large tenants querying their recent activity. The solution must:

*   Drastically reduce the latency for queries like "all 'Payment processed' events for tenant X in the last 30 days" to under 1 second.
*   Support the current write volume of 100 million new rows per month, with potential for 2-3x growth in the next year.
*   Maintain data integrity and ensure all audit events are eventually durable and queryable.
*   Minimize changes to the existing application-level querying logic where possible (i.e., the API surface for fetching audit logs should remain largely the same).
*   Handle the fact that older data (beyond 90 days) is queried far less frequently but still needs to be available for compliance, albeit with potentially higher latency.

## Deliverables

1.  A high-level diagram (text or ASCII art is fine) showing the architecture of the redesigned `audit_log` service, highlighting new components and data flows.
2.  A brief description of the core technologies you would use for each new or significantly modified component.
3.  An explanation of how the common "recent events for a specific tenant" query would be handled in the new system, detailing the read path.
4.  A discussion of how the system handles eventual consistency or data durability, and any trade-offs made.

## Going further

### 2. Core Technologies

*   **Kafka Cluster**:
    *   **Purpose**: Acts as a highly scalable, durable, and fault-tolerant message broker for ingesting audit events. It decouples the write path from the read path and allows for asynchronous processing.
    *   **Why**: Handles high write throughput (100M+ events/month) and provides ordered, replayable streams. This is crucial for ensuring no events are lost and for enabling multiple consumers (e.g., Elasticsearch, PostgreSQL, future consumers).
*   **Audit Log Service (Producer)**:
    *   **Purpose**: The existing service, modified to publish audit events to Kafka instead of directly writing to PostgreSQL.
    *   **Why**: Minimal changes to the existing application logic. It pushes events to Kafka and receives an acknowledgement, improving its immediate response time.
*   **Kafka Consumer (Data Sink)**:
    *   **Purpose**: A new microservice responsible for consuming events from Kafka and persisting them to the appropriate storage layers.
    *   **Why**: Decouples the ingestion from the persistence logic. It can be scaled independently and implement robust error handling, batching, and retries for writes to downstream systems.
*   **Elasticsearch Cluster**:
    *   **Purpose**: Primary storage for recent audit events (e.g., last 90 days). Optimized for fast, full-text, and filtered queries.
    *   **Why**: Excels at the specific query pattern "all 'Payment processed' events for tenant X in the last 30 days" due to its inverted index and ability to handle JSONB-like payloads efficiently. It provides sub-second latency for these types of queries. It scales horizontally for both reads and writes.
*   **PostgreSQL Database (Modified)**:
    *   **Purpose**: Retains its role for historical data (e.g., 90 days to 1 year or more) and as a durable, transactional backup for all data. It will be used for less frequent, complex analytical queries or as a fallback.
    *   **Why**: Leverage existing investment. While not optimal for recent high-volume queries, it's a reliable relational database for structured data and can handle long-term storage, especially if partitioned effectively. We'd likely use partitioning (e.g., by `tenant_id` or `timestamp`) to manage table size.
*   **Object Storage (e.g., AWS S3, Google Cloud Storage)**:
    *   **Purpose**: Long-term, cost-effective archival storage for all audit events, typically beyond 1 year.
    *   **Why**: Extremely cheap and durable for infrequently accessed data. Events can be exported from PostgreSQL or directly from Kafka (e.g., using Kafka Connect S3 Sink) in formats like Parquet or JSON. Queries against this layer would be slower, likely involving data lake tools (e.g., Presto, Athena).

### 3. Read Path for "Recent Events for a Specific Tenant" Query

The common query "show me all 'Payment processed' events for tenant X in the last 30 days" will be primarily served by Elasticsearch.

1.  **Application API (Read Path)**: The user's request, e.g., `GET /api/v1/audit_logs?tenant_id=X&action_type=PaymentProcessed&start_date=...&end_date=...`, hits the API gateway.
2.  **Audit Log Service (Query API)**: This service receives the request. It's responsible for routing the query to the appropriate data store.
3.  **Query Routing Logic**: Based on the query parameters, specifically the time range, the service decides where to query:
    *   If the query falls within the "recent" window (e.g., last 90 days), it queries Elasticsearch.
    *   If the query falls outside this window but within the "historical" window (e.g., 90 days to 1 year), it queries PostgreSQL.
    *   If the query is for "archival" data (beyond 1 year), it might return an error suggesting a different interface or trigger an asynchronous data retrieval job from object storage.
4.  **Elasticsearch Query**: For the given query, the service constructs an Elasticsearch query.

    Example Elasticsearch query (pseudo-JSON):
    ```json
    GET /audit_events_index/_search
    {
      "query": {
        "bool": {
          "filter": [
            { "term": { "tenant_id.keyword": "tenant_X" } },
            { "term": { "action_type.keyword": "Payment processed" } },
            { "range": { "timestamp": { "gte": "now-30d/d", "lte": "now/d" } } }
          ]
        }
      },
      "sort": [
        { "timestamp": { "order": "desc" } }
      ],
      "size": 100 // Or whatever pagination limit is appropriate
    }
    ```
    *   `tenant_id.keyword`: Using a `keyword` field type ensures exact matching and efficient filtering for `tenant_id`.
    *   `action_type.keyword`: Similar to `tenant_id`, `action_type` benefits from `keyword` type.
    *   `timestamp`: Indexed as a `date` type, allowing for efficient range queries.
    *   `bool` query with `filter` clauses ensures that these conditions are evaluated for caching and performance, as `filter` queries do not calculate relevance scores.
5.  **Results Aggregation/Transformation**: Elasticsearch returns the matching documents very quickly. The Audit Log Service transforms these documents into the expected API response format and returns them to the client.

This approach drastically reduces latency because Elasticsearch is specifically designed for these types of filtered time-series queries on large datasets, leveraging its inverted index and distributed nature.

### 4. Eventual Consistency and Data Durability Trade-offs

This design introduces eventual consistency between the Kafka topic and the downstream storage systems (Elasticsearch, PostgreSQL, Object Storage).

*   **Data Durability**:
    *   **Kafka**: Events are durable once written to Kafka. Kafka's replication (e.g., 3 replicas across different brokers) ensures that even if a broker fails, the data is not lost. The producer can be configured for `acks=all` to guarantee that the message is replicated before acknowledging success.
    *   **Kafka Consumer (Data Sink)**: This service is designed to be resilient. It uses Kafka's consumer group offset management to track its progress. If the consumer fails, it can restart and resume processing from the last committed offset, preventing data loss. It implements retry mechanisms for writes to Elasticsearch and PostgreSQL.
    *   **Elasticsearch**: Data is durable once indexed and replicated within the Elasticsearch cluster (e.g., 1 primary shard + 1 replica shard).
    *   **PostgreSQL**: Data is durable once committed to the database, leveraging its ACID properties and transactional guarantees.
    *   **Object Storage**: Extremely high durability (e.g., 99.999999999% annual durability for S3).

*   **Eventual Consistency**:
    *   There will be a small delay (typically seconds to minutes, depending on Kafka consumer lag and batching) between an event being successfully published to Kafka and it becoming queryable in Elasticsearch or PostgreSQL.
    *   **Trade-off**: The immediate consistency of a direct database write is sacrificed for significantly improved write scalability and read performance. For audit logs, this trade-off is generally acceptable. Users understand that an action might take a moment to appear in a log. The critical aspect is that *all* events are eventually recorded and queryable, not necessarily instantaneously.
    *   **Mitigation**:
        *   **Monitoring**: Closely monitor Kafka consumer lag to ensure processing delays remain within acceptable bounds.
        *   **Idempotency**: The Kafka Consumer (Data Sink) must ensure idempotency when writing to Elasticsearch and PostgreSQL. If an event is reprocessed (e.g., due to a consumer restart), it shouldn't create duplicate entries. This can be achieved by using a unique event ID (e.g., `event_id` from the original event) as the document ID in Elasticsearch and as a primary key or unique constraint in PostgreSQL.
        *   **Error Handling**: Robust dead-letter queue (DLQ) mechanisms for events that cannot be processed after multiple retries. These events can be manually inspected and reprocessed.

*   **Data Integrity**:
    *   Kafka's ordered delivery within a partition helps maintain the sequence of events.
    *   The `event_id` (or a similar unique identifier) should be generated at the source (Audit Log Service Producer) to ensure uniqueness across all storage layers and facilitate idempotency.
    *   Regular reconciliation checks can be implemented to compare event counts or checksums between storage layers (e.g., Kafka topic offsets vs. counts in Elasticsearch/PostgreSQL) to detect discrepancies.

*   **Scalability at 10x**:
    *   **Kafka**: Scales horizontally by adding more brokers and partitions.
    *   **Kafka Consumer**: Scales horizontally by adding more instances to the consumer group.
    *   **Elasticsearch**: Scales horizontally by adding more nodes and shards. Sharding strategy (e.g., by `tenant_id` or `timestamp`) is crucial.
    *   **PostgreSQL**: Will become the bottleneck for writes if it's still receiving all events. Partitioning by `tenant_id` and `timestamp` will be essential. At 10x scale, it might need to be sharded or replaced with a distributed SQL database if it needs to serve high-volume queries for historical data. For archival, it would primarily be a sink for data destined for object storage.
    *   **Object Storage**: Infinitely scalable.

### Going Further: Monitoring the Redesigned `audit_log` System

Monitoring is critical for a distributed system like this. We'd use a combination of metrics, logging, and tracing.

#### 1. Data Ingestion Rates

*   **Kafka Producer Metrics**:
    *   `records-per-second`: Rate of events published by the Audit Log Service (Producer) to Kafka.
    *   `byte-rate`: Throughput of data sent to Kafka.
    *   `request-latency-avg/max`: Latency for producers to send messages to Kafka.
    *   `failed-records-per-second`: Number of messages that failed to publish.
*   **Kafka Broker Metrics**:
    *   `messages-in-per-sec`: Total messages received by the Kafka cluster.
    *   `bytes-in-per-sec`: Total bytes received by the Kafka cluster.
    *   Disk usage, CPU, memory for brokers.
*   **Kafka Consumer Metrics**:
    *   `records-lag-max`: The maximum lag (in number of records) for any partition in the consumer group. This is the most critical metric for ingestion health. High lag indicates the consumer cannot keep up.
    *   `records-consumed-rate`: Rate of events processed by the Kafka Consumer (Data Sink).
    *   `commit-latency-avg/max`: Time taken to commit offsets to Kafka.
*   **Downstream Write Metrics (Elasticsearch/PostgreSQL)**:
    *   `documents-indexed-per-second` (Elasticsearch): Rate of documents written.
    *   `bulk-request-latency-avg/max` (Elasticsearch): Latency of bulk indexing operations.
    *   `rows-inserted-per-second` (PostgreSQL): Rate of rows inserted.
    *   `database-connection-pool-usage`: Monitor connection pool health.
    *   Error rates for writes to both systems.

**Alerting**: Set alerts for high Kafka consumer lag, significant drops in ingestion rates, or increased write error rates to Elasticsearch/PostgreSQL.

#### 2. Query Latency for Critical Paths

*   **Application API (Read Path) Metrics**:
    *   `request-duration-p99/p95/avg`: Latency for the "recent events for a specific tenant" API endpoint. This is the end-user experience metric.
    *   `error-rate`: Percentage of failed requests.
*   **Audit Log Service (Query API) Metrics**:
    *   `elasticsearch-query-latency-p99/p95/avg`: Latency of queries sent to Elasticsearch.
    *   `postgresql-query-latency-p99/p95/avg`: Latency of queries sent to PostgreSQL.
    *   `query-routing-decision-count`: Number of queries routed to Elasticsearch vs. PostgreSQL.
*   **Elasticsearch Cluster Metrics**:
    *   `search-latency-avg/p99`: Average and percentile search latency.
    *   `query-cache-hit-ratio`: Effectiveness of query caching.
    *   `cpu-usage`, `memory-usage`, `disk-iops`, `network-iops` for Elasticsearch nodes.
    *   `shard-health`: Ensure all shards are healthy and allocated.
*   **PostgreSQL Database Metrics**:
    *   `query-execution-time-avg/p99`: For specific audit log queries.
    *   `index-hit-ratio`: Effectiveness of indexes.
    *   `disk-iops`, `cpu-usage`, `memory-usage`.

**Alerting**: Set alerts for P99 latency exceeding 1 second for critical queries, increased error rates, or resource saturation on Elasticsearch/PostgreSQL.

#### 3. Data Consistency Across Different Storage Layers

*   **Reconciliation Jobs**:
    *   Run periodic (e.g., daily) background jobs to compare data counts or checksums between layers for a given time window or tenant.
    *   Example: Compare the number of events for `tenant_X` for "yesterday" in Elasticsearch vs. PostgreSQL.
    *   Example: Compare the number of events published to Kafka (based on offsets) vs. indexed in Elasticsearch.
*   **Idempotency Checks**: Monitor logs for warnings/errors related to duplicate key violations in PostgreSQL or failed upserts in Elasticsearch, which might indicate issues with idempotency logic.
*   **Dead Letter Queue (DLQ) Monitoring**:
    *   `dlq-message-count`: Number of messages in the DLQ.
    *   `dlq-processing-rate`: Rate at which messages are being consumed from the DLQ (manual intervention).
    *   **Alerting**: Alert if the DLQ message count grows unexpectedly or if messages remain unprocessed for too long.
*   **End-to-End Data Flow Tracing**:
    *   Implement distributed tracing (e.g., OpenTelemetry) to trace an audit event from its creation in the application, through Kafka, to its persistence in Elasticsearch and PostgreSQL. This helps visualize latency at each hop and identify bottlenecks or points of failure.

#### General Monitoring Tools

*   **Metrics**: Prometheus + Grafana for time-series metrics collection and visualization.
*   **Logging**: Centralized logging system (e.g., ELK stack, Splunk, Datadog Logs) for collecting logs from all services. Structured logging is essential.
*   **Tracing**: Jaeger or Zipkin for distributed tracing.
*   **Alerting**: PagerDuty or Opsgenie integrated with Prometheus Alertmanager.

By combining these monitoring strategies, the team can gain deep insights into the health, performance, and data integrity of the redesigned audit log system, allowing for proactive issue detection and resolution.
