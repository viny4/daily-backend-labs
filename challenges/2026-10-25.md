## Scenario

Your team maintains a critical backend service for a growing online banking platform. This service is responsible for handling all customer financial transactions (deposits, withdrawals, transfers). Due to regulatory requirements and the need for high availability, every transaction must be durably recorded and processed exactly once, even in the face of network partitions, service restarts, or concurrent updates.

The current architecture uses a single PostgreSQL database instance, and transaction processing is synchronous. However, with increasing transaction volume (averaging 5,000 transactions per second, with peak bursts up to 20,000 TPS), the synchronous approach is becoming a bottleneck. Latency for critical transactions is creeping up, and the risk of a single point of failure for the transaction processing logic is unacceptable. You need to redesign the transaction processing pipeline to be more resilient, scalable, and eventually consistent while maintaining strict data integrity for individual transactions.

## Requirements

The core challenge is to ensure transactional integrity (atomicity, consistency, isolation, durability) in a distributed, asynchronous processing environment. This means:

*   **Exactly-once processing:** Each valid transaction request must be processed exactly once, without duplication or omission, even if a service crashes and restarts.
*   **High throughput:** The system must be able to handle sustained transaction rates of 5,000 TPS and burst rates of 20,000 TPS without significant latency degradation.
*   **Durability and fault tolerance:** All transaction data must be durably stored and recoverable, even if multiple service instances fail. The system should automatically recover from transient failures without manual intervention.
*   **Eventual consistency for aggregated views:** While individual transactions must be immediately consistent, derived data (like account balances, which are aggregates of transactions) can be eventually consistent within a reasonable, short time frame (e.g., a few seconds).
*   **Concurrency control:** Multiple concurrent transactions affecting the same account must be handled correctly to prevent race conditions and ensure correct final balances.

## Worked answer

### 1. Key Components of the Distributed Transaction Processing Architecture

Our proposed architecture shifts from synchronous, single-database processing to an asynchronous, event-driven model. This design leverages message queues for decoupling and scalability, and dedicated services for specific responsibilities.

Here are the key components and their interactions:

1.  **API Gateway / Ingress:**
    *   **Role:** The entry point for all transaction requests from client applications.
    *   **Interaction:** Validates basic request format, applies rate limiting, and forwards valid requests to the `Transaction Ingestion Service`.
    *   **Technology:** A cloud-managed API Gateway (e.g., AWS API Gateway, GCP API Gateway) or a custom reverse proxy (e.g., NGINX, Envoy).

2.  **Transaction Ingestion Service:**
    *   **Role:** Receives raw transaction requests, performs initial validation (e.g., schema validation, basic authentication/authorization checks), generates a unique `idempotency_key` if not provided, and publishes the transaction request to a message queue.
    *   **Interaction:**
        *   Receives requests from the `API Gateway`.
        *   Publishes messages to the `Transaction Request Queue`.
        *   Persists the `idempotency_key` and initial transaction state to a `Request Log Database` (e.g., PostgreSQL) to track request status and prevent duplicate ingestion.
    *   **Technology:** A stateless microservice (e.g., Spring Boot, Node.js, Go service) deployed in a container orchestration platform (Kubernetes).

3.  **Transaction Request Queue:**
    *   **Role:** A durable, ordered message queue that acts as a buffer between the ingestion and processing stages. It decouples producers from consumers, handles backpressure, and ensures durability of requests.
    *   **Interaction:**
        *   `Transaction Ingestion Service` publishes messages.
        *   `Transaction Processing Service` consumes messages.
    *   **Technology:** Apache Kafka, AWS Kinesis, GCP Pub/Sub, or RabbitMQ. Kafka is preferred for its high throughput, durability, and ordered guarantees within partitions.

4.  **Transaction Processing Service:**
    *   **Role:** The core business logic service responsible for processing individual financial transactions. It reads requests from the `Transaction Request Queue`, applies business rules, interacts with the `Account Database`, and publishes transaction outcomes.
    *   **Interaction:**
        *   Consumes messages from the `Transaction Request Queue`.
        *   Interacts with the `Account Database` to update balances and record transaction details.
        *   Publishes `Transaction Outcome Events` to the `Transaction Outcome Queue`.
        *   Updates the `Request Log Database` with the final processing status for the `idempotency_key`.
    *   **Technology:** A stateful (for idempotency tracking) or stateless (if idempotency is handled externally) microservice, horizontally scalable.

5.  **Account Database:**
    *   **Role:** The primary source of truth for account balances and individual transaction records. It must support strong transactional guarantees (ACID) for individual account updates.
    *   **Interaction:** `Transaction Processing Service` reads and writes.
    *   **Technology:** PostgreSQL (or a highly available, sharded PostgreSQL cluster like CitusDB, CockroachDB, or YugabyteDB for extreme scale).

6.  **Transaction Outcome Queue:**
    *   **Role:** A durable message queue for broadcasting the results of processed transactions. This allows other downstream services to react to completed transactions without directly coupling to the `Transaction Processing Service`.
    *   **Interaction:**
        *   `Transaction Processing Service` publishes messages.
        *   `Notification Service`, `Reporting Service`, `Fraud Detection Service`, etc., consume messages.
    *   **Technology:** Apache Kafka, AWS Kinesis, GCP Pub/Sub.

7.  **Notification Service / Reporting Service / Other Downstream Services:**
    *   **Role:** Consume `Transaction Outcome Events` to update customer notifications, generate reports, perform fraud analysis, etc. These services operate on an eventually consistent model.
    *   **Interaction:** Consume from `Transaction Outcome Queue`.
    *   **Technology:** Various microservices.

**Component Communication and Interaction Flow:**

1.  **Client Request:** Client sends `POST /transactions` to `API Gateway`.
    ```json
    {
      "request_id": "client-generated-uuid-123", // Optional, for client-side idempotency
      "account_id": "ACC-001",
      "type": "DEPOSIT",
      "amount": 100.00,
      "currency": "USD"
    }
    ```
2.  **Ingestion:** `API Gateway` forwards to `Transaction Ingestion Service`.
    *   `Transaction Ingestion Service` generates or uses `request_id` as `idempotency_key`.
    *   Records `idempotency_key` and `status: PENDING` in `Request Log Database`.
    *   Publishes message to `Transaction Request Queue` (e.g., Kafka topic `transaction-requests`).
    ```json
    {
      "idempotency_key": "server-generated-uuid-456",
      "account_id": "ACC-001",
      "type": "DEPOSIT",
      "amount": 100.00,
      "currency": "USD",
      "timestamp": "2026-10-25T10:00:00Z"
    }
    ```
3.  **Processing:** `Transaction Processing Service` consumes from `Transaction Request Queue`.
    *   Checks `Request Log Database` for `idempotency_key`. If already `COMPLETED` or `FAILED`, it skips processing (or retries if `PENDING` and a timeout occurred).
    *   Acquires a distributed lock for `account_id` (see section 3).
    *   Performs business logic:
        *   Reads current balance from `Account Database`.
        *   Validates transaction (e.g., sufficient funds for withdrawal).
        *   Updates account balance and inserts a new transaction record in `Account Database` within a single ACID transaction.
    *   Releases lock.
    *   Updates `Request Log Database` with `status: COMPLETED` or `status: FAILED` and processing details.
    *   Publishes `Transaction Outcome Event` to `Transaction Outcome Queue` (e.g., Kafka topic `transaction-outcomes`).
    ```json
    {
      "idempotency_key": "server-generated-uuid-456",
      "transaction_id": "db-generated-tx-id-789",
      "account_id": "ACC-001",
      "type": "DEPOSIT",
      "amount": 100.00,
      "currency": "USD",
      "status": "SUCCESS",
      "new_balance": 1100.00,
      "timestamp": "2026-10-25T10:00:05Z"
    }
    ```
4.  **Downstream Consumption:** Other services consume `Transaction Outcome Events` from `Transaction Outcome Queue` to update their respective views or trigger actions.

### 2. Mechanism for Exactly-Once Processing

Achieving "exactly-once processing" in a distributed system is challenging and often means "effectively once" or "idempotent processing." We will focus on ensuring that each *valid business transaction* is applied to the `Account Database` exactly once, even if messages are delivered multiple times or services crash and restart.

Our mechanism relies on two main pillars: **Idempotency Keys** and **Atomic State Updates**.

**2.1. Idempotency Keys**

*   **Generation:**
    *   Clients *can* provide a `request_id` in their initial request. This is useful for mobile apps or frontend systems to track their own requests and retry safely.
    *   If the client does not provide one, the `Transaction Ingestion Service` *must* generate a globally unique `idempotency_key` (e.g., a UUID v4) upon receiving the request. This key uniquely identifies the *intent* of the transaction.
*   **Storage:** The `idempotency_key` is stored in a `Request Log Database` (e.g., PostgreSQL) alongside the initial transaction request details and its processing status.

**`Request Log Database` Schema (PostgreSQL):**

```sql
CREATE TABLE transaction_requests_log (
    idempotency_key UUID PRIMARY KEY,
    request_payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL, -- PENDING, PROCESSING, COMPLETED, FAILED
    created_at TIMESTAMPTZ DEFAULT NOW(),
    updated_at TIMESTAMPTZ DEFAULT NOW(),
    processing_details JSONB, -- Stores success/failure messages, transaction_id etc.
    CONSTRAINT chk_status CHECK (status IN ('PENDING', 'PROCESSING', 'COMPLETED', 'FAILED'))
);

CREATE INDEX idx_transaction_requests_log_status ON transaction_requests_log (status);
```

**2.2. Atomic State Updates in the `Transaction Processing Service`**

The `Transaction Processing Service` consumes messages from the `Transaction Request Queue`. For each message:

1.  **Check Idempotency Key:**
    *   Before any business logic, the service queries `transaction_requests_log` using the `idempotency_key`.
    *   **If `status` is `COMPLETED` or `FAILED`:** The transaction has already been processed or definitively failed. The service acknowledges the message from the queue and discards it. This handles duplicate message delivery.
    *   **If `status` is `PENDING`:** This is a new request or a retry for a request that was ingested but not yet processed. The service updates the status to `PROCESSING` *atomically* within the `Request Log Database` to prevent other instances from picking it up concurrently.
        ```sql
        UPDATE transaction_requests_log
        SET status = 'PROCESSING', updated_at = NOW()
        WHERE idempotency_key = '...' AND status = 'PENDING';
        ```
        If this update fails (e.g., another instance already set it to `PROCESSING`), the current instance can back off and retry or discard the message.
    *   **If `idempotency_key` is not found:** This is a new request. Insert it with `status = 'PROCESSING'`.

2.  **Process Business Logic (within a single ACID transaction):**
    *   The core transaction logic (debit/credit, balance update, transaction record insertion) is performed inside a single database transaction in the `Account Database`. This ensures Atomicity and Durability for the financial operation itself.
    *   **`Account Database` Schema (PostgreSQL):**
        ```sql
        CREATE TABLE accounts (
            account_id VARCHAR(50) PRIMARY KEY,
            balance NUMERIC(19, 4) NOT NULL DEFAULT 0.00,
            currency VARCHAR(3) NOT NULL,
            version INT NOT NULL DEFAULT 1, -- For optimistic locking
            created_at TIMESTAMPTZ DEFAULT NOW(),
            updated_at TIMESTAMPTZ DEFAULT NOW()
        );

        CREATE TABLE transactions (
            transaction_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
            idempotency_key UUID NOT NULL, -- Link to the request log
            account_id VARCHAR(50) NOT NULL REFERENCES accounts(account_id),
            type VARCHAR(10) NOT NULL, -- DEPOSIT, WITHDRAWAL, TRANSFER
            amount NUMERIC(19, 4) NOT NULL,
            currency VARCHAR(3) NOT NULL,
            status VARCHAR(20) NOT NULL, -- SUCCESS, FAILED, PENDING (for multi-leg)
            processed_at TIMESTAMPTZ DEFAULT NOW(),
            details JSONB,
            CONSTRAINT fk_idempotency_key FOREIGN KEY (idempotency_key) REFERENCES transaction_requests_log(idempotency_key),
            CONSTRAINT chk_transaction_type CHECK (type IN ('DEPOSIT', 'WITHDRAWAL', 'TRANSFER'))
        );

        CREATE UNIQUE INDEX idx_transactions_idempotency_key ON transactions (idempotency_key);
        ```
    *   Example update for a deposit:
        ```sql
        BEGIN;
        UPDATE accounts
        SET balance = balance + :amount, version = version + 1, updated_at = NOW()
        WHERE account_id = :account_id;

        INSERT INTO transactions (idempotency_key, account_id, type, amount, currency, status, details)
        VALUES (:idempotency_key, :account_id, :type, :amount, :currency, 'SUCCESS', :details);
        COMMIT;
        ```

3.  **Update Request Log and Publish Outcome:**
    *   **If business logic succeeds:**
        *   Update `transaction_requests_log` to `status = 'COMPLETED'` and store `transaction_id`.
        *   Publish a `Transaction Outcome Event` to `Transaction Outcome Queue`.
    *   **If business logic fails:**
        *   Update `transaction_requests_log` to `status = 'FAILED'` and store error details.
        *   Publish a `Transaction Outcome Event` with `status = 'FAILED'`.
    *   **Crucially, these two steps (updating `transaction_requests_log` and publishing to `Transaction Outcome Queue`) must be treated as an atomic operation.** This is the "transactional outbox pattern."
        *   Instead of directly publishing to Kafka, the `Transaction Processing Service` inserts the `Transaction Outcome Event` into a dedicated `outbox` table within the *same database transaction* as the account balance update and transaction record insertion.
        *   A separate **Outbox Relayer Service** (or a CDC tool like Debezium) monitors this `outbox` table, reads new entries, publishes them to the `Transaction Outcome Queue`, and then marks them as published or deletes them. This guarantees that if the database transaction commits, the event will eventually be published, and if it rolls back, no event is published.

**Outbox Table Schema (PostgreSQL, in the `Account Database`):**

```sql
CREATE TABLE outbox (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    aggregate_type VARCHAR(50) NOT NULL,
    aggregate_id VARCHAR(50) NOT NULL,
    event_type VARCHAR(50) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    published_at TIMESTAMPTZ,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING'
);

CREATE INDEX idx_outbox_status_created_at ON outbox (status, created_at);
```

**Example of Atomic Update with Outbox:**

```sql
BEGIN;
-- 1. Update account balance and insert transaction record
UPDATE accounts
SET balance = balance + :amount, version = version + 1, updated_at = NOW()
WHERE account_id = :account_id;

INSERT INTO transactions (idempotency_key, account_id, type, amount, currency, status, details)
VALUES (:idempotency_key, :account_id, :type, :amount, :currency, 'SUCCESS', :details)
RETURNING transaction_id INTO :transaction_id; -- Get the generated ID

-- 2. Insert event into outbox table
INSERT INTO outbox (aggregate_type, aggregate_id, event_type, payload)
VALUES (
    'transaction',
    :transaction_id,
    'TransactionProcessed',
    JSONB_BUILD_OBJECT(
        'idempotency_key', :idempotency_key,
        'transaction_id', :transaction_id,
        'account_id', :account_id,
        'type', :type,
        'amount', :amount,
        'currency', :currency,
        'status', 'SUCCESS',
        'new_balance', (SELECT balance FROM accounts WHERE account_id = :account_id),
        'timestamp', NOW()
    )
);

-- 3. Update the request log (this can be in the same DB or a separate one, but for simplicity, assume same DB for this example)
UPDATE transaction_requests_log
SET status = 'COMPLETED', processing_details = JSONB_BUILD_OBJECT('transaction_id', :transaction_id), updated_at = NOW()
WHERE idempotency_key = :idempotency_key;

COMMIT;
```

**Summary of "Exactly-Once":**
*   **Ingestion:** `idempotency_key` in `Request Log Database` prevents duplicate requests from entering the queue.
*   **Processing:** `idempotency_key` check in `Transaction Processing Service` prevents duplicate processing of messages from the queue.
*   **Outcome:** The transactional outbox pattern ensures that the `Account Database` update and the `Transaction Outcome Event` publication are atomic, preventing partial updates or lost events.

### 3. Handling Concurrent Updates to an Account Balance

Concurrent updates to the same account are a classic race condition problem. In a distributed, asynchronous environment, multiple `Transaction Processing Service` instances might try to process transactions for the same `account_id` simultaneously. We will use a combination of **optimistic locking** and **distributed pessimistic locking** to ensure correctness.

**3.1. Optimistic Locking (Primary Mechanism)**

Optimistic locking is generally preferred for its scalability, as it avoids holding locks for extended periods. It relies on a version number or timestamp column in the `accounts` table.

**Mechanism:**

1.  **Read:** When a `Transaction Processing Service` instance processes a transaction for `account_id`, it reads the current `balance` and `version` of the account from the `accounts` table.
    ```sql
    SELECT balance, version FROM accounts WHERE account_id = :account_id FOR UPDATE; -- FOR UPDATE for pessimistic lock during read, if needed
    ```
2.  **Calculate New Balance:** The service calculates the new balance based on the transaction (e.g., `new_balance = current_balance + amount`).
3.  **Conditional Update:** When updating the account, the `UPDATE` statement includes a `WHERE` clause that checks the `version` number.
    ```sql
    UPDATE accounts
    SET balance = :new_balance, version = :current_version + 1, updated_at = NOW()
    WHERE account_id = :account_id AND version = :current_version;
    ```
4.  **Check Rows Affected:**
    *   If the `UPDATE` statement affects exactly one row, the update was successful, and no other concurrent transaction modified the account between the read and write.
    *   If the `UPDATE` statement affects zero rows, it means another transaction updated the account in the meantime (the `version` mismatch). In this case, the current transaction must **retry** the entire processing logic (read, calculate, update) from step 1. This retry mechanism is crucial.

**Trade-offs:** Optimistic locking is efficient for low-to-moderate contention. Under high contention for the *same* account, retries can become frequent, leading to increased latency and wasted CPU cycles.

**3.2. Distributed Pessimistic Locking (for high contention or critical paths)**

For scenarios with extremely high contention on a specific account, or where retries are undesirable due to complex side effects, a distributed pessimistic lock can be employed. This ensures that only one `Transaction Processing Service` instance can modify a given `account_id` at any time.

**Mechanism:**

1.  **Distributed Lock Manager (DLM):** A separate service or a robust distributed key-value store (e.g., Apache ZooKeeper, etcd, Redis with Redlock) is used as a DLM.
2.  **Acquire Lock:** Before processing a transaction for `account_id`, the `Transaction Processing Service` attempts to acquire a lock for that `account_id` from the DLM.
    ```python
    # Example using a hypothetical distributed lock client
    lock_key = f"account_lock:{account_id}"
    lock = distributed_lock_manager.acquire(lock_key, timeout=5_seconds) # Timeout to prevent deadlocks
    if not lock:
        # Failed to acquire lock, another instance is processing.
        # Nack message to queue for redelivery or retry later.
        return
    ```
3.  **Process Transaction:** If the lock is acquired, the service proceeds with the database update using optimistic locking (or even a simple update without version check, as the distributed lock already provides mutual exclusion).
4.  **Release Lock:** After the database transaction commits (or rolls back), the service *must* release the lock. This is critical to prevent deadlocks.
    ```python
    # Example
    distributed_lock_manager.release(lock)
    ```

**Combining Approaches:**

*   **Default:** Use optimistic locking. It's simpler to implement and scales well for most cases.
*   **High Contention Accounts:** For accounts known to experience very high concurrent updates (e.g., a central treasury account), a distributed pessimistic lock can be applied. This could be configured per `account_id` or triggered dynamically if optimistic locking retries exceed a threshold.
*   **Kafka Partitioning:** For `Transaction Request Queue` (Kafka), partitioning by `account_id` can significantly reduce contention. If all messages for a specific `account_id` go to the same Kafka partition, then a single consumer instance (within a consumer group) will process them sequentially. This effectively provides a "local" pessimistic lock per `account_id` *within that partition*, reducing the need for a separate DLM for most cases. However, if the consumer crashes, another consumer takes over, and the `idempotency_key` mechanism is still vital.

**Chosen Approach:**
We will primarily rely on **Kafka partitioning by `account_id`** to ensure sequential processing of transactions for the same account within a consumer group. This is the most efficient and scalable approach for preventing race conditions.
The `Transaction Processing Service` will use **optimistic locking** (the `version` column) as a secondary defense within its database transaction, primarily to detect and handle cases where Kafka rebalances or multiple consumers somehow end up processing the same `account_id` (e.g., misconfigured partitioning, or if the `FOR UPDATE` clause isn't sufficient).
If a `Transaction Processing Service` instance receives a message for an `account_id` that is currently being processed by another instance (due to rebalancing or misconfiguration), the optimistic lock will fail, triggering a retry. The `idempotency_key` will prevent duplicate application of the transaction.

### 4. Potential Failure Mode and Mitigation

**Failure Mode:** **"Lost Update" due to `Transaction Processing Service` Crash after Database Commit but before Outbox Event Publication (without transactional outbox).**

**Description:**
Imagine the `Transaction Processing Service` successfully commits the database transaction (updating `accounts` and `transactions` tables). At this point, the account balance is correct in the `Account Database`. However, *before* the service can publish the `Transaction Outcome Event` to the `Transaction Outcome Queue` (e.g., Kafka), the service instance crashes or loses network connectivity.

**Consequences:**

*   The `Account Database` reflects the correct state.
*   The `Request Log Database` might still show `status: PROCESSING` (if the update to `COMPLETED` was also part of the post-DB-commit steps).
*   Downstream services (notifications, reporting, fraud detection) never receive the `Transaction Outcome Event`. They remain unaware of the completed transaction, leading to inconsistent views, missing notifications, or incorrect reports.
*   The original message might be redelivered by the `Transaction Request Queue` (if not acknowledged), but the `idempotency_key` would prevent re-applying the transaction to the `Account Database`. However, the event publication would still be missed.

**Mitigation/Recovery:**

Our design explicitly mitigates this using the **Transactional Outbox Pattern** (as described in Section 2.2).

1.  **Atomic Operation:** The `Transaction Processing Service` inserts the `Transaction Outcome Event` into the `outbox` table *within the same database transaction* as the `accounts` and `transactions` table updates. This ensures that either all three operations commit together, or none of them do. If the service crashes *after* the database transaction commits, the event is guaranteed to be in the `outbox` table.

2.  **Outbox Relayer Service:** A separate, dedicated **Outbox Relayer Service** continuously monitors the `outbox` table for new entries with `status = 'PENDING'`.
    *   It reads these pending events.
    *   Publishes them to the `Transaction Outcome Queue` (e.g., Kafka topic `transaction-outcomes`).
    *   Upon successful publication (and confirmation from the message queue broker), it updates the `status` of the event in the `outbox` table to `PUBLISHED` (or deletes it, depending on retention policies).

**Recovery Flow with Outbox:**

*   If the `Transaction Processing Service` crashes after committing the database transaction but before the event is published to Kafka:
    *   The event is safely stored in the `outbox` table with `status = 'PENDING'`.
    *   The `Outbox Relayer Service` (which is a separate, fault-tolerant component) will eventually pick up this `PENDING` event.
    *   It will publish the event to the `Transaction Outcome Queue`.
    *   Downstream services will then receive the event and update their states, achieving eventual consistency.
*   The `idempotency_key` in the `transaction_requests_log` will correctly show `COMPLETED` (as that update was also part of the atomic DB transaction), preventing any re-processing of the original request message.

This pattern ensures that the system's internal state (database) and its external notifications (events) remain consistent, guaranteeing that no transaction outcome is "lost" due to service crashes.

### Going Further: Why Distributed Transactions (e.g., Two-Phase Commit) are Problematic

Distributed transactions, such as Two-Phase Commit (2PC), are generally problematic for high-volume, real-time scenarios like this due to several critical drawbacks:

1.  **Performance Bottleneck:**
    *   **Synchronous Blocking:** 2PC is a synchronous protocol. The coordinator and participants must all communicate and wait for responses at each phase. This introduces significant latency, as the transaction's duration is determined by the slowest participant and the network round-trip times.
    *   **Increased Network I/O:** Multiple rounds of communication (prepare, vote, commit/abort) are required across different services and databases. This generates substantial network traffic and overhead.
    *   **Resource Holding:** Participants hold locks and resources (e.g., database locks) for the entire duration of the distributed transaction. In a high-throughput system, this leads to contention, reduced concurrency, and increased deadlocks, severely limiting scalability.

2.  **Availability and Fault Tolerance Issues:**
    *   **Single Point of Failure (Coordinator):** If the transaction coordinator fails *after* the prepare phase but *before* the commit phase, participants might be left in an "in-doubt" state, holding resources indefinitely until the coordinator recovers or manual intervention occurs. This significantly impacts availability.
    *   **Network Partitions:** 2PC is highly sensitive to network partitions. If a participant becomes unreachable during the commit phase, the entire transaction can stall, leaving resources locked.
    *   **Complexity of Recovery:** Recovering from failures in 2PC is complex, often requiring heuristics or manual intervention to resolve "in-doubt" transactions, which can compromise consistency.

3.  **Scalability Limitations:**
    *   **Tight Coupling:** 2PC tightly couples participating services and databases. Adding new services or scaling existing ones becomes harder as they must all agree on the transaction outcome.
    *   **Global State:** Maintaining a global transaction state across multiple independent systems is inherently difficult to scale horizontally.

**How our Proposed Approach Circumvents These Issues:**

Our architecture explicitly avoids distributed transactions by embracing an **eventual consistency model** driven by **asynchronous messaging** and **idempotent processing**.

1.  **Asynchronous and Decoupled:**
    *   **No Synchronous Blocking:** The `Transaction Ingestion Service` immediately returns a response after publishing to the `Transaction Request Queue`. The actual processing happens asynchronously. This dramatically reduces user-facing latency and allows the system to handle high throughput by buffering requests.
    *   **Loose Coupling:** Services communicate via durable message queues (Kafka). The `Transaction Processing Service` doesn't need to know about downstream consumers, and vice-versa. This allows independent scaling and deployment of each component.

2.  **Local ACID Transactions:**
    *   Each critical business operation (e.g., updating an account balance and recording a transaction) is performed within a **single, local ACID database transaction** in the `Account Database`. This ensures strong consistency and durability for the core financial data without involving other services in a distributed commit protocol.
    *   The **Transactional Outbox Pattern** ensures that the side effect (publishing an event) is atomically linked to the local database transaction, guaranteeing "at-least-once" delivery of events that reflect committed state changes, and combined with idempotency, "effectively once" processing downstream.

3.  **Idempotency for Retries and Fault Tolerance:**
    *   The use of `idempotency_key` ensures that messages can be safely retried and processed multiple times without causing duplicate side effects on the `Account Database`. This is fundamental for fault tolerance in an asynchronous system where messages might be redelivered due to consumer crashes or network issues.
    *   This allows individual services to fail and restart without compromising data integrity, as long as they can recover their state and resume processing from where they left off (e.g., by re-reading messages from Kafka).

4.  **Eventual Consistency for Aggregates:**
    *   While individual transactions are immediately consistent in the `Account Database`, derived views (like aggregated balances in a reporting service) are eventually consistent. This is an acceptable trade-off for high scalability in many financial contexts, especially if the "eventual" part is within a few seconds. Downstream services consume `Transaction Outcome Events` and update their own materialized views.

In essence, our design breaks down the monolithic "distributed transaction" into a series of smaller, local ACID transactions coordinated by asynchronous, idempotent messages. This shifts the complexity from maintaining a global, synchronous transaction state to managing eventual consistency and idempotent message processing, which is generally more scalable and resilient for high-volume distributed systems.
