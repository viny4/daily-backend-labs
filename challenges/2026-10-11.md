## Scenario

Your team maintains a critical backend service responsible for managing user-generated content (UGC) for a popular social media platform. Specifically, this service handles `posts` and `comments`. Due to rapid growth, the `comments` table has become extremely large, currently holding hundreds of millions of rows, and is projected to reach billions.

Users frequently view posts, which then triggers queries to fetch all associated comments. These queries are now taking several seconds, leading to a degraded user experience. The current architecture uses a single PostgreSQL instance. While the `posts` table is also large, comment retrieval is the primary bottleneck.

Constraints:
*   **Scale:** Billions of comments, millions of new comments daily.
*   **Concurrency:** Thousands of concurrent requests to fetch comments for various posts.
*   **Latency:** Comment retrieval for a single post must be consistently below 200ms, even for posts with thousands of comments.
*   **Consistency:** "Read-your-writes" consistency is required for comments. A user must immediately see their own comment after posting it. Eventual consistency is acceptable for other users seeing new comments, within a few seconds.
*   **Availability:** The system must remain highly available; no single point of failure.

## Requirements

Design a solution to significantly improve the read latency for comments, accounting for the massive scale and growth, while maintaining the specified consistency and availability requirements. Focus on the data storage and retrieval strategy for comments.

## Worked answer

### 1. High-level Distributed Data Storage and Retrieval Strategy

The core strategy revolves around **horizontal scaling** of the `comments` data using a **sharded database architecture**, specifically designed to optimize for the primary access pattern: fetching all comments for a given `post_id`. We will use **PostgreSQL as the underlying database** for its robustness, transactional guarantees, and familiarity within the team.

Instead of a single large PostgreSQL instance, we will deploy multiple independent PostgreSQL instances, each responsible for a subset of the `comments` data. The key is to shard the data by `post_id`. This means all comments belonging to a particular `post_id` will reside on the same shard.

To manage these shards, we will introduce a **sharding proxy layer** (e.g., a custom service, or an off-the-shelf solution like Citus Data if we were to consider a managed solution). This proxy will intercept all comment-related queries, determine the correct shard based on the `post_id` in the query, and route the query to that specific shard.

For read-heavy workloads and to further reduce latency, we will implement **read replicas** for each shard. This allows distributing read traffic and provides high availability in case a primary shard instance fails.

Additionally, to address the "read-your-writes" consistency requirement efficiently, we will leverage a **small, fast, in-memory cache** (e.g., Redis) that stores recent comments made by a user for a short period.

### 2. Addressing Read Latency for Fetching All Comments

The strategy directly addresses read latency by ensuring that queries to fetch all comments for a specific `post_id` are **single-shard queries**.

When a user views a post, the application will query the sharding proxy with the `post_id`. The proxy will use a **consistent hashing algorithm** or a **lookup table** (mapping `post_id` ranges or specific `post_id`s to shard IDs) to determine which PostgreSQL shard holds all comments for that `post_id`. The query is then routed to that single shard.

Since all comments for a post are co-located on the same physical database instance, the query becomes a local operation within that shard. This avoids:
*   **Cross-shard joins:** No need to aggregate data from multiple database instances.
*   **Network overhead:** The query only needs to hit one database server.
*   **Large table scans:** Each shard's `comments` table will be significantly smaller than the monolithic table, allowing indexes to be much more effective.

Within each shard, we will have a B-tree index on `(post_id, created_at DESC)` to quickly retrieve comments for a given `post_id` in chronological order. Even for posts with thousands of comments, retrieving them from a single, smaller, indexed table on a dedicated instance will be significantly faster than scanning a multi-billion row table.

Example query flow:
1.  User requests comments for `post_id = 'post_abc'`.
2.  Application sends `SELECT * FROM comments WHERE post_id = 'post_abc' ORDER BY created_at DESC;` to the sharding proxy.
3.  Sharding proxy determines `post_abc` belongs to `shard_3`.
4.  Proxy routes the query to `shard_3`'s primary or one of its read replicas.
5.  `shard_3` executes the query locally using its index.
6.  Results are returned to the application.

This approach ensures that the database operations are localized and efficient, meeting the sub-200ms latency requirement.

### 3. Maintaining "Read-Your-Writes" Consistency

"Read-your-writes" consistency for a user's own comments is crucial. While the sharded PostgreSQL provides strong consistency for writes to the primary shard, relying solely on eventual consistency for reads from replicas might introduce a slight delay before a user sees their own comment.

To guarantee immediate visibility, we will implement a two-pronged approach:

1.  **Direct Read from Primary Shard for Recent Writes:** When a user posts a comment, the write operation goes directly to the primary instance of the determined shard. For a short period (e.g., 5-10 seconds) after a user posts a comment, subsequent read requests *from that specific user* for comments on that *same post* will be explicitly routed to the **primary instance** of the relevant shard, bypassing read replicas. This ensures they read the most up-to-date state. This can be tracked using a short-lived cookie or session variable on the client/backend.

2.  **In-Memory Cache for User's Own Comments:** Additionally, upon a successful comment submission, the newly created comment will be stored in a small, user-specific, in-memory cache (e.g., Redis) for a very short duration (e.g., 30 seconds to 1 minute). When a user requests comments for a post, the application will first check this cache for any comments they recently posted on that specific `post_id`. These cached comments will be prepended or merged with the results fetched from the database before being returned to the user. This serves as a fast path for immediate display and a fallback in case of replication lag issues.

    ```python
    # Example (simplified)
    def post_comment(user_id, post_id, content):
        comment_id = generate_uuid()
        # 1. Write to primary shard
        shard_db_client.execute("INSERT INTO comments (comment_id, post_id, user_id, content, created_at) VALUES (...)")

        # 2. Store in user-specific cache
        redis_client.lpush(f"user_comments_cache:{user_id}:{post_id}", json.dumps({
            "comment_id": comment_id,
            "user_id": user_id,
            "content": content,
            "created_at": datetime.now().isoformat()
        }))
        redis_client.expire(f"user_comments_cache:{user_id}:{post_id}", 60) # Expire in 60 seconds

        # 3. Mark user session for primary read for this post_id
        session_manager.set_read_primary_for_post(user_id, post_id, expires_in=10)

        return comment_id

    def get_comments(user_id, post_id):
        # 1. Check user's recent comment cache
        cached_comments_raw = redis_client.lrange(f"user_comments_cache:{user_id}:{post_id}", 0, -1)
        cached_comments = [json.loads(c) for c in cached_comments_raw]

        # 2. Determine DB read target (primary or replica)
        if session_manager.should_read_primary_for_post(user_id, post_id):
            db_comments = shard_db_client.query_primary(f"SELECT * FROM comments WHERE post_id = '{post_id}' ORDER BY created_at DESC;")
        else:
            db_comments = shard_db_client.query_replica(f"SELECT * FROM comments WHERE post_id = '{post_id}' ORDER BY created_at DESC;")

        # 3. Merge and deduplicate (if necessary, though cached comments should be in DB by now)
        # For simplicity, assume cached comments are already in DB and we just prepend for speed.
        # A more robust solution would deduplicate by comment_id.
        all_comments = sorted(list(set(cached_comments + db_comments)), key=lambda c: c['created_at'], reverse=True)
        return all_comments
    ```

This hybrid approach ensures that the user immediately sees their own comment, while other users might experience a slight delay (a few seconds) due to replication lag, which is acceptable per the requirements.

### 4. Key Data Model Changes

The core data model for `comments` will remain largely the same, but the crucial change is the addition of a `post_id` column as the primary sharding key and the associated indexing.

**Current (Monolithic) `comments` table:**

```sql
CREATE TABLE comments (
    comment_id UUID PRIMARY KEY,
    post_id UUID NOT NULL,
    user_id UUID NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Current index for fetching comments for a post
CREATE INDEX idx_comments_post_id ON comments (post_id, created_at DESC);
```

**Proposed (Sharded) `comments` table schema (on each shard):**

The schema itself remains identical on each shard. The change is in how the data is distributed and indexed for optimal performance within each shard.

```sql
-- This schema will exist on every shard
CREATE TABLE comments (
    comment_id UUID PRIMARY KEY,
    post_id UUID NOT NULL,
    user_id UUID NOT NULL,
    content TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Crucial index for fast retrieval within each shard
-- This index ensures that fetching all comments for a post_id is efficient.
CREATE INDEX idx_comments_post_id_created_at ON comments (post_id, created_at DESC);

-- Other potentially useful indexes:
-- For user-specific comment retrieval (e.g., "my comments")
-- CREATE INDEX idx_comments_user_id ON comments (user_id, created_at DESC);
```

**Key Data Model Considerations:**

*   **`post_id` as Sharding Key:** This is the most critical aspect. Every query involving comments *must* include `post_id` to be efficiently routed to the correct shard. Queries that do not specify `post_id` (e.g., "get all comments by user X across all posts") would become "scatter-gather" queries, requiring the sharding proxy to query all shards and aggregate results, which would be very slow and should be avoided for high-volume operations. Such queries would need to be handled by a different mechanism (e.g., a data warehouse, a separate denormalized service, or be redesigned).
*   **UUID for `comment_id` and `post_id`:** Using UUIDs helps prevent collisions when generating IDs across different shards, simplifying ID generation without requiring a central ID service.
*   **`created_at` for Ordering:** Essential for displaying comments chronologically, especially with the `DESC` order in the index.

### Going Further

Simply sharding the existing PostgreSQL `comments` table by `comment_id` is unlikely to meet the latency requirements for fetching all comments for a specific `post_id` because of the **access pattern mismatch** with the sharding key.

**Why it's suboptimal:**

1.  **Distributed Joins / Scatter-Gather Queries:** If comments are sharded by `comment_id`, then comments for a single `post_id` will be randomly distributed across many, if not all, shards. To retrieve all comments for a specific `post_id`, the sharding proxy would have to:
    *   Send the `SELECT * FROM comments WHERE post_id = 'post_abc'` query to **every single shard**.
    *   Wait for responses from all shards.
    *   Aggregate (gather) all the results.
    *   Sort the aggregated results (if `ORDER BY` is specified).
    This "scatter-gather" approach introduces significant network latency, CPU overhead on the proxy for aggregation, and effectively turns many small queries into one very large, slow distributed query. The latency would be proportional to the number of shards and the slowest shard's response time, easily exceeding the 200ms target.

2.  **Inefficient Index Usage:** While each shard might have an index on `(post_id, created_at DESC)`, this index would only be useful for filtering within that specific shard's subset of data. The fundamental problem is that the `post_id` filter needs to be applied *across* all shards, not just within one. The sharding key (`comment_id`) does not help in locating `post_id` data.

**Specific characteristics of the access pattern that make this a suboptimal sharding key:**

The primary access pattern is **"fetch all comments for a given `post_id`"**. This is a **range query** or **grouping query** on `post_id`.

*   **`post_id` is the grouping key:** Users want to see *all* comments related to a single post.
*   **`comment_id` is an individual record identifier:** Sharding by `comment_id` optimizes for retrieving a *single specific comment* by its ID, which is not the bottleneck access pattern. It's like having a phone book sorted by individual names when you always want to find all people living at a specific address.

In essence, sharding by `comment_id` optimizes for point lookups on `comment_id`, whereas the requirement is for efficient lookups of *all related records* based on `post_id`. To meet the latency requirements, the sharding key must align with the most frequent and critical query pattern, which in this case is `post_id`.
