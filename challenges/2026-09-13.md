## Scenario

Your team maintains a critical backend service that processes real-time financial trades for a high-frequency trading platform. A core function of this service is to calculate the current "net position" for each unique `trading_pair` (e.g., `BTC/USD`, `ETH/EUR`) across all active users. The net position for a `trading_pair` is the sum of all `buy` quantities minus the sum of all `sell` quantities.

Currently, this calculation is done by querying a central PostgreSQL database which stores all `trade` records. As the platform's volume has grown, the `trades` table now contains hundreds of millions of rows, with thousands of new trades arriving per second. The existing query to calculate net positions, which involves summing and grouping across this massive table, has become a significant bottleneck. It frequently exceeds your 100ms latency budget, leading to stale position data for traders and potential reconciliation issues. The database is already heavily optimized, and further indexing or read replicas offer diminishing returns for this specific aggregate query.

## Requirements

The current approach is no longer sustainable. You need to design and implement a more scalable, distributed solution to maintain real-time net positions for `trading_pairs`. The solution must handle a high throughput of incoming trade events, ensure eventual consistency of net positions, and provide low-latency queries for the current net position of any given `trading_pair`. Consider that a single `trading_pair` can have thousands of trades per second. Your solution should be fault-tolerant and scale horizontally.

Constraints:
*   Incoming trade events arrive at a rate of several thousand per second.
*   Query for net position for a `trading_pair` must be under 50ms.
*   Net positions must be eventually consistent within a few seconds.
*   The system must tolerate individual node failures without data loss for committed trades.
*   You don't need to implement the full trade processing pipeline, focus on the net position aggregation and retrieval.

## Deliverables

1.  A high-level design document (text-based, 1-2 paragraphs) outlining the chosen distributed system architecture for aggregating and serving net positions.
2.  Pseudocode or a detailed description of the core logic for processing an incoming trade event and updating the net position for a specific `trading_pair`.
3.  Pseudocode or a detailed description of the logic for querying the current net position for a given `trading_pair`.
4.  Briefly describe how your proposed solution handles the eventual consistency requirement and ensures data durability in the face of node failures.

## Going further

Explain the trade-offs you made between consistency, availability, and partition tolerance (CAP theorem) in your chosen design, specifically regarding how stale data might be perceived by a user querying a net position immediately after a trade.

## Worked answer

### 1. High-level Design Document

To address the scalability bottleneck, we will adopt a stream processing architecture using Apache Kafka for trade event ingestion and Apache Flink for real-time aggregation. Incoming trade events will be published to a Kafka topic. Flink will consume these events, maintain in-memory state for each `trading_pair`'s net position, and continuously update these positions. The aggregated net positions will then be stored in a low-latency key-value store like Apache Cassandra or Redis for efficient querying. This design decouples trade processing from position aggregation, allowing independent scaling of each component.

### 2. Core Logic for Processing an Incoming Trade Event

When a trade event arrives, it contains information about the `trading_pair`, `quantity`, and `type` (buy/sell). The Flink application will consume these events, group them by `trading_pair`, and apply a stateful aggregation function. Each `trading_pair` will have a dedicated state managed by Flink, which stores its current net position.

```java
// Pseudocode for Flink Stream Processing Job

// Define the Trade Event structure
public class TradeEvent {
    String tradeId;
    String tradingPair; // e.g., "BTC/USD"
    long timestamp;
    BigDecimal quantity;
    TradeType type; // ENUM: BUY, SELL
}

public enum TradeType {
    BUY, SELL
}

// Flink Job Entry Point
public static void main(String[] args) throws Exception {
    StreamExecutionEnvironment env = StreamExecutionEnvironment.getExecutionEnvironment();

    // Configure Kafka Consumer
    Properties properties = new Properties();
    properties.setProperty("bootstrap.servers", "kafka-broker-1:9092,kafka-broker-2:9092");
    properties.setProperty("group.id", "net-position-calculator");

    DataStream<TradeEvent> tradeStream = env
        .addSource(new FlinkKafkaConsumer<>("trade-events", new TradeEventDeserializationSchema(), properties))
        .name("Kafka Trade Event Source");

    // Key the stream by tradingPair to ensure all trades for a pair are processed by the same Flink task
    DataStream<NetPositionUpdate> netPositionUpdates = tradeStream
        .keyBy(trade -> trade.tradingPair)
        .process(new NetPositionAggregator()) // Apply the stateful aggregation logic
        .name("Net Position Aggregator");

    // Sink the aggregated net positions to a low-latency key-value store (e.g., Cassandra or Redis)
    netPositionUpdates.addSink(new NetPositionStoreSink())
        .name("Net Position Store Sink");

    env.execute("Real-time Net Position Calculator");
}

// Flink's KeyedProcessFunction to maintain and update state per trading_pair
public class NetPositionAggregator extends KeyedProcessFunction<String, TradeEvent, NetPositionUpdate> {

    // ValueState to store the current net position for the keyed trading_pair
    private ValueState<BigDecimal> currentNetPositionState;

    @Override
    public void open(Configuration parameters) throws Exception {
        // Initialize the state descriptor
        ValueStateDescriptor<BigDecimal> descriptor =
            new ValueStateDescriptor<>("net-position", TypeInformation.of(BigDecimal.class));
        currentNetPositionState = getRuntimeContext().getState(descriptor);
    }

    @Override
    public void processElement(TradeEvent trade, Context context, Collector<NetPositionUpdate> out) throws Exception {
        BigDecimal currentPosition = currentNetPositionState.value();
        if (currentPosition == null) {
            currentPosition = BigDecimal.ZERO;
        }

        // Update the net position based on the trade type
        if (trade.type == TradeType.BUY) {
            currentPosition = currentPosition.add(trade.quantity);
        } else { // SELL
            currentPosition = currentPosition.subtract(trade.quantity);
        }

        // Update the state
        currentNetPositionState.update(currentPosition);

        // Emit an update event to be sent to the key-value store
        out.collect(new NetPositionUpdate(context.getCurrentKey(), currentPosition, trade.timestamp));
    }
}

// Structure for updates to the key-value store
public class NetPositionUpdate {
    String tradingPair;
    BigDecimal netPosition;
    long lastUpdateTime;

    public NetPositionUpdate(String tradingPair, BigDecimal netPosition, long lastUpdateTime) {
        this.tradingPair = tradingPair;
        this.netPosition = netPosition;
        this.lastUpdateTime = lastUpdateTime;
    }
}

// Pseudocode for NetPositionStoreSink (e.g., Cassandra Sink)
public class NetPositionStoreSink extends RichSinkFunction<NetPositionUpdate> {
    private transient Cluster cluster;
    private transient Session session;

    @Override
    public void open(Configuration parameters) throws Exception {
        // Initialize Cassandra connection
        cluster = Cluster.builder().addContactPoint("cassandra-node-1").build();
        session = cluster.connect("trading_data");

        // Ensure table exists (simplified, in production use DDL migration)
        session.execute("CREATE TABLE IF NOT EXISTS net_positions (" +
                        "trading_pair TEXT PRIMARY KEY," +
                        "net_position DECIMAL," +
                        "last_update_time TIMESTAMP)");
    }

    @Override
    public void invoke(NetPositionUpdate update, Context context) throws Exception {
        // Upsert the net position into Cassandra
        session.execute("INSERT INTO net_positions (trading_pair, net_position, last_update_time) VALUES (?, ?, ?)",
                        update.tradingPair, update.netPosition, new Date(update.lastUpdateTime));
    }

    @Override
    public void close() throws Exception {
        if (session != null) session.close();
        if (cluster != null) cluster.close();
    }
}
```

### 3. Logic for Querying the Current Net Position

The current net position for a given `trading_pair` will be queried directly from the low-latency key-value store (e.g., Cassandra or Redis). This store will be continuously updated by the Flink job.

```java
// Pseudocode for a Net Position Query Service (e.g., a REST API backend)

import com.datastax.driver.core.Cluster;
import com.datastax.driver.core.Session;
import com.datastax.driver.core.Row;
import java.math.BigDecimal;
import java.util.Optional;

public class NetPositionQueryService {
    private final Cluster cluster;
    private final Session session;

    public NetPositionQueryService() {
        // Initialize Cassandra connection (should be a singleton or managed by a DI framework)
        this.cluster = Cluster.builder().addContactPoint("cassandra-node-1").build();
        this.session = cluster.connect("trading_data");
    }

    public Optional<BigDecimal> getNetPosition(String tradingPair) {
        // Query Cassandra for the net position of the given trading_pair
        Row row = session.execute("SELECT net_position FROM net_positions WHERE trading_pair = ?", tradingPair)
                         .one();

        if (row != null) {
            return Optional.of(row.getDecimal("net_position"));
        } else {
            return Optional.empty(); // No position found for this trading pair
        }
    }

    public void close() {
        if (session != null) session.close();
        if (cluster != null) cluster.close();
    }

    // Example usage (e.g., in a REST endpoint handler)
    public static void main(String[] args) {
        NetPositionQueryService queryService = new NetPositionQueryService();
        String pair = "BTC/USD";
        Optional<BigDecimal> position = queryService.getNetPosition(pair);

        if (position.isPresent()) {
            System.out.println("Net position for " + pair + ": " + position.get());
        } else {
            System.out.println("No net position found for " + pair);
        }
        queryService.close();
    }
}
```

### 4. Eventual Consistency and Data Durability

**Eventual Consistency:**
The system achieves eventual consistency within a few seconds. Trade events are first written to Kafka, which acts as a durable, ordered log. Flink processes these events in order for each `trading_pair`. The processing time in Flink (including network latency to Kafka and to the key-value store) dictates the lag. Flink's checkpointing mechanism ensures that even if a Flink task fails, it can recover its state from the last successful checkpoint and resume processing from the correct offset in Kafka, preventing data loss and maintaining the correct order of updates. The updates to the key-value store are continuous, meaning the query service will eventually reflect all processed trades.

**Data Durability:**
*   **Kafka:** Incoming trade events are durably stored in Kafka. Kafka is designed for high-throughput and fault tolerance, replicating data across multiple brokers. As long as a configured number of replicas are available, data is not lost even if individual brokers fail.
*   **Flink Checkpointing:** Flink periodically checkpoints its operator state (the `currentNetPositionState` in our `NetPositionAggregator`) to a fault-tolerant storage like HDFS or S3. In case of a Flink job or task manager failure, the job can be restarted from the latest successful checkpoint, restoring its state and resuming processing from the corresponding Kafka offsets. This prevents loss of aggregated state.
*   **Key-Value Store (Cassandra):** Cassandra is a distributed, highly available, and fault-tolerant NoSQL database. Data is replicated across multiple nodes according to the configured replication factor. Even if several nodes fail, data remains available and durable as long as the replication factor is satisfied. The Flink sink performs an upsert, ensuring the latest position is always stored.

### Going Further

**CAP Theorem Trade-offs:**

Our chosen design prioritizes **Availability** and **Partition Tolerance (AP)** over strong **Consistency** in the immediate aftermath of a trade.

*   **Availability:** The system is designed to be highly available. Kafka, Flink, and Cassandra are all distributed systems that can tolerate node failures and continue operating. The query service can always retrieve *some* net position, even if it's slightly stale.
*   **Partition Tolerance:** The system is inherently distributed, meaning network partitions are a possibility. It's designed to continue functioning during such partitions, with components operating independently and eventually reconciling their states.
*   **Consistency (Eventual):** We explicitly chose eventual consistency. A user querying a net position immediately after their trade might perceive stale data. The trade event first needs to be written to Kafka, consumed by Flink, processed, and then written to Cassandra. This entire pipeline introduces a delay, typically in the order of hundreds of milliseconds to a few seconds. During this window, the queried net position might not reflect the very latest trade.

**Perceived Stale Data:**
If a user executes a trade and immediately queries their net position for that `trading_pair`, they might see the position *before* their trade has been processed and reflected in the key-value store. This is the direct consequence of choosing eventual consistency. The system guarantees that eventually, within a few seconds, their trade *will* be reflected, and the net position will be accurate. For a high-frequency trading platform, this might be acceptable for display purposes, but critical reconciliation or risk management systems might need to account for this latency or use a separate, strongly consistent (but potentially less scalable) mechanism for immediate post-trade verification if absolute real-time consistency is paramount.

**What breaks first at ten times the scale:**

At ten times the scale (tens of thousands of trades per second), the most likely bottlenecks would be:

1.  **Kafka Throughput/Latency:** While Kafka is highly scalable, a sustained order of magnitude increase in message volume could push its disk I/O, network bandwidth, and broker CPU limits. If producers can't keep up or consumers lag significantly, the end-to-end latency will increase. Scaling Kafka involves adding more brokers and optimizing topic partitions.
2.  **Flink Task Manager Resources:** The Flink job's `NetPositionAggregator` maintains state for each `trading_pair`. If the number of unique `trading_pair`s grows significantly, or the trade volume per `trading_pair` increases, the memory and CPU resources on Flink Task Managers could become a bottleneck. Flink's state backend (e.g., RocksDB) can spill state to disk, but this adds latency. Scaling Flink involves adding more Task Managers and optimizing parallelism.
3.  **Cassandra Write Throughput:** While Cassandra is designed for high write throughput, a ten-fold increase in updates to `net_positions` could strain its write capacity, especially if the `trading_pair` keys are not uniformly distributed across nodes, leading to hot spots. Proper data modeling, partitioning, and adding more Cassandra nodes would be necessary.
4.  **Network Bandwidth:** The sheer volume of data moving between Kafka, Flink, and Cassandra could saturate network links within the data center, requiring careful network design and potentially dedicated high-bandwidth interconnects.

The PostgreSQL database, which was the initial bottleneck, would definitely fail to keep up at this scale, reinforcing the need for the distributed stream processing approach.
