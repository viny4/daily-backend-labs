## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee expenses. A core feature allows employees to submit expense reports, which then go through an approval workflow. The `expense_reports` table has grown significantly, now containing over 50 million rows. Each report has a `status` (e.g., 'pending', 'approved', 'rejected'), a `submitter_user_id`, and an `approver_user_id`.

A common operation is for managers to view a list of *all* expense reports that are currently `pending` their approval. This query has historically been fast but has recently degraded to 5-10 seconds, which is unacceptable for a frequently accessed page. The `expense_reports` table also has a `created_at` timestamp.

The database is PostgreSQL 14, running on AWS RDS with `gp3` storage. The current instance type is `db.m5.xlarge`, with 4 vCPU and 16GB RAM.

## Requirements

The core problem is the performance of the query that fetches pending expense reports for a specific approver. You need to identify and implement a solution that brings this query's execution time consistently under 100ms, even with the large table size and concurrent access from thousands of managers. The solution must be robust enough to handle future growth of the `expense_reports` table up to 100 million rows. You can modify the database schema (add/modify indexes, change table structure if truly necessary) but cannot introduce new tables or external services.

Constraints:
*   **Scale:** The `expense_reports` table is 50M+ rows and growing.
*   **Latency:** The target query must execute in under 100ms.
*   **Concurrency:** Thousands of managers might query this view concurrently.
*   **Database:** PostgreSQL 14.
*   **Resources:** You can assume the current RDS instance and storage are sufficient if optimized correctly.
*   **No new tables/services:** Solution must be within the existing `expense_reports` table and PostgreSQL features.

## Worked answer

### 1. `CREATE TABLE` statement

```sql
CREATE TABLE expense_reports (
    id BIGSERIAL PRIMARY KEY,
    status VARCHAR(20) NOT NULL,
    submitter_user_id BIGINT NOT NULL,
    approver_user_id BIGINT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()
);
```

**Explanation of choices:**

*   `id BIGSERIAL PRIMARY KEY`: `BIGSERIAL` is used for auto-incrementing primary keys, suitable for tables expected to grow very large (over 2 billion rows, where `INT` would overflow).
*   `status VARCHAR(20) NOT NULL`: `VARCHAR` with a reasonable length constraint for status values like 'pending', 'approved', 'rejected'. `NOT NULL` ensures data integrity.
*   `submitter_user_id BIGINT NOT NULL`, `approver_user_id BIGINT NOT NULL`: `BIGINT` is used for user IDs, assuming a large number of users in a B2B SaaS platform. `NOT NULL` ensures these critical foreign keys are always present.
*   `created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT NOW()`: Stores the creation timestamp, including timezone information, which is best practice for applications spanning different regions. `DEFAULT NOW()` automatically sets the timestamp on insertion.

### 2. SQL query to fetch pending expense reports

```sql
SELECT
    id,
    status,
    submitter_user_id,
    approver_user_id,
    created_at
FROM
    expense_reports
WHERE
    approver_user_id = 123 AND status = 'pending'
ORDER BY
    created_at DESC;
```

**Explanation:**

This query selects all relevant columns for an expense report. The `WHERE` clause filters by the specific `approver_user_id` and `status = 'pending'`, which are the core conditions for the slow query. `ORDER BY created_at DESC` is added because managers typically want to see the most recent reports first.

### 3. `CREATE INDEX` statements and other DDL changes

The primary optimization will be a composite index.

```sql
CREATE INDEX idx_expense_reports_approver_status_created_at
ON expense_reports (approver_user_id, status, created_at DESC);
```

**Explanation of choices:**

*   **Composite Index:** The index `idx_expense_reports_approver_status_created_at` is a composite index on `(approver_user_id, status, created_at DESC)`.
    *   `approver_user_id`: This is the first column in the index because it's the most selective predicate in the `WHERE` clause (filtering for a specific user).
    *   `status`: This is the second column because it's the next predicate in the `WHERE` clause, further narrowing down the results to only 'pending' reports.
    *   `created_at DESC`: This is the third column and is included with `DESC` ordering. This is crucial for two reasons:
        1.  It allows the index to directly satisfy the `ORDER BY created_at DESC` clause without needing a separate sort operation, which can be very expensive for large result sets.
        2.  It can act as a "covering index" for the `ORDER BY` part, meaning the database can retrieve the `created_at` values directly from the index without having to visit the main table rows, further reducing I/O.

**Why not other indexes?**

*   A simple index on `approver_user_id` would help filter by approver, but PostgreSQL would still have to scan all rows for that approver and then filter by `status` and sort by `created_at`, potentially leading to many random I/O operations.
*   An index on `status` alone would be almost useless for this query, as 'pending' might still represent a large fraction of 50M rows.
*   An index on `(approver_user_id, status)` would be good for filtering, but the `ORDER BY created_at DESC` would still require a separate sort step, which could be slow.

### 4. Explanation of performance improvement

The proposed solution significantly improves performance by creating a **composite index** that directly supports both the filtering conditions (`WHERE approver_user_id = X AND status = 'pending'`) and the sorting requirement (`ORDER BY created_at DESC`).

Here's a step-by-step breakdown of why it works:

1.  **Efficient Filtering:** When the query executes, PostgreSQL can use the index `idx_expense_reports_approver_status_created_at` to quickly locate the exact rows that match `approver_user_id = 123` and `status = 'pending'`. Because `approver_user_id` is the leading column, the database can jump directly to the relevant section of the index. Then, within that section, it can quickly find entries where `status` is 'pending'. This avoids a full table scan or even a partial table scan that would be required with less specific indexes.

2.  **Elimination of Sorting:** The `created_at DESC` part of the index is critical. Since the data within the index for a given `(approver_user_id, status)` combination is already ordered by `created_at` in descending order, PostgreSQL can read the results directly from the index in the requested order. This completely bypasses the need for an expensive in-memory or on-disk sort operation, which is often a major bottleneck for queries returning many rows.

3.  **Reduced I/O (Index-Only Scan Potential):** For the columns included in the `SELECT` list (`id`, `status`, `submitter_user_id`, `approver_user_id`, `created_at`), if all these columns were present in the index (which they are not in our current index, only `approver_user_id`, `status`, `created_at`), PostgreSQL could perform an "index-only scan." This means it would retrieve all necessary data directly from the index without ever needing to touch the main table's data blocks. While our index doesn't fully cover all selected columns, it covers the filtering and ordering columns, significantly reducing the number of heap fetches compared to a non-indexed or poorly indexed query. The `id` column is implicitly part of every index entry for row identification, and `approver_user_id`, `status`, `created_at` are explicitly in the index. The remaining column `submitter_user_id` would require a heap fetch, but the number of such fetches would be limited to the actual result set, which is expected to be small for a single manager's pending reports.

By combining these factors, the database can fulfill the query requirements with minimal disk I/O and CPU usage, leading to sub-100ms response times even with a very large table.

### Going further

#### Trade-offs of the chosen solution

While highly effective for read performance, the composite index comes with several trade-offs, primarily impacting write operations and storage:

1.  **Increased Write Overhead:**
    *   **Insertions:** Every time a new `expense_report` is inserted, PostgreSQL must update not only the main table but also the `idx_expense_reports_approver_status_created_at` index. This involves writing new index entries, which takes time and consumes CPU and I/O resources.
    *   **Updates:** If the `approver_user_id`, `status`, or `created_at` columns of an existing expense report are updated, the corresponding index entry must also be updated. This often means deleting the old index entry and inserting a new one, which is more expensive than a simple update to the main table. For example, when a report's `status` changes from 'pending' to 'approved', the index entry for that report will need to be moved or re-indexed.
    *   **Deletions:** Deleting a row also requires removing its corresponding entry from the index.

    For a high-volume system with thousands of expense reports being submitted, approved, or rejected concurrently, this write overhead can become noticeable.

2.  **Increased Storage Consumption:**
    *   Indexes consume disk space. A composite index on three `BIGINT/VARCHAR/TIMESTAMP` columns across 50-100 million rows will be substantial. This directly translates to higher storage costs (e.g., in AWS RDS gp3) and potentially more I/O for index scans if the index doesn't fit entirely in memory. For 100M rows, an index like this could easily be several GBs.

3.  **Impact on Other Queries:**
    *   While this index is perfect for the specific "pending reports for an approver" query, it might not be optimal for other common queries. For example, if there's a need to query all reports for a `submitter_user_id` or all 'rejected' reports regardless of approver, different indexes might be required. Adding too many indexes can exacerbate the write overhead and storage consumption issues.

#### Scenarios where this optimization could become a bottleneck or have unintended side effects

*   **Extremely High Write Throughput:** If the rate of `INSERT`s and `UPDATE`s (especially on `status` or `approver_user_id`) becomes exceptionally high (e.g., tens of thousands per second), the overhead of maintaining this large index could lead to write contention, increased transaction latency, and higher CPU utilization on the database server. This could manifest as slower report submissions or approval actions.
*   **Frequent `status` changes:** If expense reports frequently change `status` (e.g., from 'pending' to 'in review' to 'approved' to 'reimbursed'), each status change would incur an index update cost.
*   **Memory Pressure:** While the current instance `db.m5.xlarge` (16GB RAM) might be sufficient, if the database grows significantly and many large indexes are created, the total size of frequently accessed indexes might exceed the available `shared_buffers` and OS cache. This would lead to more physical disk reads for index lookups, slowing down even optimized queries.
*   **Database Maintenance:** Operations like `VACUUM` (especially `VACUUM FULL`), `REINDEX`, or restoring from backups will take longer due to the larger data footprint, impacting maintenance windows.
*   **"Hot" Index Blocks:** If a small number of `approver_user_id`s are extremely active (e.g., a super-approver), the specific blocks in the index corresponding to their `approver_user_id` and `status='pending'` could become "hot," leading to contention for locks on those index pages during concurrent updates or insertions for that approver.

#### What breaks first at ten times the scale (1 billion rows)

At 1 billion rows, the primary bottlenecks would likely be:

1.  **Write Throughput Degradation:** The write overhead for `INSERT`s and `UPDATE`s would become severe. Maintaining an index of this size (potentially hundreds of GBs) with every write operation would significantly increase transaction latency. The I/O subsystem (even `gp3`) might struggle to keep up with the constant random writes to update index pages, leading to I/O wait times.
2.  **Storage Costs and Management:** The sheer volume of data and indexes would lead to very high storage costs. Managing backups, restores, and replication would become more complex and time-consuming.
3.  **`VACUUM` Performance:** PostgreSQL's MVCC (Multi-Version Concurrency Control) requires `VACUUM` to clean up dead tuples. With 1 billion rows and high update/delete rates, `VACUUM` operations would take much longer, potentially leading to table bloat if not managed aggressively, which further degrades performance.
4.  **Index Scan Efficiency (Memory):** While the index would still be logically efficient, the probability of the entire index (or even the frequently accessed parts) fitting into RAM would decrease. This would mean more disk I/O for index lookups, even for highly selective queries.
5.  **Scaling Limits of a Single Instance:** A single `db.m5.xlarge` or even larger instance would likely hit its limits in terms of CPU, RAM, and I/O for a 1 billion-row table with high concurrency and mixed workloads. At this scale, sharding or more advanced database architectures would likely be necessary.
