## Scenario

Your team maintains a critical backend service that manages real-time inventory for a large e-commerce platform. When a customer places an order, your system needs to decrement the stock of the ordered items. This happens across hundreds of thousands of distinct SKUs (Stock Keeping Units) and potentially thousands of orders per second during peak sales events. The `inventory` table, currently in a single PostgreSQL instance, contains hundreds of millions of rows, making row-level locking during high concurrency a significant bottleneck, leading to increased latency for order placement and occasional deadlocks.

The current `decrement_stock(sku_id, quantity)` function naively acquires a lock on the `inventory` row for the `sku_id`, decrements the quantity, and releases the lock. This works for low traffic but struggles under heavy load, impacting the user experience during checkout.

## Requirements

The core problem is to efficiently decrement inventory for high-volume SKUs without causing a bottleneck on a single database row or instance. You need to propose a mechanism that allows for high-concurrency, low-latency stock decrements, even when many simultaneous orders target the same popular items. Consider that eventual consistency for the *exact* stock count is acceptable for the displayed quantity on the product page (a slight delay is fine), but strong consistency is required for the *actual* decrement during order processing to prevent overselling. The solution must gracefully handle transient failures (e.g., network partitions, service restarts) without losing stock decrement requests or creating phantom stock.

3.  Describe how your proposed solution addresses the latency and concurrency issues seen with the current single-row locking approach.
4.  Briefly describe how you would handle reconciliation or rollback if an order fails *after* stock has been decremented.

## Worked answer

### 1. High-level architectural sketch

The core idea is to move away from direct row-level locking on the `inventory` table for every decrement. Instead, we'll use a distributed, asynchronous, and eventually consistent approach for the bulk of inventory updates, while maintaining strong consistency for the critical decrement operation itself. This involves a combination of message queues, a dedicated inventory service, and a different approach to database interaction.

Here's the architectural sketch:

```
[Customer Places Order]
        |
        V
[Order Service]
    - Validates order
    - Publishes "Order Placed" event
        | (Kafka/RabbitMQ Topic: order_events)
        V
[Inventory Decrement Processor] (New Service)
    - Subscribes to "Order Placed" events
    - For each item in order:
        - Attempts to reserve/decrement stock using a "compare-and-swap" (CAS) operation
          on the inventory database.
        - If successful:
            - Publishes "Stock Decremented" event (Kafka Topic: inventory_events)
            - Updates local cache (optional, for read-heavy SKUs)
        - If unsuccessful (e.g., insufficient stock, contention):
            - Publishes "Stock Decrement Failed" event (Kafka Topic: inventory_events)
            - Retries (with backoff) or flags for manual intervention/rollback
        |
        V
[Inventory Database] (PostgreSQL, potentially sharded)
    - `inventory` table: `sku_id`, `current_stock`, `reserved_stock`
    - `inventory_transactions` table: `transaction_id`, `sku_id`, `quantity_change`, `status`, `timestamp`, `order_id`
        |
        V
[Inventory Read Service] (Existing or new)
    - Subscribes to "Stock Decremented" and "Stock Decrement Failed" events
    - Updates a read-optimized data store (e.g., Redis, materialized view) for product page display.
    - Provides eventual consistent stock levels for display.
```

**Pseudo-code for `decrement_stock` within `Inventory Decrement Processor`:**

```python
# Inventory Decrement Processor service
def handle_order_placed_event(order_event):
    order_id = order_event.order_id
    items = order_event.items

    for item in items:
        sku_id = item.sku_id
        quantity = item.quantity

        try:
            # Attempt to atomically decrement stock
            success = attempt_atomic_stock_decrement(sku_id, quantity, order_id)
            if success:
                publish_event("StockDecremented", {"order_id": order_id, "sku_id": sku_id, "quantity": quantity})
                # Potentially update a local cache for this SKU
            else:
                publish_event("StockDecrementFailed", {"order_id": order_id, "sku_id": sku_id, "quantity": quantity, "reason": "Insufficient stock or contention"})
                # Log for retry or manual review
        except Exception as e:
            publish_event("StockDecrementFailed", {"order_id": order_id, "sku_id": sku_id, "quantity": quantity, "reason": f"Database error: {str(e)}"})
            # Log and potentially retry

def attempt_atomic_stock_decrement(sku_id, quantity, order_id):
    # This function uses a transaction and a CAS-like update
    with db_connection.cursor() as cursor:
        try:
            # Use SELECT FOR UPDATE to prevent other transactions from modifying this row
            # while we check and update. This is still row-level locking, but
            # it's very short-lived and only for the specific SKU.
            cursor.execute(
                "SELECT current_stock FROM inventory WHERE sku_id = %s FOR UPDATE;",
                (sku_id,)
            )
            result = cursor.fetchone()

            if result is None:
                # SKU not found, handle error
                db_connection.rollback()
                return False

            current_stock = result[0]

            if current_stock >= quantity:
                new_stock = current_stock - quantity
                cursor.execute(
                    "UPDATE inventory SET current_stock = %s WHERE sku_id = %s;",
                    (new_stock, sku_id)
                )
                cursor.execute(
                    "INSERT INTO inventory_transactions (order_id, sku_id, quantity_change, status) VALUES (%s, %s, %s, 'DECREMENTED');",
                    (order_id, sku_id, -quantity)
                )
                db_connection.commit()
                return True
            else:
                # Insufficient stock
                db_connection.rollback()
                return False
        except Exception as e:
            db_connection.rollback()
            raise e # Re-raise to be caught by the caller for logging/event publishing
```

**Key components:**

*   **Order Service:** The entry point for customer orders. It's responsible for initial order validation and then publishing an `Order Placed` event. It does *not* directly decrement stock.
*   **Kafka/RabbitMQ:** A robust message broker for asynchronous communication between services. Ensures durability of events and allows for decoupled processing.
*   **Inventory Decrement Processor:** A dedicated service responsible for handling stock decrements. It subscribes to `Order Placed` events and attempts to update the `inventory` database. This service scales independently.
*   **Inventory Database (PostgreSQL):** The source of truth for stock levels.
    *   `inventory` table: `sku_id` (PK), `current_stock` (integer, >=0), `reserved_stock` (integer, >=0, for future extensions like pre-order or cart reservation).
    *   `inventory_transactions` table: Logs every stock change, providing an audit trail and facilitating reconciliation.
*   **Inventory Read Service:** A service that consumes `inventory_events` and updates a separate, read-optimized data store (e.g., Redis, a materialized view, or even a separate read replica database) for displaying stock levels on product pages. This allows the display to be eventually consistent and highly scalable without hitting the primary inventory database.

### 2. How to ensure atomic and durable stock decrements

To ensure atomicity and durability, preventing overselling even under concurrent requests for the same SKU, we rely on the ACID properties of the PostgreSQL database, specifically using transactions and `SELECT FOR UPDATE`.

The `attempt_atomic_stock_decrement` function demonstrates this:

```sql
-- Schema for inventory table
CREATE TABLE inventory (
    sku_id VARCHAR(255) PRIMARY KEY,
    current_stock INTEGER NOT NULL CHECK (current_stock >= 0),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Schema for inventory_transactions table
CREATE TABLE inventory_transactions (
    transaction_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    order_id VARCHAR(255) NOT NULL,
    sku_id VARCHAR(255) NOT NULL REFERENCES inventory(sku_id),
    quantity_change INTEGER NOT NULL, -- Negative for decrements, positive for increments
    status VARCHAR(50) NOT NULL, -- e.g., 'DECREMENTED', 'FAILED', 'ROLLED_BACK'
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- Index for faster lookups by order_id and sku_id
CREATE INDEX idx_inventory_transactions_order_sku ON inventory_transactions (order_id, sku_id);
```

**Explanation:**

1.  **Transaction Isolation:** The entire `SELECT FOR UPDATE`, `UPDATE`, and `INSERT` sequence is wrapped in a single database transaction. PostgreSQL guarantees that transactions are atomic (all or nothing) and isolated (concurrent transactions don't interfere with each other in ways that lead to incorrect results).
2.  **`SELECT FOR UPDATE`:** This is the critical mechanism. When a transaction executes `SELECT ... FOR UPDATE` on a row, it acquires an exclusive row-level lock on that row. Any other transaction attempting to `SELECT FOR UPDATE`, `UPDATE`, or `DELETE` the same row will be blocked until the first transaction commits or rolls back.
    *   This ensures that when the `Inventory Decrement Processor` reads `current_stock` for a `sku_id`, it gets the absolute latest value, and no other concurrent decrement can modify that row until the current transaction completes.
    *   It effectively serializes access to a *single SKU's row*, but not the entire table.
3.  **Compare-and-Swap (CAS) Logic:** Although not explicitly a CAS instruction, the logic `if current_stock >= quantity` acts as a check. We read the `current_stock`, perform a check, and then update. Because of `SELECT FOR UPDATE`, we are guaranteed that `current_stock` hasn't changed between the `SELECT` and the `UPDATE` within our transaction.
4.  **Durability:** Once the `db_connection.commit()` is called, PostgreSQL guarantees that the changes are permanently stored on disk, even in the event of a system crash.
5.  **Idempotency (Partial):** The `Inventory Decrement Processor` should be designed to be idempotent where possible. If an `Order Placed` event is processed twice due to message broker retries, the `attempt_atomic_stock_decrement` function will attempt to decrement again. If the `inventory_transactions` table is checked for an existing decrement for that `order_id` and `sku_id` *before* the `SELECT FOR UPDATE`, we can prevent duplicate decrements. However, for simplicity and to prioritize preventing overselling, the current approach relies on the `order_id` in `inventory_transactions` for reconciliation rather than strict idempotency at the decrement stage. A more robust idempotent check would involve a unique constraint on `(order_id, sku_id, quantity_change)` in `inventory_transactions` or checking for existing successful transactions for that order item.

### 3. How the proposed solution addresses latency and concurrency issues

The proposed solution addresses latency and concurrency issues by:

1.  **Decoupling Order Placement from Stock Decrement:**
    *   The `Order Service` no longer waits for the database `UPDATE` to complete. It quickly publishes an `Order Placed` event to Kafka and can respond to the customer, significantly reducing the perceived latency of order placement.
    *   The actual stock decrement happens asynchronously in the `Inventory Decrement Processor`.
2.  **Shifting Bottleneck from Global Lock to Row-Level Lock (on specific SKUs):**
    *   The original problem was "row-level locking during high concurrency a significant bottleneck, leading to increased latency for order placement and occasional deadlocks." While we still use `SELECT FOR UPDATE`, it's crucial to understand the difference:
        *   **Old:** `Order Service` directly hits the DB, locking the row, making the customer wait. If many orders target *different* SKUs, the overall throughput is limited by the single DB instance's connection pool and transaction processing capacity. If many orders target the *same* SKU, they all contend for that single row lock, causing serialization and latency.
        *   **New:** The `Inventory Decrement Processor` handles the DB interaction.
            *   **High-volume SKUs:** For popular items, requests will still contend for the `SELECT FOR UPDATE` lock on that *specific SKU's row*. However, the *customer is not waiting*. The `Inventory Decrement Processor` can retry, queue, or handle this contention gracefully without impacting the order placement experience. The latency of the *decrement itself* for a highly contended SKU might still be high, but it's now an internal system latency, not user-facing.
            *   **Low-volume SKUs:** For less popular items, contention is minimal. The `SELECT FOR UPDATE` is very fast, typically milliseconds, as it only locks one row.
3.  **Asynchronous Processing and Backpressure:**
    *   Kafka acts as a buffer. During peak events, if the `Inventory Decrement Processor` cannot keep up, messages will queue up in Kafka. This provides backpressure without crashing the system or directly impacting the `Order Service`. The `Inventory Decrement Processor` can be scaled horizontally by adding more instances to consume messages from Kafka in parallel.
4.  **Horizontal Scalability of Processing:**
    *   Multiple instances of the `Inventory Decrement Processor` can run concurrently, each processing different `Order Placed` events. Kafka's consumer groups ensure that each message is processed by only one consumer within the group. This allows the system to handle thousands of orders per second by distributing the workload across many processor instances.
5.  **Dedicated Read Path:**
    *   The `Inventory Read Service` ensures that displaying stock on product pages doesn't contend with the write path. This read path can be highly optimized (e.g., using Redis for caching) and scaled independently, providing low-latency, eventually consistent stock information to customers.

**Trade-offs:**

*   **Increased Complexity:** We've introduced new services (Inventory Decrement Processor, Inventory Read Service), a message queue (Kafka), and asynchronous processing, which adds operational overhead and complexity compared to a single monolithic service.
*   **Eventual Consistency for Display:** The stock displayed on product pages will be eventually consistent, meaning there might be a slight delay (seconds to minutes, depending on processing speed) between an actual decrement and its reflection on the website. This is explicitly stated as acceptable in the requirements.
*   **Distributed Transactions/Sagas:** While the core decrement is atomic, the overall "order placed -> stock decremented -> payment processed -> order fulfilled" flow becomes a distributed transaction, which is harder to reason about and requires careful handling of failures and rollbacks (addressed in the next section).

### 4. Reconciliation or rollback if an order fails after stock has been decremented

Handling failures after stock decrement requires a robust reconciliation and rollback mechanism, often implemented as part of a [Saga pattern](https://microservices.io/patterns/data/saga.html).

1.  **Transaction Logging:** The `inventory_transactions` table is crucial here. Every successful decrement (and potentially every attempt) is logged. This provides an audit trail.

    ```sql
    INSERT INTO inventory_transactions (order_id, sku_id, quantity_change, status)
    VALUES (%s, %s, %s, 'DECREMENTED');
    ```

2.  **Order State Machine:** The `Order Service` (or a dedicated `Order Orchestrator` service) maintains the state of an order (e.g., `PENDING_PAYMENT`, `PAYMENT_FAILED`, `STOCK_DECREMENTED`, `FULFILLED`).

3.  **Compensation Events:**
    *   If the `Order Service` determines that an order needs to be cancelled *after* stock has been successfully decremented (e.g., payment failed, customer cancelled), it publishes a `Order Cancelled` or `Stock Rollback Required` event to Kafka.
    *   This event would contain `order_id` and `sku_id` (or the full list of items).

4.  **Inventory Rollback Processor:**
    *   A new service (or an extension of the `Inventory Decrement Processor`) subscribes to `Order Cancelled` / `Stock Rollback Required` events.
    *   When it receives such an event, it performs an *increment* operation on the `inventory` table for the specified SKUs.

    **Pseudo-code for `Inventory Rollback Processor`:**

    ```python
    def handle_stock_rollback_event(rollback_event):
        order_id = rollback_event.order_id
        sku_id = rollback_event.sku_id
        quantity = rollback_event.quantity # This should be the original decremented quantity

        with db_connection.cursor() as cursor:
            try:
                # Check if this specific decrement was actually successful and not already rolled back
                cursor.execute(
                    "SELECT quantity_change FROM inventory_transactions WHERE order_id = %s AND sku_id = %s AND status = 'DECREMENTED';",
                    (order_id, sku_id)
                )
                decremented_quantity_result = cursor.fetchone()

                if decremented_quantity_result is None:
                    # No successful decrement found, or already rolled back/failed. Log and exit.
                    return

                original_decremented_quantity = abs(decremented_quantity_result[0]) # Should be positive

                # Atomically increment stock
                cursor.execute(
                    "UPDATE inventory SET current_stock = current_stock + %s WHERE sku_id = %s;",
                    (original_decremented_quantity, sku_id)
                )
                cursor.execute(
                    "INSERT INTO inventory_transactions (order_id, sku_id, quantity_change, status) VALUES (%s, %s, %s, 'ROLLED_BACK');",
                    (order_id, sku_id, original_decremented_quantity)
                )
                # Update the status of the original decrement transaction to 'ROLLED_BACK' or similar
                cursor.execute(
                    "UPDATE inventory_transactions SET status = 'ROLLED_BACK' WHERE order_id = %s AND sku_id = %s AND status = 'DECREMENTED';",
                    (order_id, sku_id)
                )
                db_connection.commit()
                publish_event("StockRolledBack", {"order_id": order_id, "sku_id": sku_id, "quantity": original_decremented_quantity})
            except Exception as e:
                db_connection.rollback()
                # Log error, potentially publish a "StockRollbackFailed" event for alert
                raise e
    ```

5.  **Idempotency for Rollback:** The rollback processor must be idempotent. If it receives the same `Order Cancelled` event multiple times, it should only increment the stock once. This can be achieved by:
    *   Checking the `inventory_transactions` table for an existing `ROLLED_BACK` entry for that `order_id` and `sku_id`.
    *   Using a unique constraint on `(order_id, sku_id, status)` where `status` is `ROLLED_BACK` to prevent duplicate insertions.
    *   The `UPDATE inventory_transactions SET status = 'ROLLED_BACK'` also helps ensure that a specific decrement is only rolled back once.

6.  **Manual Reconciliation/Alerting:** For critical failures (e.g., the rollback processor crashes repeatedly, or a database issue prevents rollback), an alerting system should notify operations staff. The `inventory_transactions` table provides the necessary data to manually reconcile stock if automated processes fail. Discrepancies between the `Order Service`'s view of an order's state and the `Inventory Service`'s transactions can be detected and flagged.

### Going further: Monitoring for race conditions or inconsistencies

Monitoring a distributed inventory system for race conditions or inconsistencies requires a multi-faceted approach, combining application-level metrics, distributed tracing, and data integrity checks.

1.  **Application Metrics & Dashboards:**
    *   **Inventory Decrement Processor:**
        *   `decrement_success_count`: Total successful decrements.
        *   `decrement_failure_count`: Total failed decrements (e.g., insufficient stock, DB errors).
        *   `decrement_latency_p99`: Latency of the `attempt_atomic_stock_decrement` function. High latency here for specific SKUs can indicate contention.
        *   `messages_processed_per_second`: Throughput from Kafka.
        *   `messages_failed_to_process_per_second`: Errors in event processing logic.
        *   `retry_count_per_sku`: How many times a decrement for a specific SKU was retried. High counts indicate contention.
    *   **Inventory Rollback Processor:**
        *   `rollback_success_count`, `rollback_failure_count`, `rollback_latency_p99`.
    *   **Kafka Consumer Lag:** Monitor the consumer lag for all inventory-related consumer groups. High lag indicates that processors are falling behind, potentially leading to stale stock displays or delayed decrements.
    *   **Database Metrics:**
        *   `active_connections`, `transaction_duration_p99`, `deadlock_count` (should be zero or very low with `SELECT FOR UPDATE`), `row_lock_wait_time`.
        *   Specific metrics for `inventory` table: `update_count`, `select_for_update_count`.
    *   **Alerting:** Set up alerts for:
        *   High `decrement_failure_count` (especially for "insufficient stock" when stock *should* be available).
        *   Sustained high `decrement_latency_p99` for critical SKUs.
        *   High Kafka consumer lag.
        *   Database errors or high `row_lock_wait_time`.

2.  **Distributed Tracing:**
    *   Implement distributed tracing (e.g., OpenTelemetry, Jaeger) across all services involved: `Order Service`, Kafka, `Inventory Decrement Processor`, `Inventory Read Service`.
    *   Each `Order Placed` event should carry a trace ID. This allows you to visualize the entire flow of an order, from placement to stock decrement and display update.
    *   **Detecting Race Conditions:** Tracing helps identify where delays occur and if operations are happening out of expected order. For example, if a `Stock Decremented` event is published *before* a `Payment Successful` event, but the order requires payment first, it might indicate a logical race or incorrect orchestration.
    *   **Pinpointing Bottlenecks:** Easily see which service or database operation is adding the most latency to the overall flow.

3.  **Data Integrity Checks (Reconciliation Jobs):**
    *   **Periodically run batch jobs** to compare the `current_stock` in the `inventory` table against the sum of `quantity_change` in `inventory_transactions` for each SKU.
        *   `SELECT sku_id, SUM(quantity_change) FROM inventory_transactions GROUP BY sku_id;`
        *   Compare this sum with `SELECT sku_id, current_stock FROM inventory;`
        *   Any discrepancy indicates a data inconsistency (e.g., a decrement failed to write to `inventory_transactions` but updated `inventory`, or vice-versa).
    *   **Cross-service Reconciliation:**
        *   Compare the state of orders in the `Order Service` (e.g., `status = 'STOCK_DECREMENTED'`) with the `inventory_transactions` table. For every order item marked as stock-decremented in the `Order Service`, there should be a corresponding `DECREMENTED` transaction in `inventory_transactions`.
        *   Similarly, for every `ROLLED_BACK` transaction, ensure the `Order Service` reflects a cancelled or failed state.
    *   **Alerting on Discrepancies:** If these reconciliation jobs find inconsistencies, they should trigger high-priority alerts.

4.  **Synthetic Transactions:**
    *   Regularly run synthetic "test orders" through the entire system in production.
    *   Monitor the end-to-end latency and correctness of these transactions. For example, place an order for a known SKU, verify stock decrement, and then cancel it to verify rollback. This provides real-time validation of the entire pipeline.

5.  **Chaos Engineering:**
    *   Periodically inject failures (e.g., kill an `Inventory Decrement Processor` instance, introduce network latency to the database, temporarily pause Kafka) to observe how the system recovers and if inconsistencies arise. This helps validate the robustness of the failure handling and rollback mechanisms.

By combining these monitoring strategies, you can gain comprehensive visibility into the health and consistency of the distributed inventory system, detecting potential issues proactively.
