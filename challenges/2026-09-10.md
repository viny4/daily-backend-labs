## Scenario

Your team maintains a critical backend service for a fast-growing online learning platform. Users can create and enroll in courses, and each course consists of multiple `lessons`. The platform is experiencing rapid growth, and a key feature is the "Course Progress" page, which shows a user their completion status for all lessons in a course.

The `lessons` table, which stores details about each lesson (e.g., `id`, `course_id`, `title`, `duration_seconds`), has grown to 50 million rows. Each course typically has 10-50 lessons.

The `user_lesson_progress` table, tracking which lessons a user has completed (`user_id`, `lesson_id`, `completed_at`), has hundreds of millions of rows, with high write volume (every time a user completes a lesson).

The current "Course Progress" API endpoint (`GET /api/v1/courses/{course_id}/progress`) queries both tables to determine, for a given `user_id` and `course_id`, which lessons exist in the course and which of those the user has completed. This query now takes an unacceptable 5-10 seconds, particularly for popular courses with many enrolled users hitting the endpoint concurrently.

## Requirements

The primary requirement is to significantly reduce the latency of the "Course Progress" API endpoint. The target latency is under 500ms, even under peak load. The solution must handle:

- **Scale:** `lessons` table with 50M rows, `user_lesson_progress` with hundreds of millions of rows and high write throughput.
- **Concurrency:** Hundreds of concurrent requests to the "Course Progress" endpoint during peak hours.
- **Data Freshness:** Progress data must be fresh, reflecting completions within a few seconds.
- **Database Load:** Minimize additional load on the primary PostgreSQL database, which is already under pressure.
- **Multi-tenancy:** The system implicitly supports many courses and many users.

### 2. Explanation of the core problem and proposed solution

The core problem is that the "Course Progress" API endpoint performs a complex join query on two very large tables (`lessons` and `user_lesson_progress`) on the primary database, leading to high latency and significant database load. The `user_lesson_progress` table's high write volume further exacerbates contention. The proposed solution introduces a dedicated `CourseProgressService` that leverages a fast, in-memory cache (Redis) to serve most requests, drastically reducing latency and offloading the primary database.

When a user requests their course progress, the `CourseProgressService` first checks Redis. If the data is present and fresh, it's returned immediately. If not, it falls back to a PostgreSQL read replica. A separate `CourseProgressUpdater` service asynchronously populates and updates the Redis cache. This updater consumes change data capture (CDC) events from the primary database for `user_lesson_progress` and `lessons` tables. This ensures data freshness within seconds while minimizing direct load on the primary database. The use of a read replica for cache misses further distributes read load, and Redis's high throughput handles concurrency.

### 3. New or modified data structures

#### Modified `lessons` table (for indexing)

The existing `lessons` table is likely missing an index that would be beneficial for the read replica fallback.

```sql
-- Existing table structure (simplified)
CREATE TABLE lessons (
    id UUID PRIMARY KEY,
    course_id UUID NOT NULL,
    title VARCHAR(255) NOT NULL,
    duration_seconds INTEGER NOT NULL,
    -- other fields
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- New index to optimize fetching all lessons for a course
CREATE INDEX idx_lessons_on_course_id ON lessons (course_id);
```

**Purpose:** This index allows for efficient retrieval of all lessons belonging to a specific `course_id`, which is a critical part of the "Course Progress" query.

#### Redis Cache Schema

Redis will store the progress for each user and course. A suitable data structure is a Redis Hash, where the key identifies the user and course, and the hash fields represent lesson IDs and their completion status.

**Key Format:** `user_progress:{user_id}:{course_id}`

**Value Type:** Redis Hash

**Hash Fields:**
*   `{lesson_id_1}`: `1` (if completed), `0` (if not completed)
*   `{lesson_id_2}`: `1` (if completed), `0` (if not completed)
*   ...
*   `_last_updated`: Unix timestamp (for freshness checks)

**Example Entry:**

```
KEY: user_progress:a1b2c3d4-e5f6-7890-1234-567890abcdef:course-xyz-123
TYPE: hash
FIELDS:
  lesson-111: 1
  lesson-222: 0
  lesson-333: 1
  _last_updated: 1678886400
```

**Purpose:**
*   **`user_progress:{user_id}:{course_id}`:** Uniquely identifies the progress for a specific user within a specific course.
*   **`{lesson_id}: 1|0`:** Stores the completion status for each lesson. Using `1` for completed and `0` for not completed is space-efficient.
*   **`_last_updated`:** Allows the `CourseProgressService` to check the freshness of the cached data. If the cached data is too old (e.g., older than 10 seconds), it can trigger a read from the read replica to ensure freshness, then update the cache.

**Cache Invalidation/Expiration:**
*   Entries will have a Time-To-Live (TTL), e.g., 5 minutes. This handles cases where the `CourseProgressUpdater` might miss an event or fail.
*   The `CourseProgressUpdater` will actively update the cache upon receiving CDC events, effectively "refreshing" the TTL.

#### `user_lesson_progress` table (for indexing)

Similar to the `lessons` table, the `user_lesson_progress` table needs appropriate indexing for efficient lookups.

```sql
-- Existing table structure (simplified)
CREATE TABLE user_lesson_progress (
    user_id UUID NOT NULL,
    lesson_id UUID NOT NULL,
    completed_at TIMESTAMP WITH TIME ZONE NOT NULL,
    PRIMARY KEY (user_id, lesson_id) -- Composite primary key
);

-- New index to optimize fetching all completed lessons for a user in a course context
CREATE INDEX idx_user_lesson_progress_on_user_id_lesson_id ON user_lesson_progress (user_id, lesson_id);
-- A more specific index might be needed if course_id is not directly in this table,
-- but rather inferred via a join to the lessons table.
-- Given the current schema, the primary key is already efficient for direct lookups.
-- If we frequently query for all progress for a user across *all* lessons,
-- an index on (user_id, completed_at) could be useful, but not for this specific problem.
```

**Purpose:** The existing composite primary key `(user_id, lesson_id)` is already highly optimized for checking if a specific user has completed a specific lesson. When querying for all completed lessons for a user within a course, the join with `lessons` table (which is indexed on `course_id`) will be efficient.

### Going further: Handling lesson deletion

Handling lesson deletion requires a robust mechanism to propagate this change to the cache and ensure consistency.

1.  **Database Change Data Capture (CDC):**
    The `CourseProgressUpdater` service, which already consumes CDC events, needs to be configured to also monitor `DELETE` operations on the `lessons` table. When a lesson is deleted, a CDC event for this deletion will be emitted.

2.  **`CourseProgressUpdater` Logic:**
    Upon receiving a `DELETE` event for a `lesson_id` from the `lessons` table, the `CourseProgressUpdater` needs to:
    *   **Identify affected courses:** The event will contain the `course_id` of the deleted lesson.
    *   **Invalidate/Update Cache:** For every user who has progress recorded for that `course_id` in Redis, the updater needs to remove the `lesson_id` field from their `user_progress:{user_id}:{course_id}` hash.
        *   **Challenge:** The `CourseProgressUpdater` doesn't know *all* `user_id`s who have progress for a given `course_id`.
        *   **Solution 1 (Targeted Invalidation):** If the platform has a `user_courses` table (or similar) mapping users to enrolled courses, the updater could query this table (or a read replica of it) to get all `user_id`s for the affected `course_id`. Then, for each `user_id`, it would execute a `HDEL user_progress:{user_id}:{course_id} {deleted_lesson_id}` command in Redis. This is precise but could generate many Redis commands for popular courses.
        *   **Solution 2 (Course-level Invalidation):** A simpler approach, especially if the number of lessons per course is small (10-50), is to invalidate the *entire course progress cache entry* for all affected users. This means deleting `user_progress:{user_id}:{course_id}` for all users enrolled in that course. The next time a user requests progress for that course, it will be a cache miss, triggering a full re-computation from the read replica, which will correctly reflect the deleted lesson. This is easier to implement but might cause a temporary spike in read replica load for affected courses.
        *   **Solution 3 (Rebuild on demand):** Instead of proactive invalidation, the `CourseProgressUpdater` could simply update a `course_version` or `lessons_hash` field in a separate Redis key for the course. The `CourseProgressService` would then compare this version with a version stored in the user's progress hash. If they differ, it means the course structure changed, and the user's progress cache entry is stale and should be recomputed. This avoids iterating through all users but adds complexity to the read path.

    Given the "few seconds" freshness requirement and the relatively small number of lessons per course, **Solution 2 (Course-level Invalidation)** is a pragmatic choice. The `CourseProgressUpdater` would:
    1.  Receive `DELETE` event for `lesson_id` from `course_id`.
    2.  Query `user_courses` table (or similar) on a read replica to get all `user_id`s enrolled in `course_id`.
    3.  For each `user_id`, send a `DEL user_progress:{user_id}:{course_id}` command to Redis.

3.  **Read Replica Consistency:**
    The read replica will eventually reflect the deleted lesson due to asynchronous replication. When a cache miss occurs after invalidation, the `CourseProgressService` will query the read replica, which will no longer return the deleted lesson, thus ensuring accuracy.

**Trade-offs:**
*   **Temporary Cache Misses:** For a short period after a lesson deletion, users requesting progress for the affected course will experience a cache miss and hit the read replica. This might slightly increase latency for those specific requests until the cache is repopulated.
*   **Increased Redis/DB Load during Deletion:** If a very popular course has a lesson deleted, invalidating all user caches (Solution 2) could lead to a burst of `DEL` commands to Redis and subsequent read replica queries. However, lesson deletions are typically infrequent compared to lesson completions, so this burst should be manageable.
*   **Complexity:** Solution 1 (targeted `HDEL`) is more complex to implement correctly, especially if the `user_courses` mapping is not readily available or if the number of users is extremely high. Solution 2 is simpler but less granular.

By leveraging CDC and a targeted (or course-level) cache invalidation strategy, the system can accurately reflect lesson deletions without recomputing everything for everyone, while maintaining the desired latency targets.
