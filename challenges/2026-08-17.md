## Scenario

Your company operates a fast-growing SaaS platform that provides analytical dashboards for financial data. A core feature allows users to filter and view historical stock prices for specific symbols within a date range. The `stock_prices` table stores daily closing prices for millions of stocks, with columns like `symbol` (e.g., 'AAPL', 'GOOG'), `price_date` (DATE), and `closing_price` (DECIMAL).

The table has grown significantly and now contains over **100 million rows**, with data going back 20 years for tens of thousands of unique symbols. Users frequently query for a single symbol over a range of a few days to several months, or sometimes a full year.

The current query to fetch prices for a given symbol and date range looks like this:

```sql
SELECT price_date, closing_price
FROM stock_prices
WHERE symbol = 'MSFT' AND price_date BETWEEN '2023-01-01' AND '2023-03-31'
ORDER BY price_date;
```

This query, which used to be instantaneous, now often takes **500ms to 2 seconds** to complete, especially for longer date ranges or during peak usage times. This latency is impacting user experience, leading to dashboard loading delays and frustration. Your service level objective (SLO) for this API endpoint is **99th percentile response time below 200ms**.

You suspect a bottleneck in the database due to the table's size and the nature of the queries.

## Requirements

Your task is to identify and resolve the performance bottleneck for the described query patterns. You need to ensure that typical queries (single symbol, date range up to one year) consistently meet the 200ms latency target. Consider the implications of concurrent queries, as many users might be querying different symbols simultaneously. The solution must scale with continued data growth for at least the next year.

You are free to make schema modifications, add indexes, or suggest configuration changes to PostgreSQL.

## Deliverables

1.  A SQL statement (or set of statements) that modifies the database schema to address the performance issue.
2.  An explanation of why your chosen solution improves performance for the described query patterns.
3.  An explanation of any potential downsides or trade-offs introduced by your solution (e.g., write performance, disk space, maintenance).

## Worked answer

### 1. Schema Modifications

The primary issue is the lack of an efficient index to support the `WHERE` clause conditions (`symbol = 'MSFT' AND price_date BETWEEN '2023-01-01' AND '2023-03-31'`) and the `ORDER BY price_date`. A composite B-tree index on `(symbol, price_date)` is ideal for this access pattern.

```sql
CREATE INDEX idx_stock_prices_symbol_price_date
ON stock_prices (symbol, price_date);
```

### 2. Explanation of Performance Improvement

The `CREATE INDEX` statement creates a B-tree index on the `stock_prices` table, covering both the `symbol` and `price_date` columns. Here's why this significantly improves performance:

1.  **Efficient Filtering (`WHERE` clause):**
    *   The `symbol` column is the *leading column* in the index. This allows PostgreSQL to quickly locate all entries for a specific `symbol` (e.g., 'MSFT') using an index scan.
    *   Once the `symbol` is matched, the index is already sorted by `price_date` *within* that symbol. This means that filtering by `price_date BETWEEN '...' AND '...'` can be performed very efficiently by scanning a contiguous block of entries in the index.
    *   Without this index, PostgreSQL would likely perform a full table scan or an index scan on `price_date` (if such an index existed), which would then require filtering out rows for the incorrect `symbol`, leading to many unnecessary disk I/Os.

2.  **Efficient Ordering (`ORDER BY` clause):**
    *   Because the index is ordered by `symbol` and then by `price_date`, the data retrieved for a specific `symbol` within a date range is *already in the desired order*.
    *   This eliminates the need for PostgreSQL to perform an explicit sort operation in memory or on disk, which can be very expensive for large result sets. This is known as an "index-only scan" or "ordered index scan" depending on whether all required columns are in the index.

3.  **Reduced I/O and CPU:**
    *   The index allows PostgreSQL to quickly narrow down the search space to a small subset of the 100 million rows. Instead of reading potentially millions of rows from the main table, it only reads the relevant index entries and then performs "bookmark lookups" (heap fetches) to retrieve `closing_price` from the main table for only the matching rows.
    *   In some cases, if `closing_price` were also included in the index (e.g., using `INCLUDE (closing_price)` in PostgreSQL 11+), it could even perform an "index-only scan," avoiding heap fetches entirely. However, for this specific query, the current index is sufficient because `closing_price` is not part of the `WHERE` or `ORDER BY` clauses.

This composite index directly supports the query's selectivity and ordering requirements, transforming a potentially expensive sequential scan or partial index scan into a highly optimized index scan.

### 3. Potential Downsides or Trade-offs

1.  **Write Performance Overhead:**
    *   Every `INSERT`, `UPDATE` (on `symbol` or `price_date`), or `DELETE` operation on the `stock_prices` table will now require an update to the `idx_stock_prices_symbol_price_date` index in addition to the main table. This adds overhead to write operations, increasing their latency and CPU usage. For a high-volume write system, this could be a concern, but for a financial data platform where historical data is typically appended or rarely updated, this is usually an acceptable trade-off.

2.  **Disk Space Usage:**
    *   Indexes consume disk space. A B-tree index on two columns with 100 million rows will be significant. Each index entry will store the `symbol`, `price_date`, and a pointer to the corresponding row in the main table (the `ctid`). While much smaller than the main table, it will still be in the order of several gigabytes. This needs to be factored into storage planning and backup strategies.

3.  **Maintenance Overhead:**
    *   Indexes can become fragmented over time due to `UPDATE` and `DELETE` operations, which can slightly degrade their performance. While PostgreSQL's MVCC (Multi-Version Concurrency Control) handles this reasonably well, periodic `VACUUM` and `ANALYZE` operations are necessary to keep the table and indexes optimized and statistics up-to-date for the query planner. Reindexing might occasionally be considered for severely fragmented indexes, though less common with modern PostgreSQL.

4.  **Increased Backup/Restore Times:**
    *   Larger databases (due to indexes) take longer to back up and restore.

5.  **Not Optimal for All Query Patterns:**
    *   This index is highly optimized for queries that filter by `symbol` *first*, then `price_date`. It would not be efficient for queries that only filter by `price_date` (e.g., `WHERE price_date = '2023-01-01'`) or only by `symbol` (though it would still be used for `symbol` only). It would also not be efficient for queries that filter by `price_date` *first* and then `symbol` (e.g., `WHERE price_date = '...' AND symbol = '...'`). However, given the stated query pattern, this is the correct choice.

### Going Further

If users frequently queried for *multiple* symbols at once (e.g., `WHERE symbol IN ('MSFT', 'GOOG', 'AAPL')`) for the same date range, the current `idx_stock_prices_symbol_price_date` index would still be highly beneficial.

**How the current solution behaves:**

The existing `idx_stock_prices_symbol_price_date` index would be used effectively. PostgreSQL would perform an index scan for each symbol in the `IN` list. For example, it would:

1.  Find 'MSFT' in the index, scan its date range, and retrieve results.
2.  Find 'GOOG' in the index, scan its date range, and retrieve results.
3.  Find 'AAPL' in the index, scan its date range, and retrieve results.

The results from these separate index scans would then be combined. This is generally very efficient because each individual lookup and range scan within the index is fast. The `ORDER BY price_date` would still be efficient *within each symbol's result set*. If the overall query requires results ordered by `price_date` across *all* symbols combined, PostgreSQL might need to perform a final merge sort on the combined results, but this would still be faster than a full table scan.

**Further optimizations for `WHERE symbol IN (...)`:**

1.  **Index-Only Scan with `INCLUDE`:**
    If the `closing_price` column is frequently retrieved and the query pattern is `SELECT price_date, closing_price FROM ...`, we could enhance the existing index to be an index-only scan candidate:

    ```sql
    CREATE INDEX idx_stock_prices_symbol_price_date_incl_price
    ON stock_prices (symbol, price_date) INCLUDE (closing_price);
    ```
    This would allow PostgreSQL to retrieve `price_date` and `closing_price` directly from the index without needing to access the main table (heap fetches). This can significantly reduce I/O, especially if the `closing_price` column is small and fits well within the index pages. This is particularly beneficial for `IN` queries as it reduces heap fetches for multiple symbol ranges.

2.  **Partitioning (Advanced):**
    For extremely large tables (hundreds of millions to billions of rows) and very high concurrency, partitioning the `stock_prices` table could be considered.
    *   **By `symbol`:** If symbols are relatively static and queries predominantly involve a single symbol or a small set of symbols, partitioning by `symbol` (e.g., using hash partitioning or range partitioning for symbol groups) could isolate data for different symbols into separate physical tables. This can improve cache locality and reduce contention. However, managing tens of thousands of partitions could be complex.
    *   **By `price_date`:** Partitioning by `price_date` (e.g., monthly or yearly partitions) could be beneficial for queries that span very large date ranges or for data retention policies (e.g., dropping old partitions). However, for queries filtering by `symbol` *and* `price_date`, the `symbol` index would still be crucial within each partition.

    For the described `IN` query pattern, partitioning by `symbol` might offer some benefits by localizing data for each symbol, but the primary benefit still comes from the `(symbol, price_date)` index. Partitioning adds significant operational complexity and should only be considered if the single index solution proves insufficient at even larger scales or for specific maintenance requirements.

    Given the current scale and query patterns, the `(symbol, price_date)` index (possibly with `INCLUDE (closing_price)`) is the most straightforward and effective solution, even for `IN` queries. Partitioning would be an optimization to consider at a much larger scale or with different operational requirements.
