## Scenario

Your company operates a public API built with Node.js and Express. This API serves a `/webhook` endpoint that receives real-time event notifications from a critical third-party service. These webhooks inform your system about significant updates (e.g., payment confirmations, user subscription changes, document processing completion). The third-party service guarantees at-least-once delivery, meaning you might receive duplicate webhook events. Additionally, while the service aims for low latency, there's no guarantee on the order of delivery for related events.

A recent incident revealed that processing duplicate webhooks led to incorrect state updates in your PostgreSQL database (e.g., double-charging a user, marking a document as complete twice). Furthermore, some critical webhook handlers are long-running (up to several seconds), and directly processing them synchronously within the Express route has started causing timeouts for the third-party service and degrading overall API responsiveness under moderate load.

You need to refactor the webhook processing to ensure idempotency and handle the long-running tasks asynchronously, without losing events or introducing new failure modes. The system currently handles around 500 webhooks per second during peak times, with spikes up to 1500/second.

## Requirements

1.  **Idempotency:** Ensure that processing a webhook event multiple times has the same effect as processing it once.
2.  **Asynchronous Processing:** Decouple the webhook reception from its actual processing to prevent API timeouts and maintain responsiveness.
3.  **Reliability:** Webhook events must not be lost, even if your application crashes or restarts.
4.  **Order (Best Effort):** While not strictly guaranteed by the third-party, within your system, related events for the same entity (e.g., `user_id`) should ideally be processed in the order they were received, if possible, to simplify state management.

## Deliverables

3.  A description of how idempotency is achieved for webhook processing.
4.  A brief explanation of how event ordering for a single entity is managed or prioritized.
