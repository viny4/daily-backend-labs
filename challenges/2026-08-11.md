## Scenario

Your company operates a public API built with Node.js and Express. This API serves a `/webhook` endpoint that receives real-time event notifications from a critical third-party service. These webhooks inform your system about significant updates (e.g., payment confirmations, user subscription changes, document processing completion). The third-party service guarantees at-least-once delivery, meaning you might receive duplicate webhook events. Additionally, while the service aims for low latency, there's no guarantee on the order of delivery for related events.

A recent incident revealed that processing duplicate webhooks led to incorrect state updates in your PostgreSQL database (e.g., double-charging a user, marking a document as complete twice). Furthermore, some critical webhook handlers are long-running (up to several seconds), and directly processing them synchronously within the Express route has started causing timeouts for the third-party service and degrading overall API responsiveness under moderate load.

You need to refactor the webhook processing to ensure idempotency and handle the long-running tasks asynchronously, without losing events or introducing new failure modes. The system currently handles around 500 webhooks per second during peak times, with spikes up to 1500/second.

4.  **Order (Best Effort):** While not strictly guaranteed by the third-party, within your system, related events for the same entity (e.g., `user_id`) should ideally be processed in the order they were received, if possible, to simplify state management.

## Worked answer

### High-level Design Document

To address the challenges of idempotency, asynchronous processing, reliability, and best-effort ordering, we will introduce a message queue system and a dedicated worker service.

**Current Architecture (Simplified):**

```
Third-Party Service -> Express API (/webhook) -> Direct Database Update / Long-running Logic
```

**Proposed Architecture:**

```
Third-Party Service -> Express API (/webhook)
    -> Message Queue (e.g., AWS SQS, RabbitMQ, Kafka)
        -> Worker Service (consumes messages, processes webhooks)
            -> PostgreSQL Database (updates state)
```

**Components:**

1.  **Express API (`/webhook` endpoint):**
    *   Receives webhook events from the third-party service.
    *   Performs minimal validation (e.g., signature verification, basic schema check).
    *   Generates a unique `idempotency_key` if not provided by the third-party or if a custom one is needed.
    *   Publishes the raw webhook payload, along with metadata (e.g., `idempotency_key`, `received_at`, `entity_id` for ordering), to a message queue.
    *   Responds quickly (e.g., 200 OK) to the third-party service.

2.  **Message Queue:**
    *   Acts as a buffer between the API and the worker service.
    *   Ensures reliability: messages are persisted until successfully processed and acknowledged.
    *   Decouples producers (API) from consumers (workers).
    *   Allows for scaling the API and workers independently.
    *   Supports features like dead-letter queues (DLQs) for failed messages.
    *   We will use a queue that supports message groups/ordering keys (e.g., AWS SQS FIFO, Kafka topics with partition keys) to facilitate best-effort ordering for related events.

3.  **Worker Service:**
    *   A separate Node.js application responsible for consuming messages from the queue.
    *   Each worker instance processes messages independently.
    *   Implements the core business logic for each webhook type.
    *   Crucially, it handles idempotency checks before processing and updates the database.
    *   Acknowledges messages only after successful processing and database commit.
    *   Includes robust error handling and retry mechanisms.

4.  **PostgreSQL Database:**
    *   Stores application state.
    *   Will include a new table (`processed_webhooks`) to track processed events for idempotency.
    *   Transactions will be used to ensure atomicity of state updates and idempotency record creation.

**Data Flow:**

1.  Third-party sends webhook to `POST /webhook`.
2.  Express API receives, validates, extracts `entity_id` and `idempotency_key`, and publishes to message queue. Responds 200 OK.
3.  Worker service polls/subscribes to message queue.
4.  Worker receives a message.
5.  Worker checks `processed_webhooks` table using `idempotency_key`.
6.  If already processed, worker acknowledges message and exits.
7.  If not processed, worker starts a database transaction:
    *   Inserts `idempotency_key` into `processed_webhooks` table.
    *   Executes business logic (e.g., update user balance, change subscription status).
    *   Commits transaction.
8.  Worker acknowledges message in the queue.
9.  If any step in 7 fails, the transaction is rolled back, and the message is not acknowledged (or explicitly NACKed), making it visible again for retry (potentially after a delay or to a DLQ).

export const handleWebhook = async (req: Request, res: Response): Promise<void> => {
  // 1. Signature Verification (CRITICAL for security)
  if (!verifyWebhookSignature(req)) {
    console.warn('Webhook signature verification failed.');
    res.status(403).send('Forbidden: Invalid signature');
    return;
  }

  const eventPayload: WebhookEventPayload = req.body;

  // Basic validation of the payload structure
  if (!eventPayload || !eventPayload.id || !eventPayload.type || !eventPayload.data) {
    console.error('Invalid webhook payload received:', eventPayload);
    res.status(400).send('Bad Request: Missing required fields');
    return;

  // The third-party service might provide an idempotency key (e.g., Stripe's `id` field)
  // If not, we generate one based on a combination of event ID and type.
  const idempotencyKey = req.headers['x-idempotency-key'] as string ||
                         `${eventPayload.id}-${eventPayload.type}`;

  // 3. Determine Entity ID for Ordering
  // This is crucial for best-effort ordering. It should be an ID that groups related events.
  // Example: 'user_id' for user-related events, 'payment_id' for payment events.
  // This logic will be specific to your webhook types.
  let entityId: string;
  if (eventPayload.type.startsWith('user.')) {
    entityId = eventPayload.data.user_id;
  } else if (eventPayload.type.startsWith('payment.')) {
    entityId = eventPayload.data.payment_id;
  } else if (eventPayload.type.startsWith('document.')) {
    entityId = eventPayload.data.document_id;
  } else {
    // Fallback: use the event ID itself or a generic key if no specific entity can be identified
    entityId = eventPayload.id;
  }

  if (!entityId) {
    console.warn(`Could not determine entityId for webhook type ${eventPayload.type}. Using event ID as fallback.`);
    entityId = eventPayload.id;
  }

  const webhookMessage: WebhookMessage = {
    idempotencyKey,
    entityId,
    receivedAt: new Date().toISOString(),
    payload: eventPayload,
  };

  try {
    // 4. Publish to Message Queue
    const params = {
      QueueUrl: config.sqs.webhookQueueUrl,
      MessageBody: JSON.stringify(webhookMessage),
      MessageDeduplicationId: idempotencyKey, // Required for SQS FIFO queues
      MessageGroupId: entityId, // Required for SQS FIFO queues to ensure ordering per group

    res.status(500).send('Internal Server Error: Failed to queue webhook.');

**Explanation:**

*   **Signature Verification:** This is the first and most critical step for security. It ensures the webhook truly came from the trusted third-party service. The `bodyParser.json` configuration to store `req.rawBody` is essential because signature verification often requires the exact raw payload bytes.
*   **Idempotency Key:** We prioritize a key provided by the third-party (`X-Idempotency-Key` header) or construct one from `eventPayload.id` and `eventPayload.type`. This key will be used by the worker to check if the event has been processed before.
*   **Entity ID:** This field (`MessageGroupId` for SQS FIFO) is vital for best-effort ordering. By grouping messages for the same `user_id` or `payment_id`, SQS ensures that messages within that group are delivered to consumers in the order they were sent.
*   **Message Queue Publishing:** The `SendMessageCommand` sends the `WebhookMessage` to SQS.
    *   `MessageBody`: The full `WebhookMessage` is stringified.
    *   `MessageDeduplicationId`: This is the `idempotencyKey`. SQS FIFO queues use this to prevent duplicate messages from being delivered to the queue within a 5-minute deduplication interval. This is an *additional* layer of idempotency provided by SQS, complementing our application-level idempotency.
    *   `MessageGroupId`: This is the `entityId`. SQS FIFO queues guarantee that messages with the same `MessageGroupId` are processed in order.
*   **Fast Response:** The API responds with `202 Accepted` immediately after successfully publishing to the queue. This prevents timeouts for the third-party service and keeps the API responsive.
*   **Reliability:** If publishing to SQS fails, the API returns a `500` error. This signals to the third-party service that they should retry sending the webhook, preventing event loss. SQS itself guarantees message durability until acknowledged by a consumer.

### Description of How Idempotency is Achieved

Idempotency is achieved through a combination of a unique key and a persistent record of processed events, enforced by database transactions.

1.  **Idempotency Key Generation/Extraction:**
    *   Upon receiving a webhook, the Express API extracts or generates a unique `idempotencyKey`. This key should uniquely identify a specific *instance* of a webhook event.
        *   **Best Case:** The third-party service provides a stable, unique ID for each event (e.g., `event.id` from Stripe, `X-Request-ID` header). This is the preferred source.
        *   **Fallback:** If no such ID is provided, we construct one using a combination of fields that are guaranteed to be unique for a given event (e.g., `event.id` + `event.type`).
    *   This `idempotencyKey` is then included in the message sent to the queue.

2.  **`processed_webhooks` Database Table:**
    *   A dedicated table in PostgreSQL will store the `idempotencyKey` of every webhook that has been successfully processed.

    ```sql
    CREATE TABLE processed_webhooks (
        idempotency_key VARCHAR(255) PRIMARY KEY,
        event_type VARCHAR(100) NOT NULL,
        entity_id VARCHAR(255) NOT NULL,
        received_at TIMESTAMP WITH TIME ZONE NOT NULL,
        processed_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
    );
    -- Add an index on entity_id if you frequently query processed webhooks by entity
    CREATE INDEX idx_processed_webhooks_entity_id ON processed_webhooks (entity_id);
    ```

3.  **Atomic Check-and-Process in Worker:**
    *   When a worker service consumes a message from the queue, it performs the following steps within a single database transaction:
        1.  **Check:** It attempts to insert the `idempotencyKey` into the `processed_webhooks` table.
        2.  **Conditional Processing:**
            *   If the `INSERT` succeeds (meaning the `idempotency_key` was not already present due to the `PRIMARY KEY` constraint), the worker proceeds to execute the core business logic (e.g., update user balance, change subscription status).
            *   If the `INSERT` fails due to a `PRIMARY KEY` violation, it means this `idempotencyKey` has already been processed. The worker immediately rolls back the transaction (if any other operations were attempted) and considers the message processed (without executing business logic).
        3.  **Commit/Rollback:** If the business logic completes successfully, the entire transaction (including the `processed_webhooks` insert and any state updates) is committed. If any part of the business logic fails, the transaction is rolled back, ensuring no partial updates and that the `idempotencyKey` is not recorded as processed.

**Example Worker Logic (Conceptual):**

```typescript
// src/worker/webhookProcessor.ts
import { Pool } from 'pg';
import { WebhookMessage } from '../types/webhook';
import { config } from '../config';

const pgPool = new Pool(config.database);

export async function processWebhook(message: WebhookMessage): Promise<void> {
  const client = await pgPool.connect();
  try {
    await client.query('BEGIN');

    // 1. Idempotency Check & Record
    const insertResult = await client.query(
      `INSERT INTO processed_webhooks (idempotency_key, event_type, entity_id, received_at)
       VALUES ($1, $2, $3, $4)
       ON CONFLICT (idempotency_key) DO NOTHING
       RETURNING idempotency_key;`, // RETURNING clause helps determine if insert happened
      [message.idempotencyKey, message.payload.type, message.entityId, message.receivedAt]
    );

    if (insertResult.rowCount === 0) {
      // Idempotency key already exists, this event has been processed.
      console.log(`Webhook with key ${message.idempotencyKey} already processed. Skipping.`);
      await client.query('COMMIT'); // Commit the "do nothing" if using ON CONFLICT DO NOTHING
      return;
    }

    // 2. Execute Business Logic (only if not already processed)
    console.log(`Processing webhook ${message.idempotencyKey} of type ${message.payload.type}`);
    switch (message.payload.type) {
      case 'payment.succeeded':
        await handlePaymentSucceeded(client, message.payload.data);
        break;
      case 'user.updated':
        await handleUserUpdated(client, message.payload.data);
        break;
      // ... other webhook types
      default:
        console.warn(`Unhandled webhook type: ${message.payload.type}`);
        break;
    }

    await client.query('COMMIT');
    console.log(`Successfully processed webhook ${message.idempotencyKey}`);

  } catch (error) {
    await client.query('ROLLBACK');
    console.error(`Failed to process webhook ${message.idempotencyKey}:`, error);
    throw error; // Re-throw to signal message queue to retry
  } finally {
    client.release();
  }
}

// Example handler functions
async function handlePaymentSucceeded(client: any, data: any): Promise<void> {
  const { payment_id, user_id, amount, currency } = data;
  // Update user balance, record payment, etc.
  await client.query(
    `UPDATE users SET balance = balance + $1 WHERE id = $2;`,
    [amount, user_id]
  );
  await client.query(
    `INSERT INTO payments (id, user_id, amount, currency, status) VALUES ($1, $2, $3, $4, 'completed');`,
    [payment_id, user_id, amount, currency]
  );
  console.log(`Payment ${payment_id} for user ${user_id} of ${amount} ${currency} processed.`);
}

async function handleUserUpdated(client: any, data: any): Promise<void> {
  const { user_id, email, name } = data;
  await client.query(
    `UPDATE users SET email = $1, name = $2 WHERE id = $3;`,
    [email, name, user_id]
  );
  console.log(`User ${user_id} updated.`);
}
```

*   **Database Load:** The `processed_webhooks` table will grow indefinitely. Regular archiving or purging of old records (e.g., older than 90 days) will be necessary. Each webhook processing involves at least one `INSERT` (or `INSERT ... ON CONFLICT`) and potentially other updates, increasing database write load.
*   **Latency:** While the API responds quickly, the actual processing latency is shifted to the worker. The end-to-end latency from third-party sending to your system reflecting the change will be higher than synchronous processing, but this is an acceptable trade-off for reliability and API responsiveness.
*   **Complexity:** Introduces a new component (worker service) and a message queue, increasing operational complexity.

### Brief Explanation of How Event Ordering for a Single Entity is Managed or Prioritized

Event ordering for a single entity (e.g., all events related to `user_id=123`) is managed using the **Message Grouping** feature of the message queue.

1.  **`entityId` Extraction:** In the Express API, when a webhook is received, we extract a stable `entityId` from the webhook payload. This `entityId` should represent the primary entity that the webhook event pertains to (e.g., `user_id`, `payment_id`, `document_id`).
2.  **Message Group ID:** When publishing the webhook message to the queue (e.g., AWS SQS FIFO), this `entityId` is used as the `MessageGroupId`.
3.  **Queue Guarantee:** Message queues like AWS SQS FIFO guarantee that:
    *   Messages with the same `MessageGroupId` are delivered to consumers in the exact order they were sent.
    *   Only one message from a specific `MessageGroupId` is in flight (being processed by a consumer) at any given time. This prevents out-of-order processing for a single entity.
4.  **Worker Processing:** The worker service consumes messages. Because of the queue's guarantee, if a worker receives `user.updated` for `user_id=123` followed by `user.deleted` for `user_id=123`, it is guaranteed to process the `user.updated` event first.

This approach provides **best-effort ordering** because:

*   It only guarantees order *within* a specific `entityId` group. Events for different entities (`user_id=123` vs `user_id=456`) can be processed concurrently and out of order relative to each other.
*   It relies on the third-party service sending related events in a logical sequence *to our API*. If the third-party sends `user.deleted` before `user.updated` for the same user, our system will still process them in the order *received*, which might not be the desired logical order. However, the problem statement implies the third-party doesn't guarantee global order, so this is the best we can do without more complex mechanisms.

This mechanism is highly scalable because different `MessageGroupId`s can be processed in parallel by different worker instances, maximizing throughput while maintaining crucial per-entity ordering.

### Going Further

#### Scenario for Strict, Global Ordering

A scenario where strict, global ordering of all webhook events might be necessary is a **financial ledger system** or a **blockchain-like transaction processing system**.

Imagine a system where every webhook represents a financial transaction (e.g., deposit, withdrawal, transfer) and the *absolute order* of *all* transactions, regardless of the user or account involved, is critical for maintaining a consistent, auditable global state. For example, if a system needs to calculate a global "net asset value" across all accounts at any given point, or if the outcome of one transaction (e.g., a system-wide fee calculation) depends on the exact state after *all* preceding transactions, then global ordering is paramount.

In such a system, processing a `user_A_deposit` event after a `user_B_withdrawal` event, when the `user_B_withdrawal` logically occurred first but was delayed in delivery, could lead to an incorrect global state, potentially causing discrepancies in audits or even legal issues. The "best-effort" per-entity ordering would be insufficient because the inter-entity order matters.

#### Why Current Solution is Insufficient

Our current asynchronous, best-effort ordering solution would be insufficient because:

1.  **Parallel Processing of Different Entities:** Our solution processes messages for different `entityId`s (e.g., `user_id=123` and `user_id=456`) in parallel. There is no guarantee about the relative order of processing between these distinct groups. A `payment.succeeded` for `user_A` might be processed before a `user.created` for `user_B`, even if `user.created` was received earlier by the API.
2.  **Queue Partitioning:** Even with a single SQS FIFO queue, the `MessageGroupId` mechanism effectively partitions the queue logically. While SQS ensures order within a group, it doesn't enforce global order across groups. Multiple worker instances can consume from different `MessageGroupId`s concurrently.
3.  **No Global Clock/Sequence:** The system lacks a single, globally incrementing sequence number or clock that dictates the processing order for *all* events.

#### Changes Required for Strict Global Ordering

Achieving strict global ordering would require significant architectural changes and would fundamentally alter the system's scalability and performance characteristics:

1.  **Single Global Sequence/Ordering Mechanism:**
    *   **Kafka with a Single Partition:** Instead of SQS FIFO with `MessageGroupId`s, we would use Apache Kafka with a *single partition* for all webhook events. Kafka guarantees strict ordering within a partition. All events would be written to this single partition.
    *   **Global Sequence Number:** Alternatively, if using a different queue, each message would need to be assigned a globally unique, monotonically increasing sequence number *at the point of ingestion* (e.g., by the Express API). This sequence number would then dictate the processing order.

2.  **Single-Threaded/Single-Process Consumer:**
    *   To guarantee strict global order, there can only be **one active consumer process/thread** at any given time responsible for processing *all* webhook events. This consumer would read messages from the single Kafka partition (or order by the global sequence number) and process them one by one.
    *   This implies a "leader-follower" or "active-passive" setup for the worker service, where only the leader processes messages, and followers are on standby.

3.  **Centralized State Management:** All state updates would need to be coordinated through this single consumer, potentially leading to bottlenecks if the database cannot keep up with the serial writes.

**Revised Architecture for Strict Global Ordering:**

```
Third-Party Service -> Express API (/webhook)
    -> Kafka Topic (SINGLE PARTITION)
        -> Single Worker Leader (consumes from single partition, processes serially)
            -> PostgreSQL Database (updates state)
        -> Worker Followers (standby, for failover)
```

**Deliverables for Strict Global Ordering:**

*   **Express API:**
    *   Publishes all webhook events to a single Kafka topic with a single partition.
    *   No `MessageGroupId` or `MessageDeduplicationId` needed for ordering (Kafka handles this within the partition).
    *   May still generate an `idempotencyKey` for application-level idempotency, but Kafka's "exactly-once" semantics (producer-side) can also help.
*   **Kafka:**
    *   A single topic configured with only one partition. This is the bottleneck for write throughput.
*   **Worker Service:**
    *   A consumer group for the Kafka topic. Crucially, only one consumer instance in this group can be active for the single partition at any time.
    *   The worker processes messages strictly in the order they appear in the Kafka partition.
    *   Idempotency logic remains similar, but the primary ordering guarantee comes from Kafka.

#### Trade-offs Introduced by Strict Global Ordering

1.  **Massive Performance Bottleneck:** This is the most significant trade-off.
    *   **Ingestion:** All webhook events must be written to a single Kafka partition. While Kafka is highly performant, a single partition has a finite throughput limit. At 1500 webhooks/second, this might be manageable, but at 10x scale (15,000/sec), it would likely become a bottleneck.
    *   **Processing:** Only one worker can process events at a time. If a single webhook handler takes 1 second, the system can only process 1 event per second, regardless of how many workers are available. This would drastically reduce throughput and lead to massive backlogs in the queue under peak load. The current scenario's long-running tasks (several seconds) would make this approach completely unfeasible.
2.  **Reduced Scalability:** The system becomes inherently unscalable horizontally for processing. You cannot add more workers to increase throughput. Scaling is limited to vertical scaling (more powerful single worker instance), which has diminishing returns.
3.  **Increased Latency:** End-to-end latency would dramatically increase, as every event must wait for all preceding events to be fully processed, even if they are unrelated to the current event.
4.  **Higher Complexity for High Availability:** Ensuring high availability for the single worker leader becomes critical. Failover mechanisms (e.g., Kubernetes leader election, Zookeeper-based coordination) are needed to ensure that if the leader fails, a follower can quickly take over without disrupting the strict order or losing state. This adds significant operational complexity.
5.  **Resource Inefficiency:** Standby workers consume resources without actively processing, leading to lower resource utilization.

In summary, while strict global ordering provides strong consistency guarantees, it comes at a severe cost to performance, scalability, and operational complexity, making it suitable only for very specific, highly sensitive use cases where these trade-offs are acceptable and the processing throughput requirements are low. For the given scenario of 500-1500 webhooks/second with long-running tasks, strict global ordering would be a catastrophic choice.
