## Scenario

Your team maintains a critical backend service that handles user profile management for a popular online learning platform. A core feature of this service is allowing users to upload a profile picture. These images are stored in an S3 bucket.

Currently, when a user uploads a new profile picture, your Django/Node backend processes the raw image, resizes it to several different standard dimensions (e.g., thumbnail, medium, large), and then uploads all these versions to S3. This synchronous processing on the main application server is starting to become a bottleneck. During peak upload times, the API latency for profile picture uploads spikes significantly, leading to a poor user experience and occasional timeouts. The image processing itself is CPU-intensive, blocking the main event loop in Node.js or tying up Django worker processes.

You need to offload this image processing to improve the responsiveness and scalability of the profile picture upload API. The target latency for the initial upload response should be under 500ms, regardless of the image size. The image processing itself can take longer, but the user should get an immediate confirmation that their upload was received.

## Requirements

The current setup processes images synchronously, causing high latency and resource contention on the application servers. You need to redesign the image processing workflow to be asynchronous, ensuring the primary API endpoint remains fast and responsive. The new system must handle varying image sizes (up to 20MB per image) and maintain high availability. You should leverage AWS services to achieve this.

## Worked answer

### 1. Revised Architecture Description

The core idea is to offload the CPU-intensive image resizing from the main application servers to a dedicated, asynchronous processing pipeline. This pipeline will be triggered by new image uploads and will handle the resizing and re-uploading of derived images. The main application will only be responsible for receiving the initial upload and coordinating the asynchronous process.

Here's a high-level overview of the revised architecture:

```mermaid
graph TD
    A[User] --> B(Web Browser/Mobile App)
    B --> C(Load Balancer)
    C --> D[Django/Node Backend Service]
    D -- 1. Generate S3 Presigned URL --> B
    B -- 2. Upload Raw Image Directly --> E[S3 Bucket: `profile-pictures-raw`]
    E -- 3. S3 ObjectCreated Event --> F[SQS Queue: `image-processing-queue`]
    F -- 4. Trigger Lambda Function --> G[Lambda Function: `image-resizer`]
    G -- 5. Download Raw Image --> E
    G -- 6. Process Image (Resize) --> G
    G -- 7. Upload Processed Images --> H[S3 Bucket: `profile-pictures-processed`]
    G -- 8. Update User Profile DB --> I[Database (e.g., RDS PostgreSQL)]
    I -- 9. Notify Backend (Optional) --> D
    D -- 10. Serve Processed Images --> B
```

**Explanation:**

1.  **Direct Upload to S3 via Presigned URL:** Instead of the backend receiving the raw image, it will generate a presigned URL for the client (web browser/mobile app). This URL grants temporary, direct upload access to a specific S3 bucket (`profile-pictures-raw`). The client then uploads the image directly to S3, bypassing the backend service entirely for the large file transfer. This significantly reduces the load and latency on the backend.
2.  **Event-Driven Processing:** S3 is configured to emit an `ObjectCreated` event whenever a new image is uploaded to `profile-pictures-raw`. This event is sent to an SQS queue.
3.  **Asynchronous Processing with Lambda:** An AWS Lambda function (`image-resizer`) is triggered by messages in the SQS queue. This function downloads the newly uploaded raw image from S3, performs the resizing operations (thumbnail, medium, large), and uploads the processed versions to a separate S3 bucket (`profile-pictures-processed`).
4.  **Database Update:** After successful processing, the Lambda function updates the user's profile record in the database with the URLs of the new processed images.
5.  **Backend Confirmation:** The backend service can either poll the database for updates or receive a notification (e.g., via another SQS message or API call from Lambda) to confirm the processing is complete. For the user, the initial upload confirmation is immediate.

### 2. Specific AWS Services Involved and Their Roles

*   **Amazon S3 (Simple Storage Service):**
    *   `profile-pictures-raw` bucket: Stores the original, raw images uploaded by users. It's configured to emit events on new object creation.
    *   `profile-pictures-processed` bucket: Stores the resized and optimized versions of the profile pictures (e.g., `user-id/thumbnail.jpg`, `user-id/medium.jpg`, `user-id/large.jpg`).
    *   **Role:** Highly available, durable, and scalable object storage. Crucial for both storing raw inputs and processed outputs, and for triggering the asynchronous workflow.
*   **AWS Lambda:**
    *   `image-resizer` function: The serverless compute service that executes the image processing logic. It's triggered by SQS messages, downloads images from S3, performs CPU-intensive resizing, and uploads results back to S3.
    *   **Role:** Provides scalable, cost-effective, and event-driven compute for the asynchronous image processing without managing servers.
*   **Amazon SQS (Simple Queue Service):**
    *   `image-processing-queue`: A standard queue that receives `ObjectCreated` events from the `profile-pictures-raw` S3 bucket. The Lambda function polls this queue for new messages.
    *   **Role:** Decouples the S3 event notification from the Lambda function, providing a buffer for events, ensuring messages are not lost, and enabling asynchronous processing with retries.
*   **Amazon RDS (Relational Database Service) / DynamoDB:**
    *   (Existing) User Profile Database: Stores metadata about users, including the URLs to their profile pictures in S3. The Lambda function updates these URLs after processing.
    *   **Role:** Persistent storage for application data and image metadata.
*   **AWS IAM (Identity and Access Management):**
    *   **Role:** Manages permissions for all AWS services. Crucial for granting the backend service permission to generate presigned URLs, S3 permission to send events to SQS, SQS permission to trigger Lambda, and Lambda permission to read/write S3 and update the database.
*   **AWS CloudWatch:**
    *   **Role:** Monitoring and logging for Lambda function execution, SQS queue metrics, and S3 access logs. Essential for observing the health and performance of the pipeline and debugging issues.

### 3. High-Level Steps for User Interaction

1.  **User Initiates Upload:** The user clicks "Upload Profile Picture" in the web or mobile application.
2.  **Backend Requests Presigned URL:** The client application sends a request to the Django/Node backend API (e.g., `POST /api/profile/picture/upload-url`).
3.  **Backend Generates Presigned URL:**
    *   The backend authenticates and authorizes the user.
    *   It generates a unique object key for the raw image (e.g., `user-id/raw/timestamp-original.jpg`).
    *   It uses the AWS SDK to generate an S3 presigned URL for a `PUT` operation to `s3://profile-pictures-raw/user-id/raw/timestamp-original.jpg`. This URL includes temporary credentials and specifies the allowed HTTP method (`PUT`).
    *   The backend stores a pending record in the database for this upload, noting the `user-id` and the `raw_image_key`.
    *   The backend returns the presigned URL and the `raw_image_key` to the client.
    *   **Backend Response Time:** This step is very fast, typically under 100ms, as it involves minimal computation and no large file transfers.
4.  **Client Uploads Image Directly to S3:**
    *   The client application receives the presigned URL.
    *   It then performs an HTTP `PUT` request directly to the presigned URL, sending the raw image file as the request body.
    *   S3 receives the image.
5.  **S3 Triggers Event:**
    *   Upon successful upload to `s3://profile-pictures-raw/user-id/raw/timestamp-original.jpg`, S3 emits an `ObjectCreated` event.
    *   This event is configured to be sent to the `image-processing-queue` SQS queue. The message body contains details like the bucket name and the object key.
6.  **Lambda Processes Image:**
    *   The `image-resizer` Lambda function is triggered by the SQS message.
    *   It extracts the `bucket` and `key` of the newly uploaded raw image from the SQS message.
    *   It downloads the raw image from `s3://profile-pictures-raw/user-id/raw/timestamp-original.jpg`.
    *   It uses an image processing library (e.g., Pillow for Python, sharp for Node.js) to resize the image into multiple dimensions (e.g., 50x50 thumbnail, 200x200 medium, 800x800 large).
    *   For each resized version, it uploads the image to `s3://profile-pictures-processed/user-id/thumbnail.jpg`, `s3://profile-pictures-processed/user-id/medium.jpg`, etc. (overwriting previous versions for the same user).
    *   It updates the user's profile record in the database (e.g., `UPDATE users SET profile_picture_thumbnail_url = '...', profile_picture_medium_url = '...' WHERE id = 'user-id'`).
7.  **User Sees Processed Image (Eventually):**
    *   The client application can either poll the backend for the status of the image processing or receive a push notification (e.g., via WebSockets if implemented).
    *   Once the database is updated, the backend will serve the new profile picture URLs from `profile-pictures-processed` for subsequent requests. The user will then see their updated profile picture.

### 4. Handling Potential Failures During Image Processing

Robust error handling is crucial for an asynchronous system.

1.  **SQS Dead-Letter Queue (DLQ):**
    *   Configure the `image-processing-queue` SQS queue with a Redrive Policy that points to a Dead-Letter Queue (e.g., `image-processing-dlq`).
    *   If the Lambda function fails to process a message (e.g., throws an unhandled exception, times out, or is explicitly marked as failed) after a configured number of retries (e.g., 3-5 times), SQS will move the message to the DLQ.
    *   **Why it works:** Prevents poisoned messages from continuously failing and blocking the queue. Messages in the DLQ can be inspected, analyzed, and potentially reprocessed manually or by a separate automated process.
    *   **Terraform example for SQS queue with DLQ:**
        ```terraform
        resource "aws_sqs_queue" "image_processing_queue" {
          name                       = "image-processing-queue"
          message_retention_seconds  = 345600 # 4 days
          visibility_timeout_seconds = 300    # 5 minutes, should be > Lambda timeout

          redrive_policy = jsonencode({
            deadLetterTargetArn = aws_sqs_queue.image_processing_dlq.arn
            maxReceiveCount     = 5
          })
        }

        resource "aws_sqs_queue" "image_processing_dlq" {
          name                      = "image-processing-dlq"
          message_retention_seconds = 1209600 # 14 days
        }
        ```

2.  **Lambda Idempotency and Error Handling:**
    *   **Idempotency:** The Lambda function should be designed to be idempotent. If it processes the same SQS message multiple times (due to retries or eventual consistency), it should produce the same result without adverse side effects. For image resizing, this means overwriting existing processed images in S3 is acceptable. Updating the database with the same URLs multiple times is also fine.
    *   **Specific Error Handling:**
        *   **Image Download Failure:** If the Lambda cannot download the raw image from S3 (e.g., object deleted, permissions issue), it should log the error and allow the message to be retried or sent to the DLQ.
        *   **Image Processing Failure:** If the image processing library encounters an unsupported format or corrupted image, the Lambda should catch the exception, log it, and potentially send a specific notification (e.g., to an SNS topic for alerts) before allowing the message to be retried or sent to the DLQ.
        *   **S3 Upload Failure:** If uploading processed images to S3 fails, the Lambda should retry (using the AWS SDK's built-in retry mechanisms) or throw an error to trigger SQS retries.
        *   **Database Update Failure:** If the database update fails, the Lambda should retry or throw an error. It's critical that the database update happens *after* S3 uploads, or that the system can reconcile eventual consistency.
    *   **Lambda Timeout:** Configure a generous timeout for the Lambda function (e.g., 1-2 minutes) to allow for large image processing, but not so long that it wastes resources on hung processes. If it times out, SQS will retry the message.
    *   **Lambda Memory:** Allocate sufficient memory to the Lambda function. Image processing is memory-intensive. More memory often means more CPU, leading to faster execution and fewer timeouts.

3.  **CloudWatch Alarms:**
    *   Set up CloudWatch Alarms on the `image-processing-dlq` to notify operations staff (e.g., via SNS to an email address or Slack channel) if the number of messages in the DLQ exceeds a certain threshold (e.g., 0 for critical, 5 for warning).
    *   Monitor Lambda errors and invocations. An increase in `Errors` or `Throttles` metrics for the `image-resizer` Lambda should trigger alerts.

4.  **Traceability and Logging:**
    *   Ensure comprehensive logging within the Lambda function (to CloudWatch Logs) at each critical step: message reception, S3 download, processing start/end, S3 upload, database update.
    *   Include relevant identifiers (e.g., `user-id`, `raw_image_key`, SQS `message-id`) in all logs to facilitate debugging.

**Trade-offs and What Breaks First:**

*   **Increased Complexity:** The system is now distributed and event-driven, which adds complexity compared to a monolithic synchronous approach. Debugging across services (S3 -> SQS -> Lambda -> S3 -> DB) requires more tooling and understanding.
*   **Eventual Consistency:** The user's profile picture won't be updated *immediately* after the upload. There will be a delay (typically seconds to a few minutes, depending on queue depth and Lambda execution time) before the processed images are available and the database is updated. The frontend needs to handle this gracefully (e.g., showing a "processing" spinner, displaying the old image until the new one is ready).
*   **Cost:** While Lambda and SQS are cost-effective at scale, there are costs associated with each service. S3 storage, S3 requests, SQS messages, and Lambda invocations/duration all incur charges. This is generally cheaper than over-provisioning application servers for peak image processing load.
*   **Lambda Cold Starts:** For very infrequent uploads, Lambda might experience "cold starts," where the first invocation takes longer as AWS initializes the execution environment. For a popular platform, this is less of an issue as the function will likely be warm.
*   **Scaling Bottlenecks:**
    *   **S3 Request Limits:** S3 is highly scalable, but very high concurrent read/write operations to a single prefix might theoretically hit limits (though these are very high and rarely encountered).
    *   **Lambda Concurrency:** Lambda has a default concurrency limit per region (e.g., 1000). If image uploads spike dramatically, it's possible to hit this limit, causing SQS messages to back up. This limit can be increased.
    *   **Database Write Throughput:** If the database becomes a bottleneck for updates, it could slow down the final step of the processing pipeline. This might require scaling the RDS instance or optimizing database writes.

### Going Further: Authentication and Authorization

Ensuring only authenticated and authorized users can trigger this workflow and preventing unauthorized access/modification of source images requires a multi-layered approach.

1.  **Authentication/Authorization for Presigned URL Generation (Backend):**
    *   **Mechanism:** The Django/Node backend service is the gatekeeper. When a client requests a presigned URL, the backend must:
        *   **Authenticate:** Verify the user's identity (e.g., using JWTs, session cookies, OAuth tokens).
        *   **Authorize:** Check if the authenticated user is permitted to upload a profile picture for *their own* account. This typically involves checking if the `user_id` in the request matches the `user_id` associated with the authenticated token.
    *   **Prevention:** By performing these checks *before* generating the presigned URL, we ensure that only legitimate users can obtain a URL to upload *their* image. An unauthorized user cannot simply guess a URL or forge a request to upload an image for another user.
    *   **Presigned URL Scope:** The presigned URL itself should be highly specific:
        *   **HTTP Method:** Only allow `PUT`.
        *   **Object Key:** Confine it to a specific key path, typically including the user's ID (e.g., `user-id/raw/timestamp-original.jpg`). This prevents a user from uploading to arbitrary locations in the S3 bucket.
        *   **Expiration:** Set a short expiration time (e.g., 5-15 minutes) for the URL, limiting the window of opportunity for misuse.

    *   **Example (Node.js with AWS SDK v3):**
        ```typescript
        import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";
        import { getSignedUrl } from "@aws-sdk/s3-request-presigner";

        const s3Client = new S3Client({ region: "us-east-1" });
        const BUCKET_NAME = "profile-pictures-raw";

        async function generatePresignedUploadUrl(userId: string, fileName: string): Promise<{ url: string, objectKey: string }> {
            // In a real app, userId would come from an authenticated session/JWT
            // fileName would be sanitized and validated
            const objectKey = `${userId}/raw/${Date.now()}-${fileName}`;

            const command = new PutObjectCommand({
                Bucket: BUCKET_NAME,
                Key: objectKey,
                ContentType: "image/*", // Client should send this
                ACL: "private" // Ensure raw images are not publicly readable
            });

            const signedUrl = await getSignedUrl(s3Client, command, {
                expiresIn: 600 // URL valid for 10 minutes
            });

            return { url: signedUrl, objectKey: objectKey };
        }
        ```

2.  **S3 Bucket Policies and IAM Roles for Source Images (`profile-pictures-raw`):**
    *   **Bucket Policy:**
        *   The `profile-pictures-raw` bucket should have a bucket policy that explicitly denies public read/write access.
        *   It should only allow `s3:PutObject` actions via presigned URLs (which are temporary and specific) and `s3:GetObject` for the `image-resizer` Lambda function's IAM role.
    *   **IAM Role for Lambda:**
        *   The IAM role associated with the `image-resizer` Lambda function must have `s3:GetObject` permissions *only* on the `profile-pictures-raw` bucket and specific prefixes (e.g., `arn:aws:s3:::profile-pictures-raw/*`).
        *   It also needs `s3:PutObject` permissions on the `profile-pictures-processed` bucket.
    *   **Prevention:** This ensures that raw images are not publicly accessible. Only the authorized Lambda function can read them for processing. The presigned URL mechanism is the only way for clients to *write* to this bucket, and that is controlled by the backend's authentication/authorization.

    *   **Example IAM Policy for Lambda (Terraform):**
        ```terraform
        resource "aws_iam_role_policy" "lambda_s3_access" {
          name = "lambda-s3-access"
          role = aws_iam_role.image_resizer_lambda_role.id

          policy = jsonencode({
            Version = "2012-10-17",
            Statement = [
              {
                Effect = "Allow",
                Action = [
                  "s3:GetObject"
                ],
                Resource = [
                  "arn:aws:s3:::profile-pictures-raw/*"
                ]
              },
              {
                Effect = "Allow",
                Action = [
                  "s3:PutObject",
                  "s3:PutObjectAcl" # If you need to set ACLs, e.g., public-read for processed images
                ],
                Resource = [
                  "arn:aws:s3:::profile-pictures-processed/*"
                ]
              }
            ]
          })
        }
        ```

3.  **S3 Bucket Policies for Processed Images (`profile-pictures-processed`):**
    *   **Access Control:** For processed images, you have a choice:
        *   **Private with Presigned URLs:** Keep them private and serve them via presigned URLs generated by your backend. This adds a small latency and backend load for every image request but offers the highest security (e.g., for premium content, or if you want to track image views).
        *   **Public Read:** Make them publicly readable (e.g., `ACL: public-read` when uploaded by Lambda, or a bucket policy). This is common for profile pictures as they are typically meant to be displayed publicly or to other authenticated users. If public, ensure the object keys are sufficiently random or tied to user IDs to prevent easy enumeration.
    *   **Recommendation for Profile Pictures:** Often, `public-read` is acceptable for processed profile pictures, as the raw images are protected, and the processed versions are intended for display. The `profile-pictures-processed` bucket policy would allow `s3:GetObject` for `*` (everyone).

    *   **Example S3 Bucket Policy for `profile-pictures-processed` (Terraform):**
        ```terraform
        resource "aws_s3_bucket_policy" "processed_bucket_public_read" {
          bucket = aws_s3_bucket.profile_pictures_processed.id

          policy = jsonencode({
            Version = "2012-10-17",
            Statement = [
              {
                Effect = "Allow",
                Principal = "*",
                Action = [
                  "s3:GetObject"
                ],
                Resource = [
                  "${aws_s3_bucket.profile_pictures_processed.arn}/*"
                ]
              }
            ]
          })
        }
        ```

By combining backend authentication/authorization with precise IAM policies and presigned URLs, we create a secure workflow where:
*   Only authenticated users can initiate an upload.
*   They can only upload to a specific, temporary location for their own profile.
*   Raw images are never publicly exposed.
*   The processing Lambda has only the necessary permissions to read raw and write processed images.
*   Processed images can be served securely (private with presigned URLs) or publicly, depending on the application's requirements.
