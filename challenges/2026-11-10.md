Your team maintains a critical Node.js microservice that manages customer subscriptions for a large B2B SaaS platform. This service handles subscription lifecycle events (creation, renewal, cancellation, plan changes) and integrates with a third-party payment gateway.

Currently, the service processes subscription changes synchronously. When a customer upgrades their plan, the API call directly triggers a series of operations: updating the database, calling the payment gateway, and sending internal notifications. This works for most cases, but during peak times (e.g., end of month for renewals, promotional events), the payment gateway's API often experiences increased latency and occasional timeouts. This leads to customer-facing errors, retries, and a degraded user experience, especially when multiple customers attempt changes simultaneously. The payment gateway has a hard rate limit of 10 requests per second per API key, which is sometimes hit during these peak periods, resulting in 429 Too Many Requests errors.

You need to refactor the subscription change process to be more resilient to external API latency and failures, and to respect external rate limits, without blocking the customer-facing API response.

## Requirements

The core problem is that synchronous calls to a potentially slow and rate-limited external service are directly impacting the responsiveness and reliability of your subscription change API. The solution must decouple the immediate API response from the potentially long-running or retriable external operations, handle rate limiting gracefully, and ensure eventual consistency. The existing database structure and core business logic for subscription state changes should remain largely intact, but the integration with the payment gateway needs a more robust approach. The system must also be able to recover from transient payment gateway failures.

## Deliverables

1.  **Refactor the subscription update endpoint** (`/subscriptions/:id/change-plan` for example) to return an immediate success response to the client after initiating the plan change, without waiting for the payment gateway integration to complete.
2.  Implement a **mechanism to process payment gateway calls asynchronously**, ensuring that external API rate limits (10 requests/second) are respected. This mechanism should also handle transient failures (e.g., network errors, payment gateway 5xx responses) with automatic retries.
3.  Define **TypeScript types** for the messages or events exchanged between the API handler and the asynchronous processing mechanism.
4.  Provide a **brief explanation** (2-3 sentences) of how you would monitor the health and progress of the asynchronous payment gateway operations.

## Going further

How would you ensure that if your Node.js service crashes or restarts mid-processing, no subscription changes are lost and all pending payment gateway operations are eventually completed exactly once?

## Worked answer

### 1. Refactor the subscription update endpoint

To decouple the API response from the payment gateway interaction, we'll introduce a message queue. When a plan change request comes in, the API handler will validate the request, update the subscription's *intended* state in our database, and then publish a message to a queue. The API can then immediately return a success response.

For simplicity, we'll simulate a message queue using a local array in this example. In a real-world scenario, this would be a robust message broker like AWS SQS, RabbitMQ, or Kafka.

```typescript
// src/api/subscriptionController.ts
import express, { Request, Response } from 'express';
import { v4 as uuidv4 } from 'uuid';
import { Subscription, SubscriptionPlan, SubscriptionStatus } from '../types/subscription';
import { PaymentGatewayMessage, PaymentGatewayMessageType } from '../types/paymentGateway';
import { publishPaymentGatewayMessage } from '../queue/paymentGatewayQueue';
import { getSubscriptionById, updateSubscription } from '../data/subscriptionRepository';

const router = express.Router();

// In a real application, this would be a database or a more persistent store.
const subscriptions: Map<string, Subscription> = new Map();

// Seed some initial data
subscriptions.set('sub-123', {
  id: 'sub-123',
  customerId: 'cust-abc',
  currentPlan: SubscriptionPlan.BASIC,
  status: SubscriptionStatus.ACTIVE,
  startDate: new Date(),
  endDate: new Date(new Date().setFullYear(new Date().getFullYear() + 1)),
  version: 1,
});

router.post('/subscriptions/:id/change-plan', async (req: Request, res: Response) => {
  const subscriptionId = req.params.id;
  const { newPlan } = req.body;

  if (!newPlan || !(Object.values(SubscriptionPlan) as string[]).includes(newPlan)) {
    return res.status(400).json({ message: 'Invalid newPlan provided.' });
  }

  const subscription = await getSubscriptionById(subscriptionId);

  if (!subscription) {
    return res.status(404).json({ message: 'Subscription not found.' });
  }

  if (subscription.currentPlan === newPlan) {
    return res.status(200).json({ message: 'Subscription already on the requested plan.' });
  }

  // --- Core change: Update internal state immediately, then enqueue payment action ---

  // In a real system, this would involve a transactional update:
  // 1. Update subscription status to PENDING_CHANGE or similar.
  // 2. Store the intended newPlan.
  // 3. Increment a version or add an 'operation_id' for idempotency.
  // For this example, we'll just update the plan directly for simplicity,
  // assuming the queue worker will eventually confirm it.
  // A more robust approach would be to have a 'pendingPlan' field.

  const updatedSubscription: Subscription = {
    ...subscription,
    // For this example, we'll assume the plan is 'pending' until confirmed by payment.
    // In a real system, you might have a `pendingPlanChange: SubscriptionPlan | null` field.
    currentPlan: newPlan, // This is the *intended* plan, not yet confirmed by payment.
    status: SubscriptionStatus.PENDING_PLAN_CHANGE, // New status to indicate pending external action
    version: subscription.version + 1, // Optimistic concurrency control
  };

  try {
    await updateSubscription(updatedSubscription);

    // Publish a message to the payment gateway queue
    const message: PaymentGatewayMessage = {
      id: uuidv4(),
      type: PaymentGatewayMessageType.PROCESS_PLAN_CHANGE,
      payload: {
        subscriptionId: updatedSubscription.id,
        customerId: updatedSubscription.customerId,
        oldPlan: subscription.currentPlan,
        newPlan: updatedSubscription.currentPlan,
        amount: calculatePlanChangeAmount(subscription.currentPlan, updatedSubscription.currentPlan),
        currency: 'USD', // Example currency
        timestamp: new Date().toISOString(),
        attempt: 1, // Initial attempt count
      },
    };
    await publishPaymentGatewayMessage(message);

    console.log(`[API] Subscription ${subscriptionId} plan change to ${newPlan} initiated. Message published.`);
    return res.status(202).json({
      message: 'Subscription plan change initiated successfully. Processing payment asynchronously.',
      subscriptionId: subscription.id,
      newPlan: newPlan,
    });
  } catch (error) {
    console.error(`[API] Error processing subscription plan change for ${subscriptionId}:`, error);
    // If the database update fails or message publishing fails, we should ideally
    // revert the database change or have a compensating transaction.
    // For simplicity, we'll just return a server error.
    return res.status(500).json({ message: 'Failed to initiate plan change.' });
  }
});

// Helper function to simulate amount calculation
function calculatePlanChangeAmount(oldPlan: SubscriptionPlan, newPlan: SubscriptionPlan): number {
  const planPrices: Record<SubscriptionPlan, number> = {
    [SubscriptionPlan.BASIC]: 10,
    [SubscriptionPlan.STANDARD]: 25,
    [SubscriptionPlan.PREMIUM]: 50,
  };
  return planPrices[newPlan] - planPrices[oldPlan]; // Can be negative for downgrades
}

export default router;
```

**Explanation:**

1.  **Immediate Response (202 Accepted):** The API now returns a `202 Accepted` status code. This tells the client that the request has been accepted for processing, but the processing is not yet complete. This is the standard HTTP status for asynchronous operations.
2.  **Database Update:** The subscription's `currentPlan` is updated to the `newPlan` and its `status` is set to `PENDING_PLAN_CHANGE`. This ensures our internal system reflects the *intended* state immediately. If the payment fails, a compensating action will be needed (e.g., reverting the plan, marking as `FAILED_PLAN_CHANGE`).
3.  **Message Publishing:** A `PaymentGatewayMessage` is created with details about the plan change and published to a (simulated) message queue. This message contains all necessary information for the asynchronous worker to process the payment.
4.  **Decoupling:** The API handler no longer waits for the external payment gateway. Its responsibility is limited to validating the request, updating the local state, and enqueuing the background task.

// src/worker/paymentGatewayWorker.ts
import { PaymentGatewayMessage, PaymentGatewayMessageType, ProcessPlanChangePayload } from '../types/paymentGateway';
import { consumePaymentGatewayMessage, requeuePaymentGatewayMessage } from '../queue/paymentGatewayQueue';
import { paymentGatewayClient } from '../external/paymentGatewayClient';
import { getSubscriptionById, updateSubscription } from '../data/subscriptionRepository';
import { SubscriptionStatus } from '../types/subscription';

const MAX_RETRIES = 5; // Maximum number of retries for transient errors
const RETRY_DELAY_MS = 5000; // Initial retry delay (e.g., 5 seconds)
const CONCURRENCY_LIMIT = 5; // To respect payment gateway rate limit (e.g., 10 req/s, so 5 concurrent with 0.5s avg latency)
const RATE_LIMIT_WINDOW_MS = 1000; // 1 second window for rate limiting
const MAX_REQUESTS_PER_WINDOW = 10; // Payment gateway limit

let activeWorkers = 0;
const requestTimestamps: number[] = []; // To track requests within a window

async function processMessage(message: PaymentGatewayMessage) {
  console.log(`[Worker] Processing message ${message.id} (type: ${message.type}, attempt: ${message.payload.attempt})`);

  try {
    switch (message.type) {
      case PaymentGatewayMessageType.PROCESS_PLAN_CHANGE:
        await handleProcessPlanChange(message.payload as ProcessPlanChangePayload, message);
        break;
      default:
        console.warn(`[Worker] Unknown message type: ${message.type}. Message ${message.id} discarded.`);
        // In a real system, move to a dead-letter queue or log for manual investigation.
        break;
    }
  } catch (error) {
    console.error(`[Worker] Unhandled error processing message ${message.id}:`, error);
    // This catch block handles errors that weren't caught within specific handlers.
    // For robustness, consider requeueing with a delay or moving to a DLQ here too.
  }
}

async function handleProcessPlanChange(payload: ProcessPlanChangePayload, originalMessage: PaymentGatewayMessage) {
  try {
    await paymentGatewayClient.processPlanChange(payload);

    // If successful, update subscription status to ACTIVE (or new plan confirmed)
    const subscription = await getSubscriptionById(payload.subscriptionId);
    if (subscription) {
      const updatedSubscription = {
        ...subscription,
        status: SubscriptionStatus.ACTIVE, // Payment confirmed, plan change is now active
        // currentPlan is already updated by API handler, so no change needed here
        version: subscription.version + 1,
      };
      await updateSubscription(updatedSubscription);
      console.log(`[Worker] Successfully processed plan change for subscription ${payload.subscriptionId}. Status updated to ACTIVE.`);
    } else {
      console.error(`[Worker] Subscription ${payload.subscriptionId} not found after successful payment gateway call.`);
      // This indicates a data inconsistency. Alert and investigate.
    }
  } catch (error: any) {
    console.error(`[Worker] Failed to process plan change for ${payload.subscriptionId}: ${error.message}`);

    const currentAttempt = payload.attempt;
    if (currentAttempt < MAX_RETRIES) {
      // Increment attempt count and re-queue with exponential backoff
      const nextAttemptPayload: ProcessPlanChangePayload = {
        ...payload,
        attempt: currentAttempt + 1,
      };
      const delay = RETRY_DELAY_MS * Math.pow(2, currentAttempt - 1); // Exponential backoff
      console.log(`[Worker] Re-queuing message ${originalMessage.id} for retry ${currentAttempt + 1} in ${delay}ms.`);
      setTimeout(() => {
        requeuePaymentGatewayMessage({ ...originalMessage, payload: nextAttemptPayload });
      }, delay);
    } else {
      console.error(`[Worker] Max retries (${MAX_RETRIES}) reached for message ${originalMessage.id}. Moving to failed state.`);
      // Update subscription status to reflect payment failure
      const subscription = await getSubscriptionById(payload.subscriptionId);
      if (subscription) {
        const updatedSubscription = {
          ...subscription,
          status: SubscriptionStatus.PAYMENT_FAILED, // Indicate payment failure
          // Optionally, revert currentPlan to oldPlan or set a 'failedPlan' field
          version: subscription.version + 1,
        };
        await updateSubscription(updatedSubscription);
        console.log(`[Worker] Subscription ${payload.subscriptionId} status updated to PAYMENT_FAILED.`);
      }
      // In a real system, send to a Dead-Letter Queue (DLQ) for manual intervention.
      // Log extensively and trigger alerts.
    }
  }
}

// Rate limiting and concurrency control
async function acquireRateLimitSlot(): Promise<void> {
  return new Promise(resolve => {
    const checkSlot = () => {
      // Clean up old timestamps
      const now = Date.now();
      while (requestTimestamps.length > 0 && requestTimestamps[0] < now - RATE_LIMIT_WINDOW_MS) {
        requestTimestamps.shift();
      }

      if (requestTimestamps.length < MAX_REQUESTS_PER_WINDOW && activeWorkers < CONCURRENCY_LIMIT) {
        requestTimestamps.push(now);
        activeWorkers++;
        resolve();
      } else {
        // Wait for the next available slot
        const timeToWait = requestTimestamps.length >= MAX_REQUESTS_PER_WINDOW
          ? RATE_LIMIT_WINDOW_MS - (now - requestTimestamps[0]) + 10 // Wait until oldest request is out of window
          : 100; // Small delay if only concurrency limit is hit
        setTimeout(checkSlot, timeToWait > 0 ? timeToWait : 10);
      }
    };
    checkSlot();
  });
}

function releaseRateLimitSlot(): void {
  activeWorkers--;
}

// Main worker loop
async function startWorker() {
  console.log('[Worker] Payment Gateway Worker started. Waiting for messages...');
  while (true) {
    await acquireRateLimitSlot(); // Wait for a slot before consuming
    const message = await consumePaymentGatewayMessage();
    if (message) {
      processMessage(message).finally(() => {
        releaseRateLimitSlot();
      });
    } else {
      releaseRateLimitSlot(); // Release slot if no message was found
      await new Promise(resolve => setTimeout(resolve, 1000)); // Wait a bit before polling again
    }
  }
}

**Explanation of the Asynchronous Worker:**

1.  **Worker Loop:** The `startWorker` function continuously polls the message queue for new messages.
2.  **Concurrency and Rate Limiting (`acquireRateLimitSlot`):**
    *   **Concurrency:** `activeWorkers` limits the number of concurrent calls to the payment gateway. This is crucial because even if the rate limit allows 10 req/s, having 100 concurrent requests could overwhelm the payment gateway or our own worker.
    *   **Rate Limiting:** `requestTimestamps` tracks the time of each request within a sliding window (`RATE_LIMIT_WINDOW_MS`). Before making a new request, the worker checks if adding another request would exceed `MAX_REQUESTS_PER_WINDOW` within the last second. If so, it waits. This ensures we don't hit the `429 Too Many Requests` error.
    *   **Trade-offs:** This in-memory rate limiter is simple but not distributed. If you have multiple worker instances, each will maintain its own `requestTimestamps` and `activeWorkers` count, potentially leading to exceeding the global rate limit. For a distributed system, a shared rate limiter (e.g., Redis-based token bucket or leaky bucket) would be necessary.
3.  **Retry Mechanism:**
    *   `MAX_RETRIES` and `RETRY_DELAY_MS` define the retry policy.
    *   **Exponential Backoff:** If `paymentGatewayClient.processPlanChange` throws a transient error (e.g., network error, 5xx), the message is re-queued with an incremented `attempt` count and an exponentially increasing delay. This prevents hammering the failing service and gives it time to recover.
    *   **Max Retries:** After `MAX_RETRIES`, the message is no longer re-queued. Instead, the subscription's status is updated to `PAYMENT_FAILED`, and the message would typically be moved to a Dead-Letter Queue (DLQ) for manual inspection.
4.  **Idempotency (Implicit):** While not explicitly coded as a separate layer, the `paymentGatewayClient.processPlanChange` should ideally be idempotent on the payment gateway side. Our `PaymentGatewayMessage.id` can be passed to the payment gateway to ensure that if the same message is processed multiple times (e.g., due to a retry after a successful but unconfirmed payment), it doesn't result in duplicate charges.
5.  **Database Updates:** Upon successful payment, the subscription's status is confirmed to `ACTIVE`. If payment fails after retries, the status is set to `PAYMENT_FAILED`. This ensures eventual consistency.

### 4. Brief explanation of monitoring

Monitoring the health and progress of asynchronous payment gateway operations would involve:

1.  **Queue Metrics:** Track queue size (messages pending), message age (how long messages sit in the queue), and messages processed per second. High queue size or age indicates a bottleneck.
2.  **Worker Metrics:** Monitor the number of active workers, CPU/memory usage, error rates (e.g., `paymentGatewayClient` failures, messages moved to DLQ), and retry counts.
3.  **Subscription Status:** Observe the distribution of `PENDING_PLAN_CHANGE` and `PAYMENT_FAILED` statuses in the database. A growing number of `PENDING_PLAN_CHANGE` indicates a backlog, while `PAYMENT_FAILED` requires investigation.

### Going further

To ensure no subscription changes are lost and all pending payment gateway operations are eventually completed exactly once, even if the Node.js service crashes or restarts mid-processing, we need to employ several robust patterns:

1.  **Persistent Message Queue:** Replace the in-memory array with a durable message broker (e.g., AWS SQS, RabbitMQ, Kafka). These brokers persist messages to disk, so they survive service restarts.
    *   **Visibility Timeout:** When a worker consumes a message, the broker makes it invisible to other consumers for a configurable "visibility timeout." If the worker fails to acknowledge (delete) the message within this timeout, the message becomes visible again and can be processed by another worker. This handles worker crashes.
    *   **Acknowledgement (ACK/NACK):** Workers must explicitly acknowledge successful processing (ACK) or signal failure (NACK) to the broker. Only upon ACK is the message removed from the queue.
2.  **Idempotent Operations:**
    *   **Payment Gateway Calls:** The `PaymentGatewayMessage.id` (a UUID) should be passed to the external payment gateway as an idempotency key. The gateway should be designed to accept this key and ensure that if the same request is received multiple times with the same key, it only processes the payment once.
    *   **Database Updates:** Database updates in the worker should also be idempotent. For example, when updating `status` to `ACTIVE`, the update query could include a `WHERE status = 'PENDING_PLAN_CHANGE'` clause. Using optimistic locking (`version` field) also helps prevent concurrent updates from overwriting each other.
3.  **Transactional Outbox Pattern (for API handler):**
    *   The most robust way to ensure a message is *published exactly once* and *only if* the database transaction commits is the Outbox Pattern.
    *   Instead of directly publishing to the message queue, the API handler first inserts the `PaymentGatewayMessage` into a dedicated `outbox` table *within the same database transaction* as the subscription status update.
    *   A separate "outbox relay" process (or a transactional CDC tool like Debezium) then monitors this `outbox` table. When new messages appear, it publishes them to the real message broker and marks them as sent (or deletes them).
    *   This guarantees atomicity: either both the subscription update and the message are persisted, or neither are. If the service crashes before publishing, the message is still in the outbox table and will be picked up by the relay after restart.
4.  **Dead-Letter Queues (DLQs):** Messages that fail processing after multiple retries should be moved to a DLQ. This prevents poison-pill messages from endlessly blocking the queue and allows for manual inspection and reprocessing.
5.  **Monitoring and Alerting:** Robust monitoring (as described in the previous section) is critical to detect issues like growing DLQs, unacknowledged messages, or stalled workers, enabling quick intervention.

By combining a persistent message queue with visibility timeouts, idempotent operations, the transactional outbox pattern, and DLQs, we can achieve high reliability and "at-least-once" delivery guarantees, which, when combined with idempotency, effectively becomes "exactly-once" processing from a business perspective.
