## Scenario

Your team maintains a critical internal service responsible for generating daily analytics reports for your marketing department. This service runs as a containerized application on AWS Fargate. It processes data from a PostgreSQL database, performs complex aggregations, and then uploads the resulting CSV reports to an S3 bucket.

Recently, the volume of data in the PostgreSQL database has grown significantly, and the report generation process has started to fail intermittently due to memory exhaustion within the Fargate task. Specifically, the database query to fetch all necessary data for the report, which previously took around 30-60 seconds, now sometimes takes several minutes, leading to the Fargate task hitting its memory limits during the data processing phase. The Fargate task is currently configured with 2GB of memory and 1 vCPU. The report generation must complete reliably within a 15-minute window each day, and ideally, the data fetching and initial processing should not exceed 5 minutes.

## Requirements

The core problem is the intermittent memory exhaustion in the Fargate task due to large data fetches and processing. You need to propose and outline a cloud-native architectural adjustment that offloads or optimizes the initial heavy data fetching and/or processing steps to prevent the Fargate task from running out of memory, while keeping the overall report generation process within the 15-minute budget. The solution should be cost-effective and minimize operational overhead. You cannot simply increase Fargate task memory indefinitely, as the data volume is expected to continue growing.

## Worked answer

### 1. Architectural Diagram

The core idea is to offload the heavy data fetching and initial processing from the Fargate task to a more suitable service for large-scale data processing. AWS Glue is an excellent candidate for this, as it's a serverless data integration service that can run Spark jobs.

**New AWS Services Introduced:**

*   **AWS Glue:** For performing the heavy data fetching and initial processing (ETL).
*   **AWS EventBridge:** To schedule the daily execution.
*   **AWS Lambda:** To act as an orchestrator, triggering the Glue job and potentially the Fargate task.

### 2. Addressing Memory Exhaustion and Growing Data Volume

The proposed solution addresses the memory exhaustion problem by completely offloading the most memory-intensive part of the process – fetching a large dataset from PostgreSQL and performing initial aggregations – to AWS Glue.

*   **Memory Exhaustion:** The Fargate task previously struggled because it had to hold the entire dataset in memory (or a significant portion of it) while fetching and processing. AWS Glue, being a Spark-based service, is designed for distributed processing of large datasets. It can spill data to disk if necessary and process data in partitions, effectively handling datasets much larger than available memory on a single node. This means the Fargate task will no longer be responsible for the initial large data fetch or the complex, memory-intensive aggregations. Instead, it will read pre-processed, potentially aggregated, and optimized data (e.g., in Parquet format) from S3. Reading from S3 is typically much faster and less memory-intensive than querying a large relational database and processing the raw results.

*   **Growing Data Volume:** AWS Glue is inherently scalable. As the data volume grows, you can increase the number of Data Processing Units (DPUs) allocated to the Glue job. Each DPU provides a certain amount of compute and memory, allowing Glue to scale horizontally to handle larger datasets without requiring changes to the Fargate task's configuration. The Fargate task will continue to operate on a more manageable, pre-processed dataset, making its memory footprint more predictable and less susceptible to the raw data volume growth. The use of Parquet format in S3 is also crucial here, as it's a columnar format that is highly efficient for analytical queries, further reducing the memory and CPU requirements for the Fargate task when it reads the data.

### 3. Justification and Integration of New AWS Services

*   **AWS Glue:**
    *   **Justification:** Glue is chosen for its serverless nature, Spark compatibility, and native integration with other AWS services (S3, RDS). It eliminates the need to provision and manage EC2 instances for Spark clusters, reducing operational overhead. Its ability to scale dynamically makes it ideal for growing data volumes. It also provides a managed catalog (Glue Data Catalog) which can be useful for schema management, although not strictly required for this specific pipeline.
    *   **Integration:**
        1.  **Data Source:** The Glue job will connect directly to the existing PostgreSQL RDS instance using a JDBC connection. You'll need to ensure the Glue job's IAM role has permissions to access the RDS instance, and the RDS security group allows inbound connections from the Glue VPC endpoint or the Glue network interfaces.
        2.  **Output:** The Glue job will write its processed output to an S3 bucket in a columnar format like Parquet. This S3 bucket acts as a staging area.
        3.  **Triggering:** The Glue job will be triggered by a Lambda function, which in turn is invoked by EventBridge.

*   **AWS EventBridge:**
    *   **Justification:** EventBridge provides a robust, serverless way to schedule recurring tasks (cron jobs). It's highly reliable and integrates seamlessly with Lambda.
    *   **Integration:** A simple cron expression (e.g., `cron(0 5 * * ? *)` for 5 AM UTC daily) will trigger the Lambda function.

*   **AWS Lambda:**
    *   **Justification:** Lambda acts as a lightweight, serverless orchestrator. It's cost-effective for short-lived tasks like initiating a Glue job. It avoids the need for a dedicated EC2 instance or a complex Step Functions workflow for this relatively simple orchestration.
    *   **Integration:**
        1.  **Trigger:** EventBridge invokes the Lambda function.
        2.  **Glue Job Initiation:** The Lambda function uses the AWS SDK (e.g., `boto3` in Python) to call `glue.start_job_run()` to initiate the Glue ETL job. It can pass parameters to the Glue job if needed (e.g., the date for which to generate the report).
        3.  **Fargate Task Initiation (Optional but recommended):** Once the Glue job completes successfully (which can be detected via Glue job run status or a separate Lambda triggered by a Glue state change event), the Lambda function can then trigger the Fargate task. This ensures the Fargate task only runs when its input data is ready. This can be done by calling `ecs.run_task()`.

**Example Glue Job (Python/PySpark):**

Let's assume your PostgreSQL database has a table named `marketing_events` with columns like `event_id`, `user_id`, `event_timestamp`, `event_type`, `value`, `campaign_id`.

```python
# glue_etl_job.py
import sys
from awsglue.transforms import *
from awsglue.utils import getResolvedOptions
from pyspark.context import SparkContext
from awsglue.context import GlueContext
from awsglue.job import Job
from pyspark.sql.functions import col, sum, count, to_date, lit

# @params: [JOB_NAME, S3_STAGING_BUCKET, REPORT_DATE]
args = getResolvedOptions(sys.argv, ['JOB_NAME', 'S3_STAGING_BUCKET', 'REPORT_DATE'])

sc = SparkContext()
glueContext = GlueContext(sc)
spark = glueContext.spark_session
job = Job(glueContext)
job.init(args['JOB_NAME'], args)

s3_staging_bucket = args['S3_STAGING_BUCKET']
report_date = args['REPORT_DATE'] # e.g., '2023-01-01'

# 1. Read data from PostgreSQL
# Ensure your Glue connection 'marketing-pg-connection' is configured
# with JDBC URL, username, password, and VPC details.
datasource0 = glueContext.create_dynamic_frame.from_options(
    connection_type="postgresql",
    connection_options={
        "useConnectionProperties": "true",
        "dbtable": "marketing_events",
        "connectionName": "marketing-pg-connection"
    },
    transformation_ctx="datasource0"
)

# Convert to Spark DataFrame for easier processing
df = datasource0.toDF()

# 2. Perform initial aggregations
# Example: Daily summary of events and total value per campaign
daily_report_df = df.filter(to_date(col("event_timestamp")) == lit(report_date)) \
                    .groupBy("campaign_id", to_date(col("event_timestamp")).alias("report_date")) \
                    .agg(
                        count("event_id").alias("total_events"),
                        sum("value").alias("total_value")
                    )

# 3. Write processed data to S3 in Parquet format
# Partition by report_date for efficient querying later
output_path = f"s3://{s3_staging_bucket}/processed_data/daily_campaign_summary/"

daily_report_df.write \
    .mode("overwrite") \
    .partitionBy("report_date") \
    .parquet(output_path)

job.commit()
```

**Trade-offs:**

*   **Increased Complexity:** The architecture becomes more distributed, involving more services (EventBridge, Lambda, Glue). This increases the number of components to monitor and debug.
*   **Latency:** Introducing Glue adds an extra step to the pipeline. While Glue is efficient, its startup time and processing time will add to the overall report generation duration. However, this is acceptable given the 15-minute budget and the need to offload heavy processing.
*   **Cost:** While serverless, Glue costs are based on DPUs-hours. For very small datasets, it might be more expensive than a simple Fargate task. However, for growing data volumes, its scalability and efficiency make it cost-effective compared to over-provisioning Fargate. Lambda and EventBridge costs are negligible for this use case.
*   **Data Freshness:** The data processed by Glue will be a snapshot from the time the Glue job starts. This is addressed in the "Going Further" section.

**What breaks first at ten times the scale?**

At ten times the scale (data volume), the most likely bottlenecks would be:

1.  **PostgreSQL Read Throughput:** While Glue can scale, the underlying PostgreSQL database might struggle to serve the data fast enough if the queries become too large or complex, leading to I/O bottlenecks or high CPU utilization on the RDS instance. This would manifest as the Glue job taking longer to complete the `create_dynamic_frame.from_options` step.
2.  **Glue DPU Allocation:** If the data volume grows significantly, the default DPU allocation for the Glue job might become insufficient, leading to longer processing times. This can be mitigated by increasing DPUs, but there's a cost implication.
3.  **S3 Object Limits/Throttling:** While S3 is highly scalable, if the Glue job produces an extremely large number of very small files, or if the Fargate task tries to read an enormous number of objects concurrently, S3 might impose throttling. Using larger Parquet files (e.g., by repartitioning in Glue) helps.
4.  **Fargate Task Memory (again):** If the *final* aggregated data that the Fargate task needs to process still grows excessively large, or if the Fargate task's final processing logic becomes very memory-intensive, it could still hit memory limits. This indicates that the Glue job might need to perform *more* aggregation or pre-processing to reduce the data volume handed to Fargate.

### Going further

To ensure the data processed by the new solution is always the most up-to-date, considering potential data updates in the source PostgreSQL database even after the initial data fetch has begun, we need to implement a strategy for **snapshot isolation** or **change data capture (CDC)**.

The simplest and most common approach for analytical reporting on a daily schedule, especially when dealing with a transactional database, is to process data that was **"final" as of a specific point in time**.

Here are a few strategies:

1.  **Snapshotting at the Start of the ETL (Current Approach with Refinement):**
    *   **Mechanism:** The Glue job, when it starts, effectively takes a "logical snapshot" of the data. To ensure consistency, the PostgreSQL query executed by Glue should target data up to a specific timestamp.
    *   **Implementation:**
        *   Modify the Glue job's SQL query to include a `WHERE` clause that filters data based on a `last_updated_at` or `created_at` timestamp column.
        *   The `REPORT_DATE` parameter passed to the Glue job should represent the *end* of the reporting period. The query would fetch all data relevant to that day, up to a specific time (e.g., `WHERE event_timestamp < 'YYYY-MM-DD 00:00:00' + 1 day`).
        *   To handle updates to *existing* records for a past report date, the Glue job would need to re-process the entire day's data, or use a "merge" strategy when writing to S3 (e.g., upserting based on a primary key).
    *   **Example Glue Job (refined filter):**
        ```python
        # ... (previous Glue job setup) ...
        
        # Determine the start and end timestamps for the report period
        # Assuming REPORT_DATE is 'YYYY-MM-DD'
        report_start_datetime = f"{report_date} 00:00:00"
        # For daily reports, we usually process data up to the end of the day *before* the current run
        # Or, if processing for 'today', up to the current time of the job run.
        # Let's assume we want data for the *entire* report_date.
        report_end_datetime = (datetime.datetime.strptime(report_date, '%Y-%m-%d') + datetime.timedelta(days=1)).strftime('%Y-%m-%d %H:%M:%S')

        # 1. Read data from PostgreSQL with a specific time window
        # Using a custom query can give more control over the snapshot.
        # Ensure 'event_timestamp' is indexed in PostgreSQL.
        custom_query = f"""
            (SELECT event_id, user_id, event_timestamp, event_type, value, campaign_id
             FROM marketing_events
             WHERE event_timestamp >= '{report_start_datetime}'
               AND event_timestamp < '{report_end_datetime}') AS marketing_events_alias
        """
        
        datasource0 = glueContext.create_dynamic_frame.from_options(
            connection_type="postgresql",
            connection_options={
                "useConnectionProperties": "true",
                "dbtable": custom_query, # Use the custom query here
                "connectionName": "marketing-pg-connection"
            },
            transformation_ctx="datasource0"
        )
        # ... (rest of the Glue job) ...
        ```
    *   **Trade-offs:** Simple to implement. Data is consistent for the defined period. If data for a past day is updated, that day's report won't reflect the change unless the Glue job is re-run for that specific historical date. This is often acceptable for daily analytics reports.

2.  **Change Data Capture (CDC) with AWS DMS:**
    *   **Mechanism:** AWS Database Migration Service (DMS) can capture changes (inserts, updates, deletes) from the PostgreSQL database in real-time and stream them to an S3 bucket. These changes can then be processed incrementally by Glue.
    *   **Implementation:**
        *   Set up an AWS DMS replication instance and a replication task.
        *   Configure the task to replicate changes from your PostgreSQL RDS instance to an S3 bucket (e.g., in Parquet or JSON format). DMS can write full loads and then continuous CDC changes.
        *   Your Glue job would then read from this S3 CDC stream. Instead of doing a full read from PostgreSQL, it would process the incremental changes. This often involves merging these changes into a "data lake" table (e.g., a Delta Lake or Apache Hudi table in S3) to maintain an up-to-date view.
        *   The Fargate task would then read from this continuously updated data lake.
    *   **Trade-offs:** Provides near real-time data freshness. More complex to set up and manage than direct querying. Requires a data lake strategy (e.g., using Delta Lake or Hudi on S3 with Glue) to manage the merging of changes and maintain a consistent view. Higher operational overhead and potentially higher cost due to DMS and more complex Glue jobs.

3.  **Transactional Isolation Levels (Less Applicable Here):**
    *   **Mechanism:** While PostgreSQL supports various isolation levels (e.g., `REPEATABLE READ`, `SERIALIZABLE`), these primarily apply to individual transactions within the database itself. When fetching a large dataset over a long period, it's hard to guarantee that the *entire* fetch operation behaves as a single, atomic transaction from the perspective of external updates. A long-running query might still see some changes committed during its execution, or it might block other writes.
    *   **Why it's less suitable:** The problem isn't just about a single query's consistency, but about the consistency of the entire dataset being extracted for a report. Relying solely on database isolation for an external ETL process that takes minutes is difficult and can lead to performance issues (e.g., holding locks for too long). The "snapshotting" approach (Option 1) is a more practical way to achieve logical consistency for batch reporting.

For a daily analytics report where a slight delay in reflecting the absolute latest data (e.g., data updated a few minutes after the Glue job starts) is acceptable, **Option 1 (Snapshotting at the Start of the ETL)** is the most pragmatic and cost-effective approach. It ensures that the report reflects a consistent state of the data as of the beginning of its processing window, which is usually sufficient for daily analytics. If true real-time or near real-time reporting is required, then a more complex CDC solution with DMS and a data lake (Option 2) would be necessary.
