## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee shifts and schedules. A core feature is the ability for managers to view an "Availability Calendar" for their team. This calendar shows which employees are available or booked for specific time slots on a given day, often for a whole month at a time.

The underlying `employee_shifts` table has grown significantly and now contains hundreds of millions of rows, with each entry representing a specific shift for an employee. When a manager requests the Availability Calendar for a team of 50 employees for a 30-day period, the query to fetch all relevant shifts and then process them to determine availability can take 5-8 seconds. This latency is impacting user experience and causing frustration for managers who frequently check team availability. The data is relatively static for a given day once shifts are confirmed, but individual shifts can be added, updated, or deleted throughout the day.

## Requirements

You need to implement a caching strategy using Redis to significantly reduce the latency of loading the Availability Calendar. The goal is to bring the typical load time for a manager's calendar view down to under 500ms, even with hundreds of millions of underlying shift records. The solution must handle:

*   **High read volume:** The Availability Calendar is viewed frequently by managers.
*   **Data freshness:** While the data is mostly static for a given day, updates to individual shifts *must* be reflected in the calendar within a reasonable timeframe (under 60 seconds).
*   **Multi-tenancy:** Different companies (tenants) have their own sets of employees and shifts. Caching for one tenant should not affect another.
*   **Concurrency:** Multiple managers from the same or different teams might request calendars concurrently.
*   **Scale:** The solution should scale to support thousands of concurrent requests for calendar data across many tenants.

## Worked answer

### 1. Redis Data Structure(s)

For caching availability data, we need to store information about multiple employees' shifts over a date range. A single Redis **Hash** is a suitable data structure for storing the processed availability data for a specific team and a specific day.

**Justification:**

1.  **Key Structure:** The key for the Hash would uniquely identify the team and the date. For example, `availability:team:{team_id}:date:{YYYY-MM-DD}`. This allows for efficient retrieval of a specific day's data for a specific team.
2.  **Field-Value Pairs:** Inside the Hash, each field would represent an `employee_id`, and its value would be a serialized representation (e.g., JSON string) of their availability for that day. This could include an array of booked time slots, or a boolean indicating full availability, depending on the granularity needed.
    *   Example field: `employee:{employee_id}`
    *   Example value: `"[{\"start\": \"09:00\", \"end\": \"12:00\", \"status\": \"booked\"}, {\"start\": \"13:00\", \"end\": \"17:00\", \"status\": \"available\"}]"`
3.  **Atomic Operations:** Hashes allow for atomic updates to individual fields (e.g., updating one employee's availability without affecting others), which could be useful if we ever decided to update availability at a finer granularity than a full day. For our current scenario, we'll likely re-cache the whole day.
4.  **Memory Efficiency:** For a moderate number of employees per team (e.g., 50), a Hash is memory-efficient compared to storing each employee's availability as a separate Redis key, as it reduces key overhead.
5.  **Retrieval:** We can fetch all employees' availability for a given day with a single `HGETALL` command, or specific employees with `HMGET`.

**Example Key and Hash Structure:**

```
Key: availability:team:123:date:2026-11-04
Type: Hash
Fields:
  employee:456: "[{\"start\":\"09:00\",\"end\":\"12:00\",\"status\":\"booked\"}, {\"start\":\"13:00\",\"end\":\"17:00\",\"status\":\"available\"}]"
  employee:457: "[{\"start\":\"09:00\",\"end\":\"17:00\",\"status\":\"available\"}]"
  employee:458: "[{\"start\":\"09:00\",\"end\":\"17:00\",\"status\":\"booked\"}]"
  ... (for all 50 employees)
```

For a 30-day period, the application would make 30 `HGETALL` calls (one for each day) and combine the results. This is efficient enough for the target latency.

### 2. Cache Invalidation Strategy

The core requirement is that updates must be reflected within 60 seconds. This points towards an **active invalidation** strategy rather than relying solely on TTLs, although TTLs will be used as a fallback.

When an `employee_shift` record is created, updated, or deleted, we need to identify which cached availability calendars are affected and invalidate them.

**Steps:**

1.  **Identify Affected Caches:**
    *   When an `employee_shift` record is modified, it contains `employee_id`, `team_id`, and `shift_date`.
    *   From this information, we can construct the exact Redis key for the affected day's availability cache: `availability:team:{team_id}:date:{shift_date}`.
2.  **Asynchronous Invalidation:**
    *   Instead of performing synchronous Redis `DEL` operations within the database transaction (which could add latency to critical write paths), we should use an asynchronous mechanism.
    *   Upon a successful database write (create/update/delete of `employee_shift`), publish a message to a message queue (e.g., Kafka, RabbitMQ, or even a simple Redis Pub/Sub channel for lower scale). The message should contain the `team_id` and `shift_date` of the affected shift.
    *   A dedicated worker service or background task consumes these messages.
    *   For each message, the worker constructs the Redis key `availability:team:{team_id}:date:{shift_date}` and executes a `DEL` command on Redis for that key.
3.  **Time-to-Live (TTL) as a Fallback:**
    *   Each cached availability Hash should also have a TTL set, for example, 1 hour (3600 seconds).
    *   This serves as a safety net: if the active invalidation mechanism fails (e.g., message queue outage, worker crash), the cache will eventually expire and be refreshed from the database on the next request. A 1-hour TTL ensures data is at most 1 hour old if active invalidation fails, which is acceptable given the 60-second freshness requirement is for *normal operation*.
    *   The `EXPIRE` command would be used when the cache is initially populated.

**Detailed Flow:**

*   **Database Write:**
    ```
    BEGIN;
    INSERT/UPDATE/DELETE INTO employee_shifts WHERE ...;
    COMMIT;
    PUBLISH_MESSAGE_TO_QUEUE({
        "event_type": "shift_modified",
        "team_id": <affected_team_id>,
        "shift_date": <affected_shift_date>
    });
    ```
*   **Cache Invalidation Worker:**
    ```python
    # Worker process consuming from message queue
    def process_shift_modified_event(message):
        team_id = message["team_id"]
        shift_date = message["shift_date"]
        redis_key = f"availability:team:{team_id}:date:{shift_date}"
        redis_client.delete(redis_key)
        logger.info(f"Invalidated Redis key: {redis_key}")
    ```

This approach balances immediate invalidation with resilience and performance. The 60-second freshness requirement is met by the asynchronous invalidation worker, which should process messages much faster than that.

    all_availability = {}

    while current_date <= end_date:
        cache_key = f"availability:team:{team_id}:date:{current_date.isoformat()}"

        cached_data = redis_client.hgetall(cache_key)

            # Decode byte strings to Python strings/objects

                field.decode('utf-8').split(':')[1]: json.loads(value.decode('utf-8'))
                for field, value in cached_data.items()

            print(f"Cache HIT for {cache_key}")

### Going Further: Cache-Aside, Write-Through, Write-Back

Let's analyze the trade-offs of these caching strategies in the context of the Availability Calendar problem.

**1. Cache-Aside (Lazy Loading)**

*   **Description:** The application is responsible for checking the cache first. If data is present (cache hit), it's returned. If not (cache miss), the application fetches data from the database, returns it to the client, and then writes it to the cache for future requests. Cache invalidation is typically handled by the application explicitly deleting entries.
*   **Implicit Choice:** This is the strategy implicitly chosen in the provided code sketch and described solution.
*   **Pros for this problem:**
    *   **Simplicity:** Easiest to implement. The application logic clearly separates cache interaction from database interaction.
    *   **Data Freshness:** Allows for explicit invalidation (as described in section 2), which is crucial for the 60-second freshness requirement.
    *   **Only Caches Needed Data:** Only data that is actually requested and computed is stored in the cache, avoiding caching unused data. This is good for the "whole month at a time" scenario where not all months are viewed equally.
*   **Cons for this problem:**
    *   **Initial Latency:** The first request for a specific team's calendar for a given day will always be a cache miss and incur the full 5-8 second database latency. However, subsequent requests will be fast. This is acceptable given the "frequently check" nature.
    *   **Stale Data Window:** There's a small window between a database write and the cache invalidation message being processed where the cache might serve stale data. The asynchronous invalidation mechanism minimizes this window to seconds, satisfying the 60-second requirement.
*   **Why it's most appropriate:** The explicit invalidation mechanism (asynchronous `DEL` on `shift_modified` events) combined with a fallback TTL directly addresses the 60-second data freshness requirement. Its simplicity and control over cache content make it a good fit. The "read-heavy" nature benefits greatly from caching, and the occasional initial latency for a new day is a small price to pay for overall performance improvement.

**2. Write-Through**

*   **Description:** Data is written simultaneously to both the cache and the database. The application writes to the cache, and the cache layer (or the application) ensures the data is also written to the database before acknowledging the write operation as complete. Reads are typically from the cache.
*   **Trade-offs for this problem:**
    *   **Pros:**
        *   **Always Fresh Cache on Write:** The cache is always consistent with the database *after* a write operation completes.
        *   **Simpler Read Logic:** Reads are always from the cache, no need for cache-miss fallback.
    *   **Cons:**
        *   **Write Latency:** All write operations (creating/updating/deleting shifts) would incur the combined latency of writing to both Redis and the database. This adds latency to the critical path of shift management, which is undesirable.
        *   **Complexity:** Requires the application to manage two write operations (or a specialized cache layer) for every shift modification.
        *   **Granularity Mismatch:** The `employee_shifts` table stores individual shifts. The cache stores *processed availability* for a whole day for a whole team. A single shift modification doesn't directly map to a simple "write" to the availability cache; it requires re-computation of the entire day's availability. This makes a direct write-through impractical for the processed availability data. We would have to re-compute the entire day's availability on every shift change, which is too expensive for a synchronous write.

**3. Write-Back (Write-Behind)**

*   **Description:** Data is written first to the cache, and the write operation is acknowledged as complete immediately. The cache then asynchronously writes the data to the database.
*   **Trade-offs for this problem:**
    *   **Pros:**
        *   **Low Write Latency:** Writes are very fast because they only hit the cache initially.
    *   **Cons:**
        *   **Data Loss Risk:** If the cache fails before data is written to the database, data can be lost. This is generally unacceptable for critical operational data like `employee_shifts`.
        *   **Complexity:** Requires robust mechanisms for ensuring data persistence and handling failures during asynchronous writes.
        *   **Granularity Mismatch:** Similar to write-through, the processed availability data doesn't map well to a direct write-back from the cache. We're not "writing" availability directly; we're computing it from shifts.
        *   **Stale Data:** If the database is the source of truth, and the cache is the primary write target, other systems reading directly from the database might see stale data until the write-back occurs.

**Conclusion:**

The **Cache-Aside** strategy is the most appropriate for this problem.

*   It allows us to cache the *processed* and *aggregated* availability data, which is expensive to compute, rather than just raw shift data.
*   The 60-second freshness requirement is met through explicit, asynchronous invalidation (deleting the cached day's data when a relevant shift changes), combined with a TTL as a safety net.
*   It avoids adding latency to the critical path of creating/updating/deleting shifts, which would be a major drawback of write-through or write-back.
*   While it introduces initial latency for cache misses, this is a minor trade-off given the high read volume and the significant performance gain for subsequent requests.
*   The granularity mismatch between individual shift updates and aggregated availability data makes write-through and write-back impractical or overly complex for this specific caching layer.
