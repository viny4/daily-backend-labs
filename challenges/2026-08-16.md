## Scenario

Your company operates a global payment processing platform. A critical part of the system is recording every transaction in a `transactions` table. This table now contains hundreds of millions of rows, growing by tens of millions monthly, and is projected to reach billions within the year. Each transaction has a `transaction_id` (UUID), `user_id`, `amount`, `currency`, `status` (e.g., `PENDING`, `COMPLETED`, `FAILED`), and a `created_at` timestamp.

A new compliance requirement dictates that **all transactions for a specific `user_id` must be available for immediate lookup (within 100ms) for auditing purposes, regardless of transaction volume or age.** Currently, queries like `SELECT * FROM transactions WHERE user_id = '...' ORDER BY created_at DESC LIMIT 100;` are taking several seconds for high-volume users, and occasionally timing out. The primary database is a PostgreSQL instance, currently running on a very large VM, but it's clear this approach is not sustainable. You've been tasked with proposing a scalable solution.

Constraints:
*   High write throughput: millions of new transactions per hour.
*   Low-latency reads for a single user's transactions (audit queries).
*   Data integrity: transactions must not be lost.
*   Scalability: the solution must accommodate projected growth to billions of transactions.
*   Cost-effectiveness: avoid over-provisioning expensive resources.
*   Existing schema cannot be fundamentally altered without significant re-architecture of the entire payment system, but new tables or services are acceptable.

## Requirements

Propose a high-level architectural change to address the performance of user-specific transaction lookups. Focus on how to efficiently store and retrieve transactions for a given `user_id` at scale, while accommodating the high write volume.

## Deliverables

1.  A brief description of the chosen architectural pattern or technique to scale transaction storage and retrieval for user-specific queries.
2.  Explain how new transactions are written into this scaled system.
3.  Explain how an audit query for a specific `user_id` would retrieve its transactions.
4.  Identify one significant operational challenge introduced by your proposed solution.

## Going further

How would your solution handle a scenario where a malicious actor or a bug rapidly generates millions of transactions for a single `user_id`? What potential issues could arise, and how might your design mitigate them?

## Worked answer

### 1. Chosen Architectural Pattern: Sharding (Horizontal Partitioning)

The core problem is that a single PostgreSQL instance cannot efficiently handle billions of rows for user-specific lookups, especially with high write throughput. The chosen architectural pattern is **sharding (horizontal partitioning)** based on `user_id`. This distributes the `transactions` data across multiple independent database instances (shards), each responsible for a subset of users.

By sharding on `user_id`, all transactions for a given user will reside on the same shard. This allows user-specific queries to be routed to a single, smaller database instance, drastically reducing the amount of data scanned and improving query performance.

We will introduce a new service, the **Transaction Shard Router**, to manage the mapping of `user_id` to its corresponding shard and to route read/write requests.

### 2. How New Transactions are Written

1.  **Original Transaction Service (Writer):** When a new transaction is initiated, the original payment processing service (which currently writes to the monolithic PostgreSQL) will now send the transaction data to the `Transaction Shard Router` service.

2.  **Transaction Shard Router:**
    *   It receives the new transaction, which includes the `user_id`.
    *   It determines the target shard for this `user_id` using a consistent hashing algorithm (e.g., `hash(user_id) % N`, where `N` is the number of shards). Alternatively, a lookup table (e.g., `user_id_to_shard_map`) could be used for more flexible shard assignments, though this adds complexity. For simplicity and scalability, consistent hashing is preferred initially.
    *   It then forwards the transaction data to the designated shard database.

3.  **Shard Database:** Each shard database is a separate PostgreSQL instance. It will have its own `transactions` table.

    ```sql
    -- Schema for each shard database
    CREATE TABLE transactions (
        transaction_id UUID PRIMARY KEY,
        user_id UUID NOT NULL,
        amount NUMERIC(19, 4) NOT NULL,
        currency VARCHAR(3) NOT NULL,
        status VARCHAR(20) NOT NULL, -- e.g., 'PENDING', 'COMPLETED', 'FAILED'
        created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP NOT NULL
    );

    -- Index for efficient user-specific lookups
    CREATE INDEX idx_transactions_user_id_created_at ON transactions (user_id, created_at DESC);
    ```

    The `idx_transactions_user_id_created_at` index is crucial. Since all transactions for a `user_id` are on the same shard, this index allows very fast retrieval of a user's transactions, ordered by `created_at` descending, directly on that shard.

    The write process is:
    *   Payment Service -> Transaction Shard Router -> Shard Database (INSERT)

    For data integrity, the write to the shard database should be atomic. If the router fails to write to the shard, it should retry or queue the transaction for later processing (e.g., using a message queue like Kafka) to ensure durability. The payment service would await an acknowledgment from the router that the transaction has been durably stored.

### 3. How an Audit Query Retrieves Transactions

1.  **Audit Service (Reader):** When an audit query for a specific `user_id` comes in, it is directed to the `Transaction Shard Router`.

2.  **Transaction Shard Router:**
    *   It receives the `user_id` from the audit query.
    *   It uses the same consistent hashing algorithm (or lookup table) as the write path to determine the target shard for that `user_id`.
    *   It constructs the SQL query:
        ```sql
        SELECT transaction_id, user_id, amount, currency, status, created_at
        FROM transactions
        WHERE user_id = '...'
        ORDER BY created_at DESC
        LIMIT 100;
        ```
    *   It sends this query to the identified shard database.

3.  **Shard Database:** The designated shard database executes the query. Due to the `idx_transactions_user_id_created_at` index and the fact that the query only targets a subset of data on a single, smaller database, the query will be very fast (within 100ms).

4.  **Transaction Shard Router:** The router receives the results from the shard database and returns them to the Audit Service.

### 4. Significant Operational Challenge: Resharding

A significant operational challenge introduced by sharding is **resharding**. As the system grows, or if data distribution becomes uneven (hot spots), we may need to:
*   Add more shards.
*   Rebalance data across existing shards.

Resharding involves:
1.  **Creating new shards.**
2.  **Migrating data:** Moving transactions for certain `user_id`s from old shards to new shards. This is a complex process that must be done without downtime and without data loss. It typically involves:
    *   A "dual-write" phase where new transactions for migrating users are written to both old and new shards.
    *   A "backfill" phase where historical data for migrating users is copied from old to new shards.
    *   A "cutover" phase where the `Transaction Shard Router` updates its mapping for the migrating users to point exclusively to the new shards.
3.  **Updating the Shard Router's logic:** The consistent hashing function or lookup table needs to be updated to reflect the new shard topology.

This process is resource-intensive, requires careful orchestration, and introduces potential for data inconsistencies if not handled meticulously. It also adds significant complexity to monitoring and debugging, as a single logical database is now spread across many physical instances.

### Going Further: Malicious Actor/Bug Generating Millions of Transactions for a Single `user_id`

If a malicious actor or a bug rapidly generates millions of transactions for a single `user_id`, this would create a **"hot shard"** or **"hot user"** problem.

**Potential Issues:**

1.  **Single Shard Overload:** All transactions for that `user_id` would be directed to a single shard. This shard would experience:
    *   **High write load:** Millions of `INSERT`s, potentially saturating CPU, I/O, and network resources on that specific database instance.
    *   **High read load:** Audit queries for this user would still hit this shard, but the sheer volume of data for that user on that shard (even with an index) could degrade performance.
    *   **Disk space exhaustion:** The single shard's disk could fill up rapidly.
    *   **Impact on other users:** While other shards remain unaffected, other users whose data resides on the *same hot shard* would also experience degraded performance due to resource contention.

2.  **Shard Router Bottleneck (less likely for a single user):** The `Transaction Shard Router` might become a bottleneck if it's not designed to handle the routing rate for such an extreme spike, though its primary job is routing, not data storage.

**Mitigation in this Design:**

1.  **Rate Limiting at the Application Layer:** The most effective first line of defense is to implement rate limiting *before* transactions even reach the `Transaction Shard Router`. This should be done at the payment processing service level, per `user_id`. For example, allow only N transactions per minute per user. This prevents the hot user problem from even impacting the sharded database layer.

    ```yaml
    # Example pseudo-config for a rate limiter service
    rate_limits:
      transaction_creation:
        per_user:
          limit: 100 # transactions
          window: 60s # per minute
          action: REJECT # or THROTTLE
    ```

2.  **Shard Monitoring and Alerting:** Implement robust monitoring on each shard for metrics like CPU utilization, I/O operations, disk space, and query latency. Automated alerts should trigger if any shard shows signs of becoming a hot spot.

3.  **Dynamic Shard Rebalancing (Complex):** For extreme cases where a user genuinely has an exceptionally high volume of legitimate transactions (e.g., a major corporate client), the sharding strategy might need to adapt.
    *   **Sub-sharding:** A single `user_id` could potentially be further sharded by `created_at` or a derived key, but this complicates user-specific lookups as they would then need to query multiple sub-shards. This is generally avoided unless absolutely necessary.
    *   **Dedicated Shard:** For extremely high-volume users, they could be manually assigned to their own dedicated shard, or even a cluster of shards, effectively isolating their load. This requires a more sophisticated shard router that can handle exceptions to the consistent hashing rule.

4.  **Database-level Protections:**
    *   **Resource Governors:** PostgreSQL has some capabilities for resource management, but they are generally not designed for preventing a single `user_id` from overwhelming an entire instance.
    *   **Disk Quotas:** While not directly preventing performance degradation, disk quotas could prevent a single hot shard from running out of disk space entirely, forcing intervention.

The primary mitigation strategy should be proactive rate limiting at the application layer. If a hot user still emerges due to legitimate high volume, the monitoring and the ability to manually rebalance (or dedicate resources) become critical. Without rate limiting, even a sharded system can be brought down by a single abusive user or bug.
