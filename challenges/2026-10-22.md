Your team maintains the backend for a rapidly growing online collaboration platform. A core feature allows users to upload and share `documents` within `workspaces`. A single workspace can contain thousands of documents, and a user can be a member of hundreds of workspaces.

Recently, the `documents` table in your PostgreSQL database has grown to over 500 million rows. Each `document` record includes metadata like `id`, `workspace_id`, `owner_id`, `created_at`, `updated_at`, `name`, `type`, `size_bytes`, and a pointer to its storage location (e.g., S3 key).

The problem: The "My Documents" page, which shows all documents owned by the currently logged-in user across *all* their workspaces, is now unacceptably slow. This query often involves joining `documents` with `workspace_members` (to find all workspaces a user belongs to) and then filtering by `owner_id`. This query pattern frequently results in full table scans or very inefficient index usage, leading to query times of 10-20 seconds for users with many documents or workspaces.

The product team wants this page to load within 2 seconds. The database is currently a single large PostgreSQL instance (AWS RDS `db.r6g.xlarge`).

## Requirements

Design a solution to drastically improve the performance of the "My Documents" page. The solution must handle:

-   **High read volume:** The "My Documents" page is frequently accessed by active users.
-   **Data consistency:** Users expect to see their most recent documents. Eventually consistent data is acceptable for documents created within the last few minutes, but stale data for hours is not.
-   **Scalability:** The solution should be able to handle future growth to billions of documents and millions of users without proportional performance degradation.
-   **Operational complexity:** Keep the operational overhead for your team manageable. Avoid introducing entirely new infrastructure types if possible, favoring existing technologies (PostgreSQL, Redis, S3, Python/Django, Node.js/TypeScript).

**Data Flow for "My Documents" Page:**

1.  User's browser sends a request to the backend for the "My Documents" page.
2.  Load Balancer forwards the request to a Web Backend instance.
3.  The Web Backend constructs a query to Elasticsearch, asking for documents owned by the current user, possibly with pagination and sorting.
4.  Elasticsearch returns a list of document IDs and relevant metadata (e.g., `name`, `type`, `updated_at`).
5.  The Web Backend may optionally fetch additional, less frequently accessed, or highly consistent data for these documents from PostgreSQL (e.g., the exact S3 key if it's not stored in Elasticsearch, or to verify permissions). For the "My Documents" page, the data from Elasticsearch should be sufficient.
6.  The Web Backend aggregates the data and renders the "My Documents" page.

**Data Flow for Document Writes/Updates:**

7.  Any changes (creates, updates, deletes) to documents in PostgreSQL are captured by a Change Data Capture (CDC) mechanism (e.g., Debezium, or a custom trigger-based solution).
8.  The CDC pipeline processes these changes and pushes them to Elasticsearch, ensuring the index is kept up-to-date.

### 2. Key technologies and database schema changes

The core of the solution involves offloading the "My Documents" query from the primary PostgreSQL database to a specialized search index, specifically Elasticsearch.

**Key Technologies:**

*   **Elasticsearch (or Apache Solr):** A distributed, open-source search and analytics engine. It excels at full-text search, complex filtering, and aggregation over large datasets. It will store a denormalized view of document metadata optimized for the "My Documents" query.
*   **Change Data Capture (CDC) mechanism:** To keep Elasticsearch synchronized with PostgreSQL. Options include:
    *   **Debezium:** An open-source distributed platform that turns your existing databases into event streams, using PostgreSQL's logical decoding feature. This is generally preferred for robustness and scalability.
    *   **Custom application-level events:** The Django application could explicitly publish events to a message queue (e.g., Kafka, RabbitMQ) upon document changes, which a separate indexing service consumes.
    *   **PostgreSQL Triggers + Queue:** A less scalable but simpler approach for initial implementation, where database triggers write change events to a dedicated table, which an async job then processes.
*   **Kafka (or RabbitMQ/AWS SQS):** A distributed streaming platform. If using Debezium or custom application-level events, Kafka would serve as the message broker for change events before they are consumed by the indexing service.

**Database Schema Changes (PostgreSQL):**

No direct schema changes are required for the `documents` or `workspace_members` tables themselves. The primary database remains the source of truth.

However, to enable efficient CDC using logical decoding (e.g., with Debezium), the PostgreSQL instance needs to be configured:

*   `wal_level = logical`
*   `max_replication_slots = N` (sufficient for Debezium and other replicas)
*   `max_wal_senders = N` (sufficient for Debezium and other replicas)

**Elasticsearch Index Schema:**

A new Elasticsearch index, e.g., `documents_by_owner`, would be created. This index will store a denormalized view of the `documents` table, specifically optimized for the "My Documents" query.

```json
PUT /documents_by_owner
{
  "settings": {
    "number_of_shards": 5,
    "number_of_replicas": 1
  },
  "mappings": {
    "properties": {
      "document_id": { "type": "keyword" },     // Original PostgreSQL document ID
      "workspace_id": { "type": "keyword" },    // For potential future filtering
      "owner_id": { "type": "keyword" },        // CRITICAL for "My Documents" query
      "name": { "type": "text" },               // Document name, searchable
      "type": { "type": "keyword" },            // e.g., 'pdf', 'docx', 'image'
      "size_bytes": { "type": "long" },
      "created_at": { "type": "date" },
      "updated_at": { "type": "date" },         // For sorting
      "s3_key": { "type": "keyword", "index": false } // Stored but not indexed for search
    }
  }
}
```

**How this addresses the bottleneck:**

1.  **Dedicated Index for Specific Query:** Elasticsearch is designed for fast, complex queries over large datasets. By creating an index specifically for `owner_id`, `updated_at`, and `name`, the "My Documents" query becomes a highly efficient lookup within Elasticsearch, avoiding expensive joins and full table scans on PostgreSQL.
2.  **Scalability:** Elasticsearch is horizontally scalable. As the number of documents or users grows, more nodes can be added to the Elasticsearch cluster to distribute the data and query load.
3.  **Read Performance:** Queries against Elasticsearch are typically much faster than complex relational queries on a large, transactional database, especially for filtering and sorting.
4.  **Decoupling:** The read load for "My Documents" is completely offloaded from the primary PostgreSQL database, freeing it up for transactional writes and other complex queries.
5.  **Eventually Consistent (Acceptable):** The CDC pipeline introduces a small delay (seconds to a few minutes) between a write in PostgreSQL and its appearance in Elasticsearch. This is explicitly stated as acceptable for this use case.

### 3. Django/Python backend interaction

The existing Django/Python backend would be modified to interact with Elasticsearch for the "My Documents" page, while continuing to use PostgreSQL as the source of truth for all write operations and other data-intensive reads.

**New Dependencies:**

*   `elasticsearch-dsl` or `elasticsearch-py` library for Python.

**Example Django View (`views.py`):**

```python
from django.conf import settings
from django.shortcuts import render
from django.contrib.auth.decorators import login_required
from elasticsearch_dsl import Search, Q
from elasticsearch import Elasticsearch

# Initialize Elasticsearch client (e.g., in settings.py or a dedicated client module)
es_client = Elasticsearch(
    hosts=[{'host': settings.ELASTICSEARCH_HOST, 'port': settings.ELASTICSEARCH_PORT}],
    timeout=30
)

@login_required
def my_documents_view(request):
    current_user_id = str(request.user.id) # Ensure ID is string if that's how it's indexed
    page = int(request.GET.get('page', 1))
    page_size = 20
    start_from = (page - 1) * page_size

    # Build Elasticsearch query
    s = Search(using=es_client, index='documents_by_owner') \
        .query('match', owner_id=current_user_id) \
        .sort('-updated_at') \
        .extra(size=page_size, from_=start_from)

    # Add optional search/filter parameters
    search_query = request.GET.get('q')
    if search_query:
        s = s.query('multi_match', query=search_query, fields=['name'])

    try:
        response = s.execute()
    except Exception as e:
        # Log error, potentially fall back to PostgreSQL or show error message
        print(f"Elasticsearch query failed: {e}")
        # Fallback: This would be slow, but could be a last resort for critical failure
        # documents = Document.objects.filter(owner=request.user).order_by('-updated_at')
        # ... handle pagination for fallback ...
        return render(request, 'my_documents_error.html', {'error_message': 'Could not load documents.'})

    documents_data = []
    for hit in response.hits:
        documents_data.append({
            'id': hit.document_id,
            'name': hit.name,
            'type': hit.type,
            'size_bytes': hit.size_bytes,
            'created_at': hit.created_at,
            'updated_at': hit.updated_at,
            # S3 key might be fetched from PostgreSQL if not in ES, or if ES data is considered less authoritative
            # 's3_key': hit.s3_key if 's3_key' in hit else get_s3_key_from_postgres(hit.document_id)
        })

    total_hits = response.hits.total.value if hasattr(response.hits.total, 'value') else response.hits.total
    num_pages = (total_hits + page_size - 1) // page_size

    context = {
        'documents': documents_data,
        'current_page': page,
        'total_pages': num_pages,
        'has_next': page < num_pages,
        'has_previous': page > 1,
        'search_query': search_query,
    }
    return render(request, 'my_documents.html', context)
```

**Indexing Service (separate application or part of existing workers):**

This service would consume messages from Kafka (or other message queue) and update Elasticsearch.

```python
# Example of an indexing worker (simplified)
from elasticsearch import Elasticsearch
from kafka import KafkaConsumer
import json
import os

es_client = Elasticsearch(
    hosts=[{'host': os.environ.get('ELASTICSEARCH_HOST', 'localhost'), 'port': 9200}],
    timeout=30
)
consumer = KafkaConsumer(
    'document_changes',
    bootstrap_servers=[os.environ.get('KAFKA_BOOTSTRAP_SERVERS', 'localhost:9092')],
    auto_offset_reset='earliest',
    enable_auto_commit=True,
    group_id='document-indexer-group',
    value_deserializer=lambda x: json.loads(x.decode('utf-8'))
)

def process_document_change(message):
    payload = message.value
    operation = payload.get('op') # e.g., 'c' for create, 'u' for update, 'd' for delete

    if operation == 'c' or operation == 'u':
        # Assuming Debezium-like payload structure with 'after' for new/updated state
        document_data = payload.get('after')
        if not document_data:
            return # Malformed message

        doc_id = str(document_data['id'])
        # Construct document for Elasticsearch
        es_doc = {
            'document_id': doc_id,
            'workspace_id': str(document_data['workspace_id']),
            'owner_id': str(document_data['owner_id']),
            'name': document_data['name'],
            'type': document_data['type'],
            'size_bytes': document_data['size_bytes'],
            'created_at': document_data['created_at'],
            'updated_at': document_data['updated_at'],
            's3_key': document_data['s3_key']
        }
        es_client.index(index='documents_by_owner', id=doc_id, document=es_doc)
        print(f"Indexed/Updated document {doc_id}")
    elif operation == 'd':
        # Assuming Debezium-like payload structure with 'before' for deleted state
        document_data = payload.get('before')
        if not document_data:
            return
        doc_id = str(document_data['id'])
        es_client.delete(index='documents_by_owner', id=doc_id)
        print(f"Deleted document {doc_id}")

for message in consumer:
    process_document_change(message)
```

### 4. Potential failure modes and mitigations

**1. Data Inconsistency between PostgreSQL and Elasticsearch:**

*   **Failure Mode:** The CDC pipeline fails (e.g., Debezium connector crashes, Kafka is down, indexing service has bugs), leading to Elasticsearch becoming significantly out of sync with PostgreSQL. Users see old or missing documents on "My Documents" page.
*   **Mitigation:**
    *   **Monitoring and Alerting:** Implement robust monitoring on the CDC pipeline (Debezium, Kafka, indexing service). Track metrics like message lag, consumer group offsets, and Elasticsearch indexing errors. Alert on any significant delays or failures.
    *   **Idempotent Indexing:** Ensure the indexing service is idempotent. If a message is processed multiple times (e.g., due to retries), it should not corrupt the index. Elasticsearch's `index` operation with an `id` is inherently idempotent for updates.
    *   **Reconciliation Job:** Implement a periodic (e.g., nightly or weekly) background job that performs a full reconciliation. It would compare a subset or all documents in PostgreSQL with their corresponding entries in Elasticsearch, identifying and correcting discrepancies. This can be done by querying PostgreSQL for `updated_at` ranges and comparing with Elasticsearch, or by re-indexing documents that are known to be out of sync.
    *   **Circuit Breaker/Fallback:** In extreme cases of detected high inconsistency, the "My Documents" page could temporarily fall back to querying PostgreSQL directly (with appropriate warnings about slow performance) or display a "data temporarily unavailable" message.

**2. Elasticsearch Cluster Failure/Performance Degradation:**

*   **Failure Mode:** The Elasticsearch cluster experiences an outage, becomes unresponsive, or its performance degrades significantly (e.g., due to high load, disk issues, or bad queries), making the "My Documents" page slow or unavailable.
*   **Mitigation:**
    *   **High Availability:** Deploy Elasticsearch in a highly available configuration with multiple nodes, replica shards, and across different availability zones (if using cloud providers). This ensures that if one node fails, replicas can take over.
    *   **Resource Provisioning and Scaling:** Properly size the Elasticsearch cluster based on expected data volume and query load. Continuously monitor CPU, memory, disk I/O, and JVM heap usage. Scale out the cluster (add more nodes) as data or query volume grows.
    *   **Query Optimization:** Ensure that queries sent to Elasticsearch are efficient. Avoid expensive aggregations or wildcards on large datasets if not strictly necessary. Use `_source` filtering to retrieve only necessary fields.
    *   **Circuit Breaker/Fallback:** Implement a circuit breaker pattern in the Django backend. If Elasticsearch queries consistently time out or fail, temporarily switch to a fallback mechanism (e.g., showing a cached version of the user's documents, or a simplified view from PostgreSQL if possible, or an error message). This prevents cascading failures and ensures the primary database isn't overwhelmed by fallback attempts.
    *   **Dedicated Infrastructure:** Run Elasticsearch on dedicated infrastructure, separate from the main PostgreSQL database, to prevent resource contention.

### Going further

The proposed solution makes several trade-offs between read latency, write latency, data consistency, and operational complexity.

**Read Latency (Prioritized):**
*   **Trade-off:** Significantly improved read latency for the "My Documents" page.
*   **Why:** The core problem statement is "unacceptably slow" read times (10-20 seconds) for this critical user-facing page, with a target of 2 seconds. Moving this query to Elasticsearch, which is optimized for fast filtering and sorting over large datasets, directly addresses this. The query now hits a specialized index rather than performing expensive joins on a transactional database.

**Write Latency (Slightly Increased/Unchanged):**
*   **Trade-off:** Write latency to PostgreSQL remains largely unchanged. However, there's an *additional* eventual write to Elasticsearch.
*   **Why:** The primary write path (user creates/updates a document) still goes directly to PostgreSQL, which is the source of truth and optimized for transactional integrity. The subsequent indexing into Elasticsearch happens asynchronously via the CDC pipeline. This means the user's immediate "save" action isn't blocked by Elasticsearch indexing, maintaining good write responsiveness for the core document creation/editing flow. The slight increase in overall system write load (due to CDC and indexing) is distributed and asynchronous.

**Data Consistency (Relaxed to Eventually Consistent):**
*   **Trade-off:** Strict immediate consistency for "My Documents" is sacrificed for eventual consistency.
*   **Why:** The requirement states, "Eventually consistent data is acceptable for documents created within the last few minutes, but stale data for hours is not." This is a crucial allowance. By accepting eventual consistency (typically seconds to a few minutes of lag), we gain immense read scalability and performance. If strict, immediate consistency were required, we would likely need to stick with PostgreSQL and explore more complex sharding or replication strategies, which would be harder to scale for this specific query pattern. The CDC pipeline is designed to keep this lag minimal.

**Operational Complexity (Increased):**
*   **Trade-off:** Operational complexity increases due to the introduction of new infrastructure (Elasticsearch, Kafka/CDC) and the need to manage data synchronization.
*   **Why:** This is the biggest trade-off. We are moving from a single database type to a multi-database system with an asynchronous data pipeline. This means:
    *   **More components to monitor:** PostgreSQL, Debezium, Kafka, Indexing Service, Elasticsearch.
    *   **New failure modes:** Data inconsistency, pipeline failures, Elasticsearch cluster management.
    *   **New expertise required:** The team needs to learn how to operate and troubleshoot Elasticsearch and Kafka.
    *   **Increased infrastructure cost:** Running and maintaining these additional services.
    Despite this, the increase in complexity is deemed necessary and manageable given the severe performance bottleneck and the scalability requirements. Elasticsearch and Kafka are well-established, widely adopted technologies with strong community support and cloud-managed service options (e.g., AWS OpenSearch, MSK), which can help mitigate some of the operational burden compared to bespoke solutions. The alternative (sharding PostgreSQL for this specific query) would likely introduce comparable, if not greater, operational complexity without the same level of read performance benefits for arbitrary filtering/sorting.

**Prioritization Summary:**

The prioritization was driven by the explicit problem statement: **drastically improve read performance (target < 2 seconds) for a high-volume, user-facing page, while accommodating future growth to billions of documents, and accepting eventual consistency for recent data.**

*   **Read latency** was the highest priority because it directly addresses the user experience problem.
*   **Scalability** was next, as the platform is "rapidly growing." Elasticsearch provides horizontal scalability for reads.
*   **Data consistency** was a pragmatic compromise, leveraging the stated acceptance of eventual consistency to enable the performance gains.
*   **Operational complexity** was accepted as a necessary cost to achieve the above, mitigated by using mature technologies and cloud-managed services where possible. The alternative of trying to scale PostgreSQL for this specific query pattern would likely lead to even greater complexity or insufficient performance gains.
