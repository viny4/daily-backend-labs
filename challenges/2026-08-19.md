## Scenario

Your team maintains a popular multi-tenant SaaS platform where users can create and manage dashboards. Each dashboard can contain many widgets, and each widget displays data derived from various sources. A frequently accessed feature is the "dashboard overview" endpoint (`GET /api/v1/users/{user_id}/dashboards`), which lists all dashboards for a given user, along with a summary count of active widgets for each.

The `dashboards` table has grown to tens of millions of rows across all tenants, and the `widgets` table is even larger. The current implementation fetches all dashboards for the user and then, for each dashboard, performs a subquery to count its active widgets. This approach has led to N+1 query issues and, consequently, response times exceeding 5 seconds for users with many dashboards, especially during peak hours. The database is showing significant load from these queries.

The active widget count is not critical to be real-time; a staleness of up to 5 minutes is acceptable for this overview endpoint.

## Requirements

Optimize the `GET /api/v1/users/{user_id}/dashboards` endpoint to consistently respond within 500ms, even for users with hundreds of dashboards, while significantly reducing the database load. You should leverage Redis for caching the active widget count per dashboard.

Constraints:
* The solution must be robust against Redis failures (e.g., connection issues, unavailability) without impacting the core functionality of retrieving dashboards.
* It needs to handle concurrent updates to widget counts without race conditions leading to incorrect data.
* The system is multi-tenant, so user-specific data must remain isolated and correctly attributed.
* The cache must be invalidated or refreshed within the acceptable staleness window.

## Worked answer

### 1. High-level design description

To address the N+1 query issue and reduce database load, we will introduce a Redis cache layer specifically for storing the active widget counts per dashboard. When the `GET /api/v1/users/{user_id}/dashboards` endpoint is called, it will first fetch the user's dashboards from the database. For each dashboard, it will attempt to retrieve its active widget count from Redis. If the count is present in Redis and not expired, it will be used directly. If it's missing or expired, the system will fall back to calculating the count from the database and then asynchronously update Redis. A background worker will periodically refresh all active widget counts in Redis to ensure data freshness within the 5-minute staleness window. This design significantly offloads the database by serving most widget count requests from Redis, while the asynchronous update mechanism prevents read requests from blocking on cache misses.

### 2. Redis key structure

We will use a Redis Hash data structure to store the active widget counts. A single hash will store all dashboard widget counts for a specific user, keyed by the dashboard ID. This approach is efficient for retrieving multiple counts for a user and allows for easy expiration of all counts for a user if needed (though we'll primarily use per-field expiration within the hash).

The key structure will be:

```
dashboard_widget_counts:{user_id}
```

Within this hash, each field will be the `dashboard_id`, and its value will be the active widget count. To manage staleness, we will store not just the count, but a JSON string containing both the `count` and a `timestamp` of when it was last updated.

Example:

```json
// Redis key: dashboard_widget_counts:123
{
  "456": "{\"count\": 10, \"timestamp\": 1678886400}",
  "457": "{\"count\": 5, \"timestamp\": 1678886400}",
  "458": "{\"count\": 12, \"timestamp\": 1678886400}"
}
```

Where:
*   `user_id`: The unique identifier for the user (e.g., `123`).
*   `dashboard_id`: The unique identifier for the dashboard (e.g., `456`).
*   `count`: The number of active widgets for that dashboard.
*   `timestamp`: Unix timestamp (seconds since epoch) indicating when this count was last calculated and stored in Redis.

Using a hash per user allows us to retrieve all counts for a user with a single `HGETALL` command, which is more efficient than `N` individual `GET` commands. Storing the timestamp within the value allows us to implement a "stale-while-revalidate" pattern without relying on Redis's built-in `EXPIRE` on the hash itself (which would expire all counts for a user at once).

### 3. Cache invalidation/refresh strategy

Our strategy combines a proactive background refresh with a reactive "stale-while-revalidate" mechanism on read, ensuring the 5-minute staleness requirement is met.

1.  **Proactive Background Refresh (Primary Strategy):**
    *   A dedicated background worker (e.g., a cron job, a message queue consumer, or a scheduled task) will run every 2-3 minutes.
    *   This worker will iterate through all active users (or a subset, processing in batches) and for each user, it will:
        *   Fetch all their dashboards from the database.
        *   For each dashboard, it will perform a single, optimized database query to count its active widgets. A single query using `GROUP BY dashboard_id` can efficiently calculate counts for multiple dashboards at once.
        *   Update the `dashboard_widget_counts:{user_id}` hash in Redis with the new counts and the current timestamp. This update should use `HMSET` or `HSET` to update multiple fields atomically if possible, or individual `HSET` commands.
    *   This ensures that even if a dashboard count is never read, it will be refreshed within 2-3 minutes, well within the 5-minute staleness window.

2.  **Reactive "Stale-While-Revalidate" on Read (Fallback/Immediate Freshness):**
    *   When the `GET /api/v1/users/{user_id}/dashboards` endpoint is accessed:
        *   It retrieves the `dashboard_widget_counts:{user_id}` hash from Redis using `HGETALL`.
        *   For each dashboard, it checks the `timestamp` stored in the Redis value.
        *   If the `timestamp` is older than 5 minutes (e.g., `current_time - timestamp > 300` seconds), the count is considered stale.
        *   If stale, the endpoint will:
            *   Serve the stale count immediately to the user (meeting the 500ms requirement).
            *   **Asynchronously** trigger an update for that specific dashboard's widget count. This can be done by sending a message to a low-priority queue (e.g., Kafka, RabbitMQ) or by spawning a non-blocking background task to recalculate the count from the database and update Redis. This prevents the user request from being blocked by the database query.

3.  **Handling Widget Updates (Eventual Consistency):**
    *   When a widget is created, updated (e.g., activated/deactivated), or deleted, the system will **not** immediately invalidate or update the Redis cache. The 5-minute staleness window allows us to rely on the proactive background refresh and reactive stale-while-revalidate for eventual consistency.
    *   If immediate consistency were required for critical operations, we would add logic to publish a message to a queue on widget state changes, triggering an immediate recalculation for the affected dashboard. However, for an "overview" endpoint with acceptable staleness, this complexity is unnecessary.

**Robustness against Redis failures:**
*   If Redis is unavailable or returns an error, the `GET /api/v1/users/{user_id}/dashboards` endpoint will fall back to querying the database for all active widget counts for the user's dashboards. This will reintroduce the N+1 problem temporarily but ensures the core functionality remains available. The system should log these Redis errors for monitoring.
*   The asynchronous update mechanism ensures that even if the Redis update fails, the user request is not impacted.

**Handling concurrent updates:**
*   Redis `HSET` operations are atomic for a single field. When the background worker or the asynchronous update task writes a new count, it overwrites the previous value. Since we are storing the count and timestamp together, the entire value is updated atomically.
*   Race conditions where two processes try to update the same dashboard's count simultaneously will result in one update overwriting the other. This is acceptable because the counts are derived from the database (the source of truth) and will eventually converge to the correct value due to the periodic refreshes. The `timestamp` helps us determine which value is "fresher" if needed, but for this scenario, the latest write wins is sufficient.

    cached_counts: Dict[str, Any] = {}
    try:
        # HGETALL returns a dict of field-value pairs
        # Values are bytes, need to decode
        raw_cached_data = redis_client.hgetall(f"dashboard_widget_counts:{user_id}")
        for dashboard_id_bytes, data_bytes in raw_cached_data.items():

            widget_count = cached_data['count']

            dashboards_to_revalidate_async.append(dashboard_id)
        else:
            # Cache miss - need to get from DB. Add to a list for batch query.

        results.append(DashboardSummary(id=dashboard_id, name=dashboard_name, widget_count=widget_count))

    # If there were cache misses or stale entries that need immediate DB fallback
    if dashboards_to_recalculate_db:
        # Perform a single batch DB query for all missing/stale counts
        print(f"Cache miss/stale for {len(dashboards_to_recalculate_db)} dashboards. Querying DB...")
        db_calculated_counts = calculate_active_widget_counts_from_db_batch(user_id, dashboards_to_recalculate_db)
        
        # Update results with actual counts and trigger async Redis update
        for summary in results:
            if summary.id in dashboards_to_recalculate_db:
                actual_count = db_calculated_counts.get(summary.id, 0)
                summary.widget_count = actual_count

                dashboards_to_revalidate_async.append(summary.id)

        background_task_queue.enqueue(

1.  **`get_dashboard_overview(user_id)`:** This is the main endpoint logic.
    *   It first fetches basic dashboard metadata for the user from the database. This query is assumed to be efficient (e.g., `SELECT id, name FROM dashboards WHERE user_id = :user_id`).
    *   It then attempts a single `HGETALL` Redis command to fetch all cached widget counts for that user. This is efficient for users with many dashboards.
    *   It iterates through the dashboards:
        *   If a count is found in Redis and is not stale (within `CACHE_STALENESS_SECONDS`), it's used directly.
        *   If a count is found but is stale, it's used directly (stale-while-revalidate), but the dashboard ID is added to `dashboards_to_revalidate_async` to trigger an asynchronous refresh.
        *   If a count is not found (cache miss), the dashboard ID is added to `dashboards_to_recalculate_db`.
    *   After the loop, if there were any cache misses (`dashboards_to_recalculate_db`), a single batch database query (`calculate_active_widget_counts_from_db_batch`) is performed to get all missing counts efficiently.     *   Finally, if any dashboards need revalidation or initial caching (`dashboards_to_revalidate_async`), a background task is enqueued. This ensures the main request thread is not blocked by database queries or Redis writes, maintaining the 500ms response time.
    *   Error handling for Redis operations ensures that database fallback occurs if Redis is unavailable.

2.  **`calculate_active_widget_counts_from_db_batch(user_id, dashboard_ids)`:** This function represents the optimized database query. Instead of N individual subqueries, it performs a single `GROUP BY` query to get counts for multiple dashboards.

    ```sql
    -- Example optimized SQL query for batch calculation
    SELECT
        w.dashboard_id,
        COUNT(w.id) AS active_widget_count
    FROM
        widgets w
    WHERE
        w.dashboard_id IN (SELECT id FROM dashboards WHERE user_id = :user_id AND id IN (:dashboard_ids))
        AND w.is_active = TRUE
    GROUP BY
        w.dashboard_id;
    ```
    This query is efficient because it leverages an index on `widgets.dashboard_id` and `widgets.is_active`.

3.  **`recalculate_and_cache_widget_counts(user_id, dashboard_ids)`:** This is the background task that performs the actual database calculation and Redis update. It's designed to be idempotent and can be triggered by both the frontend endpoint (for immediate revalidation) and the periodic background worker.

4.  **`periodic_full_refresh_worker()`:** This simulates the scheduled job that ensures all active user dashboards are refreshed proactively.

### Going further

#### Trade-offs of using an eventually consistent cache

Using an eventually consistent cache for the active widget count introduces several trade-offs, primarily centered around data freshness versus performance and database load.

**Benefits (why we chose it):**
*   **Significantly reduced database load:** The primary benefit is offloading the database from expensive N+1 queries, especially during peak times. Most requests are served directly from Redis.
*   **Improved response times:** The `GET /api/v1/users/{user_id}/dashboards` endpoint can consistently respond within 500ms, as it avoids blocking on database queries for widget counts.
*   **Scalability:** The system can handle a much higher volume of read requests for dashboard overviews without overwhelming the database.

**Potential Negative User Experiences (NUEs):**

1.  **Stale Data:**
    *   **Scenario:** A user creates a new widget, activates an existing one, or deletes one. They immediately refresh the dashboard overview page.
    *   **NUE:** The widget count displayed for that dashboard might not reflect the change for up to 5 minutes. For example, if they just activated a widget, the count might still show the old number.
    *   **Impact:** Minor annoyance, potential confusion, or a feeling that the system is slow to update. For an "overview" endpoint, this is generally acceptable.

2.  **Inconsistent State Across Views:**
    *   **Scenario:** A user creates a widget, then navigates to the specific dashboard where they just created it (which shows the real-time count). Then they go back to the overview page.
    *   **NUE:** The count on the specific dashboard page is correct, but the count on the overview page is stale.
    *   **Impact:** Confusion and distrust in the data presented by the system.

3.  **Delayed Feedback for Critical Actions (if applicable):**
    *   **Scenario:** If widget counts were used for a more critical purpose (e.g., displaying a "critical alert" based on widget count thresholds), delayed updates could have more severe consequences.
    *   **NUE:** Users might miss critical information or make decisions based on outdated data.
    *   **Impact:** Higher severity, potential business impact. (Less relevant for this specific "overview" scenario, but important to consider generally).

**Mitigation Strategies:**

1.  **Clear Communication:**
    *   **"Last Updated" Timestamp:** Display a small "Last updated X minutes ago" or "Data may be up to 5 minutes old" next to the widget count or at the top of the overview page. This sets user expectations.
    *   **Documentation/Tooltips:** Provide tooltips explaining the data freshness policy.

2.  **User-Initiated Refresh (Manual Override):**
    *   Add a "Refresh Data" button on the dashboard overview page. When clicked, this button could trigger an immediate, synchronous (or high-priority asynchronous) recalculation of widget counts for that user's dashboards, bypassing the cache or forcing an immediate revalidation. This gives power to the user when they need the freshest data.

3.  **Optimistic UI Updates (for specific actions):**
    *   For actions like "activate widget" or "delete widget," if the user is immediately redirected to the dashboard overview, the frontend could optimistically update the displayed count *before* the backend cache is updated. This provides immediate feedback, but the count might revert if the backend update fails or if the user navigates away and comes back before the cache is truly updated. This adds frontend complexity.

4.  **Faster Background Refresh for Active Users:**
    *   While the general refresh is 2-3 minutes, the background worker could prioritize users who have been recently active, refreshing their data more frequently.

5.  **Event-Driven Cache Invalidation (for higher consistency needs):**
    *   If the 5-minute staleness becomes too long for certain critical actions, introduce event-driven invalidation. When a widget's status changes, publish an event to a message queue. A consumer for this queue would then immediately trigger a recalculation and update for the affected dashboard's count in Redis. This increases complexity but reduces staleness significantly for specific events. For this problem, the 5-minute staleness makes this unnecessary.

In this specific scenario, given that the feature is a "dashboard overview" and a 5-minute staleness is acceptable, the trade-offs are well-justified. The primary goal is performance and database load reduction, which the eventually consistent cache achieves effectively. The potential negative user experiences are minor and can be largely mitigated by transparent communication.
