## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee shifts and schedules. A core feature is the ability for managers to view an "Availability Report" which shows, for a given week, which employees are available to work.

The `employees` table has about 100,000 active employees across all tenants. Each employee has a `shift_preferences` JSONB column which stores their preferred working hours, days off, and any specific constraints (e.g., "cannot work before 9 AM on Mondays," "prefers to work 4-hour blocks"). This column can be quite complex, with nested arrays and objects.

The `shifts` table, which stores actual scheduled shifts, has grown to over 500 million rows, with about 1 million new shifts added per day. The `Availability Report` needs to query both the `employees` table for preferences and the `shifts` table to determine actual availability (i.e., if they're already scheduled for a shift).

Initially, the report was generated by a synchronous API call that performed complex joins and filtering. Now, with the increase in data and user concurrency, generating this report for a single manager for a single week often takes 15-20 seconds, leading to timeouts and a poor user experience. Managers need this report quickly, ideally within 2-3 seconds, especially during peak scheduling times (Monday mornings). The report is highly dynamic: managers frequently change parameters (different week, different team, different availability filters) and regenerate it.

## Requirements

The current synchronous report generation is causing significant user experience issues due to latency. We need to redesign the system to provide near real-time availability information, accounting for both employee preferences and already scheduled shifts. The solution must scale to tens of thousands of simultaneous report requests without degrading performance for other parts of the application. Data consistency for employee preferences and shifts is critical; the report must reflect the most up-to-date information.

## Deliverables

1.  A high-level system architecture diagram (boxes and arrows) illustrating the components involved in generating and serving the Availability Report.
2.  A brief description of how employee `shift_preferences` are processed and stored to facilitate fast queries for availability.
3.  A description of the data flow and communication patterns from a manager's request to receiving the report, highlighting how the 2-3 second latency target is met.
4.  Identification of potential points of failure in your proposed system and strategies to mitigate them.

**Components:**

*   **Manager UI:** The frontend application where managers request the report.
*   **API Gateway:** Routes requests, handles authentication/authorization.
*   **Availability Report Service:** A lightweight microservice that receives report requests. It first checks the `Availability Cache`. If a cached report exists and is fresh enough, it returns it. Otherwise, it publishes a request to Kafka and waits for the result (or returns a "generating" status).
*   **Kafka (Availability Report Requests):** A message queue for asynchronous report generation requests.
*   **Availability Report Processor:** A worker service that consumes messages from the `Availability Report Requests` queue. It fetches employee preferences and scheduled shifts, computes the availability, and stores the result in the `Availability Cache`.
*   **Availability Cache (Redis):** A high-performance key-value store (e.g., Redis) used to store pre-computed availability reports.
*   **Employee Preferences DB (PostgreSQL):** Stores employee details and their parsed/indexed shift preferences.
*   **Scheduled Shifts DB (PostgreSQL):** Stores all scheduled shifts.
*   **Shift Scheduling Service:** The service responsible for creating/updating/deleting shifts.
*   **Kafka (Shift Updates):** A message queue for real-time shift changes.
*   **Shift Cache Updater:** A worker that consumes shift updates and propagates them to the `Scheduled Shifts DB` and invalidates/updates relevant entries in the `Availability Cache`.
*   **Employee Management Service:** The service responsible for managing employee data.
*   **Kafka (Employee Updates):** A message queue for real-time employee data changes.
*   **Employee Preferences Updater:** A worker that consumes employee updates and propagates them to the `Employee Preferences DB` and invalidates/updates relevant entries in the `Availability Cache`.

### 2. Processing and storing employee `shift_preferences`

The `shift_preferences` JSONB column is problematic for fast queries because its structure is complex and requires parsing at query time, making indexing difficult and inefficient for complex conditions. To facilitate fast queries, we need to pre-process and normalize this data into a more query-friendly format.

**Proposed Schema for `employee_preferences` table:**

Instead of directly querying the `shift_preferences` JSONB, we'll create a new table, or augment the existing `employees` table, with pre-parsed and indexed preference data. Let's assume we augment the `employees` table for simplicity, but a separate `employee_preferences` table linked by `employee_id` could also work.

```sql
CREATE TABLE employees (
    employee_id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    name TEXT NOT NULL,
    -- Original JSONB column, kept for source of truth/auditing if needed
    shift_preferences JSONB,
    -- New columns for parsed preferences
    prefers_full_time BOOLEAN DEFAULT FALSE,
    min_hours_per_week SMALLINT,
    max_hours_per_week SMALLINT,
    -- Array of preferred day-of-week (0=Sunday, 6=Saturday)
    preferred_days_of_week SMALLINT[],
    -- Array of disliked day-of-week
    disliked_days_of_week SMALLINT[],
    -- Array of objects for time-of-day preferences per day
    -- Example: [{day: 1, start_hour: 9, end_hour: 17}, {day: 2, start_hour: 10, end_hour: 18}]
    preferred_time_slots JSONB[],
    -- Array of objects for specific date/time constraints
    -- Example: [{type: 'cannot_work', start_date: '2026-11-01', end_date: '2026-11-01', start_time: '09:00', end_time: '17:00'}]
    specific_constraints JSONB[],
    -- GIN index on JSONB arrays for fast querying of contained elements
    -- This is particularly useful for filtering employees based on specific constraints
    -- e.g., finding employees who cannot work on a specific date.
    -- However, for simple day/time preferences, the normalized columns are better.
    CONSTRAINT chk_min_max_hours CHECK (min_hours_per_week <= max_hours_per_week)
);

-- Indexes for fast lookups
CREATE INDEX idx_employees_tenant_id ON employees (tenant_id);
CREATE INDEX idx_employees_preferred_days_of_week ON employees USING GIN (preferred_days_of_week);
-- If we frequently query specific_constraints, a GIN index on it could be useful,
-- but parsing it into more columns is often better for specific, common queries.
-- CREATE INDEX idx_employees_specific_constraints ON employees USING GIN (specific_constraints);
```

**Processing Flow:**

1.  **Employee Management Service:** When an employee's `shift_preferences` are created or updated, this service publishes an event to `Kafka (Employee Updates)`.
2.  **Employee Preferences Updater:** This worker service consumes the event.
    *   It parses the complex `shift_preferences` JSONB.
    *   It extracts relevant, queryable attributes (e.g., preferred days, time blocks, specific date constraints).
    *   It updates the normalized columns in the `employees` table (or a dedicated `employee_preferences` table).
    *   Crucially, it also publishes an event to invalidate/update relevant pre-computed availability reports in the `Availability Cache`. This ensures that any reports involving this employee are regenerated or marked as stale.

**Example of preference parsing:**

If `shift_preferences` contains:
`{"days_off": ["Monday", "Wednesday"], "time_blocks": [{"day": "Tuesday", "start": "09:00", "end": "13:00"}]}`

The `Employee Preferences Updater` would parse this and update:
*   `disliked_days_of_week = [1, 3]` (assuming 0=Sunday, 1=Monday)
*   `preferred_time_slots = [{day: 2, start_hour: 9, end_hour: 13}]`

This pre-computation and normalization allow the `Availability Report Processor` to query simple, indexed columns rather than performing expensive JSONB operations, significantly speeding up preference filtering.

### 3. Data flow and communication patterns for 2-3 second latency

The key to achieving 2-3 second latency is to leverage asynchronous processing, caching, and pre-computation.

1.  **Manager Request (Non-blocking):**
    *   Manager opens the UI and requests an "Availability Report" for a specific week, tenant, and optional filters (e.g., "only show employees who prefer full-time").
    *   The **Manager UI** sends a request to the **API Gateway**.
    *   The **API Gateway** forwards it to the **Availability Report Service**.

2.  **Cache Check (Fast Path):**
    *   The **Availability Report Service** constructs a cache key based on the request parameters (tenant ID, week, filters).
    *   It queries the **Availability Cache (Redis)**.
    *   **If a fresh report exists in the cache:** The service immediately returns the cached report to the Manager UI. This is the primary path for achieving sub-second latency for frequently requested reports.
    *   **If no fresh report exists:** The service publishes a message to **Kafka (Availability Report Requests)** containing the request parameters. It then immediately returns a "Report Generation Initiated" status (e.g., HTTP 202 Accepted) to the Manager UI, possibly with a `report_id` to poll for results.

3.  **Asynchronous Report Generation (Background):**
    *   The **Availability Report Processor** consumes the request message from **Kafka (Availability Report Requests)**.
    *   **Data Retrieval:**
        *   It queries the **Employee Preferences DB** for all employees matching the tenant and preference filters (e.g., `WHERE tenant_id = :tenantId AND prefers_full_time = TRUE`). This uses the pre-parsed, indexed columns.
        *   For each employee, it fetches their `preferred_days_of_week`, `disliked_days_of_week`, `preferred_time_slots`, and `specific_constraints`.
        *   It queries the **Scheduled Shifts DB** for all shifts for the specified week and tenant. This table should be indexed by `tenant_id`, `employee_id`, and `shift_date`.
            ```sql
            SELECT employee_id, shift_start_time, shift_end_time
            FROM shifts
            WHERE tenant_id = :tenantId
              AND shift_start_time BETWEEN :weekStart AND :weekEnd;
            ```
            (An index on `(tenant_id, shift_start_time, employee_id)` would be ideal here).
    *   **Availability Computation:** For each employee, the processor iterates through the days of the requested week. For each day, it:
        *   Checks `disliked_days_of_week` and `specific_constraints` (e.g., "cannot work on Nov 1st").
        *   Compares `preferred_time_slots` against scheduled shifts to identify available blocks.
        *   Aggregates the availability information (e.g., "Employee X is available Monday 9-5, Tuesday 1-5").
    *   **Cache Storage:** The computed report (e.g., a JSON object mapping employee IDs to their weekly availability) is stored in the **Availability Cache (Redis)** with an appropriate Time-To-Live (TTL).
    *   **Notification (Optional):** The processor could publish a "Report Ready" event to another Kafka topic, or directly update a status in a database that the `Availability Report Service` polls.

4.  **Manager UI Polling/Real-time Update:**
    *   If the initial request returned a "generating" status, the **Manager UI** can poll the **Availability Report Service** using the `report_id`.
    *   Alternatively, the **Availability Report Service** could use WebSockets to push the completed report to the Manager UI once it's available in the cache.

**Latency Target Achievement:**

*   **Sub-second for cached reports:** The cache hit path is extremely fast, typically milliseconds.
*   **2-3 seconds for uncached reports:**
    *   Asynchronous processing offloads heavy computation from the request path.
    *   Pre-parsing `shift_preferences` into indexed columns makes employee filtering very fast.
    *   Dedicated indexes on `shifts` (`tenant_id`, `shift_start_time`, `employee_id`) allow for quick retrieval of scheduled shifts for a given week.
    *   The `Availability Report Processor` can be scaled horizontally to handle peak loads. Multiple instances can process requests concurrently.
    *   The computational logic for availability is optimized to work with structured data, reducing CPU overhead.

### 4. Potential points of failure and mitigation strategies

1.  **Kafka Broker Failure:**
    *   **Failure:** If Kafka brokers go down, messages cannot be published or consumed, leading to report generation requests being lost or delayed, and cache updates failing.
    *   **Mitigation:**
        *   **High Availability:** Deploy Kafka in a clustered, fault-tolerant configuration with multiple brokers and replication (e.g., 3 brokers, replication factor 3).
        *   **Producer Retries:** Configure producers (Availability Report Service, Shift Scheduling Service, Employee Management Service) to retry sending messages with exponential backoff.
        *   **Consumer Offsets:** Consumers (Availability Report Processor, Shift Cache Updater, Employee Preferences Updater) should commit offsets reliably to prevent reprocessing or losing messages after a restart.

2.  **Availability Report Processor Failure:**
    *   **Failure:** If the processor crashes, reports stop being generated, and the queue backs up.
    *   **Mitigation:**
        *   **Horizontal Scaling:** Deploy multiple instances of the processor behind a consumer group. If one fails, others can pick up its workload.
        *   **Idempotency:** Ensure report generation is idempotent. If a message is reprocessed due to a crash, it should produce the same result without side effects. Storing the report in Redis is inherently idempotent (last write wins).
        *   **Dead Letter Queue (DLQ):** Configure Kafka consumers to send messages that consistently fail processing to a DLQ for manual inspection and reprocessing.

3.  **Database (PostgreSQL) Failure:**
    *   **Failure:** If `Employee Preferences DB` or `Scheduled Shifts DB` becomes unavailable, report generation halts, and data ingestion fails.
    *   **Mitigation:**
        *   **High Availability:** Use PostgreSQL replication (e.g., streaming replication with a primary and multiple standbys) and automatic failover (e.g., using Patroni or similar tools).
        *   **Connection Pooling & Retries:** Services connecting to the DB should use connection pooling and implement retry logic with backoff.
        *   **Read Replicas:** For read-heavy workloads (like the Availability Report Processor querying shifts), consider using read replicas to distribute the load and provide read-only redundancy.

4.  **Availability Cache (Redis) Failure:**
    *   **Failure:** If Redis goes down, cache hits will fail, forcing all requests to the slower asynchronous path, potentially overwhelming the `Availability Report Processor` and increasing latency for all reports.
    *   **Mitigation:**
        *   **High Availability:** Deploy Redis in a clustered setup (e.g., Redis Cluster, Sentinel) with replication.
        *   **Graceful Degradation:** The `Availability Report Service` should be designed to function without the cache (albeit slower) by always publishing to Kafka if Redis is unavailable. This prevents a complete outage.
        *   **Circuit Breaker:** Implement a circuit breaker pattern in the `Availability Report Service` when interacting with Redis to prevent cascading failures if Redis is slow or unresponsive.

5.  **Data Inconsistency (between DBs and Cache):**
    *   **Failure:** If an employee's preferences change or a shift is added, but the cache isn't updated, managers see stale data.
    *   **Mitigation:**
        *   **Event-Driven Cache Invalidation/Update:** As shown in the diagram, `Shift Cache Updater` and `Employee Preferences Updater` are critical. They listen to Kafka events from source services (`Shift Scheduling Service`, `Employee Management Service`) and actively invalidate or update relevant cache entries.
        *   **Cache TTL:** Set an appropriate Time-To-Live (TTL) on cache entries. Even if an invalidation event is missed, the report will eventually expire and be regenerated with fresh data. For this scenario, a few minutes might be acceptable if real-time updates are critical but not absolutely instantaneous.
        *   **Idempotent Updates:** Ensure cache updates are idempotent.

6.  **Scalability Bottlenecks:**
    *   **Failure:** During peak times, a single component might become a bottleneck (e.g., `Availability Report Processor` can't keep up, or DB queries become slow).
    *   **Mitigation:**
        *   **Horizontal Scaling:** Most stateless components (API Gateway, Availability Report Service, Processors, Updaters) can be scaled horizontally by adding more instances.
        *   **Database Sharding/Partitioning:** If the `shifts` table continues to grow, consider partitioning it by `tenant_id` or `shift_date` to improve query performance and manageability. The `employees` table could also be sharded by `tenant_id`.
        *   **Indexing:** Continuously monitor and optimize database indexes.
        *   **Load Testing:** Regularly perform load testing to identify bottlenecks before they impact production.

### Going further

The proposed solution makes several trade-offs between data freshness, computational cost, and storage requirements.

**1. Data Freshness vs. Computational Cost & Latency:**

*   **Trade-off:** We prioritize low latency for the user over absolute, instantaneous data freshness for every single report request.
*   **Why it's appropriate:** The requirement is "near real-time" and "2-3 seconds latency," not "sub-millisecond, always-fresh." Managers need quick access to the report, and a slight delay (a few seconds to a few minutes) for updates to propagate to the cache is generally acceptable. The `Availability Report Processor` runs asynchronously, meaning the manager gets an immediate response (even if it's "generating") and doesn't wait for the full computation.
*   **Mechanism:**
    *   **Caching (Redis):** This is the primary mechanism. By storing pre-computed reports, we eliminate the need for expensive joins and computations on every request. This drastically reduces computational cost per request and achieves sub-second latency for cache hits.
    *   **Asynchronous Processing (Kafka):** Offloading the heavy computation to background workers means the user-facing API remains responsive. The computational cost is shifted from the request path to a scalable background process.
    *   **Event-Driven Cache Invalidation:** This ensures that when employee preferences or shifts change, the cache is updated or invalidated quickly. This balances freshness with the cost of full regeneration. A small delay (e.g., a few seconds for Kafka propagation and processing) is introduced, but it's a conscious choice to avoid synchronous re-computation.
*   **What we gave up:** We sacrifice absolute, immediate consistency. There's a small window where the cache might be stale (e.g., a shift is added, but the cache invalidation event hasn't been processed yet). However, given the "near real-time" requirement, this eventual consistency model is a good fit.

**2. Computational Cost vs. Storage Requirements:**

*   **Trade-off:** We increase storage requirements (for the `Availability Cache` and potentially denormalized preference data) to significantly reduce computational cost at query time.
*   **Why it's appropriate:** The original problem states that complex joins and filtering take 15-20 seconds. This indicates that the computational cost of *on-demand* generation is too high. By pre-computing and storing results, we shift this cost.
*   **Mechanism:**
    *   **Pre-parsed `shift_preferences`:** Storing normalized columns in `employees` (or a separate table) adds storage overhead compared to just a JSONB blob. However, it drastically reduces the CPU cost of parsing and filtering at query time, enabling fast indexed lookups.
    *   **Availability Cache (Redis):** Storing entire report results in Redis consumes memory. The size of these reports can be significant, especially if they contain detailed availability for many employees over a week.
*   **What we gave up:** Increased memory usage in Redis and potentially slightly larger database tables for denormalized preference data. However, memory is generally cheaper and more scalable than CPU cycles for complex, dynamic queries in a high-concurrency environment. The cost of storing pre-computed reports is justified by the performance gains.

**3. Simplicity vs. Scalability/Performance:**

*   **Trade-off:** We introduce significant architectural complexity (Kafka, multiple services, caching layers) to achieve the required scalability and performance.
*   **Why it's appropriate:** The original synchronous API was simple but failed at scale. The problem explicitly mentions "tens of thousands of simultaneous report requests" and "500 million rows" in the `shifts` table. A simple monolithic approach cannot handle this.
*   **Mechanism:**
    *   **Microservices:** Breaking down the system into specialized services (Report Service, Processors, Updaters) allows for independent scaling and development.
    *   **Message Queues (Kafka):** Decouples producers and consumers, provides buffering, and enables asynchronous processing, which is crucial for handling spikes in requests.
    *   **Dedicated Databases/Indexes:** Optimizing data storage and access patterns for specific query types.
*   **What we gave up:** Increased operational overhead (managing Kafka, Redis, multiple services), more complex deployment, and a steeper learning curve for new engineers. This complexity is a necessary evil to meet the non-functional requirements.

**Why these trade-offs are appropriate for this problem:**

The core problem is high latency and poor user experience due to synchronous, expensive computations on large datasets under high concurrency. The proposed solution directly addresses this by:

*   **Prioritizing user experience:** Fast responses (sub-second for cached, 2-3 seconds for uncached) are paramount.
*   **Leveraging eventual consistency:** For an "Availability Report," a few seconds of staleness is acceptable if it means the report loads quickly. It's not a real-time trading system where milliseconds matter for every single data point.
*   **Shifting computation:** Moving heavy lifting off the critical request path to background workers and pre-computation.
*   **Scaling horizontally:** Designing components that can be easily scaled out to handle increased load.

**What breaks first at ten times the scale:**

At ten times the scale (e.g., 1 million active employees, 5 billion shifts, 10 million new shifts/day, hundreds of thousands of simultaneous report requests):

1.  **PostgreSQL Database (Scheduled Shifts DB):** The `shifts` table, even with good indexing, will become a major bottleneck. 5 billion rows with 10 million new rows daily will quickly lead to:
    *   **Index bloat and maintenance:** Indexes will become huge and slow to update.
    *   **Query performance degradation:** Even with indexes, range queries over such a large dataset will be slow, especially if the working set doesn't fit in memory.
    *   **Storage and backup challenges:** Managing such a large single table becomes difficult.
    *   **Mitigation:** Aggressive database sharding (e.g., by `tenant_id` or `shift_date` range) would become essential. A time-series database or a distributed SQL database might be considered.

2.  **Availability Cache (Redis) Memory:** With 10x more employees and potentially more complex reports, the memory footprint of Redis could become enormous, leading to:
    *   **Cost:** High memory costs for Redis instances.
    *   **Performance:** Increased latency if Redis has to swap to disk or if network bandwidth to Redis becomes saturated.
    *   **Mitigation:** More aggressive TTLs, only caching the most frequently accessed reports, or implementing a multi-tier caching strategy (e.g., local service cache + Redis). Potentially, a more cost-effective distributed key-value store.

3.  **Kafka Throughput:** 10 million shifts per day means a high volume of messages on the `Kafka (Shift Updates)` topic. If each shift update triggers a cache invalidation/update, Kafka itself might struggle with throughput or the `Shift Cache Updater` might not keep up.
    *   **Mitigation:** Scaling Kafka brokers, optimizing message sizes, and ensuring consumers are highly optimized and scaled. Batching cache updates instead of per-shift updates.

4.  **Availability Report Processor Compute:** While horizontally scalable, 10x the requests and 10x the data to process per report could mean needing a massive number of processor instances, leading to:
    *   **Cost:** High compute costs.
    *   **Latency:** Even with scaling, if the individual report computation time doesn't improve, the queue might build up.
    *   **Mitigation:** Further optimization of the availability computation algorithm, potentially pre-aggregating availability data at a coarser granularity (e.g., daily summaries) instead of re-calculating from raw shifts every time.
