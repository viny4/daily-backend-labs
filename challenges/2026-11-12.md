## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee data. A core feature allows HR administrators to upload CSV files containing employee records (e.g., name, department, salary, start date) to bulk-create or update employee profiles.

These CSV files can range from a few dozen rows to several hundred thousand rows (up to 500,000 employees for large enterprises). When an HR admin uploads a file, the system needs to process it, validate the data, and then apply the changes to the `employees` table. Historically, this has been a synchronous process, where the admin waits for the import to complete. However, as the number of employees for larger clients has grown, these imports now frequently time out at the load balancer (30-second limit) and sometimes even exhaust server memory, leading to a poor user experience and failed imports.

The `employees` table currently has about 15 million rows across all tenants, and grows by about 1-2 million rows annually. The system is multi-tenant, meaning each client's data is logically separated, typically by a `tenant_id` column on most tables.

## Requirements

The new system must handle file uploads containing up to 500,000 employee records reliably.
It must provide immediate feedback to the HR admin after the file upload, indicating that the import has started and will be processed in the background. The actual data processing should happen asynchronously.
The system needs to inform the user about the import's final status (success/failure, number of records processed, any errors) once it's complete, without the user needing to constantly refresh a page.
The solution must scale to handle multiple large imports concurrently from different tenants without degrading overall system performance.
Error handling should be robust; individual row errors in a CSV should not halt the entire import, and the system should provide details on which rows failed and why.

## Deliverables

1. A high-level architectural diagram (boxes and arrows) illustrating the components involved in the new asynchronous import process and their interactions.
2. A brief explanation of the key technologies you would use for each component in the diagram (e.g., "Queue: AWS SQS", "Worker: Python Celery workers on EC2").
3. Describe the mechanism for notifying the HR admin of the import's completion and status, considering real-time updates without polling.

### 1. High-level architectural diagram

```mermaid

    subgraph Frontend
        A[HR Admin Browser] --> B(Upload CSV)

    subgraph Backend API (Synchronous)

        E -- "2. Store File (S3/GCS)" --> F[Object Storage]
        E -- "3. Create Import Record" --> G[Database (PostgreSQL)]
        E -- "4. Enqueue Job" --> H[Message Queue (e.g., RabbitMQ/SQS)]
        E -- "5. Return Import ID" --> D
        D --> B
    end

    subgraph Asynchronous Processing
        H --> I[Worker Pool (e.g., Celery/Kubernetes Jobs)]
        I -- "6. Retrieve File" --> F
        I -- "7. Process Rows" --> J[Database (PostgreSQL)]
        J -- "8. Update Import Status/Errors" --> G
        I -- "9. Send Completion Event" --> K[Real-time Notification Service (e.g., WebSockets/SSE)]
    end

    subgraph Real-time Notifications
        K --> L[Notification Service Client (e.g., Redis Pub/Sub)]
        L --> M[Web Server (e.g., FastAPI/Django)]
        M -- "10. Push Update" --> A
    end

    subgraph Monitoring & Observability
        I --> N[Metrics & Logs]
        N --> O[Monitoring System (e.g., Prometheus/Grafana)]
        N --> P[Logging System (e.g., ELK Stack/Datadog)]
    end
```

**Flow Explanation:**

1.  **HR Admin Uploads CSV:** The user uploads a CSV file through the frontend.
2.  **API Gateway/Load Balancer:** Routes the request to the web server.
3.  **Web Server (API Endpoint):**
    *   Receives the CSV file.
    *   Stores the raw CSV file in **Object Storage** (e.g., S3).
    *   Creates an initial record in the **Database** for the import job (status: `PENDING`).
    *   Puts a message on the **Message Queue** containing the import job ID and file location.
    *   Immediately returns an `HTTP 202 Accepted` response to the user with the import job ID, indicating that processing has started in the background.
4.  **Worker Pool:**
    *   Picks up messages from the **Message Queue**.
    *   Downloads the CSV file from **Object Storage**.
    *   Parses the CSV, validates each row, and processes (creates/updates) employee records in the **Database**.
    *   Records any errors encountered for individual rows.
    *   Updates the import job's status (e.g., `COMPLETED`, `FAILED`) and statistics (e.g., `rows_processed`, `rows_failed`) in the **Database**.
    *   Publishes a completion event to the **Real-time Notification Service**.
5.  **Real-time Notification Service:**
    *   Receives completion events from workers.
    *   Pushes updates to the HR admin's browser via WebSockets or Server-Sent Events (SSE), informing them of the import's final status.

### 2. Key technologies

*   **Frontend:** React/Angular/Vue.js for the UI, with a library like `axios` or `fetch` for API calls and a WebSocket client for real-time updates.
*   **API Gateway / Load Balancer:** AWS ALB, NGINX, or similar. Handles SSL termination, routing, and basic request limits.
*   **Web Server:** Python with a framework like FastAPI or Django REST Framework. Chosen for its ecosystem, developer productivity, and good asynchronous capabilities.
*   **Object Storage:** AWS S3 (Simple Storage Service) or Google Cloud Storage (GCS). Highly durable, scalable, and cost-effective for storing raw uploaded files.
*   **Database:** PostgreSQL. A robust, mature relational database suitable for multi-tenant applications. It supports transactions, JSONB for flexible error logging, and good indexing for performance.
*   **Message Queue:** RabbitMQ (self-hosted) or AWS SQS (managed service). RabbitMQ offers more features (e.g., dead-letter queues, message priorities) and is suitable for complex workflows, while SQS is simpler to operate at scale. For this scenario, AWS SQS is a good choice for its managed nature and scalability.
*   **Worker Pool:** Python Celery workers running on Kubernetes or EC2 instances with auto-scaling. Celery integrates well with Python web frameworks and message queues, providing robust task management, retries, and error handling. Kubernetes provides excellent orchestration and scaling capabilities for the workers.
*   **Real-time Notification Service:** AWS API Gateway with WebSockets or a dedicated WebSocket server (e.g., Node.js with Socket.IO, or a Python ASGI server like Uvicorn/Daphne). For a fully managed solution, AWS API Gateway's WebSocket API is ideal. Alternatively, Redis Pub/Sub could be used for inter-service communication, with the web server pushing updates to the client via SSE.
*   **Monitoring & Logging:** Prometheus for metrics collection, Grafana for dashboards, and the ELK Stack (Elasticsearch, Logstash, Kibana) or Datadog for centralized logging and error tracking.

### 3. Mechanism for notifying the HR admin

The mechanism for notifying the HR admin of the import's completion and status will leverage **WebSockets** for real-time, push-based communication, avoiding the need for the client to poll the server.

**Detailed Steps:**

1.  **Client-side Connection:** When the HR admin initiates an import or navigates to an "Import History" page, the frontend establishes a WebSocket connection to the Real-time Notification Service (e.g., `wss://api.example.com/ws/imports`). This connection is typically authenticated (e.g., by passing an authentication token in the WebSocket handshake).
2.  **Server-side Tracking:**
    *   When the initial API endpoint receives the CSV upload and enqueues the job, it also records the `import_id` and the `user_id` (or `tenant_id`) in the database.
    *   The Real-time Notification Service maintains a mapping of active WebSocket connections to `user_id`s.
3.  **Worker Completion Event:**
    *   Once a worker finishes processing an import job (successfully or with errors), it updates the `imports` table in the database with the final status, statistics, and any detailed row-level errors.
    *   Immediately after updating the database, the worker publishes a message to a dedicated topic or channel in the Real-time Notification Service (e.g., a Redis Pub/Sub channel, or directly calls an internal API endpoint of the WebSocket service). This message includes the `import_id`, `user_id`, final status, and summary statistics.
4.  **Notification Service Broadcast:**
    *   The Real-time Notification Service receives this message.
    *   It looks up all active WebSocket connections associated with the `user_id` from the event.
    *   It then sends a JSON message over the active WebSocket connection(s) to the client(s) belonging to that user.

**Example Notification Payload (JSON):**

```json
{
  "type": "import_status_update",
  "importId": "uuid-of-the-import-job",
  "status": "COMPLETED",
  "progress": 100,
  "totalRecords": 500000,
  "processedRecords": 499980,
  "failedRecords": 20,
  "errorsSummary": [
    {
      "row": 15,
      "field": "salary",
      "message": "Invalid salary format: 'abc'"
    },
    {
      "row": 102,
      "field": "department",
      "message": "Department 'Sales' does not exist"
    }
  ],
  "completedAt": "2026-11-12T14:30:00Z"
}
```

**Client-side Handling:**

*   The frontend JavaScript listens for messages on the WebSocket connection.
*   When an `import_status_update` message is received, it updates the UI (e.g., displays a toast notification, updates a progress bar, or refreshes the import history table) with the new status and details.

**Database Schema for `imports` table:**

```sql
CREATE TYPE import_status AS ENUM ('PENDING', 'PROCESSING', 'COMPLETED', 'FAILED');

CREATE TABLE imports (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    user_id UUID NOT NULL,
    file_name VARCHAR(255) NOT NULL,
    s3_key VARCHAR(512) NOT NULL, -- Path to the original CSV in S3
    status import_status NOT NULL DEFAULT 'PENDING',
    total_records INTEGER,
    processed_records INTEGER DEFAULT 0,
    failed_records INTEGER DEFAULT 0,
    error_details JSONB, -- Stores an array of row-level errors
    started_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    completed_at TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

-- Index for efficient lookup by tenant and user
CREATE INDEX idx_imports_tenant_user ON imports (tenant_id, user_id);
```

This approach provides immediate feedback, real-time updates, and avoids client-side polling, which is inefficient and can put unnecessary load on the backend.

**Comparison: Message Queue vs. Simple HTTP API + Forked Process**

Let's analyze the trade-offs:

**1. Reliability**

*   **Message Queue (MQ):**
    *   **Pros:** High reliability. Messages are persisted in the queue until successfully processed and acknowledged by a worker. If a worker crashes, the message remains in the queue and can be picked up by another worker or retried. Dead-letter queues (DLQs) can capture messages that repeatedly fail, preventing data loss and allowing for manual inspection.
    *   **Cons:** Requires careful configuration of message durability, acknowledgment, and retry policies. If the MQ itself fails (e.g., disk corruption without replication), messages could be lost, though highly available MQs mitigate this.
*   **Simple HTTP API + Forked Process:**
    *   **Pros:** Simpler to implement initially for basic "fire-and-forget" scenarios.
    *   **Cons:** Low reliability. If the background process crashes *after* being forked but *before* fully processing the data, the job is lost, and the user receives no notification of failure. The HTTP server process itself might crash, taking the forked process with it. There's no inherent mechanism for retries or dead-lettering. If the server restarts, all in-flight forked processes are typically terminated. This is particularly problematic for long-running tasks like large CSV imports.

**2. Scalability**

*   **Message Queue (MQ):**
    *   **Pros:** Excellent horizontal scalability. Workers can be added or removed dynamically based on queue depth. Multiple workers can process messages concurrently, distributing the load. The queue acts as a buffer, decoupling the ingestion rate from the processing rate, preventing the API server from being overwhelmed during peak loads.
    *   **Cons:** The MQ itself can become a bottleneck if not properly scaled or if message throughput vastly exceeds its capacity. Requires monitoring of queue depth and worker utilization to ensure optimal scaling.
*   **Simple HTTP API + Forked Process:**
    *   **Pros:** Can scale horizontally by adding more HTTP servers.
    *   **Cons:** Each HTTP server is responsible for its own background processes. This makes load balancing and resource management difficult. If one server is overloaded with background tasks, it can degrade performance for synchronous requests on that same server. It's harder to manage resource contention (CPU, memory) across multiple independent forked processes on a single machine, and harder to distribute tasks efficiently across a fleet of machines. The number of concurrent forked processes might be limited by OS resources, leading to resource exhaustion on individual servers.

**3. Operational Complexity**

*   **Message Queue (MQ):**
    *   **Pros:** Provides a clear separation of concerns between the API layer and the processing layer. Easier to monitor job status, worker health, and queue performance. Standardized tools and practices exist for managing MQs (e.g., RabbitMQ management UI, AWS SQS console).
    *   **Cons:** Introduces a new component (the message queue) into the architecture, increasing infrastructure to manage and monitor. Requires understanding of queue concepts (message acknowledgment, retries, DLQs). Debugging can be more complex as the flow spans multiple services.
*   **Simple HTTP API + Forked Process:**
    *   **Pros:** Lower initial operational complexity as it doesn't introduce a new infrastructure component. All logic resides within the web server's environment.
    *   **Cons:** Can quickly become operationally complex as the system scales or reliability demands increase. Monitoring individual forked processes is challenging. Recovering from failures is often manual. Resource contention and "noisy neighbor" problems on a single server can be difficult to diagnose. Deployments often require careful handling to avoid interrupting long-running background processes.

**Conclusion for this Scenario:**

For the given scenario (up to 500,000 rows, multi-tenant, high reliability, real-time status updates, concurrent large imports), **using a message queue is overwhelmingly the superior approach.**

The "simple HTTP API + forked process" approach would quickly fail to meet the requirements:

*   **Reliability:** Large imports would frequently fail silently if the server or process crashed, leading to data inconsistencies and a terrible user experience.
*   **Scalability:** Concurrent large imports would exhaust server resources (CPU, memory) and lead to timeouts, exactly the problem the new system aims to solve. The lack of a buffer would mean peak loads directly impact API responsiveness.
*   **Operational Complexity:** Debugging failed imports, monitoring progress, and ensuring resource isolation across tenants would be a nightmare.

The message queue, despite its added operational complexity (which is manageable with managed services like AWS SQS), provides the necessary reliability, scalability, and asynchronous processing capabilities to meet all the stated requirements effectively. It decouples the fast-responding API from the slow-running processing, making the system robust and performant.
