## Scenario

Your company operates a popular social media platform where users can post short text updates ("posts") and follow other users. You're preparing for a major marketing push that is expected to triple user engagement. One of the core features is the "feed" — when a user logs in, they see a chronologically ordered list of posts from the users they follow. This feed is currently generated by fetching all posts from followed users and sorting them on the fly.

The current `posts` table has grown to 500 million rows, with an average of 100 posts per user. The `followers` table is even larger, with an average user following 500 other users. Generating a user's feed now frequently takes 2-3 seconds, especially for users who follow many popular accounts. During peak times, this can spike to 5-10 seconds, leading to a poor user experience and increased database load. Your current infrastructure is PostgreSQL for primary data storage, Redis for caching, and Python/Django for the backend API.

## Requirements

Design a system to reduce the average feed generation time for a user to under 200 milliseconds, even during peak load, while ensuring posts appear in chronological order. Consider the implications for data consistency, system complexity, and operational overhead. The solution should be scalable to handle a 3x increase in read traffic and a 2x increase in write traffic (new posts). The existing `posts` and `followers` tables cannot be fundamentally re-architected in a way that requires a full data migration in the scope of this exercise.

**Components:**

*   **User (Browser/Mobile):** Client applications interacting with the platform.
*   **Load Balancer:** Distributes incoming requests across API servers.
*   **API Servers (Python/Django):** Handle user authentication, request parsing, and orchestrate interactions with other services.
*   **PostgreSQL DB:** Primary data store for `posts` and `followers` tables.
    *   `posts`: `id`, `user_id`, `content`, `created_at`, `...`
    *   `followers`: `follower_id`, `followed_id`, `created_at`
*   **Redis Cache:** Used for caching frequently accessed data, specifically pre-computed user feeds.
*   **Message Queue (Kafka/RabbitMQ):** Asynchronous communication bus for events like new posts.
*   **Feed Builder (Workers):** A dedicated service responsible for generating and updating pre-computed feeds. It consumes messages from the Message Queue.
*   **Feed Service (Pre-computed Feeds):** A dedicated service that serves pre-computed feeds, potentially backed by Redis or a similar high-throughput key-value store. It could also be integrated into the API servers directly, but separating it allows for independent scaling and optimization.

### 2. Data flow

#### A. User publishing a new post

1.  **User Action:** A user creates a new post in their client application and clicks "Post".
2.  **API Request:** The client sends an HTTP POST request to the API servers (e.g., `POST /api/v1/posts`) with the post content and user authentication token.
3.  **API Server Processing:**
    *   The API server validates the request and authenticates the user.
    *   It inserts the new post into the `posts` table in PostgreSQL.
    *   It publishes a "New Post" event to the Message Queue (e.g., Kafka topic `post_events`). This event includes the `post_id`, `user_id` (of the author), and `created_at` timestamp.
    *   It returns a success response to the client.
4.  **Feed Builder Consumption:**
    *   The Feed Builder service continuously consumes messages from the `post_events` topic.
    *   When it receives a "New Post" event, it queries the `followers` table to find all users who follow the author of the new post.
    *   For each follower, it updates their pre-computed feed. This involves adding the `post_id` and `created_at` to the follower's feed data structure in Redis.
    *   To optimize, for users with many followers (e.g., 100M+), the fan-out might be batched or handled by multiple workers. For users with fewer followers, it can be a direct write.

#### B. User fetching their feed

1.  **User Action:** A user logs in or navigates to their feed in the client application.
2.  **API Request:** The client sends an HTTP GET request to the API servers (e.g., `GET /api/v1/feed`) with the user's authentication token.
3.  **API Server Processing:**
    *   The API server validates the request and authenticates the user.
    *   It attempts to fetch the user's pre-computed feed from Redis using the user's ID as the key.
    *   **Cache Hit:** If the feed is found in Redis, the API server retrieves the list of `post_id`s (and potentially `created_at` timestamps) from Redis. It then fetches the full post details for these `post_id`s from PostgreSQL (or a read replica, or a separate post-details cache) and returns the chronologically ordered list to the client.
    *   **Cache Miss:** If the feed is *not* found in Redis (e.g., first login, cache eviction), the API server would trigger a synchronous (or asynchronous, with a placeholder response) feed generation process. This would involve:
        *   Querying PostgreSQL to find all users the current user follows.
        *   Querying PostgreSQL to get the latest N posts from each of those followed users.
        *   Merging and sorting these posts by `created_at`.
        *   Storing this newly generated feed into Redis for future requests.
        *   Returning the feed to the client.
        *   *Self-correction:* For a system designed for low latency, a cache miss should ideally not trigger a full synchronous rebuild. Instead, the Feed Builder should proactively populate feeds. A cache miss would imply an issue with the Feed Builder or a very new user. For a new user, the feed would be empty initially, and then populated as they follow people and new posts are made. A "cold start" for a new user would still involve querying `followers` and then `posts` for followed users, but this is a less frequent operation. The primary path is the cache hit.

### 3. Data consistency

The proposed system uses a "fan-out on write" approach for feed generation, which inherently introduces *eventual consistency*.

**How it's maintained within acceptable limits:**

*   **Asynchronous Processing:** When a user publishes a post, it's immediately written to PostgreSQL and a message is queued. The user gets a success response quickly. The actual propagation to followers' feeds happens asynchronously via the Feed Builder.
*   **Latency Budget:** The critical factor is the delay between a post being published and it appearing in a follower's feed.
    *   **Message Queue Latency:** Kafka/RabbitMQ are designed for low-latency message delivery (typically tens to hundreds of milliseconds).
    *   **Feed Builder Processing Time:** The Feed Builder's task is to fetch followers and update Redis.
        *   `SELECT follower_id FROM followers WHERE followed_id = :author_id;`
        *   `ZADD user_feed:follower_id :created_at :post_id` (Redis sorted set)
        *   For a user with 500 followers, this is 1 `SELECT` and 500 `ZADD` operations. Redis `ZADD` is O(log N) where N is the number of elements in the sorted set. If a feed has 1000 posts, it's very fast.
        *   The main bottleneck here is the `SELECT` query for followers. An index on `followed_id` (`CREATE INDEX idx_followed_id ON followers (followed_id);`) is crucial.
    *   **Overall Latency:** With optimized indexing and sufficient Feed Builder worker capacity, a post should appear in followers' feeds within **100-500 milliseconds** of being published. This is generally considered acceptable for a social media feed where immediate real-time consistency (like a banking transaction) is not strictly required.
*   **Read-Your-Own-Writes:** A user who just posted will see their own post immediately because their client application can display it optimistically or fetch it directly from the API (which would read from the primary DB). This is a common pattern to enhance perceived consistency.
*   **Feed Size Management:** Feeds in Redis will be capped (e.g., to the latest 1000 posts) to prevent unbounded growth and keep `ZADD` operations fast. Older posts would be pruned. When a user scrolls past the cached feed, a fallback to a slower, more comprehensive query of PostgreSQL might be needed, but this is less frequent.

**Trade-offs:**

*   **Eventual Consistency:** We explicitly accept that a follower might not see a post *immediately* after it's published. This is a common and necessary trade-off for scalability in high-throughput social systems.
*   **Increased Complexity:** Introducing a Message Queue and a dedicated Feed Builder service adds operational overhead and more moving parts compared to a monolithic approach.
*   **Storage Duplication:** The `post_id`s and `created_at` timestamps are effectively duplicated in Redis for each follower's feed. This is a small price for read performance.

### 4. Potential bottlenecks and mitigation

#### Current Bottlenecks (and how the new design mitigates them):

1.  **PostgreSQL Read Load for Feed Generation:**
    *   **Problem:** Fetching posts from hundreds of followed users and sorting them on the fly (`JOIN posts ON posts.user_id = followers.followed_id WHERE followers.follower_id = :user_id ORDER BY posts.created_at DESC LIMIT N;`) is extremely expensive, especially with 500M posts and 500 followed users per feed. This query hits multiple indices, performs many random disk reads, and requires significant memory for sorting.
    *   **Mitigation:** The "fan-out on write" approach pre-computes feeds. Reads become simple `GET` operations from Redis, followed by a batched `SELECT` from PostgreSQL for post details. This shifts the heavy lifting from read time to write time, which is distributed and asynchronous.

2.  **PostgreSQL Write Load for New Posts:**
    *   **Problem:** While not the primary bottleneck for *feed generation*, a 2x increase in write traffic means more `INSERT`s into the `posts` table.
    *   **Mitigation:** PostgreSQL is generally robust for `INSERT`s, especially with appropriate indexing. The new design adds an asynchronous message queue publish, which is fast. The fan-out writes to Redis are distributed across Feed Builder workers and are simple `ZADD` operations, not hitting the primary PostgreSQL database.

#### New Potential Bottlenecks in the Proposed System:

1.  **Feed Builder Worker Scalability:**
    *   **Problem:** If a popular user (e.g., 100M followers) posts, the Feed Builder needs to update 100M Redis feeds. This could overwhelm a single worker or even a small pool of workers.
    *   **Mitigation:**
        *   **Horizontal Scaling:** Deploy many Feed Builder workers. Message queues like Kafka allow multiple consumers in a consumer group to process partitions in parallel.
        *   **Batching/Sharding:** For extremely popular users, the fan-out could be batched (e.g., update 10,000 followers at a time) or even sharded (e.g., specific workers handle specific ranges of follower IDs).
        *   **Prioritization:** Less critical updates (e.g., very old posts being pruned) could be lower priority than new posts.
        *   **Rate Limiting/Circuit Breaking:** Implement mechanisms to prevent a single "hot" post from cascading failures across the Feed Builder service.
        *   **Dedicated Redis Instances:** Use separate Redis instances or clusters for feed storage to isolate performance from other Redis caches.

2.  **Redis Performance (Feed Storage):**
    *   **Problem:** Storing 500M users' feeds, each potentially with 1000 post IDs, could lead to massive memory consumption and high read/write contention on Redis.
    *   **Mitigation:**
        *   **Redis Cluster:** Use a Redis Cluster to shard data across multiple nodes, distributing memory and CPU load.
        *   **Feed Size Limits:** Strictly enforce limits on the number of posts stored per user's feed (e.g., 1000 latest posts). This keeps `ZADD` operations fast and memory usage predictable.
        *   **Memory Optimization:** Store only `post_id` and `created_at` in the sorted set. The `post_id` can be a compact integer.
        *   **Read Replicas:** For very high read traffic, Redis read replicas can offload some read requests, though `ZADD` operations still hit the primary.

3.  **PostgreSQL `followers` table reads (for fan-out):**
    *   **Problem:** When a post is made, the Feed Builder needs to query `followers` to find all followers of the author. For a user with 500 followers, this is fine. For a user with 10M followers, this query becomes a bottleneck.
    *   **Mitigation:**
        *   **Indexing:** Ensure a strong index on `followers.followed_id` (`CREATE INDEX idx_followed_id ON followers (followed_id);`).
        *   **Read Replicas:** Route these fan-out queries to PostgreSQL read replicas to offload the primary database.
        *   **Denormalization/Caching:** For extremely popular accounts, the list of their followers could be pre-cached in Redis or a dedicated service, or even denormalized into a separate table optimized for this read pattern. This is a more advanced optimization.
        *   **Reverse Fan-out (Pull Model):** If the number of followers is *extremely* high (e.g., billions), a pure fan-out on write becomes impractical. A "fan-out on read" or "pull model" might be considered, where each user's feed is generated by querying the posts of their followed users *at read time*. However, the problem statement explicitly states the current system is too slow with this approach, so we need to stick to fan-out on write for the core feed. A hybrid approach could be to pre-compute for a subset of followers, and pull for the rest.

4.  **PostgreSQL `posts` table reads (for post details):**
    *   **Problem:** After fetching `post_id`s from Redis, the API server needs to retrieve full post details. A batch `SELECT * FROM posts WHERE id IN (:id1, :id2, ...)` can still be slow if the `IN` clause is very large or if the database is under heavy load.
    *   **Mitigation:**
        *   **Read Replicas:** Use PostgreSQL read replicas extensively for these queries.
        *   **Post Details Cache:** Implement a dedicated Redis cache for individual post details, keyed by `post_id`. This would be populated on first read or proactively for popular posts.
        *   **Optimized Query:** Ensure an index on `posts.id` (which is usually the primary key).
        *   **Limit Feed Size:** By limiting the number of posts in a feed (e.g., 100-200), the `IN` clause size is kept manageable.

### Going further

If the requirement was not just chronological order, but also a ranking algorithm that prioritizes posts based on engagement (likes, comments) from the last hour, in addition to recency, the design would need significant modifications.

The core challenge is that engagement metrics are dynamic and change frequently, making pre-computation of a *ranked* feed much harder and more resource-intensive.

Here's how the design would change:

1.  **Feed Storage in Redis:**
    *   Instead of just storing `(created_at, post_id)` in a Redis Sorted Set, we'd need to store `(score, post_id)`. The `score` would be a composite value reflecting both recency and engagement.
    *   The `score` would need to be updated frequently.

2.  **Introduction of an Engagement Service:**
    *   A new service, let's call it the **Engagement Service**, would be responsible for tracking likes, comments, and other engagement metrics in real-time.
    *   It would consume events from the Message Queue (e.g., `like_events`, `comment_events`) and update engagement counters, perhaps in a fast key-value store like Redis or a time-series database.
    *   **Schema Example (Redis):**
        *   `post_engagement:post_id`: Hash storing `likes_count`, `comments_count`, `shares_count`.
        *   `post_engagement_hourly:post_id`: Hash storing `likes_count_last_hour`, `comments_count_last_hour`. This would be updated via a sliding window or time-bucketed counts.

3.  **Real-time Score Calculation and Feed Update:**
    *   **Score Calculation Logic:** The ranking algorithm would define how `created_at`, `likes_count_last_hour`, `comments_count_last_hour`, etc., combine into a single `score`. For example: `score = (post.created_at.timestamp() / 1000) + (likes_count_last_hour * WEIGHT_LIKES) + (comments_count_last_hour * WEIGHT_COMMENTS)`. The `created_at` component ensures recency is still a strong factor.
    *   **Feed Builder Enhancement:** The Feed Builder would no longer just add new posts. It would also need to:
        *   **Re-score Posts:** Periodically (e.g., every minute or every 5 minutes), it would iterate through active posts in users' feeds, query the Engagement Service for updated metrics, recalculate the score, and update the `score` in the Redis Sorted Set (`ZADD user_feed:follower_id new_score post_id`). `ZADD` can update existing members.
        *   **Triggered Re-scoring:** More efficiently, the Engagement Service could publish "Post Engagement Updated" events to the Message Queue. The Feed Builder would consume these events, re-score the affected post, and then update the score for *all* followers' feeds containing that post. This is a much more complex fan-out on update.
        *   **Complexity:** This "fan-out on update" is significantly more complex than "fan-out on write" because a single post's score change affects potentially millions of feeds.

4.  **Hybrid Approach (Pull for Ranking):**
    *   Given the complexity of real-time score updates for millions of feeds, a more practical approach for highly dynamic ranking might be a hybrid model:
        *   **Pre-computed Recency Feed:** The Feed Builder still pre-computes a chronologically ordered feed (as in the original design) into Redis. This provides a fast baseline.
        *   **API Server Ranking:** When a user requests their feed:
            1.  The API server fetches the top N (e.g., 200) `post_id`s from the pre-computed recency feed in Redis.
            2.  It then queries the Engagement Service (or a cache of engagement metrics) for the latest engagement data for these N posts.
            3.  The API server applies the ranking algorithm locally to these N posts.
            4.  It fetches full post details for the *ranked* posts and returns them.
        *   **Trade-offs:** This shifts the ranking computation back to read time, but only for a small subset of posts (N). It ensures freshness of ranking without massive fan-out updates. The "N" needs to be chosen carefully to balance freshness and performance. If N is too small, highly engaging older posts might be missed. If N is too large, the ranking step becomes slow.

5.  **Dedicated Ranking Service:**
    *   For very sophisticated ranking, a dedicated **Ranking Service** might be introduced.
    *   It would consume post and engagement events, maintain a graph of user interactions, and use machine learning models to generate personalized ranked feeds.
    *   This service would then push the ranked `post_id`s into the user's feed in Redis, similar to the Feed Builder, but with a much more complex internal logic.

**Summary of Changes for Ranking:**

*   **Data Model:** Redis feed stores `(score, post_id)`. Engagement metrics are tracked in a separate service/cache.
*   **Feed Builder Role:** Expands from just adding new posts to also *re-scoring* and *updating* existing posts in follower feeds based on changing engagement. This is the most complex part.
*   **New Service:** An Engagement Service is needed to track real-time metrics.
*   **Consistency:** The ranked feed would have a slightly higher latency for score updates compared to simple chronological order, as score recalculations and updates take time.
*   **Complexity:** Significantly increases system complexity, operational overhead, and computational resources due to continuous re-scoring and feed updates.
*   **Hybrid Approach:** A hybrid "pull for ranking" model is a common way to mitigate the complexity of full "fan-out on update" for dynamic ranking.
