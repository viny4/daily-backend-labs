## Scenario

Your team maintains the backend for a B2B SaaS platform that helps companies manage their employee expenses. A core feature allows employees to submit expense reports, which then go through an approval workflow. When an expense report is approved by a manager, a financial transaction is automatically generated and recorded.

Lately, the `transactions` table has grown substantially, now containing over 100 million rows across thousands of enterprise clients. Each transaction is linked to an `expense_report_id` and has a `transaction_date` (timestamp), `amount`, and `currency`.

A new critical requirement has emerged: for auditors, company administrators need to quickly view the **cumulative daily transaction volume** for a *specific client* over any given date range (e.g., "show me the total amount transacted each day in EUR for client X from January 1st to March 31st").

The existing query that aggregates this data directly from the `transactions` table is now unacceptably slow, often taking 15-30 seconds for a 90-day range for a large client, which exceeds the 5-second latency budget for this audit-critical report. Furthermore, this report is frequently accessed.

## Requirements

The current system needs to provide an efficient way to calculate and retrieve the cumulative daily transaction volume for a given client, currency, and date range. The solution must scale to many clients and not directly scan the `transactions` table for each report request. It should also be robust to potential data inconsistencies and ensure data integrity.

Constraints:
*   **Scale**: Over 100 million transactions in total, with some large clients having tens of millions of transactions.
*   **Latency**: Report generation for a 90-day range for any client must complete within 5 seconds.
*   **Concurrency**: Multiple administrators from different clients might request these reports concurrently.
*   **Data Freshness**: Data should be "fresh" up to the previous day; real-time reporting for the current day is not required for this specific view.
*   **Infrastructure**: You have access to PostgreSQL, Python/Django, and typical AWS services.

## Worked answer

### 1. Data Structure(s)

To efficiently support the cumulative daily transaction volume requirement, I would introduce a new aggregate table, often referred to as a "materialized view" or "summary table."

**Proposed Data Structure: `daily_client_currency_transactions` table**

This table will store pre-aggregated daily transaction volumes for each client and currency.

```sql
CREATE TABLE daily_client_currency_transactions (
    id BIGSERIAL PRIMARY KEY,
    client_id BIGINT NOT NULL,
    transaction_date DATE NOT NULL,
    currency VARCHAR(3) NOT NULL,
    total_amount NUMERIC(19, 4) NOT NULL DEFAULT 0.0000,
    transaction_count INT NOT NULL DEFAULT 0,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);

CREATE UNIQUE INDEX idx_daily_client_currency_transactions_unique
ON daily_client_currency_transactions (client_id, transaction_date, currency);

CREATE INDEX idx_daily_client_currency_transactions_client_date_currency
ON daily_client_currency_transactions (client_id, transaction_date, currency);

-- Optional: If queries frequently filter by currency first for all clients,
-- though the unique index covers the primary query pattern.
-- CREATE INDEX idx_daily_client_currency_transactions_currency_date
-- ON daily_client_currency_transactions (currency, transaction_date);
```

**Justification:**

*   **Reads (Report Generation):**
    *   **Time Complexity:** O(M log N + K) or O(K) where M is the number of clients, N is the number of unique `(client_id, transaction_date, currency)` combinations, and K is the number of days in the requested range.
        *   Specifically, with the `idx_daily_client_currency_transactions_client_date_currency` index, a query for a specific client, currency, and date range will perform an index scan. The time complexity will be close to **O(K)**, as it only needs to read K rows from the pre-aggregated table. This is significantly better than scanning potentially millions of rows in the `transactions` table.
    *   **Space Complexity:** O(C * D * U) where C is the number of clients, D is the number of days since the first transaction, and U is the number of unique currencies. This is a fixed space cost per day per client per currency, which is much smaller than the `transactions` table (O(Total Transactions)). For example, if we have 1000 clients, 5 years of data (1825 days), and 5 currencies, the table would have approximately 1000 * 1825 * 5 = 9.125 million rows, which is manageable for PostgreSQL.

*   **Writes (Updates to Underlying Data - `transactions` table):**
    *   **Time Complexity:** The insertion of a new transaction into the `transactions` table itself remains O(log N) due to indexing. The *update* to this aggregate table is decoupled and happens asynchronously (see section 2). When the aggregation job runs, it will typically involve:
        *   Scanning new/modified transactions for a given day: O(T_day) where T_day is the number of transactions for that day.
        *   Performing a `GROUP BY` and `SUM` operation: O(T_day).
        *   Performing an `UPSERT` (INSERT ON CONFLICT UPDATE) into `daily_client_currency_transactions`: O(log (C*D*U)) per unique `(client_id, transaction_date, currency)` combination for that day.
        *   Overall, the daily aggregation job will be proportional to the number of new transactions for that day, which is acceptable for a batch process.
    *   **Space Complexity:** The space complexity for writes to the `transactions` table is O(1) per transaction. The aggregate table's space complexity is discussed above and is only affected when new `(client_id, transaction_date, currency)` combinations appear, or new days are processed.

**Why this approach is superior to direct `transactions` table queries:**

The original query `SELECT transaction_date::date, SUM(amount) FROM transactions WHERE client_id = X AND currency = Y AND transaction_date BETWEEN Z AND W GROUP BY transaction_date::date` requires:
1.  Scanning a large portion of the `transactions` table (potentially millions of rows for a large client).
2.  Filtering by `client_id`, `currency`, and `transaction_date`.
3.  Performing a `GROUP BY` and `SUM` operation across all matching rows.

Even with indexes on `(client_id, transaction_date, currency)`, the `SUM` aggregation still requires reading all relevant rows and performing the aggregation at query time. For 100 million rows, even if only 1 million rows match, reading and summing them can be slow. The `daily_client_currency_transactions` table pre-computes these sums, reducing the read operation to a simple index scan and retrieval of K rows.

### 2. Population and Update Process

The `daily_client_currency_transactions` table will be populated and kept up-to-date using a daily batch job. This approach aligns with the "previous day freshness" requirement.

**High-level Process:**

1.  **Initial Backfill (One-time):**
    *   For all historical data in the `transactions` table, run a large batch job to populate `daily_client_currency_transactions`. This can be done in chunks (e.g., month by month, or year by year) to manage resource usage.
    *   Example SQL for backfill:
        ```sql
        INSERT INTO daily_client_currency_transactions (client_id, transaction_date, currency, total_amount, transaction_count)
        SELECT
            t.client_id,
            t.transaction_date::date AS transaction_date,
            t.currency,
            SUM(t.amount) AS total_amount,
            COUNT(t.id) AS transaction_count
        FROM
            transactions t
        GROUP BY
            t.client_id,
            t.transaction_date::date,
            t.currency
        ON CONFLICT (client_id, transaction_date, currency) DO UPDATE SET
            total_amount = EXCLUDED.total_amount,
            transaction_count = EXCLUDED.transaction_count,
            updated_at = NOW();
        ```
    *   This backfill should be run during off-peak hours and might take a significant amount of time (hours to days) depending on the data volume.

2.  **Daily Incremental Update (Scheduled Job):**
    *   A scheduled job (e.g., a cron job, AWS Lambda, or a dedicated worker process) will run once every 24 hours, typically after midnight UTC, to process transactions from the *previous day*.
    *   **Target Date:** The job will determine the date to process, which is `yesterday` (e.g., if it runs on 2026-11-15, it processes data for 2026-11-14).
    *   **Process:**
        *   **Step 1: Identify relevant transactions.** Query the `transactions` table for all transactions that occurred on the `target_date`.
        *   **Step 2: Aggregate.** Group these transactions by `client_id` and `currency`, summing the `amount` and counting the `transactions`.
        *   **Step 3: Upsert.** Insert or update the aggregated results into the `daily_client_currency_transactions` table.
    *   **Example Python/Django pseudocode for the daily job:**

        ```python
        from datetime import date, timedelta
        from django.db import connection, transaction

        def update_daily_aggregates(target_date: date):
            """
            Aggregates transaction data for a specific target_date
            and updates the daily_client_currency_transactions table.
            """
            print(f"Processing aggregates for date: {target_date}")

            with transaction.atomic():
                with connection.cursor() as cursor:
                    # SQL to calculate aggregates for the target_date
                    # and upsert them into the summary table.
                    # Using a CTE (WITH clause) for clarity and potential performance
                    # if the source query is complex.
                    sql = """
                    WITH daily_aggregates AS (
                        SELECT
                            t.client_id,
                            t.transaction_date::date AS transaction_date,
                            t.currency,
                            SUM(t.amount) AS total_amount,
                            COUNT(t.id) AS transaction_count
                        FROM
                            transactions t
                        WHERE
                            t.transaction_date::date = %s
                        GROUP BY
                            t.client_id,
                            t.transaction_date::date,
                            t.currency
                    )
                    INSERT INTO daily_client_currency_transactions
                        (client_id, transaction_date, currency, total_amount, transaction_count)
                    SELECT
                        da.client_id,
                        da.transaction_date,
                        da.currency,
                        da.total_amount,
                        da.transaction_count
                    FROM
                        daily_aggregates da
                    ON CONFLICT (client_id, transaction_date, currency) DO UPDATE SET
                        total_amount = EXCLUDED.total_amount,
                        transaction_count = EXCLUDED.transaction_count,
                        updated_at = NOW();
                    """
                    cursor.execute(sql, [target_date])
                print(f"Successfully updated aggregates for {target_date}")

        def run_daily_aggregation_job():
            """
            Main function for the daily scheduled job.
            Processes data for the previous day.
            """
            yesterday = date.today() - timedelta(days=1)
            update_daily_aggregates(yesterday)

        # To be called by a scheduler (e.g., manage.py command, Celery beat, cron)
        # Example: python manage.py run_aggregation_job
        ```

3.  **Error Handling and Retries:**
    *   Implement robust error handling for the aggregation job (e.g., database connection issues, query failures).
    *   Use a retry mechanism (e.g., exponential backoff) for transient errors.
    *   Consider a mechanism to re-run the job for specific dates if data is found to be inconsistent or the job failed silently. This could involve storing the last successful run date or having a "reprocess" function.

4.  **Monitoring:**
    *   Monitor the execution time and success/failure rate of the daily aggregation job.
    *   Set up alerts for job failures or unusually long execution times.

### 3. Pseudocode for `get_daily_transaction_volume`

This function will query the `daily_client_currency_transactions` table directly.

```python
from datetime import date
from typing import List, Dict, Any
from django.db import connection

def get_daily_transaction_volume(
    client_id: int,
    currency: str,
    start_date: date,
    end_date: date
) -> List[Dict[str, Any]]:
    """
    Retrieves the cumulative daily transaction volume for a given client,
    currency, and date range from the pre-aggregated table.

    Args:
        client_id: The ID of the client.
        currency: The 3-letter currency code (e.g., 'EUR', 'USD').
        start_date: The start date of the range (inclusive).
        end_date: The end date of the range (inclusive).

    Returns:
        A list of dictionaries, where each dictionary represents a day's
        transaction volume, e.g.,
        [
            {'date': '2026-01-01', 'total_amount': '1234.56', 'transaction_count': 10},
            {'date': '2026-01-02', 'total_amount': '789.00', 'transaction_count': 5},
            ...
        ]
    """
    results = []
    with connection.cursor() as cursor:
        sql = """
        SELECT
            transaction_date,
            total_amount,
            transaction_count
        FROM
            daily_client_currency_transactions
        WHERE
            client_id = %s AND
            currency = %s AND
            transaction_date BETWEEN %s AND %s
        ORDER BY
            transaction_date ASC;
        """
        cursor.execute(sql, [client_id, currency, start_date, end_date])
        # Fetch all results and convert them into a list of dictionaries
        columns = [col[0] for col in cursor.description]
        for row in cursor.fetchall():
            results.append(dict(zip(columns, row)))

    # Handle missing days: If a day in the range has no transactions,
    # the query won't return a row for it. The UI might expect a 0 for those days.
    # This post-processing step ensures all days in the range are represented.
    # Alternatively, this can be handled in the SQL query using a `GENERATE_SERIES`
    # and `LEFT JOIN`, but for a small range (90 days), Python post-processing is fine.
    
    # Create a map for quick lookup of fetched data
    fetched_data_map = {item['transaction_date']: item for item in results}
    
    # Generate a list of all dates in the range
    current_date = start_date
    all_dates_in_range = []
    while current_date <= end_date:
        all_dates_in_range.append(current_date)
        current_date += timedelta(days=1)

    final_report_data = []
    for d in all_dates_in_range:
        if d in fetched_data_map:
            final_report_data.append({
                'date': d.isoformat(), # Convert date object to string for API response
                'total_amount': str(fetched_data_map[d]['total_amount']), # Convert Decimal to string
                'transaction_count': fetched_data_map[d]['transaction_count']
            })
        else:
            # No transactions for this client/currency on this specific day
            final_report_data.append({
                'date': d.isoformat(),
                'total_amount': '0.0000',
                'transaction_count': 0
            })

    return final_report_data

```

### Going further

**Trade-offs involved in the chosen approach:**

1.  **Storage Costs vs. Read Performance:**
    *   **Trade-off:** We are explicitly trading increased storage costs for significantly improved read performance.
    *   **Explanation:** The `daily_client_currency_transactions` table is a denormalized, pre-aggregated view of the data. It duplicates information (client_id, currency, date) that already exists in the `transactions` table, plus stores the aggregated `total_amount` and `transaction_count`. This requires additional disk space.
    *   **Impact:** For 1000 clients, 5 years of data, and 5 currencies, we estimated ~9 million rows in the aggregate table. Each row is relatively small (ID, client_id, date, currency, amount, count, timestamps). This is a manageable size for PostgreSQL and a small fraction of the 100 million+ rows in the `transactions` table. The cost of this additional storage is negligible compared to the business value of fast audit reports and the operational cost of slow queries impacting user experience or even database stability.
    *   **Breaking point at 10x scale:** If the number of clients or currencies grew by 10x, or the data retention period grew by 10x, the aggregate table could grow to hundreds of millions or even billions of rows. While still potentially manageable for PostgreSQL, it would start to incur more significant storage costs and index maintenance overhead. At that scale, partitioning the `daily_client_currency_transactions` table by `client_id` or `transaction_date` would become crucial for continued performance and manageability.

2.  **Data Freshness vs. Write Performance/Complexity:**
    *   **Trade-off:** We accept "previous day freshness" (daily batch updates) instead of real-time updates. This simplifies the write path and improves `transactions` table write performance.
    *   **Explanation:** If we needed real-time cumulative volumes, every `transaction` insert would need to trigger an update to the aggregate table. This would add latency and complexity to the critical path of transaction processing (e.g., using database triggers, message queues, or synchronous updates). By processing data once a day for the previous day, we completely decouple the write path of `transactions` from the aggregate table updates.
    *   **Impact:** The `transactions` table can handle high-volume inserts without being bottlenecked by aggregate calculations. The aggregation job can run during off-peak hours, utilizing dedicated resources without affecting user-facing services.
    *   **Breaking point at 10x scale:** If the daily transaction volume becomes extremely high (e.g., billions of transactions per day), even the daily batch job might struggle to complete within its window. In such a scenario, more sophisticated streaming aggregation (e.g., using Apache Kafka and Flink/Spark Streaming) or micro-batching throughout the day would be necessary.

**Handling potential eventual consistency issues:**

Eventual consistency arises because the `daily_client_currency_transactions` table is updated asynchronously and with a delay (up to 24 hours). This means there's a window where the aggregate table does not reflect the absolute latest state of the `transactions` table.

1.  **Clear Communication to Users:**
    *   The most important step is to clearly communicate the data freshness policy to administrators. The report UI should state: "Data is current up to the end of the previous day UTC." This manages expectations and prevents confusion.

2.  **Monitoring and Alerting for Lag:**
    *   Implement robust monitoring for the aggregation job. Track its completion time and ensure it runs successfully every day.
    *   Measure the "lag" between the current date and the latest `transaction_date` successfully processed and aggregated. If this lag exceeds the expected 24 hours (e.g., due to job failures), trigger alerts to the operations team.
    *   Example check: `SELECT MAX(transaction_date) FROM daily_client_currency_transactions;` compared to `date.today() - timedelta(days=1)`.

3.  **Idempotent Updates and Retries:**
    *   The `UPSERT` (INSERT ON CONFLICT UPDATE) mechanism used in the daily job is crucial. It ensures that if the job runs multiple times for the same day, it produces the same correct result without creating duplicate entries or incorrect sums. This allows for safe retries in case of transient failures.

4.  **Reconciliation Mechanism:**
    *   For critical audit data, a periodic reconciliation process might be necessary. This could be a weekly or monthly job that:
        *   Compares the `SUM(amount)` and `COUNT(id)` from the `transactions` table for a given `client_id`, `transaction_date`, and `currency` against the corresponding entry in `daily_client_currency_transactions`.
        *   If discrepancies are found, it logs them and potentially triggers an automatic correction or manual investigation.
    *   This helps catch subtle bugs in the aggregation logic or data corruption that might not be immediately apparent.

5.  **Handling "Current Day" Data (if required in the future):**
    *   If a future requirement demands real-time data for the *current day*, the approach would need to be augmented. For example:
        *   The report could show aggregated data from `daily_client_currency_transactions` for `start_date` to `yesterday`.
        *   For `today`, it could run a lightweight, real-time query directly against the `transactions` table, filtering only for `today`'s data. This query would be much faster than the original 90-day query, as it only scans a single day's transactions.
        *   This "hybrid" approach offers the best of both worlds: fast historical data and fresh current-day data, with the complexity isolated to the current day's smaller dataset.

By clearly defining the freshness contract and implementing robust monitoring and reconciliation, the eventual consistency trade-off becomes manageable and acceptable for this specific business requirement.
