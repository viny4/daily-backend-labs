## Scenario

You're a backend engineer at a rapidly growing SaaS company. Your primary product manages customer orders and their associated line items. The `Order` table, which holds millions of records, has a `customer_id` and a `created_at` timestamp. Each order can have many `LineItem` records, stored in a separate table, linked by `order_id`.

A new feature requires displaying, for any given customer, their *N* most recent orders, along with the total quantity of a specific product (`product_sku: "PROD-XYZ"`) across all line items within those *N* orders. This display needs to be fast—ideally under 100ms for customers with hundreds of thousands of orders. Currently, retrieving all orders for a customer and then filtering/aggregating line items is unacceptably slow for larger customers, often taking several seconds. The `LineItem` table is also growing quickly, now exceeding 100 million rows.

The system processes thousands of new orders and tens of thousands of new line items per minute. The primary constraint is latency for the read operation, especially as the number of orders per customer grows. Multi-tenancy means each `customer_id` is unique and represents a distinct customer.

## Worked answer

### 1. Proposed Database Query

To retrieve the *N* most recent orders for a given `customer_id` and the aggregated quantity of `PROD-XYZ` across those *N* orders, we will use a combination of a new materialized view and a standard SQL query.

**New Database Object:** `customer_order_product_summary` (Materialized View)

```sql
-- This materialized view will store pre-aggregated data for quick retrieval.
-- It needs to be refreshed periodically.
CREATE MATERIALIZED VIEW customer_order_product_summary AS
SELECT
    o.customer_id,
    o.order_id,
    o.created_at,
    COALESCE(SUM(li.quantity) FILTER (WHERE li.product_sku = 'PROD-XYZ'), 0) AS prod_xyz_quantity
FROM
    "Order" o
JOIN
    LineItem li ON o.order_id = li.order_id
GROUP BY
    o.customer_id, o.order_id, o.created_at
WITH NO DATA; -- We will populate it later with a refresh.

-- Create unique index for efficient lookups and refreshes
CREATE UNIQUE INDEX idx_customer_order_product_summary_customer_order ON customer_order_product_summary (customer_id, order_id);
CREATE INDEX idx_customer_order_product_summary_customer_created ON customer_order_product_summary (customer_id, created_at DESC);
```

**Proposed Query:**

Given `customer_id = 123` and `N = 10`:

```sql
SELECT
    cops.order_id,
    cops.created_at,
    cops.prod_xyz_quantity
FROM
    customer_order_product_summary cops
WHERE
    cops.customer_id = 123
ORDER BY
    cops.created_at DESC
LIMIT 10;
```

**Explanation:**

1.  **Materialized View (`customer_order_product_summary`):** This view pre-calculates the `prod_xyz_quantity` for each individual order. Instead of joining `Order` and `LineItem` tables and aggregating on the fly for every query, which is expensive, we store this aggregated value.
2.  **Filtering by `customer_id`:** The `WHERE cops.customer_id = 123` clause efficiently narrows down the results to a specific customer. The `idx_customer_order_product_summary_customer_created` index (on `customer_id`, `created_at DESC`) is crucial here.
3.  **Ordering by `created_at DESC`:** This sorts the orders from most recent to oldest. The index `idx_customer_order_product_summary_customer_created` also supports this ordering directly, avoiding a sort operation.
4.  **`LIMIT N`:** This retrieves only the top *N* most recent orders. Because the data is already sorted by the index, the database can stop scanning once *N* rows are found, making this operation very efficient.

This approach leverages the pre-computation of the materialized view to avoid expensive joins and aggregations at query time, and then uses efficient indexing to quickly retrieve the top *N* results for a specific customer.

### 2. New Database Objects and Their Necessity

We will create one new database object: a **Materialized View**.

1.  **`customer_order_product_summary` (Materialized View):**
    *   **Schema:**
        ```sql
        CREATE MATERIALIZED VIEW customer_order_product_summary AS
        SELECT
            o.customer_id,
            o.order_id,
            o.created_at,
            COALESCE(SUM(li.quantity) FILTER (WHERE li.product_sku = 'PROD-XYZ'), 0) AS prod_xyz_quantity
        FROM
            "Order" o
        JOIN
            LineItem li ON o.order_id = li.order_id
        GROUP BY
            o.customer_id, o.order_id, o.created_at;
        ```
    *   **Purpose:** The primary bottleneck in the original scenario is the need to join `Order` and `LineItem` tables and then aggregate quantities for a specific product SKU. For customers with many orders and each order having many line items, this becomes extremely slow. A materialized view pre-computes this aggregation for *every* order. This means that when a query comes in, the expensive join and sum operations have already been performed, and the query only needs to read from the pre-computed view.
    *   **Necessity:** It transforms a complex, CPU-intensive, and I/O-intensive query into a simple lookup and sort operation, drastically reducing query latency.

2.  **Indexes on `customer_order_product_summary`:**
    *   `CREATE UNIQUE INDEX idx_customer_order_product_summary_customer_order ON customer_order_product_summary (customer_id, order_id);`
        *   **Purpose:** Ensures uniqueness and provides a primary key-like access path if we ever need to look up a specific order within the materialized view. Also useful for incremental refreshes.
    *   `CREATE INDEX idx_customer_order_product_summary_customer_created ON customer_order_product_summary (customer_id, created_at DESC);`
        *   **Purpose:** This is the critical index for the proposed query. It allows the database to:
            *   Efficiently filter by `customer_id`.
            *   Retrieve rows already sorted by `created_at` in descending order.
            *   Perform an "index-only scan" if all required columns (`order_id`, `created_at`, `prod_xyz_quantity`) are covered by the index or can be fetched quickly.
        *   **Necessity:** Without this index, even with the materialized view, the database would have to scan all orders for a given customer and then sort them, which would be slow for customers with hundreds of thousands of orders. This index allows for very fast "top-N" queries.

### 3. Data Consistency for Aggregated Quantity

Ensuring data consistency with high write volume (thousands of new orders, tens of thousands of new line items per minute) requires a robust refresh strategy for the materialized view.

**Strategy: Incremental Refresh with Periodic Full Refresh**

1.  **Initial Population:**
    ```sql
    REFRESH MATERIALIZED VIEW customer_order_product_summary;
    ```
    This will take a long time initially but needs to be done once.

2.  **Incremental Refresh Mechanism:**
    Since the underlying tables (`Order`, `LineItem`) are constantly changing, we cannot use `REFRESH MATERIALIZED VIEW CONCURRENTLY` directly on a complex join with aggregation in many database systems (e.g., PostgreSQL prior to very recent versions, and even then, it has limitations). Instead, we will implement a custom incremental refresh strategy.

    We'll need two additional tables to track changes:

    *   `order_updates_log`: A simple log of `order_id`s that have been created or modified.
    *   `line_item_updates_log`: A simple log of `order_id`s whose line items have been created, modified, or deleted.

    These logs can be populated using database triggers or by the application logic creating/updating orders and line items.

    **Example Trigger (PostgreSQL):**

    ```sql
    -- For Order table
    CREATE TABLE order_updates_log (
        order_id BIGINT NOT NULL,
        updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
    );
    CREATE INDEX idx_order_updates_log_order_id ON order_updates_log (order_id);

    CREATE OR REPLACE FUNCTION log_order_update()
    RETURNS TRIGGER AS $$
    BEGIN
        INSERT INTO order_updates_log (order_id) VALUES (NEW.order_id);
        RETURN NEW;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER trg_order_update
    AFTER INSERT OR UPDATE OF created_at ON "Order"
    FOR EACH ROW EXECUTE FUNCTION log_order_update();

    -- For LineItem table
    CREATE TABLE line_item_updates_log (
        order_id BIGINT NOT NULL,
        updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
    );
    CREATE INDEX idx_line_item_updates_log_order_id ON line_item_updates_log (order_id);

    CREATE OR REPLACE FUNCTION log_line_item_update()
    RETURNS TRIGGER AS $$
    BEGIN
        INSERT INTO line_item_updates_log (order_id) VALUES (NEW.order_id);
        RETURN NEW;
    END;
    $$ LANGUAGE plpgsql;

    CREATE TRIGGER trg_line_item_update
    AFTER INSERT OR UPDATE OR DELETE ON LineItem
    FOR EACH ROW EXECUTE FUNCTION log_line_item_update();
    ```

    **Incremental Refresh Process (Scheduled Job, e.g., every 1-5 minutes):**

    ```sql
    BEGIN;

    -- 1. Identify all affected order_ids from logs
    WITH affected_orders AS (
        SELECT order_id FROM order_updates_log
        UNION
        SELECT order_id FROM line_item_updates_log
    )
    -- 2. Recalculate the summary for these affected orders
    , recalculated_summaries AS (
        SELECT
            o.customer_id,
            o.order_id,
            o.created_at,
            COALESCE(SUM(li.quantity) FILTER (WHERE li.product_sku = 'PROD-XYZ'), 0) AS prod_xyz_quantity
        FROM
            "Order" o
        JOIN
            LineItem li ON o.order_id = li.order_id
        WHERE
            o.order_id IN (SELECT order_id FROM affected_orders)
        GROUP BY
            o.customer_id, o.order_id, o.created_at
    )
    -- 3. Update the materialized view
    INSERT INTO customer_order_product_summary (customer_id, order_id, created_at, prod_xyz_quantity)
    SELECT customer_id, order_id, created_at, prod_xyz_quantity
    FROM recalculated_summaries
    ON CONFLICT (customer_id, order_id) DO UPDATE SET
        created_at = EXCLUDED.created_at,
        prod_xyz_quantity = EXCLUDED.prod_xyz_quantity;

    -- 4. Clear the logs
    TRUNCATE TABLE order_updates_log;
    TRUNCATE TABLE line_item_updates_log;

    COMMIT;
    ```
    This process ensures that the materialized view is eventually consistent. The data might be a few minutes stale, but for a "most recent orders" display, this level of staleness is usually acceptable. The `ON CONFLICT` clause handles both new orders and updates to existing orders/line items.

3.  **Periodic Full Refresh (e.g., nightly or weekly):**
    ```sql
    REFRESH MATERIALIZED VIEW CONCURRENTLY customer_order_product_summary;
    ```
    Even with incremental updates, it's good practice to perform a full refresh periodically. This catches any edge cases or data inconsistencies that might have slipped through the incremental update logic (e.g., a bug in a trigger, or manual data changes that bypassed the triggers). `CONCURRENTLY` ensures the view remains available for queries during the refresh.

**Trade-offs for Consistency:**

*   **Eventual Consistency:** The data in the materialized view will not be real-time. There will be a delay (controlled by the refresh interval) between an order/line item being created/updated and its reflection in the view. For displaying "most recent orders," a few minutes of delay is generally acceptable.
*   **Increased Write Load:** Triggers add a small overhead to every `Order` and `LineItem` write. The incremental refresh job also adds load to the database, but it's batched and can be tuned.
*   **Complexity:** Managing triggers, log tables, and a scheduled refresh job adds operational complexity compared to a simple `REFRESH MATERIALIZED VIEW`.

### 4. Time Complexity Analysis

Let:
*   `C` be the number of customers.
*   `O_c` be the total number of orders for a specific customer.
*   `L_o` be the average number of line items per order.
*   `N` be the number of most recent orders to retrieve (1 to 50).
*   `S_mv` be the size of the `customer_order_product_summary` materialized view (number of rows).

**Original Approach (without materialized view):**

```sql
SELECT
    o.order_id,
    o.created_at,
    COALESCE(SUM(li.quantity) FILTER (WHERE li.product_sku = 'PROD-XYZ'), 0) AS prod_xyz_quantity
FROM
    "Order" o
JOIN
    LineItem li ON o.order_id = li.order_id
WHERE
    o.customer_id = 123
GROUP BY
    o.order_id, o.created_at
ORDER BY
    o.created_at DESC
LIMIT 10;
```

*   **Filtering `Order` by `customer_id`:** `O(log(C * O_avg))` if `customer_id` is indexed, then `O(O_c)` to retrieve all orders for the customer.
*   **Joining `LineItem`:** For each of `O_c` orders, potentially scan `L_o` line items. This is roughly `O(O_c * L_o)` in the worst case if `order_id` in `LineItem` is not indexed, or `O(O_c * log(L_total))` if `order_id` in `LineItem` is indexed (where `L_total` is total line items).
*   **Aggregation (`SUM`):** `O(O_c * L_o)` to sum quantities across all line items for all `O_c` orders.
*   **Sorting (`ORDER BY`):** `O(O_c * log(O_c))` to sort all orders for the customer.
*   **Limiting (`LIMIT N`):** `O(N)` after sorting.

**Overall Time Complexity (Original):** Dominated by the join, aggregation, and sort. Approximately `O(O_c * L_o + O_c * log(O_c))`.
For `O_c = 100,000` and `L_o = 5`, this is `100,000 * 5 + 100,000 * log(100,000)` which is very large, explaining the "several seconds" latency.

**Proposed Solution (with Materialized View and Indexes):**

```sql
SELECT
    cops.order_id,
    cops.created_at,
    cops.prod_xyz_quantity
FROM
    customer_order_product_summary cops
WHERE
    cops.customer_id = 123
ORDER BY
    cops.created_at DESC
LIMIT 10;
```

*   **Filtering and Ordering (`WHERE customer_id = X ORDER BY created_at DESC`):** This operation directly uses the `idx_customer_order_product_summary_customer_created` index. The index is a B-tree on `(customer_id, created_at DESC)`.
    *   Finding the starting point for `customer_id = 123` is `O(log(S_mv))`.
    *   Scanning the index to find the top `N` orders for that customer is `O(N)`. This is because the index is already sorted by `created_at DESC` within each `customer_id` partition. The database only needs to traverse `N` leaf nodes in the index.
*   **Retrieving data:** If `prod_xyz_quantity` is part of the index (or an included column), it's an index-only scan, `O(N)`. If not, it's `O(N)` to fetch `N` rows from the table after the index scan.

**Overall Time Complexity (Proposed Solution):** `O(log(S_mv) + N)`.

**Analysis as `O_c` increases:**

*   The `log(S_mv)` term grows very slowly with the total number of orders across all customers.
*   The `N` term is constant (N=50 max).
*   Crucially, the complexity **does not depend on `O_c` (the number of orders for the specific customer)** beyond the initial `log(S_mv)` lookup. This is the key improvement. For a customer with hundreds of thousands of orders, the query will still be `O(log(S_mv) + N)`, which is extremely fast (tens of milliseconds).

**Conclusion:** The proposed solution transforms a query with complexity dependent on the customer's total orders (`O_c`) into one that is largely independent of `O_c`, making it consistently fast even for "super-customers."

### Going Further

If the requirement changed to displaying the total quantity of `PROD-XYZ` across *all* orders for a given customer, still needing sub-100ms latency for customers with millions of orders:

**Approach: Pre-aggregate at the Customer Level**

Instead of aggregating per order, we would create a new materialized view that aggregates the total quantity of `PROD-XYZ` for *each customer*.

**New Database Object:** `customer_product_total_summary` (Materialized View)

```sql
CREATE MATERIALIZED VIEW customer_product_total_summary AS
SELECT
    o.customer_id,
    COALESCE(SUM(li.quantity) FILTER (WHERE li.product_sku = 'PROD-XYZ'), 0) AS total_prod_xyz_quantity
FROM
    "Order" o
JOIN
    LineItem li ON o.order_id = li.order_id
GROUP BY
    o.customer_id
WITH NO DATA;

CREATE UNIQUE INDEX idx_customer_product_total_summary_customer_id ON customer_product_total_summary (customer_id);
```

**Proposed Query:**

Given `customer_id = 123`:

```sql
SELECT
    total_prod_xyz_quantity
FROM
    customer_product_total_summary
WHERE
    customer_id = 123;
```

**Explanation:**

*   **Materialized View (`customer_product_total_summary`):** This view pre-calculates the `total_prod_xyz_quantity` for *each customer*. This is a single row per customer.
*   **Query:** The query becomes a simple lookup by `customer_id` on this very small materialized view.

**Time Complexity:**

*   **Query:** `O(log(C))` where `C` is the number of customers. This is incredibly fast, as it's a direct index lookup on a table with `C` rows. It's independent of the number of orders (`O_c`) or line items (`L_o`) for that customer.

**Data Consistency:**

*   The consistency challenge remains similar to the previous solution. We would need an incremental refresh strategy. The `order_updates_log` and `line_item_updates_log` tables would still be useful. The refresh logic would be:
    1.  Identify affected `customer_id`s from the logs (by joining with `Order` to get `customer_id` from `order_id`).
    2.  Recalculate `total_prod_xyz_quantity` for these affected `customer_id`s.
    3.  Update `customer_product_total_summary` using `ON CONFLICT (customer_id) DO UPDATE`.
    4.  Clear logs.
    5.  Periodic full refresh.

**Trade-offs compared to the original solution (N most recent orders):**

*   **Pros:**
    *   **Extremely Fast Query Latency:** `O(log(C))` is significantly faster than `O(log(S_mv) + N)` for the previous solution, especially if `S_mv` is very large. It's a single row lookup.
    *   **Simpler Query:** The query itself is much simpler, just a `SELECT` with a `WHERE` clause.
    *   **Smaller Materialized View:** The `customer_product_total_summary` view will have `C` rows (one per customer), which is much smaller than `customer_order_product_summary` (one row per order, potentially millions of rows). This makes refreshes potentially faster and consumes less storage.

*   **Cons:**
    *   **Loss of Granularity:** This solution *only* provides the total quantity across all orders. It cannot be used to display the *N* most recent orders or any other order-specific details. If the requirement ever shifts back to needing order-level data, this view is insufficient.
    *   **Separate Solution:** This view is distinct from the `customer_order_product_summary` view. If both requirements (N most recent orders AND total across all orders) need to be met, you would likely need *both* materialized views, each serving its specific purpose. This increases the number of database objects to manage and refresh.
    *   **Refresh Complexity:** While the view is smaller, the incremental refresh logic still requires tracking changes and recalculating sums, which can be complex to implement correctly.

In summary, for the "total across all orders" requirement, pre-aggregating at the customer level is the most efficient approach, but it comes at the cost of losing order-level detail.
