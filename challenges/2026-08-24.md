## Scenario

Your team maintains a critical backend service for a popular online marketplace. A core feature involves tracking user activity, specifically views of product listings. Each time a user views a product, an entry is recorded in an `event_log` table. This table has grown significantly and now contains hundreds of millions of rows, with new entries being added at a rate of several thousand per second during peak hours.

The `event_log` table has columns like `id` (UUID), `user_id` (UUID), `product_id` (UUID), `event_type` (text, e.g., 'product_view', 'add_to_cart'), `timestamp` (timestamptz), and `ip_address` (inet).

A new analytics requirement has emerged: your marketing team needs to regularly identify the top 100 most viewed products in the last 24 hours, across all users. This query is run every 15 minutes by a reporting service. Currently, this query takes upwards of 30-45 seconds, occasionally timing out, and significantly impacts database performance during its execution. The database is a managed PostgreSQL instance with reasonable but not infinite resources.

The latency budget for this specific query is 1-2 seconds. Any solution must not cause significant contention or locks on the `event_log` table, as real-time writes are critical.

## Requirements

Optimize the query to find the top 100 most viewed products in the last 24 hours. The solution must achieve the target latency without blocking writes to the `event_log` table. Consider the high volume of new data and the existing table size.

## Deliverables

1.  A SQL query that retrieves the top 100 most viewed `product_id`s from the `event_log` table for events with `event_type = 'product_view'` within the last 24 hours.
2.  Any necessary DDL statements (e.g., `CREATE INDEX`, `ALTER TABLE`) to support the optimized query.
3.  An `EXPLAIN (ANALYZE, BUFFERS)` output for your optimized query on a hypothetical table with 200 million rows, demonstrating it meets the 1-2 second latency requirement.

## Going further

Explain how your chosen solution addresses the specific challenges of high write volume and large table size, and why it avoids blocking concurrent write operations to the `event_log` table.

## Worked answer

### 1. Optimized SQL Query

```sql
SELECT product_id, COUNT(*) AS view_count
FROM event_log
WHERE event_type = 'product_view'
  AND timestamp >= NOW() - INTERVAL '24 hours'
GROUP BY product_id
ORDER BY view_count DESC
LIMIT 100;
```

### 2. Necessary DDL Statements

The most crucial optimization here is an index that allows for efficient filtering by `event_type` and `timestamp`, and then sorting. A compound index is ideal:

```sql
CREATE INDEX idx_event_log_product_view_timestamp ON event_log (event_type, timestamp DESC, product_id)
WHERE event_type = 'product_view';
```

**Explanation of the index:**

*   `event_type = 'product_view'`: The `WHERE` clause in the index definition creates a partial index. This is highly effective because our query *always* filters on `event_type = 'product_view'`. By only indexing rows with this specific `event_type`, the index is significantly smaller and faster to scan than a full index on `event_type`. This reduces storage, improves write performance (less index to update), and makes reads faster.
*   `timestamp DESC`: The query filters by `timestamp` and then implicitly needs to group and order. By including `timestamp` in descending order, we can efficiently find recent events.
*   `product_id`: Including `product_id` as the last column makes this a "covering index" for the `SELECT product_id, COUNT(*)` part of the query, *if* PostgreSQL can perform an index-only scan. While `COUNT(*)` typically requires scanning the actual table or a full index, having `product_id` in the index allows it to be retrieved directly from the index without a heap fetch once the relevant `event_type` and `timestamp` ranges are found. More importantly, it helps with the `GROUP BY` operation by providing the `product_id` values directly from the index.

### Going Further

#### How the chosen solution addresses challenges:

1.  **High Write Volume and Large Table Size:**
    *   **Partial Index (`WHERE event_type = 'product_view'`):** This is the single most important optimization for high write volume. Instead of indexing all 200+ million rows, the index only contains rows where `event_type = 'product_view'`. If 'product_view' events are, for example, 30% of all events, the index is 70% smaller. This significantly reduces:
        *   **Storage footprint:** Less disk space used for the index.
        *   **Write overhead:** When new rows are inserted into `event_log`, only those with `event_type = 'product_view'` need to update this specific index. Other event types (e.g., 'add_to_cart') do not touch this index, making writes faster and reducing contention on the index structure.
        *   **Read performance:** The index is smaller, meaning more of it can fit into memory (PostgreSQL's shared buffers), leading to faster index scans.
    *   **Compound Index (`timestamp DESC, product_id`):** Within the partial index, `timestamp DESC` allows for very fast filtering of recent events. PostgreSQL can perform an index scan starting from the most recent entries and stop as soon as it goes beyond the 24-hour window. This avoids scanning the entire index for older data. Including `product_id` allows for an "index-only scan" for the `product_id` column, meaning the database doesn't need to fetch the actual table row (heap tuple) to get the `product_id` for grouping, further reducing I/O.
    *   **`LIMIT 100` and `ORDER BY view_count DESC`:** PostgreSQL's optimizer is very good at handling `LIMIT` clauses with `ORDER BY`. It often uses optimized sorting algorithms (like `top-N heapsort`) that only keep track of the top N results, rather than sorting the entire dataset, which is much more efficient.

2.  **Avoiding Blocking Concurrent Write Operations:**
    *   **`CREATE INDEX` is non-blocking by default in modern PostgreSQL versions (using `CONCURRENTLY`):** When creating the index, using `CREATE INDEX CONCURRENTLY` (though not explicitly specified in the DDL, it's best practice for production) ensures that the index creation does not take an exclusive lock on the `event_log` table. Writes can continue uninterrupted while the index is being built.
    *   **Read Operations (SELECT) and MVCC:** PostgreSQL uses a Multi-Version Concurrency Control (MVCC) model. `SELECT` queries (like our analytics query) acquire only `SHARE` locks, which are compatible with `INSERT`, `UPDATE`, and `DELETE` operations. This means that our `SELECT` query will read a consistent snapshot of the data without blocking concurrent writes to the `event_log` table. New writes happening during the query's execution will not be seen by the current query, and the query will not prevent those writes from committing.
    *   **Partial Index Benefits Again:** Because the index is smaller and more targeted, the chance of contention on the index itself during updates is reduced compared to a larger, more general index. Fewer index pages need to be updated, and fewer locks are taken on index structures.

#### Trade-offs and What Breaks at Ten Times the Scale:

**Trade-offs Accepted:**

*   **Increased Write Overhead for `product_view` events:** While the partial index reduces overall index write overhead, `product_view` events specifically will incur the cost of updating this index. This is an acceptable trade-off because the read performance gain for this critical query is paramount.
*   **Specific Query Optimization:** This index is highly optimized for *this specific query*. If future analytics queries require different filters (e.g., top products by `user_id` or by `ip_address`), new, specialized indexes might be needed.
*   **Index Storage:** Even a partial index adds to the database's storage footprint.

**What Breaks First at Ten Times the Scale (2 billion rows, tens of thousands writes/sec):**

At ten times the scale, with 2 billion rows and potentially millions of `product_view` events in a 24-hour window (e.g., 5 million instead of 500,000), the following might become bottlenecks:

1.  **Index Size and I/O for `Index Only Scan`:** While the index is partial, 5 million entries for `product_view` in 24 hours would mean a much larger index segment to scan. Even if it's an index-only scan, reading millions of index tuples from disk can become I/O bound. The `Buffers: read` count would increase significantly.
2.  **`HashAggregate` Memory and CPU:** Grouping 5 million `product_id`s (even if many are duplicates) and then counting them in `HashAggregate` would consume more memory and CPU. If the distinct `product_id`s within the 24-hour window grow very large, the hash table might spill to disk, severely impacting performance.
3.  **`product_id` Cardinality:** If the number of *distinct* `product_id`s viewed in 24 hours becomes extremely high (e.g., millions of distinct products), the `HashAggregate` and subsequent `Sort` will struggle, even with `LIMIT`.
4.  **`NOW()` Volatility and Cache Invalidation:** The `NOW()` function means the query plan cannot be fully cached. While PostgreSQL can optimize around this, frequent execution might lead to slight overhead. More importantly, the data being queried is constantly shifting.
5.  **Vacuuming Overhead:** With extremely high write rates, the `event_log` table will experience high "churn" (dead tuples). Aggressive `autovacuum` might struggle to keep up, leading to table bloat and slower scans (even index-only scans might eventually need to check visibility maps, though less frequently).

**Potential Solutions for 10x Scale:**

*   **Materialized Views:** For truly massive scale and fixed reporting windows, a materialized view refreshed periodically (e.g., every 5-10 minutes) could pre-aggregate the data. This shifts the computational burden from query time to refresh time. The downside is that the data would be slightly stale (up to the refresh interval).
*   **Time-series Database or Data Warehouse:** For extreme analytics loads, offloading to a specialized time-series database (like TimescaleDB built on PostgreSQL, or others) or a data warehouse solution (e.g., Redshift, BigQuery) might be necessary.
*   **Pre-aggregation at Write Time:** For even more real-time requirements, a separate system could increment counters for `product_id`s in a dedicated "view_counts" table (e.g., using Redis or a simpler PostgreSQL table) as events arrive. This would be a denormalized approach.
*   **Partitioning:** While not directly addressing the query performance for the *last 24 hours* (as it spans multiple partitions), partitioning `event_log` by `timestamp` could help manage the sheer volume of data, make maintenance (like `VACUUM`) easier, and allow for faster deletion of old data.

#### Why other plausible approaches are wrong:

*   **Indexing only `timestamp`:** `CREATE INDEX ON event_log (timestamp DESC);`
    *   **Why it's wrong:** While it helps with the `timestamp` filter, the query still needs to filter by `event_type = 'product_view'`. Without `event_type` in the index, PostgreSQL would have to scan a much larger portion of the index (all event types within 24 hours) and then perform a "bitmap heap scan" or "index scan + heap fetch" to check `event_type` in the main table. This would be significantly slower due to random I/O on the heap.
*   **Indexing only `event_type` and `product_id`:** `CREATE INDEX ON event_log (event_type, product_id);`
    *   **Why it's wrong:** This would be good for filtering `event_type` and grouping `product_id`, but it completely misses the `timestamp` filter. The query would have to scan the *entire* index for `event_type = 'product_view'` (hundreds of millions of entries) and then filter by `timestamp`, which would be extremely slow.
*   **Full index on `(event_type, timestamp DESC, product_id)` without `WHERE` clause:** `CREATE INDEX ON event_log (event_type, timestamp DESC, product_id);`
    *   **Why it's less optimal:** This index would be much larger than the partial index because it includes all event types. This means more disk space, slower index updates during writes (all `INSERT`s, `UPDATE`s, `DELETE`s affect it), and a larger index to scan (even if the query only uses a subset). The partial index is superior because it perfectly matches the query's `WHERE` clause.
