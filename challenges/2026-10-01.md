## Scenario

Your team maintains a critical backend service that manages user-generated content for a popular online platform. Users can upload various types of media (images, videos, documents), which are stored in an S3 bucket. Currently, all media URLs are direct S3 pre-signed URLs, generated on demand and valid for 1 hour. This works for internal applications, but you're now integrating with several third-party clients (mobile apps, partner websites) who require stable, long-lived URLs to embed the content directly. These clients are experiencing issues with expiring links and need a more robust solution. You need to design a system to provide stable, publicly accessible URLs for user-generated content, while still controlling access and ensuring data integrity.

## Requirements

*   **Public Accessibility:** The generated URLs must be publicly accessible without requiring client-side authentication or re-signing.
*   **Access Control:** While public, access to content must still respect the original content's privacy settings (e.g., only content explicitly marked "public" by the user should be accessible).
*   **High Availability & Scalability:** The solution must be highly available and scalable to handle millions of requests per day, as the platform grows.
*   **Cost-Effectiveness:** Minimize operational costs, especially for data transfer.
*   **Latency:** Content retrieval via these new URLs should have low latency for global users.
*   **Security:** Prevent unauthorized access to private content and protect against common web vulnerabilities.

## Deliverables

1.  A high-level diagram illustrating the new architecture, showing how stable URLs are generated and served, including components like AWS services.
2.  A brief explanation of how you would enforce access control for public vs. private content with this new system.
3.  An explanation of how you would invalidate or update content served via these stable URLs if the original S3 object changes or is deleted.

## Going further

Explain the trade-offs involved in choosing between a content delivery network (CDN) with S3 origin vs. serving directly from S3 using S3 Static Website Hosting for public content. Under what circumstances would one be clearly preferred over the other for this specific scenario?

## Worked answer

### 1. High-level Architecture Diagram

The core idea is to introduce a CDN (CloudFront) in front of S3, using an Origin Access Control (OAC) to restrict S3 bucket access only to CloudFront. Our backend service will manage the content metadata, including its public/private status, and generate stable, user-friendly URLs pointing to the CloudFront distribution.

**Explanation of Components:**

*   **Client Applications:** Mobile apps, partner websites, and internal applications that consume the content.
*   **API Gateway / Load Balancer:** Entry point for API requests to our backend service.
*   **Content Service:** Our existing backend service responsible for managing content metadata, handling uploads, and generating the stable URLs.
*   **Database (DynamoDB/RDS):** Stores metadata about each content item, including its S3 key, public/private status, and other relevant information.
*   **AWS S3 Bucket:** Stores the actual media files. Configured to only allow access via CloudFront OAC.
*   **AWS CloudFront Distribution:** A global CDN that caches content at edge locations, reducing latency and offloading requests from S3. It uses a custom domain (e.g., `cdn.example.com`).
*   **AWS Origin Access Control (OAC):** A security feature that restricts direct access to the S3 bucket, ensuring that only specified CloudFront distributions can retrieve objects from it. This is a more secure and flexible replacement for Origin Access Identity (OAI).
*   **AWS WAF (Web Application Firewall):** (Optional but recommended) Protects the CloudFront distribution from common web exploits and bot attacks.
*   **AWS Route 53:** Manages the custom domain for the CloudFront distribution.
*   **AWS Lambda@Edge:** (Optional, for advanced access control) Can be used to execute custom logic at CloudFront edge locations, e.g., to perform real-time authorization checks based on request headers or cookies before content is served.

**Stable URL Format:**

The Content Service will generate URLs like `https://cdn.example.com/{content_id}.{extension}`.
For example: `https://cdn.example.com/a1b2c3d4e5f6g7h8.jpg`

The `content_id` would be a unique identifier for the content, which maps to the S3 object key.

### 2. Access Control Enforcement

Access control is enforced at two primary layers:

1.  **Backend Service (Content Service):** This is the authoritative source for content privacy.
    *   When a user uploads content, its privacy setting (e.g., `public`, `private`, `friends-only`) is stored in the database alongside its S3 key.
    *   When the backend service generates a stable URL for a client, it **first checks the content's privacy status**.
        *   If the content is marked `public`, the service generates and returns the CloudFront URL.
        *   If the content is `private` (or `friends-only`, etc.), the service **refuses to generate the stable URL**. Instead, it might return an error, or for internal/authenticated clients, it could generate a *short-lived S3 pre-signed URL* as a fallback (similar to the existing system) for private content. The key here is that **private content never gets a stable, publicly accessible CloudFront URL**.

2.  **CloudFront Distribution with S3 OAC:**
    *   The S3 bucket policy is configured to **only allow access from the CloudFront OAC**. This means direct access to S3 objects via their S3 URLs (e.g., `https://my-bucket.s3.amazonaws.com/object.jpg`) is blocked for everyone, including the public.
    *   The CloudFront distribution itself is configured to serve content from the S3 origin.
    *   **Crucially, CloudFront does not perform authorization based on content privacy settings.** It simply serves whatever it can retrieve from S3. The access control decision *must* happen upstream in our Content Service *before* a CloudFront URL is ever exposed to a third-party client.

**Example Database Schema (Simplified):**

```sql
CREATE TABLE content_metadata (
    content_id VARCHAR(36) PRIMARY KEY, -- UUID for stable URL
    s3_key VARCHAR(255) NOT NULL UNIQUE, -- Path in S3 bucket
    user_id VARCHAR(36) NOT NULL,
    privacy_status ENUM('public', 'private', 'friends-only') NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    file_extension VARCHAR(10) NOT NULL
);

-- Example Content Service logic (pseudo-code):
function generateStableUrl(contentId, requestingUserId) {
    content = database.query("SELECT * FROM content_metadata WHERE content_id = ?", contentId);

    if (!content) {
        throw new NotFoundError("Content not found");
    }

    if (content.privacy_status === 'public') {
        return `https://cdn.example.com/${content.content_id}.${content.file_extension}`;
    } else if (content.privacy_status === 'private' && content.user_id === requestingUserId) {
        // For private content, generate a short-lived S3 pre-signed URL for the owner
        // Or return an error if public access is strictly required.
        return s3Service.generatePresignedUrl(content.s3_key, 3600); // 1 hour validity
    } else {
        throw new UnauthorizedError("Access denied to private content");
    }
}
```

This two-tiered approach ensures that only content explicitly marked as public by the user is ever exposed via the stable, public CloudFront URLs.

### 3. Invalidation or Updating Content

When the original S3 object changes or is deleted, the CloudFront cache needs to be updated or invalidated to ensure clients receive the latest version or a proper "not found" response.

1.  **Content Update/Deletion Event:**
    *   When a user updates or deletes content through our backend service, the service first performs the action on the S3 bucket (e.g., `s3.putObject` for update, `s3.deleteObject` for deletion).
    *   It also updates the `content_metadata` in the database.

2.  **Cache Invalidation:**
    *   After the S3 object is updated or deleted, the backend service must issue an invalidation request to the CloudFront distribution for the specific URL path. This tells CloudFront to remove the cached version of that object from all its edge locations.
    *   The invalidation path should match the URL structure. For `https://cdn.example.com/{content_id}.{extension}`, the invalidation path would be `/a1b2c3d4e5f6g7h8.jpg`.
    *   For broader changes, you can invalidate paths like `/images/*` or `/*`, but this is less efficient and can incur higher costs.

**Example Invalidation Logic (using AWS SDK for CloudFront):**

```typescript
import { CloudFrontClient, CreateInvalidationCommand } from "@aws-sdk/client-cloudfront";

const cloudfrontClient = new CloudFrontClient({ region: "us-east-1" }); // CloudFront API is global, typically us-east-1

async function invalidateCloudFrontCache(contentId: string, fileExtension: string) {
    const distributionId = process.env.CLOUDFRONT_DISTRIBUTION_ID; // e.g., E1234567890ABC
    const path = `/${contentId}.${fileExtension}`;

    try {
        const command = new CreateInvalidationCommand({
            DistributionId: distributionId,
            InvalidationBatch: {
                Paths: {
                    Quantity: 1,
                    Items: [path],
                },
                CallerReference: `content-update-${Date.now()}-${contentId}`, // Unique reference
            },
        });
        const response = await cloudfrontClient.send(command);
        console.log(`Invalidation request sent for path: ${path}, ID: ${response.Invalidation?.Id}`);
        return response.Invalidation?.Id;
    } catch (error) {
        console.error(`Failed to invalidate CloudFront cache for path ${path}:`, error);
        throw error;
    }
}

// Example usage after content update/deletion
async function updateContent(contentId: string, newFile: Buffer, fileExtension: string) {
    // 1. Upload new file to S3
    await s3Service.uploadObject(contentId, newFile, fileExtension);

    // 2. Update database metadata (if necessary, e.g., file_extension)
    await database.updateContentMetadata(contentId, { file_extension: fileExtension });

    // 3. Invalidate CloudFront cache
    await invalidateCloudFrontCache(contentId, fileExtension);
}

async function deleteContent(contentId: string, fileExtension: string) {
    // 1. Delete file from S3
    await s3Service.deleteObject(contentId, fileExtension);

    // 2. Delete database metadata
    await database.deleteContentMetadata(contentId);

    // 3. Invalidate CloudFront cache
    await invalidateCloudFrontCache(contentId, fileExtension);
}
```

**Trade-offs of Invalidation:**

*   **Cost:** CloudFront invalidations are free for the first 1,000 paths per month, then cost $0.005 per path. For a highly dynamic system with millions of updates/deletions, this can add up.
*   **Latency:** Invalidation takes a few minutes (typically 1-2 minutes) to propagate across all edge locations. During this time, some users might still receive the old cached content.
*   **Complexity:** Requires integrating CloudFront API calls into the backend service's content management logic.

**Alternative: Versioning S3 Objects (and URLs):**

Instead of invalidating, you could append a version hash or timestamp to the S3 object key and, consequently, the CloudFront URL.
Example: `https://cdn.example.com/a1b2c3d4e5f6g7h8_v12345.jpg`
When content is updated, a new S3 object with a new version hash is uploaded, and the backend generates a new URL. The old URL remains valid but points to the old version. This avoids invalidation costs and latency but requires clients to always request the *latest* URL from the backend and increases S3 storage if old versions are retained indefinitely. For this scenario requiring "stable, long-lived URLs," changing the URL itself on update might be undesirable for third-party clients. Therefore, invalidation is generally preferred for truly stable URLs that point to the *current* version of content.

### Going Further: CDN with S3 Origin vs. S3 Static Website Hosting

Both AWS CloudFront (CDN) with S3 origin and S3 Static Website Hosting can serve public content. However, they are designed for different use cases and have distinct trade-offs.

#### S3 Static Website Hosting

*   **How it works:** You enable "Static website hosting" on an S3 bucket. S3 then acts as a web server, serving content directly from the bucket via an S3-specific endpoint (e.g., `http://my-bucket.s3-website-us-east-1.amazonaws.com`). You can use a custom domain with Route 53 CNAME/ALIAS record.
*   **Pros:**
    *   **Simplicity:** Very easy to set up.
    *   **Cost-effective for low traffic:** Only pay for S3 storage and data transfer.
*   **Cons:**
    *   **No CDN benefits:** Content is served from a single S3 region. High latency for global users.
    *   **Limited security features:** No built-in WAF, DDoS protection, or advanced access control beyond S3 bucket policies.
    *   **No HTTPS out-of-the-box with custom domains:** Requires an additional CloudFront distribution or a load balancer to serve HTTPS on a custom domain.
    *   **No cache control:** S3 doesn't cache content at edge locations. Every request goes to the origin.
    *   **No OAC/OAI:** Direct public access to the S3 bucket is required, which is less secure than using OAC with CloudFront.
    *   **Limited scalability for sudden spikes:** While S3 is highly scalable, serving directly from a single region might struggle with extreme global traffic spikes compared to a CDN.

#### CDN (CloudFront) with S3 Origin

*   **How it works:** CloudFront distribution is configured to use an S3 bucket as its origin. CloudFront caches content at edge locations worldwide. Access to S3 is restricted via OAC.
*   **Pros:**
    *   **Low Latency:** Content is cached at edge locations geographically close to users, significantly reducing retrieval times.
    *   **Scalability & High Availability:** CloudFront is designed to handle massive traffic loads and absorb DDoS attacks.
    *   **Cost-Effectiveness (for high traffic):** While CloudFront has its own costs, data transfer out of CloudFront is often cheaper than data transfer out of S3 for high volumes, and caching reduces the number of requests to S3, saving S3 request costs.
    *   **Enhanced Security:** Integrates seamlessly with AWS WAF for application-layer security and provides DDoS protection. OAC ensures S3 bucket is not publicly exposed.
    *   **HTTPS on Custom Domains:** CloudFront natively supports custom domains with free SSL/TLS certificates (AWS Certificate Manager).
    *   **Cache Control:** Fine-grained control over caching behavior (TTL, invalidation).
    *   **Advanced Features:** Lambda@Edge for custom logic, geo-restriction, signed URLs/cookies for private content (though not used for *public* stable URLs in our design).

#### Preference for this Specific Scenario

For the given scenario, **CDN (CloudFront) with S3 Origin is clearly preferred over S3 Static Website Hosting.**

**Reasons:**

1.  **Public Accessibility & Low Latency for Global Users:** The requirement for "low latency for global users" is the primary driver for a CDN. S3 Static Website Hosting would serve content from a single region, leading to high latency for users far from that region.
2.  **High Availability & Scalability:** A popular online platform with "millions of requests per day" and growth expectations absolutely needs the scalability and availability benefits of a CDN. S3 Static Website Hosting, while scalable, lacks the distributed nature of a CDN.
3.  **Cost-Effectiveness (Data Transfer):** For high traffic volumes, CloudFront's data transfer out costs are generally lower than S3's, especially when considering the significant offloading of requests from S3 due to caching.
4.  **Security:** The ability to use OAC to restrict direct S3 access and integrate with AWS WAF for robust security is critical for "preventing unauthorized access and protecting against common web vulnerabilities" on a "critical backend service." S3 Static Website Hosting requires the bucket to be publicly readable, which is a less secure posture.
5.  **Stable, Long-Lived URLs:** While both can provide stable URLs, CloudFront's caching ensures that these URLs perform consistently well globally.

**When S3 Static Website Hosting might be preferred:**

*   **Extremely low traffic:** If the platform had very few users, all concentrated in a single geographical region, and cost was the absolute top priority, S3 Static Website Hosting might be marginally cheaper due to avoiding CloudFront's fixed costs (even if minimal).
*   **Internal-only, non-critical content:** For internal tools or non-critical content where latency and advanced security are not paramount, and the existing S3 pre-signed URLs are already sufficient, S3 Static Website Hosting could be a quick and dirty solution.

However, for a "critical backend service" with "millions of requests per day" and "global users," the benefits of CloudFront far outweigh its additional complexity and cost, making it the only viable choice.
