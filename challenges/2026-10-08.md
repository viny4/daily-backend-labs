## Scenario

Your team maintains a critical backend service for a fast-growing online food delivery platform. A new feature allows restaurants to define complex pricing rules for their menu items, such as "20% off all pizzas between 5 PM and 7 PM on weekdays," "buy one get one free on burgers every Tuesday," or "free delivery for orders over $50." These rules can overlap and apply differently based on the day of the week, time of day, customer loyalty status, or specific items in the cart.

The current system applies a single, static price to each menu item. To implement this new feature, your service needs to calculate the final price of an order, including all applicable discounts and promotions, *before* the customer confirms their purchase. This calculation must happen in real-time as users modify their cart.

## Requirements

The pricing rule engine needs to be highly performant and accurate.
*   **Scale:** The platform has 50,000 active restaurants, each potentially defining up to 100 complex pricing rules. There are 5 million active users, with peak concurrency of 50,000 concurrent cart modifications/price calculations per minute.
*   **Latency:** The total price calculation for a typical cart (up to 20 unique items) must complete within 100ms.
*   **Accuracy:** The system must correctly apply all overlapping rules, prioritizing promotions (e.g., "buy one get one free") over percentage discounts, and larger discounts over smaller ones when conflicts arise.
*   **Availability:** The pricing service is critical path; a failure here directly impacts customer checkout and revenue. It must be highly available and fault-tolerant.
*   **Maintainability:** Rules are defined by restaurant owners through a UI and can be updated frequently. The system should reflect these changes promptly (within 5 minutes).

**Explanation of Components:**

*   **Restaurant Admin Portal:** UI for restaurant owners to define and manage pricing rules.
*   **Rule Management Service:** Backend service handling CRUD operations for pricing rules. It validates rules and persists them.
*   **Rule API:** Exposes endpoints for rule management and potentially for other internal services to query rules directly (e.g., for auditing).
*   **Rule Storage (PostgreSQL):** Primary, durable storage for all pricing rules. Chosen for its transactional integrity, strong consistency, and ability to handle complex data structures (JSONB for rule definitions).
*   **Rule Cache (Redis):** A distributed cache storing frequently accessed rules (e.g., all rules for active restaurants). Used by the `Pricing Engine` for low-latency rule retrieval.
*   **Rule Distribution Service:** A service responsible for pushing rule updates from `Rule Storage` to `Pricing Engine` instances. It listens for changes (e.g., via database triggers, CDC, or polling) and publishes them to a message queue.
*   **Pub/Sub (Kafka):** A highly scalable message broker used by the `Rule Distribution Service` to broadcast rule updates to all `Pricing Engine` instances. This ensures prompt reflection of changes.
*   **Pricing Engine Load Balancer:** Distributes incoming price calculation requests from the `Cart Service` across multiple `Pricing Engine` instances.
*   **Pricing Engine Instances:** The core service responsible for calculating the final price of a cart. It retrieves rules from the `Rule Cache`, fetches item and user details from other services, applies rules, and resolves conflicts. These instances are stateless and horizontally scalable.
*   **User Service, Cart Service, Menu Service, User Profile Service:** Existing services providing necessary data (user details, cart contents, menu item information) to the `Pricing Engine`.
*   **Metrics & Logs, Monitoring & Alerting:** Standard observability components for tracking performance, errors, and system health.

### 2. Data structures and storage mechanisms

We need to store complex, dynamic pricing rules and retrieve them efficiently for real-time calculations.

**Primary Storage: PostgreSQL with JSONB**

PostgreSQL is chosen for its strong consistency, transactional guarantees, and robust support for complex data types, particularly `JSONB`. This allows us to store the flexible structure of pricing rules without rigid schema migrations for every new rule type.

**Schema for `pricing_rules` table:**

```sql
CREATE TYPE rule_status AS ENUM ('active', 'inactive', 'pending_review');

CREATE TABLE pricing_rules (
    rule_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    restaurant_id UUID NOT NULL,
    rule_name VARCHAR(255) NOT NULL,
    rule_type VARCHAR(50) NOT NULL, -- e.g., 'percentage_discount', 'bogo', 'free_delivery'
    priority INT NOT NULL DEFAULT 100, -- Lower number means higher priority
    status rule_status NOT NULL DEFAULT 'active',
    effective_from TIMESTAMP WITH TIME ZONE NOT NULL,
    effective_to TIMESTAMP WITH TIME ZONE, -- NULL for indefinite
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    rule_definition JSONB NOT NULL, -- Stores the specific conditions and actions
    CONSTRAINT fk_restaurant
        FOREIGN KEY (restaurant_id)
        REFERENCES restaurants(restaurant_id) ON DELETE CASCADE
);

CREATE INDEX idx_pricing_rules_restaurant_id_status_effective ON pricing_rules (restaurant_id, status, effective_from, effective_to);
CREATE INDEX idx_pricing_rules_updated_at ON pricing_rules (updated_at);

-- Trigger to update `updated_at` on every change
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER update_pricing_rules_updated_at
BEFORE UPDATE ON pricing_rules
FOR EACH ROW
EXECUTE FUNCTION update_updated_at_column();
```

**Justification:**

*   **`rule_id` (UUID):** Unique identifier, good for distributed systems.
*   **`restaurant_id` (UUID):** Links rules to specific restaurants. Critical for efficient lookup.
*   **`rule_name`, `rule_type`:** Descriptive fields for management and categorization.
*   **`priority` (INT):** Explicitly defines conflict resolution order. Lower numbers indicate higher priority. This is crucial for accuracy.
*   **`status` (ENUM):** Allows for activating/deactivating rules.
*   **`effective_from`, `effective_to`:** Supports time-bound promotions.
*   **`rule_definition` (JSONB):** This is the core. It allows for flexible, schema-less storage of rule specifics.
    *   **Example `rule_definition` for "20% off all pizzas between 5 PM and 7 PM on weekdays":**
        ```json
        {
            "conditions": {
                "item_category": "pizza",
                "day_of_week": ["monday", "tuesday", "wednesday", "thursday", "friday"],
                "time_range": {"start": "17:00", "end": "19:00"}
            },
            "action": {
                "type": "percentage_discount",
                "value": 20
            },
            "applies_to": "item_total"
        }
        ```
    *   **Example `rule_definition` for "buy one get one free on burgers":**
        ```json
        {
            "conditions": {
                "item_category": "burger",
                "min_quantity": 2
            },
            "action": {
                "type": "buy_one_get_one_free",
                "free_quantity": 1
            },
            "applies_to": "cheapest_item"
        }
        ```
    *   **Example `rule_definition` for "free delivery for orders over $50":**
        ```json
        {
            "conditions": {
                "cart_total_min": 50
            },
            "action": {
                "type": "free_delivery"
            },
            "applies_to": "delivery_fee"
        }
        ```
*   **Indexes:**
    *   `idx_pricing_rules_restaurant_id_status_effective`: Essential for quickly retrieving all active rules for a given restaurant within the current time frame.
    *   `idx_pricing_rules_updated_at`: Used by the `Rule Distribution Service` to efficiently poll for recently updated rules (if CDC is not used).

**Caching: Redis**

For real-time pricing calculations, querying PostgreSQL directly for every cart modification would introduce unacceptable latency. Redis is used as a distributed, in-memory cache.

**Redis Key Structure:**

*   `pricing_rules:restaurant:{restaurant_id}`: A hash or a list containing all active rules for a specific restaurant.
    *   **Value:** A serialized list of rule objects (e.g., JSON string or Protobuf). Each rule object would contain `rule_id`, `rule_type`, `priority`, `effective_from`, `effective_to`, and the parsed `rule_definition`.
    *   **Justification:** This allows the `Pricing Engine` to fetch all relevant rules for a restaurant in a single, low-latency operation. The rules are pre-parsed and ready for evaluation.

**Data Flow for Updates:**

1.  Restaurant owner updates a rule via `Restaurant Admin Portal`.
2.  `Rule Management Service` updates the `pricing_rules` table in PostgreSQL.
3.  The `Rule Distribution Service` detects this change:
    *   **Option A (Preferred): Change Data Capture (CDC):** Using tools like Debezium to stream changes from PostgreSQL's WAL to Kafka. This provides near real-time updates.
    *   **Option B (Fallback/Simpler): Polling:** The `Rule Distribution Service` periodically queries `pricing_rules` for `updated_at > last_polled_time`.
4.  `Rule Distribution Service` publishes a message to a Kafka topic (e.g., `pricing_rule_updates`) with the `restaurant_id` and the updated rule data (or just `restaurant_id` to signal a refresh).
5.  `Pricing Engine` instances (and potentially the `Rule Cache` service itself, if separated) consume messages from Kafka.
6.  Upon receiving an update for `restaurant_id X`, a `Pricing Engine` instance (or the `Rule Cache` service) invalidates or updates the `pricing_rules:restaurant:X` entry in Redis. If a full refresh is signaled, it fetches all active rules for `restaurant_id X` from PostgreSQL and repopulates the Redis cache.

**Trade-offs:**

*   **Complexity:** Introducing Kafka and a separate `Rule Distribution Service` adds operational overhead.
*   **Eventual Consistency (for rules):** While PostgreSQL is strongly consistent, the propagation of rule updates to `Pricing Engine` instances via Kafka and Redis introduces eventual consistency. The requirement states "within 5 minutes," which this design easily meets (typically within seconds).
*   **Memory Usage (Redis):** Caching all rules for 50,000 restaurants, each with up to 100 rules, could consume significant Redis memory. We'd need to size Redis appropriately and potentially implement LRU eviction policies or only cache rules for "hot" restaurants if memory becomes a constraint. Given 50,000 restaurants * 100 rules/restaurant * ~1KB/rule (serialized JSON) = 5GB, which is manageable for a dedicated Redis cluster.

### 3. Core logic for price calculation and rule updates

The core logic resides within the `Pricing Engine`.

**Rule Structure (in-memory representation):**

When rules are loaded into the `Pricing Engine` (from Redis), they should be parsed into an efficient in-memory object structure.

```typescript
// Example TypeScript interfaces for rule representation
interface RuleCondition {
    type: 'item_category' | 'day_of_week' | 'time_range' | 'cart_total_min' | 'customer_loyalty_status' | 'item_id';
    value: any; // e.g., "pizza", ["monday", "tuesday"], {start: "17:00", end: "19:00"}, 50, "gold", "item-abc"
    operator?: 'eq' | 'in' | 'gt' | 'lt' | 'gte' | 'lte'; // For more complex conditions
}

interface RuleAction {
    type: 'percentage_discount' | 'fixed_discount' | 'buy_one_get_one_free' | 'free_delivery';
    value?: number; // e.g., 20 (for percentage), 5 (for fixed discount)
    free_quantity?: number; // for BOGO
}

interface PricingRule {
    ruleId: string;
    restaurantId: string;
    ruleType: string;
    priority: number; // Lower is higher priority
    effectiveFrom: Date;
    effectiveTo?: Date;
    conditions: RuleCondition[]; // Array of conditions, all must be met (AND logic)
    action: RuleAction;
    appliesTo: 'item_total' | 'cheapest_item' | 'delivery_fee' | 'cart_total';
    // Additional fields for internal processing, e.g., pre-compiled regex for time ranges
}
```

**Core Price Calculation Logic (`PricingEngine`):**

The `calculatePrice(cart: Cart, restaurantId: string, userId: string)` function would follow these steps:

1.  **Fetch Rules:**
    *   Retrieve all active `PricingRule` objects for `restaurantId` from the `Rule Cache` (Redis).
    *   Filter rules based on `effectiveFrom` and `effectiveTo` (current time).
    *   Sort the applicable rules by `priority` (lowest number first). This is crucial for conflict resolution.

2.  **Fetch External Data:**
    *   Call `Menu Service` to get detailed information for all items in the `cart` (e.g., category, base price).
    *   Call `User Profile Service` to get `userId`'s loyalty status or other relevant attributes.

3.  **Initialize Cart State:**
    *   Create a mutable representation of the cart, including each item's base price, quantity, and a list of applied discounts/promotions.
    *   Initialize `deliveryFee` and `cartTotal` based on base prices.

4.  **Iterate and Apply Rules (Prioritized Order):**
    *   For each `rule` in the sorted list of applicable rules:
        *   **Evaluate Conditions:** Check if all `rule.conditions` are met by the current `cart` state, `user` data, and `restaurant` data.
            *   Example: `item_category` matches an item in the cart, `day_of_week` matches today, `time_range` matches current time, `cart_total_min` is met.
        *   **If Conditions Met:**
            *   **Apply Action:** Execute `rule.action` on the cart. This is the most complex part and requires careful implementation for each `rule.type`.
                *   **`percentage_discount` / `fixed_discount`:** Identify eligible items (e.g., all pizzas). Apply the discount to their price. Mark items as "discounted" to prevent further percentage/fixed discounts from applying if a higher priority rule already gave a better discount.
                *   **`buy_one_get_one_free` (BOGO):** Identify eligible items. For every N items, mark M as free (usually the cheapest ones). This is a "promotion" type of discount.
                *   **`free_delivery`:** Set `deliveryFee` to 0.
            *   **Update Cart State:** Recalculate affected item prices, `cartTotal`, etc.
            *   **Track Applied Rules:** Keep a record of which rules were applied to which items/cart for transparency and auditing.

5.  **Conflict Resolution (Implicit and Explicit):**
    *   **Implicit (Priority-based):** By sorting rules by `priority`, higher-priority rules are applied first.
    *   **Explicit (Rule Type Precedence):**
        *   Promotions (e.g., BOGO) generally take precedence over simple percentage/fixed discounts. The `Pricing Engine` should be designed to apply these first, or at least ensure that a BOGO doesn't get "undone" by a later percentage discount. This can be handled by the `priority` field, or by having distinct processing phases (e.g., first apply all BOGO, then all fixed, then all percentage).
        *   "Larger discounts over smaller ones" for conflicting rules of the *same type* can be handled by applying the first rule that matches and marking the affected items/cart segment as "processed" for that discount type, or by evaluating all applicable rules for a segment and picking the best one. Given the `priority` field, the restaurant owner explicitly defines this. If two rules have the same priority, the order of application might be non-deterministic, so rules should ideally have unique priorities for a given restaurant.
    *   **Item-level vs. Cart-level:** Rules affecting specific items are applied first, then rules affecting the entire cart (e.g., free delivery).

6.  **Final Calculation:**
    *   Sum up all item prices (after discounts).
    *   Add `deliveryFee` (after discounts).
    *   Add taxes (if applicable, though not specified in requirements).
    *   Return the final `cartTotal` and a breakdown of applied discounts.

**Handling Prompt Reflection of Rule Updates:**

1.  **Rule Distribution Service:**
    *   Monitors PostgreSQL for changes to `pricing_rules` table (via CDC or polling `updated_at`).
    *   Upon detecting a change for `restaurant_id X`, it publishes a message to a Kafka topic (e.g., `pricing_rule_updates`) containing `restaurant_id X` and the new rule data (or a signal to invalidate).

2.  **Pricing Engine Instances:**
    *   Each `Pricing Engine` instance subscribes to the `pricing_rule_updates` Kafka topic.
    *   When a message for `restaurant_id X` is received:
        *   The instance invalidates its local cache for `restaurant_id X` (if it maintains one) and/or triggers a refresh of the `pricing_rules:restaurant:X` entry in Redis.
        *   The next request for `restaurant_id X` will fetch the updated rules from Redis (which would have been refreshed by the `Rule Distribution Service` or a dedicated cache updater service).
    *   This ensures that rule changes are propagated to all active `Pricing Engine` instances within seconds, easily meeting the "within 5 minutes" requirement.

### 4. Two potential failure modes and how the design addresses them

1.  **Failure Mode: Pricing Engine instances become stale due to rule update propagation issues.**
    *   **Description:** If the Kafka broker goes down, the `Rule Distribution Service` fails to publish messages, or `Pricing Engine` instances fail to consume messages, they might continue to use outdated pricing rules from their local cache or Redis. This leads to incorrect pricing, customer dissatisfaction, and potential revenue loss.
    *   **Addressing in Design:**
        *   **Kafka's Durability and High Availability:** Kafka is designed for high availability and fault tolerance. It uses replication and distributed logs to ensure messages are not lost and can be consumed even if some brokers fail.
        *   **Monitoring and Alerting:** We would implement comprehensive monitoring on the `Rule Distribution Service` (e.g., message production rate, error rates) and `Pricing Engine` instances (e.g., Kafka consumer lag, rule version discrepancies). Alerts would trigger if consumer lag exceeds a threshold or if rule versions diverge significantly.
        *   **Periodic Full Cache Refresh/Reconciliation:** As a last resort and a safety net, `Pricing Engine` instances could be configured to perform a full refresh of all rules for their assigned restaurants from PostgreSQL (or a dedicated cache service that fetches from PostgreSQL) at regular, longer intervals (e.g., every 30 minutes). This ensures eventual consistency even if the real-time update path temporarily fails.
        *   **Health Checks:** Load balancers for the `Pricing Engine` would perform health checks. If an instance is consistently failing to process rule updates or is reporting stale data, it could be taken out of rotation.

2.  **Failure Mode: High latency in price calculation during peak load.**
    *   **Description:** With 50,000 concurrent cart modifications per minute and a 100ms latency requirement, any bottleneck in the `Pricing Engine` or its dependencies can lead to timeouts, slow checkout experiences, and abandoned carts. Potential bottlenecks include slow rule retrieval, inefficient rule evaluation, or slow calls to external services (Menu, User Profile).
    *   **Addressing in Design:**
        *   **Rule Caching (Redis):** The primary mitigation. Rules are fetched from an in-memory Redis cache, which offers sub-millisecond latency, instead of a slower database. This is critical for the 100ms target.
        *   **Stateless Pricing Engine:** `Pricing Engine` instances are stateless, allowing for horizontal scaling. If latency increases, more instances can be spun up automatically via an autoscaling group, distributing the load.
        *   **Efficient Rule Data Structures:** Rules are pre-parsed and stored in Redis in an optimized format. The in-memory representation within the `Pricing Engine` is also optimized for quick condition evaluation (e.g., using hash maps for item lookups, pre-compiled regex for time ranges).
        *   **Asynchronous External Service Calls (where possible):** While some calls (Menu, User Profile) are synchronous and critical for the current request, the `Pricing Engine` could use connection pooling and efficient client libraries to minimize overhead. For non-critical data, asynchronous pre-fetching or eventual consistency models could be considered.
        *   **Circuit Breakers and Timeouts:** Implement circuit breakers and strict timeouts for all external service calls (Menu, User Profile, Redis). This prevents a slow dependency from cascading and taking down the entire `Pricing Engine`. If a dependency is slow, the `Pricing Engine` can return a default price or an error message, rather than hanging indefinitely.
        *   **Load Testing and Performance Tuning:** Rigorous load testing will identify bottlenecks early. Performance monitoring (metrics, tracing) will help pinpoint slow parts of the rule evaluation logic for optimization.

### Going further: A/B testing of pricing rules

To support A/B testing of pricing rules for different user segments and roll out winning rules without downtime, the design needs to adapt in several key areas:

1.  **Rule Definition and Storage:**
    *   **Experiment ID/Segment ID:** The `pricing_rules` table needs new fields to associate rules with specific experiments and user segments.
        ```sql
        ALTER TABLE pricing_rules
        ADD COLUMN experiment_id UUID,
        ADD COLUMN segment_id UUID; -- References a user segment definition
        ```
    *   **Rule Versioning:** Each rule might have multiple versions under an experiment. The `rule_definition` could evolve, or an entirely new rule might be tested. This implies a need for explicit versioning or a clear way to link experiment rules.
    *   **Experiment Metadata Table:** A new table `pricing_experiments` would store details about each A/B test:
        ```sql
        CREATE TABLE pricing_experiments (
            experiment_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
            experiment_name VARCHAR(255) NOT NULL,
            status VARCHAR(50) NOT NULL DEFAULT 'draft', -- 'draft', 'active', 'completed', 'rolled_out'
            start_time TIMESTAMP WITH TIME ZONE NOT NULL,
            end_time TIMESTAMP WITH TIME ZONE,
            control_rule_ids UUID[], -- Array of rule_ids for the control group
            variant_rule_ids JSONB,  -- { "variant_A": [rule_id1, rule_id2], "variant_B": [...] }
            traffic_allocation JSONB, -- { "control": 0.5, "variant_A": 0.5 }
            segmentation_logic JSONB, -- Defines how users are assigned to segments (e.g., loyalty status, new user)
            created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
            updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
        );
        ```

2.  **User Segmentation and Assignment:**
    *   **User Profile Service Enhancement:** The `User Profile Service` would need to be enhanced to determine a user's segment for a given experiment. This could involve:
        *   **Hashing:** A common technique is to hash a user ID (or a combination of user ID and experiment ID) to a number, then assign them to a segment based on traffic allocation percentages.
        *   **Explicit Assignment:** For specific segments (e.g., "gold loyalty members"), the service would return that information.
    *   **Experiment Assignment Service:** A dedicated service might be introduced (or integrated into `User Profile Service`) to manage experiment assignments and ensure stickiness (a user remains in the same segment for the duration of an experiment).

3.  **Pricing Engine Adaptation:**
    *   **Rule Fetching Logic:** When the `Pricing Engine` receives a request, it would first:
        *   Query the `Experiment Assignment Service` (or `User Profile Service`) to determine which active experiments the `user_id` is part of and which variant (control/A/B) they are assigned to for each experiment.
        *   Based on the assigned variants, the `Pricing Engine` would then fetch the *specific set of rules* applicable to that user for that restaurant. This means the Redis cache key might need to include `experiment_id` and `variant_id` (e.g., `pricing_rules:restaurant:{restaurant_id}:experiment:{experiment_id}:variant:{variant_id}`).
    *   **Rule Evaluation:** The core evaluation logic remains similar, but it would operate on the dynamically selected set of rules.
    *   **Logging/Observability:** Crucially, the `Pricing Engine` must log which experiment and variant were applied for each price calculation. This data is essential for analyzing experiment results.

4.  **Rule Distribution and Cache Management:**
    *   **Granular Cache Keys:** Redis cache keys would become more granular, potentially `pricing_rules:restaurant:{restaurant_id}:experiment:{experiment_id}:variant:{variant_id}`.
    *   **Experiment-aware Distribution:** The `Rule Distribution Service` would need to understand experiment states. When an experiment moves from `draft` to `active`, it would trigger a cache population for all relevant variants. When an experiment is `completed` and a variant is `rolled_out`, it would trigger an update to the "default" rules for that restaurant, effectively making the winning variant the new baseline.

5.  **Rollout Mechanism (Zero Downtime):**
    *   **Phased Rollout:** The `traffic_allocation` in `pricing_experiments` allows for gradual rollout. An experiment can start with 1% of users, then 10%, 50%, and finally 100%.
    *   **"Roll Out" Status:** When an experiment is deemed successful, its `status` in `pricing_experiments` would change to `rolled_out`.
    *   **Automatic Rule Promotion:** The `Rule Management Service` (or a dedicated `Experiment Rollout Service`) would then:
        *   Identify the winning `variant_rule_ids`.
        *   Create or update the "default" (non-experiment) rules in the `pricing_rules` table with these winning rules. This might involve updating existing `rule_definition` for existing rules or creating new `pricing_rules` entries.
        *   Deactivate the experiment-specific rules.
        *   The `Rule Distribution Service` would then pick up these changes to the default rules and propagate them to the `Pricing Engine` instances via Kafka and Redis, effectively making the winning rules the new standard for all users not explicitly in an experiment.
    *   **No Downtime:** Because the `Pricing Engine` dynamically fetches rules based on experiment assignment and the underlying rule data is updated and propagated via the existing real-time distribution mechanism, there is no need for service restarts or downtime during rollout. Users seamlessly transition to the new rules as their segment assignment or the default rules are updated.

**Trade-offs for A/B Testing:**

*   **Increased Complexity:** Significant increase in data model, services (Experiment Assignment), and `Pricing Engine` logic.
*   **Performance Impact:** Additional lookups for experiment assignment and more complex cache key management add a small overhead to each price calculation. This needs careful optimization and caching for experiment assignments.
*   **Data Consistency:** Ensuring that a user consistently sees the same variant throughout their session requires careful state management in the `Experiment Assignment Service`.
*   **Observability:** More sophisticated logging and analytics are required to track experiment performance and make data-driven decisions.
