## Scenario

Your team maintains a critical backend service for a popular online education platform. A core feature allows instructors to view "class rosters" for their courses, which lists all enrolled students along with their current progress (e.g., number of completed lessons, total quizzes passed).

The `enrollments` table has grown significantly and now contains hundreds of millions of rows, with `course_id`, `student_id`, `enrollment_date`, and `last_progress_update` columns. Student progress data (completed lessons, quizzes) is stored in a separate `student_progress` table, also very large.

The query to generate a class roster for a course with 10,000 students involves joining `enrollments` with `student_progress` and can take 5-10 seconds to execute against PostgreSQL. This endpoint is frequently accessed by instructors, especially at the start and end of academic terms, leading to database load spikes and slow UI responses. The data for a class roster is typically "fresh enough" for a few minutes, but stale data for more than 5 minutes is unacceptable.

## Requirements

Implement a caching strategy using Redis to significantly reduce the latency and database load for fetching class rosters. Your solution must handle concurrent requests for the same roster effectively, ensure data consistency within the 5-minute staleness tolerance, and be resilient to Redis failures (i.e., the application should still function, albeit slower, if Redis is temporarily unavailable). The system should be able to serve class rosters for courses with tens of thousands of students.

## Deliverables

1.  A Python/Django or TypeScript/Node.js function (`get_class_roster(course_id)`) that fetches the class roster, incorporating Redis caching.
2.  Demonstration that repeated calls to `get_class_roster` for the same `course_id` within a 3-minute window hit the cache and return results significantly faster than the initial call.
3.  Confirmation that `get_class_roster` correctly falls back to the database if the Redis cache is unavailable or the data has expired, without raising an unhandled exception.

```python
# services/roster_service.py
import json
import logging
import redis
from django.conf import settings
from django.db import connection, transaction
from django.core.serializers.json import DjangoJSONEncoder

logger = logging.getLogger(__name__)

# Initialize Redis client
# In a real application, this would likely be managed by a dependency injection framework
# or a module-level client instance.
try:
    redis_client = redis.StrictRedis(
        host=settings.REDIS_HOST,
        port=settings.REDIS_PORT,
        db=settings.REDIS_DB,
        decode_responses=True # Decodes responses from bytes to strings
    )
    # Test connection
    redis_client.ping()
    REDIS_AVAILABLE = True
    logger.info("Successfully connected to Redis.")
except redis.exceptions.ConnectionError as e:
    REDIS_AVAILABLE = False
    logger.error(f"Could not connect to Redis: {e}. Caching will be disabled.")
except Exception as e:
    REDIS_AVAILABLE = False
    logger.error(f"An unexpected error occurred during Redis connection: {e}. Caching will be disabled.")


CACHE_TTL_SECONDS = 4 * 60 # 4 minutes, slightly less than the 5-minute tolerance
CACHE_KEY_PREFIX = "class_roster:"

def _fetch_roster_from_db(course_id: int) -> list[dict]:
    """
    Fetches class roster data directly from the database.
    This function simulates the expensive join operation.
    """
    logger.info(f"Fetching roster for course_id {course_id} from database.")
    # Using raw SQL for demonstration of a complex join,
    # but Django ORM could also be used for simpler cases.
    # This query joins enrollments with student progress and student details.
    with connection.cursor() as cursor:
        cursor.execute(
            """
            SELECT
                e.student_id,
                s.name AS student_name,
                e.enrollment_date,
                sp.completed_lessons,
                sp.total_quizzes_passed
            FROM
                enrollment e
            JOIN
                student s ON e.student_id = s.id
            LEFT JOIN
                student_progress sp ON e.id = sp.enrollment_id
            WHERE
                e.course_id = %s;
            """,
            [course_id]
        )
        columns = [col[0] for col in cursor.description]
        roster_data = [
            dict(zip(columns, row))
            for row in cursor.fetchall()
        ]
    return roster_data

def get_class_roster(course_id: int) -> list[dict]:
    """
    Fetches the class roster for a given course_id, utilizing Redis caching.
    """
    cache_key = f"{CACHE_KEY_PREFIX}{course_id}"
    roster_data = None

    if REDIS_AVAILABLE:
        try:
            # Attempt to acquire a lock to prevent thundering herd on cache misses
            # We use a simple lock here. For production, consider Redlock or similar.
            lock_key = f"{cache_key}:lock"
            # Try to acquire lock for a short period (e.g., 30 seconds)
            # This is a blocking call if another process holds the lock.
            # For a non-blocking approach, use `redis_client.set(lock_key, '1', nx=True, ex=30)`
            # and handle the case where the lock is not acquired.
            # For simplicity, we'll use a blocking lock for this example.
            # A better approach for thundering herd is a non-blocking lock with a short retry.
            # For this example, we'll use a simpler, blocking lock for clarity,
            # but note its potential for blocking requests.
            # Let's refine this to a non-blocking approach with a short wait.

            # Non-blocking lock acquisition attempt
            # `nx=True` means "set if not exists". `ex` is expiry in seconds.
            lock_acquired = redis_client.set(lock_key, '1', nx=True, ex=30) # Lock expires in 30s

            if lock_acquired:
                logger.debug(f"Acquired lock for {cache_key}")
                try:
                    # Check cache again after acquiring lock, in case another process
                    # populated it while we were waiting for the lock.
                    cached_roster = redis_client.get(cache_key)
                    if cached_roster:
                        roster_data = json.loads(cached_roster)
                        logger.info(f"Cache hit (after lock) for course_id {course_id}")
                        return roster_data

                    # Cache miss, fetch from DB
                    roster_data = _fetch_roster_from_db(course_id)
                    # Store in cache with TTL
                    redis_client.setex(cache_key, CACHE_TTL_SECONDS, json.dumps(roster_data, cls=DjangoJSONEncoder))
                    logger.info(f"Cache miss for course_id {course_id}. Data fetched from DB and cached.")
                    return roster_data
                finally:
                    # Release the lock
                    redis_client.delete(lock_key)
                    logger.debug(f"Released lock for {cache_key}")
            else:
                # Lock not acquired, another process is likely populating the cache.
                # Wait briefly and then try to read from cache.
                # This prevents multiple processes from hitting the DB simultaneously.
                logger.debug(f"Could not acquire lock for {cache_key}. Waiting for cache population.")
                # A short busy-wait or a more sophisticated pub/sub mechanism could be used.
                # For simplicity, we'll just try reading from cache immediately after a very short delay.
                # In a real system, you might want to implement a short loop with `time.sleep()`
                # and retry reading from cache a few times.
                import time
                time.sleep(0.1) # Wait 100ms

                cached_roster = redis_client.get(cache_key)
                if cached_roster:
                    roster_data = json.loads(cached_roster)
                    logger.info(f"Cache hit (waiting for lock) for course_id {course_id}")
                    return roster_data
                else:
                    # If after waiting, cache is still empty, it means the lock holder
                    # failed or the lock expired. Fallback to DB.
                    logger.warning(f"Cache still empty after waiting for lock for {course_id}. Falling back to DB.")
                    roster_data = _fetch_roster_from_db(course_id)
                    # We don't try to cache here, as another process might still be working
                    # or the lock might have just expired.
                    return roster_data

        except redis.exceptions.RedisError as e:
            logger.error(f"Redis error during cache operation for course_id {course_id}: {e}. Falling back to DB.")
            # Fallback to database
            roster_data = _fetch_roster_from_db(course_id)
        except json.JSONDecodeError as e:
            logger.error(f"JSON decode error for cached data for course_id {course_id}: {e}. Falling back to DB.")
            # Invalidate potentially corrupt cache entry
            if REDIS_AVAILABLE:
                try:
                    redis_client.delete(cache_key)
                    logger.warning(f"Deleted corrupt cache entry for {course_id}.")
                except redis.exceptions.RedisError as e_del:
                    logger.error(f"Error deleting corrupt cache entry for {course_id}: {e_del}")
            roster_data = _fetch_roster_from_db(course_id)
    else:
        logger.warning(f"Redis is unavailable. Fetching roster for course_id {course_id} directly from DB.")
        roster_data = _fetch_roster_from_db(course_id)

    return roster_data

```

**Explanation:**

1.  **Redis Client Initialization:** The `redis_client` is initialized globally. A `try-except` block handles `redis.exceptions.ConnectionError` to gracefully degrade if Redis is down. `decode_responses=True` ensures Redis returns strings instead of bytes.
2.  **`_fetch_roster_from_db`:** This private helper function encapsulates the expensive database query. It simulates joining `enrollment`, `student`, and `student_progress` tables. Using raw SQL here highlights the complexity, but Django ORM could be used for simpler queries.
3.  **`get_class_roster`:**
    *   **Cache Key:** A unique cache key `class_roster:<course_id>` is constructed.
    *   **Redis Availability Check:** It first checks `REDIS_AVAILABLE`. If `False`, it bypasses Redis entirely and goes straight to the database, fulfilling the resilience requirement.
    *   **Cache Miss with Lock:**
        *   It attempts to acquire a distributed lock (`lock_key`) using `redis_client.set(lock_key, '1', nx=True, ex=30)`. `nx=True` ensures the lock is only set if it doesn't already exist (atomic operation). `ex=30` sets an expiry of 30 seconds on the lock to prevent deadlocks if the process holding it crashes.
        *   If the lock is acquired, the process becomes the "cache builder". It then *re-checks* the cache (`redis_client.get(cache_key)`) because another process might have populated the cache while this process was waiting for the lock.
        *   If still a cache miss, it fetches data from the database, serializes it to JSON, and stores it in Redis using `setex` (set with expiry). `CACHE_TTL_SECONDS` is set to 4 minutes, ensuring data is fresh enough.
        *   Finally, it releases the lock.
    *   **Lock Not Acquired:** If the lock is *not* acquired, it means another process is already building the cache. This process waits for a very short period (`time.sleep(0.1)`) and then attempts to read from the cache. This prevents the "thundering herd" problem where many requests simultaneously hit the database on a cache miss. If the cache is still empty after waiting, it falls back to the database without caching the result, assuming the lock holder failed or the lock expired.
    *   **Cache Hit:** If `redis_client.get(cache_key)` returns data, it's a cache hit. The JSON data is deserialized and returned immediately.
    *   **Error Handling:** `try-except redis.exceptions.RedisError` catches any Redis-related issues (e.g., connection drops, command errors) and falls back to the database, ensuring the application remains functional. `json.JSONDecodeError` handles potential corruption of cached data, deleting the bad entry and fetching from the DB.
    *   **Serialization:** `json.dumps` is used to store the list of dictionaries as a JSON string in Redis. `DjangoJSONEncoder` handles Django-specific types (like `datetime` objects) during serialization.

### 3. Confirmation of Redis fallback

The `get_class_roster` function is designed with a robust fallback mechanism.

**How it works:**

1.  **Initial Connection Check:** The `REDIS_AVAILABLE` flag is set during the initial `redis_client` instantiation. If `redis_client.ping()` fails, `REDIS_AVAILABLE` becomes `False`.
    ```python
    try:
        redis_client = redis.StrictRedis(...)
        redis_client.ping()
        REDIS_AVAILABLE = True
    except redis.exceptions.ConnectionError as e:
        REDIS_AVAILABLE = False
        logger.error(f"Could not connect to Redis: {e}. Caching will be disabled.")
    ```
2.  **Runtime Error Handling:** Even if Redis is initially available, network issues or Redis server crashes can occur mid-operation. The `try-except redis.exceptions.RedisError` block within `get_class_roster` catches any exceptions that occur during `get`, `setex`, or `delete` operations.
    ```python
    if REDIS_AVAILABLE:
        try:
            # ... Redis operations ...
        except redis.exceptions.RedisError as e:
            logger.error(f"Redis error during cache operation for course_id {course_id}: {e}. Falling back to DB.")
            roster_data = _fetch_roster_from_db(course_id)
    else:
        logger.warning(f"Redis is unavailable. Fetching roster for course_id {course_id} directly from DB.")
        roster_data = _fetch_roster_from_db(course_id)
    ```
    In both scenarios, the function logs the error/warning and proceeds to call `_fetch_roster_from_db(course_id)`, ensuring the application continues to serve requests, albeit with higher latency and database load. No unhandled exceptions are raised to the caller.

### Going further: Race conditions and mitigation

The chosen caching strategy, specifically the "cache-aside" pattern with a distributed lock, addresses several potential race conditions:

1.  **Thundering Herd Problem (Cache Miss Storm):**
    *   **Scenario:** When a cache entry expires or is invalidated, multiple concurrent requests for the same `course_id` will all result in a cache miss. Without mitigation, all these requests would simultaneously hit the backend database, causing a "thundering herd" and potentially overwhelming the database.
    *   **Mitigation in Implementation:** The use of a Redis distributed lock (`redis_client.set(lock_key, '1', nx=True, ex=30)`) directly addresses this.
        *   Only the first request successfully acquires the lock. This request becomes the "cache builder."
        *   Subsequent requests for the same `course_id` will fail to acquire the lock. Instead of hitting the database, they wait for a short period (`time.sleep(0.1)`) and then re-check the cache. By the time they re-check, the cache builder (the process that acquired the lock) should have populated the cache.
        *   If the cache is still empty after waiting (e.g., the cache builder crashed or the lock expired), these requests fall back to the database but do *not* attempt to cache, preventing a new thundering herd.
    *   **Trade-offs:** The `time.sleep(0.1)` introduces a small artificial delay for requests that don't acquire the lock. For very high concurrency, a more sophisticated approach might involve a short loop with exponential backoff and retries, or a Redis Pub/Sub mechanism where the cache builder publishes a "cache populated" event. However, for a 5-10 second DB query, a 100ms delay is acceptable. The `ex=30` on the lock is crucial to prevent deadlocks if the cache builder crashes.

2.  **Stale Data After Cache Invalidation/Expiration (Write-After-Read Race):**
    *   **Scenario:** Imagine a cache entry expires. Request A fetches data from the DB and is about to write it to the cache. Meanwhile, Request B (a legitimate data update, e.g., a student completes a lesson) updates the database. If Request A then writes its *older* data to the cache *after* Request B updated the DB, the cache would contain stale data.
    *   **Mitigation in Implementation:** Our current implementation primarily focuses on read-heavy scenarios and a fixed TTL. It doesn't explicitly handle cache invalidation on *writes* to the `enrollments` or `student_progress` tables.
        *   For the given scenario, where "stale data for more than 5 minutes is unacceptable," the fixed `CACHE_TTL_SECONDS = 4 * 60` (4 minutes) ensures that data is refreshed regularly, limiting the maximum staleness.
        *   **To fully mitigate this (Going Further):** If immediate consistency after a write was required, an explicit cache invalidation step would be added to the write path. For example, after a `student_progress` update, the system would explicitly `redis_client.delete(f"class_roster:{course_id}")`. This ensures the next read triggers a cache miss and fetches the freshest data. This is often called "write-through" or "write-behind" with invalidation. Our current strategy is "read-through" with TTL.

3.  **Cache Stampede (similar to Thundering Herd, but often refers to the initial population):**
    *   **Scenario:** When a new `course_id` is accessed for the first time, or after a global cache flush, many requests might simultaneously try to populate the cache.
    *   **Mitigation:** The distributed lock mechanism also covers this. The first request to acquire the lock populates the cache, while others wait or fall back.

**Trade-offs and What Breaks First at Ten Times the Scale:**

*   **Trade-offs:**
    *   **Complexity:** Adding Redis and a distributed locking mechanism increases system complexity compared to a simple database query.
    *   **Operational Overhead:** Redis needs to be deployed, monitored, and maintained.
    *   **Consistency Model:** We've chosen "eventual consistency" within the 5-minute window. Data might be slightly stale for up to 4 minutes. If real-time consistency were paramount, this strategy would need modification (e.g., aggressive cache invalidation on writes, or a different caching pattern).
    *   **Lock Contention:** While the lock prevents thundering herd, high concurrency on a *single* cache key could still lead to many requests waiting for the lock, introducing latency. The `time.sleep(0.1)` is a simple solution; for extreme scale, more advanced non-blocking patterns or client-side request coalescing might be needed.
    *   **Redis as a Single Point of Failure (without clustering):** While the application gracefully falls back, if Redis is down, all benefits of caching are lost, and the database will experience full load.

*   **What breaks first at ten times the scale (100,000 students per class, or 10x more concurrent requests):**
    1.  **PostgreSQL Database:** Even with caching, if there are many unique `course_id`s being accessed for the first time or after cache expiry, the database will still be hit hard. A class with 100,000 students means a 10x larger query result set, increasing DB query time and network transfer. The 5-10 second query time could easily become 50-100 seconds.
    2.  **Redis Memory:** Storing 100,000 student rosters (each a large JSON string) could consume significant Redis memory. If there are many such courses, Redis might run out of memory, leading to evictions or crashes.
    3.  **Network Bandwidth:** Transferring large JSON payloads (100,000 students) between the application server and Redis, and then from Redis to the client, will consume more network bandwidth.
    4.  **Serialization/Deserialization Overhead:** While fast, processing 10x larger JSON strings for serialization/deserialization will consume more CPU on the application server.
    5.  **Lock Contention (for extreme concurrency on same key):** If hundreds or thousands of requests simultaneously hit the *exact same* expired cache key, even with the lock, many requests will be waiting for the `time.sleep(0.1)` period, leading to increased perceived latency for those requests. The simple `time.sleep` might not scale well for very high contention.

**Plausible-looking approach that is wrong (and why):**

**Wrong Approach:** Not using a distributed lock on cache misses.

```python
# Simplified, BAD example without a lock
def get_class_roster_bad(course_id: int) -> list[dict]:
    cache_key = f"{CACHE_KEY_PREFIX}{course_id}"
    cached_roster = redis_client.get(cache_key)

    if cached_roster:
        return json.loads(cached_roster)
    else:
        # Cache miss - DANGER: Thundering Herd!
        roster_data = _fetch_roster_from_db(course_id)
        redis_client.setex(cache_key, CACHE_TTL_SECONDS, json.dumps(roster_data))
        return roster_data
```

**Why it's wrong:**

If the cache for `course_id` expires, and 100 concurrent requests arrive for that `course_id` at nearly the same time:

1.  All 100 requests will check `redis_client.get(cache_key)`.
2.  All 100 requests will find it's a cache miss.
3.  All 100 requests will then proceed to call `_fetch_roster_from_db(course_id)`.
4.  This means the database will execute the expensive 5-10 second join query 100 times simultaneously. This is the "thundering herd" problem and would likely crash or severely degrade the performance of the PostgreSQL database, leading to service outages.

The distributed lock is essential to ensure that only one process (the "cache builder") performs the expensive database fetch and populates the cache, while others wait or read the newly populated cache.
