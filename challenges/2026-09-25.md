## Scenario

Your team maintains a critical backend service that powers the real-time activity feed for a popular social media platform. This feed displays updates like "User X posted a photo," "User Y commented on Z's post," or "User A followed User B." The service currently runs on a fleet of EC2 instances behind an Application Load Balancer (ALB) and stores activity data in a managed PostgreSQL database.

The platform is experiencing rapid growth, and during peak hours (e.g., major sporting events, breaking news), the current architecture struggles to keep up with the volume of read requests for activity feeds. Users are complaining about stale feeds, slow loading times, and occasional `504 Gateway Timeout` errors from the ALB. The database CPU utilization frequently spikes above 80%, and the EC2 instances are auto-scaling aggressively, but the problem persists. You've identified that fetching a user's activity feed involves a complex join across several tables (e.g., `activities`, `users`, `posts`, `comments`) and often results in retrieving thousands of rows for a single user's feed. Latency for fetching a feed regularly exceeds 500ms.

## Requirements

The goal is to improve the read performance and scalability of the activity feed service, specifically during high-traffic periods, without significantly increasing operational complexity or introducing a complete rewrite of the existing data model. You need to leverage AWS services to offload the heavy read burden from the primary database and accelerate feed delivery. The solution must handle a read QPS of 10,000+ for feed retrieval with an average latency below 100ms, even with highly active users, while maintaining data consistency within a few seconds.

### 2. Explanation of proposed architecture

The proposed architecture introduces Amazon ElastiCache for Redis as a caching layer to offload the heavy read burden from the primary PostgreSQL database. When a user requests their activity feed, the backend service (running on EC2) will first attempt to retrieve the data from the Redis cache. If the feed is found in Redis (a cache hit), it is returned directly to the user, significantly reducing latency and database load. Only on a cache miss will the backend service query the PostgreSQL database, fetch the data, populate the cache, and then return it to the user.

To manage data consistency, a write-through caching strategy will be employed for critical updates. Whenever a user action (e.g., posting a photo, commenting, following) results in a new entry in the PostgreSQL database, the backend service will asynchronously or synchronously update the relevant user feeds in the Redis cache. For example, when "User X posts a photo," the service will not only write to the `activities` table but also invalidate or update the cached feeds of User X and potentially their followers. This ensures that the cache remains relatively fresh. For less critical updates or to handle eventual consistency, cache entries can be given a Time-To-Live (TTL) to ensure they are periodically refreshed from the database, preventing stale data from persisting indefinitely. This hybrid approach balances read performance with acceptable consistency within a few seconds, meeting the requirements.

### 3. Key AWS services

1.  **Amazon ElastiCache for Redis:** This managed in-memory data store is central to the solution. It provides extremely low-latency read access (sub-millisecond) and high throughput, making it ideal for caching frequently accessed activity feeds. Its cluster mode allows for horizontal scaling to handle the 10,000+ QPS requirement and provides high availability. We would store serialized representations of user feeds (e.g., JSON strings) as values, with user IDs as keys.
2.  **Amazon SNS (Simple Notification Service) / SQS (Simple Queue Service):** While not explicitly in the diagram, these services would be crucial for managing cache consistency asynchronously. When a new activity is written to the database, the backend service can publish a message to an SNS topic. An SQS queue subscribed to this topic would then receive the message, triggering a Lambda function or a dedicated cache-update service. This service would then invalidate or update the relevant keys in ElastiCache, ensuring that the cache is updated without adding synchronous latency to the primary write path. This decouples the cache update logic from the core write operation, improving system resilience and scalability.

### 4. Rough estimate of additional operational overhead

**Moderate.**

The introduction of ElastiCache for Redis adds a new critical component to the infrastructure. While ElastiCache is a managed service, it still requires monitoring (cache hit ratio, memory utilization, network I/O), capacity planning, and understanding its operational characteristics (e.g., eviction policies, cluster scaling). The cache invalidation/update logic, especially if implemented with SNS/SQS/Lambda, introduces additional distributed system complexity that needs to be designed, implemented, and maintained. Debugging cache-related issues (e.g., stale data, cache misses) will require new tooling and expertise. However, the benefits in performance and scalability are substantial, and the managed nature of ElastiCache reduces the burden compared to self-hosting Redis.

### Going further

#### Potential data consistency challenge

A significant data consistency challenge that could arise is **"stale reads due to delayed cache invalidation."**

Consider the scenario where a user (User X) posts a new photo. The backend service writes this activity to the PostgreSQL database. Immediately after, User Y (who follows User X) requests their activity feed. If the cache invalidation or update for User Y's feed is delayed (e.g., due to a transient issue with the SNS/SQS/Lambda pipeline, network latency, or processing backlog), User Y might retrieve a cached version of their feed that does *not* include User X's new photo. A few seconds later, the cache update completes, and subsequent requests from User Y would show the new photo. This "eventual consistency" is acceptable for many social media feeds, but if the delay is too long or frequent, it degrades user experience.

#### Monitoring for it

To monitor for stale reads, we would implement the following:

1.  **Synthetic Transactions/Canary Users:** Create "canary" users and automate a sequence of actions:
    *   Canary User X posts an activity.
    *   Record the exact timestamp of the database write.
    *   Immediately (or after a short, fixed delay) Canary User Y (who follows X) requests their feed.
    *   Check if User X's new activity is present in User Y's retrieved feed.
    *   Measure the time difference between the database write and when the activity appears in the cached feed.
    *   Alert if this latency exceeds a defined threshold (e.g., 5 seconds) or if the activity is consistently missing.
2.  **Cache Hit Ratio and Eviction Metrics:** Monitor ElastiCache's `CacheHitRate` and `Evictions` metrics in CloudWatch. A sudden drop in hit rate could indicate issues with cache population or an invalidation storm. High eviction rates might mean the cache is undersized, leading to more frequent database reads and potentially increasing the likelihood of stale data if the evicted items were recently updated.
3.  **Application-level Logging:** Log the timestamp of when a feed is served from cache and, if possible, include a version identifier or a hash of the feed content. When a user reports stale data, these logs can help trace whether the cached entry was indeed outdated at the time of retrieval.
4.  **Database vs. Cache Comparison (Audit):** Periodically, for a small sample of users, fetch their feed directly from the database and compare it with the cached version. Report discrepancies and the age of the cached data. This can be run as a background batch job.

#### Mitigation strategies

1.  **Optimized Cache Invalidation/Update Logic:**
    *   **Asynchronous Processing with Retries:** Ensure the SNS/SQS/Lambda pipeline for cache updates has robust error handling and retry mechanisms. Dead-letter queues (DLQs) for SQS are essential to capture and reprocess failed messages.
    *   **Batching Updates:** For users with many followers, instead of invalidating/updating each follower's cache individually, consider a more efficient strategy like invalidating a "fan-out" key or using a background job to update multiple feeds in batches.
    *   **Event Sourcing for Activities:** If the complexity allows, an event-driven architecture where all activity changes are events could feed a dedicated cache-building service that constructs and updates feeds in Redis more consistently.
2.  **Short TTLs for Critical Feeds:** For highly active users or critical feeds where freshness is paramount, set a relatively short TTL (e.g., 30-60 seconds) on their cached entries. This ensures that even if an invalidation is missed, the data will eventually be refreshed from the database.
3.  **"Read-Through with Refresh" Strategy:** Instead of pure write-through, implement a read-through strategy where, on a cache miss, the application fetches from the DB, updates the cache, and returns. Additionally, for critical feeds, consider a background refresh mechanism that periodically fetches the latest data from the DB and updates the cache, even if there's a cache hit.
4.  **Graceful Degradation / User Feedback:**
    *   **"Pull to Refresh":** Implement a "pull to refresh" mechanism in the UI, allowing users to explicitly request the latest data, which would bypass the cache or trigger an immediate cache refresh.
    *   **Display Last Updated Time:** Inform users about the freshness of the feed (e.g., "Last updated 30 seconds ago"). This manages expectations.
5.  **Cache Sizing and Scaling:** Ensure the ElastiCache cluster is adequately sized to prevent excessive evictions, which can lead to more frequent database reads and potentially stale data if the evicted items were not yet updated by the invalidation pipeline. Monitor memory usage and scale out the cluster proactively.

By combining robust monitoring with these mitigation strategies, we can minimize the impact of eventual consistency on user experience while still leveraging the performance benefits of caching.
