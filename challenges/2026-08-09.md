## Scenario

Your company operates a global SaaS platform where users can schedule and manage tasks. Each task has a `status` (e.g., `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED`) and a `due_date`. We use a PostgreSQL database.

A critical background worker service is responsible for identifying tasks that are overdue (`status` is `PENDING` and `due_date` is in the past) and transitioning their status to `FAILED`. This service currently runs as a single instance, querying the `tasks` table every 5 seconds.

The `tasks` table has grown significantly to hundreds of millions of rows, with millions of tasks becoming overdue daily across different timezones. The single background worker is now critically bottlenecked: it can't keep up with the volume of overdue tasks, leading to significant delays in status updates. Furthermore, if the single worker fails, no tasks are marked as failed, which impacts dependent downstream processes.

You need to scale this overdue task processing system to handle the increased load and improve its reliability. The solution must be highly available and tolerate worker failures gracefully.

## Requirements

The core challenge is to design and describe a distributed system for marking overdue tasks as `FAILED` that meets the following criteria:

*   **High Throughput:** Efficiently process millions of overdue tasks per day, updating their status promptly.
*   **Fault Tolerance:** The system should continue operating even if individual worker instances fail. No overdue tasks should be missed due to worker failure.
*   **No Duplicate Processing:** Each overdue task must be marked as `FAILED` exactly once.
*   **Scalability:** The system should easily scale horizontally by adding more worker instances.
*   **Minimal Database Load:** Avoid excessive read/write contention on the `tasks` table, especially for the update operations.

|                   |     |                   |
+---------+---------+     +---------+---------+
          |                       |
          | (Publishes Overdue    | (Consumes Overdue

+-----------------------------------+

+-----------------------------------+
          ^                       ^
          |                       |
          | (Reads Task Data)     | (Updates Task Status)

**Components:**

*   **PostgreSQL Database:** Stores the `tasks` table.
*   **Task Scheduler (Leader Election):** A set of instances responsible for querying the database for overdue tasks and publishing their IDs to a message queue. Only one instance acts as a leader at any given time to prevent duplicate publishing.
*   **Message Queue (Kafka):** A distributed, fault-tolerant message broker used to decouple the scheduling and processing of overdue tasks. It stores task IDs that need to be marked as `FAILED`.
*   **Task Processor (Workers):** A group of stateless worker instances that consume task IDs from the message queue, fetch the latest task status from the database, and update the status to `FAILED`.

### 2. Mechanisms for exactly-once processing and fault tolerance

Achieving "exactly-once" semantics in a distributed system is challenging and often refers to "effectively once" or "at-least-once processing with idempotency." Here, we'll aim for effectively once processing by combining at-least-once delivery with idempotent updates.

**Leader Election for Task Scheduler:**
To prevent multiple schedulers from publishing the same overdue task IDs, we'll use a leader election mechanism (e.g., ZooKeeper, etcd, or a database-backed lock). Only the elected leader will perform the database query and publish tasks to Kafka. If the leader fails, a new leader is elected, ensuring continuous operation.

**Kafka as a Message Queue:**
Kafka provides several features crucial for fault tolerance and ordered processing:
*   **Durability:** Messages are persisted to disk and replicated across multiple brokers, ensuring no data loss even if brokers fail.
*   **Partitioning:** Tasks can be distributed across multiple partitions, allowing parallel consumption by workers.
*   **Consumer Groups:** Multiple worker instances can form a consumer group, with each partition assigned to a single consumer within the group. This ensures that each message is processed by exactly one worker in the group. If a worker fails, its partitions are automatically reassigned to other workers in the group.
*   **Offset Management:** Kafka consumers commit their processed offsets, indicating the last message successfully processed. If a worker fails and restarts, it can resume processing from the last committed offset, preventing reprocessing of already handled messages (or minimizing it if offsets are committed strategically).

**Idempotent Task Updates:**
The most critical part for "exactly once" is making the task update operation idempotent. This means applying the update multiple times has the same effect as applying it once.

When a `Task Processor` consumes a task ID:
1.  It fetches the task from the database.
2.  It checks the current `status` and `due_date`.
3.  It updates the `status` to `FAILED` *only if* the current status is `PENDING` and the `due_date` is in the past. This conditional update is key.

The SQL update statement would look like this:

```sql
UPDATE tasks
SET status = 'FAILED',
    updated_at = NOW()
WHERE id = :task_id
  AND status = 'PENDING'
  AND due_date < NOW();
```

**Why this is idempotent:**
If a worker processes a task, updates its status to `FAILED`, and then crashes *before* committing its Kafka offset, another worker (or the restarted worker) might pick up the same message. When it executes the `UPDATE` statement again, the `WHERE` clause `status = 'PENDING'` will no longer be true (because it's already `FAILED`), so no further changes will be made. The `updated_at` timestamp might be updated again, but the core `status` change only happens once.

**Trade-offs:**
*   **At-least-once delivery from Kafka:** While Kafka consumer groups ensure each message is delivered to one consumer, network issues or worker crashes can lead to a message being delivered again (e.g., if a worker crashes after processing but before committing its offset). The idempotent update handles this.
*   **Increased database reads:** Each worker needs to read the task status before updating. This is a trade-off for strong idempotency. An alternative could be to push more logic into the SQL update, but reading allows for more complex conditional logic if needed.

### 3. Distributing workload and minimizing contention

**Task Scheduler Workload Distribution:**
The `Task Scheduler` leader will query for overdue tasks in batches. To avoid contention on the `tasks` table and distribute the load of *finding* tasks, the query can be optimized:

```sql
SELECT id, due_date
FROM tasks
WHERE status = 'PENDING'
  AND due_date < NOW()
ORDER BY due_date ASC
LIMIT 10000; -- Process in batches
```

To avoid repeatedly scanning the same tasks, the scheduler can maintain a cursor or use time-based partitioning. For example, it could query for tasks overdue in specific time windows. However, a simpler and more robust approach for high volume is to rely on the `status = 'PENDING'` clause. Once a task is marked `FAILED`, it won't be picked up again by the scheduler.

To prevent the scheduler from overwhelming the database, it should:
*   **Batching:** Query for a limited number of tasks (e.g., 10,000-50,000) in each run.
*   **Rate Limiting:** Introduce a delay between query runs (e.g., once every 5-10 seconds, similar to the original system, but now only for finding, not updating).
*   **Partitioning Kafka topics:** The scheduler can publish tasks to different Kafka partitions based on a hash of the `task_id` or `user_id` to ensure related tasks are processed by the same worker (if that's a requirement, though not explicitly stated here). For general overdue tasks, round-robin or random partitioning is sufficient.

**Task Processor Workload Distribution:**
*   **Kafka Consumer Groups:** As described, multiple `Task Processor` instances form a consumer group. Kafka automatically distributes partitions among consumers in the group. Each partition is processed by at most one consumer at a time. This allows for horizontal scaling: add more worker instances, and Kafka will rebalance partitions, distributing the load.
*   **Parallel Processing within Workers:** Each `Task Processor` instance can use multiple threads or goroutines to process messages concurrently from its assigned partitions. This maximizes CPU utilization within a single worker.
*   **Database Connection Pooling:** Workers should use efficient database connection pooling to minimize overhead and contention on the database server.
*   **Batch Updates (Optional, but beneficial):** While the idempotent update is per task, workers could accumulate a small batch of `task_id`s and perform a single `UPDATE` statement using `WHERE id IN (...)` for multiple tasks. This reduces network round-trips and database transaction overhead. However, it complicates error handling (if one task in the batch fails) and offset management (if the batch update fails, all tasks in the batch might need to be reprocessed). For simplicity and strong "effectively once" guarantees, per-task updates are often preferred unless throughput becomes a bottleneck *at the database update level*. Given the millions of updates, batching *could* be considered for the `UPDATE` operation, but it requires careful design. For this solution, we assume individual updates for clarity and robustness.

### 4. Schema and indexing changes

**Existing `tasks` table schema (assumed):**

```sql
CREATE TABLE tasks (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    status VARCHAR(50) NOT NULL, -- e.g., 'PENDING', 'IN_PROGRESS', 'COMPLETED', 'FAILED'
    due_date TIMESTAMP WITH TIME ZONE NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT NOW(),
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT NOW()
);
```

**Required changes:**

1.  **Add an index for efficient querying by the `Task Scheduler`:**
    The scheduler frequently queries `WHERE status = 'PENDING' AND due_date < NOW()`. A composite index on these columns is essential.

    ```sql
    CREATE INDEX idx_tasks_status_due_date ON tasks (status, due_date);
    ```
    **Why:** This index allows PostgreSQL to quickly find tasks that are `PENDING` and then efficiently filter by `due_date`. The `ORDER BY due_date` in the scheduler's query would also benefit from this index.

2.  **Consider a `last_checked_at` or `processing_lock` column (Optional, for advanced scenarios):**
    While the `status = 'PENDING'` clause in the update is sufficient for idempotency, if the system needed to prevent *any* worker from even attempting to process a task already being handled by another, a `processing_lock` column could be added. However, this adds complexity and potential for deadlocks if not managed carefully. For this specific problem (marking overdue tasks as `FAILED`), the idempotent update is generally preferred for its simplicity and robustness.

    *Self-correction:* For this problem, adding a `last_checked_at` or `processing_lock` column is an anti-pattern. The `status` column itself, combined with the idempotent `UPDATE` statement, serves as the implicit lock. Introducing another column for locking would add complexity, potential for stale locks, and unnecessary database writes/reads without providing significant additional benefit for the "overdue to failed" transition. The current design relies on the eventual consistency of the `status` update.

### Going further: Preventing race conditions with multiple services

The scenario describes a potential race condition: a user completes a task (setting `status` to `COMPLETED`) just as our system marks it as `FAILED`.

Our proposed solution already incorporates the primary mechanism to prevent this: **optimistic locking via conditional updates.**

The `Task Processor` uses the following SQL statement:

```sql
UPDATE tasks
SET status = 'FAILED',
    updated_at = NOW()
WHERE id = :task_id
  AND status = 'PENDING'
  AND due_date < NOW();
```

**How it prevents race conditions:**

1.  **User completes task:** If a user service updates the task `status` to `COMPLETED` (or `IN_PROGRESS`) *before* our `Task Processor` executes its `UPDATE` statement, the `WHERE status = 'PENDING'` condition will evaluate to `FALSE`. Consequently, our `UPDATE` statement will affect zero rows, and the task's status will remain `COMPLETED` (or `IN_PROGRESS`). The `Task Processor` will effectively "do nothing" for that task, which is the desired outcome.

2.  **Our system marks task as FAILED:** If our `Task Processor` executes its `UPDATE` statement *before* the user service updates the task, the status will be set to `FAILED`. If the user service then tries to mark it `COMPLETED`, it should also use a conditional update (e.g., `WHERE status = 'PENDING' OR status = 'IN_PROGRESS'`) or handle the `FAILED` status gracefully.

**Key principles for multiple services:**

*   **Conditional Updates (Optimistic Locking):** Any service attempting to change a task's status should include the *expected current status* in its `WHERE` clause. This ensures that an update only proceeds if the task is in the state the service expects.

    Example for a user completing a task:
    ```sql
    UPDATE tasks
    SET status = 'COMPLETED',
        completed_at = NOW(),
        updated_at = NOW()
    WHERE id = :task_id
      AND status IN ('PENDING', 'IN_PROGRESS'); -- Only update if not already FAILED or other terminal state
    ```

*   **Define Status Transition Rules:** Clearly define the valid state transitions for tasks. For example:
    *   `PENDING` -> `IN_PROGRESS`
    *   `PENDING` -> `FAILED` (by our system)
    *   `IN_PROGRESS` -> `COMPLETED`
    *   `IN_PROGRESS` -> `FAILED` (if it times out while in progress)
    *   `COMPLETED` -> (no further changes)
    *   `FAILED` -> (no further changes, or only to `RETRY` if implemented)

    Any service attempting an update should validate against these rules. The conditional `WHERE` clauses enforce these rules at the database level.

*   **Application-level conflict resolution:** If an update fails (0 rows affected) because the `WHERE` clause wasn't met, the application service should detect this. For example, the user service might inform the user "Task could not be completed as it was already marked failed."

By consistently applying conditional updates based on the current `status`, all services can safely operate on the `tasks` table without explicit global locks, relying on the database's atomic `UPDATE` operation to resolve concurrent attempts correctly. This is a standard pattern for optimistic concurrency control in distributed systems.
