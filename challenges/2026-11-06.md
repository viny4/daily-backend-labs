## Scenario

Your team maintains the backend for a B2B SaaS platform that processes various types of financial reports for thousands of enterprise clients. A critical component is the **report generation service**, which asynchronously creates PDF reports based on complex SQL queries against a large PostgreSQL database (managed by RDS).

These reports can vary significantly in size and complexity depending on the client's data volume and the specific report template. Historically, reports took anywhere from 30 seconds to several minutes to generate. Your current setup involves a single auto-scaling group of EC2 instances running Django/Celery workers that pull jobs from an SQS queue, perform the database queries, generate the PDF using a headless browser (e.g., Playwright or Puppeteer), and then upload the resulting PDF to an S3 bucket.

The problem: during peak times (e.g., end-of-month reporting), the SQS queue depth grows rapidly, leading to report generation latencies exceeding several hours. Some individual report generation jobs are also timing out (after 15 minutes) on the worker instances, even with increased instance sizes. The root cause appears to be two-fold:
1. A small percentage of reports are extremely data-intensive, requiring significantly more CPU and memory than average.
2. The current worker fleet is not scaling fast enough, or efficiently enough, to handle the bursty nature of report generation requests.

You need to propose and outline an architectural change to improve the scalability and reliability of this report generation service, specifically addressing the long queue times and timeouts for large reports.

## Requirements

The solution must address the following constraints:

*   **Scalability:** The system must be able to handle sudden bursts of thousands of report generation requests without significant degradation in latency (target average report generation time < 10 minutes, with p99 < 30 minutes).
*   **Cost-effectiveness:** While performance is key, the solution should avoid over-provisioning resources during off-peak times.
*   **Reliability:** Individual report generation jobs, especially the large ones, must complete successfully without timing out.
*   **Minimal code changes:** While some configuration or infrastructure-as-code changes are expected, a complete rewrite of the existing Django/Celery application logic is out of scope for this immediate task.
*   **AWS native:** The solution should leverage AWS services as much as possible.

## Worked answer

### 1. High-level Architectural Diagram

The core idea is to introduce a mechanism to differentiate between "small" and "large" reports and process them using distinct compute environments optimized for their respective resource needs. AWS Step Functions will orchestrate this process, leveraging AWS Lambda for smaller, burstable tasks and AWS Fargate (or potentially EC2 Spot Instances within an ECS cluster) for larger, long-running, and resource-intensive jobs.

**Workflow Description:**

1.  **Request Ingestion:** Client requests for report generation are received via an API Gateway or an existing service entry point.
2.  **Initial Processing (Lambda):** A lightweight Lambda function receives the request, performs initial validation, stores report metadata (e.g., `report_id`, `client_id`, `template_id`, `status: PENDING`) in DynamoDB, and then publishes a message to an SQS queue. This decouples the request ingestion from the report generation workflow.
3.  **Workflow Trigger (SQS -> Step Functions):** The SQS message triggers an AWS Step Functions state machine.
4.  **Report Type Determination (Step Functions Choice State):** The Step Functions workflow first retrieves the report metadata from DynamoDB (or the SQS message itself contains enough information). Based on pre-defined heuristics (e.g., `template_id`, `expected_data_volume` derived from client configuration, or even a quick pre-query against the database), it determines if the report is "small" or "large".
5.  **Parallel Processing:**
    *   **Small Reports (Lambda):** If classified as "small", the workflow invokes a dedicated Lambda function. This Lambda function contains the existing Django/Celery worker logic (or a refactored version of it) for database querying and PDF generation. Lambda is ideal for bursty, short-lived tasks, scaling instantly and costing per invocation.
    *   **Large Reports (ECS Fargate):** If classified as "large", the workflow launches an ECS Fargate task. This Fargate task runs a Docker container containing the same Django/Celery worker logic but with significantly more allocated CPU and memory. Fargate provides serverless containers, eliminating EC2 instance management while offering fine-grained resource control and longer execution times.
6.  **PDF Storage (S3):** Both Lambda and Fargate tasks upload the generated PDF to an S3 bucket.
7.  **Status Update (Step Functions/Lambda):** After successful generation, the Step Functions workflow (or a final step in the Lambda/Fargate task) updates the report status in DynamoDB to `COMPLETED` and notifies the client (e.g., via SNS or a webhook).

### 2. Central AWS Services and their Contribution

1.  **AWS Step Functions:**
    *   **Contribution to Scalability:** Step Functions orchestrates complex workflows, allowing for parallel execution branches and retries. It doesn't directly provide compute but ensures that jobs are routed to the *correct* compute environment. Its ability to manage long-running workflows (up to a year) is crucial for reports that might take a long time, ensuring state persistence and visibility. It acts as a robust, serverless coordinator that can handle thousands of concurrent workflow executions.
    *   **Contribution to Reliability:** Step Functions provides built-in error handling, retries, and choice states, making the overall report generation process more resilient. If a Lambda invocation fails or a Fargate task encounters an issue, Step Functions can automatically retry, catch errors, or transition to a compensatory state, preventing jobs from being lost or timing out without resolution. It also provides a visual workflow for debugging and monitoring.

2.  **AWS Fargate (within Amazon ECS):**
    *   **Contribution to Scalability:** Fargate provides serverless compute for containers, meaning you don't provision or manage EC2 instances. It scales instantly by launching new tasks as needed, without waiting for EC2 instances to boot or join an ASG. This is critical for handling the bursty nature of large report requests, as it can provision exactly the right amount of CPU and memory for each task. It eliminates the problem of slow EC2 ASG scaling.
    *   **Contribution to Reliability:** Fargate tasks are isolated and can be configured with high CPU and memory limits (e.g., up to 16 vCPUs and 120 GB memory), ensuring that even the most data-intensive reports have sufficient resources to complete without timing out. Each task runs in its own dedicated environment, preventing "noisy neighbor" issues that can occur on shared EC2 instances. Its ability to run for up to 24 hours (for ECS tasks) easily accommodates the "several minutes" to "15 minutes" timeout issues.

### 3. Handling Different Resource Requirements ("Small" vs. "Large" Reports)

The proposed architecture handles different resource requirements by creating two distinct processing paths, each optimized for a specific report profile:

*   **"Small" Reports (AWS Lambda):**
    *   **Characteristics:** These reports are expected to complete quickly (e.g., under 5-10 minutes), require moderate CPU/memory, and are highly burstable.
    *   **Execution Environment:** AWS Lambda functions are used. Lambda scales almost infinitely and instantly based on the number of concurrent invocations. You pay per millisecond of compute time and memory used.
    *   **Resource Allocation:** Lambda functions can be configured with memory from 128 MB up to 10,240 MB (10 GB). CPU is allocated proportionally to memory. For small reports, we would likely configure them with 1-2 GB of memory, which is sufficient for most typical web application tasks.
    *   **Cost-effectiveness:** Ideal for bursty, short-lived tasks as you only pay for actual compute time, avoiding idle capacity costs.

*   **"Large" Reports (AWS Fargate Task):**
    *   **Characteristics:** These reports are data-intensive, require significant CPU and memory, might run for longer durations (e.g., 10-30 minutes, potentially up to an hour), and are less sensitive to cold starts than small reports.
    *   **Execution Environment:** AWS Fargate tasks within an Amazon ECS cluster. Fargate provides a serverless container experience, where you specify CPU and memory requirements, and AWS manages the underlying EC2 instances.
    *   **Resource Allocation:** Fargate tasks offer much higher resource limits than Lambda, ranging from 0.25 vCPU and 0.5 GB memory up to 16 vCPU and 120 GB memory. For large reports, we would configure tasks with, for example, 4-8 vCPUs and 16-32 GB of memory, tailored to the observed needs of the most demanding reports.
    *   **Cost-effectiveness:** While potentially more expensive per hour than Lambda for very short tasks, Fargate is cost-effective for longer-running, resource-intensive jobs because it provides dedicated resources and avoids the overhead of managing EC2 instances. It scales out quickly to meet demand without over-provisioning.

The **Step Functions Choice state** is the key component that intelligently routes jobs. The logic for this choice would be based on:
*   **Report Template ID:** Certain templates are known to generate large reports.
*   **Client Tier/Data Volume:** Enterprise clients with massive datasets are more likely to generate large reports.
*   **Pre-computation/Estimation:** A quick, lightweight query could estimate the number of rows or complexity involved, informing the choice.
*   **User Input:** The user initiating the report might explicitly tag it as "large".

      name     = "ReportGenerationWorkflow"
      role_arn = aws_iam_role.sfn_execution_role.arn

      definition = jsonencode({
        Comment = "Workflow for generating reports, routing based on size."
        StartAt = "RetrieveReportMetadata"
        States = {
          RetrieveReportMetadata = {
            Type = "Task"
            Resource = "arn:aws:states:::dynamodb:getItem"
            Parameters = {
              TableName = aws_dynamodb_table.report_metadata.name
              Key = {

              }
            }
            ResultPath = "$.ReportDetails"
            Next = "DetermineReportSize"
          }
          DetermineReportSize = {
            Type = "Choice"
            Choices = [
              {
                Variable = "$.ReportDetails.Item.report_size_estimate.S"
                StringEquals = "LARGE"
                Next = "GenerateLargeReport"
              },
              {
                Variable = "$.ReportDetails.Item.report_size_estimate.S"
                StringEquals = "SMALL"
                Next = "GenerateSmallReport"

                MaxAttempts = 6
                BackoffRate = 2

            ]
            Catch = [
              {
                ErrorEquals = ["States.ALL"]
                Next = "HandleReportFailure"
              }
            ]
            Next = "UpdateReportStatusSuccess"
          }
          GenerateLargeReport = {
            Type = "Task"
            Resource = "arn:aws:states:::ecs:runTask.sync" # Use .sync to wait for task completion
            Parameters = {
              Cluster = aws_ecs_cluster.report_cluster.arn
              TaskDefinition = aws_ecs_task_definition.large_report_task.arn
              LaunchType = "FARGATE"
              NetworkConfiguration = {

                  Subnets = aws_subnet.private.*.id
                  SecurityGroups = [aws_security_group.ecs_tasks.id]
                  AssignPublicIp = "DISABLED"
                }
              }
              Overrides = {
                ContainerOverrides = [
                  {
                    Name = "report-worker"
                    Environment = [
                      { Name = "REPORT_ID", Value = "$.report_id" },
                      { Name = "CLIENT_ID", Value = "$.client_id" },
                      { Name = "TEMPLATE_ID", Value = "$.template_id" }
                    ]
                  }
                ]
              }
            }
            Retry = [
              {
                ErrorEquals = ["States.TaskFailed"]
                IntervalSeconds = 10
                MaxAttempts = 3
                BackoffRate = 1.5
              }
            ]
            Catch = [
              {
                ErrorEquals = ["States.ALL"]
                Next = "HandleReportFailure"
              }
            ]
            Next = "UpdateReportStatusSuccess"
          }
          UpdateReportStatusSuccess = {
            Type = "Task"
            Resource = "arn:aws:states:::dynamodb:updateItem"
            Parameters = {
              TableName = aws_dynamodb_table.report_metadata.name
              Key = {
                report_id = { "S.$": "$.report_id" }
              }
              UpdateExpression = "SET #status = :status_val, #completed_at = :completed_at_val, #s3_path = :s3_path_val"
              ExpressionAttributeNames = {
                "#status" = "status"
                "#completed_at" = "completed_at"
                "#s3_path" = "s3_path"
              }
              ExpressionAttributeValues = {
                ":status_val" = { "S": "COMPLETED" }
                ":completed_at_val" = { "S.$": "$$.State.EnteredTime" } # Or from task output
                ":s3_path_val" = { "S.$": "$.s3_path" } # Assuming task returns s3_path
              }
            }
            End = true
          }
          HandleReportFailure = {
            Type = "Task"
            Resource = "arn:aws:states:::dynamodb:updateItem"
            Parameters = {
              TableName = aws_dynamodb_table.report_metadata.name
              Key = {
                report_id = { "S.$": "$.report_id" }
              }
              UpdateExpression = "SET #status = :status_val, #error_message = :error_message_val"
              ExpressionAttributeNames = {
                "#status" = "status"
                "#error_message" = "error_message"
              }
              ExpressionAttributeValues = {
                ":status_val" = { "S": "FAILED" }
                ":error_message_val" = { "S.$": "$.Cause" } # Step Functions provides error details in Cause

            }

      })

### Going Further

**Trade-offs compared to simply scaling up existing EC2 instances or increasing Celery worker concurrency:**

1.  **Resource Utilization:**
    *   **Proposed Solution (Lambda + Fargate):**
        *   **Pros:** Highly optimized resource utilization. Lambda is billed per millisecond, eliminating idle costs for small, bursty tasks. Fargate allows precise CPU/memory allocation per task, ensuring large reports get exactly what they need without over-provisioning an entire EC2 instance for a single job. This leads to significantly better resource efficiency, especially during off-peak hours or when dealing with a mixed workload.
        *   **Cons:** Potentially higher cost per unit of compute for very long-running, consistently high-utilization tasks compared to a fully optimized EC2 instance. However, for bursty and varied workloads, the savings from eliminating idle time and right-sizing usually outweigh this.
    *   **Scaling Existing EC2/Celery:**
        *   **Pros:** Simpler to manage if the workload is uniform and predictable. Can be cheaper if instances are consistently 100% utilized.
        *   **Cons:**
            *   **Over-provisioning:** To handle peak demand or large reports, you'd need to scale up EC2 instances to sizes capable of running the largest reports. These large instances would then be underutilized when processing smaller reports or during off-peak times, leading to wasted resources and higher costs.
            *   **Under-provisioning:** If you scale for average load, large reports will time out or significantly delay the queue.
            *   **Slow Scaling:** EC2 Auto Scaling Groups (ASGs) can take several minutes to launch new instances, especially if they need to download large Docker images or run user data scripts. This delay contributes directly to queue depth during sudden bursts.
            *   **"Noisy Neighbor" Problem:** A single large report can monopolize resources on an EC2 instance, starving other Celery workers on the same instance and causing multiple jobs to fail or slow down.

2.  **Operational Overhead:**
    *   **Proposed Solution (Lambda + Fargate):**
        *   **Pros:** Significantly reduced operational overhead related to server management. No EC2 instances to patch, update, or manage. AWS handles the underlying infrastructure. Focus shifts to application code, Docker image management, and workflow definition. Step Functions provides excellent visibility and debugging for workflow execution.
        *   **Cons:** Requires familiarity with new AWS services (Step Functions, Fargate, Lambda invocation models). Debugging distributed workflows can be more complex than a monolithic application on a single server, though Step Functions helps mitigate this. Initial setup complexity is higher.
    *   **Scaling Existing EC2/Celery:**
        *   **Pros:** Familiar technology stack for teams already using EC2/Celery.
        *   **Cons:** Requires ongoing management of EC2 instances (OS patching, security updates, AMI management), ASG configuration, and capacity planning. Debugging can be challenging when issues span multiple instances and Celery workers. Managing Celery worker concurrency and resource limits on shared instances requires careful tuning.

3.  **Cost:**
    *   **Proposed Solution (Lambda + Fargate):**
        *   **Pros:** Generally more cost-effective for bursty, unpredictable, or highly variable workloads due to pay-per-use models and precise resource allocation. Eliminates costs associated with idle EC2 instances.
        *   **Cons:** Costs can become higher than EC2 for very stable, high-utilization, long-running workloads where you can consistently pack tasks onto a few large EC2 instances. Lambda costs can escalate rapidly with extremely high concurrency and execution times.
    *   **Scaling Existing EC2/Celery:**
        *   **Pros:** Potentially cheaper for very stable, predictable, and consistently high-utilization workloads where instances can be purchased with Reserved Instances or Savings Plans.
        *   **Cons:** High risk of over-provisioning and paying for idle capacity. Scaling up to large instances to handle peak demand or large reports means paying for that capacity even when it's not fully utilized.

**What breaks first at ten times the scale in the scenario:**

At ten times the scale (tens of thousands of reports per hour, with a similar distribution of small/large):

1.  **RDS Database Contention:** The most likely bottleneck will shift to the PostgreSQL RDS database. Ten times the number of concurrent report generation tasks (each running complex SQL queries) will put immense pressure on database CPU, memory, I/O, and connection limits. Even with read replicas, write operations (e.g., updating report status, or even the initial data retrieval if not optimized) will become a choke point.
    *   **Mitigation:** Database sharding, read replicas for report data retrieval, query optimization, aggressive caching, and potentially moving some report data to a purpose-built data warehouse (e.g., Redshift or Snowflake) for reporting queries.

2.  **DynamoDB Throughput (if not configured correctly):** While `PAY_PER_REQUEST` handles scaling, if the access patterns for `report_metadata` become extremely high (e.g., thousands of reads/writes per second for status updates or metadata retrieval), it could hit soft limits or experience throttling if not provisioned correctly or if the partition key design leads to hot spots.
    *   **Mitigation:** Ensure `report_id` is a good partition key for even distribution. Monitor DynamoDB metrics closely.

3.  **AWS Service Limits:** While Lambda and Fargate scale massively, there are still account-level soft limits (e.g., concurrent Lambda invocations, concurrent Fargate tasks in a region). These would need to be monitored and increased through AWS support requests.
    *   **Mitigation:** Proactive monitoring and limit increase requests.

4.  **S3 API Request Limits:** If every report generation task uploads to S3, the sheer volume of `PutObject` requests could hit S3's per-prefix or per-bucket request limits, leading to throttling.
    *   **Mitigation:** S3 scales extremely well, but ensuring good key naming (e.g., `client_id/report_id/report.pdf`) helps distribute requests across prefixes.

The proposed architecture handles the compute scaling very well, pushing the bottlenecks further down the stack to shared resources like the database or service limits, which are easier to identify and address systematically.
