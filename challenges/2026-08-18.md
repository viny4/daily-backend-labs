## Scenario

Your team maintains a critical internal microservice built with Node.js and TypeScript. This service aggregates data from various upstream services (e.g., customer profiles, subscription details, usage metrics) to create a comprehensive "customer dashboard" view for your support and sales teams. A key endpoint, `/api/v1/customer-summary/:customerId`, is responsible for fetching and combining this data.

Lately, the endpoint has become a bottleneck. As your customer base grows, the number of API calls to this endpoint increases, and more importantly, the latency for individual requests has become unpredictable, sometimes spiking to 5-8 seconds. The primary issue is that fetching data from each upstream service is an independent, potentially slow, network operation. The current implementation fetches these sequentially. Additionally, some upstream services are less reliable than others and occasionally fail or time out. Your team has a strict latency budget of 1.5 seconds for this endpoint, and support agents are complaining about slow dashboards.

## Requirements

The core problem is to significantly reduce the perceived latency of the `/api/v1/customer-summary/:customerId` endpoint by executing upstream service calls concurrently. You also need to gracefully handle individual upstream service failures without failing the entire summary request, providing partial data where possible. The system should prioritize speed and resilience.

Constraints:
*   **Latency Budget:** The `/api/v1/customer-summary/:customerId` endpoint must respond within 1.5 seconds for 99% of requests.
*   **Concurrency:** Calls to different upstream services must be made concurrently.
*   **Error Handling:** If one upstream service fails or times out, the other successful responses should still be returned. The response should clearly indicate which parts of the data are missing or failed.
*   **TypeScript:** All new or modified code must be strictly typed.
*   **Node.js Environment:** You can use standard Node.js APIs and common utility libraries. Assume a modern Node.js runtime.

## Worked answer

### 1. Revised `getCustomerSummary` Function

The `getCustomerSummary` function will orchestrate concurrent calls to mock upstream services. We'll use `Promise.allSettled` to ensure that all promises resolve, regardless of individual success or failure, allowing us to collect partial data.

```typescript
// --- Mock Upstream Services (simulating network calls) ---

interface CustomerProfile {
  customerId: string;
  name: string;
  email: string;
  address: string;
}

interface SubscriptionDetails {
  customerId: string;
  plan: string;
  status: 'active' | 'inactive' | 'trial';
  startDate: string;
  renewalDate: string;
}

interface UsageMetrics {
  customerId: string;
  dataUsedGB: number;
  callsMade: number;
  smsSent: number;
  lastUpdated: string;
}

// Simulate a network delay and potential failure
async function fetchCustomerProfile(customerId: string): Promise<CustomerProfile> {
  const delay = Math.random() * 300 + 100; // 100-400ms
  await new Promise(resolve => setTimeout(resolve, delay));
  if (Math.random() < 0.1) { // 10% chance of failure
    throw new Error(`Failed to fetch profile for ${customerId}`);
  }
  return {
    customerId,
    name: `Customer ${customerId}`,
    email: `customer${customerId}@example.com`,
    address: `123 Main St, Anytown`,
  };
}

async function fetchSubscriptionDetails(customerId: string): Promise<SubscriptionDetails> {
  const delay = Math.random() * 500 + 200; // 200-700ms
  await new Promise(resolve => setTimeout(resolve, delay));
  if (Math.random() < 0.05) { // 5% chance of failure
    throw new Error(`Failed to fetch subscription for ${customerId}`);
  }
  return {
    customerId,
    plan: 'Premium',
    status: 'active',
    startDate: '2023-01-01',
    renewalDate: '2024-01-01',
  };
}

async function fetchUsageMetrics(customerId: string): Promise<UsageMetrics> {
  const delay = Math.random() * 800 + 300; // 300-1100ms
  await new Promise(resolve => setTimeout(resolve, delay));
  if (Math.random() < 0.15) { // 15% chance of failure
    throw new Error(`Failed to fetch usage metrics for ${customerId}`);
  }
  return {
    customerId,
    dataUsedGB: 150,
    callsMade: 1200,
    smsSent: 500,
    lastUpdated: new Date().toISOString(),
  };
}

// --- Core `getCustomerSummary` implementation ---

import { CustomerSummary } from './types'; // Assuming types are in a separate file

export async function getCustomerSummary(customerId: string): Promise<CustomerSummary> {
  const profilePromise = fetchCustomerProfile(customerId);
  const subscriptionPromise = fetchSubscriptionDetails(customerId);
  const usagePromise = fetchUsageMetrics(customerId);

  // Use Promise.allSettled to run all promises concurrently and collect all outcomes
  const [profileResult, subscriptionResult, usageResult] = await Promise.allSettled([
    profilePromise,
    subscriptionPromise,
    usagePromise,
  ]);

  const summary: CustomerSummary = {
    customerId: customerId,
    profile: undefined,
    subscription: undefined,
    usage: undefined,
    errors: [],
  };

  // Process results and populate the summary object
  if (profileResult.status === 'fulfilled') {
    summary.profile = profileResult.value;
  } else {
    summary.errors.push({ source: 'profile', message: profileResult.reason.message });
  }

  if (subscriptionResult.status === 'fulfilled') {
    summary.subscription = subscriptionResult.value;
  } else {
    summary.errors.push({ source: 'subscription', message: subscriptionResult.reason.message });
  }

  if (usageResult.status === 'fulfilled') {
    summary.usage = usageResult.value;
  } else {
    summary.errors.push({ source: 'usage', message: usageResult.reason.message });
  }

  return summary;
}
```

**Explanation:**

1.  **Mock Services:** We define three mock asynchronous functions (`fetchCustomerProfile`, `fetchSubscriptionDetails`, `fetchUsageMetrics`) that simulate network requests. They introduce random delays and a chance of failure to mimic real-world unreliable services.
2.  **Concurrency with `Promise.allSettled`:** Instead of `await`ing each `fetch` call sequentially, we initiate all three promises simultaneously by calling the functions without `await`.
3.  **Error Handling and Partial Data:** `Promise.allSettled` is crucial here. It waits for all promises to settle (either fulfill or reject) and returns an array of objects, each describing the outcome of a promise.
    *   If a promise `fulfilled`, its result object has `status: 'fulfilled'` and `value: T`.
    *   If a promise `rejected`, its result object has `status: 'rejected'` and `reason: any` (typically an `Error` object).
4.  **Constructing the Summary:** We iterate through the results from `Promise.allSettled`. If a service call was successful, its data is assigned to the corresponding field in the `summary` object. If it failed, we add an entry to the `errors` array, indicating which part of the data is missing and why. This ensures that even if one service fails, the overall request still returns successfully with whatever data was available.

### 2. Type Definitions

These types define the structure of the combined customer summary object and how missing or failed data segments are represented. We'll place these in a `types.ts` file.

```typescript
// types.ts

// Re-exporting mock service interfaces for clarity
export interface CustomerProfile {
  customerId: string;
  name: string;
  email: string;
  address: string;
}

export interface SubscriptionDetails {
  customerId: string;
  plan: string;
  status: 'active' | 'inactive' | 'trial';
  startDate: string;
  renewalDate: string;
}

export interface UsageMetrics {
  customerId: string;
  dataUsedGB: number;
  callsMade: number;
  smsSent: number;
  lastUpdated: string;
}

// Type for individual error reporting
export interface CustomerSummaryError {
  source: 'profile' | 'subscription' | 'usage'; // Identifies which upstream service failed
  message: string; // The error message from the upstream service
}

// The combined customer summary object
export interface CustomerSummary {
  customerId: string;
  profile?: CustomerProfile;       // Optional, as it might fail
  subscription?: SubscriptionDetails; // Optional, as it might fail
  usage?: UsageMetrics;           // Optional, as it might fail
  errors: CustomerSummaryError[]; // Array to collect all encountered errors
}
```

**Explanation:**

*   **Optional Properties (`?`):** The `profile`, `subscription`, and `usage` properties are marked as optional (`?`). This correctly reflects that they might be `undefined` if the corresponding upstream service call fails.
*   **`CustomerSummaryError`:** A dedicated interface to provide structured error information, including the `source` of the error (e.g., 'profile') and the `message`.
*   **`errors` Array:** The `errors` array allows us to collect multiple failure reports if more than one upstream service call fails, providing a comprehensive view of what went wrong.

### 4. Explanation of Individual Upstream Call Timeouts

While not explicitly implemented in the mock services above (as they have internal random delays), managing timeouts for individual upstream calls is critical for meeting the overall latency budget and preventing a single slow service from holding up the entire concurrent operation.

**Approach:**

The standard way to implement timeouts for individual promises in Node.js is to use `Promise.race()` with a competing `setTimeout`-based promise.

Here's how you would modify an individual `fetch` call (e.g., `fetchCustomerProfile`) to include a timeout:

```typescript
// Example of a fetch function with a timeout
async function fetchCustomerProfileWithTimeout(customerId: string, timeoutMs: number): Promise<CustomerProfile> {
  const profilePromise = fetchCustomerProfile(customerId); // Original fetch call

  const timeoutPromise = new Promise<never>((_, reject) =>
    setTimeout(() => reject(new Error(`Profile service timed out after ${timeoutMs}ms`)), timeoutMs)
  );

  // Promise.race will resolve or reject as soon as one of the promises settles
  return Promise.race([profilePromise, timeoutPromise]);
}
```

Then, in `getCustomerSummary`, you would call these timeout-wrapped functions:

```typescript
// Inside getCustomerSummary
const PROFILE_TIMEOUT = 500; // ms
const SUBSCRIPTION_TIMEOUT = 700; // ms
const USAGE_TIMEOUT = 900; // ms

const profilePromise = fetchCustomerProfileWithTimeout(customerId, PROFILE_TIMEOUT);
const subscriptionPromise = fetchSubscriptionDetailsWithTimeout(customerId, SUBSCRIPTION_TIMEOUT);
const usagePromise = fetchUsageMetricsWithTimeout(customerId, USAGE_TIMEOUT);

// ... then use Promise.allSettled as before
const [profileResult, subscriptionResult, usageResult] = await Promise.allSettled([
  profilePromise,
  subscriptionPromise,
  usagePromise,
]);
// ... process results
```

**Trade-offs and Considerations:**

*   **Granularity:** Each upstream service can have its own timeout, reflecting its typical latency and importance.
*   **Resource Management:** While `Promise.race` rejects early, the underlying network request might still be in progress in the background. For HTTP requests, libraries like `node-fetch` or `axios` allow passing an `AbortSignal` to truly cancel the request, freeing up resources. This is generally recommended for long-running or resource-intensive operations.
*   **Overall Budget:** The individual timeouts should be chosen carefully so that even if all services take their maximum allowed time (but within their timeout), the sum of the longest *concurrent* operation still fits within the overall 1.5-second budget. For example, if the slowest service has a 900ms timeout, and others are faster, the overall request might complete around 900ms.
*   **User Experience:** Timeouts prevent indefinite waits and ensure a predictable response time, even if it means returning partial data.

### Going Further: `Promise.all` vs. `Promise.allSettled`

**`Promise.all`**

*   **Behavior:** Takes an iterable of promises and returns a single promise. This single promise fulfills with an array of the fulfillment values of the input promises, in the same order, *only if and when all of the input promises have fulfilled*. If *any* of the input promises reject, the promise returned by `Promise.all` immediately rejects with the reason of the first promise that rejected.
*   **Use Case:** Best suited when *all* operations must succeed for the overall result to be meaningful. If even one piece of data is missing, the entire result is considered invalid.
*   **Example:** Fetching data for a transaction where all components (e.g., debit, credit, logging) must succeed, or the transaction must be rolled back.

**`Promise.allSettled`**

*   **Behavior:** Takes an iterable of promises and returns a single promise. This single promise fulfills with an array of objects, each describing the outcome of each input promise, *after all input promises have settled* (either fulfilled or rejected). The returned array will contain objects with `status: 'fulfilled'` and `value`, or `status: 'rejected'` and `reason`.
*   **Use Case:** Ideal when you need to perform multiple independent asynchronous operations and want to know the outcome of *all* of them, regardless of whether they succeeded or failed. It allows for graceful handling of partial failures and collecting as much data as possible.
*   **Example:** The current customer summary scenario, where some data is better than no data, and the UI can display "data unavailable" messages for failed sections.

**Justification for Preference in this Problem:**

For the given requirements, **`Promise.allSettled` is strongly preferred over `Promise.all`**.

The requirements explicitly state:
*   "You also need to gracefully handle individual upstream service failures without failing the entire summary request, providing partial data where possible."
*   "The response should clearly indicate which parts of the data are missing or failed."

If we had used `Promise.all`:

```typescript
// If we used Promise.all
try {
  const [profile, subscription, usage] = await Promise.all([
    fetchCustomerProfile(customerId),
    fetchSubscriptionDetails(customerId),
    fetchUsageMetrics(customerId),
  ]);
  // If any promise rejects, this block is skipped, and the catch block runs
  return { customerId, profile, subscription, usage, errors: [] };
} catch (error: any) {
  // This catch block would be hit immediately if ANY service fails.
  // We would lose all successful data and only get the error from the FIRST failing service.
  // This does not meet the requirement of providing partial data.
  return {
    customerId,
    profile: undefined,
    subscription: undefined,
    usage: undefined,
    errors: [{ source: 'unknown', message: error.message }],
  };
}
```

As demonstrated, `Promise.all` would immediately reject the entire summary request if even one upstream service failed. This would prevent us from collecting and returning any successfully fetched data, directly violating the requirement to "provide partial data where possible."

`Promise.allSettled`, on the other hand, allows us to inspect the outcome of each individual promise. We can then construct the `CustomerSummary` object by including the data from fulfilled promises and logging errors for rejected ones, perfectly aligning with the requirements for resilience and partial data delivery.
