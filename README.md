# Daily Backend Labs

One backend engineering challenge every morning — with a worked answer — both
generated by the Gemini API and opened as a pull request.

**Read the question, try it yourself, then read the answer.** Everything is
published so anyone can learn from it, not just the person who set it up.

The question and the answer are two separate API calls. The first writes the
problem from a production scenario; the second is handed that problem and has to
solve it. Generating both at once produces a question shaped around a convenient
answer, which is backwards — the scenario should come first and the answer
should have to deal with it.

Answers are generated, so they are occasionally confidently wrong. Every PR is
reviewed before merging, and the answer is worth reading critically rather than
copying.

## The week

| Day | Topic |
| --- | --- |
| Monday | PostgreSQL |
| Tuesday | TypeScript and Node.js |
| Wednesday | Redis and caching |
| Thursday | System design |
| Friday | AWS and cloud infrastructure |
| Saturday | Data structures and algorithms |
| Sunday | Distributed systems |

Challenges are grounded in production situations rather than puzzles — *"this
invoices query got slow at 40 million rows"* rather than *"reverse a linked
list"*. Each one states its constraints, lists concrete deliverables, and ends
with a "going further" question that probes whether the solution is understood
or just copied.

The question prompt is forbidden from including its own answer — that is the
second call's job, working only from the finished question. Both prompts are
editable: [`prompts/challenge.md`](prompts/challenge.md) and
[`prompts/solution.md`](prompts/solution.md).

The answer has to address every deliverable, show the real SQL or code rather
than describe it, name the trade-offs it accepted, and say what breaks first at
ten times the scale in the scenario.

## Layout

```
challenges/2026-08-07.md      the question, then the worked answer
prompts/challenge.md          how the question is written
prompts/solution.md           how the answer is written
scripts/generate_challenge.py the generator
solutions/2026-08-07/         optional: your own code, if you work through one
```

## Daily loop

```bash
gh pr checkout challenge/2026-08-07   # 1. take today's PR
                                      # 2. read the question, try it yourself
                                      # 3. check the answer is actually correct
gh pr merge --squash                  # 4. merge
```

Step 3 is the one that matters. A wrong answer published is worse than no
answer — fix it in the branch before merging.

## Answering a challenge that has none

**Actions → Answer a challenge → Run workflow**, give it one date or several
separated by spaces. It writes the answers and opens a single PR.

For days generated before answers were part of the daily run, and for replacing
an answer that came back wrong — it overwrites the existing one rather than
adding a second below it.

## Running it manually

```bash
export GEMINI_API_KEY=...

python scripts/generate_challenge.py                # today's topic, with answer
python scripts/generate_challenge.py --topic Kafka  # override
python scripts/generate_challenge.py --dry-run      # print, write nothing
python scripts/generate_challenge.py --list-models  # what your key supports

# answer a challenge that already exists, or redo one that came back wrong
python scripts/generate_challenge.py --answer --date 2026-08-10
```

Each full run is two API calls — one for the question, one for the answer.

Standard library only — no dependencies to install or keep updated.

If the API returns a 404, the model id has been renamed or retired. Run
`--list-models` and set the `GEMINI_MODEL` repository variable to one of the
ids it prints.

## Setup

1. Get a key at [aistudio.google.com/apikey](https://aistudio.google.com/apikey)
2. **Settings → Secrets and variables → Actions → New repository secret**
   `GEMINI_API_KEY`
3. Optionally set a repository *variable* `GEMINI_MODEL` to pin a model
4. **Actions → Daily challenge → Run workflow** to test it without waiting for
   the 09:00 schedule

The schedule is `30 3 * * *` (03:30 UTC = 09:00 IST). GitHub's cron is
best-effort and can lag under load, so treat it as "some time in the morning".

## How duplicates are prevented

Three separate guards, because the model has no memory and the workflow can be
re-run at any time:

| Risk | Guard |
| --- | --- |
| Two challenges for the same date | The generator exits if `challenges/YYYY-MM-DD.md` already exists on the default branch |
| Two PRs for the same date | The workflow checks for an existing `challenge/YYYY-MM-DD` branch — before calling the API, so a re-run costs nothing |
| **The same problem set twice on different dates** | The last 40 challenges are summarised into the prompt as a "do not repeat these" list |

The third is the one that actually matters over a year. Without it the model
would happily reissue "the invoices table got slow, design the indexes" every
few Mondays, because each run is a blank slate. Feeding the history back in is
what keeps a 365-day series varied.

That history includes challenges still sitting in unmerged PRs, not just the
ones on `main`. A skipped day never lands on disk, and skipped days are the
ones most worth not repeating — you haven't solved them yet.

## A note on what the commits mean

The generated commits are authored by `github-actions[bot]`, so the daily run
does not put anything on anyone's contribution graph by itself. What lands on
mine is the review — merging a day means I read the answer and decided it was
right. That is a smaller claim than "I solved this from scratch", and it is the
accurate one.
